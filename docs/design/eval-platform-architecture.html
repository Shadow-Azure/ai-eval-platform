1. 目标与范围

平台用于对 AI 编程 Agent 做标准化评测：管理评测数据集与用例，配置被测模型与 API Key，按「Agent 运行时 × 开发 Skill × 模型 × 资源池」的组合启动评测，实时查看进展与按数据集自定义的结果指标，并能从任意用例回看主 Agent 与子 Agent 的完整会话轨迹。

  • 账号密码登录；单租户起步，数据模型预留多租户（组织、工作区、项目三层）。
  • 数据集插件化：首期支持 SWE-bench，新增评测集只需实现数据集适配器并注册指标定义。
  • 模型与凭据集中管理，支持 MiniMax、DeepSeek、GLM、Kimi、小米 MiMo 等任意 OpenAI 兼容端点。
  • 资源池复用 GitHub Actions 自托管 Runner，Mac mini 与阿里云 Linux 机器混合接入。
  • 评测支持并发，并发度等于在线 Runner 数，可横向扩容。
  • 会话轨迹归一化后存入数据库，原始文件归档对象存储，前端支持用例级跳转查看。

2. 总体方案

平台层全部自建；评测调度复用 GitHub Actions 与自托管 Runner；评分复用 SWE-bench 官方 harness 的 Docker 评分镜像；会话轨迹的归一化语义对齐 OpenInference 与 OpenTelemetry GenAI 约定。

3. 总体架构

平台由五个部分组成：Web 前端、API 服务、调度器、数据存储、执行资源池。API 服务负责全部业务读写；调度器把一次评测拆成用例分片并触发执行、接收心跳、回收结果；执行资源池由 GitHub 仓库中的通用工作流和挂在各机器上的自托管 Runner 组成。

4. 评测执行流程

  1. 用户选择数据集版本、Agent 运行时、开发 Skill、模型凭据与资源池，提交后创建评测（eval_run），用例按分片（每片 ≤ 256）写入用例表。
  2. 调度器对每个分片调用 GitHub REST 接口发送 repository_dispatch 事件，负载携带评测编号、用例清单、回调地址与超时时间。
  3. Runner 上的 in-job 脚本拉取用例与环境定义，在沙箱内准备代码仓库，以无头模式驱动 Agent 运行时（首期 Claude Code，stream-json 输出），收集补丁与会话文件。
  4. 沙箱内运行 SWE-bench 官方评分镜像得到是否解决与测试输出；脚本上传评分报告、产物包与原始会话文件到 OSS，并回调平台上报状态与摘要指标。
  5. 平台把回调写入用例表，导入器把原始会话归一化为 session / span 记录，原始文件保留在 OSS。
  6. 调度器以回调为准更新实时进度，经 SSE 推送到前端；GitHub check-runs 接口仅用于对账。
  7. 分片结束后按数据集注册的指标定义（如解决率）聚合评测级结果，前端结果页展示。

5. 功能设计

5.1 账号与租户

账号密码登录，密码加盐哈希存储，会话使用签名令牌。数据模型按组织、工作区、项目三层设计，所有业务表带租户标识；单租户阶段只存在一条组织记录，新增租户不需要改表。

5.2 数据集管理

数据集与版本分离，版本不可变；用例存储兼容 SWE-bench 事实标准字段（实例编号、仓库、基础提交、问题描述、参考补丁、测试补丁、应通过测试、不应回退测试），数据集特有字段放 JSONB。适配器接口负责导入、浏览与执行器视图；详情页展示用例数量、预期指标与用例列表。新增评测集只需新增适配器并注册指标定义。数据集的配置流程固定为五步：

  1. 在数据集页面选择评测集类型（平台已注册的适配器，首期提供 SWE-bench）；
  2. 填写数据来源（上传数据文件或数据集地址）与版本号，发起导入；
  3. 适配器解析并校验标准字段，用例按版本批量入库，预期指标一并登记；
  4. 平台按评测任务包契约生成该版本的任务视图，环境定义、判分命令与指标映射随版本固化；
  5. 详情页立即可查用例数、预期指标与用例列表，发起评测时直接引用该版本。

5.3 模型与凭据管理

模型配置记录服务商、接口地址与模型名，统一按 OpenAI 兼容协议接入；API Key 加密存储，解密只在派发任务时进行。启动评测时可引用已有凭据，也可临时填入新凭据（只绑定本次评测）。任务下发使用平台换发的短期凭据，不落盘到 Runner 机器。

5.4 Agent 运行时与 Skill

运行时记录名称、版本与启动命令模板，首期只接 Claude Code，随后按同一适配器接口扩展 Codex、OpenCode 与 pi。开发 Skill 作为评测输入随任务下发（如挂载到 Agent 工作目录由其原生机制加载）。适配器接口固定三段：启动并流式输出事件、收集原始会话文件、归一化为统一轨迹模型。

5.5 资源池

资源池登记 Runner 元数据与标签；GitHub 按 runs-on 标签把任务路由到 Mac mini 或 Linux 机器。Runner 全部使用临时模式：接一个任务、执行、注销，由守护进程自动重装注册。Mac mini 侧重 macOS 专属用例并用 tart 虚机做一任务一隔离；Linux 机器用 Docker 沙箱承接容器类评测。承载评测的仓库必须为私有仓，Runner 机器不存任何长期凭据。资源池与接入凭证分离：凭证登记为租户级的资源连接，资源池引用连接并只保存池参数，一个连接可挂多个池；多租户时每个租户维护自己的连接，跨租户不可见。单租户阶段所有连接自动归属默认租户，机制与多租户完全一致，启用多租户时不需要迁移数据模型。

5.6 调度与实时进度

调度器把评测拆成分片并发派发，同一评测设并发组防重复触发；用例状态机为排队、运行、成功、失败、超时、取消。实时进度以 in-job 脚本心跳回调为准，超时未回调由调度器标记并触发重试策略。调度器对执行后端抽象统一接口，当前为 GitHub Actions 后端，未来可新增队列后端无损切换。

5.7 评分与结果

评分不自行实现：SWE-bench 用例交给官方 harness 评分镜像产出结构化报告，平台解析后入库。结果指标按数据集注册：每个数据集声明自己的指标与展示形态（解决率、通过率、加权总分等），用例表存指标快照，结果页按数据集渲染对应指标卡与用例明细表。

5.8 会话轨迹

归一化入库为主、原始文件归档为辅：适配器把各 Agent 原生会话（Claude Code JSONL、Codex JSONL+SQLite、OpenCode SQLite、pi 树形 JSONL）统一映射为 session / span 两层模型，属性键兼容 OpenTelemetry GenAI 与 OpenInference 约定，评测域自定义键加评测前缀。session 表用父会话标识表达主 Agent 与子 Agent 的树，span 表记录消息、工具调用与 thinking 步骤的层级、耗时与 token 细分。前端从用例行跳转到会话树再展开为 span 时间线；回放或审计时从 OSS 取原始文件。

5.9 执行隔离

评测任务一律在容器内执行，Runner 宿主机不信任任何任务代码。隔离分两层：

宿主层
Runner 宿主机（只留容器运行时，不信任任何任务代码）
第一层
任务级容器
只装 in-job 脚本与工具链，是任务在宿主机上的唯一执行入口
第二层
用例沙箱容器
Agent 与被测代码只在其中运行：非 root、只读挂载、网络按需放开

图 3　两层执行隔离（Mac mini 无 Linux 容器，用 tart 虚机替代，一任务一虚机）

两层都不落长期凭据，任务凭据由平台换发、用完即弃。用例容器需要 Docker 能力时不挂载宿主机 Docker 接口（挂载会抵消隔离），改用无 root 的 Docker 或独立的 Docker 服务容器。

5.10 评测任务包契约

平台与 eval-runner 之间通过一份通用的评测任务包解耦，新增评测数据集不需要改动 eval-runner 的任何代码。任务包固定携带四部分，落盘为五个文件，格式与 Harbor 任务格式一致：

任务包的五个文件（Harbor 兼容）

task.toml：任务名与元数据 instruction.md：给 Agent 的题面 environment/Dockerfile：环境定义 tests/test.sh：判分命令 solution/solve.sh：参考解（仅自检）

in-job 脚本的固定五步（写一次，永不改）

起沙箱→ 注入用例→ 运行判分命令→ 解析结果文件→ 回传

该布局与 Harbor 的任务格式一致，后续可直接搬用 Harbor 社区适配器。新增数据集只需要在平台侧实现数据集适配器，并把判分脚本或评分镜像作为数据集版本的一部分登记；只有契约本身演进时才需要同步 runner。SWE-bench 是该契约的第一个实现：判分命令即官方评分镜像，指标映射即解决率。

5.11 多租户资源权限

多租户启用时，资源与权限分四层管理；单租户阶段四层全部退化为默认值，不需要改表或改代码。

表 7　多租户资源权限的四层机制
层机制说明
第一层　物理隔离runner group / 仓库级 runner限定不同租户只能使用各自的执行机
第二层　逻辑归属资源池绑定工作区平台只向租户有权使用的资源池派发任务，共享池走配额模式
第三层　配额与公平调度器按租户计数并发上限超出配额的任务排队等待，防止单一租户占满全部资源
第四层　凭据与审计短期凭据按租户与操作人签发全程记录，可追溯每一次任务发起与执行

资源连接与资源池从第一天起就带租户标识：单租户时全部归属默认租户，多租户启用时按租户拆分，接入流程与数据模型都不变。

5.12 新增数据集与评测指标

新增评测集分两类工作：一次性开发在平台仓库内完成，日常运营在界面上完成。只新增指标、不新增数据集时，跳过开发部分，直接注册指标定义即可。

一次性开发（平台仓库，随版本发布）

① 实现数据集适配器：按 Harbor 任务格式生成任务目录，四方法 + 三个命令行参数 ② 注册指标定义：指标名、计算方式、展示形态、口径说明 ③ 登记进数据集类型注册表，平台其余部分不改动

日常运营（界面操作）

① 新建数据集与版本，选类型、填来源、提交号与版本号 ② 执行导入：任务包落到 OSS，查看用例数与校验失败明细 ③ 抽查用例详情与任务包，确认题面、环境、判分脚本 ④ 发起评测选该版本，结果页按注册指标自动渲染

版本标识采用三元组：来源 + 提交号或标签 + 适配器版本，同一版本可完整复现。首期只实现 SWE-bench 一个适配器，产出物与 Harbor 格式对齐；后续新增评测集优先从 Harbor 社区适配器（60+ 个，Apache-2.0）移植，保留原项目声明即可。

5.13 适配器的扩展方式

适配器读取数据集、内置转换规则、产出统一任务包；数据集仓只读引用，不需要 fork 或改动。转换规则分三层：声明式映射（纯文本问答类，填配置即可）、适配器代码（需要容器与测试的评测集族，写一次复用）、社区适配器移植（Harbor 已提供六十多个）。

后续新增评测集按与现有适配器的相似度分三种情况，只有第三种需要写新代码，且都是新增而不是修改：

表 12　新增评测集的三种情况
情况例子工作量
同 schema 的衍生集SWE-bench Lite、Verified、Multimodal、Multilingual、SWE-rebench不写代码，登记新版本（来源、提交号、适配器版本）

7. 并发能力

并发模型简明：一个 Runner 同时只执行一个任务，平台并发度 = 在线 Runner 数。

  • Mac mini 建议注册 2 至 4 个临时 Runner 实例，以 tart 虚机隔离，数量受 CPU 与内存约束。
  • 更高并发时在阿里云追加 Linux Runner 横向扩容；单一评测批次用 job matrix 一次承载不超过 256 个用例。
  • 没有空闲 Runner 时任务在 GitHub 侧排队：延迟不可控但不丢任务，排队上限 24 小时。
  • 并发需求超过 50~100、或需要秒级确定性调度时，启用调度器的队列后端演进为自研 worker + 队列，in-job 脚本保持不变。

8. 资源池的弹性供给

8.1 供给模式

资源池的算力来源抽象为可插拔的供给模式，每种模式由一个供给器实现，负责按需创建与释放执行机。首期实现自有机器注册与竞价实例两种供给器，其余模式预留同样的扩展位置：用户申请好资源后，在资源池页面选择模式、填入资源凭据与容量上限即可完成接入，不需要平台发版。

表 8　供给模式对比
模式计价特点状态
自有机器注册已有硬件，不计云资源费注册即接入、随时撤下，适合 Mac mini 与办公室机器首期实现
包年包月 ECS包年价，约为按量付费的四分之一稳定不被回收，适合常驻兜底算力预留
按量付费 ECS按秒计费，随时释放无回收风险，适合短时可预期的批次预留
竞价实例 ECS按量价的 1 至 3 折浮动可能被回收，任务需可重试，适合大规模批次首期实现
弹性容器实例 ECI按秒计费，vCPU 与内存分别计价秒级交付、跑完即停，无机器运维预留
用户自管 Runner 组用户自负平台只登记标签与心跳，不参与供给，适合多云与自建机房预留

8.2 竞价供给器的工作方式

竞价供给器监听调度队列，容量随负载伸缩；实例被回收或任务跑完即释放。竞价实例创建后有一小时保护期，之后可能因库存或市价被回收，因此被中断的任务由调度器自动重试，用例级状态机保证重跑不产生重复结果。成本约为同规格按量付费的一到三折，算力费用随实际执行时长计费，空载不产生费用。

竞价供给器的工作循环

监听调度队列→ 排队超过常驻算力→ 创建竞价实例→ 注册临时 Runner→ 执行用例→ 释放实例

实例被回收 → 调度器自动重试用例；空载时零费用。

8.3 供给器的扩展机制

新增供给模式只需三步：实现供给器接口（创建、释放、健康查询三个动作），在平台注册模式定义与配置表单，用户即可申请资源并接入资源池。调度器只面向资源池的标签与容量调度，不感知供给模式的差异；实例被回收、机器掉线等异常统一由重试与重装流程兜底。这套机制同样覆盖未来的执行后端切换：自研 worker 加队列落地时，供给器接口保持不变，只是执行机的注册对象从 GitHub Runner 换成平台 worker。

8.4 资源池的配置流程

资源池的配置统一走「先建连接、再建池」两步。连接是某个云账号的接入凭证，租户级、可复用；资源池引用连接并只保存池参数，一个连接可挂多个池。以竞价弹性资源池为例：

竞价弹性资源池的配置步骤

阿里云侧：创建 RAM 访问密钥（授予竞价实例创建与释放权限）→ 平台「资源连接」：填密钥并做只读验证→ 「资源池」：选连接与竞价模式，填地域、交换机、规格、容量与池上限→ 供给器接管，资源池页实时显示容量与当日花费

排队任务超过常驻算力 → 自动创建实例并注册为带池标签的临时 Runner；任务完成或实例被回收即释放。自有机器模式更简单：运行一键注册脚本即接入。两种模式的差异只在供给器内部，对调度与评测链路完全透明。

8.5 新增资源池（以阿里云竞价池为例）

新增资源池分两段：先建资源连接，再建资源池。首次接入约需十五分钟，之后复用连接，新增一个池只需填池参数。单租户阶段连接自动归属默认租户，多租户启用后各租户在自己可见的连接下建池，流程不变。

资源连接（一次性，租户级，约 10 分钟）

① 开通 ECS，确认竞价权限与可用容量，选定地域与可用区 ② 创建只授创建/释放/查询权限的访问密钥 ③ 「资源连接」填密钥，平台只读验证：列区域、查容量、检查权限范围 ④ 准备交换机与安全组，只放行必要流量；制作预装 Runner 与评测环境的基础镜像

资源池（可复用同一连接，约 5 分钟）

① 新建资源池，选刚建的连接与竞价实例模式 ② 填地域、可用区、交换机、规格、系统盘、并发与池上限、出价上限 ③ 保存，供给器生成注册配置并准备镜像，状态变为就绪

验证与观测

测试供给：开一台实例并注册临时 Runner→ 跑 5~10 个用例的小批量评测→ 确认任务落到该池、结果正常回传→ 日常看容量、在线执行机与当日花费

被中断的实例触发用例自动重试，无需人工介入。

体验档的自建与迁移

体验档把 PostgreSQL 与 Redis 作为容器跑在同一台平台 ECS 上，与业务服务同属一份 Compose 编排，省掉云数据库开支；代价是没有高可用，需要为云盘配置每日快照，并在 Compose 中增加定时备份任务，把数据库导出文件上传到对象存储。迁往云数据库时只需修改连接串，迁移脚本与表结构不变，低峰期即可完成切换；当评测数据增长到几十万行、平台需要多人同时使用、或不再想自行管理备份时，即应切换到推荐档的云数据库。

更便宜的选择

平台机可关注轻量应用服务器与经济型 e 的限时活动（2 核 2G 低至 ¥38~99/年），足以承载整个体验档；数据库可关注 RDS PostgreSQL Serverless，按秒计费并支持自动启停，空闲时只收存储费，契合评测平台时忙时闲的负载；Redis 平台用量很小，托管入门版也要约 ¥60~100/月，体验档与成长期初期都建议自建，内存占用可忽略。

9.3 评测成本模型

一次评测的成本由模型费与算力费两部分构成，模型费通常占九成以上。模型费按 token 计，算力费按机时计；两者都随用例数与单例复杂度线性增长，并发只缩短等待时间、不改变总成本。

模型费 ≈ 90%
算力 ≈ 10%

按标准档估算：单例模型费约 ¥0.28，单例算力费约 ¥0.033。

模型费以 deepseek-v4.1-flash 为例，价格按峰谷分时：闲时缓存命中输入 ¥0.02/百万 token、未命中 ¥1/百万 token、输出 ¥4/百万 token，高峰时段翻倍。编程 Agent 每例的 token 量取决于用例复杂度，按轻量、标准、重度三档估算，缓存命中率按七成计，单例模型费见表 10。

11. 操作场景与数据流转

目标态下有六类高频操作场景，按「谁操作、数据怎么流转」逐场景说明。下图先总览六个场景的数据走向，后面逐场景展开。

11.1 配置管理

登录→ 签发令牌→ 凭据加密入库→ 适配器解析数据集→ 用例按版本入库

页面只回显凭据掩码；数据集特有字段随版本走 JSONB。

11.2 发起评测

选择组合→ 创建评测→ 用例分片→ dispatch→ Runner 拉任务包→ 沙箱驱动 Agent

任务包含短期凭据与 Skill 文件；Agent 产出补丁后进入评分。

11.3 观测进展

心跳回调→ 更新用例表→ Redis 发布→ SSE 推送→ 前端进度刷新

只传状态与摘要；评分报告、产物包等大文件直传 OSS，不经接口。

11.4 查看结果

分片完成→ 按指标定义聚合→ 指标卡＋ 用例明细表

用例行级指标以快照入库，与评测当时的口径一致。

11.5 轨迹回放

点击用例→ 查出会话树→ 展开 span 时间线； OSS 限时下载原始文件

会话树的父子关系对应主 Agent 与子 Agent。

11.6 部署运维

合入 main→ 测试＋构建镜像→ 数据库迁移（阻断点）→ 滚动更新＋健康检查； Runner 心跳上报

迁移失败即回滚；掉线 Runner 自动进入待重装流程。

10.1 配置管理场景

管理员登录后录入模型凭据、导入数据集、登记资源池。浏览器把账号密码提交给 API 服务，校验通过后签发令牌，后续请求都携带令牌；模型凭据加密后存入数据库，页面只回显掩码。导入数据集时，上传数据文件或填写数据集地址，数据集适配器把内容解析为标准字段，用例按版本批量入库，预期指标一并登记。

10.2 发起评测场景

评测负责人在发起页选择数据集版本、Agent 运行时、开发 Skill、模型凭据与资源池，提交后 API 服务创建一次评测并把用例按分片写入用例表；调度器逐片调用调度接口，GitHub 把任务派发到带匹配标签的 Runner；Runner 上的脚本拉取任务包（用例定义、短期凭据、Skill 文件），在沙箱内驱动 Agent 运行直至产出补丁。

10.3 观测进展场景

执行期间 Runner 脚本按心跳周期回调平台，上报用例状态与摘要指标；API 服务更新用例表后通过 Redis 发布变更，经服务端实时通道推送到浏览器，前端进度条与用例状态随之刷新。此场景只传输状态与摘要，评分报告与产物包等大文件不经由接口传输，直接上传对象存储。

10.4 查看结果场景

一个分片全部完成后，调度器按数据集注册的指标定义聚合评测级结果，结果页渲染指标卡与用例明细表；用例行级指标来自评分报告的解析结果，以指标快照形式存于用例表，与评测当时的口径保持一致。

10.5 轨迹回放场景

用户在用例明细中点击某条用例，API 服务按会话标识查出会话树（父子关系对应主 Agent 与子 Agent），前端展开为 span 时间线；需要核对原始数据时，API 服务向对象存储申请限时下载地址，浏览器凭该地址直接下载原始会话文件。

10.6 部署运维场景

代码合入 main 后流水线自动执行：测试与文档门禁，构建镜像推送镜像仓库，在数据库执行迁移脚本（失败即阻断），经 SSH 滚动更新平台机的容器服务并做健康检查；Runner 机器上的守护进程定期向平台上报心跳，资源池页面据此展示在线状态，掉线的 Runner 自动进入待重装流程。
