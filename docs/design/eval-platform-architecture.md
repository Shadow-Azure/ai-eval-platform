# 评测平台架构方案

[English](eval-platform-architecture.en.md) | 中文

本文是已定稿的架构设计，覆盖功能范围、总体结构、执行流程、数据模型、并发能力、阿里云部署与 CI/CD，对应需求共十一条。调研过程与候选方案对比见仓库 `research/` 目录，正式文档只记录定稿结论。

## 1. 目标与范围

平台用于对 AI 编程 Agent 做标准化评测：管理评测数据集与用例，配置被测模型与 API Key，按「Agent 运行时 × Agent 资产源 × 模型 × 资源池」的组合启动评测，实时查看进展与按数据集自定义的结果指标，并能从任意用例回看主 Agent 与子 Agent 的完整会话轨迹。

- 账号密码登录；单租户起步，数据模型预留多租户（组织、工作区、项目三层）。
- 数据集插件化：首期支持 SWE-bench，新增评测集只需实现数据集适配器并注册指标定义。
- 模型与凭据集中管理，支持 MiniMax、DeepSeek、GLM、Kimi、小米 MiMo 等任意 OpenAI 兼容端点。
- 资源池复用 GitHub Actions 自托管 Runner，Mac mini 与阿里云 Linux 机器混合接入。
- 评测支持并发，并发度等于在线 Runner 数，可横向扩容。
- 会话轨迹归一化后存入数据库，原始文件归档对象存储，前端支持用例级跳转查看。

## 2. 总体方案

平台层全部自建；评测调度复用 GitHub Actions 与自托管 Runner；评分复用 SWE-bench 官方 harness 的 Docker 评分镜像；会话轨迹的归一化语义对齐 OpenInference 与 OpenTelemetry GenAI 约定。技术选型见表 1。

## 3. 总体架构

平台由五个部分组成：Web 前端、API 服务、调度器、数据存储、执行资源池。API 服务负责全部业务读写；调度器负责把一次评测拆成用例分片并触发执行、接收心跳、回收结果；执行资源池由 GitHub 仓库中的通用工作流和挂在各机器上的自托管 Runner 组成。架构见图 1。

## 4. 评测执行流程

1. 用户在平台选择数据集版本、Agent 运行时、模型凭据与资源池，可选地选择 Agent 资产源及可编辑 Ref；提交后创建一次评测（eval_run），用例按分片大小不超过 256 写入评测用例表。
2. 调度器对每个分片调用 GitHub REST 接口发送 repository_dispatch 事件，负载携带评测编号、分片内用例清单、回调地址与超时时间。
3. Runner 接到任务后启动 in-job runner 脚本：拉取用例与环境定义，在沙箱内准备代码仓库，以无头模式驱动 Agent 运行时（首期 Claude Code，使用 stream-json 输出），完成后收集模型产出的补丁与会话文件。
4. 沙箱内运行 SWE-bench 官方评分镜像得到该用例是否解决及测试输出，in-job 脚本把评分报告、产物包与原始会话文件上传 OSS，并调用平台回调接口上报用例状态与摘要指标。
5. 平台把回调内容写入评测用例表，同时由导入器把原始会话文件归一化为会话与 span 记录，原始文件保留在 OSS。
6. 调度器以回调为准更新实时进度，经 SSE 推送到前端；GitHub 检查运行接口只用于对账。
7. 一个分片全部结束后平台聚合指标：按数据集注册的指标定义（如解决率）计算评测级结果，前端结果页展示。

## 5. 功能设计

### 5.1 账号与租户

账号密码登录，密码加盐哈希存储，会话使用签名令牌。数据模型按组织、工作区、项目三层设计，所有业务表带租户标识；单租户阶段只存在一条组织记录，新增租户不需要改表。

### 5.2 数据集管理

数据集与数据集版本分离，版本不可变；用例存储兼容 SWE-bench 事实标准字段（实例编号、仓库、基础提交、问题描述、参考补丁、测试补丁、应通过测试、不应回退测试），数据集特有字段放 JSONB。数据集适配器接口负责导入、浏览与交付执行器所需视图；数据集详情页展示用例数量、预期指标与用例列表。新增评测集只需新增适配器并注册指标定义，平台其他部分不变。数据集的配置流程固定为五步：

1. 在数据集页面选择评测集类型，即平台已注册的数据集适配器，首期提供 SWE-bench。
2. 填写数据来源（上传数据文件或数据集地址）与版本号，发起导入。
3. 适配器解析并校验标准字段，用例按版本批量入库，预期指标一并登记。
4. 平台按评测任务包契约生成该版本的任务视图，环境定义、判分命令与指标映射随版本固化。
5. 数据集详情页立即可查用例数量、预期指标与用例列表，发起评测时直接引用该版本。

数据集版本同时登记执行与评分镜像 digest：导入时可覆盖平台默认值，未填写时采用平台默认配置；发起评测选定版本后自动带出，仍可按次覆盖。

### 5.3 模型与凭据管理

模型配置记录服务商、接口地址与模型名，统一按 OpenAI 兼容协议接入；API Key 加密存储，解密只在派发任务时进行。启动评测时可引用已有凭据，也可临时填入新凭据，临时凭据只绑定本次评测。任务下发到 Runner 时使用平台换发的短期凭据，不落盘到 Runner 机器。

### 5.4 Agent 运行时与资产

Agent 运行时记录名称、版本与启动命令模板，首期只接 Claude Code，随后按同一适配器接口扩展 Codex、OpenCode 与 pi。Agent 资产作为评测输入随任务下发，由 Runtime 适配器把所需 Skill、Command 与 Subagent 映射到工作目录并交给原生机制加载。适配器接口固定三段：启动并流式输出事件、收集原始会话文件、归一化为统一轨迹模型。

Skill、Command 与 Subagent 统一归入可配置的 Agent 资产源。资产源绑定 Git 仓库、租户级源码连接、默认 Ref、扫描路径、选择方式和资产类型；选择方式支持扫描目录下全部资产或仅指定路径。Skill 以包含 `SKILL.md` 的目录为识别单位，Command 与 Subagent 由目标 Runtime 适配器按原生文件格式识别；无法可靠识别时必须由用户显式指定类型，不能仅凭扩展名猜测。

发起评测时可选地选择资产源；选择后 Ref 输入框默认填入资产源的默认 Ref，用户可以改成其他分支、tag 或 commit，未选择资产源时只使用 Runtime 内置能力。提交后平台把 `requested_ref` 解析为 `resolved_commit`，校验所选权限下的路径和资产在树中的可用性，冻结资产清单、内容摘要与运行依赖，并把仅包含所选资产的不可变包写入 OSS。一次评测的所有分片使用同一个快照；分支后续提交、移动或删除不会改变已启动评测，Runner 也不需要在执行时重新访问 Git。

资产源记录解析后的 commit、tree 摘要、配置选择、所有权和审计人；评测记录通过资产快照而非可变仓库引用追溯输入。Superpowers 可作为以 `skills/` 为扫描根目录的完整资产源读取，OpenSpec 的 `skills/` 是 Skill 来源，其 Command 由 `openspec init/update` 在目标 Runtime 中生成，因此这类仓库必须在资产源中声明运行时前置步骤。Runtime 映射由适配器完成：Claude Code 使用 `.claude/` 资产目录，Codex、OpenCode 与 pi 共享 `.agents/` Skill 目录，Command 与 Subagent 继续按各 Runtime 的原生格式生成或安装。

### 5.5 资源池

资源池登记自托管 Runner 的元数据与标签；GitHub 按 runs-on 标签把任务路由到 Mac mini 或 Linux 机器。Runner 全部使用临时模式：接一个任务、执行、注销，由机器上的守护进程自动重装注册，避免长期驻留凭据与状态。Mac mini 侧重 macOS 专属用例并用 tart 虚机做一任务一隔离；Linux 机器用 Docker 沙箱承接容器类评测。私密性要求：承载评测的仓库必须为私有仓，Runner 机器不存放任何长期凭据。资源池与接入凭证分离：凭证登记为租户级的资源连接，资源池引用连接并只保存池参数，一个连接可挂多个池；多租户时每个租户维护自己的连接，跨租户不可见。单租户阶段所有连接自动归属默认租户，机制与多租户完全一致，启用多租户时不需要迁移数据模型。

资源连接与供给模式按能力约束组合，不是可以自由搭配的两个下拉项。资源连接记录供应商、区域与能力清单，供给器声明所需的连接能力；资源池创建界面先选择连接，再只启用与该连接兼容的供给模式，后端在调用供给器前再次校验。例如 GitHub 私有 Runner 连接只能使用自有机器注册或 Runner 组，阿里云竞价实例必须引用具备 ECS 创建权限的阿里云连接；不兼容请求返回 `connection_provider_mismatch`，不创建资源池，也不进入实例创建阶段。兼容关系见表 8a。

表 8a 资源连接与供给模式兼容关系

| 资源连接 | 允许的供给模式 | 典型不兼容组合 |
|---|---|---|
| GitHub 私有 Runner | 自有机器注册、用户自管 Runner 组 | 竞价、按量或包年包月 ECS；连接不具备云厂商 API 权限 |
| 阿里云 ECS | 包年包月 ECS、按量付费 ECS、竞价实例 ECS | 自有机器注册、用户自管 Runner 组；由 GitHub Runner 连接负责 |
| 阿里云 ECI | 弹性容器实例 ECI | ECS 竞价与自有机器注册；由对应连接和供给器负责 |

### 5.6 调度与实时进度

调度器把评测拆成分片并发派发，同一评测设并发组防止重复触发；用例状态机为排队、运行、成功、失败、超时、取消。实时进度以 in-job 脚本心跳回调为准，超时未回调由调度器标记并触发重试策略。调度器对执行后端抽象出统一接口，当前实现为 GitHub Actions 后端，未来可新增队列后端而无损切换。

### 5.7 评分与结果

评分不自行实现，SWE-bench 用例交给官方 harness 的评分镜像产出结构化报告，平台解析后入库。结果指标按数据集注册：每个数据集声明自己的指标定义与展示形态（解决率、通过率、加权总分等），评测用例表存原始指标快照，结果页按数据集渲染对应指标卡与用例明细表。

### 5.8 会话轨迹

会话轨迹采用归一化入库为主、原始文件归档为辅：适配器把各 Agent 的原生会话（Claude Code 的 JSONL、Codex 的 JSONL 加 SQLite、OpenCode 的 SQLite、pi 的树形 JSONL）统一映射为会话与 span 两层模型，属性键兼容 OpenTelemetry GenAI 与 OpenInference 约定，评测域自定义键加评测前缀。会话表用父会话标识表达主 Agent 与子 Agent 的树，span 表记录消息、工具调用与 thinking 步骤的层级、耗时与 token 细分。前端从评测用例行跳转到会话树，再展开为 span 时间线；需要回放或审计时从 OSS 取原始文件。

### 5.9 执行隔离

评测任务一律在容器内执行，Runner 宿主机不信任任何任务代码。隔离分两层：第一层是工作流的任务级容器，由 GitHub Actions 原生的容器配置承载，只装载 in-job 脚本与工具链，是任务在宿主机上的唯一执行入口；第二层是用例沙箱容器，按用例的环境定义启动，Agent 与被测代码只在其中运行，容器以非 root 用户启动、文件系统只读挂载、网络按需放开。两层都不落长期凭据，任务凭据由平台换发、用完即弃。用例容器需要 Docker 能力时不挂载宿主机 Docker 接口（挂载会抵消隔离），改用无 root 的 Docker 或独立的 Docker 服务容器。Mac mini 上没有 Linux 容器，其隔离层用 tart 虚机实现，一任务一虚机，隔离级别与两层容器模型等价。

### 5.10 评测任务包契约

平台与 eval-runner 之间通过一份通用的评测任务包解耦，新增评测数据集不需要改动 eval-runner 的任何代码。任务包固定携带四部分：用例内容、环境定义、判分命令与指标映射，落盘为五个文件：task.toml 记录任务名与元数据，instruction.md 是题面，environment/Dockerfile 定义环境，tests/test.sh 是判分命令，solution/solve.sh 是参考解、仅用于自检。该布局与 Harbor 的任务格式一致，后续可直接搬用 Harbor 社区适配器。in-job 脚本只认契约、不认数据集，按固定顺序执行起沙箱、注入用例、运行判分命令、解析结果文件并回传；新增数据集只需要在平台侧实现数据集适配器，并把判分脚本或评分镜像作为数据集版本的一部分登记；只有契约本身演进时才需要同步 runner。SWE-bench 是该契约的第一个实现：判分命令即官方评分镜像，指标映射即解决率。

### 5.11 多租户资源权限

多租户启用时，资源与权限分四层管理。第一层物理隔离：用 runner group 或仓库级 runner 限定不同租户只能使用各自的执行机。第二层逻辑归属：资源池记录绑定工作区，平台只向租户有权使用的资源池派发任务，共享池走配额模式。第三层配额与公平：调度器按租户统计并发上限，超出配额的任务排队等待，防止单一租户占满全部资源。第四层凭据与审计：短期凭据按租户与操作人签发并全程记录，可追溯每一次任务发起与执行。单租户阶段四层全部退化为默认值，不需要改表或改代码。资源连接与资源池从第一天起就带租户标识：单租户时全部归属默认租户，多租户启用时按租户拆分，接入流程与数据模型都不变。

### 5.12 新增数据集与评测指标

新增评测集分两类工作：一次性开发在平台仓库内完成，日常运营在界面上完成。只新增指标、不新增数据集时，跳过开发部分，直接注册指标定义即可。

一次性开发（平台仓库，随版本发布）：

1. 实现数据集适配器，按 Harbor 任务格式把外部评测集转换成任务目录，固定四个方法：解析来源、校验字段、批量导入、生成任务视图，并支持输出目录、条数限制与指定用例三个命令行参数。
2. 注册指标定义：指标名、计算方式（如解决数除以提交数）、展示形态（指标卡、明细表或分布图）、口径说明。
3. 在数据集类型注册表登记适配器与指标定义，完成后平台其余部分不需要改动。

数据集版本用「来源 + 提交号或标签 + 适配器版本」三元组标识，同一版本可完整复现。首期只实现 SWE-bench 一个适配器，产出物与 Harbor 任务格式对齐；后续新增评测集可优先从 Harbor 社区适配器移植，保留原项目声明即可。

日常运营（界面操作）：

1. 新建数据集与版本，选择评测集类型，填写来源、提交号与版本号。
2. 执行导入：适配器生成任务包并落到对象存储，页面显示用例数量与校验失败明细。
3. 抽查用例详情与生成的任务包，确认题面、环境与判分脚本无误。
4. 发起评测时选择该版本，结果页按注册的指标自动渲染。

### 5.13 适配器的扩展方式

适配器读取数据集、内置转换规则、产出统一任务包；数据集仓只读引用，不需要 fork 或改动。转换规则分三层：声明式映射适合纯文本问答类评测集，填配置即可；适配器代码适合需要容器与测试的评测集族，写一次复用；社区适配器可移植，Harbor 已提供六十多个（Apache-2.0）。

后续新增评测集按与现有适配器的相似度分三种情况，只有第三种需要写新代码，且都是新增而不是修改：

| 情况 | 例子 | 工作量 |
|---|---|---|
| 同 schema 的衍生集 | SWE-bench Lite、Verified、Multimodal、Multilingual、SWE-rebench | 不写代码，登记新版本（来源、提交号、适配器版本） |
| 同族但字段有差异 | multi-swe-bench 等 | 加配置档，或用薄子类覆盖单个方法 |
| 完全不同的形态 | Terminal-Bench、GAIA、OSWorld | 新增适配器包并注册，可优先移植 Harbor 适配器；已有适配器与执行器不动 |

只有当上游数据格式变化或适配器存在缺陷时才需要修改已有适配器代码，这属于维护：升级适配器版本并重跑校验。扩展的判断标准始终是：契约层稳定（五文件任务包）、适配器层只增不改、执行层完全无感。

## 7. 并发能力

并发模型简明：一个 Runner 同时只执行一个任务，平台并发度等于在线 Runner 数。Mac mini 建议注册 2 至 4 个临时 Runner 实例，以 tart 虚机隔离，数量受机器 CPU 与内存约束；需要更高并发时在阿里云增加 Linux Runner 横向扩容，单一评测批次用 job matrix 一次承载不超过 256 个用例。需要说明的边界：没有空闲 Runner 时任务在 GitHub 侧排队，延迟不可控但不丢任务；排队上限二十四小时。当并发需求超过 50 至 100，或出现秒级确定性调度要求时，启用调度器的队列后端演进为自研 worker 加队列，in-job 脚本保持不变。

## 8. 资源池的弹性供给

### 8.1 供给模式

资源池的算力来源抽象为可插拔的供给模式，每种模式由一个供给器实现，负责按需创建与释放执行机。首期实现自有机器注册与竞价实例两种供给器，其余模式预留同样的扩展位置：用户申请好资源后，在资源池页面选择模式、填入资源凭据与容量上限即可完成接入，不需要平台发版。各模式的特点见表 8。

表 8 供给模式对比

| 模式 | 计价 | 特点 | 状态 |
|---|---|---|---|
| 自有机器注册 | 已有硬件，不计云资源费 | 注册即接入、随时撤下，适合 Mac mini 与办公室机器 | 首期实现 |
| 包年包月 ECS | 包年价，约为按量付费的四分之一 | 稳定不被回收，适合常驻兜底算力 | 预留 |
| 按量付费 ECS | 按秒计费，随时释放 | 无回收风险，适合短时可预期的批次 | 预留 |
| 竞价实例 ECS | 按量价的 1 至 3 折浮动 | 可能被回收，任务需可重试，适合大规模批次 | 首期实现 |
| 弹性容器实例 ECI | 按秒计费，vCPU 与内存分别计价 | 秒级交付、跑完即停，无机器运维 | 预留 |
| 用户自管 Runner 组 | 用户自负 | 平台只登记标签与心跳，不参与供给，适合多云与自建机房 | 预留 |

### 8.2 竞价供给器的工作方式

竞价供给器监听调度队列：排队任务超过常驻算力时自动创建竞价实例、注册为临时 Runner 并打上资源池标签；任务跑完或实例被回收即释放，容量随负载伸缩。竞价实例创建后有一小时保护期，之后可能因库存或市价被回收，因此被中断的任务由调度器自动重试，用例级状态机保证重跑不产生重复结果。成本上竞价实例约为同规格按量付费的一到三折，算力费用随实际执行时长计费，空载时不产生费用。

### 8.3 供给器的扩展机制

新增供给模式只需三步：实现供给器接口（连接能力声明、创建、释放、健康查询四个部分），在平台注册模式定义与配置表单，用户即可申请资源并接入资源池。连接能力声明固定所需供应商与能力键，资源池保存前由 API 校验，配置界面据此启用或禁用可选模式。调度器只面向资源池的标签与容量调度，不感知供给模式的差异；实例被回收、机器掉线等异常统一由重试与重装流程兜底。这套机制同样覆盖未来的执行后端切换：自研 worker 加队列落地时，供给器接口保持不变，只是执行机的注册对象从 GitHub Runner 换成平台 worker。

### 8.4 资源池的配置流程

资源池的配置统一走「先建连接、再建池」两步。连接是某个云账号的接入凭证，租户级、可复用；资源池引用连接并只保存池参数，一个连接可挂多个池。资源池页面在连接选定后才开放兼容的供给模式：GitHub 私有 Runner 连接显示自有机器注册与 Runner 组，竞价实例等云供给模式显示为禁用并说明需要阿里云 ECS 连接；阿里云 ECS 连接则只启用包年包月、按量和竞价模式。以竞价弹性资源池为例：用户在资源连接页面填好阿里云密钥，平台做只读验证；然后在资源池页面选择该连接与竞价实例模式，填写地域、交换机、实例规格、单实例容量与池上限，供给器即开始接管；排队任务超过常驻算力时自动创建实例并注册为带资源池标签的临时 Runner，任务完成或实例被回收即释放，资源池页实时显示容量、在线执行机与当日花费。自有机器模式更简单：在机器上运行平台提供的一键注册脚本，机器即注册为临时 Runner 并打上资源池标签。两种模式的差异只在供给器内部，对调度与评测链路完整透明。

### 8.5 新增资源池（以阿里云竞价池为例）

新增资源池分两段：先建资源连接，再建资源池。首次接入约需十五分钟，之后复用连接，新增一个池只需填池参数。单租户阶段连接自动归属默认租户，多租户启用后各租户在自己可见的连接下建池，流程不变。

资源连接（一次性，租户级）：

1. 开通云服务器 ECS，确认账号具备竞价实例权限与可用容量，选定地域与可用区。
2. 创建只授竞价实例创建、释放与查询权限的访问密钥。
3. 在资源连接页面新建连接，选择供应商与区域并填入密钥，平台执行只读验证（列区域、查容量、检查权限范围），通过后连接可用。
4. 准备交换机与安全组，只放行入站必要端口与出站到平台回调地址、GitHub 与软件源的流量，并制作预装 Runner 与评测环境的基础镜像。

资源池（可复用同一连接）：

1. 在资源池页面新建资源池，选择刚建的连接与竞价实例供给模式。
2. 填写地域、可用区、交换机、实例规格、系统盘大小、单实例并发上限、池容量上限与出价上限。
3. 保存后供给器接管：生成注册配置、准备镜像，资源池状态变为就绪。

验证与观测：

1. 点测试供给，供给器创建一个实例并注册为临时 Runner，状态显示在线后自动释放。
2. 发起五到十个用例的小批量评测，确认任务落到该资源池并正常回传结果。
3. 日常在资源池页查看容量、在线执行机与当日花费；被中断的实例触发用例自动重试，不需要人工介入。

### 9.3 评测成本模型

## 11. 操作场景与数据流转

目标态下有六类高频操作场景，以下按「谁操作、数据怎么流转」逐场景说明。

### 11.1 配置管理场景

管理员登录后录入模型凭据、导入数据集、登记资源池。浏览器把账号密码提交给 API 服务，校验通过后签发令牌，后续请求都携带令牌；模型凭据加密后存入数据库，页面只回显掩码。导入数据集时，上传数据文件或填写数据集地址，数据集适配器把内容解析为标准字段，用例按版本批量入库，预期指标一并登记。

### 11.2 发起评测场景

评测负责人在发起页选择数据集版本、Agent 运行时、模型凭据与资源池，可选地选择 Agent 资产源与 Git Ref；提交后 API 服务解析 Ref 与 commit，生成不可变资产快照（未选择资产时不生成），创建一次评测并把用例按分片写入用例表；调度器逐片调用调度接口，GitHub 把任务派发到带匹配标签的 Runner；Runner 上的脚本拉取任务包（用例定义、短期凭据、资产快照），在沙箱内驱动 Agent 运行直至产出补丁。

### 11.3 观测进展场景

执行期间 Runner 脚本按心跳周期回调平台，上报用例状态与摘要指标；API 服务更新用例表后通过 Redis 发布变更，经服务端实时通道推送到浏览器，前端进度条与用例状态随之刷新。此场景只传输状态与摘要，评分报告与产物包等大文件不经由接口传输，直接上传对象存储。

### 11.4 查看结果场景

一个分片全部完成后，调度器按数据集注册的指标定义聚合评测级结果，结果页渲染指标卡与用例明细表；用例行级指标来自评分报告的解析结果，以指标快照形式存于用例表，与评测当时的口径保持一致。

### 11.5 轨迹回放场景

用户在用例明细中点击某条用例，API 服务按会话标识查出会话树（父子关系对应主 Agent 与子 Agent），前端展开为 span 时间线；需要核对原始数据时，API 服务向对象存储申请限时下载地址，浏览器凭该地址直接下载原始会话文件。

### 11.6 部署运维场景

代码合入 main 后流水线自动执行：测试与文档门禁，构建镜像推送镜像仓库，在数据库执行迁移脚本（失败即阻断），经 SSH 滚动更新平台机的容器服务并做健康检查；Runner 机器上的守护进程定期向平台上报心跳，资源池页面据此展示在线状态，掉线的 Runner 自动进入待重装流程。

## 12. 风险与演进

主要风险与对策见表 4。

表 4 风险与演进

| 风险 | 影响 | 对策 |
|---|---|---|
| GitHub 对私有仓自托管 Runner 的收费政策变化 | 资源池成本上升 | 跟踪官方公告；调度器后端抽象支持切换到自研队列 |
| 不可信代码在 Runner 上执行 | 宿主机与凭据泄露 | 一律沙箱执行，Runner 用临时模式，不存长期凭据 |
| 单一评测批次超过 256 用例 | 触发 matrix 上限 | 调度器自动拆多个分片多次派发 |
| 框架升级导致 Agent 输出格式变化 | 轨迹解析失败 | 适配器版本化，解析失败回落到原始文件展示 |
| 并发超过 Runner 承载 | 排队延迟变长 | 追加 Linux Runner；达到演进阈值切换队列后端 |
