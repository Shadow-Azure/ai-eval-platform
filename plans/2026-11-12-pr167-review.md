## §1 一页速览

一句话：把已经落库的 attempt、session、span 变成可稳定读取的轨迹 API，并把 raw 原文与大内容收口到管理员限时、可审计下载。

比喻：数据库里的轨迹像档案室，session 是案卷目录，span 是页内条目，原始 JSONL 是未经整理的底稿。PR #167 做的是前台的借阅目录和受控底稿窗口；普通成员能看整理后的目录，只有管理员能开底稿柜，且每次开柜留下登记。

| 交付块 | 结果 |
|---|---|
| attempt 首页 | 文件、parser、session 树、质量、统计 |
| span 读取 | `(ordinal,id)` keyset 分页、类型筛选、详情 |
| 安全边界 | tenant/project/case/attempt/session/span 逐层校验 |
| 角色策略 | viewer 隐藏 thinking；敏感属性始终脱敏 |
| raw 访问 | 仅管理员，300 秒 URL，写 `audit_log` |
| 性能 | 会话树批量聚合，测试锁定查询数不随 session 数增长 |

验证基线：完整 backend pytest、Node 69、runner/Node 158、docs-sync、flow、Ruff、Web build；定向 API 测试 15 passed。

## §2 架构导览

### 2.1 路由层

`backend/app/api/traces.py:46` 提供 attempt 轨迹首页，支持显式 `attempt` 或缺省取最新。`backend/app/api/traces.py:66`、`:93` 分别返回 session span 页与 span 详情。所有路由都先取当前租户默认项目，再把 tenant/project 下推给 service。

`backend/app/api/traces.py:112` 与 `:173` 是受控内容出口。管理员依赖在路由层执行，URL 只签 300 秒，成功签发后才写审计并提交。响应不返回数据库中的 object key，只返回文件/span 身份、digest、size 与地址。

### 2.2 查询与安全层

`backend/app/services/trace_queries.py:110` 和 `:145` 用 attempt、case run、eval run 的复合归属链校验 session/span。跨 tenant 与跨 project 在查不到时统一 404，避免暴露目标存在性。

`backend/app/services/trace_queries.py:34` 到 `:67` 是属性脱敏器。凭据键和凭据值被遮蔽，标准 `gen_ai.usage.input_tokens` 等 usage 属性保留。thinking 的隐藏策略在 `:185` 到 `:219` 落地。

### 2.3 稳定分页

`backend/app/services/trace_queries.py:70` 到 `:107` 编码 `session_id + ordinal + span_id` 游标。游标绑定 session，复用旧 attempt/session 游标返回 `422 invalid_cursor`。实际查询在 `:538` 后使用 keyset，而不是 offset。

### 2.4 质量标记

`backend/app/services/trace_queries.py:222` 聚合 session 的 ready/degraded/unlinked 与 orphan parent；`:248` 聚合文件状态、错误码、错误摘要和行号。时间倒置通过 SQL `case` 聚合为 `clock_comparable=false`。

## §3 数据流走查

1. 浏览器请求 `GET /eval-case-runs/:id/trace?attempt=N`，路由取得 tenant/project（`traces.py:46`）。
2. service 先校验 case run 属于该 tenant/project，再按 attempt 取文件与 session（`trace_queries.py:314`）。
3. 一次分组查询汇总每个 session 的 span 数、token、cost 和时钟异常，避免按 session 循环查详情。
4. service 根据 `parent_session_id` 组装树；未知 parent 和环状残留仍显示且标质量，不静默消失。
5. 展开 session 时请求 span 页；游标包含 session scope，排序固定为 `(ordinal,id)`。
6. 点击 span 请求详情；viewer 的 THINKING 正文为空并标 `thinking_requires_admin`。
7. 管理员请求 raw/大内容地址；平台按已登记记录签发 300 秒 GET，写审计后返回地址。

## §6 讨论点

### D1 父 span 的 session 归属

- 位置：`backend/app/services/trace_queries.py:608`
- 现象：初版只校验父 span 与当前 span 同 tenant，父 ID 来自同一 attempt 的另一个 session 时仍被视为存在。
- 问题：会把跨 session 引用伪装成合法层级，削弱 root fragment 诊断。
- 预判：父 span 必须同时同 tenant、同 session。
- 结论：已修复并加入跨 session 回归测试。

### D2 时钟可比性

- 位置：`backend/app/services/trace_queries.py:392`
- 现象：初版比较整个 session 的最早 start 与最晚 end，单条 span 的 end < start 可能被更长 span 掩盖。
- 问题：页面会错误显示时钟可比。
- 预判：必须逐 span 检测倒置并在聚合查询中计数。
- 结论：已修复，`clock_invalid > 0` 即 `clock_comparable=false`。

### D3 标准 usage 属性脱敏

- 位置：`backend/app/services/trace_queries.py:34`
- 现象：初版用宽泛 `token` 子串判定敏感键，`gen_ai.usage.input_tokens` 被遮蔽为 `[REDACTED]`。
- 问题：破坏 OTel/OpenInference 标准属性的可读性，导致用量无法诊断。
- 预判：只隐藏凭据型 token 键，保留 usage token 计数。
- 结论：已修复并加回归断言。

### D4 flow-online 侧栏关联

- 位置：GitHub PR 元数据
- 现象：首次 CI 报“PR 未关联 milestone/project”。
- 问题：代码与离线 flow 均正常，失败来自 GitHub 侧栏元数据。
- 预判：补齐 M6 milestone 与 Projects v2。
- 结论：已修复，flow-online 复跑通过。

### D5 签名 URL 响应缓存

- 位置：`backend/app/api/traces.py:112`
- 现象：初版签名地址响应没有明确禁止缓存。
- 问题：短时 URL 可能被共享缓存或浏览器历史长期保存，削弱过期边界。
- 预判：签发响应必须设置 `Cache-Control: no-store`，并避免通过 Referer 传播。
- 结论：已修复 raw 与大内容两个响应，并加回归断言。

## §9 文件级代码分析

### `backend/app/api/traces.py`

职责：把 HTTP 参数、登录/管理员角色、对象存储签名和审计组合成可测试端点。

关键依赖是现有 `require_session`/`require_admin` 与 `ObjectStore` 签名能力；本文件不重新实现鉴权或 SigV4，像前台把身份证校验和档案柜钥匙分别交给现有门卫与保险柜。

新增代码块的核心是两条权限链：

```python
tenant_id, project_id = _scope(session, context)
...
context = Depends(require_admin)
```

前一条把用户上下文收窄到默认项目；后一条保证 raw/大内容只有管理员进入。签名地址后立即写 audit 再 commit，确保成功签发的请求留有审计记录。

实现思路：读接口返回 DTO，写接口只返回短时 URL，不泄露长期凭据或 object key。已知边界：单项目 MVP 固定默认 project ID；进入多项目阶段需把 project 选择加入会话上下文。

### `backend/app/services/trace_queries.py`

职责：所有轨迹查询的领域边界与数据整形。

关键依赖是 SQLAlchemy 的事件聚合、复合归属链和现有 redaction helper。像档案管理员先核验案卷属于哪个租户，再一次取完整索引，而不是每翻一页就去仓库确认一次。

变更块分成四段：

- `_sanitize`：递归处理属性和正文，区分凭据 token 与 usage token。
- `_session_or_404` / `_span_or_404`：逐层 join，统一隐藏跨边界对象。
- `attempt_trace`：一次聚合 session 统计，再组装树和质量。
- `session_spans` / `span_detail`：keyset 分页与同 session parent 校验。

实现思路：查询入口统一 tenant/project scope，返回前统一脱敏；树形响应不依赖 ORM lazy load。已知弱点：树响应目前返回完整 session 列表，若未来单 attempt 出现数千 session，需要增加 session 级分段接口；当前单 attempt 的 Agent 树规模由设计限定。

### `backend/app/main.py`

职责：把新 router 接入统一登录门禁。

变更仅两行 import 与 `include_router`。沿用现有 console API 模式，像在已有门禁后增加一条走廊，不另开旁门。

### `tests/backend/test_trace_api.py`

职责：把接口验收变成可重复证据。

测试先构造 root/child session、span、敏感属性和 StubObjectStore，再验证：分页游标、attempt 切换、viewer 隐藏、admin 审计、跨 tenant/project、N+1 上限、parent/clock 质量。对签名的断言检查 `X-Amz-Expires=300` 与无 secret key；真实对象存储过期行为仍由 OSS 自身 SigV4 负责。
