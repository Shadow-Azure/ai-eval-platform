## §1 一页速览

一句话：把冷 spot 的安全补丁从“评测中随机自动升级”挪到“镜像构建期”，并在启动与 job 生命周期上加两道护栏。

比喻：spot 实例像一辆只在赛道上跑一圈的出租车；以前它会在载客途中自己进维修站换轮胎（unattended-upgrades → needrestart），现在维修只在发车前做，发车后车门焊死（mask timer），行驶中禁止进站（systemd-inhibit），而且发现车况要求返厂就不接单（reboot-required）。

| 交付块 | 用户可见结果 |
|---|---|
| 运行期加固 | 新冷 spot 实例不会再因自动安全更新重启 Runner |
| 镜像路径 | 依赖固化后开机不再 apt，补丁周期前移到镜像重建 |
| 兜底 | 待重启实例不接单；job 中禁止关机/休眠 |
| 诊断/冒烟 | SIGTERM 与 runner-smoke 能直接证明实例处于加固状态 |

验证基线：`npm test` 113 passed；`pytest tests/backend` 全量通过；`verify:docs`、`verify:flow`、`verify-flow --diff origin/main` 通过。

## §2 架构导览

`spot_cloud_init.py` 在 bootstrap 最前部写 APT/needrestart 配置并 mask 单元（`backend/app/services/provisioning/spot_cloud_init.py:84-108`），然后才判断镜像标记（`:117`）。stock 镜像走 `--no-upgrade` 兼容安装（`:126-135`），baked 镜像只校验依赖存在（`:117-124`）。启动 runner 前检查 `/var/run/reboot-required`（`:291-296`），Runner 单元用 `systemd-inhibit` 包住 `run.sh`（`:241-246`）。

`prepare.sh` 把同一套加固用于构建期（`infra/runner-image/prepare.sh:31-48`），安装完成后写入 `/etc/eval/runner-image-baked` 和版本 JSON（`:93-107`）；`build.sh` 通过 Cloud Assistant 执行它，需要时重启 builder，再停止并 `CreateImage`（`infra/runner-image/build.sh:133-184`）。

SIGTERM 诊断新增四个字段（`runner/lib/diagnostics.mjs:228-237`），数据来自 `systemctl is-enabled`、`apt-config dump`、needrestart 配置和镜像记录（`:160-183`）；runner-smoke 在 spot 实例上重复同一组断言（`.github/workflows/eval-shard.yml:85-113`）。

## §3 数据流走查

1. 平台创建 spot 实例，`render_cloud_init` 生成 cloud-config；脚本打成 gzip tar，JIT 单独写 0600 文件（`spot_cloud_init.py:363-386`）。
2. cloud-init 的 `runcmd` 解包并执行 bootstrap（`:387`）；bootstrap 先关自动更新，再按镜像标记选择安装路径。
3. 如果 `/var/run/reboot-required` 存在，bootstrap 退出，Runner 不注册，平台记 `register_timeout`。
4. 正常启动后 `systemd-inhibit` 持有 shutdown/sleep 锁；job 结束 Runner 退出、锁释放，`ExecStopPost` 关机（`:247-251`）。
5. 镜像构建时 `prepare.sh` 完成同一套加固并清理 cloud-init 状态；`build.sh` 校验六个单元和 reboot-required 后创建镜像并写版本记录。

## §6 讨论点

### 6.1 UserData 16 KiB 上限（已修复）

- **位置**：`spot_cloud_init.py:363-386`
- **现象**：初版把 JIT 嵌在 bootstrap 里再整体 base64，等于双重编码；按 4 KiB JIT 估算会超过 Aliyun 16 KiB 上限。
- **问题**：验收要求 16 KiB 内，且真实 JIT 比测试 fixture 大得多。
- **预判**：改为“脚本 tar.gz + JIT 单独 0600 文件”，4 KiB JIT 实测 12048 字节。
- **结论**：已按预判修复，并新增真实 JIT 长度测试（`tests/backend/test_spot_cloud_init.py:346`）。

### 6.2 固定 Runner 也会跑 runner-smoke（已修复）

- **位置**：`.github/workflows/eval-shard.yml:89-93`
- **现象**：加固检查原先对所有 runner-smoke 生效，固定 Runner 没有这套加固会误报。
- **问题**：破坏既有手动冒烟入口。
- **预判**：仅当 `RUNNER_NAME` 以 `spot-` 开头时执行检查。
- **结论**：已加条件，固定 Runner 明示跳过。

### 6.3 镜像构建未在真实云执行（保留为限制）

- **位置**：`infra/runner-image/build.sh`
- **现象**：本次没有 builder 实例与 image_id，只有 dry-run 和静态检查。
- **问题**：无法证明 `RunCommand → Reboot → CreateImage` 在真实账号一次通过。
- **预判**：合并后由运维按 README 跑一次，记录 image_id；未验证前不宣称镜像已上线。
- **结论**：保留为 PR 描述的明确限制，待运维执行。

## §9 文件级代码分析

### `spot_cloud_init.py`（M）

职责：生成冷 spot 的 cloud-config。变更核心是“先加固、再安装”，并把 JIT 与脚本分开编码。

旧代码直接 `apt-get update/install`，新代码先写 `99-eval-no-auto-upgrade`、`20auto-upgrades`、needrestart 配置并 mask 六个单元（`:84-108`），然后才进入依赖安装分支。这是把“自动更新”从运行期整体拿掉，而不是只在日志里发现它。bootstrap 末尾的 reboot-required 守卫（`:291-296`）让平台在注册超时阶段失败，而不是在 Agent 跑到一半时被重启。

JIT 从 bootstrap 的 heredoc 移到独立 `write_files`（`:380-386`），脚本三件套打成 tar.gz；`runcmd` 解包、删除 tar、chmod、执行（`:373-387`）。这样 JIT 只被 base64 一次，且不会出现在 bootstrap 的日志/文本里。

### `prepare.sh` / `build.sh`（A）

`prepare.sh` 是镜像构建期的“一次性安装”：APT 配置、mask、依赖、Node、auditd、journal，最后写 marker/JSON 并 `cloud-init clean`。`build.sh` 是它的云上驱动器，`--dry-run` 可先看步骤；`ExitCode=2` 表示需要重启，脚本重启 builder 后重跑，最后校验并创建镜像。两者都用 `set -euo pipefail`，失败不会留下“看似成功”的镜像。

### `diagnostics.mjs`（M）

新增字段直接读系统状态，不靠日志推断：`auto_update_units` 看六个单元是否 masked，`apt_periodic` 看 APT 配置，`needrestart` 看配置，`runner_image` 看镜像版本。这样下一次 SIGTERM 能第一时间区分“加固未生效”和“加固生效但另有原因”。

### `.github/workflows/eval-shard.yml`（M）

runner-smoke 增加一个 step，在 spot 实例上复跑诊断里的关键断言；固定 Runner 跳过。它把“单元测试说会这样”变成“真实实例确实这样”。

### 测试（M/A）

`test_spot_cloud_init.py` 现在解析 tar 并解出三个脚本，覆盖 16 KiB（含 4 KiB JIT）、APT/needrestart、镜像跳过、reboot-required、inhibitor；`test_aliyun_provisioner.py` 改为断言 JIT 在独立 env 文件、不在 bootstrap；`runner-image.test.mjs` 做 `bash -n`、dry-run 和 cloud-init/prepare 加固项交叉检查。
