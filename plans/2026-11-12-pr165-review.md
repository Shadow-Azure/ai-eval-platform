## §2 架构导览

### 2.1 Parser 选择与版本边界

`ClaudeCodeParser` 固定 `claude-code-2.1.278-v1`，注册在通用 parser 之后，Claude runtime 默认命中专用实现；`format_versions=("*",)` 让未知未来版本仍能进入 parser 并显式返回 degraded，而不是在 registry 选择阶段抛错。锚点：`backend/app/services/trace_parsers/claude_code.py:290`、`backend/app/services/trace_parsers/__init__.py:121`。

### 2.2 两层对象模型

Parser 输出 `ParsedSession + ParsedSpan + ParsedRelation`。Session 对应 Agent 执行上下文，Span 对应 AGENT/LLM/TOOL/MESSAGE/THINKING/CHAIN，Relation 只承载跨文件的候选证据。这个分层让单个 parser 不必知道数据库 ID，ingestion 再在事务内转换成 `trace_session/span`。锚点：`backend/app/services/trace_parsers/base.py:43`、`claude_code.py:716`。

### 2.3 跨文件关系恢复

主文件先建立 `tool_use.id -> toolUseResult.agentId`，metadata 文件再提供 `agent文件名 -> toolUseId/agentType`，子文件提供 `agentId + isSidechain`。只有 agent、tool ID 和 parent session 全部一致才建立 parent；多证据或 mismatched evidence 进入 unlinked/degraded。锚点：`claude_code.py:716`。

### 2.4 Ingestion 原子边界

普通 runtime 仍按文件隔离；Claude attempt 一旦已有 session/terminal provenance，存在待处理文件时会整 attempt staging，并原子替换派生树。这样 root 已 ready、child 稍后到达时不会用“只看本批次”的残缺证据把 child 永久标成 unlinked。锚点：`backend/app/services/trace_ingestion.py:1401`、`trace_ingestion.py:1614`。

## §3 数据流走查

1. 回调入队：Manifest 中 root、child、meta 各形成 `trace_file(pending)`。
2. 下载校验：Worker 校验 size 与 sha256，解析前不修改派生树。`trace_ingestion.py:763`。
3. Root parser：按 Agent tool call 和 tool result 建立 spawn 候选；消息按 `message.id` 合并为一个 LLM span。
4. Child parser：读取 agentId/isSidechain，以稳定 agent key 形成候选 session；不单凭同 sessionId 挂父。
5. Metadata parser：解析 toolUseId、agentType、spawnDepth；元数据文件本身不生成执行 session。
6. 跨文件解析：合并四方证据，写入 `parent_native_session_id` 或 unlinked/degraded。`claude_code.py:716`。
7. 持久化：事务内写 session/span；缺失 parent 的 span 保留 root fragment，不伪造层级。
8. 状态发布：单文件失败隔离；Claude 部分重试原子重放；聚合继续沿用 M6-02 的 failed > incomplete > degraded > ready。

## §6 讨论点

### D1 · Claude parser 的版本策略

**位置**：`backend/app/services/trace_parsers/claude_code.py:290`

**现象**：parser_version 固定到 2.1.278，同时支持 format_version `"1"`；未知格式版本会进入 parser 后 degraded。

**问题**：如果未来 CLI 版本继续沿用 format `"1"` 但改变字段语义，仅靠 format_version 不能区分。

**预判**：当前 issue 明确要求固定 Runtime 版本 fixtures，且原生记录 `version` 已写入 span 属性；后续版本应新增 parser_version，不原地改 2.1.278。

**结论**：本 PR 采用固定版本策略；真实版本族兼容由后续扩展 issue 评估。

### D2 · 大内容引用粒度

**位置**：`claude_code.py:163`

**现象**：大内容保存截断预览、原 `content_object_key` 与 locator；不复制全文到 span。

**问题**：locator 目前指向原文件中的 record/block，受控读取 API 仍需在 #93 提供 range 解释。

**预判**：元数据层已避免全文入库，符合当前边界；分片读取和权限审计归 #93。

**结论**：本 PR 只建立受控引用，不提前实现 raw API。

### D3 · Claude attempt 原子重放

**位置**：`backend/app/services/trace_ingestion.py:1401`

**现象**：存在已有 Claude 派生树时，后续 pending 文件会触发整 attempt staging。

**问题**：重放成本高于单文件替换，但换来跨文件证据一致性。

**预判**：Claude 文件数量有限且关系正确性优先；parser upgrade 已有同样原子策略。

**结论**：接受整 attempt 重放成本，避免部分证据永久 unlinked。

## §9 文件级代码分析

### `backend/app/services/trace_parsers/claude_code.py`（A）

职责：解析 Claude Code 2.1.278 原生 JSONL/meta，输出统一 session/span/relation。

关键依赖：仅标准库 JSON、datetime、Decimal 与仓库内脱敏模块；无网络和框架运行时依赖。

变更代码块分析：

- `_content_block_spans`：把 thinking/text/tool_use/tool_result 变成稳定 native ID 的 span，工具调用和结果使用 call ID 关联；大预览外置。
- `_parse_session`：先按 record UUID 去重，再按 `message.id` 合并 usage；`parentUuid` 只决定 span parent；子文件关系先标记 derived candidate。
- `_parse_metadata`：提取 toolUseId/agentType/spawnDepth，不伪造 session。
- `resolve_cross_file_relations`：合并 spawn 与 metadata，校验 tool ID、parent session 和歧义；成功写 authoritative evidence，失败写 unlinked/degraded。

实现思路：先证据、后树；先归一化、后数据库 ID；无法证明就不猜测。

检视发现：无未决问题；unknown、重复 tool、parent mismatch 已在本次修复并补测。

### `backend/app/services/trace_ingestion.py`（M）

职责：在既有幂等 ingestion 上增加跨文件关系解析和 Claude 原子重放。

变更代码块分析：

- `_resolve_batch_relations`：仅对本次 staging 的可解析文件统一跑关系 resolver，并把 parser 更新后的 degraded 状态回写 staging。
- `claude_cross_file`：已有 provenance 时把 Claude pending 重试升级为整 attempt staging。
- `ingest_trace_file`：Claude 单文件入口委托整 attempt；unknown/degraded 无 session 时保留文件状态而不是误判 failed。

实现思路：文件下载继续隔离，Claude 关系提交必须整体一致。

检视发现：无未决问题；原子重放和 unknown degraded 已有测试。
