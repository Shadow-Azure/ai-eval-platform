## §2 架构导览

标签解析是“地址解析器”：池配置记录任务应该找哪类机器，GitHub Actions 再用 `runs_on` 匹配实际 Runner。`pool_runner_labels()` 是 dispatch 和 spot registration 共用的唯一解析入口，避免两边各写一套规则。

历史固定池的 `{"kind":"fixed"}` 是身份元数据，和 Runner 能力标签不是同一种东西。修复在选择标签前先排除这个精确历史形态，再从 `instance_config_json` / `labels_json` 中读取显式标签，最后回退到默认固定 Runner 标签。

`ensure_fixed_pool()` 是系统池的生产者。它过去写历史占位值；现在新池直接写 `{"runs_on":["self-hosted","linux","eval"]}`，从源头阻止新错误数据产生。

## §3 数据流走查

```text
ResourcePool.labels_json
  → pool_runner_labels()
  → dispatch client_payload.runs_on
  → manifest.runs_on
  → GitHub matrix execute.runs_on
  → fixed-linux-eval pickup
```

1. `ensure_fixed_pool()` 新建池写入显式 `runs_on`。
2. `build_case_dispatches()` 通过 `run_runs_on()` 调用统一解析器。
3. 同一组 `runs_on` 同时写入 dispatch 和 manifest，二者不会漂移。
4. GitHub Actions 以 `self-hosted/linux/eval` 匹配 fixed-linux-eval。
5. 生产新评测从 `queued` 进入 `running`，证明标签链闭合。

## §6 讨论点

### 6.1 固定池映射同时含 `kind` 与 console 标签

- 位置：`backend/app/services/runner_labels.py:77`
- 现象：本次只排除精确的 `{"kind":"fixed"}`；若未来同一映射同时包含 `kind` 和 `{label:true}`，仍可能把 `kind` 纳入标签。
- 问题：历史上控制台保存标签时会替换整个映射，当前生产数据没有这种混合形态，因此没有实际故障。
- 预判：不阻塞本 issue；若控制台未来改为合并 metadata 与 labels，应统一过滤 provider metadata key。
- 结论：✅ 2026-11-12 判定为无实害的后续加固，不在本 issue 扩大范围。

### 6.2 容器内 Claude 原生文件宿主不可读

- 位置：`runner/scripts/real-task.mjs` 容器删除与宿主 trace capture 之间
- 现象：生产复测 job 已由 fixed Runner 接单，但评分阶段读取 `.runtime-home/.claude`、创建 `trace/diagnostics` 时出现 `EACCES`。
- 问题：Claude 生成的受限目录和文件由容器用户持有，宿主进程无法遍历；标签修复本身有效，但完整执行被另一个权限边界阻断。
- 预判：在删除容器前由容器内 root 对 `/testbed` 恢复 `a+rwX` 最小且直接；用 mode 000 的 fake Docker fixture 可稳定复现。
- 结论：✅ 2026-11-12 本分支已按 TDD 修复，待合并部署后用新固定池评测复测。

## §9 文件级代码分析

### `backend/app/services/runner_labels.py`（M）

职责：把池配置转换成 shard 的唯一 `runs_on` 列表。

关键依赖：SQLAlchemy `ResourcePool` 只提供配置数据；解析本身是纯函数，适合单测。

旧代码：

```python
labels = _labels(pool.labels_json)
```

新代码：

```python
if pool.provisioning_mode == "fixed" and pool.labels_json == LEGACY_FIXED_LABELS:
    labels = []
else:
    labels = _labels(pool.labels_json)
```

这在做什么：把历史固定池的 provider 标记从“标签候选”中剔除；没有可用标签时落到统一默认值。

为什么这么写：精确匹配最小化对其他池形态的影响，并保持显式 `runs_on` / `labels` 的优先级。

实现思路：先读显式标签 → 排除已知历史标记 → 再回退默认值。

检视发现：精确匹配边界清楚；mixed mapping 已记录为无当前实害的后续加固。

### `backend/app/services/runners.py`（M）

职责：幂等创建系统固定池。

旧代码：

```python
labels_json={"kind": "fixed"}
```

新代码：

```python
labels_json={"runs_on": list(DEFAULT_RUNS_ON)}
```

这在做什么：新池直接存可执行标签，而不是身份占位。

为什么这么写：从生产者修复坏数据来源；常量复用避免与 workflow 默认值漂移。

实现思路：创建时冻结显式标签，读取时仍兼容历史数据。

检视发现：无额外发现。
