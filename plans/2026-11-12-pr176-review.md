## §1 一页速览

一句话：终端回调原本拿的是“2 号票/3 号票”，但心跳 sidecar 已经把这两张票反复用掉了；修复后终端事件拿一组远后方的专用票，确保顺序始终在心跳之后。

| 交付块 | 结果 |

| 生产现象 | completion/failed 回调 HTTP 500，数据库报 `uq_eval_event_case_attempt_sequence` 冲突 |
| 根因 | heartbeat 从 2 递增，terminal 固定 2/3 |
| 修复 | completion=1000000，failure=1000001 |
| 数据恢复 | Reconciler 已把本用例恢复为 resolved，trace ready |
| 回归 | 旧编号两项失败，新编号 4 项 heartbeat integration 全通过 |

## §2 架构导览

`real-task` 在 Agent 执行期间被同步 Docker 调用阻塞，因此 heartbeat 由独立 sidecar 进程递增 sequence。主进程恢复后无法直接从子进程内存读取最后编号，所以终端事件采用明确保留区间，保证大于实际 case timeout 内可能产生的心跳数，同时不改变平台状态机。

平台唯一键 `(case_run_id, attempt_no, sequence)` 仍是最终幂等底线；这次修复让 Runner 发送端遵守该契约，而不是放宽数据库约束。

## §3 数据流走查

```text
started sequence 0
  → synchronous heartbeat sequence 1
  → sidecar heartbeat sequence 2..N
  → sidecar stopped
  → completion sequence 1,000,000
  → if completion rejects: failed sequence 1,000,001
```

## §6 讨论点

### 6.1 使用高位保留编号

- 位置：`runner/scripts/real-task.mjs`
- 现象：终端事件使用 1,000,000 与 1,000,001。
- 问题：为何不让 sidecar 写状态文件供主进程读取？
- 预判：高位编号不依赖跨进程可变状态，回归稳定；用例 timeout 内不可能产生百万级 heartbeats，且 schema 仅要求非负整数。
- 结论：✅ 2026-11-12 接受；若未来放宽 heartbeat 频率到不可控级别，再改为共享序列状态。

## §9 文件级代码分析

### `runner/scripts/real-task.mjs`（M）

旧代码：upload failure、completion、callback failure 分别写固定 sequence 2/3。

新代码：定义 `TERMINAL_SEQUENCE = 1_000_000` 和 `TERMINAL_FAILURE_SEQUENCE = 1_000_001`，所有终端/失败回调复用它们。

这在做什么：给终端事件一个高于常规 heartbeat 的确定顺序。

为什么这么写：Runner 主进程无法实时读取 sidecar 最后 sequence，高位保留值比共享状态更小、更可测。

实现思路：只改发送端编号，不改平台终态、幂等键或事件类型。

检视发现：无额外发现。

### `tests/runner/heartbeat-integration.test.mjs`（M）

职责：验证 sidecar 与真实 case 的并发顺序。

新增断言覆盖 completion 与 callback failure 两条路径。测试在旧 2/3 编号下失败，在保留高位编号下通过。

检视发现：无额外发现。
