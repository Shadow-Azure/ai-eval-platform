## §2 架构导览

### 2.1 查询留在数据库

`list_version_cases` 仍是单一的 `select(DatasetCase)`，但把搜索与筛选变成 SQL 谓词：

- **搜索**：`q` 同时匹配 `case_key` 与 `repo`，对两边 `lower()` 后做子串 `LIKE`；用户输入的 `%`、`_`、`\` 先由 `_escape_like` 转义，避免“搜 `%` 返回全表”的意外。`services/datasets.py:619`、`:696`。
- **难度**：先把该版本所有原始难度标签做一次 `GROUP BY`（`_version_difficulty_labels`，`:682`），把请求的 easy/medium/hard 映射回原始标签集合，再用一个 `IN` 谓词分页。这样不会把 500 条用例拉到 Python 里过滤。
- **总数**：`paginate()` 对过滤后的查询取 `count`，`page_info.total` 是过滤后总数，前端分页器不会拿全量 500 去算页数。
- **facet**：`version_difficulty_facets` 用同一份标签聚合出各难度计数。选项来自整个版本，搜索时不会因为当前页只剩一类而让筛选器跳动。

### 2.2 难度不是新造的数据

SWE-bench Verified 的难度字段是人工解决时长档位（仓库内 vendored 切片里是 `15 min - 1 hour`、`1-4 hours`），不是 easy/medium/hard。

实现把两件事分开：

- `difficulty_label` = 适配器原始标签，原样保留，用于 tooltip 与抽屉展示；
- `difficulty` = 展示层档位：≤1 小时 easy、≤4 小时 medium、>4 小时 hard；已经写 easy/medium/hard 的数据集直接透传，无法识别的标签返回 `None`，不进入筛选。

锚点：`services/datasets.py:631`、`:666`。这既满足原型的三档筛选，也没有伪造一个上游不存在的难度值。

### 2.3 校验结果来自导入记录

`version_import_validation` 按 `dataset_id + version` 找最近一条 `succeeded` / `duplicate` 的 `dataset_import`，读取它持久化的 `validation_report_json`：

- `passed = invalid_count == 0 && !report.fatal`
- `completeness_percent` = 各必填字段完整率的最小值（最弱字段，而不是平均值）
- 同时返回 `total_count` / `valid_count` / `invalid_count` / `error_codes` / `report_available`

锚点：`services/datasets.py:756`、`api/datasets.py:527`。旧版 JSON 导入没有报告时，卡片显示计数并明确“未记录逐字段完整率”，不假装 100%。

### 2.4 一个 CaseBrowser，两个页面

`CaseBrowser` 负责两个页面必须一致的部分：工具栏（搜索 + 额外筛选）、服务端分页（20/50/100）、初始骨架屏、空态、错误卡、行区间文案。页面只负责自己的列定义与 query 参数。

锚点：`CaseBrowser.tsx:48`（组件）、`:72`（错误 endpoint 可覆盖）、`:117`（骨架）、`:147`（分页）。数据集页在 `DatasetDetailPage.tsx:583` 使用；评测详情在 `EvalDetailPage.tsx:874` 使用，并传入评测的 endpoint `:945`。

### 2.5 页面编排

数据集页保留原先的版本列表、版本摘要与指标口径表，同时补上：

- 四张版本指标卡（版本 / 用例数 / 预期指标 / 适配器版本）；
- 左栏用例浏览器，右栏版本元数据 + 校验结果；
- 用例抽屉（题面、预期检查、评分材料），入口是行点击/回车。

锚点：`DatasetDetailPage.tsx:400`（页面）、`:203`（校验卡）、`:274`（抽屉）、`:583`（浏览器）。

## §3 数据流走查

1. 进入 `/datasets/:id`，并行请求数据集、版本列表；默认选中最新版本。
2. 版本详情请求返回 metrics 与 validation；右侧元数据卡和校验卡直接使用响应，不在前端重算。
3. 用例请求携带 `limit`、`offset`、`q`、`difficulty`。搜索输入 300ms 防抖后写回 query 并重置到第 1 页。
4. 后端把 `q` 转成大小写不敏感的 `LIKE`，把难度档位转成原始标签 `IN`，返回过滤后的 `items + page_info + facets`。
5. 用户切难度：Select 的值进入 query；facet 仍来自整个版本，因此选项稳定。
6. 用户翻页：`page/pageSize` 进入 query key；旧请求被取消，新页只拉 20/50/100 条。
7. 用户点行：打开抽屉，单独请求 `/dataset-cases/:id`，题面与评分材料分开展示。
8. 刷新按钮同时 refetch 数据集、版本列表、版本详情与用例；版本列表切换会清空难度筛选和抽屉，避免旧条件静默限制新版本。

## §6 讨论点

### 6.1 难度档位阈值是产品选择

- **位置**：`backend/app/services/datasets.py:631`
- **现象**：把时长档位映射为 ≤1h easy、≤4h medium、>4h hard。
- **问题**：上游没有 easy/medium/hard 的官方定义；阈值改变会影响筛选分布与截图口径。
- **预判**：issue 明确要三档，原始标签已保留，当前映射可解释；若要更保守可只展示原始时长档位。
- **结论**：

### 6.2 Facet 覆盖整个版本，不是当前搜索

- **位置**：`backend/app/services/datasets.py:736`
- **现象**：搜索结果里仍显示全版本的难度计数。
- **问题**：用户可能期望计数随搜索条件收缩。
- **预判**：稳定选项优先，避免筛选项在输入过程中跳动；计数含义在代码注释与 PR 里说明。
- **结论**：

### 6.3 校验失败态在正常流程中不可达

- **位置**：`backend/app/services/datasets.py:756`
- **现象**：只有校验通过的导入才能生成版本，因此版本详情通常只会看到 `passed=true`。
- **问题**：`passed=false` 的分支目前是防御性代码，真实流程不会触发。
- **预判**：保留分支可让历史脏数据或未来“允许带警告入库”时有正确展示；不额外制造失败数据。
- **结论**：

### 6.4 `expected_test_count` 的口径

- **位置**：`backend/app/services/datasets.py:675`
- **现象**：把 `expected_metrics_json` 中所有数组长度相加。
- **问题**：对 SWE-bench 是 F2P+P2P，对其他适配器可能包含非测试数组。
- **预判**：当前只有 SWE-bench 适配器；列名与注释写清“预期检查数”，不宣称是测试通过数。
- **结论**：

### 6.5 冒烟数据与 m5-17 运行时覆盖

- **位置**：PR 描述“冒烟限制”
- **现象**：本地无法访问 HuggingFace，500 条由 vendored 真实切片逐字段扩展；本地也没有模型/资产/资源池，无法创建真实评测 run。
- **问题**：分页/筛选/校验的 UI 行为已被 15 条断言覆盖，但官方完整语料与评测详情运行时页面没有截图。
- **预判**：组件复用通过代码引用 + typecheck/build 验证；真实评测页面留给有资源的 CI/部署环境。PR 已如实标注。
- **结论**：
