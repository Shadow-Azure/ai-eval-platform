## §1 一页速览

一句话：总览的「最近评测」原本是块写死空数组的展示板（`dataSource={[]}`），现在接上了真实任务列表，并且每页只向服务端要 5 条；顺带把评测页里那套展示函数抽成共享模块，两页从此不再各养一份。

比喻：以前是餐厅门口一块「最近订单屏」，屏幕里写死「暂无订单」；现在屏幕后面接了一条按时间倒序的出餐带——每次只送 5 盘（服务端 `limit=5&offset=…`），翻页就是让后厨再送下一批；换盘时先把旧的 5 盘留在台面上（`keepPreviousData`），避免台面瞬间空一下。

## §2 架构导览

### 2.1 请求层：一个 hook 把「第几页」翻译成 offset

`web/src/api/overview.ts:7-8` 定义缓存键 `["overview","recent-evaluations",page,pageSize]`；`36-45` 是新增 hook：

```ts
export function useRecentEvaluationsQuery(page: number, pageSize = 5) {
  return useQuery({
    queryKey: recentEvaluationsQueryKey(page, pageSize),
    queryFn: ({ signal }) =>
      fetchEvaluations({ limit: pageSize, offset: (page - 1) * pageSize }, signal),
    placeholderData: keepPreviousData,
    staleTime: 15_000,
    retry: 1,
  });
}
```

三个关键点，都是「薄翻译」而不是新机制：

- 页号到 offset 只在一处换算（`offset = (page-1)*5`），页面侧不拼 URL，避免两处各算一遍；
- `signal` 原样透传到 `fetchEvaluations`（`web/src/api/evaluations.ts:732-742`），快速连点翻页时旧请求会被 abort，不会出现「第 3 页的响应盖住第 2 页」；
- `placeholderData: keepPreviousData` 让换页期间保留上一页 5 行，表格不闪空（比喻：换盘时先不撤旧盘）。

`fetchEvaluations` 的 offset 有个细节：`web/src/api/evaluations.ts:737` 只在 offset 为真值时写入查询串，所以第 1 页的 URL 根本没有 `offset` 参数，后端默认 0，两者等价。

类比：这个 hook 像电梯的「楼层按钮」——你只按 7 楼，它自己算要走几层、什么时候取消上一次按错的方向。

### 2.2 服务端契约：排序稳定、窗口由 offset 决定

后端接口 `backend/app/api/evaluations.py:416-469` 接收 `limit`（1..200）与 `offset`（≥0），交给 `backend/app/services/evaluations.py:602-636`：

```python
.order_by(EvalRun.created_at.desc(), EvalRun.id.desc())
.offset(max(0, offset))
.limit(max(1, min(limit, 200)))
```

- 排序是「创建时间倒序 + id 倒序」，加了 id 兜底，同一秒创建的多条记录不会在页与页之间跳来跳去（这正是 offset 分页最容易翻车的地方）；
- `total` 用同一组过滤条件单独 count（`services/evaluations.py:627-635`），所以前端分页器页数可信；
- 每次列表请求还会顺带算 `stats`（`api/evaluations.py:467` → `services/evaluations.py:665`），总览页用不到，属于「搭车」开销，35 条量级无实害。

数据库层没有按 project 过滤（`list_evaluations` 只用 `q/status/dataset_id`），而总览计数接口 `backend/app/api/overview.py:41-63` 是按 `tenant_id` 过滤的。单租户部署下两个数字必然一致；如果将来做多租户，角标「N 个任务」（列表 total）和「评测任务总数」（overview counts）会来自不同口径——当前无实害，记录在案。

### 2.3 展示层：把「怎么显示」从页面里拔出来

`web/src/utils/evaluationDisplay.ts` 是新文件，6 个纯函数，无 React 依赖：

- `runtimeLabel`（:10-13）：运行时 key → 展示名，未知 key 原样返回，避免出现空白；
- `dateTimeLabel`（:15-27）：同一天显示「今天 HH:mm」，否则「M 月 D 日 HH:mm」，非法时间原样返回（:17-18）；
- `durationLabel`（:29-37）/ `durationCompact`（:39-47）：同一套取整逻辑，一个输出「1 小时 5 分」，一个输出 `1h 5m`（卡片用）；
- `progressPercent`（:49-53）：优先用服务端 `finished_count`，缺失时用 `total - queued - running` 兜底，最后 `Math.min(100, …)` 夹住；
- `rateLabel`（:55-57）：`null` 显示「—」，否则一位小数 + `%`。

`web/src/pages/EvalsPage.tsx:21-28` 改为 import；对比 base 版本（`git show origin/main:web/src/pages/EvalsPage.tsx`），删掉的 6 个函数与新区块逻辑逐行相同，只多了 `export`。这是「搬家不改家具」，风险极低。

### 2.4 三态与分页渲染：状态判断集中在一处

- `dataSource`：`web/src/pages/OverviewPage.tsx:413`，`isError` 时给空数组，否则给 `data.items ?? []`；
- `loading`：`:415` 用 `isFetching`（含后台刷新），与 `isLoading`（首次）区分；
- `locale.emptyText`：`:426-457` 三选一——失败态（`:426-442`）、成功且 `total===0` 的空态（`:443-455`）、其余 `null`；
- `pagination`：`:416-424`，`current` 取 `Math.min(recentPage, recentPageCount)`，`hideOnSinglePage` 让 ≤5 条时不出现翻页器，`showTotal` 输出「共 N 条」；
- 角标：`:405-408` 只有拿到 data 才显示「N 个任务」，失败时不会出现误导性的「0 个任务」。

`emptyText: null` 这一格值得说清：antd 的 Table 在 `dataSource` 是空数组时仍会渲染占位行，只有 `dataSource` 为 `null/undefined` 且 loading 才跳过占位（`web/node_modules/antd/es/table/InternalTable.js:344-361`）；`locale.emptyText` 显式给了 `null` 时，占位行里什么都不画。所以首屏与「本页确实没数据」时，用户看到的是 Spin + 一条高度为 0 的占位行，而不是一句错误的「暂无数据」。这个细节选对了。

分页状态本身只有两个来源：`recentPage`（:96）与 `recentTotal`（:98）。`recentPageCount` 用 `Math.max(1, …)` 兜住 0 条的情况（:99），再由 `useEffect`（:101-103）在总数变小时把页码夹回去。这套写法的边界行为见 §6.1 与 §6.3。

## §3 端到端走查

主线剧本（正常路径）：

```text
/login 登录
  → 跳 /overview（默认 index 重定向）
  → 并行发 3 个请求：overview 计数、readyz、recent page=1（limit=5, offset 省略）
  → 首屏：骨架屏/Spin，最近评测表占位行留白
  → 数据到：卡片 4 张、健康卡、最近评测 5 行 + 角标「35 个任务」+ 分页器 7 页
  → 点第 2 页：page=2 → limit=5&offset=5 → 6–10 条（切换期间第 1 页仍在屏上）
  → 点行尾箭头：/evals/{run_id} → 详情页
```

逐步锚点：

1. 登录进总览：`web/src/app/routes.tsx:23`（`/login`）、`:26`（index → `/overview`）、`:27`（总览路由）。总览页并行发起三个查询：`web/src/pages/OverviewPage.tsx:92-97`。
2. 首屏加载：`isLoading` 渲染骨架（`:246`），最近评测表 `dataSource=[]`、`loading=true`（`:413-415`），`emptyText` 为 `null`（`:456`），只显示 Spin 与空占位行。
3. 数据到达：`recentTotal=35`、`recentPageCount=7`（`:98-99`）；表格 5 行取自 `data.items`；角标 `:405-408`；分页器 `:416-424` 显示 7 页与「共 35 条」。
4. 翻到第 2 页：`onChange` 触发 `setRecentPage(2)`（`:423`），缓存键变化（`web/src/api/overview.ts:38`），查询串变为 `limit=5&offset=5`（`:40`），后端按 `created_at desc, id desc` 取窗口（`backend/app/services/evaluations.py:622`），返回第 6–10 条与同一个 `total`。切换期间 `keepPreviousData` 让第 1 页继续可见（`web/src/api/overview.ts:41`）。
5. 进入详情：行尾按钮 `navigate(\`/evals/${row.id}\`)`（`:208-221`，路由在 `routes.tsx:31`）。按钮带 `aria-label="查看评测 {name}"`（`:216`），键盘可达。
6. 空态：0 条且请求成功时显示「暂无评测任务」+「发起评测」（`:443-455`）；`hideOnSinglePage` 让翻页器整体消失（`:421`），不出现空白页。
7. 失败态（第 1 页 / 首次加载）：`isError` 为真、无 data → `dataSource=[]`（`:413`）+ 错误空态与重试（`:426-442`），错误文案优先用 `ApiError.message`（`:127-132`）。
8. 失败态（第 ≥2 页，异常分支）：第 2 页请求失败后，该缓存键在 error 态没有 data（react-query 的 `placeholderData` 只在 `pending` 时生效，见 `web/node_modules/@tanstack/query-core/build/modern/queryObserver.js:344-355`；错误时 `status: "error"` 见 `query.js:522-534`），于是 `recentTotal` 变 0、`recentPageCount` 变 1，`useEffect` 把 `recentPage` 夹回 1；第 1 页若仍有新鲜缓存（`staleTime` 15s 内），错误空态只存在一帧就换成第 1 页数据、错误提示彻底消失。这是本次检视发现的真实行为断裂，详见 §6.1。

## §6 讨论点

### 6.1 第 ≥2 页请求失败会把用户静默弹回第 1 页

- **位置**：`web/src/pages/OverviewPage.tsx:98-103`（`recentTotal`/`recentPageCount`/clamp effect）与 `:413`、`:417`、`:426-442`。
- **现象**：停在任意页 ≥2 时，如果该页请求最终失败，页面会先闪一下「最近评测加载失败」，随即被夹回第 1 页：若第 1 页缓存仍新鲜则直接显示旧数据、错误提示消失，用户既失去页码也不知道刚才失败过（若第 1 页缓存已过期并重取失败，则会停在第 1 页的错误态，页码同样已被重置）。PR 的失败态冒烟从描述看是在首次加载（第 1 页）注入 500，此时 `recentPage=1`、clamp 不触发，所以覆盖不到这条路径。
- **问题**：`recentPageCount` 由 `recentQuery.data?.total ?? 0` 推导，把「还不知道总数」（loading / error / 尚未返回）和「总数确实是 0」混成了同一个值；`useEffect` 因此把 error 态的页码当成越界处理。同时 `pagination.current` 用 `Math.min(...)` 显示夹过的值，会让用户以为一直在第 1 页。
- **预判**：这是本次检视最值得修的一条，改动很小且不改变正常路径：clamp 只在拿到 data 时执行，并让 `current` 直接等于 `recentPage`（越界修正交给 effect）。例如 `if (recentQuery.data && recentPage > recentPageCount) setRecentPage(recentPageCount)`。修完应补一条「第 2 页失败仍停在第 2 页、重试重取第 2 页」的冒烟。
- **结论**：（待拍板）

### 6.2 失败态清空「上一次成功数据」，与同页 banner 的策略相反

- **位置**：`web/src/pages/OverviewPage.tsx:413`（`dataSource={recentQuery.isError ? [] : …}`）与同文件 `:254-264`（总览刷新失败 banner「以下为最近一次成功数据」）。
- **现象**：同一张页面里两套策略——页面级刷新失败保留旧数据并挂 banner，表格级刷新失败则清空所有行、整块换成错误空态。react-query 在已有数据时后台重取失败会把 state 置为 error 但保留 `data`（`query.js:522-534`），所以窗口聚焦、断网重连这类自动重取失败时，用户会看到本可保留的 5 行突然全没了。
- **问题**：应该「有旧数据就留着 + 顶部提示」，还是「失败就必须让用户看到明确失败」？清空的好处是不会让用户误以为旧数据是新的；代价是短暂网络抖动被放大成整表消失。
- **预判**：倾向保留数据：把 `dataSource` 改为 `recentQuery.data?.items ?? []`，错误态仅在 `!data` 时占满表格；有 data 时改用一行内联告警 + 重试（可以复用 `:254-264` 的 banner 样式，保持一页一致）。这样 §6.1 的「弹回第 1 页」也不会被错误态掩盖。
- **结论**：（待拍板）

### 6.3 分页 clamp 会有一帧「页码已对、行是空的」

- **位置**：`web/src/pages/OverviewPage.tsx:101-103` 与 `:416-417`。
- **现象**：当总数变小（例如记录被删、筛选口径变化）导致当前页越界时，`current` 渲染的是夹过的页码，但 `recentPage` 还是旧值，于是这一帧里表格请求的是越界窗口（返回 0 条），下一帧 effect 才把页码改掉并重取。
- **问题**：用户可能看到一次「翻页器停在第 6 页、表格却是空白」的闪烁；`emptyText` 为 `null` 时这一帧连提示都没有（空白占位行）。
- **预判**：发生条件很窄（需要总数下降，而当前产品没有删除评测的入口），无实害，不值得为它引入额外状态；如果 §6.1 按「只在有 data 时 clamp」修，这一帧会保留，但同样只在总数下降时出现。建议记录不修。
- **结论**：（待拍板）

## §9 文件级代码分析

### 9.1 `web/src/api/overview.ts`（M）

职责：总览页的查询集中处，本次新增「最近评测分页」这条查询；M 的前身只有 `useOverviewQuery` / `useReadyzQuery`。

关键依赖：`@tanstack/react-query` v5（社区库、构建期打包、运行时在浏览器内存里缓存请求结果）。本文件只用到三件事：`useQuery` 缓存、`keepPreviousData` 占位、`signal` 透传。比喻：它像前台的一个「登记本」，同一个 key 只派一次跑腿，跑腿回来前先把上一次的复印件留在桌上。

旧代码（base）：

```ts
import { useQuery } from "@tanstack/react-query";
export const overviewQueryKey = ["overview"] as const;
export const readyzQueryKey = ["readyz"] as const;
```

新代码：

```ts
export const recentEvaluationsQueryKey = (page: number, pageSize: number) =>
  ["overview", "recent-evaluations", page, pageSize] as const;

export function useRecentEvaluationsQuery(page: number, pageSize = 5) {
  return useQuery({
    queryKey: recentEvaluationsQueryKey(page, pageSize),
    queryFn: ({ signal }) => fetchEvaluations({ limit: pageSize, offset: (page - 1) * pageSize }, signal),
    placeholderData: keepPreviousData,
    staleTime: 15_000,
    retry: 1,
  });
}
```

这在做什么：把「第几页」翻译成 `limit/offset`，并按页缓存；换页时旧页数据继续展示。

为什么这么写：服务端已经支持 `limit/offset` 与稳定排序（`backend/app/services/evaluations.py:622`），前端不需要把 35 条全拉下来再切片；按页做 key 才能让「回到第 1 页」命中缓存而不是重新请求。

实现思路：薄翻译层，不接管请求细节，不复制 `fetchEvaluations` 的参数拼装。

检视发现：

- `pageSize = 5` 的默认值与页面常量 `RECENT_EVAL_PAGE_SIZE = 5`（`OverviewPage.tsx:22`）重复；页面总是显式传值，默认值实际不会被用到。属于无害冗余，可留可去。
- 缓存键挂在 `["overview", …]` 下：`invalidateQueries({ queryKey: ["overview"] })` 会前缀命中最近评测（react-query 默认非 exact），行为上「刷新总览连最近评测一起刷」是合理的；但也意味着两个查询的失效边界被绑在一起，将来若只想刷计数会误伤。当前没有调用方，记录备查。
- 无自动刷新（§6.8），不是本文件的错，是「要不要准实时」的产品决定。

### 9.2 `web/src/pages/OverviewPage.tsx`（M）

职责：总览页；本次把「最近评测」从写死的空表改成真实数据表，并补三态、分页、详情入口，删除 M3 横幅。

关键依赖：`antd` 的 `Table`（社区组件库、构建期打包）负责渲染与分页器；本页只喂 `columns` / `dataSource` / `pagination` / `locale.emptyText`。比喻：Table 是「展示柜」，页面负责决定每一格放什么、没货时挂牌子还是留白。

旧代码（base）：

```tsx
interface RecentEvalRow { id: string; name: string; agent: string; … }
const recentEvalColumns: TableColumnsType<RecentEvalRow> = [ … ];
…
<Table<RecentEvalRow>
  className="recent-table"
  columns={recentEvalColumns}
  dataSource={[]}
  rowKey="id"
  pagination={false}
  locale={{ emptyText: <EmptyState … title="暂无评测任务" … /> }}
/>
```

新代码：

```tsx
const [recentPage, setRecentPage] = useState(1);
const recentQuery = useRecentEvaluationsQuery(recentPage, RECENT_EVAL_PAGE_SIZE);
const recentTotal = recentQuery.data?.total ?? 0;
const recentPageCount = Math.max(1, Math.ceil(recentTotal / RECENT_EVAL_PAGE_SIZE));
useEffect(() => {
  if (recentPage > recentPageCount) setRecentPage(recentPageCount);
}, [recentPage, recentPageCount]);
…
<Table<EvaluationSummary>
  columns={recentColumns}
  dataSource={recentQuery.isError ? [] : (recentQuery.data?.items ?? [])}
  loading={recentQuery.isFetching}
  pagination={{ current: Math.min(recentPage, recentPageCount), pageSize: 5, total: recentTotal,
                showSizeChanger: false, hideOnSinglePage: true,
                showTotal: (value) => `共 ${value} 条`, onChange: setRecentPage }}
  locale={{ emptyText: /* 失败态 / 空态 / null 三选一 */ }}
/>
```

这在做什么：列从「扁平 mock 字段」换成 `EvaluationSummary` 的真实字段（`runtime_key`、`dataset_name`、`resolve_rate`、`duration_seconds` 等），数据来自服务端分页，并给出行尾详情按钮（`:208-221`）。

### 9.4 `web/src/utils/evaluationDisplay.ts`（A）

职责：评测展示层的纯函数集合，供总览与评测列表共用。

关键依赖：`EvaluationSummary` 只是类型导入（编译期擦除），运行时零依赖；这是它能被将来单测直接 import 的前提。

变更形态：A，新文件。内容全部来自 `EvalsPage.tsx` base 版本的搬家，未改语义。

代码块分析：

```ts
export function durationLabel(seconds: number | null | undefined): string {
  if (seconds === null || seconds === undefined || seconds < 0) return "—";
  const totalMinutes = Math.round(seconds / 60);
  const hours = Math.floor(totalMinutes / 60);
  const minutes = totalMinutes % 60;
  if (hours > 0) return `${hours} 小时 ${minutes} 分`;
  if (minutes > 0) return `${minutes} 分`;
  return `${Math.max(1, Math.round(seconds))} 秒`;
}
```

这在做什么：先把秒四舍五入到分钟，再拆小时/分钟；不足 1 分钟时回退到秒并至少显示 1 秒。

为什么这么写：列表空间小，统一到分钟级可读性最好；`Math.max(1, …)` 避免出现「0 秒」这种看起来像没跑的文案。

`progressPercent` 则优先信任服务端 `finished_count`，缺失时才用 `total - queued - running` 兜底，并用 `Math.min(100, …)` 夹住，避免脏数据把进度条画到框外。

实现思路：只做「值 → 字符串/数字」的确定性映射，不读全局状态、不依赖 locale 配置。

检视发现：

- `dateTimeLabel` 不输出年份（`:25-26`），跨年记录会显示成「12 月 5 日 09:30」，无法判断是哪一年。这是从 `EvalsPage` 原样搬来的既有行为，当前数据都在几天内，无实害；若将来做历史对比，需要补年份。
- `durationLabel` 会把 90s 显示成「2 分」，1h0m 显示成「1 小时 0 分」——取整策略而不是精确保留，属展示取舍。
- 两个时长函数（`durationLabel` / `durationCompact`）逻辑重复度很高，只差单位词。可以参数化，但会让调用点变啰嗦；保持现状可接受。
- 本文件无测试（§6.5）。
