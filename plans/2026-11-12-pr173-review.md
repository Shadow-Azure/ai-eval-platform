## §1 一页速览

一句话：这个 PR 把“主机自己生一把钥匙”改成“GitHub 发同一把钥匙”，并在换钥匙前确认旧主机拿的是同一把。

一个比喻：主机 `.env` 像保险柜的钥匙串。过去每次换办公室都重新磨一把钥匙，旧保险柜就打不开了；现在钥匙统一存放在 GitHub Secrets，搬家时先核对新钥匙与旧办公室钥匙是否一致，再整串交接到新办公室。

交付块：

| 交付 | 结果 |
|---|---|
| Secret 来源 | 7 个长期密钥全部从 GitHub Secrets 注入。 |
| 旧主机保护 | 现有 `.env` 值与 Secrets 的 SHA-256 不一致时，在覆盖前失败。 |
| 新主机 | 没有 `.env` 时允许用 Secrets 初始化。 |
| 原子写入 | 先写临时文件，再 `mv` 替换 `.env`，权限保持 0600。 |
| 禁止随机密钥 | `deploy.sh` 不再调用 `openssl rand`。 |
| 容器注入 | API/worker 的长期密钥和 runner token 矩阵有契约断言。 |

## §2 架构导览

### 2.1 Secret 身份与来源

Deploy job 的 env 把 7 个长期值从 GitHub Secrets 映射进来，见 `.github/workflows/deploy.yml:169` 到 `:175`。在写主机前，`:219` 到 `:225` 用 shell 参数展开强制要求每个值非空；缺少任一值会在任何主机修改前失败。

这层相当于“门卫”：先确认钥匙串齐全，再允许接近主机。密钥没有进入 argv；后续通过 stdin 管道写入远端 shell。

### 2.2 现有主机的一致性闸门

`:236` 到 `:241` 在 GitHub Runner 内计算每个 Secret 的 SHA-256。`:242` 到 `:259` 通过 SSH 读取主机 `.env` 的对应值，同样只返回摘要。

`:260` 到 `:263` 比较两组摘要。现有主机不一致时直接退出，不覆盖 `.env`。这是本 PR 最关键的安全边界，能避免把历史密文的解密 key 悄悄换掉。

### 2.3 原子 `.env` 更新

真正的写盘发生在 `:287` 到 `:307`。远端先 `mktemp`，把未受管键从旧 `.env` 过滤到临时文件，再从 stdin 追加新的受管值，`chmod 600` 后用 `mv` 原子替换。

相比旧实现先截断 live `.env` 再回写，新实现把“可回滚”放在文件系统 rename 语义上。即使副本生成失败，旧 `.env` 应在最终 `mv` 前保持原样。

### 2.4 容器消费面

API 在 `deploy/docker-compose.prod.yml:62`、`:65`、`:66`、`:75`、`:85`、`:86` 读取 runner、session、box 和 gateway secrets。Worker 在 `:142` 到 `:144` 读取容量控制器需要的 key 与 token，数据库 URL 在 `:125` 强制要求密码。

### 2.5 主机部署 fail-fast

`deploy/deploy.sh:24` 到 `:30` 定义 `require_secret`，`:35` 到 `:41` 逐一要求 7 个长期值。删除了原来的 `ensure_secret` / `ensure_fernet_secret` 和 `openssl rand`，因此主机不会在缺失时自行“修复”成一把新钥匙。

## §6 讨论点

### 6.1 远端 stdin 中断可能把不完整 `.env` 原子替换成正式文件

**位置**：`.github/workflows/deploy.yml:287` 到 `:307`。

**现象**：远端在 `cat >> "$tmp"` 读到 EOF 后继续执行 `mv "$tmp" .env`。如果 SSH 连接在传输若干受管行后断开，远端 `cat` 可能以成功状态结束，而 `tmp` 只包含部分密钥。

**问题**：当前测试只检查 `mktemp`、`mv` 等文本存在，没有验证“载荷完整”后才允许 rename。文件替换是原子的，但原子替换不一定代表内容完整。

**预判**：建议由本地先计算整个受管 payload 的 digest，在流末尾发送明确的结束标记；远端校验结束标记和 digest 后才 `mv`。或者用 `scp` 传临时文件并在远端比对 digest，再合并未受管键。该问题直接关系换机时是否可能带着半套密钥启动。

**结论**：

### 6.2 预建空/模板 `.env` 的迁移机会被误判为旧主机不一致

**位置**：`.github/workflows/deploy.yml:250` 到 `:263`。

**现象**：远端只有“完全没有 `.env`”才返回 `__NO_ENV__`。如果新主机由镜像、初始化脚本或运维模板预先创建了 `.env`，但没有 7 个长期键，远端返回 7 个 `__MISSING__`，随后与期望摘要比较失败。

**问题**：这类主机没有旧密文可保护，却被当成“旧主机 key 不一致”拒绝。验收要求换机可部署，但当前分支只覆盖完全没有文件的情况。

**预判**：把“所有 7 个长期键都缺失”识别为空模板并允许初始化；只有至少一个存在且与 Secrets 不一致时才拒绝。需要同时补真实 shell 行为测试。

**结论**：

### 6.3 新增测试没有执行远端 shell，只验证字符串片段

**位置**：`tests/deploy/deploy-contract.test.mjs:207` 到 `:295`。

**现象**：18 个契约测试对安全属性很重要，但新增测试主要调用 `workflow.includes(...)` 和 `script.includes(...)`。`mktemp` 存在并不证明中断时不会替换半写文件，`__NO_ENV__` 存在也不证明模板 `.env` 能通过。

**问题**：密钥迁移属于高破坏面逻辑，纯文本断言无法覆盖 shell quoting、stdin EOF、grep 退出码、空 `.env` 和权限/rename 顺序。

**预判**：抽取远端 env writer 为可在临时目录执行的脚本，使用假 HOME/DEPLOY_DIR 和假“新值”文件做行为测试。至少覆盖：正常替换、未受管键保留、空模板迁移、部分载荷、grep 无匹配、rename 前失败。

**结论**：

### 6.4 Compose 注释仍声称密钥由 deploy.sh 生成

**位置**：`deploy/docker-compose.prod.yml:70` 到 `:73`、`:81` 到 `:84`。

**现象**：注释仍写着 `AUTH_SESSION_SECRET`、`SECRET_BOX_KEY`、`GATEWAY_TOKEN_SECRET` 由 deploy.sh 首次生成。

**问题**：实际实现已改为 GitHub Secrets 注入。注释会误导后续运维重新引入主机随机生成。

**预判**：Minor，随本 PR 修正即可。

**结论**：

### 6.5 Secret 主动轮换目前没有显式迁移路径

**位置**：`.github/workflows/deploy.yml:260` 到 `:263`。

**现象**：只要 GitHub Secret 与主机旧值不同，部署就失败。这是保护历史密文的正确默认，但未来主动轮换时也需要一个明确的“先迁移/重加密、再切换 key”的受控流程。

**问题**：当前安全失败不会丢数据，但运维看到的是通用“不一致”错误，没有轮换指引。

**预判**：可在错误信息中指向轮换 runbook；不在本 issue 实现自动轮换。Minor。

**结论**：

## §9 文件级代码分析

### 9.1 `.github/workflows/deploy.yml`

**职责**：从 GitHub Secrets 接收 7 个长期值，保护现有主机，更新 `.env`，再触发主机迁移/部署。

**关键依赖解读**：SSH 是“传送带”，GitHub Actions 提供的 `ssh` 客户端把受管 env 流送到主机；主机端 shell 是唯一真正具备写 `.env` 权限的一方。SHA-256 只是“指纹”，用于判断两把钥匙是否同一把，不保存或输出钥匙本身。

**变更代码块分析**：

旧代码在 `.env` 上直接 `grep > .env.tmp`、`cat .env.tmp > .env`、`cat >> .env`，中间任何一步失败都可能留下截断文件。新代码把旧未受管内容和新受管值都写到独立 tmp，最后 `mv`，这是正确方向。

旧 `deploy.sh` 的 `ensure_secret` / `ensure_fernet_secret` 会在缺失时随机生成；新代码改为 `require_secret`，把“缺失”变成显式部署失败。这符合换机要求。

**实现思路总结**：先确认同源，再原子替换，最后让主机 fail-fast 消费。

**检视发现**：见 §6.1、§6.2、§6.3、§6.5。

### 9.2 `deploy/deploy.sh`

**职责**：在主机上执行迁移、滚动更新、健康检查和部署记录。

**关键依赖解读**：`common.sh` 提供 `.env` 路径、compose 参数与记录函数。这里像“替换钥匙后才允许启动机器”的启动脚本，必须先检查钥匙齐全。

**变更代码块分析**：

旧代码中的 `openssl rand` 是换机事故的根源；新代码把随机源彻底移除。`require_secret` 只判断非空，不读取值，失败信息只包含 key 名称。

**实现思路总结**：删除自动修复，改为缺 Secret 即阻断。

**检视发现**：逻辑方向正确；其健壮性取决于 workflow 写入完整 `.env`，见 §6.1。

### 9.3 `deploy/docker-compose.prod.yml`

**职责**：把主机 `.env` 中的长期值注入 API/worker/migrate。

**关键依赖解读**：Compose 使用 `${KEY:?}` 表示“缺了就拒绝启动”，`${KEY:-}` 表示“允许空值由应用自己判定”。Postgres 密码和 DB URL 采用前者，其他长期项在本 PR 的契约补丁中做了核对。

**变更代码块分析**：结构未改，但 PR 的测试把 API/worker 矩阵固定下来。对本 issue 而言这是合理保护；注释陈旧见 §6.4。

**实现思路总结**：环境映射显式化，并以测试防止后续回归。

**检视发现**：无新增代码逻辑缺陷，除注释误差。

### 9.4 `tests/deploy/deploy-contract.test.mjs`

**职责**：验证 Secret 名称、注入、原子写入、比较分支与 compose 矩阵。

**关键依赖解读**：Node 内置 `node:test`，没有额外包依赖；测试直接读仓库文本，启动快，但只能证明文本模式存在。

**变更代码块分析**：

新增测试清楚固定了 7 个 Secret 名单，并防止 `openssl rand` 回归。缺陷是关键流程没有执行远程 shell，见 §6.3。

**实现思路总结**：静态契约保护明确，行为级保护不足。

**检视发现**：Important，见 §6.3。
