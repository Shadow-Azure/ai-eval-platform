## §2 架构导览

`real-task.mjs` 是固定 Runner 的宿主控制面。它在 Docker 中启动 Agent，容器退出后必须继续完成三件事：读取 Claude 原生文件、执行评分、上传轨迹并清理临时目录。

Docker 内 `eval` 用户与宿主服务的 uid 不保证一致，Claude 又可能创建只允许自身访问的会话路径。因此在容器仍存活时，由容器 root 对挂载的 `/testbed` 做一次 `a+rwX` 归一化，是在不复制文件、不改变内容、不引入宿主机 root 依赖的前提下最直接的修复。

该权限调整只作用于一次性 case workdir；目录本身位于平台临时目录，任务结束立即删除。

## §3 数据流走查

```text
Docker agent writes /testbed/.runtime-home and /testbed/trace
  → agent exits
  → container root chmod -R a+rwX /testbed
  → container removed
  → host reads native JSONL
  → host writes diagnostics and scores
  → trace manifest upload
  → workdir cleanup
```

修复点必须位于容器删除之前；容器删除后再执行 chmod 已没有机会访问挂载树。

## §6 讨论点

### 6.1 权限修复范围

- 位置：`runner/scripts/real-task.mjs`
- 现象：`chmod -R a+rwX /testbed` 会统一放宽一次性工作区的访问位。
- 问题：是否存在敏感文件被同机其他用户读取的风险？
- 预判：workdir 位于 runner 的私有临时目录，任务结束即删除；不修改源仓库或长期目录。风险低于继续依赖未知 uid 导致评分失败。
- 结论：✅ 2026-11-12 接受；由权限回归和临时目录生命周期共同约束。

### 6.2 completion/failure sequence 与 heartbeat 冲突

- 位置：`runner/scripts/real-task.mjs` 的 uploads/completed/failed callback
- 现象：权限修复部署后的复测不再 EACCES，但长任务 heartbeat 已占用 sequence 2/3，completion 与 failed callback 返回 500。
- 问题：`real-task` 将 completion 固定为 sequence 2、failure 固定为 3，心跳 sidecar 从 2 单调递增，长任务必然碰撞 `UNIQUE(case, attempt, sequence)`。
- 预判：终端回调使用高位保留 sequence，并断言大于所有已发送 heartbeat；不需要跨进程共享可变计数器。
- 结论：✅ 2026-11-12 本分支已按 TDD 修复，待部署后再次复测。

## §9 文件级代码分析

### `runner/scripts/real-task.mjs`（M）

职责：宿主侧执行单个真实 case 的 Docker 生命周期、评分、轨迹与回调。

旧代码：Agent 退出后，`finally` 直接删除容器，随后宿主读取 `.runtime-home` 和 `trace`。

```javascript
} finally {
  dockerRun(["rm", "-f", agentName], { allowFailure: true });
}
```

新代码：

```javascript
} finally {
  dockerRun(
    ["exec", agentName, "chmod", "-R", "a+rwX", "/testbed"],
    { allowFailure: true, timeout: 60_000 },
  );
  dockerRun(["rm", "-f", agentName], { allowFailure: true });
}
```

这在做什么：在挂载仍然存在、容器 root 仍可执行命令时，把 Agent 产物的目录/文件权限调整为宿主可遍历和读取。

为什么这么写：容器删除后宿主无法再借容器 UID 修复；`a+rwX` 对普通文件只增加读写，对目录增加遍历，适合一次性 workdir。

实现思路：不复制轨迹、不改变内容、不依赖宿主 root。

检视发现：无阻塞问题；权限范围由临时目录生命周期限制。
