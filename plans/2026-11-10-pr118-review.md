## §1 一页速览

一句话：把评测详情从“结果展示页”升级为“解释结果 + 采取恢复动作”的工作台。

比喻：它像医院分诊台——概览是分诊大屏，用例表是病历索引，抽屉是单个病人的历次检查，配置是入院登记，事件日志是护理记录；重试只是重新安排一次检查，旧报告不会被撕掉。

## §2 架构导览

**读路径。** HTTP 适配层只做参数校验和错误映射，查询集中在 `services/workbench.py:200`。case 列表先按 `eval_run_id` 过滤，再按状态/搜索/显式状态字段叠加条件；`page_info` 带 `has_more/next_offset`。测试摘要不是逐行查询，而是先找出本页 case 的最新 attempt，再一次性 group by（`workbench.py:131`），避免 20 行表格产生 40 次 SQL。

**写路径。** 重试没有复制 M4 的状态机，而是复用 `case_attempts.build_retry_dispatch`（`case_attempts.py:674`）生成新 attempt + outbox，再由调度器派发。服务和 API 只负责“是否允许重试”和事件审计，真正的执行语义仍只有一处。`retry_state`（`workbench.py:354`）把 run 状态、case 终态、attempt 上限和 active attempt 四道闸门集中表达。

**SSE。** 事件端点仍是“快照 + 游标回放”。本次在 `backend/app/api/evaluations.py:337` 有两个关键动作：支持 `before_id` 向更早翻页；在返回流之前 `session.close()`（第 372 行），让长连接不再占住请求级连接池。生成器每次轮询使用独立的短 session。

**前端。** URL 是唯一状态源：`tab/status/q/execution_status/result_status/trace_status/page/pageSize/case/attempt` 都进入 query string（`EvalDetailPage.tsx:420`）。查询 key 与 URL 一一对应，SSE 只做失效/合并，不在多个组件里各自累加计数。`useEvalEvents`（`useEvalEvents.ts:64`）在 runId 变化时重置事件、cursor 和连接；传输错误按指数退避重连，401/403/404 或终态正常关闭时停止。

## §3 数据流走查：一次失败用例重试

1. 用户在抽屉点击“重试该用例”，`CaseDrawer` 打开确认框（`EvalDetailPage.tsx:1966`），确认后发 `POST /api/v1/eval-case-runs/:id/retry`。
2. API 进入 `workbench.retry_case`（`workbench.py:447`），用 `SELECT … FOR UPDATE` 锁 case 行，复核 run/case/attempt 状态。
3. 通过后调用 `build_retry_dispatch` 创建 attempt 2 + outbox，保留 attempt 1；写入 `case.retry_requested` 事件，`refresh_run_progress` 重算 run 计数。
4. 两个并发请求只有第一个能提交；第二个由行锁或 `(case_run_id, attempt_no)` 唯一约束拦下，服务回滚并转成 409 `case_retry_conflict`。
5. 调度器消费 outbox，按既有 M4 链路派发到资源池。
6. SSE 把 `case.retry_requested` 推给页面，detail/drawer 查询失效；UI 出现 attempt 2，旧 attempt 的轨迹和测试仍可切换查看。

批量重试是同一事务里对多个 case 重复步骤 2–3，最后写一条 `eval.retry_failed` 汇总事件（`workbench.py:482`）。

## §6 讨论点

### 6.1 SSE 长连接占用连接池（已修复）

- 位置：`backend/app/api/evaluations.py:337-372`
- 现象：打开多个详情页后，`/overview`、`/auth/me` 等普通请求开始 500：`QueuePool limit of size 5 overflow 10 reached`。
- 问题：FastAPI 的请求级 session 在 StreamingResponse 整个生命周期内不释放；每个打开的 tab 占一个连接。
- 预判：只影响长连接场景，但生产多用户会放大。
- 结论：返回流前 `session.close()`，生成器每次轮询用自己的短 session；新增 `test_sse_releases_request_session_before_streaming`。6 条流 + 30 次请求实测全 200。

### 6.2 重试并发双击可能 500（已修复）

- 位置：`backend/app/services/workbench.py:447`、`:482`
- 现象：两个请求同时通过 `retry_state` 后，后提交者触发唯一约束，直接冒成 500。
- 问题：前端禁用按钮只是体验层，服务端没有把竞争翻译成业务冲突。
- 预判：真实并发低但双击/重放可复现。
- 结论：case 行加锁；`IntegrityError` 回滚并返回 409 `case_retry_conflict`；新增冲突测试。

### 6.3 SQLite naive 时间被浏览器当成本地时间（已修复）

- 位置：`backend/app/services/evaluations.py:914`
- 现象：本地运行显示 08:04，实际本地时间 16:04，差 8 小时。
- 问题：SQLite 丢失 tzinfo，API 返回无偏移 ISO，浏览器按本地时区解析。
- 预判：生产 Postgres 不受影响，但本地/测试证据会误导。
- 结论：公共 `iso_utc` 对 naive 值补 UTC；results API 同步使用。

### 6.4 分页用 offset 而非设计建议的 cursor（接受）

- 位置：`backend/app/services/workbench.py:200`
- 现象：design 04 §1 建议 `items + page_info` 游标分页；这里用 offset + 稳定排序 `ordinal,id`。
- 问题：理论上并发插入会导致跨页重复/漏项。
- 预判：评测创建后 case 集合不可变，重试只增加 attempt，不增加 case；原型也是页码分页。
- 结论：保留 offset，并在 `page_info` 提供 `has_more/next_offset`；若未来支持运行中增删 case 再切 cursor。

### 6.5 手动重试只在运行中开放（接受）

- 位置：`backend/app/services/workbench.py:354`
- 现象：终态评测不提供单用例重试。
- 问题：用户可能希望评测结束后补跑失败用例。
- 预判：重开终态 run 会牵动指标失效、调度与计费状态机，属于新的状态设计；原型也只在运行中显示“重试失败用例”。
- 结论：保持当前边界；终态重跑由发起评测流程承担，未来若需要再单独设计。

### 6.6 批量重试的 fan-out 与 N+1（接受）

- 位置：`backend/app/services/workbench.py:482`
- 现象：对每个失败 case 依次查询 attempt 并创建 outbox；500 个失败用例会产生较多 SQL 与派发行。
- 问题：极端失败风暴下请求时间较长。
- 预判：与预算恢复的重新调度规模同级，当前数据集上限和 UI 可接受。
- 结论：先保留；若线上出现大 run 的批量重试超时，再改为分页/后台任务。

### 6.7 页面组件偏大（接受）

- 位置：`web/src/pages/EvalDetailPage.tsx:420`
- 现象：单文件约 2300 行，包含五个面板与抽屉。
- 问题：后续 M6 轨迹与 M5-06 基线对比继续堆叠会难维护。
- 预判：当前同文件共享大量状态与格式化函数，提前拆分会引入 prop 噪音。
- 结论：接受；M5-06/M6 引入新面板时再按 feature 拆分。

### 6.8 用例列与原型的差异（接受）

- 位置：`web/src/pages/EvalDetailPage.tsx:1053`
- 现象：原型有难度/评分/Token，本实现是执行/结果/轨迹/测试打点。
- 问题：视觉上与原型不完全逐列一致。
- 预判：难度/评分/Token 当前未进入 `eval_case_run` API；伪造值比缺列更糟。
- 结论：按 design 3.6/04 §4 与 #87 验收保留当前列，PR 描述已说明。

### 6.9 前端无单元测试（接受）

- 位置：`web/`
- 现象：仓库没有 vitest/jest 配置，本次以 Playwright 冒烟 + 视觉对照作为验收证据。
- 问题：回归保护弱于后端。
- 预判：引入测试框架是独立基础设施工作，超出 #87。
- 结论：接受；冒烟脚本可后续沉淀为发布前检查。

## §9 文件级代码分析

**`backend/app/services/workbench.py`（A）** — 职责：把“一个 run 的解释与恢复”集中成可测服务。关键依赖：SQLAlchemy 2.0 select；复用 `case_attempts.build_retry_dispatch`。读路径的关键是批量测试摘要：先按本页 case 取最新 attempt，再 group by outcome/group，避免逐行 N+1。写路径的关键是“先锁、再判断、最后唯一约束兜底”。已知弱点见 6.6/6.4。

**`backend/app/api/eval_workbench.py`（A）** — 职责：薄 HTTP 层。`_http_error` 把 service 的 404/409/422 映射成统一 `{error:{code,message}}`；写路由显式 `require_admin`，读路由沿用应用级 session 依赖。没有业务判断，便于 CLI/测试复用 service。

**`backend/app/services/evaluations.py`（M）** — 变更集中在三处：`evaluation_detail` 增加 `case_counts/trace_counts/retryable_count` 与 case repo/trace；`list_events` 改为“默认最新窗口、before 更早、after 前向”，返回 `has_more/direction`；`iso_utc` 统一 UTC 输出。旧代码默认从最旧事件开始，长 run 的事件页会永远看不到最新事件，这是行为修正而非纯重构。

**`backend/app/api/evaluations.py`（M）** — 事件路由新增 `before_id`；SSE 在返回流之前释放请求 session。旧代码把 `session.get_bind()` 传给 `stream_factory` 后就让依赖保持到流结束，真实使用中会耗尽 QueuePool。修复不改变 SSE 协议。

**`backend/app/api/results.py`（M）** — `generated_at` 改用 `iso_utc`，与 detail/events 的时区契约一致。没有改指标选择逻辑（仍优先 `is_final`）。

**`backend/app/services/case_attempts.py`（M）** — `build_retry_dispatch` 增加关键字参数 `retry_reason`，默认保持 `runner_retryable_failure`；自动重试与手动重试共用同一派发构造，只改审计标签。

**`tests/backend/test_eval_workbench.py`（A）** — 覆盖筛选/计数/分页、测试摘要、attempt、重试成功/重复/终态/耗尽/冲突、批量重试、配置快照、事件窗口、detail 计数。测试用真实迁移后的 SQLite，不 mock service。

**`tests/backend/test_sse.py`（M）** — 新增“流开始前释放请求 session”的回归；保留原有 replay/terminal 与未登录测试。

**`web/src/pages/EvalDetailPage.tsx`（M）** — 主要复杂度在 URL 状态与生命周期：筛选/页码/抽屉都从 query string 派生；SSE 只触发失效。抽屉的 attempt 选择通过 URL `attempt` 保持深链；测试表按 group 展示 F2P/P2P/OTHER。已知弱点见 6.7/6.9。

**`web/src/api/useEvalEvents.ts`（A）** — 先取快照再建 SSE；游标取快照最大 id，避免重放已展示事件。连接循环区分“正常关闭且无新事件”（终态，停止）与“传输错误”（退避重连）；401/403/404 立即停止。runId 变化时 reset + abort，防止旧事件混入。

**`web/src/app/App.tsx` / `PageHeading.tsx` / `EvalsPage.tsx` / `main.tsx`（M）** — 小改动：AntD `App` 上下文消除静态 message 警告；标题支持 ReactNode 以嵌入状态标签；事件调用改用新签名；导入新样式。
