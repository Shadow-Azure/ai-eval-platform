## §1 一页速览

一句话：给每个资源池发一张“专属门牌”，作业派发和 Runner 注册必须同时使用同一张门牌，fixed 作业不能再被 spot Runner 顺路接走。

比喻：GitHub Actions 的标签匹配像“钥匙串”——作业列出它需要的所有钥匙，任何拥有这套钥匙的 Runner 都能开门。以前 fixed 作业只要 `self-hosted,linux,eval` 三把公共钥匙，而 spot Runner 恰好三把都有、还多一把池钥匙，于是 fixed 作业也能开 spot 的门。现在每个池再发一把只有自己有的钥匙（`pool-fixed-linux` / `m5-08-spot`），作业和 Runner 都必须带上这把钥匙，公共钥匙相同也不会串门。

| 交付块 | 内容 | 验证 |
|---|---|---|
| 必填唯一标签 | 池必须有 `runs_on`，包含 `self-hosted` 和至少一个非默认标签 | `test_runner_labels.py`、`test_resource_api.py` |
| 派发不回退 | 池存在但缺标签时 `RunnerLabelsMissing`，只有无池 synthetic 用默认 | `test_runner_labels.py`、`test_evaluations.py` |
| 跨池冲突 | 与另一池标签集构成子集/超集时 422 | `test_pool_runs_on_is_required_and_unique` |
| 历史回填 | `{"kind":"fixed"}` 池迁移后得到默认三件套 + 唯一标签 | `test_pool_unique_label_migration_backfills_legacy_pools` |
| 注册一致 | fixed bootstrap 与 spot JIT 都使用池标签 | `test_runner_bootstrap`、现有 spot smoke |
| 派发隔离 | fixed 作业标签不是 spot Runner 标签的子集 | `test_fixed_and_spot_job_labels_are_not_subsets` |
| 预检 | missing / mismatch / overlap 的阻断与警告 | `test_preflight.py` |
| 控制台 | 标签按 `runs_on` 展示，表单必填 | `web build` + 冒烟截图 |

## §2 架构导览

### 2.1 标签解析只有一个入口

`pool_runner_labels()` 是整个平台唯一的“池标签 -> 派发标签”解析函数（`backend/app/services/runner_labels.py:127`）。它现在只做两件事：池为 `None` 时返回默认三件套；池存在时读取显式标签，读不到就抛 `RunnerLabelsMissing`。旧代码的 `fallback` 参数和 `LEGACY_FIXED_LABELS` 分支被删除，这样“池存在但没标签”不会再静默借用全局标签。

`resolve_labels()`（`runner_labels.py:88`）负责从 `instance_config_json`、`labels_json` 和旧的控制台 `{label: true}` 映射中取值；`kind` 是历史元数据，永远不作为标签。这样 fixed 池的 `{"kind":"fixed"}` 只会被识别为“没有标签”，而不是“标签叫 kind”。

### 2.2 创建/更新时就把坏配置挡住

`validate_pool_runs_on()`（`backend/app/services/resources.py:273`）做四件事：非空、去重、包含 `self-hosted`、包含至少一个非默认的池唯一标签；随后与同租户其他池比较，只要两边标签集互为子集或超集就拒绝。选择“子集/超集”而不是只拒绝“完全相同”，是因为真正的泄漏条件是“作业标签集合 ⊆ Runner 标签集合”，完全相同只是它的一个特例。

`normalize_pool_label_storage()`（`resources.py:366`）把控制台映射和 `instance_config.runs_on` 统一收敛到 `labels_json.runs_on`，并移除 `instance_config` 中的旧标签键，避免两个来源长期分叉。API 在创建和更新时各调用一次（`backend/app/api/resources.py:488`、`:621`）。

### 2.3 迁移先回填，再让应用收紧

`0034_pool_unique_runner_labels.py` 先解析每个池的现有标签；为空或只有默认三件套时，按池名派生 `pool-<slug>`（如 `pool-fixed-linux`）；如果两个池的标签集仍构成子集/超集，追加 id 短标签打破重叠。迁移只改池行，不改 `runner` 行：Runner 的 `labels_json` 是心跳上报的现场快照，篡改它会让预检误以为 Runner 已经带新标签。

### 2.4 注册与派发共用同一列表

- spot：`aliyun._runner_labels()` 直接调用 `pool_runner_labels(pool)`，JIT 注册、cloud-init 和分片 dispatch 三处拿到的是同一个列表（`backend/app/services/provisioning/aliyun.py:506`）。
- fixed：Runner 的 GitHub 注册标签由 `infra/runner/bootstrap.sh` 写入；脚本默认追加 `RUNNER_POOL_LABEL`（默认 `pool-fixed-linux`），已有配置缺少时补一次，重复时不重复追加（`infra/runner/bootstrap.sh:207-213`）。
- 系统 fixed 池：`ensure_fixed_pool()` 创建时写入 `default_pool_runs_on(settings.runner_fixed_pool_name)`（`backend/app/services/runners.py:89`）。

### 2.5 预检负责“配置存在但物理没到位”

`check_preparation()` 在资源池存在时（`backend/app/services/preflight.py:112` 起）新增三层检查：

1. `pool_runs_on` 为空 -> `pool_runs_on_missing` 阻断；
2. 在线 Runner 没有全部池标签 -> fixed 池且无兼容 Runner 时 `runner_pool_labels_mismatch` 阻断；spot 池或仅部分 Runner 缺标签时警告（旧 spot Runner 会在下一次实例回收/新建时自然替换）；
3. 与另一 active 池标签集构成子集/超集 -> `pool_runs_on_overlap` 阻断。

这样即使迁移/API 校验被绕过，启动前仍会给出可诊断的缺失标签，而不是让作业静默排到别的池。

### 2.6 控制台只做展示与必填

`labelList()`（`web/src/api/resources.ts:538`）现在优先读取 `runs_on`（兼容 `runner_labels`/`labels` 和旧映射），避免后端迁移后列表显示成 `runs_on=self-hosted,...` 一长串。资源池表单的 Runner 标签改成必填并给出 `pool-fixed-linux` 示例（`web/src/pages/ResourcesPage.tsx:1684`），与服务端校验一致。

## §3 数据流走查

1. 管理员新建 fixed 池，提交 `labels = {runs_on: [self-hosted, linux, eval, pool-fixed-linux]}`。
2. `create_resource_pool()` 调 `validate_pool_configuration()` 与 `validate_pool_runs_on()`；后者与现有池比较，无子集/超集后返回标签。
3. `normalize_pool_label_storage()` 写入 `labels_json = {runs_on: [...]}`，`instance_config_json` 不含标签键。
4. fixed Runner 首次心跳：`ensure_fixed_pool()` 创建/复用系统池；心跳把 Runner 的 `labels_json` 快照写入库。
5. 启动评测：预检读取池标签和在线 Runner 标签，确认至少一个 Runner 包含全部池标签；fixed 池无兼容 Runner 时阻断。
6. `create_synthetic_evaluation()` 调 `run_runs_on()`，把池标签写进 outbox 的 `client_payload.runs_on` 与 manifest `runs_on`。
7. 调度器 POST repository_dispatch；GitHub 只把作业派给同时拥有这些标签的 Runner。
8. spot 池扩容：`aliyun._runner_labels()` 用同一列表生成 JIT config，新 Runner 注册时即带池标签。
9. spot 失败回退：`spot_fallback._fallback_labels()` 同样只取目标池显式标签，不再回退默认。

## §6 讨论点

### D1 为什么拒绝“子集/超集”而不只是“完全相同”

- 位置：`backend/app/services/resources.py:323-361`
- 现象：两个池即使标签集不完全相同，只要 A ⊆ B，A 的作业仍可能落到 B 的 Runner。
- 问题：issue 文字要求“拒绝与另一个池完全相同的标签集”，实现比文字更严格；会不会误伤合理配置？
- 预判：平台用池做容量隔离，任何子集关系都意味着容量串用；完全相同只是最明显的特例。固定池和 spot 池共享 `self-hosted,linux,eval` 本来就是合法的，只要各自带唯一标签，二者互不为子集。因此严格化不会误伤“共享公共标签 + 各自唯一标签”的正常配置。
- 结论：接受严格化；根因就是子集匹配，不能用“完全相同”覆盖。

### D2 固定 Runner 的物理标签是运营步骤，不是纯代码

- 位置：`infra/runner/bootstrap.sh:207-213`；`backend/app/services/preflight.py:323-359`
- 现象：迁移只回填池行，不会修改已在 GitHub 注册的 fixed Runner 标签；部署后 fixed 池会因缺少 `pool-fixed-linux` 被预检阻断，直到 Runner 重注册。
- 问题：这是否会导致部署后 fixed 评测全部不可用？
- 预判：预检阻断是刻意设计——宁可阻断也不让 fixed 作业回退到 spot。本次已在生产机 `fixed-linux-eval` 上执行 `config.sh remove` + 带 `self-hosted,linux,eval,pool-fixed-linux` 重新注册，并更新 `/etc/eval-platform/runner.env`；后续换机按 bootstrap 默认即可。
- 结论：接受；发布说明必须保留“fixed Runner 重注册”步骤，且预检会把漏配显式暴露。

### D3 部署窗口内的在途 outbox 不会被迁移重写

- 位置：`backend/app/services/evaluations.py:462-473`；`dispatch_pending_outbox()` 直接发送已冻结 payload
- 现象：迁移只改池行；部署前已经创建、尚未派发的 outbox 行仍携带旧 `runs_on`。
- 问题：这些在途 fixed 评测在部署窗口内仍可能落到 spot Runner。
- 预判：重写 outbox 需要同时改 `client_payload`、manifest 文本和 digest，跨 dialect 迁移风险高于收益；新创建与重试派发已全部使用新标签。发布时选择低峰、取消/等待在途 fixed 评测，即可消除窗口。
- 结论：接受为已知发布限制；不在本 PR 重写历史 outbox。PR 描述与发布说明写明。

### D4 spot 旧 Runner 缺标签只警告，不阻断

- 位置：`backend/app/services/preflight.py:323-354`
- 现象：spot 池迁移后，已在线但未带池标签的旧 Runner 与池标签不兼容。
- 问题：既然它们接不到新作业，为什么只警告？
- 预判：spot Runner 是一次性实例，缺标签的旧 Runner 会在回收后自然消失；spot 扩容会用 cloud-init 按池标签注册新 Runner。阻断启动会无谓地阻止 spot 评测排队扩容。fixed 池没有自动补 Runner 的能力，所以 fixed 才阻断。
- 结论：接受；fixed 阻断、spot 警告的分层与容量模型一致。

### D5 迁移对“只有自定义标签、没有 self-hosted”的历史池补公共标签

- 位置：`backend/migrations/versions/0034_pool_unique_runner_labels.py` 的 `_ensure_unique()`
- 现象：若历史池的标签只有 `gpu-only`，迁移会补 `self-hosted`，但不会补 `linux`/`eval`。
- 问题：补 `self-hosted` 是否越权改变运营配置？
- 预判：GitHub 自托管 Runner 必然带 `self-hosted`；缺它作业永远不会被匹配。`linux`/`eval` 并非所有池必需（例如 macOS 池），迁移不应擅自补。补 `self-hosted` 是让历史配置重新可用所需的最小修正。
- 结论：接受；迁移测试覆盖 `["gpu-only"] -> ["self-hosted","gpu-only"]`。

### D6 `MAX_LABELS` 截断发生在校验前

- 位置：`backend/app/services/runner_labels.py:88-124`
- 现象：`resolve_labels()` 先截断到 64 个；`validate_pool_runs_on()` 的“超过 64”分支实际不会触发。
- 问题：如果唯一标签恰好是第 65 个，会被静默丢弃。
- 预判：64 是 dispatch 契约上限，截断行为与旧代码一致；正常池远少于 64 个标签，且截断后若只剩默认标签会命中 `pool_runs_on_required`，不会静默接受。该分支是防御性死代码，无当前实害。
- 结论：接受；后续如需严格报错，可在 `normalize_labels` 前增加“原始长度”检查，不在本 PR 扩大范围。

### D7 更新池时不改已有唯一标签的值

- 位置：`backend/app/api/resources.py:621-640`
- 现象：池名可以改，但 `runs_on` 不会被自动改名；只有显式提交新标签才会变。
- 问题：改名后池唯一标签还是旧名字，是否会造成误解？
- 预判：Runner 的 GitHub 标签是物理注册事实，改名不应静默让作业等一个不存在的标签。保持标签稳定、由管理员显式改标签并重注册 Runner，是更安全的语义；预检会在 Runner 未跟上时阻断。
- 结论：接受；显式修改标签是运营动作，不是改名副作用。

## §9 文件级代码分析

### 9.1 `backend/app/services/runner_labels.py`（M）

职责：把“池”翻译成 GitHub Runs-on 标签列表，并给系统 fixed 池派生唯一标签。旧版在池没有显式标签时回退 `DEFAULT_RUNS_ON`，且把 fixed 的 `{"kind":"fixed"}` 当元数据跳过；新版把“没有标签”变成显式错误。

```python
# 旧：池没标签 -> 回退默认
labels = fallback or DEFAULT_RUNS_ON
# 新：池没标签 -> 抛错；只有 pool is None 才用默认
if pool is None: return list(DEFAULT_RUNS_ON)
labels = resolve_pool_labels(pool)
if not labels: raise RunnerLabelsMissing(pool)
```

实现思路：解析与默认值决策分离，调用方无法再用 `fallback` 悄悄改变语义；`derive_pool_label()` 用池名 slug 保证固定池得到可读的 `pool-fixed-linux`。

for other in other_pools:
