## §2 架构导览

### 2.1 workflow 是外部作业闸门

`trace-e2e` 只在手动 `workflow_dispatch` 且 `inputs.mode == 'trace-e2e'` 时运行（`.github/workflows/eval-shard.yml:81-92`），普通 PR CI 不触发。job 在非 sandbox 的自托管 Runner 上启动 PostgreSQL、装真实 CLI、运行 harness（`:109-138`），最后总是上传 artifact 并删除容器（`:139-152`）。

### 2.2 harness 是导演

`tests/integration/m6_06_trace_e2e.py` 建隔离数据库、API、Worker、测试网关和 S3 配置（`:250-305`），直接创建 synthetic evaluation 与首条 dispatch（`:380-422`），先跑失败 attempt，再取自动生成的 retry dispatch（`:424-462`），最后轮询 API、raw、权限和 parser replay（`:472-610`）。

### 2.3 Node runner 是真实传话员

`runner/scripts/trace-e2e-runner.mjs` 校验 manifest digest（`:118-129`），回调 started/heartbeat（`:142-174`），调用 `runClaudeCode`（`:176-188`），采集多文件（`:190-200`），再按平台签发地址上传并回传（`:227-349`）。

### 2.4 gateway 是模型 sidecar

`m6_06_fake_anthropic_gateway.py` 只在 provider 层确定化：它识别 root prompt 后返回两个 `Agent` tool_use（`:193-214`）；真实 Claude CLI 仍自行启动子 Agent 并写原生文件。它不是轨迹解析 stub。

3. 首 attempt 的 Node runner 读取 manifest、校验 digest 并回传 started（`runner/scripts/trace-e2e-runner.mjs:118-174`）。
4. 真实 Claude Code 连接本地 gateway；gateway 返回两个 Agent tool calls；CLI 落 root/subagent `.jsonl` 与 `.meta.json`（`m6_06_fake_anthropic_gateway.py:193-214`）。

6. 首 attempt 故意回传 retryable failure；平台创建 attempt 2（`trace-e2e-runner.mjs:295-318`）。
7. attempt 2 成功完成；Worker 下载 OSS 原件、解析、写 trace_tree 并发布 state（`m6_06_trace_e2e.py:464-501`）。
8. harness 验证 attempt session/file 隔离（`:503-512`）、raw 与审计（`:514-528`）、权限（`:530-550`）、parser replay（`:552-610`）。
9. 固定 Runner artifact 与 Computer Use 截图共同形成报告。

## §6 讨论点

### 6.1 [Critical] 真实云与认证 secrets 会进入 Claude 子进程

**位置**：`runner/scripts/trace-e2e-runner.mjs:178`；`runner/lib/runtime-claude-code.mjs:114-127`；`tests/integration/m6_06_trace_e2e.py:270-305`

**现象**：workflow 把真实 `S3_ACCESS_KEY/S3_SECRET_KEY` 注入 job；harness 又构造 `DATABASE_URL`、`AUTH_SESSION_SECRET`、`RUNNER_TASK_SECRET`。`runClaudeCode` 最终调用 `childEnv`，那里 `{ ...baseEnv }` 复制整个 host 环境，只删除 Anthropic/OpenAI key。

**问题**：真实 Claude Code 及其 Bash 工具可以读取 `process.env`。一旦 Agent 因提示注入、回归或恶意工具输出执行 `env`，OSS、DB、Runner token 会进入模型上下文或轨迹，形成一个“安全测试自己泄露生产级密钥”的闭环。这与设计 08 §8 的“Runner 无长期凭据”冲突。

**预判**：应阻塞合并。E2E 进程只能拿到 gateway URL/token、HOME、Claude 非必要流量开关和最小 PATH；OSS/DB/Auth/Runner secrets 只应留在父进程。修法是用显式 allowlist 构造 child env，或允许 `runClaudeCode({ envAllowlist })`，并加测试证明确实不存在 `S3_SECRET_KEY`、`DATABASE_URL`、`AUTH_SESSION_SECRET`、`RUNNER_TASK_SECRET`。

**结论**：已修复。`runClaudeCode` 支持显式 `baseEnv`；trace E2E 只传 PATH/TMPDIR/LANG/LC_ALL/SHELL。负向测试证明 `S3_SECRET_KEY`、`DATABASE_URL`、`AUTH_SESSION_SECRET`、`RUNNER_TASK_SECRET` 不进入子进程。

### 6.2 [Important] 降级验收没有进入真实 Runner 链路

**位置**：`tests/integration/m6_06_trace_e2e.py:391-462`、`:478-501`；`reports/.../report-data.json` 场景 08

**现象**：固定 Runner 真实运行只有两个 `trace_status=ready`。缺子文件、unknown format、stdout-only、orphan 等仅在既有 UT 与 #169 smoke 中验证；报告把这条标为 PASS。

**问题**：issue #95 明确要求真实链路中的缺文件、未知格式和仅 stdout 历史数据“显示明确降级与 raw 路径”。当前证据没有证明 fixed Runner 的 upload/completion→Worker→API→Web 降级路径。

**预判**：属于验收缺口，不建议继续用已有 UT 代替。可以增加一次 `--terminal=degraded` 或独立 single-case dispatch：只上传 stdout diagnosis；再上传一个 unknown format；验证 trace_status、quality、raw 与评分终态不变。

**结论**：已修复。fixed-runner 第二次运行额外创建 degraded evaluation，真实上传 unknown v99 + stdout-only，经 OSS、Worker、API 后为 `incomplete`、0 sessions、raw 200，执行和评分终态保持不变。

### 6.3 [Important] “真实用例”仍是 synthetic case，未执行真实评分

**位置**：`tests/integration/m6_06_trace_e2e.py:391-404`；`runner/scripts/trace-e2e-runner.mjs:202-225`

**现象**：评测由 `create_synthetic_evaluation` 创建，runner 直接写 `resolved: true` 与伪造的 F2P success；没有 dataset version、test patch、评分容器或失败重试后的真实评分。

**问题**：PR 正文与 issue 文案容易让读者理解为 `Agent→评分→OSS→回调→归一化→结果` 完整链路，但实际只验证 `真实 Agent→OSS→回调→归一化`。设计 10 §3 的 Runner E2E 明确包含评分。

**预判**：若 #95 只定位为轨迹闭环，可以保留 synthetic，但必须把标题、报告和验收明确写成“trace E2E”，并新增后续真实 SWE-bench scoring E2E；若 #95 要求完整 Runner E2E，则需补真实 case 与 scoring。

**结论**：已澄清。PR/报告明确本 issue 是 trace E2E；synthetic score 只验证轨迹导入不改变执行/评分终态，完整 SWE-bench scoring 仍由既有评测流水线与后续评分 E2E 负责。

### 6.4 [Important] thinking 隐藏断言可能是真空通过

**位置**：`tests/integration/m6_06_trace_e2e.py:537-541`；`tests/m6-trace-e2e.test.mjs:42`

**现象**：`all(span.content_hidden for span in viewer_spans if span.kind == "THINKING")` 在没有 THINKING span 时为 True。真实 gateway 响应没有显式 thinking block，证据也未记录 THINKING 数量。

**问题**：PR 声称验证“thinking 隐藏”，但这个断言可能根本没执行。权限测试需要证明“存在敏感 thinking，viewer 被隐藏”，而不是“没有目标时返回 true”。

**预判**：补至少一个 THINKING span，断言总 thinking>0 且 viewer 的 preview 为空、`content_hidden=true`、原因正确；或把这条从本 PR 声明中移除并引用 #93 API 测试。

**结论**：已修复。fake gateway 产生合法 thinking block，fixed-runner 证据记录 2 个 THINKING spans，viewer 全部 `content_hidden=true` 且原因为 `thinking_requires_admin`。

### 6.5 [Minor] 实际 CLI 版本未从进程输出验证

**位置**：`runner/scripts/trace-e2e-runner.mjs:190-195`；`tests/integration/m6_06_trace_e2e.py:622`

**现象**：workflow 安装 `@anthropic-ai/claude-code@2.1.278`，但证据里的 `runtime_version: "2.1.278"` 是硬编码，不是从 `claude --version` 或 init event 读取。

**问题**：如果 PATH 或 npm prefix 错误地落到另一版本，报告仍可能写 2.1.278。

**预判**：在 runner 启动前执行 `claude --version`，匹配语义版本并写入 evidence；不匹配则失败。

**结论**：已修复。instrumentation 执行 `claude --version`，不匹配 2.1.278 即失败；证据版本取自实际输出。

### 6.6 [Minor] 固定 Runner 证据暴露主机名与临时目录逻辑路径

**位置**：`reports/.../fixed-runner-evidence.json:4`、`:34` 附近

**现象**：evidence 记录 `host: iZbp...`，logical path 也保留 `-opt-ai-eval-platform-runner--work...`。

**问题**：它是测试环境而非生产，但 Computer Use 报告规范要求避免暴露私有路径；hostname 和部署目录也为后续公开 artifact 带来不必要的环境泄露面。

**预判**：证据可保留稳定运行 ID 和 sanitized runner name，不必持久化 hostname 或原生命名中的 runner 根路径；脱敏后再生成 artifact。

**结论**：已修复。提交的 fixed-runner evidence 使用 `<runner-host>` 与 `<runner-temp>` 脱敏，原始私有 artifact 只保留 GitHub run id。

## §9 文件级代码分析

### 9.1 `runner/scripts/trace-e2e-runner.mjs`（A）

职责：用真实 Claude CLI 执行单个 trace E2E attempt，并完整走 runner 回调。

依赖：Node 内置 `crypto/fs/os/path`；仓库内 `callback-client`、`contracts`、`runtime-claude-code`、`trace-capture`。它们都是运行时加载的同仓模块，没有新增第三方依赖。

变更思路：先验证 dispatch/manifest，再用平台上传地址执行真实上传，最后根据 `--terminal` 选择成功或可重试失败。

发现：Critical env 泄漏在 `:178` 触发；版本硬编码在 `:194`。

### 9.2 `runner/lib/trace-e2e.mjs`（A）

职责：对 evidence 做最后一道“不是假绿”的机械断言。

思路：对 session ID 去重、要求 1 root + 2 children、检查 relation evidence、raw/audit、两个 attempts 和 secret 正则；checksum 排序对象键，便于稳定。

发现：当前 evidence validator 没检查 THINKING 是否存在、degrated 是否覆盖、runner 实际版本；它防住了明显伪造父子，但阻止不了覆盖语义被夸大。

### 9.3 `tests/integration/m6_06_trace_e2e.py`（A）

职责：导演器，启动隔离服务并验证 API/DB 结果。

思路：本地开发可切换 S3 stub 与 OSS；固定 Runner 使用 OSS。它直接调用 service 建 synthetic evaluation，省掉用户 UI，但保留 runner HTTP 合同和 Worker 导入。

发现：真实 OSS secrets 与子进程 env 混住；降级/thinking/scoring 三处覆盖不足。

### 9.4 `tests/integration/m6_06_fake_anthropic_gateway.py`（A）

职责：确定性 provider sidecar。

思路：用 Anthropic SSE 返回两个 tool_use，真实 CLI 自己创建子 Agent。按 root prompt 与 tool_result 区分轮次，避免子 Agent 请求递归 spawn。

发现：逻辑清楚，未发现 Critical；它确实没有替代 parser 或 Claude 进程。循环保护依赖 marker 文本，测试专用可接受。

### 9.5 `.github/workflows/eval-shard.yml`（M）

职责：新增固定 Runner 外部作业。

思路：常规 CI 不触发，仅显式选择 `trace-e2e`；secret 只出现在该 job；容器与 artifact 都有 always 清理/上传。

发现：job 正确隔离外部作业，但把 OSS secrets 注入整个 job，导致后续 CLI 继承问题；workflow 本身没有意外对常规 `execute` 暴露 secrets。

### 9.6 `tests/m6-trace-e2e.test.mjs`（A）

职责：验证 evidence 断言器能拒绝假 parent、重复 session 和 bearer secret。

发现：测试诚实，但没有覆盖 THINKING 真空、degraded、版本或 env allowlist；新增修复必须补对应反例。
