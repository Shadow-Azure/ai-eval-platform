## §2 架构导览

### 2.1 保存校验在调用链中的位置

`create_template` / `update_template` 都经过 `_validate_fields`（`backend/app/services/eval_templates.py:380`）。该校验原先只检查引用行、用例范围、执行策略等；本 PR 在 `_normalise_execution` 之后调用 `_image_dependency_blockers`（`:269`），按「执行策略 override → 数据集版本 → 平台默认」解析两个 digest；任一为空就抛 `TemplateInvalid(code="template_save_blocked")`，由 API 的 `_http_error` 转成统一错误 envelope。

`_image_dependency_blockers` 同时被 `template_view`（`:713`）复用，因此保存判定和列表/详情展示使用同一套规则，不会出现“保存说可以、列表说不行”的分叉。

### 2.2 为什么更新只对部分字段重新校验 digest

更新模板时，`update_template` 先合并出完整 `current` 再校验。若每次 PATCH 都强制校验 digest，阻塞模板的「停用」「改名」「改说明」都会被 422 拦截，用户甚至无法先停用一个已知不可启动的模板。因此更新路径只在 `dataset_version_id` 或 `execution` 变化时重算确定性 digest gate（`backend/app/services/eval_templates.py:571`）；其他字段照常校验引用与格式。这是本次检视的 D1 修复。

### 2.3 前端如何消费 blocker

`TemplateLaunchModal` 打开时先用 `template.preflight.blockers` 进入阻断态；若用户仍通过旧数据/竞态触发启动，422 响应的 `details.blockers` 会经 `issuesFromDetails`（`web/src/components/TemplateLaunchModal.tsx:30`）解析并替换为服务端明细。`TemplateBlockerList`（`web/src/components/TemplateBits.tsx:64`）统一渲染 code、原因、字段和修复建议；`blockerFixHint`（`:22`）按 issue 给出的 code 映射修复方式，未知 code 原样展示原因。

## §3 数据流走查

1. 用户保存模板 → 前端 `buildTemplatePayload` → `POST/PATCH /api/v1/eval-templates`。
2. 后端 `_validate_fields` 解析版本、模型、资源池、执行策略；`_normalise_execution` 得到 `execution`。
3. `_image_dependency_blockers` 依次取 `execution.execution_image_digest`、`version.execution_image_digest`、`settings.default_execution_image_digest`；评分同理。
4. 任一为空 → 422，`details.fields` 两个字段，`details.blockers` 两个 issue（code、message、field、dataset_version）。
5. 前端 `saveTemplateOnly.onError` 识别 `template_save_blocked` → 把 blockers 放入保存区的 `TemplateBlockerList`，保留表单状态。
6. 模板列表/详情读取 → `template_view` 重算 blockers → `preflight` 字段 → 「待修复」Tag / banner / 「镜像依赖」行。
7. 启动 → 后端仍然走既有 preparation；422 返回 `details.blockers` → 启动弹窗展示明细并禁用确认。

## §6 讨论点

### D1 阻塞模板无法停用/改名 → 已修复

- 位置：`backend/app/services/eval_templates.py:571`
- 现象：初版在每次 PATCH 都重算 digest gate，导致阻塞模板的 `enabled=false` 或 `name` 更新也返回 422。
- 问题：用户无法先停用一个已知不可启动的模板；编辑元数据也被阻断。
- 预判：保存 gate 的目标是阻止“新写入一个必然阻塞的启动配置”，不是锁死所有元数据。
- 结论：只在 `dataset_version_id` / `execution` 变化时重算；补测试覆盖阻塞模板可改名/停用/重新启用。✅ 已修复。

### D2 `preflight` 只覆盖镜像 digest，不是全部静态引用 → 保留

- 位置：`backend/app/services/eval_templates.py:804`
- 现象：模板引用的数据集版本被停用、资源池被删除等不会进入 `preflight.blockers`，仍只在启动时暴露。
- 问题：字段名 `preflight` 看起来像完整预检。
- 预判：issue #398 与原型都只要求确定性镜像 digest；资产解析、容量、凭据等实时项明确留在启动时。把全部引用检查塞进列表会扩大范围并增加每行查询。
- 结论：保留当前范围；文案使用「镜像依赖」而非「全部预检」，不声称覆盖实时检查。✅ 接受。

### D3 保存前预检面板的可达性 → 记录

- 位置：`web/src/pages/EvalWizardPage.tsx:934`
- 现象：正常模板向导先执行 prepare；缺 digest 时 prepare 已经返回 blocker，向导停在执行策略步骤，不会进入保存评审。
- 问题：页面内的保存前预检在普通流程中较少出现。
- 预判：这不是本 PR 引入的缺陷；保存 API 的确定性拒绝才是兜底，且已由 422 冒烟覆盖。要彻底消除，需要把模板保存改成不依赖 prepare 的独立流程，属于流程重构。
- 结论：保留并在 PR 边界中说明；后续若重做模板向导可一并调整。✅ 记录，不在本 PR 扩大。

### D4 通用修复建议文案带了“未创建评测” → 已修复

- 位置：`web/src/components/TemplateBits.tsx:22`
- 现象：未知 code 的兜底文案是“按上面的原因修正配置后重试；本次没有创建评测”，在保存模板场景不准确。
- 问题：同一组件被保存和启动复用。
- 预判：兜底文案应保持场景中性，场景结论由外层 Alert 说明。
- 结论：改为“按上面的原因修正配置后重试。” ✅ 已修复。

### D5 前端没有自动化组件测试 → 保留

- 位置：`web/src/components/TemplateLaunchModal.tsx`
- 现象：后端有 pytest，前端只有 build/typecheck 与本次 Playwright 冒烟。
- 问题：未来改文案或结构时缺少回归保护。
- 预判：仓库当前没有 web 测试运行器；引入 Vitest/Testing Library 是新依赖与门禁变更，超出 #398。
- 结论：用实际 API+Web 的 Playwright 冒烟报告留存证据；后续单独建前端测试基础设施。✅ 接受。

## §9 文件级代码分析

### 9.1 `backend/app/services/eval_templates.py`

职责：模板 CRUD、列表视图与一键启动；本 PR 新增确定性 digest gate 和 `preflight` 视图。

关键依赖：SQLAlchemy 查询 `DatasetVersion` / `Settings`；没有新增第三方包。`Settings.default_execution_image_digest` 与 `default_scoring_image_digest` 是平台默认值，来自环境/配置，保存和启动共用。

变更代码块：

```python
# 新增：override → dataset version → platform default
digest = _effective_digest(
    resolved_execution.get(key),
    getattr(version, key, None) if version is not None else None,
    getattr(settings, f"default_{key}", None),
)
```

为什么这么写：把三处来源收敛为一个函数，保存与视图复用，避免两边规则漂移；空字符串/None 统一视为缺失。

```python
# 更新路径只在 launch 字段变化时重新 gate
validate_image_dependencies=(
    "dataset_version_id" in changes or "execution" in changes
),
```

为什么这么写：见 D1；防止元数据编辑被已存在的阻塞状态锁死。

```python
"preflight": {
    "status": "blocked" if image_blockers else "ready",
    "blockers": image_blockers,
},
```

为什么这么写：列表/详情不需要额外接口即可显示阻塞状态；每次读取重算，所以回填 digest 后自动恢复，不需要迁移或缓存失效。

检视发现：D1（已修复）、D2（范围接受）。无其他正确性问题；`details.dataset_version` 只包含版本号，不含凭据。

### 9.5 `web/src/components/TemplateLaunchModal.tsx`

职责：一键启动确认与错误处理；新增 blocker 状态。

数据流：打开时读取 `template.preflight.blockers`；提交失败时从 `ApiError.details` 解析 blockers/warnings；有 blocker 时 footer 只保留「关闭」，正文展示 blocker 列表和「未创建评测」说明。

为什么这么写：不能只 toast `error.message`（原缺陷）；也不能在客户端硬编码 blocker 文案，修复建议按 code 映射，未知 code 回退。保留 idempotency key，失败后重试仍安全。

检视发现：无阻断性问题；`useEffect` 依赖 `preflight.status`，同一个 blocked 模板重新拉取时 blockers 明细变化不会重置，但打开/关闭会重置，实际影响很小。可接受。
