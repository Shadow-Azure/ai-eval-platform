## §1 一页速览

一句话：把「手动重试 500」「启动失败空等 1 小时」「runner 退出被记成 spot 回收」「两条评测各自按全池算并发」「spot 重试超出 max_attempts」五个可靠性缺口收敛到平台已有的 attempt 状态机里，不新增表、不改 API 契约（只扩 failure 枚举）。

比喻：原来的调度像五个窗口各自拿着同一张「全池容量」的票根去向同一排座位领人；现在票根在池门口统一扣减，窗口再按整池剩余座位发号；runner 自己走掉与云厂商把椅子搬走也分开记账。

## §2 主线数据流

1. **手动重试**：控制台 `POST /api/v1/eval-case-runs/{id}/retry` → `workbench.retry_case` → `_create_retry_attempt` 创建 attempt N+1 与 outbox；`case.retry_requested` 写在新 attempt 的保留序号 `1_000_100`，`case.started` 仍占 0，首个心跳占 1。
2. **started 冲突**：Runner 调 `/runner/v1/case-runs/{id}/started` → `handle_started` 插入 sequence 0 → 唯一键冲突时 rollback → `_recover_started_sequence_conflict` 回读事件；同 event_id 去重，历史平台事件迁入保留区间后重试，否则 409。
3. **启动失败**：execute job 在 `real-task.mjs` 之前失败 → `Report bootstrap failure` 步骤先检查 markers；只在没有 `capacity-wait` 且没有 `started` 标记时读 dispatch 文件、请求 manifest 端点取得 `X-Runner-Task-Token` → POST `/failed`，`error_code=runner_bootstrap_failed`、`phase=bootstrap`、`sequence=1000002`。
4. **runner 退出**：Aliyun sync 观察到实例 Running、runner offline/heartbeat 丢失 → `_reclaim` 按 reason 分流；`runner_exited`/`runner_heartbeat_lost` → `handle_runner_lost` → `settle_attempt_failure(retryable=True)`，错误码 `runner_lost`，受 `max_attempts` 约束；provider 侧原因留在 spot 中断路径。
5. **容量**：dispatcher / started 调 `capacity.effective_concurrency`；`pool_in_flight` 汇总其他活跃 run 已释放 attempt，cap 扣减；started 先锁池行（pool→eval_run 一致锁序）再统计 running/scoring/uploading，超过 `max_capacity` 返回 429 `capacity_waiting`。

## §3 讨论点

### D1 平台事件使用保留正数序号

- **位置**：`backend/app/services/lifecycle.py`（`PLATFORM_EVENT_SEQUENCE = 1_000_100`）、`backend/app/services/workbench.py`、`backend/app/services/case_attempts.py`
- **现象**：手动重试事件若写新 attempt 的 0，会与 `case.started` 撞唯一键；负序号会被控制台事件读取器拒绝（`sequence < 0` 判无效），旧 attempt 归属又会让事件摘要显示「attempt 1 → 1」。
- **问题**：需要同时满足序号唯一、事件归属新 attempt、控制台读取契约。
- **预判**：正数保留区间 `1_000_100+` 高于 Runner 的终态失败 `1_000_001`，远离 started(0)/heartbeat(1..N)；控制台无需改动。
- **结论**：采用保留正数序号；历史 0 冲突行迁入同一区间，不再落到心跳 1。

### D2 池级预留与锁序

- **位置**：`backend/app/services/capacity.py`（`pool_in_flight` / `pool_started_attempts` / `lock_pool`）、`backend/app/services/case_attempts.py`（`_enforce_capacity_gate`）
- **现象**：第二个评测在第一个评测已有 5 个 released attempt 时 effective=0，即使这 5 个还没全部 started。
- **问题**：偏保守的预留可能让第二个评测多等；更危险的是 started 若先 flush `eval_run` 再锁 pool，会与池 reconciler 的 pool→eval_run 顺序形成 ABBA 死锁。
- **预判**：先锁 pool 再 flush eval_run，与 `capacity_control` 的锁序一致；预留保守性符合 #306 P1-2 验收。
- **结论**：保留保守预留；锁序改为 pool→eval_run，并新增 started 硬闸测试。

### D3 bootstrap 失败只结算真正的启动前失败

- **位置**：`.github/workflows/eval-shard.yml`（`Report bootstrap failure`）、`runner/scripts/real-task.mjs`（markers）
- **现象**：`failure() || cancelled()` 会捕获所有失败；real-task 在 capacity wait 耗尽时故意退出 1 且不发失败回调，post-start 崩溃也可能被误记为 bootstrap。
- **问题**：误结算会消耗 `max_attempts`、覆盖真实 phase。
- **预判**：real-task 写 `.capacity-wait-<case>` 与 `.started-<case>` 标记；失败步骤看到任一标记就退出，只对真正的启动前失败回调。
- **结论**：已按标记分流；取消宽限仍由平台 queue timeout 兜底。

### D4 runner 退出与 provider 侧原因的边界

- **位置**：`backend/app/services/provisioning/aliyun.py`（`PROVIDER_INTERRUPTION_REASONS`、`_reclaim`）
- **现象**：`runner_exited`/`runner_heartbeat_lost` 是 runner 自身退出，实例仍 Running；`provider_stopped`/`spot_interrupted`/`provider_unhealthy`/`instance_missing` 是 provider 侧原因。
- **问题**：把所有 reclaim 都记成 `runner_lost` 会把 provider 丢实例误算进普通重试预算；反之会把 runner 抖动算成 spot 回收。
- **预判**：runner 两类走 `runner_lost`，provider 四类走 spot 中断；spot 调用点显式传 provider_state，避免使用过期的 `last_state`。
- **结论**：已按此边界分流，并在 `runner_exited` 测试中断言 provider_state=Running。

### D5 bootstrap 步骤的幂等与 runner 绑定

- **位置**：`.github/workflows/eval-shard.yml`
- **现象**：失败步骤若带 `x-runner-id`，在 runner 行已注销/未注册时会在进入 handler 前 404；manifest GET 单次失败也会让结算落空。
- **问题**：结算链路的健壮性。
- **预判**：failed 回调不需要 runner 绑定头；manifest GET 与失败 POST 都做有限重试（3 次）。
- **结论**：已去掉 `x-runner-id` 并加入重试；manifest 端点不可达时仍由 queue timeout 兜底。

### D6 flow-online 的外部阻塞

- **位置**：仓库流程树与 GitHub Project
- **现象**：本地 `verify:flow` 与 flow-offline 通过；flow-online 报 `.agents/flow/issues/m8-dataset-image-preflight-ensure.md`、`m9-per-case-badcase-report.md` 本地 done 但 GitHub #290/#288 仍 OPEN，以及 PR 未关联 Project。

- **预判**：需要人把 PR 加入 Project，并决定 #290/#288 是关闭还是改本地状态；处理后重跑 CI 即可。
- **结论**：待人工处理；本 PR 其他检查已全绿。
