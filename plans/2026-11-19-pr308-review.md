## §1 一页速览

一句话：把「手动重试 500」「启动失败空等 1 小时」「runner 退出被记成 spot 回收」「两条评测各自按全池算并发」「spot 重试超出 max_attempts」五个可靠性缺口收敛到平台已有的 attempt 状态机里，不新增表、不改 API 契约（只扩 failure 枚举）。

比喻：原来的调度像五个窗口各自拿着同一张「全池容量」的票根去向同一排座位领人；现在票根在池门口统一扣减，窗口再按整池剩余座位发号；runner 自己走掉与云厂商把椅子搬走也分开记账。

## §2 主线数据流

1. **手动重试**：控制台 `POST /api/v1/eval-case-runs/{id}/retry` → `workbench.retry_case` → `_create_retry_attempt` 创建 attempt N+1 与 outbox；`case.retry_requested` 写在新 attempt 的 `sequence=-1`，`case.started` 仍占 0。
2. **started 冲突**：Runner 调 `/runner/v1/case-runs/{id}/started` → `handle_started` 插入 sequence 0 → 唯一键冲突时 rollback → `_recover_started_sequence_conflict` 回读事件；同 event_id 去重，历史平台事件移到空闲正序号后重试，否则 409。
3. **启动失败**：execute job 在 `real-task.mjs` 之前失败 → `Report bootstrap failure` 步骤读 dispatch 文件、请求 manifest 端点取得 `X-Runner-Task-Token` → POST `/failed`，`error_code=runner_bootstrap_failed`、`phase=bootstrap`、`sequence=1000002`。
4. **runner 退出**：Aliyun sync 观察到实例 Running、runner offline/heartbeat 丢失 → `_reclaim` 按 reason 分流；`runner_exited`/`runner_heartbeat_lost` → `handle_runner_lost` → `settle_attempt_failure(retryable=True)`，错误码 `runner_lost`，受 `max_attempts` 约束。
5. **容量**：dispatcher / started 调 `capacity.effective_concurrency`；`pool_in_flight` 汇总其他 run 已释放 attempt，cap 扣减；started 再锁池行并统计 running/scoring/uploading，超过 `max_capacity` 返回 429 `capacity_waiting`。

## §3 讨论点

### D1 平台事件用负数序号，而不是挂到旧 attempt

- **位置**：`backend/app/services/workbench.py`（`PLATFORM_EVENT_SEQUENCE = -1`）、`backend/app/services/case_attempts.py`（`_recover_started_sequence_conflict`）
- **现象**：手动重试事件若写新 attempt 的 0，会与 `case.started` 撞唯一键；若写旧 attempt，控制台事件摘要的「attempt 1 → 2」需要改 UI 文案。
- **问题**：选哪边都会留下一个语义或 UI 代价。
- **预判**：负数命名空间不需要改 UI、不改变事件归属，且设计 06 明确允许「平台事件独立序号命名空间」。历史 0 冲突行仍由 started 自愈逻辑迁移。
- **结论**：采用负数序号；如果后续需要事件严格按 sequence 排序，可在事件查询层把负数排到最前。

### D2 池级预留按「已释放 attempt」计数

- **位置**：`backend/app/services/capacity.py`（`pool_in_flight` / `pool_started_attempts`）、`backend/app/services/case_attempts.py`（`_enforce_capacity_gate`）
- **现象**：第二个评测在第一个评测已有 5 个 released attempt 时 effective=0，即使这 5 个还没全部 started。
- **问题**：这是偏保守的预留，可能让第二个评测多等一会儿；但换来「不会把同一份容量发两次」。
- **预判**：符合 #306 P1-2 的验收「第二条 effective=0 并排队」；池 `max_capacity` 未配置时保持原有 runner 数约束，不做池级预留。
- **结论**：保留保守语义；如果后续要缩短等待，可把 `dispatching/queued` 从预留计数中拆出，单独用 TTL 管理。

### D3 bootstrap 失败统一 retryable=true

- **位置**：`.github/workflows/eval-shard.yml`（`Report bootstrap failure`）
- **现象**：脚本包/checkout 失败、dispatch 校验失败、execute 异常都发 `runner_bootstrap_failed` 且 `retryable=true`。
- **问题**：dispatch 校验失败更像永久错误，重试可能只是再失败一次。
- **预判**：execute 阶段的 dispatch 已在 prepare 校验过一次，失败通常是 runner 环境/网络瞬时问题；#306 明确要求脚本包被阻断时自动重试。后续可按 `VALIDATE_OUTCOME` 细分永久/可重试。
- **结论**：当前按 #306 验收优先保证「不再空等 3600 秒」；细分留作后续增强。

### D4 flow-online 的外部阻塞

- **位置**：仓库流程树与 GitHub Project
- **现象**：本地 `verify:flow` 与 flow-offline 通过；flow-online 报 `.agents/flow/issues/m8-dataset-image-preflight-ensure.md`、`m9-per-case-badcase-report.md` 本地 done 但 GitHub #290/#288 仍 OPEN，以及 PR 未关联 Project。
- **问题**：这两处不是本 PR 引入（对应文件与 origin/main 一致），且 agent 账号没有 `project` scope，关闭 issue 也超出本 ticket 授权。
- **预判**：需要人把 PR 加入 Project，并决定 #290/#288 是关闭还是改本地状态；处理后重跑 CI 即可。
- **结论**：待人工处理；本 PR 其他检查已全绿。

### D5 取消时失败步骤的执行时机

- **位置**：`.github/workflows/eval-shard.yml`
- **现象**：step 用 `failure() || cancelled()`；GitHub 取消 job 时 step 是否运行取决于取消宽限。
- **问题**：极端情况下取消仍只能靠平台 queue timeout 兜底。
- **预判**：这是 GitHub Actions 的固有边界，不是本 PR 能消除的；平台侧 3600 秒兜底仍在。
- **结论**：接受，并在 PR 风险中写明。
