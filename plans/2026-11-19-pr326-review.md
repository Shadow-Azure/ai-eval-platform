## §1 一页速览

**一句话**：把 `repository_dispatch` 的 `client_payload` 从“10 个键里塞 digest/expires”继续收敛到“只带 job 启动前必须知道的 8 个键”，digest、过期时间改由 manifest 响应头提供、脚本包 pin 继续由 `/scripts` 提供，同时保留 1.0 旧载荷让滚动发布期的在途派发不受影响。

**比喻**：dispatch 就像酒店前台给客人的**房卡**——卡上只印“住哪间、几点退房、去哪个楼栋”，至于房间的实际门锁序列号（digest）、退房绝对截止时间（expiry）和行李寄存柜位置（scripts bundle）不用印在卡上；客人进楼后到服务台（manifest/`/scripts` 端点）凭房卡号现查即可。前台换新版房卡时，旧版房卡（1.0）仍能开同一扇门。

| 交付块 | 用户/运维能看到什么 |
|---|---|
| 派发更稳 | 新建与重试派发固定 8 个顶层键、序列化远小于 60KB，不再挤 GitHub 的 10 键上限；为未来字段留出余量 |
| 服务端 descriptor | manifest 响应带 `X-Manifest-Digest` / `X-Manifest-Expires-At`；`/scripts` 继续返回 content-addressed bundle pin 与下载地址 |
| 兼容旧行 | 1.0 旧 dispatch（带 digest/expires）仍通过契约；旧 outbox 行由 manifest 端点回退到 `client_payload` 取值；已 `sent` 的旧派发无需重写 |
| Runner 消费 | 四个 runner 脚本都是“dispatch 字段优先、响应头回退”，1.1 走头、1.0 走原字段 |
| 一致性 | 创建/派发刷新/重试/spot 回退四条写路径里，outbox 行的 digest 与 manifest 字节、expiry 与响应头保持同源 |

## §2 架构导览

### 2.1 为什么 1.1 只能留 8 个字段

这 8 个字段的共同点是“GitHub 在 job 开始调度前就必须读到”：`runs_on` 决定 `runs-on`（spot 自定义标签是动态的，见 `.github/workflows/eval-shard.yml:383-391`），`job_timeout_minutes` 在 `timeout-minutes` 求值时必须存在（`:405`），`manifest_url` 是启动后的第一跳，其余 5 个是身份/去重键。`manifest_digest`、`expires_at`、`scripts_bundle` 都是“job 已经跑起来之后才能校验/下载”的信息，因此可以下放（issue #323 方案 C 的原始判断）。

### 2.2 契约：`oneOf` 的真实语义

`runner-contract/schemas/v1/dispatch.schema.json:75-99` 的写法是“基础 schema 管公共字段，`oneOf` 分支只加 `schema_version` 的 `const` 与各自必填项”：

- 1.0 分支：`schema_version=1.0` + 必填 `manifest_digest`、`expires_at`（不要求 `runs_on`/`job_timeout`，兼容 #304 之前的旧派发）；
- 1.1 分支：`schema_version=1.1` + 必填 `runs_on`、`job_timeout_minutes`。

仓库里两个校验器都实现了“恰好匹配一个分支”而不是“至少一个”：Python `backend/app/runner_contracts.py:132-147` 与 Node `runner/lib/json-schema-subset.mjs:60-77` 的循环、计数和报错格式相同。我按 7 组 payload 实测（1.1 正例 / 1.1 缺 timeout / 1.0 正例 / 1.0 缺 digest / 1.1 加 3 个多余键 / 1.1 缺 runs_on / 1.0 十键），Python 侧结果全部符合预期；Node 侧同一批语义由 `tests/runner/contracts.test.mjs:90-107` 固定。

一个需要说清的“非缺陷”：**1.1 分支并不禁止 `manifest_digest` / `expires_at`**（分支里没有 `additionalProperties: false` 或 `maxProperties: 8`），所以“8 键”是生产者的约定、不是契约的强制保证；1.1 带 digest 也合法，runner 会优先用 dispatch 里的值。这是有意保留的余量（1.0/1.1 同文件、未来字段继续进 properties），见 D5。

### 2.3 服务端 descriptor：outbox 行是唯一事实源

`backend/app/api/runners.py:707-723` 在返回 manifest 原文（`row.payload_json["manifest_text"]`）的同时构造 descriptor 头，`:730-741` 写进响应：

- `X-Manifest-Digest` 优先取 `row.payload_json["manifest_digest"]`；缺失时才按原文现算（`:713-717`，防御性分支）；
- `X-Manifest-Expires-At` 取 `row.payload_json["expires_at"]`，没有时回退到旧的 `client_payload["expires_at"]`（`:718-723`）——这正是滚动发布期已 `sent` 的 1.0 旧行能继续工作的关键；
- 响应体与摘要同源：`Response(content=manifest_text)` 与摘要计算输入是同一个字符串；`test_runners.py:1148-1176` 断言响应头等于 `sha256(manifest_text)`，我另外用旧行探针确认了回退分支。

`/scripts`（`runners.py:745-849`）没有改：仍从 outbox 行的 `scripts_bundle` 读 pin，没有 pin 才回退 settings，因此 1.1 的 pin 来源不变。

### 2.4 四条写路径的 digest/expiry 一致性

| 路径 | 行 | digest/expiry 写在哪 | 谁读 |
|---|---|---|---|
| 创建分片 | `evaluations.py:552-590` | `manifest_text`、顶层 `manifest_digest`、顶层 `expires_at`，payload 仅 8 键 | manifest 端点读顶层；runner 读响应头 |
| 派发前刷新 | `dispatcher.py:187-241` | 重算 manifest 文本/摘要/新 expiry，写回顶层 `manifest_digest`、`expires_at`；1.0 旧行同时回写 `client_payload` 的同名键 | 同上；旧行 runner 读 payload |
| 重试分片 | `case_attempts.py:1002-1044` | 同创建：1.1 payload + 顶层 digest/expires | 同上 |
| spot 回退 retarget | `spot_fallback.py:350-378` | 只改 manifest 的 `runs_on` 并重算顶层 `manifest_digest`；不改 deadline，所以 expiry 不需要重算；仅当 payload 里仍有 digest 键（1.0）时才回写 | 同上；1.1 无 digest 可改 |

关键不变量：**任何会让 `manifest_text` 变化的路径都同步重算顶层 `manifest_digest`**；expiry 只有在 deadline 被重写时才重算，而 spot retarget 不动 deadline，所以不会出现“manifest 变新、expiry 还是旧值”的错配。刷新路径的 `expires_at = now + max(ttl, deadline_seconds)` 与创建路径的公式口径一致（`max` 而非相加），测试 `test_capacity_scheduling.py:465-479`、`test_execution_timeout_hierarchy.py:146-163` 固定了这一点。

### 2.5 Runner 消费顺序与 fail-open

`runner/lib/dispatch-descriptor.mjs:12-22` 的三行逻辑决定了所有脚本的行为：

- `dispatchManifestDigest = dispatch.manifest_digest || 响应头.manifestDigest || null`：1.0 用旧字段，1.1 用头；两处都没有时返回 null，脚本报“manifest digest 缺失”；
- `dispatchExpiresAt` 同理；
- `isExpired(ts)` 在 `ts` 为空时返回 `false`（不判过期）。

因此组合行为是：1.1 dispatch 先跳过一次判空（无 dispatch expiry），拉 manifest 后再用响应头判过期；1.0 dispatch 在拉取前就会先判过期，拉取后再判一次（两次值相同）。`file://` 本地模式没有响应头，仍依赖 dispatch 自带字段，与旧行为一致。

**fail-open 的说明（非本 PR 引入）**：`isExpired("")/isExpired(undefined)` 都返回 false；旧代码 `Date.parse(undefined) < Date.now()` 得到 `NaN < x = false`，行为相同。也就是说“响应头缺失”时过期校验会被静默跳过——digest 校验仍在，且平台对每条 outbox 行都会返回 expiry，所以当前无实害；若以后要收紧，应改成“缺失即失败”，但那不是本 PR 的回归。

### 2.6 Workflow：这次只改注释，真正消费在 #324 已就位

`.github/workflows/eval-shard.yml` 本 PR 只有 11 行注释变化（`git diff` 确认）。实际行为来自已合并的 #324：prepare 从 `client_payload` 落盘 → 校验 dispatch（`contracts.mjs`）→ 经 `/scripts` 元数据取 pin（`:219-350`）→ plan-cases 里读 manifest 头；execute 用 `runs_on` 与 `job_timeout_minutes`（`:402`、`:405`）。

这里有一个**已接受的设计取舍**：workflow 的 `const pin = dispatch.scripts_bundle || {}`（`:224`、`:437`）在 1.1 下恒为空，`readImageCache()`（`:265-275`）要求 `expected.name && expected.sha256` 才读镜像预置，所以**镜像预置这条“主源”在 1.1 下不会命中**，spot 启动必然走 `/scripts` 元数据 + OSS/代理下载。issue #323 方案 A 已明示该代价（“多一次元数据请求，不影响正确性”），本 PR 不需要修；但步骤注释里的“镜像预置是主源”（`:198-200`）已与实现不符，见 §9。

### 2.7 发布顺序：不存在“1.1 派发撞上旧脚本包”的窗口

我核对了 `.github/workflows/deploy.yml`：`deploy` job 的 `needs` 包含 `scripts-bundle`（`:167`），bundle 先上传 OSS；部署脚本在重启 api/worker 之前先把 `RUNNER_SCRIPTS_BUNDLE_*` 写进主机 `.env`（`:217-220`、`:330-333` 与写 env 步骤）。所以新后端开始发 1.1 时，同一 commit 的新脚本包已经可被 `/scripts` 取到；pin 又冻结在 outbox 行，旧 bundle 也继续存在。**没有“新后端 + 旧 runner 脚本”窗口**。

## §3 数据流走查

场景：完整 bundle 配置下创建一个 3 用例的评测（1 个分片），走 fixed 池。

1. 创建：`build_case_dispatches` 生成 manifest（含 deadline、runs_on、cases），`sha256(manifest_text)` 作为摘要；`client_payload` 固定 8 键（`evaluations.py:552-564`）；outbox 行同时写入 `manifest_text`、顶层 `manifest_digest`、顶层 `expires_at`（`:578-587`）。
2. Worker 取行并 claim（`dispatcher.py:302-315`），`_refresh_dispatch_window` 按当前并发重算 deadline/digest/expiry 并回写（`:187-241`）；随后 pin scripts bundle（`:317-343`），调用 `post_repository_dispatch`（`:381-405`），本地护栏先数键/字节（`github_dispatch.py:75-104`）。
3. GitHub 用默认分支上的 `eval-shard.yml` 起 run。prepare 把 payload 写成 `dispatch.json`，`contracts.mjs` 按 1.1 分支校验，`plan-cases.mjs` 再校验一次并算 case 矩阵。
4. `plan-cases.mjs:58-75`：`isExpired(dispatch.expires_at)` 对 1.1 是 no-op → 拉 manifest（`fetchManifest` 透传两个头）→ 用 `X-Manifest-Expires-At` 判过期 → `dispatchManifestDigest` 取 `X-Manifest-Digest` → `sha256(bytes) === 摘要`。之后校验 manifest 内容与 `dispatch_key`/attempt 一致。
5. execute 每个 matrix case 跑 `real-task.mjs`，同样的 descriptor 逻辑在 `:1053-1071` 再走一遍；manifest 响应同时下发短期 token 与 tasks/model 地址。
6. 回调、心跳、上传、完成/失败链路本 PR 未改。

**1.0 在途变体**：部署前已 `sent` 的旧行不经过刷新；manifest 端点对这类行从 `client_payload` 取 expiry、从顶层取 digest（我用手工探针验证），旧版本 runner 脚本只读 dispatch 字段、新版本优先读 dispatch 字段——两条组合都能跑。部署前还在 `pending` 的旧行会在派发时被刷新，刷新分支会保留 `schema_version=1.0` 并回写 digest/expiry，更新后的 1.0 载荷仍通过契约（探针验证）。

### D5 `oneOf` 没有在契约层锁死“1.1 恰好 8 键”

- **严重度**：低（契约宽松，无实害）
- **位置**：`runner-contract/schemas/v1/dispatch.schema.json:75-99`
- **现象**：1.1 分支只加了 `schema_version=1.1` 与两条 required，不禁止 `manifest_digest`/`expires_at`，所以“1.1 + digest”也是合法载荷（`tests/runner/scenario-helpers.mjs:95` 正好利用这一点模拟篡改摘要；`test_dispatch_loop.py` 只断言生产代码发出的是 8 键）。基础 schema 的 `maxProperties: 10` 也不阻止 1.1 长到 10 键。
- **问题**：契约层面“8 字段”只是生产者约定；将来若有人把 digest 又塞回 1.1 payload，schema 不会拦，runner 会优先用 dispatch 值——如果值过期/不一致，表现为 digest mismatch 或跳过响应头，而不是契约错误。
- **预判**：注意这不是当前 bug（8 键断言 + runner 的 `||` 优先序都按预期工作）；`manifest_digest`/`expires_at` 保留在 properties 里是为了 1.0 兼容与未来余量，删不得。若要把 8 键变成硬约束，只能在 1.1 分支加白名单式 `properties`/`maxProperties`，会牺牲“未来字段继续加”的灵活性，也需要改 1.1+digest 的测试写法。
- **结论**：已拍板并修复（2026-11-19）：1.1 分支加 `maxProperties: 8`，把“恰好 8 键”从生产者约定升级为契约约束；未来新增启动前字段需显式发布 1.2。`manifest_digest`/`expires_at` 仍保留在顶层 properties 供 1.0 分支使用，1.1 夹带时会被 8 键上限拒绝。

## §9 文件级代码分析

新增依赖：无。`runner/lib/mock-platform.mjs` 新引入的 `node:crypto` 是 Node 标准库，runner 仍保持零第三方依赖；后端只用 `hashlib`。

旧代码块取自 `git diff origin/main...HEAD`；旧 outbox 行形状另用 `git show origin/main:backend/app/services/evaluations.py` 核对（顶层只有 `client_payload`/`manifest_text`/`manifest_digest`/`attempt`/`shard_id`，`expires_at` 只在 `client_payload` 里），这是 D2 的对照基线。

### `runner-contract/schemas/v1/dispatch.schema.json`（M，核心）

- 职责：定义 `repository_dispatch` 单分片载荷；本 PR 把版本从“固定 1.0”改成“1.0/1.1 双分支”。
- 关键依赖：schema 是 Python（`runner_contracts.py`）与 Node（`json-schema-subset.mjs`）共同实现的“子集”契约；两边都支持 `const`/`required`/`oneOf`/`maxProperties`，所以选择 `oneOf` 而不是 `if/then` 不会产生实现差异。
- 旧代码 vs 新代码：

  ```jsonc
  // 旧：单一形状
  "required": [..., "manifest_url", "manifest_digest", "expires_at"],
  "properties": { "schema_version": { "const": "1.0" }, ... }

  // 新：公共 required 只保留启动前 6 键，分支各加自己的必填
  "required": [..., "manifest_url"],
  "properties": { "schema_version": { "enum": ["1.0", "1.1"] }, ... },
  "oneOf": [
    { "properties": { "schema_version": { "const": "1.0" } },
      "required": ["manifest_digest", "expires_at"] },
    { "properties": { "schema_version": { "const": "1.1" } },
      "required": ["runs_on", "job_timeout_minutes"] }
  ]
  ```

  这样写的好处是公共约束（键数、长度、正则、`additionalProperties: false`）只维护一份；分支只表达“版本相关的必填项”。实现思路总结：**版本差异用 `oneOf` 表达，公共形状留在顶层；旧字段保留在 properties 里只为 1.0 可读**。
- 检视发现：语义正确，但 8 键不是硬约束（D5）；1.0 分支不要求 `runs_on`/`job_timeout` 是刻意的（旧派发兼容）。

### `backend/app/api/runners.py`（M）

- 职责：manifest 端点从“只回 manifest 原文 + token”扩展为“原文 + digest/expiry 服务端 descriptor”。
- 旧代码 vs 新代码：

  ```python
  # 旧
  manifest_text = row.payload_json["manifest_text"]
  ...
  headers={..., "X-Shard-Dispatch-Key": dispatch_key, **model_headers}

  # 新
  manifest_digest = row.payload_json.get("manifest_digest")
  if not manifest_digest:
      manifest_digest = "sha256:" + hashlib.sha256(manifest_text.encode()).hexdigest()
  expires_at = row.payload_json.get("expires_at") or row.payload_json.get(
      "client_payload", {}).get("expires_at")
  descriptor_headers = {"X-Manifest-Digest": manifest_digest}
  if expires_at:
      descriptor_headers["X-Manifest-Expires-At"] = str(expires_at)
  ```

  实现思路：**行内值优先、现算兜底**；旧行没有顶层 `expires_at` 时回退到 1.0 payload，这正是兼容旧行的关键。
- 检视发现：`manifest_digest` 的现算兜底其实对所有现存行都用不到（创建/重试/刷新/spot 都会写顶层），属于防御性代码，**无实害**；expiry 回退分支无自动化测试（D2，我已手工验证）。

### `backend/app/services/dispatcher.py`（M，核心）

- 职责：派发前按实际释放时间重算 manifest 窗口，并让 outbox 行与响应头保持同源。
- 旧代码 vs 新代码：

  ```python
  # 旧：expires_at 是 datetime，client_payload 无条件写 digest/expires
  client_payload = {**client_payload,
      "manifest_digest": digest,
      "job_timeout_minutes": ...,
      "expires_at": expires_at.isoformat(...)}

  # 新：expires_at 先转字符串；1.1 只补 job_timeout；1.0 旧行才回写 digest/expires
  updated_client_payload = {**client_payload,
      "job_timeout_minutes": job_timeout_minutes(...)}
  if "manifest_digest" in client_payload: ... = digest
  if "expires_at" in client_payload:      ... = expires_at
  row.payload_json = {..., "manifest_digest": digest, "expires_at": expires_at,
                      "client_payload": updated_client_payload}
  ```

  实现思路：**行级字段是新版 runner 的唯一来源；1.0 旧载荷按“原来有才更新”保持形状**，不改 `schema_version`、不新增键，避免 10 键上限被打破。
- 检视发现：逻辑一致；`job_timeout_minutes` 对旧行是无条件更新（旧行本来也会有或补上，仍 ≤10 键）。旧行分支无测试（D2）。

### `backend/app/services/evaluations.py` / `case_attempts.py`（M）

- 职责：创建与重试两条派发写路径改成 1.1，digest/expiry 从 payload 移到 outbox 行顶层。
- 旧代码 vs 新代码（两条路径同构）：

  ```python
  # 旧
  "schema_version": "1.0", ..., "manifest_digest": manifest_digest,
  "runs_on": runs_on, "job_timeout_minutes": ..., "expires_at": expires_at.isoformat(...)

  # 新
  "schema_version": "1.1", ..., "runs_on": runs_on,
  "job_timeout_minutes": job_timeout_minutes(run.case_timeout_seconds)
  # outbox payload_json 顶层多写一个 expires_at
  ```

  实现思路：**payload 只留启动前字段，行内留全部服务端事实**；创建与重试保持同一形状，runner 不需要区分“首跑/重试”。
- 检视发现：两条路径都在构造后调用 `validate_payload`，写错字段会立刻抛 `ContractInvalid`；测试覆盖了创建路径的 8 键，重试路径仅靠运行期校验，无显式断言（§7）。

### `backend/app/services/spot_fallback.py`（M）

- 职责：spot 回退时把 pending 派发的 `runs_on` 改成兜底池标签，并重算 manifest 摘要。
- 旧代码 vs 新代码：

  ```python
  # 旧
  payload["manifest_digest"] = digest
  client_payload["manifest_digest"] = digest   # 1.0/1.1 都会写

  # 新
  payload["manifest_digest"] = digest
  if "manifest_digest" in client_payload:
      client_payload["manifest_digest"] = digest
  ```

  实现思路：**只改仍然携带摘要的旧载荷**；1.1 的摘要从端点取，不需要也不应该往 payload 里加键。
- 检视发现：这里只改 `runs_on`、不改 deadline，所以 expiry 不需要重算；如果将来 retarget 也要改 deadline，必须同步重算 expiry（当前没有调用点会这样做）。

### `runner/lib/dispatch-descriptor.mjs`（A）+ `manifest-source.mjs`（M）

- 职责：把“dispatch 字段 vs manifest 响应头”的优先序收敛到一处，四个脚本复用。
- 旧代码 vs 新代码：

  ```js
  // 旧（每个脚本各写一遍）
  if (Date.parse(dispatch.expires_at) < Date.now()) fail(...);
  const { bytes } = await fetchManifest(...);
  if (sha256(bytes) !== dispatch.manifest_digest) fail(...);

  // 新
  if (isExpired(dispatch.expires_at)) fail(...);
  const manifestResponse = await fetchManifest(...);
  if (isExpired(dispatchExpiresAt(dispatch, manifestResponse))) fail(...);
  const expectedDigest = dispatchManifestDigest(dispatch, manifestResponse);
  if (!expectedDigest) fail("manifest digest 缺失", "manifest_digest_mismatch");
  if (sha256(manifestResponse.bytes) !== expectedDigest) fail(...);
  ```

  实现思路：**助手只做取值，不替调用方决定错误码**，所以各脚本仍保留自己的诊断口径；`fetchManifest` 只多透传两个头，不改变校验责任。比喻：助手像“查号台”，告诉你该去哪个柜台取号，但“号码不对怎么办”仍由各窗口自己喊。
- 检视发现：`||` 优先序会让 1.1 带空字符串 digest 时回退到响应头（`""` 是 falsy）；由于 schema 的 pattern 不允许空串，正常路径走不到，无实害。`isExpired` 的 fail-open 与旧行为等价（§2.5）。

### `runner/scripts/plan-cases.mjs` / `real-task.mjs` / `synthetic-task.mjs` / `trace-e2e-runner.mjs`（M）

- 职责：四个消费点统一改成“先验证 dispatch，再取 manifest，再按优先序校验 digest/expiry”。`synthetic-task.mjs` 还维护了一份本地 `fetchManifest`（未用共享 helper），所以本 PR 在那份副本里也补了同样的两个响应头。
- 检视发现：plan-cases / synthetic-task 有 1.1 测试；real-task 经 `scenario-helpers` 默认 1.1 覆盖；trace-e2e-runner 无自动化（D3）。`trace-e2e-runner` 新增的过期拒绝属于行为变化，但方向与其他三个脚本一致，且手工 E2E 的 dispatch 是刚创建的，不会误伤。

### `.github/workflows/eval-shard.yml`（M，仅注释）

- 旧代码 vs 新代码：diff 只有顶部注释从“payload 带 digest”改成“digest/expiry 从 manifest 响应头、pin 从 `/scripts` 读”；`runs_on`/`timeout-minutes`/`/scripts` 的消费逻辑没有变化（#324 已就位）。
- 检视发现：注释与实现基本一致，只有 M8-47 步骤的“镜像预置是主源”已过时（§2.6）；保留为已知的、issue #323 已接受的取舍。另一个 `runner/workflows/eval-shard.yml` 是私有 runner 仓库的参考模板，本 PR 未改；它只从 payload 读 `job_timeout_minutes`（带 60 分钟回退）并复用同一套 `plan-cases`/`real-task`，1.1 下无需改动。
