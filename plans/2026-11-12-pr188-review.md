## §1 一页速览

**一句话**：管理员在轨迹页一键把**当前 attempt** 的主 Agent 与全部子 Agent 的**原始 native 文件**（不重新序列化）连同 `manifest.json` 打成一个 ZIP 流式下载；只读账号只有禁用入口，缺失对象跳过并在清单里标记 `missing`。

**比喻**：像把一整摞原始录音带装进一只带**装箱单**的箱子。装箱单（`manifest.json`）放在箱子最上面：先告诉你箱里应有几盘带子、每盘的指纹（sha256）、哪几盘没找到（`missing_files`），而不是把缺的带子用空白补上——所以即使有缺失，箱子本身仍然可用，也不会伪装成完整。

| 交付块 | 内容 |
|---|---|
| 入口 | 顶栏主按钮「下载轨迹包」+ Raw source 面板「打包下载」；只读账号禁用并提示权限 |
| 弹窗 | 主/子 Agent 数、原始文件数、ZIP 预估；逐 session 列表（角色、span 数、原生 session id、文件/大小）；ZIP 目录文本预览；权限与缺失说明 |
| 后端 | `POST /api/v1/eval-case-runs/{case_run_id}/trace/export?attempt=<n>`，管理员专属，写 `trace.export.download` 审计 |
| 归档 | 根目录 `trace-<case_key>-attempt-<n>/`，内含 `manifest.json`、`main/`、`subagents/<agent>/`、`unlinked/` |
| 清单 | schema `trace-export/1`、case/eval_run/attempt、parser 版本、session/span 统计、每个文件 sha256/size/路径/`missing`/`size_mismatch` |

## §2 架构导览

### 2.1 路由、权限与响应外壳

入口在 `backend/app/api/traces.py:67-131`。`require_admin`（`backend/app/api/dependencies.py:58-66`）先经 `require_session` 完成登录校验（未登录 401），角色不是 `admin` 即 403，错误体沿用统一的 `error_detail`。导出路由本身是 **POST**，因此不会被浏览器/中间缓存当作可缓存 GET；响应再显式加 `Cache-Control: no-store`（`traces.py:126`）。

租户/项目作用域不是直接读 query 参数，而是 `_scope`（`traces.py:34-44`）用当前 tenant + membership workspace 解析默认 project，再交给 `plan_trace_export`。这层设计与既有 trace 查询一致，新增端点没有自创一套鉴权。

### 2.2 计划层：先把“导什么”变成纯数据

`plan_trace_export`（`trace_export.py:218-307`）不写 ZIP，只产出 `TraceExportPlan`：

1. 复用 `trace_queries.attempt_trace`（`trace_queries.py:315`）解析 attempt。好处是 tree/质量口径只有一份；manifest 实际只用到其中的 `session_count` / `span_count`，而 `attempt_trace` 还会为每个 session 聚合 input/output token 与 cost（`trace_queries.py:391-426`），这部分对导出是顺带开销。
2. 再用 `_case_and_run`（`trace_export.py:178-200`）单独取 case/run，用来生成可读文件名和 manifest 的 case 段。
3. 以 `eval_case_attempt_id + tenant_id` 查 `TraceFile`（`245-254`）与 `TraceSession`（`257-266`），按 `ordinal, id` 稳定排序，再用 `by_file` 把 session 挂回文件（`267-271`）。
4. `archive_root` 由 `safe_segment(case_key)` + attempt 号拼成（`274-277`）；每个文件经 `_session_directory` 决定目录、`safe_segment` 决定文件名、`unique_archive_path` 处理重名（`278-293`）。
5. 一条 `TraceFile` 都没有时直接 409 `trace_export_unavailable`（`255-256`）。

### 2.3 准入磁盘与清单：缺失是数据，不是异常

`_stage_files`（`trace_export.py:310-339`）逐个对象做 `head_object` + `iter_object`，写进 `mkdtemp` 出来的 staging 目录：

- `ObjectMissing`（404）→ `missing=True` 并继续下一个；`ObjectStoreError`（其它存储错误）→ 立即 502 `trace_export_failed`（`313-320`）。
- 已 `head` 成功但 `iter_object` 中途 404 的竞态也按 missing 处理，并删掉半截文件（`327-331`）。
- `head` 报的 size 与 DB 记的 size 不一致 → `size_mismatch`；实际落盘字节数再与 `head` 比一次（`321`、`336-338`）。

`_manifest`（`342-419`）把结果写成可机读的“装箱单”：`files[]` 覆盖全部登记文件（含 missing），`missing_files[]` 单独列原因 `object_missing`，`sessions` 直接复用 `attempt_trace` 的树形 session（`381`）。**清单里没有 `object_key`**，只有 id、`logical_path`、`archive_path`、sha256、size。（`trace` 原始文件内容本身可能含密钥，这是“原始件”语义的必然，权限与审计是它的边界。）

### 2.4 ZIP 构建与大小收敛

`_build_archive_file`（`464-494`）用 `tempfile.TemporaryFile()` 建匿名临时文件，然后最多重写 8 轮：manifest 的 `stats.archive_size` 需要等于最终 ZIP 字节数，而 manifest 自身长度又取决于这个数字的位数。为让不动点快速收敛，唯一被设为 `ZIP_STORED` 的条目就是 manifest（`439-447`），其余文件用 `ZIP_DEFLATED`（`451-455`）；`written == candidate` 即收敛，否则把实测值作为下一轮输入。超过 8 轮则保留最接近的值并再写一次（`481-490`），注释说明这是“从未观测到的病态情况”。

`build_trace_export`（`497-516`）在 `finally` 里 `rmtree` staging 目录，返回一个仍打开着的 `TraceExportArchive`；`iter_chunks`（`165-175`）在生成器 `finally` 里 `close`，从而把临时文件生命周期绑定到流式响应。

### 2.5 前端数据层

`downloadTraceArchive`（`web/src/api/traces.ts:516-559`）刻意绕开 JSON 的 `request` 助手：`fetch` POST、`credentials: same-origin`、`Accept: application/zip`，非 2xx 时先 `notifyUnauthorized` 再解析错误体，2xx 但 `Content-Type` 是 JSON 时也当错误处理（`544-549`），最后 `blob()` 并解析文件名。`parseArchiveFilename`（`436-449`）优先 RFC 5987 的 `filename*`，失败回退 ASCII `filename`，两者都过一遍 `safeArchiveFilename`（去控制字符、取 basename、去前导点、截 180 字符）。错误信封同时接受 `{"error":...}` 与 FastAPI 的 `{"detail":{"error":...}}`（`467-508`）。

### 2.6 前端模型与页面

`traceExportModel.ts` 是纯函数层：`summarizeTraceExport`（`129-200`）把 API 的 session 树按 `parent_session_id` 展平成 `main / subagent / unlinked` 三类并统计；`buildArchiveTree`（`277-324`）把同一个模型渲染成弹窗里的文本目录树。页面 `TracePage.tsx` 只负责组合：`isAdmin` 门控（`517-518`）、`canExportArchive`（`774`）、两个入口按钮（`819-835`、`947-966`）、弹窗（`1034-1162`）与 `saveBlob`（`136-149`）。

### 2.7 原型与样式

原型同步了顶栏主按钮（`prototype/app.js:2326`）、Raw source 小按钮与摘要行（`2350` 附近）以及弹窗（`3564` 起）。生产 CSS 把同样的视觉语言落到 AntD（`trace-viewer.css` 追加 195 行），并补了 640px 以下统计卡两列、会话行换行的降级。

## §3 数据流走查

### 3.1 后端主链

1. 浏览器 `POST /api/v1/eval-case-runs/<case_run_id>/trace/export?attempt=1`（`TracePage.tsx:1058` → `traces.ts:524-532`）。
2. FastAPI 先跑 `require_admin`：未登录 401、非管理员 403（`dependencies.py:58-66`），**不写审计**（测试 `test_export_requires_admin_...:393` 断言）。
3. `_scope` 解析默认 project（`traces.py:77`），进入 `plan_trace_export`（`traces.py:79`）。
4. `attempt_trace` 校验 `case_run.tenant_id / run.project_id`，取 attempt（默认最新，显式则按 `attempt_no`），404 `attempt_not_found` / `eval_case_run_not_found`（`trace_queries.py:323-368`）。
5. `_case_and_run` 二次校验同一作用域（`trace_export.py:185-200`）。
6. 查 `TraceFile`；为空 → `TraceExportError(409, trace_export_unavailable)`（`245-256`）。
7. 查 `TraceSession`，按 `trace_file_id` 分组；`_session_directory` 决定 `main/` / `subagents/<agent>/` / `unlinked/`（`203-215`、`280-293`）。
8. `object_store_from_settings` 未配置 → 503 `object_store_unavailable`（`traces.py:90-96`）。
9. `_stage_files` 逐对象 `head` + `iter`：404 记 missing；其它 `ObjectStoreError` → 502（`trace_export.py:310-339`）。
10. `_build_archive_file` 写 manifest + 文件条目，最多 8 轮收敛 `archive_size`（`464-494`）。
11. `build_trace_export` 删 staging 目录，返回 `TraceExportArchive`（`497-516`）。
12. 写审计 `trace.export.download`（`traces.py:101-118`）并 `commit`；若审计失败先 `archive.close()` 再抛（`119-121`）。
13. 返回 `StreamingResponse`：`application/zip`、`no-store`、`Content-Disposition`（ASCII 回退 + RFC 5987）、`Content-Length=archive.size`、`Referrer-Policy: no-referrer`（`122-131`）。
14. 响应体由 `iter_chunks()` 从临时文件按 64 KiB 读出，结束或断流时 `close()`（`165-175`）。

### 3.2 前端主链

1. `TracePage` 装载 `attemptTraceQuery`；`files`、`trace.attempt.attempt_no` 就绪后 `canExportArchive` 才为真（`TracePage.tsx:772-781`）。
2. 管理员点顶栏「下载轨迹包」→ `setExportOpen(true)`（`829-830`）；只读账号按钮 disabled，hover 显示「仅管理员可下载轨迹包」（`775-780`、`822-830`）。
3. 弹窗渲染 `exportSummary`（`567-575`）与 `exportTree`（`786-791`）：统计卡（`1082-1095`）、包含的会话（`1100-1140`）、ZIP 目录（`1152-1160`）。
4. 点「下载 ZIP · <预估>」→ `archiveDownload.mutate(attemptNo)`（`1058`）→ `downloadTraceArchive`（`traces.ts:516`）。
5. 成功：`saveBlob` 建 object URL、`<a download>` 点击、10s 后 revoke（`TracePage.tsx:136-149`），关闭弹窗并 toast（`696-700`）。
6. 失败：非 2xx 解析错误信封；401 触发全局登出事件；403/409/502/503 的 `message` 直接进 toast（`traces.ts:540-542`、`TracePage.tsx:701-703`）。
7. 文件名：优先取 `Content-Disposition` 的 `filename*`，否则回退 `trace-<caseRunId>-attempt-<n>.zip`（`traces.ts:556-558`）。

### 3.3 一句话看“钱花在哪”

主要成本在**服务端把每个原始对象完整下载两次**（一次 `head` 拿 size、一次 `GET` 落盘），再压缩写第二份临时文件，且整包在响应开始前就构建完毕。内存占用被控制住了（流式 + 64 KiB），磁盘与请求时长没有被控制。

## §6 讨论点

### D1 `unlinked/` 目录的实际归属与 UI/issue 的承诺相反

- **位置**：`backend/app/services/trace_export.py:203-215`（`_session_directory`）对照 `web/src/pages/TracePage.tsx:1142-1145`、`web/src/features/traces/traceExportModel.ts:150-155`。
- **现象**：后端只按 `parent_session_id is None or 不在 known_ids` 判断 → 一律进 `main/`；只有**文件没有任何关联 session** 时才进 `unlinked/`。而前端把 `status === "unlinked"` 与“父 session 不在树里”都判为 `unlinked`，弹窗还明确写「N 个未关联会话会写入 unlinked/」。我已用真实函数实测：`status=unlinked && parent=None` → `main`；悬空父 → `main`；无 session → `unlinked`。Claude Code 解析器在缺少/矛盾父子证据时确实会留下 `status="unlinked"` 且不设 parent 的**子 Agent session**（`claude_code.py:449`、`747-806`），所以这不是理论分支。
- **问题**：用户按弹窗核对“子 Agent 是否齐全”时，ZIP 里子 Agent 的原生文件却躺在 `main/`，看起来像主 Agent 的第二个文件；PR 描述明写按 `main/`、`subagents/<agent>/`、`unlinked/` 归档（issue 目标只列了前两者），08 设计也要求“无法关联的子 session 进入 unlinked 分组”。同一份数据在 UI、manifest 路径和实际目录三处给出不同答案。
- **预判**：这是本 PR 最值得先修的正确性问题，不是文案问题。建议后端把 `status == "unlinked"`（或 parent 悬空）的 session 归到 `unlinked/`，`main/` 只放真正 parent 为空的 root session；同时补一条“unlinked 子 Agent 落 unlinked/”的 API 测试。若决定维持 `main/`，则必须改弹窗文案与前端角色判定，不能让 UI 继续承诺 `unlinked/`。评审收尾时工作区已出现按此方向的未提交修复（`_session_directory` 改为按 status/可解析父分流），待提交后复核。
- **结论**：

### D2 弹窗的 ZIP 目录预览不是权威清单，存在重复与遗漏

- **位置**：`web/src/features/traces/traceExportModel.ts:261-268`（`fileEntries`）、`277-310`（`buildArchiveTree`），对照 `tests/backend/test_trace_export_api.py:338-367`。
- **现象**：后端明确支持“同一 `TraceFile` 同时挂 root 和 child session”，并只归档一次到 `main/`（测试 `test_file_with_root_and_child_sessions_is_archived_once_under_main`）。HEAD 版前端没有任何“已投影”集合：`main` 行和 `subagent` 行各带同一个 `fileName`，目录树会把同一文件同时画进 `main/` 和 `subagents/<agent>/`。反向的遗漏也存在：解析失败等**没有任何 session 的 TraceFile** 后端落 `unlinked/<file>`，前端 `unlinked` 只从 session 行生成，预览里完全不出现——用户看到「原始文件 3」但目录树只有 2 个文件。
- **问题**：弹窗的目录树是用户下载前唯一的“包内容预览”，它应当是 manifest 的投影而不是第二套推导逻辑。现在它既可能重复也可能遗漏，和 08 设计“manifest 是权威”的原则冲突。
- **预判**：评审时工作区已出现一条未提交的去重改动（给 row 加 `fileId`、用 `claimed` 集合跨 `main/subagents/unlinked` 去重，并补 `orphanFiles`），方向正确。更稳的做法是让后端在 plan/预览接口直接给出 `files[].archive_path`，前端只渲染；次优做法是前端以 `files` 为全集、按 `trace_file_id` 归组，任何未认领文件落到 `unlinked/`。建议把这条作为合并前修复项，待该改动提交后复核“重复/遗漏”两类用例。
- **结论**：

### D3 越权、半途失败与边界输入没有测试

### D4 大 attempt 的磁盘与请求时长没有上限

- **位置**：`backend/app/services/trace_export.py:497-516`（`mkdtemp` + `TemporaryFile`）、`310-339`（逐对象全量落盘）。
- **现象**：导出会把该 attempt 的**每个**原始对象完整下载到 staging 目录，再压缩成第二份临时文件；整包在响应开始前构建完毕。没有文件数上限、总字节上限、单对象上限，也没有并发/速率限制。一个 500 文件 × 10 MB 的 attempt 会同时占用约 10 GB staging + 数 GB ZIP，并让 HTTP 请求在代理层空等数分钟。
- **问题**：这是“流式返回”容易造成的错觉——内存确实没有爆，但磁盘和连接时长没有边界；失败时用户只看到超时，审计已记 completed（见 D5）。
- **预判**：不是本 PR 必须解决的阻塞项（真实轨迹通常远小于此），但应在合并前至少记录已知上限，或在 `plan_trace_export` 增加可配置的 `max_files/max_bytes` 并返回可读错误；长期更合适的是异步导出任务 + 完成后通知。建议列入后续 issue，而不是在弹窗里假装“立即完成”。
- **结论**：

### D5 审计在字节真正发出之前就记为 completed

- **位置**：`backend/app/api/traces.py:101-121`。
- **现象**：`record_audit(..., result="completed")` 与 `commit()` 发生在 `StreamingResponse` 返回之前；此后客户端断线、代理中断或读临时文件失败，审计仍然是 `completed`。反过来，`build_trace_export` 成功但审计失败会 500，用户拿不到包（可接受）。
- **问题**：审计的语义是“谁把原始轨迹拿走了”。现在它更接近“谁请求并成功构建了包”，对“是否真正下载完整”不敏感；安全审计场景下这是偏差。
- **预判**：无实害但语义不精确。务实做法是把 `result` 改成 `prepared`/`started` 并在生成器 `finally` 里补一条完成/中断记录（需要独立 session，成本略高）；或至少把 metadata 里加 `streamed=false` 之类的限定，避免过度承诺。建议归后续小 PR。
- **结论**：

### D6 弹窗统计口径与原型细节的偏差

- **位置**：`web/src/features/traces/traceExportModel.ts:197-198`、`web/src/pages/TracePage.tsx:1080-1096`；对照 `prototype/app.js:2350`。
- **现象**：① `estimatedArchiveSize = 原始字节总和 + 8192`，忽略 deflate 压缩与 missing 对象，实际包常显著更小（PR 冒烟 3 文件实际 6459 B，而估算按原始字节 + 8 KB）；按钮却把它当“下载 ZIP · X”展示。② 原型在 Raw source 里加了一行「主 Agent + 1 个子 Agent · 3 个原始文件」摘要，生产只加了「打包下载」按钮，没有这行摘要。③ 原型会话行显示“2 个文件 · 1.2 MB”，生产因 `trace_file_id` 一对一，最多显示“1 个文件”。
- **问题**：预估口径没有在 UI 上解释，容易让用户以为包异常小；原型摘要行的缺失让 Raw source 少了一层“包范围”提示。
- **预判**：都是 Minor。建议把文案改成「预估（未压缩）/ 实际以下载为准」，或在后端 plan 里返回精确的 `archive_size`（需要先构建，代价大）；补上原型那行摘要成本很低。③ 是数据模型差异，不必强行对齐原型。
- **结论**：

### D7 存储异常的类型边界

- **位置**：`backend/app/services/trace_export.py:313-335`；`backend/app/services/object_store.py:235-257`。
- **现象**：`_stage_files` 只把 `ObjectMissing` 与 `ObjectStoreError` 映射为 missing/502。`urllib` 在读取阶段还可能抛 `TimeoutError`/`socket.timeout`（`OSError` 子类）或磁盘写入 `OSError`，这些会冒泡成 FastAPI 500，且不写审计、错误文案是框架默认。
- **问题**：对用户是“未知 500”，对排障是缺少统一错误码；与同文件里其它存储错误 502 的处理不一致。
- **预判**：无实害（网络超时本来就该重试），但建议在 `iter_object`/`_stage_files` 外层再包一层 `OSError` → `TraceExportError(502, ...)`，或把 `object_store` 的读取异常统一成 `ObjectStoreError`。可与 D4 一起做。

### 9.1 `backend/app/services/trace_export.py`（A，530 行）

**职责**：把一次 attempt 的原始 trace 对象打成带 manifest 的 ZIP，并把构建结果交给 API 层流式返回。**依赖**：`zipfile` / `tempfile` / `shutil` 是标准库（构建产物在请求内写盘，无第三方打包依赖）；`object_store.ObjectStore` 负责 HEAD/GET；`trace_redaction.redact_text` 只用于清单里的展示字段；`trace_queries.attempt_trace` 复用作用域与树口径。

```ts
const blob = await response.blob();
```

优点：2xx-JSON 也被当错误、错误信封同时兼容 `error` 与 `detail.error`、文件名解析优先 RFC 5987 并做净化。弱点：没有校验 ZIP 魔数（代理返回 200 HTML 时会落盘成 `.zip` 的 HTML）；`signal` 参数存在但调用方从未传；`blob()` 会把整包读进内存（浏览器端无法避免，除非用 File System Access API）。这些均为 Minor。
