## §2 架构导览

### 2.1 服务端：过滤条件与 join 的边界

`_run_filter_conditions`（`services/evaluations.py:567`）只构造 WHERE 片段；`_run_select`（`:589`）在数据页始终 `outerjoin dataset_version/dataset` 以便返回数据集名与版本，而 count/聚合只有在搜索或数据集筛选时才加 join（`:597` 的 `_needs_dataset_join`）。`dataset_version_id` 没有数据库外键，outer join 保证合成评测（无数据集）不会从列表消失。

### 2.2 聚合口径

`evaluation_list_stats`（`:665`）用 5 条查询分别取：总数、活动数、运行用例数、resolved/scored、平均耗时。活动数用 `ACTIVE_RUN_STATUSES`（`:540`，非终态集合）；解决率按用例加权 `resolved/(resolved+unresolved)`，避免 3 用例的小任务和 500 用例的大任务同权；平均耗时只取同时有 started/finished 的行，在 Python 侧相减以兼容 SQLite/PostgreSQL。

页内每条评测的 resolved/scored 由 `evaluation_case_totals`（`:639`）一次 `GROUP BY eval_run_id` 取回，避免 N+1。

### 2.3 前端：一个筛选状态驱动一切

`EvalsPage`（`EvalsPage.tsx:200`）把 `search` 做 250ms 防抖，筛选值进入 React Query key；请求带 `AbortSignal`，旧请求由 Query 取消。统计卡、表格、空态都读同一个 `listQuery.data`，因此筛选后三处天然一致。

`evalStatus.ts:13` 是唯一的状态文案表；列表、详情、总览都从 `evalStatusMeta` 取标签，避免三页各写一份。

## §3 数据流走查

1. 用户输入「GLM」→ `search` state 更新 → 250ms 后 `debouncedSearch` 变化 → queryKey 变化（`EvalsPage.tsx:215`）。
2. `fetchEvaluations` 拼 `/api/v1/evaluations?limit=50&q=GLM…`（`api/evaluations.ts:703`）→ FastAPI `list_evaluations`（`api/evaluations.py:417`）。
3. service `list_evaluations`（`services/evaluations.py:602`）outer join 数据集、按条件查询 → `evaluation_case_totals` 取页内解决数 → `evaluation_summary` 计算 `resolve_rate` 与 `duration_seconds`。
4. 同一请求里 `evaluation_list_stats` 计算 4 卡数据；响应 `{items, total, stats}`。
5. 前端 `readStats` 解析（`api/evaluations.ts:558`）→ 4 张 `StatusCard`、表格、空态同时刷新；3 秒后自动重查。

## §6 讨论点

### 6.1 平均耗时的样本边界

- 位置：`backend/app/services/evaluations.py:665`、`web/src/pages/EvalsPage.tsx:469`
- 现象：平均耗时把 completed / partial / failed / cancelled 都计入（只要 started 与 finished 都有），而卡片副标题写「按已完成任务平均」。
- 问题：失败与取消任务的耗时是否应该参与「平均耗时」？如果产品只想看成功任务，当前口径会偏低。
- 预判：终态任务的平均完成时间对运营更有信息量，排除失败会掩盖调度/环境问题；保留全终态样本，但把文案改成准确表述。
- 结论：已修复文案为「按终态任务平均」（2026-11-11）；口径不变，后续如有产品定义再调整。

### 6.2 统计聚合的查询成本

- 位置：`backend/app/services/evaluations.py:665`
- 现象：每次列表请求（含 3 秒轮询）执行 5 条聚合查询，其中 resolved/scored 需要对筛选范围内的 `eval_case_run` 做条件求和；目前没有 `result_status` 单列索引。
- 问题：真实规模（数千评测 × 数百用例）下轮询是否会成为数据库热点？
- 预判：当前单租户试点规模可接受；数据量上来后有两个方向——为 `(eval_run_id, result_status)` 建索引，或把 resolved/scored 维护成 `eval_run` 计数快照。
- 结论：本 PR 接受现状，已在 PR「未覆盖」记录；不在 M5-16 内做迁移。

### 6.3 数据集筛选只加载前 50 个数据集

- 位置：`web/src/pages/EvalsPage.tsx:475`（`fetchDatasets` 固定 `limit=50`，`api/datasets.ts:144`）
- 现象：数据集超过 50 个时，下拉里看不到后面的数据集。
- 问题：是否需要服务端搜索/分页？
- 预判：当前数据集目录规模很小；等目录分页（m5-13）稳定后复用同一查询参数即可。
- 结论：记录为后续优化，不在本 PR 扩大范围。

### 6.4 m5-17 尚未在自己的 issue 里引用 ADR

- 位置：`.agents/notes/adr-0002-eval-run-status-enum.md`、`.agents/flow/issues/m5-17-eval-detail-entry.md`
- 现象：ADR 已在「适用 issue」写明 m5-16/m5-17，但 m5-17 issue 的 `adr` 字段仍为空。
- 问题：验收第 3 条要求「被 m5-16/m5-17 共同引用」。
- 预判：修改 m5-17 文件超出本 issue 的 scope；#145 落地时补一行 `adr` 引用即可，ADR 本身已可供其引用。
- 结论：本 PR 只更新 m5-16 的 `adr`；#145 实现时补引用。

### 6.5 分页测试的时序脆弱性

- 位置：`tests/backend/test_evaluations.py:329`
- 现象：原断言用「offset=1 的 id ≠ q=codex 的 id」，但三条评测同一秒创建、按 UUID 兜底排序，offset=1 可能正好是 Codex 那条。
- 问题：随机失败会污染 CI。
- 预判：断言只需证明 offset 生效且返回的是集合内条目即可。
- 结论：已改为「返回条数 1 且 id 属于全集」（2026-11-11），复跑通过。

## §9 文件级代码分析

### 9.1 `backend/app/services/evaluations.py`

职责：评测列表查询、页内用例汇总与统计聚合。

旧代码（`git show origin/main:backend/app/services/evaluations.py`）：

```python
def list_evaluations(session: Session, *, limit: int = 50) -> tuple[list[EvalRun], int]:
    query = select(EvalRun).order_by(EvalRun.created_at.desc(), EvalRun.id.desc()).limit(...)
    items = list(session.scalars(query))
    total = int(session.scalar(select(func.count()).select_from(EvalRun)) or 0)
    return items, total
```

新代码（`:602`）：

```python
rows = session.execute(
    _run_select(EvalRun, Dataset.name, DatasetVersion.version, joins=True)
    .where(*conditions).order_by(...).offset(offset).limit(...)
).all()
```

变更思路：过滤条件下推到 SQL；数据集标签随行返回，页面不用再发 N 个详情请求；统计聚合独立成函数，创建/详情路径不受影响。实现要点：outer join 保证无数据集的合成评测仍在列表；`_as_utc` 统一 SQLite naive 与 PostgreSQL aware 的时间差计算。

检视发现：`evaluation_list_stats` 的 5 条查询可合并为 2 条，但可读性会下降；当前保留，已有性能记录。

### 9.2 `backend/app/api/evaluations.py`

职责：HTTP 参数校验与响应组装。

旧代码只接收 `limit`；新代码（`:417`）接收 `q/status/dataset_id/offset`，未知 status 返回 422 `evaluation_invalid`，并在一次 `now` 下组装所有 item，避免同一页内耗时口径漂移。实现思路：参数校验留在 API 层，聚合细节留在 service。

检视发现：未知 `dataset_id` 不报错而是返回空列表，符合筛选语义（可对比 `/datasets` 的 404 行为）；不修改。

### 9.3 `web/src/pages/EvalsPage.tsx`

职责：评测列表页。

旧代码是「状态/进展/创建/操作」四列 + antd 默认空态；新代码（`:310`）补 Agent/模型、数据集、解决率、开始时间列，`:435` 起是 4 张统计卡，`:475` 是筛选栏，`:516` 起区分空态与无结果态。

变更思路：所有筛选进入 queryKey（`:215`），页面不再对数据做二次过滤；解决率与耗时只格式化服务端值。实现总结：服务端是唯一事实源，前端只做展示与交互。

检视发现：`合成评测` 入口保留在筛选栏右侧，属于线上保留能力，原型没有；已在 PR 说明。

### 9.4 `web/src/utils/evalStatus.ts`

职责：11 个状态的中文标签、Tag 颜色与原型 tone。旧代码在列表/详情/总览各写一份，且列表缺 preparing/finalizing/cancelling；新代码集中一份，三页复用。检视发现：`ACTIVE_EVAL_STATUSES` 目前只导出未使用，保留给 m5-17 的进度条使用。

### 9.5 `tests/backend/test_evaluations.py`

新增 2 个用例：服务端过滤/分页/非法状态；数据集/Agent 列、统计聚合与 partial 解决率。检视发现：分页断言时序问题已修（§6.5）。
