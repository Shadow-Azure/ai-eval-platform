## §1 一页速览

**一句话**：给评测题面加一张可选的“便利贴”——prepare 时冻结、创建时随 run 落库、Runner 在 problem_statement 之后追加 `## Additional instructions`，前端可填写、确认与回看；空值逐字节保持原题面。

**比喻**：像寄快递时在面单后附一张说明卡。仓库里的数据集（面单）不动，说明卡随本次运单（eval_run）一起冻结；同一快照的后续分片都用同一张卡。

| 交付块 | 内容 |
|---|---|
| API | `prompt_suffix` 可选、≤4000；prepare 与 direct create 均接受 |
| 冻结 | snapshot + summary + identity；digest 覆盖 |
| 存储 | `eval_run.prompt_suffix` + 0022 迁移（server_default ""） |
| 执行 | 每个 case 任务携带；Runner 拼接为 `${prompt}\n\n## Additional instructions\n${suffix.trim()}` |
| UI | 第 3 步 textarea、第 4 步确认行、右侧摘要、评测配置 |

**验证基线**：targeted backend 83 passed；runner 95 passed；全量 backend 726 passed / 1 skipped；web build 通过；本地真实前后端冒烟 5/5。

## §3 数据流走查

1. 向导第 3 步输入 → `draft.promptSuffix`（本地 draft 持久化，读取时截断 4000）→ prepare 负载 trim 后为空则不发。
2. prepare → `build_preparation` strip → snapshot/summary/identity；两个不同 suffix 的 preparation digest 不同。
3. create（preparation 路径）→ `consume_preparation` 读 snapshot → `EvalRun.prompt_suffix`。
4. create（direct 路径）→ payload 直接落库（见 §6.1）。
5. 调度 → 分片任务每个 case 带 `prompt_suffix`。
6. Runner → `composePrompt(problem, suffix)` → `buildPrompt` → `claude -p` 的 PROMPT / 轨迹用户消息。
7. 详情 API → summary `prompt_suffix` → 前端评测配置。

**例子**：题面 `Fix the separable model bug.`，suffix `非交互评测…` → Runner 收到的题面是 `Fix the separable model bug.\n\n## Additional instructions\n非交互评测…`；suffix 为空 → 原题面逐字节不变。

## §6 讨论点

### 6.1 direct create 未规范化（P3，本 PR 修复）

`create_synthetic_evaluation` 落库为 `prompt_suffix or ""`（`evaluations.py:288`），而 prepare 路径已 strip。经 direct API 提交仅含空白的 suffix 时，run 记录会是空白字符，评测配置显示“已配置”而 Runner 拼接时又会 trim，前后不一致。修复：落库前统一 `.strip()`，并补 direct create 的空白用例。

### 6.2 部署前 active preparation 会失效（P3，接受并写发布说明）

identity 新增 `prompt_suffix` 键（`preparations.py:392`）。部署前创建、部署后仍在有效期内的 preparation 其存储 identity 没有该键，consume 时会得到 `409 configuration_changed["prompt_suffix"]`。`eval_preparation_ttl_seconds` 默认 900 秒，影响窗口短；建议在发布说明提示重新 prepare，不在本 PR 加兼容分支。

### 6.3 缺少真实轨迹的端到端断言（P3，后续可选）

`composePrompt` 有单测、`real-task.mjs` 只有一行 wiring；没有测试断言最终轨迹用户消息包含追加段。可在后续用 fake docker 捕获 PROMPT 环境变量增强，或在生产 SuperPower 评测的轨迹里人工确认。

### 6.4 prepare 顶层与 summary 重复暴露（P3，保留）

prepare 响应同时返回顶层 `prompt_suffix` 与 `summary.prompt_suffix`；与其他已冻结字段的返回形态一致，无害，保留。

## §9 文件级代码分析

- `backend/app/api/evaluations.py`：两个可选字段与两处透传；prepare 与 direct create 的语义分开，preparation 路径以快照为准。
- `preparations.py`：单一 `strip()` 入口；identity 覆盖是“可复现”的关键；consume 只读快照，避免二次解释。
- `evaluations.py`：落库与 summary 为单一事实来源；summary 返回空串而非 null，前端无需兼容 null。
- `0022` 迁移：`server_default=""` 让旧行安全；down 只 drop 列，符合本仓迁移风格。
- `runners.py`：按 case 放字段，利用既有 `buildCaseTasks` 展开，避免改任务包库。
- `prompt.mjs`：唯一拼接点，空/空白返回原串，便于测试与复用。
- `real-task.mjs`：wiring 在 `buildPrompt` 之前，保持数据集约束仍在题面内。
- `EvalWizardPage.tsx`：草稿持久化 + 4000 截断 + trim 后省略；与原型文案一致。
- `EvalDetailPage.tsx`：读 run summary 字段，避免依赖 `/config` 快照，空值显示“未设置”。
- 测试：prepare/create/task payload/迁移头 + composePrompt 边界，覆盖主要路径；direct create 空白、真实轨迹为已知缺口。
