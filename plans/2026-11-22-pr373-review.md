## §1 一页速览

一句话：把“先领票再排队”改成“排到号再领票”——Runner 拿到容量之前不再请求 `/tasks`，因此平台不会提前签发会过期的镜像 tarball URL。

一个比喻：旧流程像在演唱会开场前两小时就把入场二维码打印好，然后让人在门口排两小时队；二维码 60 分钟后失效，排到时已经刷不进去。新流程是排到检票口、确认有座位后才生成二维码，二维码只需要覆盖走到座位的那几分钟。

## §2 架构导览

1. **调度入口**：`main()` 仍提前拉取 manifest（`runner/scripts/real-task.mjs:1124` 附近），因为 token、deadline、digest 校验需要它；但不再提前拉 `/tasks`。`fetchTasks()` 被抽成闭包（`:1176-1193`），只在 case 循环里调用。
2. **容量准入**：每个 case 先 `postStartedWithCapacityWait`，429 时继续等待（`:1481` 附近），2xx 后才进入 `try` 块。`/tasks` 的首次请求在 `:1555`，位于 `started` 成功之后、镜像下载之前。
3. **镜像加载**：`loadImageTarball()` 现在用 `curl --write-out %{http_code}` 记录真实 HTTP 状态（`runner/lib/image-tarball.mjs:137-145`）；`loadImageTarballWithRefresh()`（`:215`）只在 401/403 时调用刷新回调，并且只重试一次。
4. **平台签发**：`shard_tasks` 每次响应都调用 `task_image_tarball(settings, image)`（`backend/app/api/runners.py:1121`），所以 Runner 在容量准入后重新请求即可拿到新 URL；API 结构不变。
5. **TTL**：`presign_ttl_seconds()`（`backend/app/services/dataset_image_tarballs.py:35`）从 900s 下载预算加 300s 余量得到 1200s；配置默认值同步改为 1200（`backend/app/config.py:41-45`），不再引用 `case_timeout`。

## §3 数据流走查

1. GitHub job 启动 `real-task.mjs`，拉 manifest，验证 token/digest/deadline；此时**不**请求 `/tasks`。
2. 取到本 case，调用 `started` 回调；平台并发已满时返回 429，Runner 按 `case_timeout + 300s` 的预算等待。
3. `started` 返回 2xx，写 `.started-*` 标记，发 heartbeat，然后调用 `fetchTasks()`。
4. 平台处理 `/tasks`，为分片内每个 case 现签一个 1200s 的 OSS 内网 GET URL；Runner 只取当前 case。
5. `realCase` 先 `docker image inspect`；未命中才下载。首次下载若返回 403，`loadImageTarballWithRefresh` 调用 `refreshTask` → 再次 `/tasks` → 用新 URL 重试一次。
6. 第二次仍失败（或 404/超时/损坏/load 失败）则回退 `image_sources`；诊断记录 `http_status`、`cause`、`retried`，但不记录签名 URL。
7. 镜像就绪后继续 checkout、Agent、评分、回调，与旧流程一致。

## §6 讨论点

### 6.1 `/tasks` 5xx 的失败回调仍标记 `retryable: false`

- **位置**：`runner/scripts/real-task.mjs:1184`、`:1597-1620`
- **现象**：`fetchTasks` 对 5xx 抛 `callback_retryable`，但 case 失败回调的 `retryable` 字段是既有 catch 里硬编码的 `false`。
- **问题**：平台按 payload 的 `retryable` 决定是否重排 attempt；5xx 本来是瞬态故障，却可能被永久结算。
- **预判**：这是既有 catch 的统一语义，本 PR 只新增了一个进入该 catch 的瞬态分支；改动它会同时影响 image/pull 失败的既有行为，建议单独评估。
- **结论**：

### 6.2 TTL 仍可被环境变量覆盖为长值

- **位置**：`backend/app/config.py:41-45`、`backend/app/services/dataset_image_tarballs.py:35-40`
- **现象**：默认值已降到 1200s，但 `DATASET_IMAGE_TARBALL_TTL_SECONDS` 仍可设成 3600 或更大。
- **问题**：误配置会重新扩大不可撤销 bearer URL 的暴露面。
- **预判**：保留覆盖是运维逃生口；ADR 已明确不推荐长 TTL，是否要加硬上限需要产品决定。
- **结论**：

### 6.3 没有端到端 403 刷新用例

- **位置**：`tests/runner/image-tarball.test.mjs:169-240`
- **现象**：刷新逻辑由模块单测覆盖，`/tasks` 顺序由 `case-entry` 覆盖；没有一条同时经过 `realCase` 的集成用例。
- **问题**：若未来有人改动 `realCase` 与 `refreshTask` 的接线，单测不会失败。
- **预判**：当前接线只有三行，且 mock Docker 的集成成本较高；可作为后续测试债务。
- **结论**：

### 6.4 分片模式下每次 `/tasks` 会重签全分片 URL

- **位置**：`runner/scripts/real-task.mjs:1555`、`backend/app/api/runners.py:1121`
- **现象**：无 `--case` 的整分片模式每跑一个 case 都请求一次 `/tasks`，平台会为分片内所有 case 重新签发。
- **问题**：256 用例分片会产生额外签名开销。
- **预判**：生产 execute job 是 matrix 一 job 一 case，整分片模式主要用于本地/兼容；专用按 case 端点属于 issue #371 的非目标。
- **结论**：

## §9 文件级代码分析

### 9.1 `runner/scripts/real-task.mjs`

职责：单个 execute job 的入口；解析 manifest、等待容量、逐个 case 执行 Agent 并回传结果。变更形态：M。

关键依赖：`fetch`（Node 内置 HTTP 客户端）负责 `/tasks`；`loadImageTarballWithRefresh` 负责镜像下载与一次刷新。这里没有新第三方依赖。

变更前（启动时取全部任务）：

```js
let taskByCase = new Map();
if (tasksUrl) {
  const tasksResponse = await fetch(tasksUrl, ...);
  if (tasksResponse?.ok) taskByCase = buildCaseTasks(taskPayload);
}
// 之后才进入 started 的 429 容量等待
```

变更后（容量准入后按 case 取）：

```js
const fetchTasks = async () => { /* GET tasksUrl，失败抛带 code 的错误 */ };
// ...
const startedResult = await postStartedWithCapacityWait(...);
if (startedResult.status === 429) { /* 继续等 */ }
// 2xx 之后：
const taskByCase = await fetchTasks();
task = taskByCase.get(item.case_run_id) ?? null;
```

实现思路：把“签发时机”从 job 启动挪到 `started` 2xx 之后，同时保留整分片模式的兼容路径；`refreshTask` 复用同一个 `fetchTasks`，保证刷新也走同一 token 与错误处理。

检视发现：无阻断缺陷；`retryable` 语义见 6.1。

### 9.2 `runner/lib/image-tarball.mjs`

职责：下载、`docker load`、校验 OSS tarball，并向调用方报告可回退的结构化结果。变更形态：M。

关键依赖：`runCommand`（项目内的异步子进程封装）执行 `curl` 与 `docker`；`curl --write-out` 是 curl 自带能力，不新增依赖。

变更前（只靠 stderr 文本判断失败）：

```js
const download = await run("curl", ["-fsSL", "--max-time", ..., "-o", tarPath, url]);
if (download?.status !== 0) return finish("download", stderr);
```

变更后（记录状态码，鉴权失败刷新一次）：

```js
const download = await run("curl", [..., "--write-out", "%{http_code}", ...]);
result.httpStatus = parseHttpStatus(download?.stdout);
if (isTarballAuthFailure(result)) {
  const refreshed = await refresh();
  if (refreshed?.url && refreshed.url !== tarball.url) return loadImageTarball(refreshed, options);
}
```

实现思路：用 HTTP 状态区分“凭证被拒”和“对象不存在”；刷新只发生在 401/403，且最多一次，避免把过期凭证变成无限重试。

检视发现：无阻断缺陷；404 与刷新失败都有单测。

### 9.3 `backend/app/services/dataset_image_tarballs.py` 与 `backend/app/config.py`

职责：派生确定性 OSS key、签发 per-case GET URL；配置默认值。变更形态：M。

关键依赖：项目自带的 SigV4 预签名实现（`object_store.py`），没有新增依赖。

变更前：

```python
ttl = max(60, int(settings.dataset_image_tarball_ttl_seconds))  # 默认 3600
```

变更后：

```python
DOWNLOAD_BUDGET_SECONDS = 900
DOWNLOAD_MARGIN_SECONDS = 300
PRESIGN_TTL_SECONDS = 1200
ttl = presign_ttl_seconds(settings.dataset_image_tarball_ttl_seconds)
```

实现思路：TTL 只表达“一次下载需要多久”，不再读取 `case_timeout` 或容量等待上限；保留配置覆盖和 60s 下限。

检视发现：无阻断缺陷；覆盖值的上限见 6.2。
