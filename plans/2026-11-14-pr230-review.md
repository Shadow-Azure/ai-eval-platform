## §1 一页速览

一句话：部署成功后，把本机 Docker 镜像收敛到“当前正在用的 + 上一版可回滚的 + 每个仓库最近 3 版”，其余按 id 删除，删不掉只告警。

比喻：远端 ACR 是图书馆书库（按 digest 永久留档），ECS 本机只是借阅台。借阅台只需要摆着正在读的书、上一本可退回的书和最近借过的几本；以前每借一本都堆在台面上，71 次部署后堆了 22.5G。

## §2 架构导览

### 2.1 配置与仓库识别

`deploy/common.sh:138` 把保留窗口固定为默认 3，`IMAGE_PRUNE_DF_PATH` 默认 `/`。`app_image_repositories`（`deploy/common.sh:147`）从 `API_IMAGE`、`WEB_IMAGE`、`RUNNER_EGRESS_PROXY_IMAGE`、`PROXY_IMAGE` 里剥掉 `@sha256:...` 或 `:tag`，去重后作为“本部署拥有的仓库”白名单；`postgres`、`redis` 这类基础镜像因此永远不是候选。

### 2.2 keep 集合的三层来源

`prune_old_images`（`deploy/common.sh:169`）先枚举候选行，再依次加入：

1. `docker ps -q` + `docker inspect --format '{{.Image}}'` 得到运行中容器使用的镜像 id（`deploy/common.sh:233`）；
2. `previous_image_references`（`deploy/common.sh:163`）读取 `.state/previous.env` 的 API/WEB 引用，digest 形式按 RepoDigest 匹配、tag 形式按 `repo:tag` 匹配（`deploy/common.sh:247` 起）；
3. 每个仓库按 `CreatedAt` 倒序的前 N 个不同镜像 id（`deploy/common.sh:261` 起）。

候选 id 去掉 keep 集合后逐个 `docker image rm <id>`（`deploy/common.sh:288`）。失败只累加 `PRUNE_FAILED` 并打印 daemon 的错误，不中断循环。

### 2.3 非致命调用

`deploy/deploy.sh:111` 在 `/readyz` 成功后、写 deployment 记录前调用：

```bash
stage_begin image_prune
if prune_old_images; then
  stage_finish success "..."
else
  stage_finish skipped "镜像清理失败，已跳过；部署保持成功"
fi
```

放在 `if` 条件里有两个作用：Bash 的 `ERR` trap 不会对函数体内失败的命令触发（所以不会走 `on_error` 回滚），函数返回非零也只落到 `skipped` 分支。清理阶段随后随 `record_deployment succeeded` 一起写入 `deploy_stages`。

### 2.4 测试替身

`tests/deploy/image-retention.test.mjs` 在临时目录里放一个假 `docker`，它支持被测代码用到的四种调用（`ps -q`、`inspect --format`、`image ls --digests --format`、`image rm`），并把删除记录到 `removed` 文件，从而能断言“删了哪些、没删哪些、重跑还删不删”。这比只对脚本文本做 `includes` 断言更能锁住行为。

## §3 数据流走查

1. 部署 workflow 用 digest 拉起新 api/web/proxy，`/readyz` 通过。
2. `deploy.sh` 早先把旧 `.env` 的 API/WEB 写进 `.state/previous.env`，这就是回滚目标。
3. 进入 `image_prune`：枚举本机所有镜像 → 过滤出三个平台仓库 → 收集运行中 / previous / 最近 N 版 → 其余按 id 删除。
4. 输出 `retention=... kept=... removed=... failed=...` 与 `df -h /` 行，经 SSH 直接进入 Actions 日志。
5. `record_deployment succeeded` 把包含 `image_prune` 的阶段明细写入 deployment 记录。

## §6 讨论点

### 讨论点 1：保留窗口按“镜像构建时间”而不是“部署顺序”排序

- **位置**：`deploy/common.sh:213`（`sort -t'|' -k5,5r`）
- **现象**：窗口取 `docker image ls` 的 `CreatedAt`（镜像构建时间）倒序前 N 个。
- **问题**：如果有人用 `workflow_dispatch` 重新构建一个旧 commit，它的构建时间变新，可能把真正较新的部署版本挤出窗口。
- **预判**：main 的正常路径是按合并顺序构建、部署，构建时间与部署顺序一致；被挤出的旧版本仍在 ACR 中，可重新 pull，回滚目标 `.state/previous.env` 又单独保留，所以影响有界。若以后需要严格“最近 N 次部署”，可在本机维护一个 `.state/image-history` 文件，以部署顺序而非构建时间计算窗口。
- **结论**：待用户拍板是否需要更强的部署顺序语义。

### 讨论点 2：清理发生在 pull 之后，不能预防“部署前磁盘已满”

- **位置**：`deploy/deploy.sh:70`（`compose pull`）与 `deploy/deploy.sh:111`（prune）
- **现象**：如果下次部署开始时磁盘已满，`pull` 可能先失败，清理没有机会执行。
- **问题**：是否需要在 pull 前也做一次更保守的清理？
- **预判**：issue 的验收明确是“部署成功后自动清理”；当前诊断已人工回收约 16G，且每次成功部署都会把窗口收敛回 N 版，正常情况不会再次涨满。pull 前清理需要另一套只保留运行中 + previous 的 keep 集合，复杂度更高；可等真的复现“pull 时满盘”再加。
- **结论**：待用户确认是否作为后续增强。

### 讨论点 3：VPC 规范化之前的公共 registry 旧镜像不在清理范围

- **位置**：`deploy/common.sh:147`（仓库白名单来自当前 `API_IMAGE`）
- **现象**：`normalize_images` 从 2026-11-09（#12）起把 API/WEB 改写成 ACR VPC 域名；更早按公共域名拉取的旧镜像仓库名不同，不会命中白名单。
- **问题**：这部分是一次性历史残留，而不是持续增长。
- **预判**：不影响“连续多次部署后保持有界”的验收；首次部署后用 `docker image ls` 人工确认即可，必要时手工删一次。不建议为历史命名写特判。
- **结论**：待用户确认是否需要一次性清理。

### 讨论点 4：部署页不展示 `image_prune` 阶段

- **位置**：`backend/app/services/deployments.py:38`（`STAGE_DEFINITIONS` 固定五阶段）
- **现象**：阶段明细写入了 `detail_json`，但前端只渲染五个既定阶段，清理阶段不在页面上。
- **问题**：是否需要把清理做成第六个可见阶段？
- **预判**：issue 只要求 Actions 日志可见；新增可见阶段会改前端与原型（超出本 PR 的 scope），先保留内部记录。
- **结论**：待用户决定是否另开 UI issue。

### 讨论点 5：`docs/architecture.md` 未记录保留策略

- **位置**：`docs/architecture.md`（部署段）
- **现象**：现状文档没有描述镜像保留窗口，只有 `plans/` 设计文档补了。
- **问题**：`docs/**` 不在 #228 的 scope 内。
- **预判**：合并后按“现状进 docs”规则补一段，或随下一次部署文档整理一起做。
- **结论**：待用户确认是否另开文档 issue。

## §9 文件级代码分析

### `deploy/common.sh`

变更形态 M（+182）。新增四个函数：`image_short_id` 把 `docker inspect` 的 64 位 id 截成与 `docker image ls` 一致的 12 位；`app_image_repositories` 生成白名单；`previous_image_references` 只读 `.state/previous.env` 的两行；`prune_old_images` 是主流程。

实现思路：先在临时目录把“候选 / 保留 / 版本窗口”落成文本文件，再集合相减得到删除清单。这样避免依赖 Bash 4 的关联数组，macOS 的 Bash 3.2 也能跑测试。窗口上限 10（`deploy/common.sh:184`–`188`）是防止误配成 50 后清理形同虚设。删除用短 id 而不是 reference，避免 `<none>:<none>` 标签问题。

检视发现：候选只来自当前配置的仓库，历史公共域名镜像不覆盖（讨论点 3）；`PRUNE_KEPT` 是“计划保留数”，删除失败的镜像会同时出现在 kept 与 failed 计数里，日志已用独立 `failed` 字段表达，语义可接受。

### `deploy/deploy.sh`

变更形态 M（+11）。把清理放在健康检查之后、deployment 记录之前，并包在 `if` 中。这是本 PR 最关键的非功能要求：issue 明确“失败时给出明确日志，不把已完成的部署判为失败”。`if` 条件同时让 `ERR` trap 失效，避免误触发 `on_error` 里的自动回滚。

检视发现：无。清理耗时与 daemon 卡死没有单独超时；按 136 个旧镜像的规模，`docker image rm` 是本地操作，仍在 30 分钟 job 超时内。

### `tests/deploy/image-retention.test.mjs`

新增 A（332 行）。假 docker 是行为替身而非文本匹配：`image rm` 会真的从 `images.tsv` 删除并记录，因此幂等测试有意义。8 个用例分别锁住保留集合边界（`191`）、幂等（`207`）、删除失败容错（`222`）、N 非法/上限（`236`）、基础镜像不受影响（`249`）、`deploy.sh` 调用位置（`260`）、脚本契约（`274`）与 daemon 不可用时 ERR trap 不触发（`292`）。

检视发现：真实 Docker daemon 的 `--digests`/`CreatedAt` 输出格式没有被本机 daemon 实测（本机 daemon 未运行），属于测试替身的固有边界；首次生产部署的日志可作为最终验证。

### `plans/m1-02-fullstack-design/10-deployment-testing-and-review.md`

变更形态 M（+4/−1）。在交付流水线里补“清理旧镜像”一步与 best-effort 说明，并把“镜像保留窗口边界”加入 Deployment 测试层。属于设计对齐，不改产品 UI，因此没有 `prototype` 差异。
