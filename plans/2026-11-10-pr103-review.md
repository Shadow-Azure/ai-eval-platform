## §1 一页速览

**一句话**：当模型网关的水表走到头，评测不再“失败”，而是像断路器跳闸一样停在 `paused_budget`；用户加钱、确认后，只把没跑完的用例重新送上流水线。

**一个比喻**：`model_usage` 是电表，`budget_version` 是合同版本号。电表到额度时，网关先拉闸（402），调度器把已派发但没启动的 Job 取消，正在跑的 Agent 允许把手里产物交回来；等所有 attempt 收口，页面出现“预算已暂停”。用户签补充协议（resume-budget）时，服务端校验合同版本号，原子加预算、盖章（审计）后，只重排未完成用例。

**交付块**：

| 块 | 内容 |
|---|---|
| 状态机 | `queued/running → pausing_budget → paused_budget → queued`，`paused_budget` 非终态 |
| 数据 | `eval_run` 三个字段 + `0014` 迁移 |
| 服务 | `services/budget.py`、`reconciler` 每轮对账、`dispatcher` 暂停态保护 |
| API | `POST /api/v1/evaluations/:id/resume-budget` |
| UI | 详情预算卡片 + 暂停告警 + 二次确认弹窗；列表状态标签 |
| 测试 | 11 个预算测试 + 网关撤销测试 + 全量回归 |
| 证据 | 同场景 Before/After 截图、结构化检视、冒烟报告 |

**验证基线**：后端全量 pytest 404 passed / 1 skipped；受影响子集 94 passed；`npm run build`、`npm test`、`verify:flow`、`lint:docs` 通过。CI 唯一未通过项是 PR 未关联 GitHub Project（权限/人工操作，见 §6.9）。

## §2 架构导览

### 2.1 数据模型：把“已花多少、预算第几版、为什么停”落到 run 上

`eval_run` 原本只有 `model_budget_usd`（`backend/app/models/evaluation.py:77`），没有权威花费快照、版本和暂停原因。本 PR 增加三列（`evaluation.py:78-86`）：

```text
budget_spent_usd  Numeric(12,6) NULL   最近一次对账的花费快照（权威值仍是 ModelUsage SUM）
budget_version    Integer NOT NULL 1   恢复时的乐观版本号，初始 1
pause_reason      String(64) NULL      budget_exceeded 等非终态暂停原因
```

迁移 `0014_budget_pause_resume.py` 是 expand-only：`budget_version` 带 `server_default="1"`，另外两列可空，旧镜像滚动部署时仍能读表（设计 05 §9）。

**为什么快照不是权威值**：模型网关每次请求都要判断“是否到预算”，如果每次都改 run 行，会把并发模型调用串行化在同一个行锁上。因此 `model_usage` 是权威值，`budget_spent_usd` 只是列表/暂停时展示的快照，由 worker 每轮和暂停入口刷新（`budget.py:307-350`）。

### 2.2 触发：网关的 402 同时是平台级暂停开关

网关鉴权顺序在 `backend/app/api/model_gateway.py:72-107`：

1. 校验 token 与 run/shard/attempt 绑定；
2. `ensure_budget` 用 **run 当前预算**（不是 token 签发时的快照）比较 `ModelUsage` 累计花费（`model_gateway/service.py:135-160`）；
3. 超预算返回 `402 budget_paused`；
4. `_authorize` 的异常分支记录一条 `budget_paused` usage，并调用 `budget_service.pause_for_budget(..., source="model_gateway")`（`api/model_gateway.py:84-101`）。

```python
# api/model_gateway.py:88-98（节选）
try:
    service.record_usage(session, claims, config, status="budget_paused")
except Exception:
    session.rollback()
try:
    run = session.get(EvalRun, claims.eval_run_id) if claims.eval_run_id else None
    if run is not None:
        budget_service.pause_for_budget(session, run, source="model_gateway")
except Exception:
    session.rollback()
```

同时 `validate_claims_binding` 在暂停态直接拒绝（`model_gateway/service.py:96-102`），所以“暂停后不再有新模型调用”不依赖某个 Agent 自觉退出。**恢复后旧 token** 的问题单独在 §2.7 说明。

### 2.3 停止派发：调度器看 run 状态，而不是看 GitHub 队列

`dispatcher._dispatch_row` 在发送前检查 run 状态（`dispatcher.py:246-254`）：暂停态不把 pending 行标成永久失败，而是把 `available_at` 往后推并保留，避免恢复后只剩失败行。

真正停止新分片靠 `pause_for_budget` 里的 `_park_pending_dispatches`（`budget.py:167-185`）：把 `pending/processing` 的 shard outbox 改为 `cancelled`，`last_error=budget_paused`。恢复时 `resume_budget` 会生成全新的 dispatch_key，旧行只作为审计记录保留。

### 2.4 收口：未启动的立即停，已跑的给宽限期

`pause_for_budget`（`budget.py:188-239`）在 run 行锁下完成：

1. `queued → pausing_budget`，写 `pause_reason=budget_exceeded`、花费快照、清 `queue_reason`；
2. `_settle_not_started`（`budget.py:141-164`）：`pending/dispatching/queued` 的 attempt 立即 `cancelled`，case 保持 `queued`（未完成，可恢复）；
3. `_park_pending_dispatches` 取消未发送分片；
4. 写 `eval.budget_pausing` 事件（按 `budget_version` 去重）。

已经 `running/scoring/uploading` 的 attempt 不动：它们仍然可以上传产物、回调 `completed`。如果 Agent 不配合，worker 每轮 `reconcile_budget_pauses`（`budget.py:307-350`）在超过 `eval_budget_pause_grace_seconds`（默认 600s）后调用 `_force_settle_active`（`budget.py:278-295`）：attempt 置 `cancelled`、释放 runner、case 回到 `queued`，然后 `finalize_paused` 把 run 置为 `paused_budget` 并写 `eval.budget_paused` 事件。

**非终态保护**：`refresh_run_progress` 在 `PAUSED_RUN_STATUSES` 时只重算计数、不做 completed/partial/failed 判定（`evaluations.py:815-819`）。因此暂停期间不会“意外终局”，也不会写最终指标。

### 2.5 恢复：版本号 + 行锁，只重排未完成用例

接口在 `api/evaluations.py:316-381`，请求体（`api/evaluations.py:69-77`）只有两个字段：

```text
additional_budget_usd  Decimal > 0，6 位小数，上限与 Numeric(12,6) 对齐
budget_version         客户端看到的版本号；不匹配 → 409 budget_version_conflict
```

`resume_budget`（`budget.py:390-487`）的事务：

1. `SELECT ... FOR UPDATE` 锁 run（SQLite 忽略，Postgres 串行化并发确认）；
2. `pausing_budget` → 409 `budget_pause_in_progress`；非 `paused_budget` → 409 `evaluation_not_budget_paused`；版本不匹配 → 409，**不修改预算**；
3. 校验新增金额、上限，计算 `spent`；
4. 原子更新：`model_budget_usd += additional`、`budget_version += 1`、`budget_spent_usd=spent`、`status=queued`、清 `pause_reason/finished_at/effective_concurrency`；
5. 查 `execution_status in (queued, running)` 的未完成用例，按 `latest_attempt_no + 1` 分组，逐组调用 `build_case_dispatches` 生成新 attempt + outbox；
6. 写 `AuditLog(action="eval.budget_resumed")` 和 `eval.budget_resumed` 事件；
7. 刷新计数并 commit。

**为什么按 attempt 分组**：shard manifest 里的 `attempt` 是整片统一值。如果两个用例一个在第 1 次、一个在第 3 次，不能塞进同一个 manifest；按“下一次 attempt 号”分组后，每组内部可以继续按 `shard_size` 打包，既保持契约，又避免一用例一 workflow。

**幂等语义**：重复请求会看到 `budget_version` 已从 1 变 2（状态也已 queued），命中“版本更高 → conflict”分支，只返回 409，不会二次加钱；测试 `test_resume_adds_budget_and_only_reschedules_unfinished_cases` 与 `test_second_pause_cycle_records_new_events_and_grace_clock` 覆盖。

### 2.6 前端：在现有详情页补一块预算区，而不是新造页面

原型没有独立的“预算”页面（`plans/m1-02-fullstack-design/02-prototype-and-interactions.md` §3.6 只描述“达到预算时显示预算已暂停”）。因此本 PR 在 `EvalDetailPage` 内补：

- `EvalDetailPage.tsx:210-244` 预算卡片：预算、已花费、剩余、版本、已完成/未完成、暂停原因；
- `EvalDetailPage.tsx:213-233` 两种告警：`pausing_budget` 说明正在收口；`paused_budget` 展示“评测尚未结束”并提供恢复入口；
- `EvalDetailPage.tsx:290-330` 确认弹窗：展示当前预算/花费/未完成数，输入新增预算，提示“只重新调度未完成用例”；
- `EvalDetailPage.tsx:184-192` 头部在暂停态出现“增加预算并恢复”。

状态文案和颜色沿用详情页既有 `statusLabels/statusColor`，列表页补 `pausing_budget/paused_budget` 两个标签（`EvalsPage.tsx:34-35`）与三个预算事件的中文标签。

### 2.7 撤销点：run 状态 + attempt 终态

取消（M4-02）用 run 状态撤销 token。预算暂停也有同样问题：token 在 TTL 内仍可验签。因此：

- `pausing_budget/paused_budget` → `409 budget_paused`（`model_gateway/service.py:96-102`）；
- 恢复后 run 回到 `queued`，旧 attempt 已在暂停时置终态；若不额外检查，旧 token 会重新“复活”。本 PR 增加 `attempt.status in TERMINAL_ATTEMPT_STATUSES → 409 stale_attempt`（`model_gateway/service.py:109-116`），并由 `test_gateway_budget_refusal_triggers_platform_pause` 覆盖“暂停 → 恢复 → 旧 token 仍被拒”。

这是本次自检发现并修复的问题（§7 #4）。

## §3 数据流走查：从一次 402 到一次恢复

```text
Agent 调模型
  → 网关鉴权：token 绑定、run 状态、attempt 状态
  → ensure_budget: sum(model_usage.cost_usd) >= run.model_budget_usd
  → 402 budget_paused
  → record_usage(status=budget_paused)
  → pause_for_budget:
       run.status = pausing_budget
       budget_spent_usd = spent; pause_reason = budget_exceeded
       未启动 attempt → cancelled；未发送 shard → cancelled
       写 eval.budget_pausing
  → Agent 收到 402，上报 failed（runner 合同只允许 runtime_error 等枚举）
  → lifecycle.settle_attempt_failure 看到 run 是暂停态：
       attempt = cancelled；case 留在 queued；不创建 retry
  → worker reconcile_budget_pauses:
       没有活跃 attempt → run.status = paused_budget
       写 eval.budget_paused（finished/unfinished 计数）
  → 页面显示预算卡片 + “预算已暂停”
  → 用户输入新增预算 → POST resume-budget(additional, version=1)
  → 行锁 + 版本校验通过 → 预算 10→15、version 2、写审计
  → 未完成 case 按 attempt 2 生成新 shard/outbox
  → run = queued，调度器按容量重新派发
  → 新 attempt 完成后，run 终态 → 写 is_final=True 指标
```

一条容易忽略的支线：**暂停期间完成回调**。已在跑的 case 仍可能成功完成；`finalize_completion` 会写 case 结果，但 `refresh_run_progress` 因暂停态不做终局判定，`_ingest_report_and_metrics` 的 `is_final` 为 False。测试 `test_no_final_metrics_are_written_while_paused` 同时验证“暂停时 False、恢复并完成最后用例后 True”。

## §6 讨论点

> 每条五段：位置 / 现象 / 问题 / 预判（供拍砖，不替用户拍板）/ 结论（留空）。§7 有分流状态。

### 6.1 双触发路径：网关即时 + worker 对账

- **位置**：`backend/app/services/budget.py:188`、`:307`；`backend/app/api/model_gateway.py:94`
- **现象**：预算耗尽既可能由一次 402 立即触发暂停，也可能由 worker 每 5s 的 `reconcile_budget_pauses` 扫描发现（例如最后一个成功请求的花费把累计值推过线，而之后没有新请求）。
- **问题**：两条路径同时存在，是否会造成重复暂停、重复事件或宽限期起点不一致？
- **预判**：`pause_for_budget` 在 run 行锁下检查 `queued/running`，第二条路径看到 `pausing_budget` 会直接返回；事件按 `budget_version` 去重；`_pausing_since` 也只认当前版本的最早事件。双路径是有意的：网关负责“立即止血”，worker 负责“兜底与收口”。代价是多一个后台扫描点。
- **结论**：

### 6.2 `budget_spent_usd` 是快照，列表可能比详情慢一个 worker tick

- **位置**：`backend/app/services/budget.py:307-350`；`backend/app/services/evaluations.py:498-512`、`:466-480`
- **现象**：详情接口实时 `SUM(model_usage)`；列表接口读 `budget_spent_usd` 快照。
- **问题**：两个入口的花费数字可能相差几秒，用户会不会误以为数据不一致？
- **预判**：详情是操作入口，必须权威；列表是浏览视图，5s 内最终一致可以接受。若未来列表也要强一致，可改为一次 grouped SUM 子查询，而不是每行一次 SUM。
- **结论**：

### 6.3 暂停宽限期是全局配置，不是每 run 配置

- **位置**：`backend/app/config.py:118-121`；`backend/app/services/budget.py:278`
- **现象**：所有评测共用 `eval_budget_pause_grace_seconds=600`。
- **问题**：长任务（例如 30 分钟单用例）可能 600s 内来不及上传；短任务又等太久。
- **预判**：MVP 与取消宽限期（同样 600s）保持一致，先保证“不会永久卡住”；如果出现真实长任务上传超时，再按 run 增加字段或按流程配置。当前代价是极端长任务可能被提前收口，产物由旧 attempt 保留、恢复后新 attempt 重跑。
- **结论**：

### 6.4 “attempt cancelled + case queued” 的状态组合

- **位置**：`backend/app/services/lifecycle.py:263-275`、`:318-330`；`backend/app/services/budget.py:141-164`
- **现象**：暂停打断的 attempt 落 `cancelled`，但 case 仍 `queued`（等待恢复），而不是 `failed/timeout`。
- **问题**：attempt 终态与 case 未终态同时存在，是否会让报表口径困惑？
- **预判**：这是“平台主动暂停”与“用例失败”的区分：attempt 终态表示这一跑结束了，case 未终态表示业务上还没完成。事件 payload 带 `paused: true`，恢复后 case 会被新 attempt 覆盖。代价是查询 case 状态时不能仅凭 attempt 终态推断 case 终态。
- **结论**：

### 6.5 恢复分片按 attempt 号分组

- **位置**：`backend/app/services/budget.py:440-465`；`backend/app/services/evaluations.py:344-470`
- **现象**：未完成用例按 `latest_attempt_no+1` 分组，再按 `shard_size` 打包；不同 attempt 号一定在不同 shard。
- **问题**：如果大量用例的 attempt 号分散，会产生较多小分片和 workflow run。
- **预判**：正常评测大多数用例 attempt 号一致（首次或同一轮重试），分组数很小；极端情况下多几个 workflow run，比“一个用例一个 run”好得多。manifest 契约要求整片 attempt 一致，这是必要的取舍。
- **结论**：

### 6.6 旧 token 的撤销点从 run 状态扩展到 attempt 终态

- **位置**：`backend/app/model_gateway/service.py:109-116`
- **现象**：恢复后 run 状态回到 `queued`，如果不看 attempt，旧 token 会重新可用。
- **问题**：把“attempt 终态”作为撤销点，会不会误伤未来“同一 attempt 续跑/重连”的能力？
- **预判**：当前契约里一个 attempt 终态后不会再有合法的模型调用；续跑一定创建新 attempt。因此以 attempt 终态撤销是安全且必要的。代价是未来若引入“暂停但不结束 attempt”的远程冻结能力，需要重新设计 token 生命周期。
- **结论**：

### 6.7 UI 有两个“增加预算并恢复”入口

- **位置**：`web/src/pages/EvalDetailPage.tsx:184-192`、`:226-233`
- **现象**：头部按钮和告警条 action 各一个。
- **问题**：是否视觉重复？
- **预判**：与原型“危险/重要操作在头部 + 就地提示”的习惯一致；暂停时用户视线在告警条，头部按钮方便长页面滚动后操作。若用户觉得重复，可只保留告警条入口。
- **结论**：

- **预判**：M4-05 验收明确要求“页面与 API 能展示……”，UI 必须在 web；本任务又要求 UI 证据、检视文档与冒烟报告落盘。把证据目录写进 scope 是流程自洽的最小改动，已在 PR 描述说明。若用户认为 UI 不应进本 issue，可拆出独立前端 issue。

## §9 文件级代码分析

### 9.1 `backend/app/services/budget.py`（A，核心）

**职责**：预算暂停/恢复的全部状态迁移与幂等边界。前身不存在。

**依赖解读**：只依赖 SQLAlchemy 与平台内部的 `evaluations/lifecycle/identity`；没有第三方调度库。`identity.record_audit` 复用 M3-05 的审计表，恢复操作因此与登录/资源变更落在同一审计面。

**关键变更块**：

```python
# 旧：没有这个模块。
# 新：pause_for_budget 先锁 run，再判断是否仍可暂停。
locked = _lock_run(session, run)
if locked is None:
    return False
run = locked
if run.status not in ("queued", "running"):
    return False
...
run.status = "pausing_budget"
run.pause_reason = "budget_exceeded"
...
_settle_not_started(...)
_park_pending_dispatches(...)
_append_budget_event(..., budget_version=run.budget_version)
```

实现思路：把“暂停入口”和“收口入口”分开——入口只负责止血和标记，收口交给 worker 的宽限期逻辑；恢复则是一个带版本校验的单事务。

**检视发现**：无未决 bug；§6.3 的宽限期与 §6.5 的分片粒度是已接受的取舍。

### 9.2 `backend/app/model_gateway/service.py`（M）

**职责**：网关鉴权、预算判断、花费用量记录。

**旧 vs 新**：

```python
# 旧：只看 token 里签发时的预算
if spent_usd(session, claims) >= Decimal(str(claims.budget_usd)):
    raise GatewayError(402, "budget_paused", ...)

# 新：优先读 run 当前预算；暂停态与终态 attempt 都拒绝
limit = budget_limit_usd(session, claims)
if limit is None: return
if spent_usd(session, claims) >= limit: raise GatewayError(402, ...)
...
if attempt.status in TERMINAL_ATTEMPT_STATUSES:
    raise GatewayError(409, "stale_attempt", ...)
```

实现思路：恢复可以改预算而不重签 token，所以预算必须以 run 行为准；撤销点从 run 状态扩展到 attempt 终态，解决恢复后旧 token 复活。

**检视发现**：`budget_limit_usd` 在 run 不存在时回退 token 预算，属于兼容旧 token 的防御分支；正常绑定校验会先拒绝不存在的 run。

### 9.3 `backend/app/api/model_gateway.py`（M）

**职责**：在 402 异常路径上触发平台暂停。

**旧 vs 新**：

```python
# 旧：只记 usage
except service.GatewayError as error:
    if error.code == "budget_paused":
        service.record_usage(...)

# 新：再调用 pause_for_budget；失败不影响 402 返回
try:
    run = session.get(EvalRun, claims.eval_run_id) ...
    budget_service.pause_for_budget(session, run, source="model_gateway")
except Exception:
    session.rollback()
```

实现思路：网关仍是同步拒绝的第一现场；暂停落库失败时回滚，worker 对账会兜底，不让“暂停失败”变成“模型调用放行”。

**检视发现**：宽泛 `except Exception` 会吞掉暂停失败；这是有意的降级，日志缺失是弱点（见 §6.1 预判）。

### 9.4 `backend/app/api/evaluations.py`（M）

**职责**：新增 resume-budget 路由与错误映射。

**旧 vs 新**：

```python
# 旧：只有 create/list/detail/events/cancel
# 新：
@router.post("/api/v1/evaluations/{run_id}/resume-budget")
def resume_budget(...):
```

**检视发现**：恢复沿用 `require_admin`（与取消一致），没有新增独立权限枚举。

### 9.5 `backend/app/services/lifecycle.py`（M）

**职责**：失败/超时 attempt 的统一收口。

**旧 vs 新**：

```python
# 旧：终态 attempt 后按错误码把 case 置 failed/timeout
ctx.case_run.execution_status = terminal_case_status(error_code)

# 新：run 处于暂停态时，attempt 记 cancelled，case 保持 queued
paused_run = ctx.run.status in evaluations.PAUSED_RUN_STATUSES

    terminal_status = "cancelled"
...
if paused_run:
    if case.execution_status not in TERMINAL:
        case.execution_status = "queued"
```

实现思路：暂停期间的失败原因不可靠（可能是网关 402 导致的 runtime_error），因此不把 case 判死，留给恢复后的新 attempt。

**检视发现**：暂停期间的确定性配置错误也会被当作“未完成”并在恢复后重跑一次；代价是一次额外 attempt，换取“不漏掉被打断用例”。

### 9.6 `backend/app/services/evaluations.py`（M）

**职责**：分片构建、summary/detail、进度汇总、取消。

**关键变更**：
