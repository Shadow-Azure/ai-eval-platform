## §1 一页速览

**一句话**：把资源池页从“四个原始计数”改回“能看出容量风险和今天花了多少钱”的运维视图，并为页面数字提供可复算的后端读模型。

**比喻**：资源池像停车场。以前页面只写“总车位 12、已停 10、还有 2 个在扩建”，现在补上了“今天车位利用率多少、今天停车费多少、还有几辆车在门口排队、车位是绿/蓝/黄/灰哪种状态”。排队黄色条越长，越该去加车位。

**交付块**：

| 块 | 内容 |
|---|---|
| 统计卡 | 在线 Runner / 最大并发 / 当前利用率 / 今日资源成本 |
| 池卡片 | 就绪/自动扩容中、彩色容量分段、同色统计、排队风险、原运维明细 |
| 后端 | `usage`：utilization / cost / queue_risk；列表与详情共用同一读模型 |
| 数据 | 实例创建时快照报价；历史实例回退当前报价并显式计数 |

**验证基线**：`pytest` 594 passed / 1 skipped；`npm run build`；`npm test` 69 passed；`verify:docs` 全绿；Ruff；浏览器冒烟 12/12。

## §2 架构导览

### 2.1 后端读模型（`backend/app/services/resource_usage.py`）

- `day_window`（81-87）：把“当地自然日”换算成 UTC 窗口。使用固定偏移（默认 +8）而非 `ZoneInfo`，避免精简镜像缺 tzdata；中国无夏令时，语义等价。
- `utilization`（90-102）：`busy / max_capacity`。`live = online + busy` 仅作展示辅助。
- `queue_risk`（105-126）：`queued > 0` 且（`live/capacity >= 0.8` 或 `queued > 5`）时预警。
- `pool_today_cost`（178-225）：逐实例取 `cost_json.price_cny`，缺失时回退 `capacity_state.price_cny`/`pool.price_cny`；用 `requested_at`（或 `created_at`）到 `released_at`（或 now）与当日窗口求交集。
- `pool_usage`（228-256）：把三者打包，注入 settings 偏移。

### 2.2 API 聚合（`backend/app/api/resources.py`）

- `_pool_console_payload`（238-263）：`pool_payload + capacity_state + runners + usage`。列表（426）与详情（508）共用；写入路径保持基础 `pool_payload`，避免在创建/更新时触发供给器报价与网络调用。
- `test_provisioning`（668-671）：probe 创建后把报价写入 `cost_json`。

### 2.3 前端渲染（`web/src/pages/ResourcesPage.tsx`）

- `parseUsage`（`resources.ts:271-315`）：容错解析，缺失字段给零点/空值。
- `summary`（313-350）：跨池累加 live/busy/capacity/starting/成本，页级利用率 = Σbusy / Σcapacity。
- `poolStatusMeta`（205-216）：由容量快照推导就绪/自动扩容中。
- `PoolCapacityBar`（797-840）：按 在线/忙碌/排队/离线/扩容中/空闲 分段；`aria-label` 逐项朗读。
- `PoolStat`（759-782）：统计行加同色圆点，与分段形成图例。

## §3 数据流走查

1. 打开 `/resources` → `fetchResourcePools` → `GET /api/v1/resource-pools`。
2. 后端对每个池：`_capacity_state`（报价/排队/缺口）→ `_runner_summary`（心跳状态计数）→ `resource_usage.pool_usage`（利用率/当日成本/排队风险）。
3. 前端 `parsePool` → `usage` → `summary` 汇总四张统计卡。
4. 每张池卡片：`poolStatusMeta` → 状态标签；`PoolCapacityBar` → 分段；`queue_risk.at_risk` → 预警横幅；`pool.usage.cost.today_cny` → 运维明细。
5. 点“详情” → `GET /api/v1/resource-pools/{id}`（同一 console payload + events）→ 抽屉展示 Runner/事件/配置/利用率/成本。
6. 点“编辑” → PATCH → 返回基础池字段；前端随后 refetch 列表/详情拿到 `usage`。

## §6 讨论点

### D1 利用率口径：忙碌 Runner 还是在线 Runner？

- **位置**：`resource_usage.py:90-102`；`ResourcesPage.tsx:650-655`
- **现象**：原型 83% 恰等于 10/12 在线数；本实现用 `busy/capacity`，演示数据为 58%。
- **问题**：两种都能自洽，但混用会让“当前利用率”和“在线 Runner”读起来重复或矛盾。
- **预判**：取 `busy/capacity` 更符合“当前有多少并发在真正干活”，也与卡片 meta“N 个 Job 执行中”一致；在线数已在另一张卡单独表达。
- **结论**：保留 `busy/capacity`，PR 描述与接口字段已说明；不修改。

### D2 排队阈值硬编码（5 / 80%）

- **位置**：`resource_usage.py:39-42`
- **现象**：阈值是模块常量，不可按池配置。
- **问题**：不同池的合理排队深度可能不同；但本 issue 只要求“超过阈值有预警”。
- **预判**：先给统一常量，避免为本期引入配置面；若后续需要按池调参，再迁到 `Settings` 或池配置。
- **结论**：接受，记录为后续可配置项；不修改。

### D3 固定 Runner 的“今日成本”为 0

- **位置**：`resource_usage.py:178-225`
- **现象**：只有竞价实例有价格来源，自有机器成本恒为 0。
- **问题**：原型总成本包含非竞价部分，容易让人误以为漏算。
- **预判**：平台没有自有机器的计费数据，伪造一个成本更糟；页面 meta 只在有竞价成本时显示“竞价实例 ¥X”，否则显示“暂无云实例计费”。
- **结论**：接受，PR 已声明为已知边界；不修改。

### D4 历史实例缺价格快照

- **位置**：`resource_usage.py:129-150`
- **现象**：本次之前创建的实例 `cost_json` 没有 `price_cny`。
- **问题**：回退到池当前报价会与历史真实价格有偏差。
- **预判**：回退并计入 `unpriced_instance_count`，在页面 meta 明确提示“缺少价格快照”，比静默按 0 或按现价冒充精确更诚实。
- **结论**：接受；后续实例会带快照，偏差随实例自然淘汰收敛。不修改。

### D5 每个池一次实例查询（N+1）

- **位置**：`resources.py:238-263`、`resource_usage.py:190-196`
- **现象**：列表 N 个池会做 N 次 `provisioned_instance` 查询。
- **问题**：池数量增长后读放大。
- **预判**：资源池是低频配置页，当前量级（个位数池）可接受；真要优化可改为一次 `IN` 查询后分组。
- **结论**：接受，记录为性能优化候选；不修改。

### D6 创建/更新响应缺少 `usage`

- **位置**：`resources.py:432-490`、`515-591`
- **现象**：列表/详情有 `usage`，创建/更新只有基础池字段，前端拿到后会解析成零值 usage。
- **问题**：同一资源在不同端点形状不一致，未来消费者容易误读。
- **预判**：最初想统一返回 console payload；实际改完发现它会顺带执行 `capacity_state`，在写入路径触发供给器报价（测试里甚至会打到真实阿里云）。
- **结论**：**撤回修复**。写入路径保持基础 `pool_payload`，`parseUsage` 对缺失字段容错，前端保存后 refetch；用“读路径统一、写路径不触发云调用”换掉形状一致性，避免写接口产生网络副作用。

### D7 成本窗口偏移未校验

- **位置**：`config.py:121-125`
- **现象**：`RESOURCE_COST_UTC_OFFSET_HOURS` 可设任意整数。
- **问题**：极端值会把“今日”窗口推到不存在的时区。
- **预判**：加 `-12..14` 范围校验，成本低。
- **结论**：**已修复**（`Field(default=8, ge=-12, le=14)`）。

### D8 详情抽屉状态与卡片不一致

- **位置**：`ResourcesPage.tsx:1682-1685`（修复前）
- **现象**：卡片显示“自动扩容中/就绪”，抽屉仍显示通用“运行中”。
- **问题**：同一池两个位置口径不同。
- **预判**：复用 `poolStatusMeta`，并在抽屉补利用率/今日成本。
- **结论**：**已修复**。

### D9 分段包含“扩容中/空闲”超出 issue 四色

- **位置**：`ResourcesPage.tsx:797-840`
- **现象**：issue 点名在线/忙碌/排队/离线；实现另有扩容中与空闲。
- **问题**：是否算偏离需求？
- **预判**：扩容中来自原型黄色点阵，空闲是容量条的底；统计行也包含扩容中，整体一致，属于 additive。
- **结论**：接受；PR 描述已说明与原型 3 格容量区的有意差异。

### D10 测试冻结时钟的做法

- **位置**：`test_resource_usage.py:35-48`
- **现象**：monkeypatch `resource_usage.datetime` 为子类。
- **问题**：只影响该模块，`capacity_control` 仍用真实时钟。
- **预判**：正是想要的隔离；测试断言只依赖 `usage` 的窗口，稳定。
- **结论**：接受。

## §9 文件级代码分析

### `backend/app/services/resource_usage.py`（A）

职责：把“利用率/当日成本/排队风险”从页面的临时计算变成可测试的后端读模型。

变更核心：新增文件。实现思路：

1. 纯函数（`day_window`/`utilization`/`queue_risk`）不碰数据库，便于单测与复用。
2. 成本只依赖持久化行：实例价格快照 + 生命周期 + 当地日窗口，接口返回窗口起止，任何数字可复算。
3. 缺价实例显式计数，不静默按 0 处理。

### `backend/app/api/resources.py`（M）

旧：列表/详情各自拼 `pool_payload + capacity_state`。
新：`_pool_console_payload` 统一读路径；probe 创建后补价格快照。写入路径不计算 `usage`，避免触发供给器报价。

```python
# 旧
return {**pool_payload(pool), "capacity_state": _capacity_state(...)}

# 新
return {**pool_payload(pool), "capacity_state": state, "runners": runners,
        "usage": resource_usage.pool_usage(...)}
```

### `backend/app/config.py`（M）

新增 `resource_cost_utc_offset_hours`；检视后补 `Field(ge=-12, le=14)`。

### `backend/app/services/provisioning/{aliyun,fake}.py`（M）

创建实例时把 `pool.price_cny` 写入 `cost_json.price_cny`。旧实例没有该字段时由读模型回退。

新增 `PoolUsage` 三块类型与 `parseUsage`；`parsePool` 注入 `usage`。全部字段容错，缺失即零值。
