## §1 一页速览

**一句话**：把“派发被 GitHub 以 422 拒绝后耗尽退避预算、最后 `dispatch_failed`”改成“发 POST 前本地按 GitHub 的 10 个顶层属性、64KB、100 字符 `event_type` 限制预检，超限当场终态失败并写明字段数/字节数”，同时把 `scripts_bundle` 从 `client_payload` 挪回 outbox 行，由 workflow 通过 `/scripts` 元数据端点取回。

**比喻**：这个 PR 像快递柜前的称重台。GitHub 规定一个包裹最多 10 件、总重小于 64KB、面单名不超过 100 字；以前平台把 11 件塞进去，快递员拒收，平台还一遍遍重送。现在柜台先数件数、称重量、量面单，超了当场退回并写明“第 11 件 / 61KB”；同时把“取件码”（`scripts_bundle`）留在柜台（outbox 行），workflow 拿 `manifest_url` 换成 `/scripts` 去柜台取，而不是把取件码也塞进包裹。

## §2 架构导览

### 2.1 为什么要把 GitHub 的限制搬到本地（传输护栏）

GitHub 对 `POST /repos/{owner}/{repo}/dispatches` 的约束是文档化的：`client_payload` 最多 10 个顶层属性、JSON 总大小必须小于 64KB；`event_type` 必须 100 字符以内（[GitHub REST 文档](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28#create-a-repository-dispatch-event)）。`github_dispatch.py:31-33` 把三个常量写死为 `10 / 60*1024 / 100`，故意比 64KB 留 4KB 余量。

`validate_dispatch_request`（`github_dispatch.py:75-105`）按顺序做四件事：

1. `event_type` 必须是非空字符串且 `len <= 100`（`:83-88`）；
2. `client_payload` 必须是 JSON object（`:89-92`）；
3. 顶层键数 `<= 10`（`:93-98`）；
4. 用 `json.dumps(..., ensure_ascii=False).encode("utf-8")` 算字节数，`<= 60KB`（`:99-105`）。

预检挂在 `post_repository_dispatch` 里、token 检查之后、URL/body 构造之前（`github_dispatch.py:143-148`）。所以它只对真正会发 POST 的路径生效，而且失败时 transport 一次都不会被调用。错误信息是给运维看的，例如：

- 11 键 → `dispatch_payload_invalid: client_payload 顶层属性 11 个，超过 GitHub 上限 10`
- 61KB → `dispatch_payload_invalid: client_payload 序列化 61469 字节，超过本地护栏 61440 字节（GitHub 硬上限 64KB）`
- 101 字符 event_type → `dispatch_payload_invalid: event_type 长度 101 超过 100 字符`

一个不显眼但重要的细节是**预检和实际报文必须用同一种序列化**。第二个提交 `03a1ddd` 专门修了这点：预检用 `ensure_ascii=False` 算 UTF-8 字节数，而请求体原来保持默认 `ensure_ascii=True`，非 ASCII 会被转义成 `\uXXXX` 把体积放大；现在 `github_dispatch.py:151-156` 也显式 `ensure_ascii=False` + `.encode("utf-8")`，预检算出的字节数和 GitHub 收到的字节数一致。否则“本地 60KB 通过、GitHub 64KB 拒绝”会重新出现，只是换了个触发条件。

### 2.2 422：终态失败还是继续退避

`GitHubDispatchError` 增加了一个布尔字段 `retryable`（`github_dispatch.py:37-48`），默认 `True`，所以网络错误、429、5xx、401/403/404 都保持原来的“可重试”语义；只有 422 需要再分：

- `_422_is_terminal`（`github_dispatch.py:65-72`）把响应体转小写，**不含 `spammed` 就视为终态**；
- `post_repository_dispatch` 的非 2xx 分支（`:167-173`）据此设置 `retryable=not (status == 422 and _422_is_terminal(text))`。

dispatcher 侧（`dispatcher.py:382-407`）有两个 except：

- `DispatchPayloadInvalid` 是 `GitHubDispatchError` 的子类，必须放在前面；命中后 `_exhaust_dispatch`（`:386-388`），outbox `failed`、错误前缀 `dispatch_payload_invalid`、用例转 `dispatch_failed`；
- 普通 `GitHubDispatchError` 先看 `exc.retryable`：`False` 就直接 `_exhaust_dispatch`（`:394-402`，错误形如 `github_dispatch_failed:422:...`）；`True` 才走 `_handle_dispatch_error`（`:405`），把 outbox 放回 `pending`，按 `dispatch_backoff_seconds * 2^(attempts-1)`、封顶 `dispatch_backoff_cap_seconds` 计算 `available_at`。

用两个真实响应举例：

```text
422 {"message":"No more than 10 properties are allowed; 11 were supplied."}
  → retryable=False → outbox failed, attempts=1, case dispatch_failed（不重试）

422 {"message":"The endpoint has been spammed."}
  → retryable=True  → outbox pending, available_at 往后推, attempt.status 仍 pending、dispatch_status 回 pending（等下一轮）
```

`_422_is_terminal` 的启发式是本 PR 最需要运维经验的一处，见 §6 D2。

### 2.3 10 个顶层键：pin 从“随包裹走”改为“留在柜台”

`evaluations.py:547-560` 构造的 `client_payload` 正好 10 个键：

```text
schema_version, eval_run_id, shard_id, attempt, dispatch_key,
manifest_url, manifest_digest, runs_on, job_timeout_minutes, expires_at
```

`evaluations.py:562` 在创建时就用新 schema 校验；`dispatcher.py:318-335` 只把 `scripts_bundle` 写回 `row.payload_json`（outbox 行），不再复制进 `client_payload`。这个“只留 outbox”的设计依赖三件事同时成立：

1. **写**：dispatcher 在 POST 前 commit 行上的 pin（`dispatcher.py:331-335`）；
2. **读**：`/scripts` 端点从同一行读 pin（`runners.py:750`），并用 `_load_shard_dispatch`（`runners.py:544-602`）校验 `dispatch_key`、`shard_id`、`attempt`、`eval_run_id` 的绑定；
3. **取**：workflow 用 `manifest_url` 把结尾 `/manifest` 换成 `/scripts`（`eval-shard.yml:292-293`、`:505-506`），URL 上的 `eval_run_id/attempt/dispatch_key` 查询串原样保留，正好满足端点签名（`runners.py:730-732`）。

端点返回 `name/url/oss_url/md5/sha256/size/token/expires_at`（`runners.py:817-828`），workflow 先试 `metadata.oss_url`（私有 OSS 直连），再试 `metadata.url` + Bearer token（平台代理），最后才 `actions/checkout`（`eval-shard.yml:305-325`）；下载后用 metadata 的 sha256/md5/size 校验（`:244-258`）。我用 `/tmp` 脚本把 workflow 里同一段内嵌 fetcher 抽出来，对着本地 HTTP server 跑了一次：无 pin + `/scripts` 返回 metadata + 包 → `source=proxy`，metadata 1 次、包 1 次、解包字节数正确；证明**“pin 不在载荷、经 `/scripts` 仍能拿到包”这条主路径是通的**。

但这条设计有一个明确的副作用：workflow 里还留着“镜像缓存优先”的分支（`eval-shard.yml:219`、`:260-269`、`:432`、`:473-482`），它依赖 `dispatch.scripts_bundle`；pin 从载荷移除后该对象恒为 `{}`，`readImageCache()` 永远返回 `null`。详见 §6 D1。

### 2.4 schema 与 Python/Node 子集的一致性

`dispatch.schema.json:7` 增加 `maxProperties: 10`，`:5` 更新描述，并删除了整段 `scripts_bundle` 定义。由于 `additionalProperties: false` 且 `properties` 正好 10 个，`maxProperties` 在“当前 schema”下是冗余的；它的价值是**当未来有人往 schema 加第 11 个字段时，校验会先失败**，把 GitHub 的硬限制固化在契约里，而不是等生产 422。

Python 侧在 `runner_contracts.py:175-179` 的 object 分支里加了 `minProperties`/`maxProperties`；Node 侧在 `json-schema-subset.mjs:114-120` 做了同样的事。两边的错误文案逐字一致（`至少 N 个属性` / `最多 N 个属性`），并且 `tests/runner/json-schema-subset.test.mjs:40-55` 对 Node 的 `minProperties`/`maxProperties` 都做了断言。Python 的 `minProperties` 目前没有 schema 使用、也没有单测，这是“为对齐而加”的对称实现，风险低。

向后兼容性值得记一笔：新载荷（10 键）在旧 schema 下也合法（旧 schema 只是多了可选的 `scripts_bundle`，没有 `maxProperties`）；但**旧载荷（11 键）在新 schema 下会同时报 `最多 10 个属性` 和 `不允许的额外字段`**。这正好是 §6 D3 的部署窗口问题。

### 2.5 失败结算的两条路径

- `_exhaust_dispatch`（`dispatcher.py:468-511`）：outbox `failed`、写 `last_error`、所有 attempt `dispatch_failed`、case `failed`、写 `eval.dispatch_failed`、`refresh_run_progress`。预检失败、422 终态、最大重试耗尽都汇到这里。
- `_handle_dispatch_error`（`dispatcher.py:442-465`）：可重试错误回 `pending` + 退避；但当 `row.attempts >= dispatch_max_attempts` 时它内部也会调 `_exhaust_dispatch`（`:453-455`），而调用方 `:405-406` 仍然 `outcome.retried += 1`。这是**既有**的小记账问题（不是本 PR 引入），不影响终态，但会让“本轮 exhausted 的行”被统计成 `retried`；如果以后用 `DispatchOutcome` 做指标，建议单独修。

## §3 数据流走查

主场景：一个完整 bundle 配置下的分片，从创建到 runner 执行。

1. **建 run + 冻结载荷**：`evaluations.py:543-560` 生成 `manifest_url` 和 10 键 `client_payload`；`:562` 用 dispatch schema 校验（此时 `maxProperties` 已生效）；outbox 行保存 `client_payload/manifest_text/manifest_digest`。
2. **派发前刷新窗口**：`dispatcher.py:307` 调 `_refresh_dispatch_window`，重算 manifest digest、`job_timeout_minutes`、`expires_at`；这些字段仍在 schema 内。
3. **pin 只写 outbox**：`dispatcher.py:318-335` 在 name/md5/sha256 齐全且 size>0 时写 `row.payload_json["scripts_bundle"]`，然后 commit。`client_payload` 保持 10 键。
4. **本地 bundle 存在性检查**：`dispatcher.py:340-372` 用 outbox 行 pin 去对象存储 `head_object`；缺失/大小不符仍走 `_exhaust_dispatch`（`runner_scripts_bundle_missing` / `runner_scripts_bundle_size_mismatch`）。注意这一步读的也是 outbox 行，不是载荷。
5. **传输预检**：`dispatcher.py:375-381` 调 `post_repository_dispatch`；`github_dispatch.py:146-148` 先跑 `validate_dispatch_request`。若 11 键/超字节/超长 event_type → `DispatchPayloadInvalid`，transport 0 次，直接走第 8 步的终态分支。
6. **POST 与成功结算**：预检通过后 `github_dispatch.py:150-156` 用同一序列化构造 body，POST 成功返回 2xx；`dispatcher.py:409-439` 把 outbox 置 `sent`、写 `dispatched_at/github_status`、attempt 置 `queued` 并加 queue lease，写 `eval.dispatched`。
7. **workflow prepare 取包**：`eval-shard.yml:198-349` 的 `Fetch the scripts bundle` 先 `readImageCache()`（无 pin → null），再从 `manifest_url` 派生 `/scripts` 元数据（`:292-299`），拿到 `oss_url`/`url` 后下载并按 metadata 摘要校验（`:301-325`），解包成功设 `EVAL_SCRIPTS_DIR`；失败则单次 `actions/checkout` 兜底（`:350-358`）。execute 的每个 matrix job 重复同一段（`:411-561`）。
8. **失败分支**：
   - 预检失败 → `dispatcher.py:382-390` → `_exhaust_dispatch`，outbox `failed`、错误 `dispatch_payload_invalid:...`、用例 `dispatch_failed`；
   - 422 参数终态 → `dispatcher.py:391-404` → `_exhaust_dispatch`，错误 `github_dispatch_failed:422:...`；
   - 422 spam / 429 / 5xx / 网络 → `dispatcher.py:405-406` → `_handle_dispatch_error`，outbox 回 `pending`、`available_at` 退避；
   - `/scripts` 不可达且无镜像缓存 → workflow 回退 checkout；都失败则 `Report bootstrap failure` 回调（`:607`），由平台按重试预算生成下一次 attempt。

## §6 讨论点

> 结论栏留空，等用户逐条拍板后再回写 §6 与 §7。D1–D3 的处置已在 2026-11-19 闭环 PR 落地，见 §7；结论仍留给读者复核。

### D1 移除载荷 pin 后，`/opt/eval/runner-scripts` 的预置缓存变成了死路径

- **位置**：`backend/app/services/dispatcher.py:331-334`（不再写 `client_payload.scripts_bundle`）；`.github/workflows/eval-shard.yml:219`、`:260-269`、`:432`、`:473-482`（仍按载荷 pin 找缓存）；`backend/app/services/provisioning/spot_cloud_init.py:102-128`、`aliyun.py:713-736`（仍在预置）；`tests/runner/scripts-bundle-fetch.test.mjs:117-143`（仍用带 pin 的载荷测缓存命中）。
- **现象**：workflow 的 `const pin = dispatch.scripts_bundle || {}` 现在恒为空对象，`readImageCache()` 在 `!expected.name || !expected.sha256` 时直接返回 `null`，而且它在 metadata 请求之前调用、之后不再重试缓存。结果是：spot 实例启动时 cloud-init 仍会预取/保留 `/opt/eval/runner-scripts/<name>.tar.gz`，但 prepare 和每个 execute job 都不读它，改为调用 `/scripts` 元数据并下载包。用 `/tmp` 脚本抽取 workflow 内嵌 fetcher 的实测对照：
  - 有 pin + 缓存文件 + `/scripts` 返回 503：`ok=true`，`source=image`，**0 次网络请求**；
  - 无 pin + 同一缓存文件 + `/scripts` 返回 503：`ok=false`，`image cache and OSS sources unavailable`，**1 次元数据请求**；
  - 无 pin + `/scripts` 返回 metadata + 包：`ok=true`，`source=proxy`，1 次元数据 + 1 次包下载。
- **问题**：#312/M8-47 的验收语是“断开平台 scripts 端点，spot 仍从镜像缓存启动”；本 PR 后这条能力消失，平台 `/scripts`/OSS 变成每次取包的必经路径（否则退回 checkout）。设计文档说“代价是 spot 启动多一次 `/scripts` 元数据请求”，但实际是**每个 prepare 和每个 execute job 都多一次元数据请求 + 一次包下载**（500 用例、8 个分片、每 job 一个 case 时是几百次），而且预置缓存、预签名 URL、镜像烘焙、相关测试都还在，形成“继续做但没人用”的死代码/死配置。更明显的是 `spot_cloud_init.py:105-106` 的注释仍写“The GitHub job then reads local disk and survives a flaky platform scripts endpoint”，`runner/README.md:67` 也仍写“按 dispatch payload 的 `scripts_bundle` 找镜像缓存”，均与现状不符。
- **预判**：移除载荷 pin 是 10 键限制下必须做的；但不必连带废弃缓存。最小修法是在 fetcher 拿到 metadata 之后、下载之前，用 `metadata.name` 去 `/opt/eval/runner-scripts` 找同名文件，并用现成的 `verify(bytes, metadata)` 校验 sha256/md5/size，命中就 `source=image` 返回——这不会增加请求（metadata 本来就要取），但能保留离线/端点抖动时的启动能力，也保住 #312 的验收。若团队认为“预置缓存不值得维护”，则应在本 PR 或紧随的 follow-up 里删除 cloud-init 预置、`aliyun.py` 预签名、`runner/README` 说明和相关测试，避免长期空转。我倾向前者（恢复缓存读取）。
- **结论**：

### D2 422 是否为终态，完全依赖响应体里是否出现 `spammed`

- **位置**：`backend/app/services/github_dispatch.py:65-72`、`:167-173`；`backend/app/services/dispatcher.py:391-404`。
- **现象**：所有 422 中，只有 body 小写后含 `spammed` 才重试，其余一律终态。GitHub 文档只写了 422 的语义是“Validation failed, or the endpoint has been spammed”，并没有把响应体的字段结构/文案列为契约；本 PR 的测试用的是自造的 `No more than 10 properties...` 与 `The endpoint has been spammed.`。
- **问题**：这个默认值风险不对称。若 GitHub 某天用不含 `spammed` 的措辞表达临时性 422（或中间代理返回 422），分片会被**永久** `dispatch_failed`，比原来的“退避耗尽再失败”更糟；反过来，若某个参数校验响应恰好含 `spammed`，会白烧退避预算（回到本 PR 想修的老问题）。
- **预判**：对本仓库当前的真实故障（10 属性校验）终态是正确且必要的。更稳的做法是把默认值反过来：只对**已知的参数校验特征**（如 `No more than 10 properties`、`too large`、`is too long`、`client_payload`）判终态，其余 422 按可重试处理并设一个小上限；同时把原始响应体完整写进 `last_error`（当前截 200 字符）便于事后改判。这样最坏情况是“多退避几次”，而不是“分片永久失败”。如果坚持当前启发式，至少应把原始 body 落日志/事件，并在文档里把它写成显式的运维假设。
- **结论**：

### D3 升级窗口里由旧代码创建的 11 键 outbox 行会被本地护栏直接终态，而不是被“救回来”

- **位置**：`backend/app/services/dispatcher.py:374-390`；`backend/app/services/github_dispatch.py:93-98`；`tests/backend/test_dispatch_loop.py:290-313`。
- **现象**：`_dispatch_row` 只做“写 pin”，从不清理 `row.payload_json["client_payload"]` 里可能已有的 `scripts_bundle`。因此 #312 期间创建、但因容量门/退避仍挂在 outbox 的旧行，在部署本 PR 后第一次派发就会被本地预检判成 11 键并终态失败。测试里的 11 键场景本质上就是这条路径。
- **问题**：这些旧行在旧代码下也会被 GitHub 以同样的 422 拒绝，最终同样 `dispatch_failed`，所以**不是新的回归**；但本 PR 恰好有能力把它们救回来：在预检前对 `client_payload` 做一次 `pop("scripts_bundle", None)`（或在迁移/一次性脚本里清掉），旧行就能用 10 键成功派发。现在的实现选择了“坏载荷直接死”，会让升级窗口内的在途评测无谓失败。另外，“不消耗重试预算”的说法与实际不符：乐观 claim 在 `dispatcher.py:294-305` 已经把 `row.attempts` 加 1，测试也断言 `row.attempts == 1`；虽然不会再重试，但说“不消耗”容易让人误判。
- **预判**：建议在 `_dispatch_row` 组装/刷新后、调用 `post_repository_dispatch` 前，显式把 `client_payload` 收敛到 schema 允许的 10 个键（至少 `pop` 掉历史的 `scripts_bundle`），再让预检作为最后防线；这既修复升级窗口，也把“10 键”从“碰巧成立”变成“代码保证”。若团队更希望“脏载荷必须显式失败”，则保留现状并在 release note/issue 里写明升级窗口的影响，同时把“不消耗重试预算”改成“不进入退避重试（但已记 1 次尝试）”。
- **结论**：

## §9 文件级代码分析

### 9.1 `backend/app/services/github_dispatch.py`（M）

**职责**：一次 repository_dispatch 的 HTTP 封装；本 PR 把 GitHub 的三条硬限制前移到本地，并给错误加上可重试标记。
**变更形态**：M（+91 / -4）。**关键依赖**：只用标准库 `json` / `urllib`（Python 第一方、运行时加载、无新增供应链面）；不存在新增第三方包，因此没有 dep-allowlist / tarball 检查事项。

旧代码的失败路径只有一种“抛 `GitHubDispatchError`，由 dispatcher 统一退避”：

```python
class GitHubDispatchError(Exception):
    """One dispatch attempt failed (HTTP error or transport failure)."""

    def __init__(self, message: str, *, status: int) -> None:
        self.status = status
        self.message = message
        super().__init__(message)
...
if status < 200 or status >= 300:
    raise GitHubDispatchError(f"GitHub 派发失败：HTTP {status} {text.strip()[:200]}", status=status)
```

新代码把“错误是否值得重试”变成错误自身的一部分，并新增预检和异常类型：

```python
class GitHubDispatchError(Exception):
    def __init__(self, message: str, *, status: int, retryable: bool = True) -> None:
        self.status = status
        self.message = message
        self.retryable = retryable
        super().__init__(message)


class DispatchPayloadInvalid(GitHubDispatchError):
    def __init__(self, detail: str) -> None:
        super().__init__(
            f"{DISPATCH_PAYLOAD_INVALID}: {detail}", status=0, retryable=False
        )


def validate_dispatch_request(*, event_type: str, client_payload: dict) -> bytes:
    # event_type 非空且 <=100；payload 是 dict；len <=10；UTF-8 字节 <= 60KB
```

请求体序列化也改了，和预检对齐：

```python
# 旧：默认 ensure_ascii=True，非 ASCII 会被转义
body = json.dumps({"event_type": event_type, "client_payload": client_payload}).encode()

# 新：与 validate_dispatch_request 的字节预算一致
body = json.dumps(
    {"event_type": event_type, "client_payload": client_payload},
    ensure_ascii=False,
).encode("utf-8")
```

422 分支：

```python
# 旧
raise GitHubDispatchError(f"... HTTP {status} ...", status=status)
# 新
raise GitHubDispatchError(
    message, status=status,
    retryable=not (status == 422 and _422_is_terminal(text)),
)
```

**实现思路总结**：限制前置 + 错误自带重试语义；预检与实际报文共用同一种序列化，避免“本地通过、线上超限”。
**检视发现**：`validate_dispatch_request` 的返回值没有被 `post_repository_dispatch` 使用（`github_dispatch.py:148` 丢弃，`:153-156` 重新序列化外层）。因为 payload 子串的序列化完全相同，当前无实害；但 docstring 说“caller reuses the exact bytes”不准确，建议删返回值或真正复用。422 子串启发式见 §6 D2。

### 9.2 `backend/app/services/dispatcher.py`（M）

**职责**：outbox claim → 可选 pin → 传输 → 成功/失败结算。
**变更形态**：M（+33 / -10）。**关键依赖**：SQLAlchemy 会话与既有 outbox 状态机；无新依赖。

旧代码把 pin 同时写进 outbox 行和派发载荷（11 键的根因）：

```python
row.payload_json = {
    **row.payload_json,
    "scripts_bundle": bundle_pin,
    "client_payload": {
        **row.payload_json.get("client_payload", {}),
        "scripts_bundle": bundle_pin,
    },
}
```

新代码只写 outbox 行：

```python
row.payload_json = {
    **row.payload_json,
    "scripts_bundle": bundle_pin,
}
```

错误分流从单一 except 变成两个：

```python
# 旧
except GitHubDispatchError as exc:
    _handle_dispatch_error(session, row, run=run, attempts=attempts, exc=exc, settings=settings, now=now)
    outcome.retried += 1
    return

# 新
except DispatchPayloadInvalid as exc:
    _exhaust_dispatch(session, row, run=run, attempts=attempts, now=now, last_error=exc.message[:500])
    outcome.failed += 1
    return
except GitHubDispatchError as exc:
    if not exc.retryable:
        _exhaust_dispatch(session, row, run=run, attempts=attempts, now=now,
                          last_error=f"github_dispatch_failed:{exc.status}:{exc.message}"[:500])
        outcome.failed += 1
        return
    _handle_dispatch_error(session, row, run=run, attempts=attempts, exc=exc, settings=settings, now=now)
    outcome.retried += 1
    return
```

**实现思路总结**：预检/422 终态复用 `_exhaust_dispatch` 的统一结算；可重试路径完全保持原样。
**检视发现**：旧 11 键行不会被清理（§6 D3）；`_handle_dispatch_error` 内部耗尽时调用方仍计 `retried`（既有问题，§7）；预检失败时 `row.attempts` 已在 `:294-305` 的乐观 claim 中加 1，与“不消耗重试预算”的文案不一致。

### 9.3 `backend/app/runner_contracts.py` + `runner/lib/json-schema-subset.mjs`（M）

**职责**：仓库自实现的 JSON Schema 子集校验器（Python 供后端，Node 供 runner/workflow）；本 PR 让两边都认识 `minProperties`/`maxProperties`。
**变更形态**：M（+4 / +6）。**关键依赖**：没有第三方 JSON Schema 库，自己维护一个“够用即可”的子集；这也是为什么新增关键字必须两边手写、并保持文案一致。

Python 旧代码只处理 `required` / `properties` / `additionalProperties`：

```python
if _is_plain_object(data):
    for key in schema.get("required", []):
```

新代码先看属性数：

```python
if _is_plain_object(data):
    if "minProperties" in schema and len(data) < schema["minProperties"]:
        errors.append(f"{path}: 至少 {schema['minProperties']} 个属性")
    if "maxProperties" in schema and len(data) > schema["maxProperties"]:
        errors.append(f"{path}: 最多 {schema['maxProperties']} 个属性")
    for key in schema.get("required", []):
```

Node 侧结构相同：

```js
if (isPlainObject(data)) {
  if (schema.minProperties !== undefined && Object.keys(data).length < schema.minProperties) {
    errors.push(`${path}: 至少 ${schema.minProperties} 个属性`);
  }
  if (schema.maxProperties !== undefined && Object.keys(data).length > schema.maxProperties) {
    errors.push(`${path}: 最多 ${schema.maxProperties} 个属性`);
  }
```

**实现思路总结**：两个实现共享同一段语义与同一套中文错误文案，测试分别覆盖。
**检视发现**：Python 的 `minProperties` 无 schema 使用、无单测；Node 的 `minProperties`/`maxProperties` 都有测试。没有功能问题，只是对称性未闭合；可补一条 Python 单测或在文档里注明“为未来保留”。

### 9.4 `runner-contract/schemas/v1/dispatch.schema.json`（M）

**职责**：repository_dispatch `client_payload` 的唯一契约；也是 workflow 里 `contracts.mjs dispatch` 的校验依据。
**变更形态**：M（+2 / -26）。**关键依赖**：JSON Schema draft 2020-12 的声明，但实际由仓库自实现的子集验证；所以 `maxProperties` 的价值取决于 9.3 的两个校验器，而不是通用 JSON Schema 工具。

改动前：没有属性数上限，`scripts_bundle` 是第 11 个可选属性。

```json
"description": "... never cases, prompts, model keys or cloud credentials.",
"type": "object",
"additionalProperties": false,
"required": ["schema_version", "...", "expires_at"],
"properties": {
  "...": {},
  "scripts_bundle": {
    "type": "object",
    "required": ["name", "md5", "sha256", "size"],
    "...": {}
  }
}
```

改动后：`maxProperties` 固化上限，`scripts_bundle` 整段删除。

```json
"description": "... GitHub allows at most 10 top-level properties and 64KB per dispatch, so scripts bundle metadata stays in the outbox row and is fetched by the workflow through the shard scripts metadata endpoint.",
"type": "object",
"maxProperties": 10,
"additionalProperties": false,
"required": ["schema_version", "eval_run_id", "shard_id", "attempt",
             "dispatch_key", "manifest_url", "manifest_digest", "expires_at"],
"properties": {
  "...": {},
  "job_timeout_minutes": { "type": "integer", "minimum": 1, "maximum": 7200 }
}
```

**实现思路总结**：把“最多 10 个”写进契约，删掉不再下发的字段；用 `additionalProperties: false` + `maxProperties` 双保险。
**检视发现**：`maxProperties` 与 `additionalProperties: false` 在当前 10 个 property 下功能重叠；作为“未来加字段时先失败”的护栏是合理的。注意旧 11 键载荷在新 schema 下会报两个错（`最多 10 个属性` + `不允许的额外字段`），测试已覆盖。
