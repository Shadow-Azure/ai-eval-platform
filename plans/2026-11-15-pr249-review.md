## §0 结论

实现与 issue #248 和设计文档一致：数据集版本 `agent_timeout_seconds`（默认 1800s，60–86400s）→
评测启动可选覆盖 → 冻结到 `eval_run` → preparation/identity → shard manifest → task payload →
Runner wall-clock。真实 UI、原型、迁移和测试均已覆盖；未发现阻塞性缺陷。

## §1 数据流核对

1. 数据集导入：Step 2 字段 → upload/commit `agent_timeout_seconds`（分钟 ×60）→ `DatasetImport` →
   `DatasetVersion.agent_timeout_seconds`。
2. 评测：`PrepareRequest/CreateEvaluationRequest.agent_timeout_seconds`（可选）→
   生效 = 覆盖 > 数据集版本默认 > 1800 → `EvalRun.agent_timeout_seconds`。
3. 运行：manifest/task payload → `real-task` 的 `TIMEOUT_MS` → Claude Agent wall-clock；
   外层 `REAL_TASK_AGENT_TIMEOUT_MS` 默认 `max(1900000, inner+120000)`。
4. 展示：数据集详情/导入确认、评测 Step 3/Step 4/侧栏、评测详情/用例详情。

## §2 发现与处理

| # | 发现 | 定性 | 处理 |
|---|---|---|---|
| F1 | 超时以秒存储、以分钟编辑，存在单位转换边界 | 契约 | 记录：API/DB 用秒，UI 用分钟 ×60；测试覆盖 30/45/60/1440 分钟 |
| F2 | `DatasetImport.agent_timeout_seconds` 可为 NULL（上传未填） | 兼容 | 记录：materialize 回退 1800s；commit 可覆盖 |
| F3 | 无 DB CHECK，范围只在 Pydantic/service 层 | 一致性 | 记录：与 `max_turns` 一致；非法直接写入会在消费时回退/报错 |
| F4 | `REAL_TASK_TIMEOUT_MS` 仍优先于评测配置 | 运维逃生阀 | 记录：部署默认不设置；保留全局覆盖 |
| F5 | 0027 之前 preparation 快照没有 timeout，identity 会变化 | 迁移 | 记录：prepare 短 TTL，安全失效为 `configuration_changed` |

无需要修复的阻塞项。
