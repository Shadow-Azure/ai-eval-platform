## §1 一页速览

**一句话**：把“排队 → 买一台阿里云竞价机 → 机器自己领一张一次性 GitHub 门禁卡 → 干完活自动注销并退租”接通，并保证价格/库存/中断/超时都不会把用例误判失败。

**比喻**：供给器像包工头，阿里云是劳务市场，`RUNNER_ADMIN_TOKEN` 是给临时工办门禁卡的介绍信；门禁卡只能用一次（JIT），干完活工牌销毁、人退场（DeleteInstance）。

## §2 架构导览

### 2.1 供给器 seam 与原子的边界

`Provisioner` 在 M4-03 的四段接口上增加 `verify`（只读鉴权）与 `sync`（云端状态对账），并给 `quote` 增加可选 `session`（真实供给器要解密租户凭据）。`create`/`release`/`sync` 只 flush 不 commit，事务边界仍归容量控制器（`provisioning/__init__.py:110` 起）。这保留了 M4-03 的 fake 与既有测试，又让真实供给器有地方做云 API。

### 2.2 阿里云客户端：签名与错误归一

`AliyunEcsClient`（`aliyun.py:138`）只实现本 issue 需要的 action：`DescribeSpotPriceHistory`、`DescribeInstances`、`DescribeImages`、`DescribeVSwitches`、`DescribeSecurityGroups`、`RunInstances`、`DeleteInstance`。签名是 RPC 风格 HMAC-SHA1：参数按 key 排序、RFC3986 编码、`POST&%2F&...`，测试用独立重算校验（`test_aliyun_provisioner.py::test_signing_uses_sorted_rfc3986_params`）。

错误按可恢复性归一为稳定 code：鉴权 → `aliyun_auth_failed`；库存 → `inventory_unavailable`；参数 → `cloud_request_invalid`；限流/5xx → `provider_throttled`；其余 → `cloud_api_failed`。错误详情只保留 provider code/action/status，不带请求体或凭据。

### 2.3 创建：先办卡，再开机

`AliyunEcsProvisioner.create`（`aliyun.py:698`）顺序是：

1. 解析连接凭据（`resolve_aliyun_credentials`，只解密到内存）；
2. 解析/自动发现 vSwitch、VPC、安全组、镜像；`_vswitch_choice`（`aliyun.py:519`）保证“报价 zone / 实例 zone / 安全组 VPC”来自同一个 vSwitch；
3. 生成唯一 runner 名，向 GitHub 申请 JIT（`generate_jitconfig`，`runner_registration.py:133`）；
4. 把 JIT 写进 cloud-init（`spot_cloud_init.py:147`），调用 `RunInstances(SpotStrategy=SpotAsPriceGo)`；
5. 落 `ProvisionedInstance`，`cost_json` 只存 runner 名、数字 runner id、region/zone/镜像等非密信息。

任何一步失败都不会留下“有卡无机”的幽灵 Runner：`RunInstances` 失败时 best-effort 删除刚申请的 JIT。

### 2.4 对账：Running / 中断 / 失联 / 超时

`sync`（`aliyun.py:861`）一次 `DescribeInstances` 批量拉状态，然后：

- Running + runner 心跳在线 → 实例置 `online`、关联 `runner_id`、写去重事件 `resource.instance.registered`；
- 有 `Recycling`/spot/maintenance lock 或 Stopped/Stopping → `_reclaim`（`aliyun.py:804`）写 `resource.instance.interrupted`，Runner 置 offline，尝试注销+释放；
- requested/creating/registering 超过 `EVAL_SPOT_REGISTER_TIMEOUT_SECONDS` → `resource.instance.create_timeout` 并回收；
- online 但 Runner 心跳超过 `heartbeat_timeout + grace`（或 Runner 行消失）→ 回收，交给 M4-02 的 attempt 重试；
- 回收失败 → 实例停 `draining`，由 `_retry_pending_releases` 下个 tick 重试。

所有回收都不改 attempt 结果；用例保持排队/由既有 reaper 生成新 attempt，旧结果不被覆盖。

### 2.5 缩容与释放顺序

`_scale_down`（`capacity_control.py:605`）沿用 M4-03 的 drain→offline→release；`AliyunEcsProvisioner.release`（`aliyun.py:772`）先按数字 id 或名字删 GitHub Runner（404 视为已自行注销），再 `DeleteInstance`（NotFound 视为已回收）。顺序保证被释放的实例不会再接到新 Job。

### 2.6 密钥卫生

- AccessKey 只从 `Credential` 解密到 `AliyunEcsClient` 内存，不入 DB/事件/异常文本；
- JIT 只存在于 cloud-init 的 bootstrap 文件；runner 启动 90 秒后 `cleanup.sh` 用 `shred -u` 删除 JIT env 与 `/var/lib/cloud/instance/user-data.txt`；
- `cost_json` 只存 `runner_name`/`github_runner_id`；测试 `test_create_embeds_jit_in_user_data_only` 断言 JIT 不在 DB/事件里；
- `RUNNER_ADMIN_TOKEN` 只用于 `generate-jitconfig`/delete，不复用 dispatch token。

## §3 数据流走查

1. **Worker tick**：`worker/main.py:92` 注册 `aliyun` 供给器；`capacity_once` 调 `reconcile_pools`（`capacity_control.py:822`）。
2. **单池**：`reconcile_pool`（`capacity_control.py:685`）先重试 `draining` 释放，再 `provisioner.sync`；sync 失败只记录事件，不中断 tick。
3. **报价**：`_quote`（`capacity_control.py:229`）调 `quote`；价格超阈值 → `resource_price_above_threshold`，不创建。
4. **扩容**：`_scale_up`（`capacity_control.py:466`）按 batch 调 `create`；失败映射到 `runner_registration_unavailable`/`resource_provider_auth_failed` 等 reason，用例不 failed。
5. **实例开机**：cloud-init 安装 Docker/runner，启动 heartbeat（带 `resource_pool_id`）与 `run.sh --jitconfig`；Runner 进入仓库并带唯一标签。
6. **Runner 心跳**：`record_runner_heartbeat`（`runners.py:114`）按 `resource_pool_id` 把 Runner 放进 spot 池；`api/runners.py:49` 接收该字段。
7. **下一次 sync**：实例 Running + Runner online → `online`；队列 gap 下降，停止扩容。
8. **空闲缩容**：Runner online 多于 `min_capacity` → drain/offline；`release` 删 Runner、删实例；事件 `resource.capacity.scaled_down`/`released`。
9. **中断**：spot lock → `interrupted` 事件 + 回收；M4-02 reaper 依据心跳超时给受影响 attempt 建新 attempt。

## §6 讨论点

### 6.1 价格 zone 与实际创建 zone 的一致性

- **位置**：`backend/app/services/provisioning/aliyun.py:519`、`:638`、`:698`
- **现象**：早期实现报价取全区域最低价，创建却用第一个 vSwitch 的 zone，可能“报价 A 区、开机 B 区”。
- **问题**：阈值判断与实际扣费可能不一致。
- **预判**：已改为先解析 vSwitch（含配置的 vswitch_id），报价与创建共用其 ZoneId/VpcId；新增 `test_configured_vswitch_drives_zone_vpc_and_instance`。
- **结论**：

### 6.2 GitHub 注销失败是否应阻塞 ECS 释放

- **位置**：`aliyun.py:772`
- **现象**：`release` 先删 GitHub Runner；若 GitHub API 无权限/不可用，抛错，实例停 `draining` 并重试。
- **问题**：严格“先注销再释放”会保证不接新 Job，但长期 API 故障会持续计费；直接删实例又会留下幽灵 Runner。
- **预判**：保留严格顺序，靠短周期重试；若确认长期故障，再加“实例已停止时允许跳过注销”的降级开关。
- **结论**：

### 6.3 共享 Runner 心跳 token 的池绑定

- **位置**：`backend/app/services/runners.py:114`、`backend/app/api/runners.py:49`
- **现象**：spot 心跳可带 `resource_pool_id` 加入对应池，但 token 仍是全局共享的 `RUNNER_HEARTBEAT_TOKEN`。
- **问题**：多租户/多池后，泄露 token 可冒充任意池的 Runner。
- **预判**：单租户阶段可接受；多租户前应改为池级短期 token 或在心跳里校验实例签名。
- **结论**：

### 6.4 真实冒烟的操作依赖

- **位置**：`.github/workflows/spot-smoke.yml`、`tests/integration/m4_04_spot_smoke.py`
- **现象**：workflow 需要 `RUNNER_ADMIN_TOKEN`（仓库 Admin PAT）与 `run-spot-smoke` label；PR 还需 Project 关联。
- **问题**：这些是人类授权/配置点，不是代码缺陷。
- **预判**：配置后按 §5 跑一次，把 `reports/2026-11-10/m4-04-spot/` 证据提交到本 PR。
- **结论**：

### 6.5 sync 的部分失败与事务边界

- **位置**：`capacity_control.py:685`
- **现象**：`sync` 可能更新了几个实例后抛错；控制器捕获后继续，调用方 commit 已有部分更新。
- **问题**：是否需要在 sync 内部按实例隔离失败，避免一个坏实例影响整池？
- **预判**：当前按“整次云调用失败才抛”设计；单实例异常在循环内已尽量局部处理。后续可加 per-instance try。
- **结论**：

## §9 文件级代码分析

### 9.1 `backend/app/services/provisioning/aliyun.py`（A，1042 行）

职责：阿里云 ECS 竞价供给与状态对账。关键依赖：`httpx`（运行时 HTTP）、`cryptography`（经 `secrets.get_secret_box` 解密）、SQLAlchemy 模型。实现思路：薄 RPC 客户端 + 单一 provisioner 类；所有云错误归一为 `ProvisionerError.code`；`sync` 按实例状态机更新 DB。

变更块：新文件。重点函数 `quote`（CNY→USD、zone 与 vSwitch 同源）、`create`（JIT→cloud-init→RunInstances→落库）、`release`（先删 Runner 再删实例）、`sync`（Running/中断/超时/失联→回收）。

### 9.2 `backend/app/services/provisioning/spot_cloud_init.py`（A）

职责：生成 cloud-config。`heartbeat.sh` 用 bash+curl 上报 `resource_pool_id`；`bootstrap.sh` 安装 Docker/runner、写 0600 JIT env、启动两个 systemd 服务；`cleanup.sh` 90 秒后 shred JIT env 与 user-data。无 `set -x`，不 echo 密钥。

### 9.3 `backend/app/services/runner_registration.py`（A）

职责：GitHub 仓库级 Runner API。`generate_jitconfig` 校验响应；`find_runner` 分页按名查；`delete_runner` 404 视为成功。错误只保留 status，不保留响应 body。

### 9.4 `backend/app/services/capacity_control.py`（M）

变更：`_quote` 传入 session；`reconcile_pool` 先 sync、捕获 quote 错误并记录；`_provisioning_reason` 把供给器 code 映射为稳定池 reason；新增 4 个资源事件。既有 gap/缩容/事件去重逻辑不变。

### 9.5 `backend/app/services/runners.py` / `api/runners.py`（M）

变更：`HeartbeatRequest.resource_pool_id`；`record_runner_heartbeat` 校验 active spot 池并按池 upsert；未知池返回 404。固定 Runner 省略字段时行为不变。

### 9.6 入口与 API（M）

`main.py:30` 与 `worker/main.py:92` 注册内置供给器（无网络副作用）；`resources.verify_connection` 调 provider `verify`；`api/resources.py:569` 试供给先检查库存，避免无库存时仍创建。

### 9.7 测试（A/M）

`test_aliyun_provisioner.py`：签名、价格换算、JIT 只进 user_data、创建失败清卡、释放顺序、sync 的 online/中断/超时/失联、vSwitch 一致性。`test_runner_registration.py`：JIT 请求、权限错误、按名/ID 删除。`test_spot_cloud_init.py`：YAML、大小、清理。`test_m4_04_capacity_sync.py`：sync 计数与 verify 失败。`test_runners.py`：池绑定。

### 9.8 工作流与冒烟脚本（A/M）
