## §1 一页速览

一句话：**把“竞价 Runner 能注册 GitHub”补成“能回平台取任务、按池标签落到正确工位”。**

一个比喻：竞价实例像外包工，GitHub 是派工系统；原来工位门牌（`runs_on`）写死在公告上，且工位到平台前台（回调地址）没有分机。这个 PR 给前台装了 VPC 分机，并把派工单改成“按池子门牌派工”。

交付块：

| 块 | 结果 |
|---|---|
| VPC 回调入口 | API 保留回环 + 可选 VPC 绑定；安全组是边界 |
| 回调基址 | `RUNNER_CALLBACK_BASE_URL` 注入 api/worker，写入主机 `.env` |
| 标签调度 | dispatch/manifest 冻结 `runs_on`；execute 动态选择 |
| 供给测试语义 | 明确为创建验证，避免“能建实例 = 能跑任务”的误读 |
| 验证 | 本地 127 项后端、148 项 node、5 用例并发冒烟；生产验收待人工启用 |

验证基线：CI（PostgreSQL 全量 pytest + migration）、docs/flow 门禁、deployment contract、runner contract。

## §2 架构导览

### 2.1 标签只有一个事实源

`runner_labels.py:39` 的 `pool_runner_labels` 是唯一解析入口：依次读 `instance_config_json`、`labels_json` 的 `runs_on` / `runner_labels` / `labels`，支持逗号字符串和数组，最后回落到调用方的 default。`provisioning/aliyun.py:479`（云初始化注册）与 `evaluations.py:375`（分片派发）都调用它，因此“Runner 注册什么标签”和“job 去哪里跑”不再可能各写一份。

这里保留了历史兼容：`labels` 是旧别名；`instance_config_json` 优先于 `labels_json`，方便运维临时按池覆盖。

### 2.2 冻结而不是运行时猜

`evaluations.py:413` 在构造分片前解析一次 `runs_on`，写入 manifest（`:430`）和 `client_payload`（`:461`）。重试路径 `case_attempts.py:710/736` 同样处理。manifest digest 覆盖 `runs_on`，所以 Runner 校验 digest 时也间接校验了标签。

契约里 `runs_on` 是**可选**字段：滚动部署期间旧平台发出的 dispatch 仍能通过新 Runner 的校验；新平台发出的 dispatch 在旧 Runner 上也只多一个被忽略的字段（Schema 的 `additionalProperties: false` 在旧 Runner 上会拒绝新字段——这是唯一的滚动部署风险，见 §6.3）。

### 2.3 回调入口的最小暴露

`deploy/docker-compose.prod.yml` 仍只映射 `127.0.0.1:8000:8000`，固定 Runner 的回环路径不变。`deploy/docker-compose.vpc.yml` 额外映射 `${API_BIND_ADDRESS}:8000:8000`，由 `deploy/common.sh:10-14` 在 `.env` 指定非回环地址时叠加。`deploy.yml:90-92` 从 Secrets 注入三个值，`:152-154` 写入主机 `.env`，`:155` 的 `grep -Ev` 保证重部署时替换而不重复。回调基址默认由 `API_BIND_ADDRESS` 推导为 `http://<IP>:8000`（owner 反馈后追加），显式 `RUNNER_CALLBACK_BASE_URL` 仍可覆盖。

安全组仍是实际网络边界：即使 API 绑定了 VPC 地址，没有放行规则时外部不可达。

### 2.4 工作流动态 runs-on

`eval-shard.yml:118` 把 prepare 的 `runs_on` 作为 job output；`:138-146` 从 dispatch JSON 读取并写入 `GITHUB_OUTPUT`；`:157` 的 execute 用 `fromJson(...)` 选择 Runner。缺口时回落到历史默认值，行为与改动前一致。

## §3 数据流走查

1. 管理员在 `/resources` 建阿里云连接与竞价池，池标签写入 `labels_json.runs_on`（M5-03 已有）。
2. 发起评测时平台解析池标签，写进 manifest 与 repository_dispatch，并冻结 digest。
3. eval-shard 的 `prepare` 在固定 Runner 上校验 dispatch、输出 `runs_on` 与矩阵。
4. `execute` 在池标签对应的 Runner 上执行；Runner 用 manifest 里的 `callback_base_url` 回平台取 manifest、报 started/completed。
5. 平台聚合结果；容量控制器缩容时先注销 Runner 再释放实例。

## §6 讨论点

### 6.0 流程门禁：PR 未关联 Project

- **位置**：GitHub Project（仓库外）与 `scripts/verify-flow-online.mjs`。

- **预判**：owner 在 PR 侧栏把 #120 加入项目后重跑该 job 即可。
- **结论**：待 owner 操作。

### 6.1 生产资源与安全组（阻塞验收）

- **位置**：`deploy/docker-compose.vpc.yml`、安全组（仓库外）。
- **现象**：代码已支持 VPC 绑定与回调基址，但生产环境尚未放行 8000，也未设置两个 Secrets。
- **问题**：没有这两步，竞价实例仍取不到 manifest，“能建池”仍不等于“能跑任务”。
- **预判**：这是本 issue 无法由代码单独闭环的部分，需要 owner 授权并执行。
- **结论**：待 owner 确认。

### 6.2 供给测试仍是创建验证

- **位置**：`backend/app/api/resources.py` 的 `test_provisioning`（未改代码）、`docs/architecture.md`。
- **现象**：实例创建后立即释放，不等待 Runner 注册。
- **问题**：用户可能把“供给测试通过”理解为“能跑任务”。
- **预判**：#119 验收允许“文档明确为创建验证”；同步等待会长时间占用 HTTP 请求，异步化需要新增实例用途字段与页面轮询，超出本次范围。文档已写明完整链路由真实评测验证。
- **结论**：接受现状，后续可做异步注册验证。

### 6.3 契约向后兼容

- **位置**：`runner-contract/schemas/v1/dispatch.schema.json`。
- **现象**：`dispatch` 的 `additionalProperties` 为 `false`，新平台发 `runs_on` 时旧 Runner 会判为非法。
- **问题**：滚动部署窗口内旧 Runner 可能拒绝新 dispatch。
- **预判**：Runner 与平台同仓部署，窗口很短；如要严格兼容，可让 Runner 先升级或把 `runs_on` 放入 manifest（Runner 只校验 digest，不反序列化额外字段）。当前接受。
- **结论**：留待评估。

### 6.4 重试时重新解析标签

- **位置**：`backend/app/services/case_attempts.py:693`。
- **现象**：重试派发在重试时重新读取池标签，而不是复用首次冻结值。
- **问题**：池标签在两次 attempt 之间变化时，重试可能落到不同 Runner。
- **预判**：标签是池级配置，变化意味着“换工位”，重试跟随新工位可以接受；若要求严格可溯源，应在 run 上冻结一份标签快照。
- **结论**：当前接受，记录为后续可观测性改进。

### 6.5 无 UI 变更与视觉证据

- **位置**：`web/**` 无改动。
- **现象**：本 PR 只改部署、调度与文档；资源页沿用 M5-03。
- **问题**：没有可对照原型的截图。
- **预判**：原型没有“生产 Runner 回调入口”界面；按交付规则，无 UI 变更不要求 Before/After，但生产验收截图需在启用后补。
- **结论**：接受。

## §9 文件级代码分析

### 9.1 `backend/app/services/runner_labels.py`（A）

职责：把“池配置 → Runner 标签列表”收敛成一份实现。旧代码在 `aliyun.py` 私有函数里重复，dispatch 侧根本没有，导致自定义标签池注册后接不到 job。实现思路：按来源与键的优先级遍历，字符串按逗号拆分，数组去空白，最后用 fallback 兜底并截断到 64。无第三方依赖。

### 9.2 `backend/app/services/evaluations.py`（M）

`run_runs_on` 依据 run 绑定的池决定 fallback：spot 池用 `RUNNER_SPOT_LABELS`，固定池/无池用 `self-hosted,linux,eval`。`build_case_dispatches` 在循环外解析一次，manifest 与 payload 写同一个列表，digest 自然覆盖。边界：run 的 `resource_pool_id` 为空时走默认，不影响合成评测。

### 9.3 `backend/app/services/case_attempts.py`（M）

`build_retry_dispatch` 增加一次解析与两个字段，其他行为不变；token/attempt 创建顺序未动。

### 9.4 `.github/workflows/eval-shard.yml`（M）

prepare 的 plan step 读 dispatch 文件输出 `runs_on`，execute 用 `fromJson`。选 `node -e` 而不是新增脚本，是为了让改动停留在工作流内；回退默认值保持旧行为。风险：`fromJson` 的空值分支依赖表达式 `||`，CI 已验证 YAML 解析，实际运行需一次真实 dispatch（生产验收覆盖）。

### 9.5 部署三件套（M/A）

`docker-compose.vpc.yml` 只加一条端口映射；`common.sh` 用 `.env` 而不是 shell 变量判断，保证 deploy/rollback/手工 compose 行为一致；`deploy.yml` 的空值写入让未配置 Secret 的环境保持回环默认，不会因缺少 Secret 部署失败。
