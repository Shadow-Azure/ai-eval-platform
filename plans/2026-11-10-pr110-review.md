## §2 架构导览

### 2.1 后端读模型：列表与详情同形

`list_resource_pools`（`resources.py:397`）在原有 `capacity_state` 外补了 `runners` 汇总；`_runner_summary`（`resources.py:201`）现在同时返回各状态计数和 `last_heartbeat_at`。这样页面列表不必为每个池再发一次详情请求，列表和详情的卡片模型也一致：

```python
# 旧：列表只有 capacity_state
return {"items": [_pool_state_payload(session, pool, settings) for pool in pools]}

# 新：列表附带 runner 汇总，详情复用同一 shape
return {
    "items": [
        {**_pool_state_payload(session, pool, settings),
         "runners": _runner_summary(session, pool)}
        for pool in pools
    ]
}
```

容量事实仍由 `capacity_control.pool_capacity_state` 只读计算；API 不写容量状态，写路径仍归 worker。

### 2.2 写路径：先落库、再审计、后提交

连接创建/验证、池创建/更新都新增了 `identity.record_audit`（`resources.py:312/359/424/507`）。新行先 `flush` 取得 id，再写审计，最后提交：

```python
session.add(pool)
_flush_or_conflict(session, "同名资源池已存在")
identity.record_audit(..., action="resource.pool.created", target_id=pool.id, ...)
_commit_or_conflict(session, "同名资源池已存在")
```

`_flush_or_conflict`（`resources.py:277`）把唯一约束冲突继续映射成既有 `409 resource_conflict`，避免审计目标 id 为空。

### 2.3 供给测试：把「发生了什么」交给后端

`test_provisioning`（`resources.py:602`）除实例、价格外新增 `steps`：费用确认 → 询价 → 创建实例 → 注册 Runner → 自动释放。每个步骤带 `status` 与脱敏 `detail`，前端不再猜测阶段：

```python
steps = [
    {"key": "cost_confirmed", "status": "passed", ...},
    {"key": "quote", "status": "passed", "detail": {"price_usd": ..., "price_threshold_usd": ...}},
    {"key": "instance_created", "status": "passed", ...},
    {"key": "runner_registration", "status": "skipped",
     "detail": {"reason": "test_instance_released_before_registration", ...}},
    {"key": "instance_released", "status": "passed" if released else "failed", ...},
]
```

释放失败不再返回 500：实例进入 `draining`、写 `resource.release_failed` 事件、步骤标记 `failed`，响应仍 200 供页面保留诊断。

### 2.4 前端数据层：防御式解析 + 可复用错误信封

`resources.ts` 的解析器把后端 snake_case 与可空字段归一化（`parseRunnerSummary` / `parseCapacityState`），避免页面直接消费 `unknown`。`ApiError` 新增 `fields`/`details`（`types.ts:36`），`request` 从 4xx 信封提取（`evaluations.ts:184`），让 422 能回到表单字段、供给测试失败能展示错误码。

### 2.5 页面结构：页签 + 卡片 + 抽屉/弹窗

`ResourcesPage`（`ResourcesPage.tsx:265`）由三块组成：

- 顶部四个 `StatusCard`：在线/容量、池上限、扩容实例、排队 Job；
- 页签：池卡片网格（含容量条、Runner 圆点、价格阈值、心跳、下次检查、排队原因）；连接卡片网格（能力、状态、最近验证、掩码、写操作）；
- 弹窗/抽屉：连接新建、池新建/编辑、池详情（Runner 表 + 事件时间线）、费用确认供给测试。

只读成员通过 `session.role` 隐藏所有写入口；详情抽屉仍可查看容量与 Runner。

## §3 数据流走查

一条端到端剧本（与冒烟截图对应）：

1. 管理员登录后进入 `/resources`，`GET /resource-pools` 与 `GET /connections` 并发加载；空态展示「先建连接、再建池」。
2. 点「新建资源连接」：`POST /credentials`（`kind=resource`，密钥加密）→ `POST /connections` → `POST /connections/:id/test`。成功后卡片显示「验证通过、最近验证时间、`****et`」。
3. 从连接卡「新建资源池」：默认选中竞价模式；提交 `POST /resource-pools`。后端 `validate_pool_configuration` 校验 `ecs:spot`、provider 与容量，不匹配返回 `422 connection_provider_mismatch`，前端把 `fields` 映射到表单。
4. 列表刷新：`GET /resource-pools` 返回 `capacity_state` + `runners`。价格高于阈值且存在排队 Job 时，卡片显示「当前竞价价格高于阈值」并解释排队 Job 保留。
5. 打开详情：`GET /resource-pools/:id` 与 `/runners` 并行；抽屉展示在线/忙碌/离线 Runner、最近心跳、当前 Job、资源事件。
6. 点「测试供给」：费用提示 + 复选框二次确认 → `POST /resource-pools/:id/test-provisioning`（`confirm_cost=true`）。后端创建并立即释放实例，返回 `steps`；页面按步骤渲染，注册步骤因测试实例立即释放而显示「跳过」。
7. 只读成员登录：同一页面只保留「刷新/详情」，连接页显示只读说明，凭据仍只显示掩码。

## §6 讨论点

### 6.1 池列表的 N+1 查询

- **位置**：`resources.py:397`（每池一次 `capacity_state`，再加一次 `_runner_summary`）。
- **现象**：池数量为 N 时，列表请求约 2N 组查询；当前产品规模（个位数池）无实害。
- **问题**：未来池数量上升会放大列表延迟；容量状态本身还包含一次 Spot 询价。
- **预判**：M5 阶段可接受，先保证语义正确；若池数量进入几十个，建议批量聚合 runner 计数/心跳，并把询价结果短 TTL 缓存。
- **结论**：观察项，不阻塞本 PR。

### 6.2 凭据与连接创建不是原子操作

- **位置**：`ResourcesPage.tsx:912`（先 `POST /credentials`，再 `POST /connections`）。
- **现象**：连接创建失败时，凭据可能已经落库；自检修复后弹窗会切到「使用已有资源凭据」并选中刚建的凭据，避免重复粘贴密钥。
- **问题**：仍没有服务端事务保证「凭据 + 连接」一起成功；极端失败会留下一个未使用凭据（可复用，不是泄漏）。
- **预判**：现有 API 未提供组合端点，前端复用已建凭据是成本最低的补救；若未来有批量接入需求，再加组合端点或显式清理策略。
- **结论**：已做前端补救，服务端原子性留作演进。

### 6.3 供给测试的「注册 Runner」步骤是 skipped

- **位置**：`resources.py:602` 的 steps 与 `ResourcesPage.tsx:1757` 的步骤文案。
- **现象**：M4-03 的测试供给按设计「创建后立即释放」，不会注册 Runner；页面显示「注册 Runner — 跳过」并解释。
- **问题**：issue 验收写的是「展示创建实例到注册 Runner 的过程」，字面上可能被理解为必须注册成功。
- **预判**：不伪造注册成功更安全；真实扩容时注册由供给器异步完成，页面在容量/Runner 明细里继续展示。
- **结论**：保持现状并在 PR 描述说明；若产品要求测试实例真的注册，需要改 M4-03 的立即释放策略并承担计费风险。

### 6.4 供给模式与供应商范围

- **位置**：`ResourcesPage.tsx:1156`、`resources.py:424`。
- **现象**：页面只开放已实现的自有机器（fixed）与竞价（spot）两种模式；连接供应商只开放阿里云，GitHub 标记待接入；页面对预留模式有文字说明。
- **问题**：原型展示了 Runner 组、按量、包年包月与 ECI；设计文档把它们列为预留。
- **预判**：不提供不可用的假入口是对的；范围差异来自后端供给器实现，不是本 PR 的遗漏。
- **结论**：维持现状，PR 描述已声明差异。

### 6.5 前端没有自动化组件测试

- **位置**：`web/src/pages/ResourcesPage.tsx` 全文件。
- **现象**：本仓库 `web/` 目前没有组件测试基础设施；本 PR 用真实浏览器冒烟覆盖主路径，但没有可进 CI 的 UI 回归。
- **问题**：后续改动可能悄悄破坏空态/权限/弹窗，只能靠人工冒烟发现。
- **预判**：建立 web 测试底座（MSW + 测试渲染器）是独立工作；强行在本 PR 引入会显著扩大范围。
- **结论**：记录为后续测试基建项；本 PR 的 API 边界由 pytest 覆盖。

### 6.6 掩码清洗是启发式

- **位置**：`services/resources.py:82`。
- **现象**：`rstrip('"}')` 去掉 JSON 结尾结构符，使 `****et"}` 变成 `****et`。
- **问题**：如果某类 secret 的最后 4 位本身以 `}` 结尾，会少显示一位；不影响安全性，只影响可读性。
- **预判**：当前资源凭据就是 JSON，收益大于风险；若未来支持非 JSON secret，可改为按 provider 生成专用掩码。
- **结论**：可接受。
