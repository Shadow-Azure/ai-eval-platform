## §1 一页速览

**一句话**：给 OpenSpec/CodeSpec 这类“仓库里没有 Skill/Command、要装 CLI 后 init 才生成”的资产源，补上运行时前置配置、隔离加载测试、结果持久化、快照冻结与 prepare/UI 门禁。

**比喻**：仓库只是毛坯房的零件清单（静态扫描 0 件）；加载测试是在临时工棚里按说明书把家具装一遍，确认能装出 4 个 Command、6 个 Skill、5 个 Agent；快照把成品封箱送进评测现场。当前两个关键缺口是：评测现场没有工具箱（Runner 不装 CLI），而且评测向导的选品清单只列仓库零件、不列成品（生成资产）。

## §2 架构导览

### 2.1 API 边界与 token

- 预览请求模型在 `backend/app/api/agent_assets.py:45-49`，只接受 `repo_url`、`requested_ref`、`scan_paths`、`runtime_prerequisites`；端点 `:183-199` 加 `require_admin`，返回 `{"load_test_token": token, **load_test_view(result)}`。
- 源码级加载测试端点 `:244-258` 复用 `run_load_test`；create 的 `load_test_token` 字段 `:40-42`。
- 前置校验在 `backend/app/services/agent_assets.py:225-283`：只允许 `install_command` / `init_command` / `runtime` 三个键，每个 ≤2000/100 字符，必须同时有 install 与 init。这里的“校验”只做形状与长度，不解释语义。
- token 缓存声明 `:56-67`，写入/读取 `:701-727`，fingerprint `:681-698`。指纹包含 `repo_url`、`requested_ref`、`scan_paths`、`runtime_prerequisites`，所以改了任一字段都拿不到旧结果；但 token 只存在进程内，多副本会静默退化为 `requires_setup`。

### 2.2 加载测试执行

- 执行壳 `run_setup_command` 在 `backend/app/services/agent_assets.py:361-378`：`/bin/sh -lc`、`cwd=临时目录`、`env={HOME: 临时目录, PATH: 继承}`、`timeout=600`、`capture_output=True`、`text=True`。
- 主流程 `_execute_load_test:586-678`：install→init 顺序执行；非零退出/扫描为空都算“正常失败”，超时/OSError 返回 `(result, infrastructure_error=True)`；日志只保留最后 20000 字符。
- 生成扫描 `_scan_generated_assets:467-536`：Skill 以目录为资产并收目录内全部普通文件；Command 递归收 `.md`；Agent 只收顶层 `.md`。所有路径都会 `resolve()` 后校验仍在根目录，符号链接全部跳过。
- 文件读取 `_read_generated_file:392-426`：超过 `MAX_ASSET_FILES` / `MAX_ASSET_BYTES`（8 MB）直接 422；内容按 UTF-8 `errors="replace"` 解码；mode 固定 `100644`。

### 2.3 冻结、合并与 digest

- 把已存的生成清单还原成 `ScannedAsset + 文件字节` 在 `_generated_source_assets:786-885`；会再次校验路径、类型、重复项、文件映射冲突——这是对数据库内容的自防御。
- resolve 主链在 `:1745-1756`：先 `_check_generated_conflicts`（`:1371-1408`），再按用户选择 `_select_assets`（`:1426-1535`），然后 `_merge_generated_assets`（`:1411-1423`）把**全部**生成资产并入，最后算 digest。
- 冲突判断比较的是“运行时目标路径”：Git 侧所有扫描资产（即使未选中）与生成资产不能映射到同一 destination；发现即 `generated_asset_conflict`。
- selection digest `:1310-1335`：非 CLI 源保持旧的 `{commit,runtime,assets}` 形态；有生成文件时追加 `generated: {path: sha256}`。这样内容变了但路径不变会产生新快照；内容不变重复 resolve 命中旧快照。
- 打包 `_pack_assets:1540-1650`：生成文件从 `generated_files` 读取，bundle 目标为 `skills/<name>/...`、`commands/<name>.md`、`agents/<name>.md`，与 Runner 的 `.claude` 物化约定一致。

### 2.4 状态机与 prepare 门禁

- `_source_status:292-301`：source 配了前置时，只有 `load_test.status == "passed"` 才 `ready`，否则 `requires_setup`；没配前置时沿用旧的 `_scan_status`。
- `run_load_test:761-784`：保存结果后，基础设施错误→`error`，通过→`ready`，普通失败→`requires_setup`。
- `create_source:1125-1230`：用 token + 完全匹配的 fingerprint 才持久化缓存结果；通过→`ready`，其余→`requires_setup`；没有 token 但有前置→`requires_setup`，否则 `unverified`（`:1156-1173`）。
- prepare 的阻断在 `backend/app/services/preflight.py:411-430`：检查的是 **source 当前** 的 `runtime_prerequisites_json` 与 `load_test_json`，不是快照里冻结的那份（见 §6.3）。

### 2.5 前端主线

- 添加向导：前置开关 + install/init 输入 + 加载测试 `AssetsPage.tsx:586-666`；保存门禁 `:512-520` 与 `handleSave:465-505`。加载测试通过后把返回的生成资产合并进本地 `scan.assets` 并选中（`:420-460`），保存时作为 resolve 的 `paths`。
- 卡片 `:1086-1099`、详情 `:939-958` 渲染 `RuntimePrerequisiteBlock` 并提供“重新测试”。
- 评测向导 `EvalWizardPage.tsx:342-350` 判断 `runtimeSetupBlocked`；`runPrepare/goNext` 在 `:671-674`、`:727-733` 阻断。资产列表来自 `/tree` 的 `last_scan.assets`（`:312-316`），因此看不到生成资产（见 §6.2）。

## §3 数据流走查

以 `main-copy-ar` 为主角（报告实测：静态扫描 0，加载测试生成 4 Command + 6 Skill + 5 Agent）：

1. **添加源**：操作员在添加向导填 repo/ref/scan path，点“自动扫描”。`preview_scan` 只读 Git tree，得到 0 个资产；UI 显示空状态并提示配置运行时前置。
2. **加载测试预览**：点“加载测试”，请求 `POST /agent-asset-sources/load-test-preview`。后端把 install/init 依次放进临时 HOME 执行；成功后扫描 `.claude`，返回状态、耗时、命令、`generated` 计数、`assets` 清单和 `log_tail`，同时把完整结果（含文件内容）放进进程内缓存，返回随机 token。
3. **保存**：`create_source` 用 repo/ref/scan_paths/前置重新算 fingerprint，命中缓存才把结果写入 `load_test_json`；通过→`ready`。随后 UI 立刻调用 `resolve`，把生成资产的虚拟路径（如 `.claude/skills/x`）作为 `paths`，resolve 重新扫描 Git、还原生成资产、检测冲突、打包并写快照。
4. **快照内容**：bundle 文件是 `skills/x/SKILL.md`、`commands/opsx/propose.md`、`agents/spec-reviewer.md`；manifest 额外记录 `runtime_prerequisites` 与 `load_test` 视图（`:1837-1838`）；selection digest 含生成文件 digest，重复 resolve 幂等。
5. **评测向导**：用户从资产页“用于评测”跳到 `/evals/new?assetSourceId=...`。向导的资产表来自 `/tree`，而 `/tree` 只返回 `source.last_scan_json.assets`（Git 静态，0 个），生成资产不在这里；`selectedPaths` 为空，“读取资产”按钮禁用（`EvalWizardPage.tsx:1166-1173`）。用户可以直接下一步，prepare 不带 `asset_snapshot_id`，于是这次评测**静默地不使用任何生成资产**。
6. **prepare**：若用户确实选中了静态资产并冻结了快照，`check_preparation` 读取 source 当前状态；若加载测试未通过则返回 `asset_runtime_setup_required`。但它不读快照 manifest 里冻结的 `load_test`，因此“通过后重测失败”会误伤旧快照，“测试前冻结、之后才通过”又会放过缺生成资产的旧快照（§6.3）。
7. **Runner**：任务包把 `asset_snapshot` 整体传给 Runner（`backend/app/api/runners.py:933`），Runner 只下载 bundle、把文件写进 `.claude`（`runner/lib/asset-bundle.mjs:114-136`、`runner/scripts/real-task.mjs:211`）。`runtime_prerequisites` 字段虽在快照里，Runner 完全不读；安装/init 不会在评测沙箱重放，生成的 `opsx` 命令调用 `codespec/openspec` 时仍然找不到 CLI（§6.1）。

**例子 A（主用例）**：`main-copy-ar` 加载测试通过，快照里有 15 个生成资产；但评测向导显示“该资产源还没有扫描结果”，直接下一步后评测无资产。添加向导创建的首个快照在 UI 上也没有入口被评测复用。

**例子 B（重测失败）**：某源在 10:00 加载测试通过并冻结了快照；11:00 因网络抖动重测失败，`source.load_test_json` 变成 failed。此后即使快照内容完全没变，prepare 仍会报 `asset_runtime_setup_required`，旧的有效快照被当前状态“连坐”。

**例子 C（冲突）**：Git 仓库本身有 `.claude/commands/opsx/propose.md`，CLI 又生成同名目标路径。加载测试通过、源为 `ready`；但每次 resolve 都在 `_check_generated_conflicts` 抛 `generated_asset_conflict`（测试 `test_resolve_generated_asset_conflict_with_git_scan_fails_clearly` 就是这样构造的）。源没有编辑入口，操作员只能重建源或改仓库。

## §6 讨论点

> 级别口径：P1 阻断合并/验收；P2 应修；P3 可后续、接受或仅记录。结论栏留给主审拍板。

### 6.1 P1：Runner 没有执行运行时前置，生成 Command 在评测现场仍缺 CLI

### 6.3 P2：prepare 用 source 实时状态判断，而不是快照冻结的 load_test

**位置**：`backend/app/services/preflight.py:411-430`；快照 manifest 的冻结值在 `backend/app/services/agent_assets.py:1837-1838`；prepare 透传在 `backend/app/services/preparations.py:311-312`。

**结论**：待拍板（本检视建议：修）。

### 6.5 P2：加载测试子进程没有硬化——非 UTF-8 输出 500、超时留下孤儿、输出无上限

**位置**：`backend/app/services/agent_assets.py:361-378`（`subprocess.run(..., capture_output=True, text=True)`）、`:616-650`（超时/异常捕获）、`:624-637`（只捕获 `TimeoutExpired`/`OSError`/`SubprocessError`）。

**现象**（均本机实测）：
- 命令输出非法 UTF-8（如 `printf '\377\376abc'`）→ `subprocess.run` 抛 `UnicodeDecodeError`，该异常不在捕获列表；API 只把 `AgentAssetError`/`GitClientError` 转成错误信封，最终是 500，而不是稳定的 `load_test_execution_failed`。
- 命令 `sleep 30 & wait` 配 1s 超时 → `TimeoutExpired` 抛出后，`sleep 30` 仍以 PPID 1 存活；因为 `subprocess.run` 只杀直接子进程 `/bin/sh`，不会杀进程组。600s 超时的真实场景会积累 npm/node 子进程，且临时 HOME 已被删除。
- `capture_output=True` 会先把完整 stdout/stderr 缓冲在内存，最后才截到 20k 日志；一个话痨安装器可把 API worker 内存打高。

**问题**：这是管理员专用的高风险 shell 执行端点，稳定性与资源边界必须自己保证；上述三点都不是“输入非法”而是“正常 CLI 行为”，会让加载测试偶发 500 或拖垮 worker。

**预判**：建议修。`subprocess.run(..., errors="replace")` 解决解码；用 `Popen(start_new_session=True)` + 超时 `os.killpg` 清理整组；流式读取并限制 stdout/stderr 缓冲（超过 N 字节只保留尾部），而不是先全收再截。测试补：非法 UTF-8、超时后无残留子进程、超大输出。

**结论**：待拍板（本检视建议：修）。

**现象**：若生产/测试库里存在旧 API 写入的非空 `runtime_prerequisites_json`（例如只有 `{"cli":"openspec"}`，或 `{"install_command": "..."}` 缺 init），部署后：scan 会把 source 置 `requires_setup`；prepare 会阻断；`POST /load-test` 直接 422 `runtime_prerequisites_incomplete`；而源没有编辑入口，无法补齐。

**问题**：字段不是本 PR 新增（本 PR 新增的是 `load_test_json`），但本 PR 第一次给这个字段赋予了“强语义”和阻断力，没有数据迁移/读取兼容。是否有实际旧数据取决于环境；代码层没有兜底。

**预判**：建议先查生产/预发是否有非空 `runtime_prerequisites_json` 且不是 install+init 形状。若有，迁移成空（视为未配置）或补齐；若是任意未知形状，读取时降级为“未配置”并给 warning，而不是阻断。补一条 legacy 形状测试。

**结论**：待拍板（本检视建议：先查数据，再决定迁移或兼容）。

### 6.13 P3：selection digest 不含前置命令/加载测试身份，快照可能带旧配置

**位置**：`backend/app/services/agent_assets.py:1310-1335`（digest 只含 commit/runtime/选中资产/生成文件 digest）；manifest 前置写入 `:1837-1838`；existing snapshot 命中 `:1757-1771`。

**现象**：如果管理员改了 install/init 命令，但新命令生成的资产内容/路径完全相同，digest 不变，resolve 会返回旧快照；旧快照 manifest 里的 `runtime_prerequisites` 仍是旧命令。重跑加载测试得到相同生成内容时，也不会更新快照里的 `load_test.ran_at`/日志。反之，生成内容变了会正确产生新快照。

**问题**：快照声称“前置命令随快照冻结”，但选择 identity 没有绑定前置配置；在“命令变了、产物没变”的场景下，追溯信息是旧的。影响限于审计/可复现性，不会直接跑错资产，但会让“冻结可追溯”打折扣。

**预判**：建议后续把规范化后的 `runtime_prerequisites`（或其 hash）加入 digest（仅当前置非空时，避免改变非 CLI 源的历史 digest），或在命中旧快照时校验 manifest 前置与当前一致、不一致则生成新快照。补“命令变、产物不变”的测试。

**结论**：待拍板（本检视建议：后续）。

**问题**：这两点如果随未提交修复一起合入，会把“快照是唯一执行输入”的承诺打破：要么命令因 HOME 不同而失败，要么 init 的产物替换冻结产物，导致同一快照在不同 CLI 版本/环境下跑出不同资产。前者是 P1（主用例直接跑不起来），后者是 P1/P2（可复现性/审计被破坏）。

**预判**：合入前先修：install 与 init 统一用同一个用户和 HOME（推荐 `-u eval -e HOME=/home/eval`，并确保该 HOME 可写）；或者规定命令不得依赖 `$HOME`、显式写死系统路径。`init` 要么只在加载测试执行、Runner 只 install + 注入冻结资产；要么先 setup 再 materializeSnapshot，让冻结文件最后落盘。runner 测试补两条：`$HOME` 相对命令可用；`asset_count>0` 时 setup 不覆盖冻结文件。

**结论**：待拍板（本检视建议：合入前修，否则 6.1 不能算真正关闭）。
