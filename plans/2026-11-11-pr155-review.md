## §1 一页速览

**一句话**：把 `/deployments` 从“该功能将在后续里程碑接入”的占位页，换成由真实部署记录驱动的交付流水线页，并把“回滚”拆成两层——控制面负责权限、确认、审计和派发，ECS 主机负责真正替换镜像。

**一个比喻**：部署记录像高铁时刻表，页面是站台大屏；回滚按钮不是司机，它只是向调度台（GitHub Actions）发一张工单，真正换轨的是主机上的 `rollback.sh`。控制面永远不直接伸手去换轨，也不会把数据库“倒着开”。

## §2 架构导览

### 2.1 读路径：一条“按需拼装”的只读链

`GET /api/v1/deployments`（`api/deployments.py:71`）只做参数与响应编排，真正的拼装在 `services/deployments.py:442`：

- 历史行按 `started_at` 倒序取 `limit+1`，用 `has_more` 表达截断（`deployments.py:445`）。
- 当前/上一版本只看 `status == "succeeded"`（`deployments.py:308`），失败记录留在历史里，不会顶掉“当前生产版本”。
- Alembic 版本直接读 `alembic_version`（`deployments.py:87`），与当前部署记录的 `migration_revision` 对比，得到 `in_sync`。
- 环境健康只做五个轻量探针（`deployments.py:342`），并把结果压缩成“状态 + 一句话”；容量、桶名、表行数留在 `/operations`（ADR 0002）。
- CI 门禁只对当前部署查询（`deployments.py:192`），失败/无 token/无运行降级 `unknown`。

### 2.2 回滚路径：控制面与主机职责分离

`POST /{id}/rollback`（`api/deployments.py:85`）的顺序是：

1. 目标必须存在且属于当前环境；
2. 目标必须是“上一成功版本”（`api/deployments.py:55`），避免前端拿着旧页面回滚到任意历史；
3. 当前版本与目标的迁移版本都必须等于数据库当前 revision（`services/deployments.py:414`）；不相等就 409，不猜“向前兼容”；
4. `confirm=true`（`api/deployments.py:139`）；
5. 通过 `repository_dispatch` 派发 `deployment-rollback`（`services/deployments.py:522`）；
6. 写 `deployment.rollback_requested` 审计并提交（`api/deployments.py:161`）。

部署工作流的 rollback job（`deploy.yml:284`）只走 SSH 到 ECS 执行 `deploy/rollback.sh`；脚本只恢复 `.state/previous.env` 里的应用镜像，数据库阶段标记为 `skipped`（`rollback.sh:34`）。

### 2.3 五阶段数据从哪来

`STAGE_DEFINITIONS`（`services/deployments.py:38`）与原型一致：

| 阶段 | 数据来源 | 缺失时 |
|---|---|---|
| 测试与文档门禁 | GitHub Actions runs（`github_dispatch.py:187`） | unknown |
| 构建镜像并推送 ACR | 部署脚本前置事实（`deploy.sh:73`） | success（脚本能跑说明构建已成功） |
| PostgreSQL 迁移 | 部署脚本阶段（`deploy.sh:76-82`） | 旧记录按整体状态推断 |
| ECS 滚动更新 | 部署脚本阶段（`deploy.sh:84-86`） | 旧记录按整体状态推断 |
| 健康检查 | 部署脚本阶段（`deploy.sh:88-93`） | 旧记录按整体状态推断 |

旧记录没有 `detail_json.stages` 时，`_inferred_status`（`services/deployments.py:117`）只把能确定的阶段标成功，其余标 unknown；不会伪造耗时。

## §3 数据流走查

**剧本：管理员打开 `/deployments`，看到旧版本健康下降，执行一次回滚。**

1. 浏览器 `fetchDeployments` 调 `GET /api/v1/deployments`（`web/src/api/deployments.ts:200`）。
2. 后端取 `deployment` 行；当前版本 `32b9119`，上一版本 `a9e10ff`；数据库 revision `0019_trace_capture_status`；两者 `in_sync=true`。
3. 后端查 `32b9119` 的 Actions runs，识别 Backend & Web CI / Documentation Gates / Flow Gates 全绿，生成 quality_gate 成功阶段（`services/deployments.py:192`）。
4. 页面用 `DeployTimeline` 渲染五个阶段（`DeploymentsPage.tsx:88`）；`EnvironmentCard` 渲染五行组件（`:126`）；`RollbackCard` 因为 `rollback.available=true` 显示“回滚到 a9e10ff”（`:152`）。
5. 管理员点击按钮 → `RollbackModal` 打开（`:214`）；未勾选时确认按钮禁用，勾选后启用。
6. 点击确认 → `useRollbackMutation` POST（`api/deployments.ts:230`）；后端再次校验目标、迁移版本、confirm，派发事件并写审计。
7. GitHub Actions rollback job SSH 到 ECS，`rollback.sh` 拉取上一版镜像、`up -d`、`wait_ready`，写入 `rolled_back` 行；页面下一次轮询看到新历史行。

## §6 讨论点

### D1 · flow-online 要求 PR 关联 Project

- **位置**：`.github/workflows/flow-gates.yml` / PR #155 侧栏。
- **现象**：CI `flow-online` 失败：`PR 未关联 project（GitHub 侧栏设置）`；本地 agent token 无 `read:project`。
- **问题**：不是代码问题，是 PR 元数据缺失；需要人工把 PR #155 加入仓库 Project。
- **预判**：由人工在侧栏添加后重跑 CI 即可通过。
- **结论**：待人工操作。

### D2 · 回滚迁移版本采用“精确相等”而不是“向前兼容”

- **位置**：`backend/app/services/deployments.py:414`。
- **现象**：只有目标与当前部署的 `migration_revision` 都等于数据库 revision 时才允许回滚；数据库一旦前进，旧镜像回滚会被拒绝。
- **问题**：比设计里的“可回滚到兼容旧镜像”更保守；好处是不会把旧应用接到未知 Schema，代价是跨迁移回滚不可用。
- **预判**：当前阶段可接受；如果未来需要跨 expand 迁移回滚，需要记录兼容窗口或镜像 Schema 版本。
- **结论**：

### D3 · GET 每次都会探活对象存储并查询 GitHub

- **位置**：`backend/app/services/deployments.py:342`、`:192`。
- **现象**：页面每 30 秒轮询一次；每次 GET 会做 Redis/OSS 探针并可能调 GitHub Actions API。
- **问题**：单租户、低并发下可接受；若后续多用户高频打开，可能放大外部调用。
- **预判**：可加 15–30 秒进程内缓存或把探针拆分；当前不制造额外基础设施。
- **结论**：

### D4 · 部署记录是平台全局数据，没有 tenant_id

- **位置**：`backend/app/models/operations.py`（Deployment）。
- **现象**：`deployment` 表由 m2-02 创建时没有租户字段；本 PR 沿用表结构，所有登录成员能读同一份部署历史。
- **问题**：当前是单租户平台设计，部署属于平台级事实；未来多租户需要重新定义可见性。
- **预判**：不阻塞本 issue；若引入多租户，应在 ADR 与表中补归属。
- **结论**：

### D5 · 回滚请求没有幂等键/互斥锁

- **位置**：`backend/app/api/deployments.py:85`。
- **现象**：同一目标连续点击两次（网络重试）会派发两次 `repository_dispatch`；工作流 `concurrency: production` 会串行执行，第二次通常是重复恢复同一镜像。
- **问题**：不会造成数据损坏，但会产生两条审计与两次流水线。
- **预判**：可接受；若要更严谨，可对同目标短时间窗口去重或检查进行中的 rollback 记录。
- **结论**：

### D6 · 部署脚本阶段记录没有 shell 级测试

- **位置**：`deploy/common.sh:22-58`、`deploy/deploy.sh:73-97`。
- **现象**：`record_deployment.parse_stages` 有单元测试，但 `stage_begin/stage_finish`、`current_database_revision` 的真实 shell 行为只在生产运行时验证。
- **问题**：语法或 `docker compose exec` 行为错误会等到首次部署才暴露。
- **预判**：合并后首次部署核对 `detail_json.stages` 与 Alembic revision；必要时补一个本地 Compose 集成测试。
- **结论**：

### D7 · PR 描述中的测试数量已修正

- **位置**：PR #155 描述。
- **现象**：初稿写“7 项”，实际 `tests/backend/test_deployments.py` 收集 8 项。
- **问题**：描述与事实不一致，会误导验收。
- **预判**：已改。
- **结论**：已修正，无需代码变更。

## §9 文件级代码分析

### 9.1 `backend/app/api/deployments.py`（A）

职责：只读列表与管理员回滚两个端点。关键依赖 FastAPI、SQLAlchemy、Pydantic；没有新增第三方包。

变更代码块：

```python
current = session.scalar(select(Deployment).where(...).limit(1))
previous = _previous_succeeded(session, settings.deploy_environment, current)
if previous is None or previous.id != target.id:
    raise _http_error(409, "rollback_target_changed", ...)
```

这一段把“目标必须是上一成功版本”从 UI 承诺变成服务端硬约束；前端刷新滞后时不会回滚到任意历史。预判：目标 id 比较是必要的，但并发窗口内若新部署完成，服务端仍可能把旧目标当作上一版本；工作流执行时使用主机 `.state/previous.env`，与“上一版本”语义一致。

检视发现：无阻塞问题；`_http_error` 与 `error_detail` 的 envelope 与其他 API 一致。

### 9.2 `backend/app/services/deployments.py`（A）

职责：部署读模型、阶段推断、CI 门禁、环境健康、回滚可用性。

关键依赖：SQLAlchemy、`github_dispatch`、`object_store`、`redis`（可选）。

变更代码块：

```python
if conclusions & {"failure", ...}:
    stage["status"] = "failed"
elif statuses & {"queued", "in_progress", ...}:
    stage["status"] = "running"
```

检视时发现初版先判 running，会在一项失败、另一项仍在跑时显示“进行中”；已改为失败优先并补测试。其余推断逻辑把“不知道”保持为 unknown，符合“不伪造”的目标。

### 9.3 `backend/app/services/github_dispatch.py`（M）

职责：新增 `list_workflow_runs_for_commit`，与既有 dispatch/cancel 共用认证头与 transport 注入。HTTP 非 2xx、非 JSON、缺列表都转 `GitHubDispatchError`，由上层降级 unknown。

检视发现：没有分页处理；一个 commit 的 Actions runs 通常少于 50。若未来超过，需要按 `total_count` 翻页。

### 9.4 `deploy/common.sh` / `deploy.sh` / `rollback.sh`（M）

职责：把阶段、真实 Alembic revision 与 run URL 写入部署记录。`stage_begin/stage_finish` 用 shell 变量累积 `key|status|started|finished|detail` 行，`record_deployment.py` 解析成 JSONB。

变更代码块：

```sh
MIGRATION_REVISION="$(current_database_revision)"
```

这一行替代了原来的 `0002_deployment` 硬编码；`current_database_revision` 从 `.env` 读角色/库名，避免自定义库名时探针失败。检视发现：依赖 postgres 容器正在运行；失败时 fallback unknown，不阻塞部署记录。

### 9.5 `.github/workflows/deploy.yml`（M）

职责：新增 `repository_dispatch: deployment-rollback` 与 rollback job。所有原 build/deploy job 在 `repository_dispatch` 下跳过，避免回滚时重新构建/迁移。

变更代码块：

```yaml
if: github.event_name == 'repository_dispatch' && github.event.client_payload.deployment_id != ''
```

检视发现：rollback job 对 payload 做格式校验；仍建议在真实演练时确认 GitHub Environment 的审批规则不会阻塞紧急回滚。

### 9.6 `web/src/pages/DeploymentsPage.tsx`（A）

职责：页面组合与交互。`DeployTimeline`、`EnvironmentCard`、`RollbackCard`、`RollbackModal`、历史表、加载/空态。

变更代码块：

```tsx
<Checkbox checked={acknowledged} onChange={...} />
...

```

检视发现：二次确认是“点击回滚 → 勾选影响 → 确认”，比单纯一次弹窗更明确；`destroyOnHidden` 替换了 AntD 废弃的 `destroyOnClose`。历史表把版本与提交合并为一个 SHA 链接，避免重复；与原型有语义版本差异，已在 PR 说明。

### 9.7 `web/src/api/deployments.ts`（A）

### 9.8 测试与文档
