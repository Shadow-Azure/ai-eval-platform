## §1 一页速览

一句话：**给每个 attempt 装上五个独立闹钟，并让取消变成一次“关跑道”而不是“炸飞机”**。

比喻：Runner 是飞行员，`started` 是起飞报告，心跳是“我还在飞”；Worker 的 reaper 是塔台计时器，reconciler 是雷达复核。取消时塔台先关闭跑道（停止新派发、拒绝新模型调用），已经在飞的飞机可以落地并交回黑匣子（上传产物），塔台再宣告航班取消；迟到的报告只进档案，不改变已取消的事实。

交付块：

| 块 | 内容 |
|---|---|
| 五类超时 | queue / execution / scoring / upload / heartbeat，各自错误码与终态 |
| 失败分类 | retryable / permanent / scoring_only，评分失败不重跑 Agent |
| 取消 | `cancelling` → 收口或宽限强收 → `cancelled`；409 拒绝新 started/模型调用 |
| 对账 | GitHub find+cancel 幂等；丢失的完成事件从已上传对象回填 |
| Runner | 心跳 sidecar，真实 Agent 执行期间持续证明控制脚本存活 |

验证基线：`pytest` 314 passed/1 skipped；`node --test tests/runner/*` 62 passed；`npm test` 67；CI 全绿；冒烟 `reports/2026-11-10/m4-02-lifecycle/`。

## §2 架构导览

- **唯一收口**：`lifecycle.settle_attempt_failure`（`lifecycle.py:120` 附近）负责终态、事件、释放 Runner 绑定、可选重试；callback 的 `handle_failed` 与 reaper 都走它，避免两套状态机漂移。
- **相位时钟**：`phase_changed_at` 只在 `mark_status` 里推进；reaper 用它测量 queue/scoring/upload 预算，避免 `updated_at` 被任意写入刷新（`reaper.py:54`）。
- **取消**：`cancel_evaluation`（`evaluations.py:548`）只取消 `pending/dispatching/queued`，运行中 attempt 保留；`refresh_run_progress`（`:688`）有独立 cancelling 分支，全部收口后 `finalize_cancelled`（`:634`）。
- **对账**：`reconcile`（`reconciler.py:64`）先合并 reaper 计数，再逐个 `_reconcile_cancel`（`:110`）与 `_backfill_completion`（`:219`）。取消事件按 (run,type) 去重，第二轮不再发 GitHub 请求。
- **撤销点**：`started` 在 `case_attempts.py:315` 抛 409；网关在 `model_gateway/service.py` 的 claim binding 处拒绝 cancelling/cancelled run——无状态 HMAC token 不需要黑名单。

## §3 数据流走查（一条主线）

1. Runner 拉 manifest 拿短期 token，`started` → attempt `running`，`phase_changed_at=now`。
2. 长任务：sidecar 每 30s 心跳；平台 reaper 用 `heartbeat_at` 判断存活。
3. 用户取消：API → `cancelling`；未启动 attempt 直接 `cancelled`；运行中 attempt 继续。
4. 运行中 attempt 上传/完成 → `finalize_completion`；`refresh_run_progress` 发现无 queued/running → run `cancelled`。
5. 若完成回调丢失：对象已上传但 attempt 停在 `uploading` → reconciler 校验对象、读 score、回填 `case.reconciled_completed`。
6. 若远程取消失败：`eval.cancel_failed` 记录，下一轮重试；宽限到期强收所有活跃 attempt（`cancel_grace_exceeded`）。

## §6 讨论点

### D1 多 Worker 并发取消可能重复 POST GitHub cancel
- **位置**：`services/reconciler.py:110`（事件去重发生在调用之后）
- **现象**：两个 worker 同时处理同一 cancelling run，在写入 `eval.cancel_requested` 前的窄窗口内都可能发出 POST。
- **问题**：GitHub 的 cancel 是幂等的，但会产生重复请求与重复审计。
- **预判**：当前单 worker 部署无实害；多副本前应加 DB 租约或条件更新（`cancel_sent_at IS NULL`）。
- **结论**：

### D2 reaper 在 cancelling 期间暂停计时
- **位置**：`reaper.sweep_lifecycle` 跳过 cancelling/cancelled run
- **现象**：取消宽限（600s）内若运行中 attempt 既不上报也不心跳，靠宽限强收，而不是 execution/heartbeat 超时。
- **问题**：诊断码会是 `cancel_grace_exceeded` 而非更具体的超时原因。
- **预判**：可接受；取消场景下“尽快收口”优先于区分死因，且宽限可配置。
- **结论**：

### D3 心跳 sidecar 在父进程被 SIGKILL 时可能成为孤儿
- **位置**：`runner/scripts/heartbeat-agent.mjs`（`process.once("exit")` 只覆盖优雅退出）
- **现象**：force kill 父进程后 sidecar 继续每 30s 心跳，心跳超时不会触发；由 `case_timeout_seconds` 兜底。
- **问题**：极端情况下晚 1 小时才收口。
- **预判**：GitHub 通常杀整个进程组；可接受，M4-04 的临时 Runner 生命周期会整体回收实例。
- **结论**：

### D4 `run-name` 用 dispatch_key 而非 eval_run_id
- **位置**：`.github/workflows/eval-shard.yml:25`、`github_dispatch.py:97`
- **现象**：`run-name` 为 `eval-shard <dispatch_key>`；dispatch_key 前缀是 eval id，所以 `display_title` 仍可匹配。
- **问题**：匹配依赖 dispatch_key 格式；若未来改格式需同步。
- **预判**：当前测试已锁定该格式，可接受。
- **结论**：

### D5 完成回填的 `result_status` 依赖 score JSON
- **位置**：`reconciler.py:219`
- **现象**：score 不可读时回填为 `not_scored`；对象存储未配置时跳过回填。
- **问题**：无 OSS 的纯开发环境不会触发回填。
- **预判**：生产必有 OSS；开发环境由 callback 覆盖。
- **结论**：

## §9 文件级代码分析（要点）

- `lifecycle.settle_attempt_failure`：单事务内完成终态、事件、绑定释放、重试/终态分支；幂等靠“已终态 + event_id 已存在”双重判断。风险低。
- `reaper.sweep_lifecycle`：固定顺序 execution → heartbeat，避免心跳超时掩盖执行超时；每类有 batch 上限，单轮有界。风险低。
- `evaluations.cancel_evaluation` / `refresh_run_progress`：取消分支不参与 completed/partial 判定；queued-only 取消立即终态，保持既有测试语义。风险低。
- `reconciler._reconcile_cancel`：find → cancel → 事件；失败可重试；宽限强收。风险：多副本重复请求（D1）。
- `case_attempts.finalize_completion`：callback 与回填共用，避免两套完成逻辑；回填写独立事件便于审计。
- `heartbeat-agent.mjs`：token 只走 env、不打印；停止路径 SIGTERM→5s→SIGKILL；测试覆盖成功/异常/禁用。风险：SIGKILL 孤儿（D3）。
- `github_dispatch.find/cancel`：沿用 dispatch 的 token/url 约定；只接受 202/204；100 条 run 窗口（D4 相关）。
