## §1 一页速览

一句话：per-case manifest 刷新不再借用一条可能已被平台挂断的 keep-alive 连接，而是每次重新拨号；拿不到 case token 仍然 fail closed，但错误里能看见真实的传输原因。

一个比喻：原来的 `fetch` 像用一条公共电话线，说完话把听筒搁着；平台五秒后挂断，runner 埋头搬镜像没听见忙音，再拿起听筒只听到“嘟嘟嘟”。现在每次刷新都重新拨号，不再赌上一通电话还通着。

## §2 架构导览

1. **传输层**（`runner/lib/manifest-source.mjs:37-78`）：`fetchOnce` 用 `node:http` / `node:https` 发 GET，`agent: false` 让每次请求新建 TCP，`Connection: close` 要求服务端响应后关连接。响应头由 `fetchManifest`（`:85-100`）统一映射为 token / digest / expiry / tasks / model token；`file://` 本地模式完全不变。
2. **总超时**（`:62-76`）：`http.request` 的 `timeout` 只覆盖已有 socket 的空闲时间，连不上时不会触发；因此额外用 `setTimeout` 保留原来 `AbortSignal.timeout(10000)` 的总截止语义，连接、等待响应、读 body 任一段超时都会 destroy。
3. **刷新调用**（`runner/scripts/real-task.mjs:557-602`）：镜像 tar 加载与 `git checkout` 两个 `spawnSync` 之后，带 `case_run_id` 重新拉 manifest。成功才把 `X-Runner-Model-Token` 注入 `CLAUDE_GATEWAY_TOKEN`；失败则 `failCase`，不启动 Agent。
4. **诊断层**（`runner/lib/manifest-source.mjs:102-117`、`real-task.mjs:564-596`）：`manifestErrorDetail` 同时读取 `error.cause.code`（旧 `fetch` 的 `UND_ERR_SOCKET`）与 `error.code`（新 http client 的 `ECONNRESET` / `ECONNREFUSED`）；日志写 `cause_code` / `cause_message`，用例错误摘要写 `code: message`，不必翻 runner 日志也能定位。
5. **测试缝**（`runner/lib/mock-platform.mjs:20-66`）：`behavior.manifestReset(url)` 在读到 manifest 请求时直接 `socket.destroy()`，让“初始 shard 拉取成功、per-case 刷新传输失败”可复现，而不必真的等 42 秒镜像。

## §3 数据流走查

1. `real-task.mjs` 启动，先拉 shard manifest，拿到任务 payload 与任务 token；这次也走一条新的短连接。
2. 发送 `started` 回调，随后 `loadImageTarball` 用 `spawnSync` 下载并 `docker load`（冷 spot 约 42 秒），再 `git checkout` 基线提交（约 4–5 秒）。这段时间 Node 事件循环被完全占住。
3. 平台 uvicorn 默认 5 秒关闭空闲 keep-alive 连接；FIN 留在内核缓冲区，runner 恢复后也不去处理它。
4. 刷新调用 `fetchManifest(dispatch.manifest_url, { caseRunId })`。修复后这里直接新建 TCP，不查旧池；服务端按 `case_run_id` 校验并签发 case token。
5. 拿到 token：`CLAUDE_GATEWAY_TOKEN` 注入 Agent 容器，模型调用按 case 归因。
6. 拿不到 token：日志记 `model_token_refresh_failed` 与 cause；用例以 `model_token_unavailable` 结束，错误摘要带传输原因，Agent 不启动，也不回退启动早期的 shard token。

## §6 讨论点

### 6.1 不再跟随 HTTP 重定向

- **位置**：`runner/lib/manifest-source.mjs:37-78`
- **现象**：旧实现用 `fetch`，默认跟随 301/302/307/308；新的 `http.request` 只发一次请求，3xx 会按非 2xx 失败。
- **问题**：如果平台地址或反向代理以后用重定向把 HTTP 切到 HTTPS，runner 会拉不到 manifest。
- **预判**：`manifest_url` 由 `runner_callback_base_url` 直接拼出，生产是 VPC 内直连 `http://<vpc-ip>:8000`，没有重定向；为 P0 保持改动最小，先不引入重定向逻辑。若以后接入代理或域名跳转，再补有界重定向。
- **结论**：待人工确认是否接受；当前生产拓扑无重定向。

### 6.2 初始 shard 拉取也变成新连接

- **位置**：`runner/lib/manifest-source.mjs:85-100`
- **现象**：`fetchManifest` 的所有 HTTP 调用都走 `fetchOnce`，不只 per-case 刷新。
- **问题**：每个分片多一次 TCP/TLS 握手；`plan-cases` 与 `trace-e2e-runner` 也共享这个 helper。
- **预判**：每个 shard 只有个位数 manifest 请求，握手成本可忽略；统一走一条确定性路径比保留两种传输更难出错。`plan-cases` 每次 job 只拉一次，不受影响。
- **结论**：接受，保持单一传输实现。

### 6.3 测试桩用 `closeIdleConnections` 模拟 uvicorn

- **位置**：`tests/runner/manifest-source.test.mjs:101-124`
- **现象**：测试用 `server.closeIdleConnections()` 立即关掉空闲 socket，再 `spawnSync("sleep")` 阻塞客户端；真实环境是 uvicorn 5 秒计时器关连接。
- **问题**：测试没有真的等 5 秒，也没有覆盖 uvicorn 的真实行为。
- **预判**：这里要验证的是“客户端在 FIN 未处理时仍能成功刷新”，而不是 uvicorn 的计时器本身；用 100ms/300ms 把时序压缩到确定性范围，比 sleep 5 秒更稳。真实 5 秒窗口仍需生产复跑确认。
- **结论**：保留确定性版本；生产复跑作为补充证据。

### 6.4 flow priority 记 P2、GitHub issue 是 P0

- **位置**：`.agents/flow/issues/m8-runner-manifest-fresh-connection.md:8`
- **现象**：GitHub issue #362 的修复优先级是 P0，但流程树记为 P2。
- **问题**：两处优先级不一致，读流程树的人可能误判严重程度。
- **预判**：这是流程门禁的结构限制：m9 已有 done 的 P0 issue，若在 m8 新增未 done 的 P0，`verify:flow` 会把 m9 的 P0 判成“跨 milestone 串行未清”；m8 当前最高未清档是 P1（仅剩 1 个），P2 是唯一解锁档。GitHub issue 的 P0 不变。
- **结论**：待人工确认；若流程规则调整，可回填 P0。

### 6.5 诊断字段只覆盖 cause，不覆盖 HTTP 状态错误

- **位置**：`runner/lib/manifest-source.mjs:102-117`、`runner/scripts/real-task.mjs:570-596`
- **现象**：HTTP 500/503 返回的是 `Error("manifest 拉取失败：HTTP 503")`，没有 `code`，所以 `cause_code` 为 null，摘要只带 message。
- **问题**：如果失败是服务端 5xx 而不是 socket，日志里看不到结构化错误码。
- **预判**：5xx 的 message 已包含状态码，且平台访问日志能按 `case_run_id` 查到请求；issue 只要求补 `error.cause.code`，不为 HTTP 状态额外造错误码，避免诊断口径膨胀。
- **结论**：接受；后续若需要按状态码聚合，再统一约定。

## §9 文件级代码分析

### 9.1 `runner/lib/manifest-source.mjs`

职责：分片脚本共享的 manifest 传输；负责 HTTP(S) / file:// 读取、case token 查询参数与响应头映射。

变更形态：M（前身 `git show origin/main:runner/lib/manifest-source.mjs`，22 行 HTTP 拉取）。

关键依赖：只用 Node 内置 `node:http` / `node:https` / `node:crypto` / `node:fs`，保持 runner 零第三方依赖；`node:http` 的 `agent: false` 等价于“这通电话打完就挂，不复用线路”。

旧代码：

```js
const response = await fetch(requestUrl, { signal: AbortSignal.timeout(10000) });
if (!response.ok) throw new Error(`manifest 拉取失败：HTTP ${response.status}`);
const bytes = Buffer.from(await response.arrayBuffer());
```

新代码：

```js
const req = request(url, {
  method: "GET",
  agent: false,
  timeout: timeoutMs,
  headers: { connection: "close" },
}, (response) => { /* collect bytes + status */ });
```

实现思路：把“连接生命周期”从全局 undici 池收回到单次请求；状态码、body、响应头的解析责任不变，仍由 `fetchManifest` 统一映射。总超时用独立 timer 保留旧语义，避免连接阶段无上限等待。`manifestErrorDetail` 是纯函数，便于单测。

检视发现：无未决缺陷；重定向与 HTTP 状态错误码的取舍见 §6.1 / §6.5。

### 9.2 `runner/scripts/real-task.mjs`

职责：单个 case 的执行入口，包含镜像准备、manifest 刷新、Agent 启动与结果上报。

变更形态：M（刷新段与 failCase 摘要）。

旧代码：

```js
}).catch((error) => {
  console.error(JSON.stringify({ status: "model_token_refresh_failed", message: ... }));
  return null;
});
if (!agentModelToken) {
  return failCase("model_token_unavailable", "manifest 未签发 case 级 model token，拒绝启动 Agent", ...);
}
```

新代码：

```js
let refreshError = null;
...catch((error) => { refreshError = error; ... cause_code: detail.causeCode ... });
if (!agentModelToken) {
  const reason = [detail?.causeCode, refreshError.message].filter(Boolean).join(": ");
  return failCase("model_token_unavailable", `...${reason ? `（${reason}）` : ""}`, ...);
}
```

实现思路：失败路径只多保存一个 `refreshError` 引用，成功路径零变化；fail-closed 判定仍是 `if (!agentModelToken)`，没有新增回退分支。

检视发现：`refreshError` 只在这个 case 的闭包内使用，没有跨 case 泄漏；摘要截断 200 字符，避免超长错误撑爆回调。

### 9.3 `runner/lib/mock-platform.mjs`

职责：契约测试用的最小平台桩，记录请求、对象与回调状态。

变更形态：M（新增一个行为钩子）。

新代码：

```js
if (request.method === "GET" && request.url?.startsWith("/manifest") && resetManifest(request.url)) {
  requests.push({ ... });
  request.socket.destroy();
  return;
}
```

实现思路：在读取 body 之前断开，最接近“服务端已关连接”的传输失败；钩子默认 false，不影响既有测试。

检视发现：钩子只支持 GET manifest，范围足够；没有暴露到生产代码。
