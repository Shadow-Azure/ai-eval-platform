## §1 一页速览

一句话：给评测结果页加一栏“同条件上一次考试”的对照，先确认两次考试用的是同一套题（用例集合与指标口径），再算分差，并把两次的配置差异摊开。

| 交付块 | 内容 |
|---|---|
| 推荐 | 同数据集版本 + Runtime + 模型 + 资产快照优先，次选去掉资产快照；没有就空态 |
| 手动基线 | 任意同租户、有最终结果的终态评测；逐项标差异 |
| 指标差值 | percentage（pp）/number/cny/ms/histogram，版本/分母/用例集合不符不计算 |
| 配置差异 | 数据、执行、策略、镜像 4 类共 14 行 |
| UI | 质量摘要卡、指标卡差值行、页头入口与宽弹窗 |
| 测试 | pytest 9 项 + 浏览器冒烟 13 项 + 构建/门禁 |

验证基线：`pytest` 全量、`ruff`、`npm run build`、`npm test`、`verify:docs`、`verify:flow --diff` 通过；冒烟 13/13。

## §2 架构导览

### 2.1 服务层：先定“能否比”，再算“差多少”

`compare_run`（`backend/app/services/comparison.py:678`）是唯一入口：

1. 取当前结果：终态优先 `is_final`，运行中回退快照（`_select_metric_rows`，:124）。
2. 计算用例集合摘要：对 `EvalCaseRun.case_key` 排序后 sha256（`_case_digest`，:111）。这是“同一套题”的判据，比只比数据集版本更准，能覆盖同版本下不同子集。
3. 候选与推荐：`_candidate_runs`（:554）先按 `EXISTS(MetricResult.is_final)` 过滤，再限量 20；`_recommend`（:626）两轮扫描实现“优先同资产快照、降级为同数据集/Runtime/模型”。
4. 配置事实与差异：`_config_facts`（:204）把两边冻结输入整理为可比较的 `compare` 键与展示值；`_config_differences`（:339）只把用例集合/指标口径标为不可比，其余差异只提示。
5. 指标差值：`_metric_deltas`（:422）逐指标做版本、分母口径、分母、用例集合、展示类型与值结构六道守卫；只有全部通过才计算 delta/ratio/improvement。

### 2.2 API 层：薄适配器

`compare_eval_run`（`backend/app/api/results.py:87`）负责租户作用域、当前评测 404 与 `ComparisonInvalid` 到 `{error: {code, message, request_id}}` 的映射；不自带业务判断。

### 2.3 前端：一次查询，三处复用

`EvalDetailPage` 在结果页/弹窗打开时请求对比（`web/src/pages/EvalDetailPage.tsx:507`），`metric_deltas` 同时喂给指标卡差值行、质量摘要卡与弹窗表格，避免三份口径漂移。

## §3 数据流走查

1. 用户进入 `/evals/:id?tab=results`；结果与对比两个查询并行（:490 / :507）。
2. 对比请求带可选 `baseline_run_id`；服务端先做租户与自身引用校验，再读基线最终结果（`compare_run` :678–760）。
3. 自动模式：候选按 `finished_at` 倒序；推荐命中后返回 `recommendation.tier` 与中文理由；未命中返回 `empty_state=no_comparable_baseline` 与候选列表。
4. 指标差值：`resolved_rate` 40% vs 30% → `delta=0.1`，前端按 percentage 显示 `+10.0 pp`；`cost_per_case` 0.30 vs 0.35 → `delta=-0.05`，按 `lower_is_better` 判为 improvement。
5. 配置差异与指标表一起进入弹窗；用户切换 Select 后 query key 变化，重新请求并同步摘要、警告、表格。
6. 用例集合不一致时：`case_set.comparable=false` → 顶部“指标不可直接比较”警告 + 每行“不可比”原因；仍然展示两边原值与配置差异。
7. 当前评测仍在运行：`is_final=false` → 弹窗提示“快照指标”，但差值照常展示。

## §6 讨论点

### 6.1 候选窗口先限量后过滤（已修复）

- **位置**：`backend/app/services/comparison.py:554`。
- **现象**：原实现 `LIMIT CANDIDATE_LIMIT * 3` 后才跳过没有最终指标的评测。
- **问题**：如果最近 60 个终态评测都没有最终指标（合成评测或无数据集评测），更早的可比基线会被挤出窗口，页面误报空态。
- **预判**：概率低但可复现，属于“空态判断被无关数据污染”。
- **结论**：已修复——查询内用 `EXISTS(MetricResult.is_final)` 过滤后再 `LIMIT 20`，并补 60+ 无指标评测的回归测试。

### 6.2 候选列表的 N+1 查询

- **位置**：`_candidate_runs`（:554）。
- **现象**：每个候选再查一次指标行、用例 key 与模型/数据集名称。
- **问题**：候选上限 20，单次对比最多约百次小查询；当前无实害，但数据量增长后会放大。
- **预判**：可接受；对比是低频读路径，且租户内评测数量有限。
- **结论**：不修，保留可读性；若后续候选上限提高，再改为批量查询。

### 6.3 质量摘要用数值而非原型的环形图

- **位置**：`web/src/pages/EvalDetailPage.tsx:1766`。
- **现象**：原型用环形图展示解决率；本实现用大号数值 + 差值。
- **问题**：视觉不完全一致；但差值对比页的核心是“差多少”，大号差值比环形图更直接，也避免再引入一套图形组件。
- **预判**：信息等价，不构成功能差异。
- **结论**：接受，PR 描述中如实标注该差异。

### 6.4 手动基线未写入 URL

- **位置**：`:507` 的查询状态。
- **现象**：手动切换基线只存在 React state，刷新后回退到自动推荐。
- **问题**：无法把“我选了这个基线”分享给同事；但原型与 issue 均未要求深链。
- **预判**：属于后续体验增强，不影响正确性。
- **结论**：登记为后续项，不在本 PR 扩大范围。

### 6.5 空态标题与“当前无结果”复用

- **位置**：`:1766` 空态分支。
- **现象**：`current_results_unavailable` 与 `no_comparable_baseline` 都落在“暂无可比基线”卡片，但描述文案不同。
- **问题**：标题略笼统。
- **预判**：描述已说明原因，用户可理解。
- **结论**：接受；如后续要做引导跳转再细分。
