## §2 架构导览

### 2.1 Schema

`runner-contract/schemas/v1/dispatch.schema.json` 只允许 opaque ID、manifest URL/digest 和过期时间；`additionalProperties: false` 防止有人把模型 Key 塞进 GitHub payload。`completion.schema.json` 的 `score_manifest` 同时要求 `object_key/sha256/size`，与 M2-05 的对象存在性校验对齐。

### 2.2 执行前拒绝顺序

`runner/scripts/synthetic-task.mjs` 的顺序是：dispatch schema → 过期时间 → token 绑定 → manifest 拉取 → digest → manifest schema → run/shard/attempt 一致 → claim。任何一步失败都不写对象、不发 completion；测试分别断言“未发 POST”“未拉 manifest”“无对象”。

### 2.3 幂等

`dispatch-guard.mjs` 用 `mkdir` 原子 claim `dispatch_key`；`callback-client.mjs` 用 `event_id` 作为 `Idempotency-Key`，网络错误/429/5xx 有界退避，其他 4xx 不重试。平台数据库的唯一约束仍是最终底线，本地 claim 只是 Runner 侧第一道闸。

### 2.4 对象与回调

`object-store.mjs` 以 sha256 作为对象键，天然去重；`synthetic-task.mjs` 先写 score/trace，再发 upload manifest，最后发 completion。真实 OSS 只需替换 store 的 put 实现，协议不变。

## §3 数据流走查

1. 测试启动 mock platform，生成 manifest 文本与 digest。
2. 生成绑定 eval_run/shard/attempt 的 token，写入 dispatch.json。
3. CLI 校验 dispatch/token，拉取 manifest，校验 digest 与字段一致性。
4. claim dispatch_key；逐用例写对象、发心跳、上传清单、发 completion。
5. 第二次同 dispatch：claim 失败，输出 duplicate，不执行。
6. 回调 500：同一 event_id 重试；400：写 failure；409：停止且不写 failure。

## §6 讨论点

### 6.1 HMAC 演示 secret 与“不在 Runner 存长期密钥”冲突

- **位置**：`runner/workflows/eval-shard.yml`、`runner/lib/auth.mjs`
- **现象**：模板注入 `RUNNER_TASK_SECRET`。
- **问题**：这是长期验证材料，和设计的安全边界不一致。
- **预判**：M2-03 只证明 token 校验路径；M2-04 必须换 OIDC，且模板注释已标注。
- **结论**：接受为 M2-03 的演示限制，M2-04 阻塞项。

### 6.2 本地 claim 不能替代平台唯一约束

- **位置**：`runner/lib/dispatch-guard.mjs`
- **现象**：claim 是本地文件系统锁。
- **问题**：多 Runner 并发时本地锁无效。
- **预判**：平台 `(tenant_id, dispatch_key)` 唯一约束才是权威；本地锁只防止同一 Runner 重复执行。
- **结论**：保留，M2-05 用平台回调/DB 做最终裁决。

### 6.3 JSON Schema 子集校验器

- **位置**：`runner/lib/json-schema-subset.mjs`
- **现象**：只支持本协议使用的关键字。
- **问题**：未来 Schema 增加 `oneOf`/`$ref` 时校验器会静默忽略。
- **预判**：当前六份 Schema 未使用这些关键字；新增时需同步扩展校验器并补测试。
- **结论**：接受，README 已说明。

### 6.4 workflow 仍是单 job

- **位置**：`runner/workflows/eval-shard.yml`
- **现象**：一个 shard 一个 job，没有 matrix。
- **问题**：与设计 06 的用例级 matrix 不完全一致。
- **预判**：M2-03 只冻结协议；M2-05 按分片/用例扩展。
- **结论**：接受，作为 M2-05 工作项。

## §9 文件级分析（分组）

### 9.1 `runner-contract/schemas/v1/*`

职责：六份可被外部工具复用的 JSON Schema。关键依赖 Draft 2020-12；`additionalProperties: false` 和 `schema_version` const 是防止协议漂移的两道闸。检视发现：dispatch 的 `manifest_url` 允许 `file://`，是为本地 fixture；生产平台会只发 https。

### 9.2 `runner/lib/*`

职责：零依赖参考实现。`auth.mjs` 用 HMAC 演示，`dispatch-guard.mjs` 用 mkdir 原子性，`callback-client.mjs` 有界重试。检视发现：`verifyToken` 未强制 `pool_id`（当前调用方不传），M2-04 接入 pool 时补绑定。

### 9.3 `runner/scripts/synthetic-task.mjs`

职责：确定性合成任务 CLI。结果只由 `dispatch_key + case_key` 决定，不使用随机数或当前时间；测试用两次独立运行逐字节比对证明。检视发现：未发 `started` 回调，M2-05 接入平台状态机时补。

### 9.4 `tests/runner/*`

职责：24 个 node:test 契约测试。覆盖 schema 正反例、成功闭环、重复、拒绝、重试、永久失败、409、确定性、workflow 文本约束。检视发现：根 `npm test` 不包含子目录，M2-02 CI 需显式加 `node --test tests/runner/*.test.mjs`。
