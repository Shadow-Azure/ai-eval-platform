## §1 一页速览

一句话：把镜像 tar 下载/加载和 `git checkout` 从“调用期间整个世界暂停”的 `spawnSync`，换成“子进程在隔壁干活、主线程继续收消息”的异步 `spawn`。

一个比喻：原来前台接待员亲自去仓库搬 42 秒的货，期间电话没人接；现在他叫了搬运工，自己继续接电话，只在货到后才继续下一步。

## §2 架构导览

### 2.1 异步命令封装（`runner/lib/run-command.mjs:50`）

`runCommand` 用 `spawn` 起子进程，返回与 `spawnSync` 同形的结果对象：`status`、`signal`、`stdout`、`stderr`、`error`。命令失败**不 reject**，调用方继续用现有的 `status`/`error` 分支，避免把“业务失败”与“封装异常”混在一起。

- 超时：`timeout` 计时器触发 `stop("ETIMEDOUT")`，先 SIGTERM，5 秒后 SIGKILL（`run-command.mjs:116`）。
- 输出上限：stdout/stderr 分别计数，超过 `maxBuffer` 截断并 `stop("ENOBUFS")`（`run-command.mjs:128`）。
- 取消：`AbortSignal` 在 spawn 前已 abort 时直接返回 `ABORT_ERR`；运行中 abort 则杀子进程。
- 结束：`close` 统一 resolve；若已被超时/取消/截断标记为失败，`status` 归一为 `null`，与 `spawnSync` 的 killed 结果一致（`run-command.mjs:158`）。

### 2.2 镜像加载（`runner/lib/image-tarball.mjs:63`）

`loadImageTarball` 变成 async，内部用局部 `run()` 把调用方注入的 `spawn` 传给 `runCommand`。四个步骤（缓存 inspect、curl、`docker load`、verify inspect）全部 `await`；`finish()` 仍同步写 `trace/image-tarball.json` 并返回原结果结构。失败 stage 仍为 `download` / `load` / `verify`，`scrubUrl` 仍把签名 URL 替换成 `<tarball-url>`。

### 2.3 用例编排（`runner/scripts/real-task.mjs:466`、`:556`）

`realCase` 本来就是 async：镜像 tar 加载、checkout 和两处递归 `chmod` 改为 `await` 后，per-case manifest 刷新前的事件循环不再被这些子进程占住。`dockerRun` 仍同步（`:156`），原因见 §6 D1。

## §3 数据流走查

以冷 spot 机、`image_tarball` 命中为例：

1. `realCase` 创建 `trace/`（`:455`），调用 `await loadImageTarball`（`:466`）。
2. `loadImageTarball` 先 `docker image inspect` 判缓存（`:96`）；未命中则创建临时目录。
3. `curl` 异步下载 tar（`:112`），期间事件循环可处理定时器、信号和网络 I/O。
4. `docker load -i`（`:132`）与 verify inspect（`:144`）继续异步执行；每步失败都写 trace 并返回 `{ok:false, stage, error}`。
5. 回到 `realCase`，`docker create/cp` 仍是同步 `dockerRun`（已知剩余风险），随后 `await runCommand("chmod", …)`（`:508`）。
6. `await runCommand("git", ["checkout", …])`（`:556`），失败仍抛 `checkout 失败`。
7. `fetchManifest` 的 per-case 刷新在以上 await 之后执行；长任务期间事件循环已能处理 keep-alive 关闭（#362 的竞态前提被削弱）。

## §6 讨论点

### D1 `dockerRun` 仍同步，registry pull 回退仍可能阻塞

- **位置**：`runner/scripts/real-task.mjs:156`
- **现象**：`docker pull/create/cp/run/exec` 全部经 `dockerRun` 的 `spawnSync` 执行；镜像 tar 未命中而回退公开源时，pull 仍会阻塞事件循环。
- **问题**：本 issue 的验收只点名镜像 tar 与 checkout；把 `dockerRun` 整体改 async 需要重写用例编排的调用链，改动面远大于本 PR。
- **预判**：接受为已知剩余风险，PR 描述已写明；在 `run-command` 就绪后可作为后续 issue 逐步迁移。#362 的非池化刷新仍是该回退路径的确定性保证。
- **结论**：本 PR 不修，留作后续（已知限制已记录）。

### D2 `extractSourceArchive` 的 tar 解压仍同步

- **位置**：`runner/lib/source-archive.mjs:102`、`:133`
- **现象**：M8-22 source mode 下载用 fetch（异步），但 `tar -tzf` / `tar -xzf` 仍是 `spawnSync`。
- **问题**：解压大仓库可能阻塞数秒；不过它发生在 per-case token 刷新之后，不在 #362 的失败窗口内，也不在本 issue 点名的路径上。
- **预判**：保持现状，若后续统一迁移 `spawnSync` 再处理。
- **结论**：本 PR 不修。

### D3 `flow-online` 需要 PR 关联 Projects v2

- **位置**：`scripts/verify-flow-online.mjs:49`、PR 侧栏
- **现象**：CI 只有 `flow-online` 红，原因是 PR 未加入 Project 看板；bot token 缺 `read:project`，无法自助添加。
- **问题**：流程门禁要求 PR 同时挂 milestone 与 project；milestone 已补，project 需要人工在侧栏操作。
- **预判**：在 PR 侧栏加入项目后重跑 `flow-online` 即可，不需要改代码。

### D5 `maxBuffer` 截断精度与 `spawnSync` 略有差异

## §9 文件级代码分析

### `runner/lib/run-command.mjs`（A）

职责：把一次性、可能长达数十秒的子进程执行变成可 await 的 Promise，同时保留 `spawnSync` 时代调用方依赖的结果形状。

关键依赖：只用 `node:child_process` 的 `spawn`，无第三方包。`node:events`/`stream` 由 Node 内部实现，测试里用 `process.execPath` 起真实子进程。

变更块：

- 旧：无此文件，调用方直接用 `spawnSync`，阻塞事件循环。
- 新：`spawn` + `close` resolve + 三个失败通道（超时/取消/输出超限）。`stop()` 统一杀进程并映射错误码；`finish()` 统一归一 `status`。
- 实现思路：把 `spawnSync` 的“同步结果”拆成“异步事件 + 一次性 resolve”，不改变调用方的分支结构。

检视发现：无阻塞问题；`maxBuffer` 精度差异见 D4。

### `runner/lib/image-tarball.mjs`（M）

职责：冷启动 OSS 镜像 tar 的下载、load、校验与回退诊断。

变更块：

- 旧：`spawn("docker"/"curl", …, {encoding, timeout, maxBuffer})` 同步返回。
- 新：`await run(...)`，四个阶段依次 await；`finish()`/trace 写入不变。
- 实现思路：只替换执行原语，不改 stage 名称、错误文案来源或回退契约。

检视发现：无；超时测试确认失败仍落在 `download` stage。

### `runner/scripts/real-task.mjs`（M）

职责：单个真实用例的编排：取镜像、准备 workspace、刷新 token、跑 Agent、评分。

变更块：

- 旧：`loadImageTarball(...)` 同步；`spawnSync("git", checkout)`；`spawnSync("chmod")` ×2。
- 新：`await` 上述四处；checkout 同时检查 `error`，保留 `checkout 失败` 错误路径。
- 实现思路：让 async 函数在长任务期间把控制权交回事件循环，同时不改变后续步骤顺序。

检视发现：`dockerRun` 仍是同步边界（D1）。

### `tests/runner/run-command.test.mjs`（A）

职责：固定异步封装的失败语义与事件循环响应性。

关键点：超时/取消/输出截断都用真实子进程验证，避免 mock 掩盖 `close`/`kill` 行为；响应性测试用“定时器先于命令完成”的顺序断言，而不是松散的耗时阈值。

检视发现：无。

### `tests/runner/image-tarball.test.mjs`（M）

职责：镜像 tar 各阶段与失败回退。

关键点：`fakeSpawn` 记录命令并返回真实 Node 子进程，既保留命令序列断言，又让 `run-command` 的流/超时逻辑真正执行；新增下载超时与响应性用例。

检视发现：无。
