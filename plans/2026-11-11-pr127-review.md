## §1 一页速览

一句话：让每次用例执行把 Claude Code 的主/子 Agent 原生会话、关系元数据与 stdout/stderr 按 attempt 归档，并把单文件清单升级为可校验的多文件清单。

比喻：像把一次性快递袋换成带面单的分拣箱——面单只写平台可接受的安全相对路径（`logical_path`），每件货物有摘要（`sha256`）和大小；宿主的真实货架地址不出现在面单上。旧快递袋（单文件 `trace_manifest`）仍能收，只是没有分拣信息。

|---|---|---|
| 原生采集 | 主/子 Agent JSONL、`subagents/*.meta.json`、stdout/stderr 诊断 | runner 测试 8 项 + fake `claude` |

## §2 架构导览

### 2.1 采集层：从隔离 HOME 里“抄作业”

`collectTraceBundle` 是唯一入口（`runner/lib/trace-capture.mjs:171`）。它做四件事：

1. 把 `trace/claude-stream.jsonl`、`trace/claude-stderr.log` 映射为逻辑路径 `diagnostics/stdout.jsonl`、`diagnostics/stderr.log`（`:187-216`）；`trace/diagnostics/` 下由失败路径写入的补充诊断也一并收进来。
2. 递归遍历 `<runtimeHome>/.claude/projects/`，只收 `.jsonl` 与 `.meta.json`（`:229-246`）。`.meta.json` 被分类为 `trace_metadata`，其余 `.jsonl` 为 `trace`；`/subagents/` 只影响 `native_format`（`:116-132`）。
3. 用 `captureReasons` 判断完整性（`:135-168`）：没有主会话 → `native_session_missing`；stdout 里的 `session_id` 找不到同名文件 → `root_session_missing`；子会话缺 meta 或 meta 缺会话 → `subagent_metadata_missing` / `subagent_session_missing`；缺 stdout → `stdout_missing`。任一原因存在即 `partial`，否则 `complete`（`:253-255`）。
4. `dedupeTraceObjects` 以 `(artifact_kind, sha256)` 去重，并拒绝“同一逻辑路径对应两个 digest”（`:275-299`）；`traceManifestFromBundle` 只保留清单需要的字段，不带 `bytes`，也不带宿主源路径（`:303-335`）。

关键取舍：**清单是“对象级”的，不是“文件路径级”的**。相同字节只保留一个 object，因此两个不同逻辑路径若内容完全相同，只会留下先出现的那个路径（详见 §6.6）。

### 2.2 契约层：一个字段承载两种形态

上传清单（`upload-manifest.schema.json`）与完成清单（`completion.schema.json`）是两套不同的东西：

- 上传清单面向“平台已签发对象键”的登记，每个对象必须有 `artifact_kind/object_key/sha256/size/content_type`；`logical_path` 可选（`:13-44`）。
- 完成清单的 `trace_manifest` 既可以是旧三字段 `{object_key, sha256, size}`，也可以是 `{manifest_version, capture_status, incomplete_reasons, objects[]}`；`objects[]` 里 `logical_path` 必填（`completion.schema.json:80-201`）。

这里有一个必须知道的实现事实：仓库用的是**自定义 JSON Schema 子集**，不是完整 draft 2020-12。JS 侧只实现 `type/const/enum/minLength/maxLength/pattern/format/minimum/maximum/minItems/maxItems/items/required/properties/additionalProperties`（`runner/lib/json-schema-subset.mjs:46-112`），Python 侧逐字镜像（`backend/app/runner_contracts.py:109-157`）。**`oneOf`、`allOf`、`if/then`、`not`、`minProperties` 都不支持**。所以“legacy 或多文件”的二选一无法只在 schema 里表达，除非先扩展两个镜像校验器。

### 2.3 后端：先归一化，再合并，最后落状态

`trace_manifest.py` 是唯一权威：

- `normalize_trace_manifest`（`:161-205`）先看有没有 `objects`：有就走多文件分支，没有就走旧三字段分支。多文件分支会校验 `capture_status`、`incomplete_reasons`，并强制“只有诊断文件时不能声称 complete”（`:193-202`）。
- `_dedupe`（`:119-138`）以 `(artifact_kind, sha256)` 去重，同时检查同一 `logical_path` 是否对应不同 digest；冲突抛 `manifest_conflict`。
- `merge_manifest_objects`（`:238-274`）按 `object_key` 把上传阶段的对象并入 attempt 清单，缺字段时用完成回调补齐；同一 object key 不同 digest 或同一路径不同 digest 抛冲突。
- `trace_status_for`（`:226-235`）把采集状态映射成 `ready/incomplete/degraded/failed`；旧单文件固定 `ready`。

`case_attempts.py` 的接线：

- 上传回调先 `normalize_upload_objects`，再 `_verify_objects`（HEAD + size），最后合并进 `attempt.artifact_manifest_json`（`:501-524`）。
- 完成回调先 `normalize_trace_manifest`，再对 `trace_objects()` 逐个 `_verify_objects`（`:676-684`），然后 `finalize_completion` 落 case 的 `trace_status` 并写事件（`:612-639`）。

### 2.4 失败与重试：workdir 是隔离边界

`realCase` 为每个用例创建独立 `mkdtemp` workdir（`real-task.mjs:153`），把 `<workdir>/.runtime-home` 挂成容器里的 `/testbed/.runtime-home`，Claude Code 的 `HOME` 与 `CLAUDE_CONFIG_DIR` 都指向这里（`runtime-claude-code.mjs:114-128`）。因此：

- 同一 attempt 的采集只看到本次 HOME，不会混入别的 attempt。
- 重试是新的 attempt 行、新的 workdir、新的 `artifact_manifest_json`；旧 attempt 的清单不被覆盖（测试 `test_retry_attempt_keeps_its_own_trace_manifest`）。
- 失败路径在 `collectCapture` 里仍会读 workdir 中的文件；`finally` 只删除 workdir（`real-task.mjs:369-371`），而采集到的 `bytes` 已在内存里，所以上传不受影响。

### 2.5 状态与迁移

模型枚举从 `pending/ready/failed/unlinked` 扩到 `pending/ready/incomplete/degraded/failed/unlinked`（`evaluation.py:43`），CHECK 约束名沿用命名约定 `ck_eval_case_run_trace_status`（`evaluation.py:208`、初始迁移 `1a795994c4e9:187`）。`0019` 用 `batch_alter_table` 先删旧约束再建新约束（`0019_trace_capture_status.py:28-31`），downgrade 先把新值回填成 `ready` 再恢复旧约束（`:34-41`）。

### 2.6 前端：本 PR 没动，但状态值已经变了

后端会产出 `incomplete`/`degraded`，但现有 `EvalDetailPage` 的 `TRACE_OPTIONS` 与 `traceStatusMeta` 仍只有四个旧值（`web/src/pages/EvalDetailPage.tsx:85-90`、`:121-126`）。结果：筛选项里没有新状态；表格/抽屉会把 `incomplete`、`degraded` 原样显示成英文 token，颜色为默认灰。PR 明确说本 issue 不含前端，因此这更像 #94/#95 的交付项，而不是本 PR 的阻塞项（见 §6.7）。

## §3 数据流走查：一次带子 Agent 的成功执行

1. `realCase` 创建 workdir，`docker cp` 出测试镜像的 `/testbed`，创建 `.runtime-home` 与 `trace/`（`real-task.mjs:153-174`）。
2. 容器以 `-v <workdir>:/testbed` 启动，`HOME=/testbed/.runtime-home`；按设计假设（真实布局待验证，见 §6.5），Claude Code 把主会话写到 `.runtime-home/.claude/projects/<project>/<session>.jsonl`，子 Agent 写到同目录 `subagents/agent-<id>.jsonl`，关系元数据写到 `agent-<id>.meta.json`。
3. 执行结束，`runClaudeCode` 把 stdout/stderr 写入 `trace/claude-stream.jsonl` / `trace/claude-stderr.log`（`runtime-claude-code.mjs:337-347`）。
4. `collectCapture` 调 `collectTraceBundle`：先收诊断，再递归收 projects；`captureReasons` 用 stdout 里的主 `session_id` 校验主文件是否存在，并检查每个子会话与 meta 是否成对。
5. `dedupeTraceObjects` 去重；`store.putBytes` 为每个文件算本地对象键；`requestUploadUrls` 只把 kind/digest/size/content_type 发给平台换平台键（`real-task.mjs:496-517`）。
6. Runner 按平台键 PUT 每个对象，再把“平台键 + 原逻辑路径/版本”回填成 `reportedObjects`（`:679-731`），调用 `uploads` 回调；后端 HEAD 每个对象并合并进 attempt 清单（`case_attempts.py:501-524`）。
7. Runner 用 `traceManifestFromBundle` 生成多文件清单，并随 `completed` 回调发送（`real-task.mjs:771-789`）；后端再次 HEAD、归一化、合并，按 `capture_status` 落 `case_run.trace_status`，写 `case.completed` 事件（`case_attempts.py:612-656`）。
8. 前端收到事件后刷新 case 列表；`trace_status=complete` 显示为 `ready`，只有 stdout 时显示为 `incomplete`。

失败分支：

- 资产快照失败：写 `trace/diagnostics/asset-failure.json`，返回 `traceBundle`，`executionStatus=failed`（`real-task.mjs:204-228`）。
- Agent 非零退出：保留 stdout/stderr 与已生成的 native 文件，`traceBundle` 带 `failureDetail`（`:320-337`）。
- 空补丁：`executionStatus=succeeded`、`resultStatus=unresolved`，仍上传轨迹（`:339-352`）。
- **评分阶段异常（测试补丁 `git apply` 失败、`parseReport` 抛错等）没有兜底采集**：异常直接冒出 `realCase`，`finally` 删掉 workdir，外层 catch 只 `fail()`，不会上传轨迹（见 §6.2）。

## §6 讨论点

### 6.1 Schema 比后端宽松：`{}`、缺字段、双分支、`..` 都能通过校验

- 位置：`runner-contract/schemas/v1/completion.schema.json:80-201`、`upload-manifest.schema.json:13-44`、`backend/app/services/trace_manifest.py:161-205`
- 现象：本次实测用仓库自己的 `validatePayload` 校验，以下 payload 全部返回 `ok: true`，但后端会拒绝或改变语义：
  1. `trace_manifest: {}` 通过 schema，后端 422 `manifest_invalid`；
  2. `trace_manifest: {object_key}` 通过 schema，后端 422（缺 `sha256/size`）；
  3. `trace_manifest` 同时带 `object_key` 与 `objects[]` 通过 schema，后端静默只取 `objects`；
  4. `logical_path: "a/../b.jsonl"` 通过完成 schema 实测（上传 schema 使用同一 `pattern`），后端 422。
- 问题：schema 是契约的“规范产物”，但当前它无法表达“legacy 或多文件二选一”和各分支的必填字段；自定义校验器又不支持 `oneOf/if/not/minProperties`（`json-schema-subset.mjs:46-112`、`runner_contracts.py:109-157`）。外部实现的 Runner 可能按 schema 生成合法 payload，却在平台收到 422。
- 预判：这是契约准确性问题，不是安全漏洞；后端仍然是最终权威，runner 会先本地校验，正常路径不会踩到。但既然本 issue 的目标就是扩展契约，建议在合并前把“规范产物”和真实校验对齐，而不是让 schema 只做形状提示。
- 结论：

### 6.2 “失败执行保留轨迹”在评分阶段异常时会丢

- 位置：`runner/scripts/real-task.mjs:355-361`、`:369-371`、`:825-845`
- 现象：`realCase` 只在资产失败（`:204-228`）、Agent 非零退出（`:320-337`）、空补丁（`:339-352`）三条路径调用 `collectCapture`。如果 Agent 已成功产出轨迹，但随后 `writeFileSync(testPatchPath)`、`dockerRun(applyTestPatchArgs)`（`git apply` 非零直接抛）或 `parseReport` 抛异常，异常会冒出 `realCase`，`finally` 删除 workdir，外层 catch 只调用 `fail()`，不会上传任何 trace。
- 问题：SWE-bench 的测试补丁在 Agent 改过测试文件或上下文漂移时 `git apply` 失败并不罕见；这属于“执行失败但已产生完整轨迹”的典型场景，恰好违反 issue 验收里的“执行失败时保留已产生文件”。现有测试 `a failed claude run still retains native and diagnostic files` 只测了 `runClaudeCode` 的退出码，没有覆盖 `realCase` 的评分阶段异常。
- 预判：修法不复杂——在 `realCase` 外层加 `catch`，先 `collectCapture(...)` 再返回 failed 结果，或把评分段包在内层 try/catch 里给异常附加 `traceBundle`；同时补一个 fake `realCase`/adapter 测试，让 `applyTestPatchArgs` 抛错并断言仍上传了 native 文件。建议本 PR 修，否则“失败保留”只在两类失败里成立。
- 结论：

### 6.3 “attempt 归属”只绑定了 token，没有绑定对象键

- 位置：`backend/app/services/case_attempts.py:467-498`、`backend/app/api/runners.py:310-313`、issue #90 验收第 1 条
- 现象：平台在 `upload-urls` 生成的键形如 `evaluations/{run}/{shard}/attempt{n}/{case_run_id}/{kind}/{sha256}`，但 `_verify_objects` 只做 `store.verify_object(object_key, expected_size)`，不检查键是否属于当前 run/shard/attempt/case/kind/digest。Runner 只要持有某个 attempt 的 token，就可以在完成回调里引用同桶内任意已存在对象（包括另一个 attempt 的对象），后端会把它合并进当前 attempt 的清单。
- 问题：PR 描述与 `docs/architecture.md:65` 都写了“后端校验 attempt 归属”，但当前只校验了 token 的 attempt 绑定；对象本身没有归属校验。issue 验收要求“每个清单条目都能追溯到当前 attempt”，这一条没有被实现，也没有对应测试（重试测试只验证 attempt 2 初始清单为空，没有验证 attempt 2 不能引用 attempt 1 的键）。
- 预判：有两种修法。A（更贴平台语义）：在对象存储可用时校验 `object_key` 的平台前缀与 `/{kind}/{sha256}` 后缀；这会牵动测试 helper 里缩短的键。B（更小改动）：完成回调中的 trace 对象必须是当前 attempt `uploads` 清单里已登记过的 `object_key+sha256` 子集，天然阻断跨 attempt 引用，且不依赖键格式。建议至少做 B；如果认为 Runner 完全可信，则应把文档里的“attempt 归属”改成“token 归属”，并把它明确划到 #91 的对象校验里。
- 结论：

### 6.4 128 个对象 × 顺序 HEAD，撞上 5 秒回调超时

- 位置：`backend/app/services/case_attempts.py:467-498`、`runner/lib/callback-client.mjs:18`、两份 schema 的 `maxItems: 128`
- 现象：上传回调和完成回调都会对清单里的每个对象顺序执行一次 `verify_object`（HEAD）。Runner 的 `postCallback` 默认 `timeoutMs = 5000`（`callback-client.mjs:18/36`），而 `real-task.mjs` 调 uploads/completed 时没有覆盖这个超时。127 个 trace 对象 + 1 个 score 对象时，两次回调各要做接近 128 次串行 HEAD；单次 HEAD 40ms 就接近 5 秒，跨区域 OSS 或抖动时很容易超时。
- 问题：超时后 Runner 会重试（`retries=4`，指数退避），但服务端可能仍在处理；重试本身有 event_id 幂等兜底，不会写坏状态，却会把一次成功执行拖成多次长请求，并放大数据库事务与对象存储压力。更严重的是，如果服务端在超时后才提交，Runner 可能先看到超时、再发 `failed` 回调，最后靠幂等/409 收敛，诊断体验很差。
- 预判：可以并行化 HEAD（有界并发）、把 trace 对象的逐文件校验推迟到 #91 的异步导入（设计 08 §5 本来就是异步校验 size+sha256）、或至少给 uploads/completed 单独设置更长的 `timeoutMs`。考虑到 #91 会重新校验，建议本 PR 先把“完成回调只同步校验 score”作为降载手段，或明确记录 5 秒预算与 128 上限的乘积风险。
- 结论：

## §9 文件级代码分析

### 9.1 `runner/lib/trace-capture.mjs`（A）

职责：把隔离 HOME 的原生文件与诊断文件变成“安全逻辑路径 + digest + 完整性状态”的可序列化清单。

依赖：只用 Node 内置 `node:crypto`、`node:fs`、`node:path`，没有引入第三方包，符合零依赖约束。

关键块：

```js
// 前身（real-task.mjs 的旧逻辑）：直接读 trace/claude-stream.jsonl 作为唯一 trace
const trace = existsSync(tracePath) ? readFileSync(tracePath) : Buffer.from("");

// 新：先收 stdout/stderr 诊断，再递归收 .claude/projects 的原生会话与 meta
const stdoutPath = join(traceDir, "claude-stream.jsonl");
add(fileEntry({ ..., logicalPath: "diagnostics/stdout.jsonl", artifactKind: "trace_diagnostic" }));
walkFiles(projectsRoot, (sourcePath) => {
  if (!sourcePath.endsWith(".jsonl") && !sourcePath.endsWith(".meta.json")) return;
  const logicalPath = `native/${sanitizeRelative(rawRelative)}`;
  add(fileEntry({ ... }));
});
```

实现思路：逻辑路径只由相对路径与固定前缀组成，`sanitizeComponent` 把不安全字符替换为 `_`，`add` 先到先得；摘要与大小都由实际 bytes 计算，避免清单与上传内容不一致。

检视发现：

- `add` 对重复逻辑路径是静默跳过（`:181-185`）。这既是“stdout 已先加入”的正常去重，也会掩盖 sanitize 碰撞（两个原始路径映射到同一逻辑路径），后者不会产生 `incomplete_reasons`。概率低，但属于可观测性缺口。
- `fileEntry` 用 `readFileSync` 把每个文件完整读入内存，bundle 在采集到上传之间一直持有全部 `bytes`；超长会话/大量子 Agent 会放大 Runner 内存。设计里的“大内容外置”在 #91，但采集侧至少应记录/限制单文件大小，避免 OOM。
- `runtime_version` 在失败早退时可能保留 adapter 的 `"2.x"`（见 9.2），不是具体版本；`format_version` 全部硬编码 `"1"`。对 #91 的 parser 选择来说，这两个字段需要明确的语义。

### 9.2 `runner/scripts/real-task.mjs`（M）

职责：真实用例入口；本次把单文件 trace 改为 bundle，并接入上传/完成契约。

旧代码（`main`）：

```js
const { score, trace } = caseResult;
const traceObject = store.putBytes(Buffer.from(trace, "utf8"), { contentType: "application/x-ndjson" });
const pendingObjects = [
  { artifact_kind: "score", ...scoreObject },
  { artifact_kind: "trace", ...traceObject },
];
```

新代码：

```js
const traceFiles = dedupeTraceObjects(caseBundle.files);
const pendingObjects = [
  { artifact_kind: "score", ...scoreObject },
  ...traceFiles.map((file) => ({
    artifact_kind: file.artifact_kind,
    ...store.putBytes(file.bytes, { contentType: file.content_type }),
    ...uploadFields(file),
  })),
];
```

思路：先按 `(kind,digest)` 去重，再把每个文件写成独立对象；上传成功后把平台键回填到 `reportedObjects`，完成时用 `traceManifestFromBundle` 生成清单。上传 URL 的查找从“按 kind 找第一个”改为“按 kind+digest 精确匹配”，这是多文件场景必须的修复。

检视发现：

- `collectCapture` 的调用点只覆盖资产失败、Agent 退出、空补丁、成功/未解决；评分阶段异常没有兜底（§6.2）。
- `runtimeVersion` 只在 Agent 启动后通过 `claude --version` 探测（`:279-284`）；早退路径保留 `"2.x"`。
- 128 个对象的上限在 `requireValid("upload"/"completion")` 处触发；`contract_invalid` 不在外层 catch 的 `callback_retryable/callback_permanent/upload_failed` 分支里，因此不会发 `failed` 回调，只能等心跳/执行超时（`:825-845`）。这让“对象太多”表现为挂起而不是可诊断失败。
- `postCallback` 没有为 uploads/completed 覆盖 5s 超时（§6.4）。

### 9.3 `backend/app/services/trace_manifest.py`（A）

职责：后端唯一的清单归一化与状态映射模块。

关键块：

```python
if "objects" in raw:
    objects = normalize_trace_objects(raw["objects"])
    status = raw.get("capture_status") or _infer_capture_status(objects)
    if status == "complete" and not any(item["artifact_kind"] == "trace" for item in objects):
        status = "partial"
        reasons = [*reasons, "native_session_missing"]

    # legacy: object_key / sha256 / size
```

思路：多文件形态先校验对象，再用“是否含原生会话”纠正 Runner 的 complete 声明；legacy 形态只保留三字段，保证旧 Runner 可继续工作。

检视发现：

- `"objects" in raw` 决定分支，**不检查两分支是否同时存在**；两者都有时旧字段被静默忽略（§6.1）。
- `manifest_version` 用 `str(...)` 兜底，没有长度/类型/受支持版本校验；schema 只限制 1–16 字符。
- `_infer_capture_status` 把 `trace_metadata` 也算“complete”，但 `normalize_trace_manifest` 会二次纠正；`trace_status_for` 在直接对未归一化 manifest 调用时不会纠正，是一个潜在不一致（当前调用点都先归一化，未触发）。
- `merge_manifest_objects` 只按 `object_key` 合并，不校验同一 key 的 `size` 是否一致，也不按 digest 去重；同一对象重复上报不会重复，但“同 digest 不同 object_key”仍会产生两条清单项。

### 9.4 `backend/app/services/case_attempts.py`（M）

职责：上传/完成回调的业务事务。

关键块：

```python
# uploads
objects = normalize_upload_objects(payload["objects"])
_verify_objects(ctx, objects, now=now)
merged["objects"] = merge_manifest_objects(merged.get("objects"), objects)

# completed
trace_manifest = normalize_trace_manifest(payload["trace_manifest"])
_verify_objects(ctx, trace_objects(trace_manifest), ...)
finalize_completion(..., trace_manifest=trace_manifest, ...)
case_run.trace_status = trace_status_for(manifest_record)
```

思路：把“格式校验”和“对象存在性校验”分开，冲突映射为 409 `manifest_conflict`，格式/路径错误映射为 422 `manifest_invalid`；旧单文件 manifest 也走同一归一化路径。

检视发现：

- `_verify_objects` 只 HEAD + size，不校验对象键归属，也不校验内容 sha256（§6.3、§6.4）。
- 一个缺失的 trace 对象会把整个 attempt 标成 `artifact_missing`、case 标失败（`:481-498`）；这和“缺失子文件应可降级”是不同语义，当前 PR 用“上传失败”处理，合理但需要和 #91 的 partial/degraded 区分。
- `handle_uploads` 并发合并没有行锁；两个并发上传清单可能后写覆盖先写。实际 Runner 单线程发送，风险低，但契约上不是严格幂等。

### 9.5 `backend/app/services/reconciler.py`（M）

职责：完成回调丢失时，从上传清单补全 completion。

旧代码只找 `artifact_kind == "trace"` 的单个对象；新代码收集所有 trace kind，构造多文件 manifest，再走同一个 `finalize_completion`。

检视发现：

- `capture_status` 用“是否存在 `trace` kind”推断 complete；部署边界上的旧 Runner 可能把 stdout 也标成 `trace`，从而被补成 `complete/ready`。窗口很窄，但迁移期值得留意。
- `stored_trace_manifest` 分支在正常流程里基本不可达（completion 成功即 terminal，不会进入 uploading 补全）；保留无实害。
- 补全同样没有内容 sha256 校验，与 §6.3 一致，属于 #91 的异步导入职责。

### 9.6 `backend/migrations/versions/0019_trace_capture_status.py`（A）

职责：扩展 `eval_case_run.trace_status` 的 CHECK 约束。

实现：`batch_alter_table` 删旧约束再建新约束，兼容 SQLite/Postgres；downgrade 先把 `incomplete/degraded` 回填为 `ready`，再恢复旧约束。约束名与模型命名约定 `ck_%(table_name)s_%(constraint_name)s` 一致（`models/base.py:14`），初始迁移也用了同名约束（`1a795994c4e9:187`）。

检视发现：upgrade/downgrade 顺序正确；downgrade 有语义损失（degraded → ready），但这是删除状态值的必然取舍，建议在迁移注释里写明“降级会丢失区分度”。迁移测试只覆盖升级，未覆盖 downgrade；若团队要求可回滚，建议补一条 SQLite 降级再升级的测试。

### 9.7 `runner-contract/schemas/v1/*.schema.json`（M）

职责：Runner 与平台的共享契约。

上传 schema：新增 `logical_path`/`path`、`native_format`、`runtime_version`、`format_version`，对象上限 128；`logical_path` 的 `pattern` 与后端 `SAFE_LOGICAL_PATH` 一致，但**不拒绝 `..` 组件**（正则允许 `.` 和 `-`，`..` 是合法字符组合）。完成 schema：`trace_manifest.objects[]` 要求 `logical_path`，但没有要求 `trace_manifest` 本身必须包含 `objects` 或 `object_key`，也没有禁止两者同时出现。
