## §1 一页速览

一句话：这个 PR 不再把 76 个 span 平铺成一条 0ms 瀑布，而是让前端把“模型调用 — 工具调用 — 工具结果”这串原始流水账整理成 5 个可读阶段，并把每一步按工具类型展开成命令、diff、文件内容或子 Agent。

一个比喻：原来的瀑布像把监控录像的每一帧单独打印出来贴满墙；新页面像一位剪辑师，把素材按“理解任务 → 定位 → 修复 → 验证 → 总结”剪成 5 个章节，章节可折叠，点开某个镜头才看细节。剪辑师只拿得到后台给的“前 500 字场记单”——这正是 §6.1 的问题根源。

## §2 架构导览

### 2.1 分层

```
TracePage.tsx (React 组件、URL 状态、查询)
  └─ buildTraceViewModel(spans, sessions)   ← traceViewModel.ts 纯函数
       ├─ steps[]   一步 = 一个 tool/thinking/message span + 关联 tool_result
       ├─ phases[]  连续的同类步骤归并成阶段
       └─ 派生计数：工具数、错误数、0ms span 数、成本、token
  └─ buildTraceTimeline(model, clockComparable) ← 阶段窗口 → 百分比条
```

页面只做三件事：取数（`spansQuery`）、把模型结果映射成组件、把交互写回 URL。数据口径全部集中在 `traceViewModel.ts`，这是本 PR 最好的结构决策——只要补上单测，归并规则可独立回归。

### 2.2 阶段归并规则（`traceViewModel.ts:1055-1112`）

- 每个步骤先定 `category`：edit/write → `fix`；bash 命中测试/构建正则 → `verify`，否则 `explore`；read/search/skill/subagent/tool → `explore`（`:402-418`、`:198-207`）。
- 思考 / 消息没有 category，先进 `pending`，等下一条有类别的步骤再一起归入下一阶段（`:1057-1063`）。注释里的理由成立：测试前的思考属于验证，不属于上一次编辑。
- 连续同类合并；`explore` 紧跟在 `fix/verify/summary` 之后时并入上一阶段，避免“修复→验证”之间插一条“补充探索”（`:1064-1078`）。
- `explore` 段会在第一个“定位边界”（Read、非 grep 的 search/tool/bash）处一分为二，得到“理解 / 定位”（`:882-893`、`:420-432`）。
- 阶段窗口取组内所有非根 AGENT span 的最早开始/最晚结束（`:838-865`），所以阶段耗时是“墙钟窗口”，不是步骤耗时之和。

### 2.3 步骤构造（`traceViewModel.ts:599-830`）

工具 span 的“输入”只有一个来源：`span.content_preview`（`:351-353`）。`parseToolInput` 要求它以 `{` 开头且能 `JSON.parse`（`:257-269`）。解析成功后才有 `command`、`filePath`、`old_string/new_string`，进而才有 diff 和命令展示；解析失败则回退到原文。

工具结果通过两条索引配对：结果 span 的 `parent_span_id`（解析器写成 `tool:{call_id}`）和 `attributes["gen_ai.tool.call.id"]`（`:948-964`、`:974-980`）。这与后端解析器 `:215-224` 的实际写入一致，配对思路是对的。

### 2.4 时间线（`traceViewModel.ts:1270-1375`）

`clock_comparable=false` 或总时长为 0 时进入“只按顺序”模式：`ordinalOnly=true`，条宽为 0，页面只画一个定位点并显示说明（`:1281-1329`）。可比时按阶段窗口算 `left/width` 百分比，并把阶段之间没被覆盖的时间累加成 `gapMs`（`:1350-1362`）。0ms span 计数单独给页面提示（`:1227-1232`）。

### 2.5 页面状态与深链（`TracePage.tsx:1772-2114`）

- URL 是唯一选中态：`attempt / session / span / kind` 写入 `searchParams`（`:1793-1813`）。
- 首次进入若没有 `span`，自动选“第一个 fix 步骤”，否则第一个带工具名的步骤，否则第一个 span（`:1905-1916`）；关闭详情会置 `dismissedSelection` 防止立刻被重新选中（`:2102-2107`）。
- 页面加载后把 `span` 单独再取一次完整记录（`:1919-1933`），用于 `content_available`、属性等预览里没有的字段。
- 切会话/切 attempt 会重置展开状态与选中（`:2037-2055`、`:1969-1979`）。

### 2.6 响应式

布局是 `230px + 1fr + 372px` 网格（`trace-viewer.css:223-228`）；`≤1280px` 去掉右栏、显示“详情”按钮、抽屉内恢复 `.trace-inspector`（`:2526-2544`）；`≤900px` 三栏改单列并隐藏会话树（`:2580-2630`）。JS 侧的 `useNarrowViewport(1280)` 与 CSS 断点一致（`TracePage.tsx:195-209`）。

## §3 数据流走查（以冒烟轨迹 76 spans 为例）

1. `spansQuery` 拉第 1 页 100 条，`mergeSpanPages` 合并，`markMissingParents` 标根片段（`TracePage.tsx:1863-1898`）。
2. `buildTraceViewModel` 按 `ordinal` 排序（`traceViewModel.ts:943-946`）。
3. 先摘出所有 `tool_result` 并按父 span / call id 建索引（`:948-964`）。
4. 遍历 span：根 AGENT 与 tool_result 跳过；TOOL/子 AGENT → 工具步骤；THINKING → 思考步骤；MESSAGE 里的 user/system 抽成“用户任务”，其余消息成消息步骤（`:972-1019`）。
5. 没有任何子步骤的 LLM span 才单独成为一个“模型调用”步骤（`:1021-1031`）。
6. 定 category、挑最后一条尾部消息为“总结”，其余消息不归阶段（`:1039-1053`）。
7. 连续同类步骤合并成 run，`explore` 在定位边界处再切一刀（`:1055-1112`）。
8. 生成 5 个阶段，回填 `phaseId`、窗口、计数（`:1114-1160`）。
9. 没被任何步骤认领的 span（根 AGENT、LLM 容器、未配对 result）按 ordinal 就近塞进阶段，保证 span 总数不丢（`:1200-1208`）。
10. 页面渲染：概览指纹（`TracePage.tsx:317-398`）→ 阶段导航 / 会话树（`:2360-2406`）→ 中栏三视图（`:2506-2535`）→ 右栏检查器（`:2196-2209`）。
11. 点某一步 → `openStepDetail` → 写 URL → `detailQuery` 拉完整 span → 检查器联动（`:2065-2071`、`:1919-1933`）。
12. 切到时间线 → 用同一份 model 生成阶段窗口与“时间去向”（`:1947-1954`、`:1100-1278`）。
13. 1280 以下 → 选中步骤时开 Drawer（`:2056-2061`、`:2554-2567`）。

## §6 讨论点

### 6.1 工具输入只有前 500 字，大 Edit / 长命令的展开会静默失效

**位置**：`web/src/pages/traceViewModel.ts:351-353`、`:604-654`、`:618-619`；契约源头 `backend/app/services/trace_parsers/claude_code.py:23`（`MAX_PREVIEW = 500`）与 `:207`、`:231`。

**现象**：页面解析工具输入的唯一来源是 `span.content_preview`，而后端对 tool_use 的 `input` 做 `json.dumps` 后按 500 字符截断（截断处补 `…`）。一旦 input JSON 超过 500 字符，`parseToolInput` 必然 `JSON.parse` 失败，于是 `toolInput` 为 null，连锁导致：`command` 为 null（Bash 卡显示“—”）、`filePath` 为 null（Read/Edit 标题退化成工具名）、`diff` 为空（Edit 卡只剩一段被截断的 JSON 原文）。

实测（直接调用仓库解析器的 `_preview`）：用一个 13 行的 `old_string/new_string` 构造 Edit input，JSON 847 字符；返回的 preview 只有 500 字符且以 `…` 结尾，`json.loads` 抛 `JSONDecodeError`。这说明它不是边缘情况：一个几十行的函数替换、一个带 heredoc 的 Bash、一个多行 Write 都会命中。反过来说，冒烟场景 03 既然渲染出了红绿 diff，那条 astropy Edit 的输入 JSON 必然在 500 字符以内——冒烟样本恰好落在“能解析”的一侧。

**问题**：这是本 PR 主卖点（“Edit 展开完整 diff”“Bash 展开命令”）的静默降级路径，而且没有任何提示：`steps` 只检查了 **结果** span 的 `content.truncated`（`:615-617`），从未检查工具 span 自身的 `attributes["content.truncated"]`。更麻烦的是，非管理员无法补救：完整内容只能通过 `POST /api/v1/trace-spans/{id}/content-url` 获取，而该路由要求 `require_admin`（`backend/app/api/traces.py:176-183`），所以普通只读用户永远看不到一条 1KB 的 diff。

**预判**：根因在后端预览上限，超出本 PR 声明的“不改后端”范围，但不该由前端静默吞掉。建议分两层处理：本 PR 内先“诚实降级”——检查工具 span 的 `content.truncated`，在 Edit/Write/Bash 卡上明确写“输入已截断（超过 500 字符），无法展开 diff/命令；完整内容需管理员权限”，并把原文放进可滚动 `<pre>`；同时用宽松提取（从截断 JSON 里正则取 `file_path`/`command` 的前几个键）保住卡片标题，避免整张卡退化成“Edit”。跟进项另开 issue：提高 tool_use 输入的预览上限（或为工具输入/结果单独设上限），并评估只读角色是否应能读取工具输入正文。

**结论**：（留空）

### 6.2 深链 span 不在已加载页/当前筛选内时，不再被并入中栏模型

**位置**：`web/src/pages/TracePage.tsx:1892-1902`、`:1919-1933`、`:1955-1964`；被移除的旧逻辑是 `origin/main:web/src/pages/TracePage.tsx` 的 `mergeSelectedSpan` 用法。

**现象**：`model` 只由 `spans`（分页 + `kind` 筛选后的结果）构建，选中 span 的完整记录虽然单独取回（`detailQuery`），但没有并回 `model`。旧页面用 `mergeSelectedSpan(spans, span, selectedSessionId, filter)` 把深链 span 合进 waterfall。后果：会话超过 100 条 span（`limit: 100`，`:1877`）时，深链指向第 2 页的 span 后，中栏没有该步骤、阶段导航不高亮、概览少算一个 span，只有右栏检查器还能显示原始 span；`?kind=` 深链跨类型时同理。

**问题**：PR 声称“保留 attempt / session / span / kind 深链”。冒烟场景 10 能过，只是因为那条轨迹 76 个 span 全在第 1 页。这是一个真实的回归边界：越是长轨迹（正是本 PR 想解决的场景），越容易踩到。它不会崩，但深链会“只恢复一半”。

**预判**：建议在构建 model 前把 `span` 合回列表（复用现成的 `mergeSelectedSpan`，约 5 行），或单独给 model 传一个 `extraSpans`。补一个“第 2 页 span 深链”的人工验收即可覆盖。

**结论**：（留空）

### 6.3 输出里出现 “N failed” 的验证步骤不算错误，“仅错误”会漏

**位置**：`web/src/pages/traceViewModel.ts:340-349`、`:626-635`、`:751`；消费方 `web/src/pages/TracePage.tsx:2003`、`:2445`。

**现象**：`passedLabel` 会在输出中匹配 `N failed` 并把它作为 `statusText`（例如 “1 failed”），但 `error` 字段只由 `resultHasError`（`is_error` / `error.type` / status）或非零 `exitCode` 决定（`:626`、`:751`）。Bash 的工具输入里通常没有 `exit_code`，工具结果 span 的 status 也为空，所以“输出显示 1 failed”与“该步 error=false”可以同时成立。结果是：卡片状态被 `stepStatusTone` 染成错误色（`:179-183` 的 `/fail|error/` 匹配），但“仅错误 N”计数和 `errorOnly` 过滤不包含它——同一个页面用两套口径回答“哪一步失败了”。

**问题**：这正是轨迹页最需要可信的字段（哪一步失败、有几处失败）。冒烟场景 09 的“1 个错误步骤”只覆盖了带 `is_error` 的情况。建议让 `passedLabel` 返回结构化结果（`{label, failed:number}`），在 `buildToolStep` 里 `failed > 0` 时置 `error = true`；同时把 `statusText` 的 “failed” 判定作为兜底。

**预判**：属于小改动（约 10 行）+ 一个纯函数单测，建议合并前修掉；否则“仅错误”会长期给出偏乐观的数字。

**结论**：（留空）

### 6.4 成本与会话口径取自“筛选后的 span”，加类型筛选后成本变“—”

**位置**：`web/src/pages/TracePage.tsx:2331`（成本）、`:325-327`（“本会话 N 个 span”）、`:1899-1902`（model 由筛选后的 spans 构建）。

**现象**：`model.cost` 是把当前 `spans` 的 `cost` 求和（`traceViewModel.ts:1234-1240`），而成本只写在会话根 AGENT span 上（`claude_code.py:671`）。一旦用户点了 `Tool / LLM / 消息 / 思考` 任一切换，根 AGENT span 不在结果里，成本立刻显示“—”；但同一行的 token 数来自 `trace.stats`（`TracePage.tsx:2189`），仍然是全量。概览的“本会话 N 个 span”同样变成“筛选后的 N”。

**问题**：同一行摘要里，token 是全量、成本是筛选后、span 数是筛选后，口径不一致；用户会以为这条轨迹没有成本。改法很简单：成本优先取 `selectedSession?.cost`（`TraceSession.cost` 就是会话 final cost），概览文案在筛选时改成“当前筛选 N / 共 M 个 span”。另外注意 `model.inputTokens/outputTokens` 是把根 AGENT 与各 LLM span 相加（`:1237-1244`），一旦未来接上 UI 会重复计数，本期未使用。

**预判**：低风险小修；建议和 6.2 一起在合并前处理。

**结论**：（留空）

### 6.5 思考步骤显示的是所属 LLM 调用的用量，读者会误以为是这一步消耗

**位置**：`web/src/pages/traceViewModel.ts:777-779`、`:816`；展示 `web/src/pages/TracePage.tsx:908-919`、`:1309-1315`。

**现象**：THINKING span 本身没有 token/cost，`buildTextStep` 用 `parentLlm` 的值兜底，于是同一个 LLM 调用下的多条思考步骤会各自显示完整的 `input/output tokens` 和模型名；`statusText` 的三元表达式两侧都是“完成”（`:816`），说明这里没做过区分。

**问题**：per-step 展示父级用量，属于“归属错误”而非“重复求和”，不会影响头部总账，但会让读者高估单步成本/上下文。建议只在 `kind === "llm"` 时展示用量，或在思考步骤上标注“所属模型调用用量”；顺手删掉 `:816` 的死三元。

**预判**：观感与口径问题，不阻塞；可以放到后续清理 PR。

**结论**：（留空）

### 6.6 子 Agent 嵌套步骤只取 100 个 span / 只显示 40 步，且没有截断提示

**位置**：`web/src/pages/TracePage.tsx:690-701`。

**现象**：`SubagentNested` 用 `fetchTraceSessionSpans(session.id, { limit: 100 })` 取一页，`nested.slice(0, 40)` 后直接渲染；不翻页、不提示“还有更多”。子会话有 300 个 span 时，页面看起来像“子 Agent 只有 40 步”。

**问题**：与 §6.1 同类的“静默截断”，但这里连 `content.truncated` 这种后端标记都没有。至少应在 `nested.length === 40` 或 `session.span_count > 100` 时显示“仅展示前 N 步，打开子会话查看全部”。冒烟报告也明确写了“Skill/Subagent 需要带子会话的 fixture 才能真实验证”，说明该路径证据最弱。

**预判**：不阻塞（本轨迹无子会话），但属于必须补的诚实性提示；建议本 PR 补一行提示，翻页功能另开 issue。

**结论**：（留空）

### 9.1 `web/src/pages/traceViewModel.ts`（A，1411 行）

**职责**：纯展示模型。输入 span 列表 + 会话树，输出步骤、阶段、时间线、计数；不碰 React、不发请求。

**变更代码块**：新增文件，无旧代码对照。核心块：
