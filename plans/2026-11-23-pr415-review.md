## §1 一页速览

一句话：让评测列表能看出“这条记录是从哪个模板一键启动的”，并允许直接点模板名跳回模板详情，而不是只看到运行 ID。

比喻：原来的评测列表像快递柜的取件码，只知道有一个包裹；模板启动的记录现在多贴了一张寄件人标签，标签上的名字还能点回寄件人的主页。自定义发起的包裹本来就没有寄件模板，所以不贴这张标签。

| 交付块 | 内容 | 验证 |
|---|---|---|
| 列表来源行 | 模板启动的行显示「来自模板 · 模板名」；自定义行不显示 | 冒烟 4/4 有来源、2/2 无来源 |
| 模板跳转 | 模板名进入 `/evals/templates/<id>` | Chrome 交互断言 |
| 评测跳转 | 行内其他区域进入 `/evals/<id>`；操作按钮/模板链接不误触 | Chrome 交互断言 |
| 长名截断 | `max-width: 220px`、省略号、完整 `title` | `clientWidth 220 < scrollWidth 309`，`title` 完整 |
| 详情来源 | 模板启动显示横幅，自定义不显示 | 详情截图 + 断言 |
| 接口命名 | 列表摘要 `template` 与详情同构：`id/name/version/enabled` | 后端测试 + 实际响应 |
| 原型一致 | 标签配色、图标、层级、截断与原型一致 | 1500×1100 @2x 并排截图 |

## §2 架构导览

### 2.1 来源模板从哪里来

`GET /api/v1/evaluations` 原本已经从 run 行返回 `template_id` 与 `template_version`（`backend/app/services/evaluations.py:914-916`），但没有可读名称。本 PR 在列表接口里先把当前页所有 run 的 `template_id` 收集起来，用一次批量查询换成 brief，再附加到每条摘要：`backend/app/api/evaluations.py:539-556`。`template_briefs` 的租户过滤与原有 `template_brief` 完全相同，只是把 `id ==` 换成 `in_`：`backend/app/services/eval_templates.py:816-843`。

### 2.2 为什么不在前端逐行取模板

列表默认 10 行，逐行调用 `/api/v1/eval-templates/{id}` 会产生最多 10 个额外请求，而且还要处理请求竞态、缓存和部分失败；批量查询把成本固定为每页一次，响应里直接带名称。该字段与详情页已有的 `template` 同构，前端只需要一个解析函数。

### 2.3 详情页复用同一语义

详情页的横幅一直由 `evaluation_detail` 按 `run.template_id` 解析（`backend/app/services/evaluations.py:1093-1103`），并不依赖 `?fromTemplate=`。本 PR 把 `template_brief` 改为复用 `template_briefs`，所以详情与列表对“可解析到的模板”采用同一套租户与存在性规则；模板被删除时两处都回落到不显示，run 里的 `template_id` 与 `template_snapshot_json` 仍保留（`backend/app/models/evaluation.py:151-156`）。

### 2.4 行点击的边界

`EvalsPage` 的 `onRow` 在点击非交互元素时进入评测详情（`web/src/pages/EvalsPage.tsx:465-473`）。模板名是 `<button>`、操作列是 Ant Design 按钮，二者都会命中 `closest("button, a")` 提前返回，因此不会出现“点模板名先跳模板、又被行点击覆盖”的双跳转。这个行为来自原型整行可点击的交互，也与验收项“点击行内其他区域仍进入评测详情”一致。

## §3 数据流走查

1. 浏览器请求 `GET /api/v1/evaluations?limit=10&offset=0`。
2. 服务端先按过滤条件取 run 页，再取用例聚合 `totals`。
3. `template_briefs` 用 `template_id IN (...)` 一次查出仍存在的模板，构造 `{id: brief}`。
4. 每条 `evaluation_summary` 生成后附加 `template`（自定义或模板已删除时为 `null`）。
5. 前端 `parseEvaluationSummary` 解析 `template`（`web/src/api/evaluations.ts:798-812`）。
6. `EvalsPage` 的任务列在名称与运行 ID 下渲染 `EvalTemplateOrigin`（`web/src/pages/EvalsPage.tsx:177-185`）。
7. 点击模板名：`EvalTemplateOrigin` 调 `onOpen(id)` → `navigate('/evals/templates/<id>')`；点击行其他区域 → 行点击 → `navigate('/evals/<id>')`。
8. 详情页继续按 run 记录解析来源并显示横幅（`web/src/pages/EvalDetailPage.tsx:943-953`）。

## §6 讨论点

### D1 列表显示模板的“当前名称”，不是启动时的快照名称 → 接受

- 位置：`backend/app/services/eval_templates.py:816-843`；`backend/app/models/evaluation.py:151-156`
- 现象：`eval_run` 同时保存 `template_id`、`template_version` 与 `template_snapshot_json`；列表读取的是 `eval_template` 当前行的 `name`。
- 问题：模板改名后，历史运行在列表里显示新名称；如果模板被删除，来源行整条消失，尽管 run 的快照里仍有旧名称。
- 预判：验收要求“模板名是链接，点击进入对应模板详情”，所以名称必须指向可访问的当前模板；原型 `evalSourceTemplate(run)` 也是从当前模板列表解析，删除后不显示。issue 的“运行记录保留启动快照”约束的是数据不被改写，不是列表必须回放快照名称。详情页早于本 PR 就是同一规则。
- 结论：接受；需要看历史快照名称时走运行详情/库内的 `template_snapshot_json`，不在列表增加第三套名称来源。

### D2 行点击是新加交互，issue 的“方案”段只写了列表来源 → 接受

- 位置：`web/src/pages/EvalsPage.tsx:465-473`
- 现象：生产列表原先只有操作列“详情”按钮可进入详情；本 PR 让整行可点击。
- 问题：这是列表交互面的扩大，可能带来误触或选中文本时跳转。
- 预判：issue 验收明确写“点击行内其他区域仍进入评测详情”，原型整行可点击；若不实现，验收项不成立。实现用 `closest("button, a")` 保住既有操作按钮与模板链接，范围仍限于列表行。
- 结论：接受；交互与原型一致，操作按钮行为不变。

### D3 `template` 只出现在列表摘要和详情，创建/状态响应没有 → 接受

- 位置：`backend/app/api/evaluations.py:556`；`backend/app/services/evaluations.py:899`
- 现象：`evaluation_summary` 本身不接收 `template`，列表在生成摘要后附加字段；`POST /api/v1/evaluations` 等响应没有该键。
- 问题：同一个“摘要”形状在不同端点不完全一致，严格消费者可能意外。
- 预判：前端类型把 `template` 标为可选，旧响应已兼容；创建的是自定义 run，本来就不存在来源模板。把字段推进 `evaluation_summary` 会让所有创建/状态响应多一个恒为 `null` 的键，属于与 #410 无关的接口面扩大。设计文档已限定为“评测列表的摘要”。
- 结论：接受；保持列表/详情按需返回，后续若统一摘要契约再单独处理。

### D4 没有前端组件测试，靠冒烟兜底 → 接受（既有基础设施限制）

- 位置：`web/src/components/TemplateBits.tsx`、`web/src/pages/EvalsPage.tsx`
- 现象：仓库 web 侧只有 `tsc` + Vite build，没有组件测试运行器；本次验证依赖 typecheck/build 与 Chrome 冒烟。
- 问题：未来改动来源行或行点击时缺少快速单测回归。
- 预判：引入 Vitest/Testing Library 是新依赖和 CI 门禁变更，超出 #410 的列表展示范围；现有测试策略在本仓库其它 UI PR 同样使用冒烟兜底。
- 结论：接受；冒烟覆盖来源行、两种跳转、截断、详情横幅与自定义详情。

### D5 `template_briefs` 加载整行 ORM，而不是只选四列 → 无实害，接受

- 位置：`backend/app/services/eval_templates.py:828-834`
- 现象：`select(EvalTemplate)` 会带出自进化密文字段等列，最终只输出 `id/name/version/enabled`。
- 问题：多取了几列，理论上增大查询与对象构造成本。
- 预判：每页最多 10 个模板 ID，`eval_template` 行含少量 JSONB 与一个可空密文字段；本次是读路径，密文不出现在响应。改成列选择器会牺牲与 `template_brief` 共用同一构造逻辑的简洁性。
- 结论：接受；若模板表将来变宽，再改为显式列选择。

### D6 10px 弱化色链接的可读性 → 接受（沿用既有表格层级）

- 位置：`web/src/styles/overview.css:419-435`
- 现象：模板名 10px、`--muted` 灰色，与 `table-secondary` 同级；悬停变主色并下划线。
- 问题：小字号 + 低对比度对可读性/无障碍不理想。
- 预判：这是既有的表格次级信息样式，也是原型定义的信息层级；把模板名提成主字号会与运行 ID 争夺视觉层级，超出本 issue。
- 结论：接受；如后续整体做表格无障碍，再统一调整次级文字对比度。

## §9 文件级代码分析

### 9.1 `backend/app/services/eval_templates.py`

职责：评测模板的保存、列表、启动、历史与 brief 视图。

关键依赖：SQLAlchemy 2.x `select` / `Session.scalars`；没有新增第三方包。

变更代码块分析：

- 旧：`template_brief` 单个查询 `EvalTemplate.id == template_id`，返回四字段 dict。
- 新：`template_briefs` 把一组 id 去重后 `IN` 查询并构造 `{id: brief}`；`template_brief` 变成一次单元素调用（`:816-849`）。空集合直接返回 `{}`，不发查询。
- 实现思路：把“可见模板 brief”的租户过滤与字段形状收在一处，详情与列表共用。

检视发现：D5 是唯一的性能取舍；无正确性缺陷。

### 9.2 `backend/app/api/evaluations.py`

职责：评测列表/详情/事件等读接口；列表侧负责过滤、分页、统计与摘要组装。

变更代码块分析：

- 旧：遍历 `rows` 直接 `items.append(evaluation_summary(...))`。
- 新：先批量取 `templates`，循环内把 `summary` 存到变量、附加 `template` 后再 append（`:539-558`）。如果 `template_id` 为空或模板已不可见，值为 `null`。
- 实现思路：只增加一次批量查询，不改变过滤、统计、分页和排序。

检视发现：无；字段为新增，旧客户端可忽略。

### 9.3 `web/src/api/evaluations.ts`

职责：评测 API 类型与响应解析。

变更代码块分析：

- 旧：`EvaluationDetail` 自己声明内联的 `template` 形状，`parseEvaluationDetail` 单独解析。
- 新：`EvaluationSummary` 增加可选的 `EvaluationTemplateBrief`；`parseTemplateBrief` 供摘要与详情共用（`:79-88`、`:798-812`）。详情解析删除重复块，仍从同一 payload 字段读取。
- 实现思路：把来源模板定义为摘要级可选字段，列表与详情各自消费。

检视发现：D3 的接口面取舍；解析行为不变，缺少字段时回落 `null`。

### 9.4 `web/src/components/TemplateBits.tsx`

职责：模板相关的小型展示组件与文案映射。

变更代码块分析：

- 实现思路：把来源行做成纯展示组件，列表页负责路由；与原型 `evalTemplateOriginLine` 的 DOM 结构/文案一一对应。

检视发现：D6 的视觉层级；无逻辑缺陷。

检视发现：D2 的交互边界；已用冒烟验证模板链接、操作按钮不误触。
