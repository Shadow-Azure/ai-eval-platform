## §1 一页速览

一句话：**把“数据集里写什么镜像”改成“平台按用例解析镜像，并先问公开仓库有没有，全部没有就不让建版本”。**

比喻：数据集像菜谱，镜像是后厨。以前平台把“某家后厨的地址”直接写进菜谱，后厨搬走/换锁就做不了菜；现在菜谱仍只写菜，平台按菜名找到对应的标准后厨，并依次问几家公开后厨“这道菜你们能做吗”，都做不了就不收这份订单。

| 交付块 | 内容 |
|---|---|
| 数据模型 | `dataset_case.environment_image`（nullable），版本级字段保留为单镜像回退 |
| 解析 | `swebench/sweb.eval.{arch}.{org}_1776_{repo}-{issue}:latest`，支持 raw `docker_image`/`image_name` 覆盖 |
| 探测 | 有序 `DATASET_IMAGE_REGISTRIES`；Docker Hub token、v2 manifest、404/401/429/timeout 分类 |
| 阻断 | 上传 worker、legacy 导入、commit 三处；错误码 `dataset_image_unavailable` |
| 前端 | Step 2 逐源/逐用例结果、阻断提示、按钮禁用、只读源配置弹窗 |
| Runner | `task_json.environment_image` → case task → `docker create` |

## §2 架构导览

### 2.1 解析层：数据集适配器不再假设“一个版本一个镜像”

`backend/app/services/dataset_images.py:106-149` 是纯函数层：`parse_instance_id` 把 `astropy__astropy-12907` 拆成 org/repo/issue，`image_for_case` 先看 raw 里的显式镜像，再对 SWE-bench 套模板。它不查网络、不读数据库，因此可以单独测试，也不把 registry 细节泄漏进 adapter。

`backend/app/services/datasets.py:420` 在写 `DatasetCase` 时固化镜像；`backend/app/services/evaluations.py:254` 在创建 eval 时把镜像冻结进 `task_json`。这样评测执行不再依赖“当时的 dataset_version 字段”，也不会被后续数据变更影响。

### 2.2 探测层：一个可注入 HTTP client 的小型 registry 客户端

`dataset_images.py:243-343` 用 Docker Registry v2 的 `/v2/<repo>/manifests/<ref>` 判断镜像是否存在；Docker Hub 先取匿名 token（`:216-235`），其他源直接请求；401/404/429/超时分别落状态。`probe_image`（`:320`）按源顺序短路，`probe_case_images`（`:345`）对唯一镜像并发探测并聚合报告。

关键取舍：**只探 manifest，不拉 blob**。因此探测成本是“HTTP 头级”，不会因为 500 个 SWE-bench 镜像把 worker 磁盘打满；代价是“源说存在”不等于“Runner 一定能拉完”，这是本 PR 明确接受的边界。

### 2.3 阻断层：三处闸门，避免半成品

1. 上传 worker：`dataset_imports.py:477` 把探测结果写进 `validation_report_json.image_check`；字段校验通过但镜像 blocked 时仍保持 `validated`，让用户在 Step 2 看到原因。
2. commit：`dataset_imports.py:883-885` 再次拒绝 `image_check.status=blocked`，防止校验后源状态变化。
3. legacy JSON 导入：`datasets.py:548-553` 在 materialize 前探测，blocked 抛 `DatasetImageUnavailable`；API 返回 422 `dataset_image_unavailable`。

### 2.4 展示层：把“能不能建”变成可解释的逐源结果

`web/src/pages/DatasetImportPage.tsx` 在 Step 2 的 review 区插入镜像检查卡：源顺序、每源状态、前 3 个用例、可用计数、阻断 Alert；`imageBlocked` 同时禁用“生成版本”。`web/src/api/datasets.ts:544-579` 增加 `ImageCheckReport` 类型。前端不自行推断镜像，全部读后端 `image_check`。

## §3 数据流走查

场景：用户上传 6 条 SWE-bench JSONL。

1. `POST /api/v1/dataset-imports/uploads` 暂存文件，返回 queued import；前端进入 Step 2 并轮询。
2. 隔离 worker 调 `validate_source_file`（`dataset_imports.py:124`）：逐条 `normalize_case`，对合法记录调 `image_for_case`，得到 6 个 `swebench/sweb.eval...` 镜像。
3. `validate_uploaded_import` 调 `probe_case_images`（`:477`）：对唯一镜像按 `DATASET_IMAGE_REGISTRIES` 顺序探测；本例配置的 `invalid.example` 返回连接错误，6 个用例全部 blocked。
4. 报告写入 `validation_report_json.image_check`，状态保持 `validated`；前端轮询到报告后展示“未找到 / 生成版本已阻断”，按钮 disabled。
5. 若源可用，用户点“生成版本” → `begin_commit` 检查 `image_check`（`:883`）→ `materialize_dataset_version` 逐 case 写 `environment_image`（`datasets.py:420`）。
6. 发起评测 → `evaluations.py:254` 把镜像写进 `task_json`；`runners.py:983` 下发 case task；`runner/lib/task-payload.mjs:16` 优先 case 镜像；`real-task.mjs` 用该镜像 `docker create`。

## §6 讨论点

### 6.1 探测“存在”不等于“Runner 拉得动”

- **位置**：`dataset_images.py:243`（manifest 探测）/ `real-task.mjs` 的 `docker create`。
- **现象**：只检查 manifest 200，不验证 blob 下载、磁盘、网络或认证在 Runner 侧是否成立。
- **问题**：源 A 的 manifest 可见，但 Runner 网络到源 A 不通，仍会在评测时失败；这是“部分解决”的边界。
- **预判**：这是有意的成本取舍。manifest 探测能挡住 404/仓库名错/未推送，已经覆盖这次事故的主因；完整拉取校验会把数据集创建变成“下载数 GB”，不适合同步请求。后续可在 Runner 侧加 `image_pull` 预检或失败快速回调。
- **结论**：（待人类拍板）

### 6.2 默认源是 Docker Hub，国内网络可能直接 blocked

- **位置**：`backend/app/config.py:104`（`docker.io` 默认）。
- **现象**：生产 Runner/worker 若无法访问 Docker Hub，所有新 SWE-bench 导入都会被阻断，直到配置国内加速/GHCR/ACR 公开仓库。
- **问题**：这是“安全默认”还是“上线即阻断”？
- **预判**：默认严格比静默放行好；但需要在部署 `.env` 同步配置 `DATASET_IMAGE_REGISTRIES`（例如 Docker Hub + DaoCloud/阿里云加速 + GHCR），否则上线后导入会被门禁挡住。建议在部署文档/PR 描述里写一条配置项。
- **结论**：（待人类拍板）

### 6.3 每个 case 探测一次，500 条会慢

- **位置**：`dataset_images.py:345`（并发探测）。
- **现象**：500 个唯一镜像 × 最多 4 个源；并发 8，单源超时 8s。最坏情况可能数分钟。
- **问题**：上传校验 worker 的 30 分钟超时是否足够？用户是否愿意等？
- **预判**：manifest 请求通常几十毫秒，命中第一个源就短路；最坏情况是源不可达，8s×批次数。并发 8、500 条约 60 批，理论 8 分钟内；可接受但偏慢。可后续加“源级熔断”：某源连续超时后本次跳过，或把探测放到独立轻量任务。
- **结论**：（待人类拍板）

### 6.4 前端“重新检测”没有实现

- **位置**：`DatasetImportPage.tsx` Step 2。
- **现象**：原型有“重新检测”，实际只有“重新上传”；源状态变化后要重传文件。
- **问题**：是否需要在同一 import 上重跑 image_check？
- **预判**：当前阻断后用户通常去修源配置，再重传是合理的；但“只改源、不想重传”的场景会多一步。可后续加 `POST /dataset-imports/{id}/image-check`（只重跑探测、不重读文件）。
- **结论**：（待人类拍板）

## §9 文件级代码分析

### 9.1 `backend/app/services/dataset_images.py`（A）

职责：把“数据集 case”翻译成“镜像名”，再按源顺序探测。依赖 `httpx`（运行时 HTTP 客户端，不是前端包），只读网络、不写库。

关键变更块：
- `image_for_case`：显式镜像优先，SWE-bench 模板兜底。这样衍生数据集仍可覆盖，官方 SWE-bench 不需要新增字段。
- `probe_source`：Docker Hub token + v2 manifest；把 401/404/429/timeout 分开，避免把“认证失败”误报成“不存在”。
- `probe_case_images`：唯一镜像并发、源级短路、报告截断 200 条。截断是防止 500 条 × 4 源结果把 `validation_report_json` 撑大。

已知弱点：只验 manifest；HTTP-only 源不支持（生产公开源均 HTTPS；本地测试用 `httpx.MockTransport`）。

### 9.2 `backend/app/services/dataset_imports.py`（M）

职责：上传导入的隔离 worker。新增 `ValidationResult.images`，在字段校验循环里顺带收集镜像；校验后探测；报告写入 `image_check`；commit 检查 blocked。

关键变更块：
- `validate_source_file` 增加 `settings` 参数与 `case_images`；只对“字段校验通过”的 case 收集镜像，避免坏记录污染探测。
- `validate_uploaded_import` 的 blocked 不把状态改成 failed，而是保留 validated + 报告；这样 Step 2 能解释原因，commit 再拒绝。
- `begin_commit` 先检查 status，再检查 image_check；顺序修复过一次误把逻辑放进 `cancel_import` 的问题（见 §7）。

已知弱点：worker 内探测受 `dataset_import_timeout_seconds` 约束；源不可达时最坏情况接近超时。

### 9.3 `backend/app/services/datasets.py`（M）

职责：版本物化与 legacy 导入。`materialize_dataset_version` 逐 case 写 `environment_image`；`import_dataset_version` 在写库前探测。

关键变更块：
- per-case 镜像来自 `image_for_case(adapter_key, normalized.case_key, raw, arch)`；版本级 `environment_image` 仍是参数，保留给单镜像数据集。
- legacy 导入的探测在 `materialize_dataset_version` 之前；blocked 抛异常，不产生 import 记录/版本。

已知弱点：legacy JSON 导入是同步接口，500 条探测可能拉长请求；生产 UI 走上传 worker，legacy 主要给脚本/API。

### 9.4 `web/src/pages/DatasetImportPage.tsx`（M）

职责：导入向导。新增镜像检查卡与按钮禁用。

关键变更块：
- `imageCheck = report.image_check`；`imageBlocked` 同时控制 Tag、Alert、commit disabled。
- 只展示前 3 个 unavailable/case；500 条不会把页面撑爆。
- 源状态只读弹窗；配置仍由后端 `DATASET_IMAGE_REGISTRIES` 管理（与 issue 的“配置多个源”一致，未做前端编辑）。

已知弱点：无“重新检测”；skipped 状态仍允许提交（仅当检查被显式关闭/无镜像时）。
