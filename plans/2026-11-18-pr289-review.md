## §1 一页速览

一句话：**长评测里先跑完的 bad case 不再等“整车装满”，结果一不可变就单独发车，run 结束时仍保留整车兜底。**

比喻：原来的上报像“等所有乘客到齐才发一班车”，跑几个小时的评测里，先到的乘客只能在站里干等。现在 worker 每轮看一眼：这位乘客的目的地已经确定、行李（trace）也已到站，就先送走；总站发车时只补送漏掉的人。

| 交付块 | 内容 |
|---|---|
| 提前入队 | `enqueue_settled_case_reports` 在 worker 每轮 trace 发布后扫描已结算用例 |
| 最终性 | `succeeded + 非 resolved` 直接入队；`failed/timeout` 要求 `latest_attempt_no >= run.max_attempts` |
| trace 门禁 | 只接受 `ready/incomplete/degraded/failed`，且最终 attempt 仍有可解析轨迹对象 |
| 重试一致性 | 新 attempt 创建时 `trace_status=pending`，避免旧 badge 被误判为 settled |
| 幂等 | 复用 `(tenant_id, bad_case_id)` 唯一键；插入在 savepoint 内，冲突即放弃 |
| 兜底 | run 终态批量入队保持不动；取消/取消中不新增 |

验证基线：`pytest -q` 全量通过；`ruff check` 改动文件通过；`npm test`、`verify:flow`、`lint:docs`、`verify:docs` 通过。

## §2 架构导览

### 2.1 候选筛选：只碰“结果不可再变”的用例

`services/self_evolution.py:421-445`。SQL 一次筛出 run + case 组合：

- run 必须启用上报且不在 `completed/partial/failed/cancelling/cancelled`，把终态批量入队与取消规则留在原处；
- case 的 `execution_status` 属于 `succeeded/failed/timeout`，`result_status != resolved`，且 `latest_attempt_no > 0`；
- 最终性用 `or_(execution_status == "succeeded", latest_attempt_no >= max_attempts)`：成功用例本来就不能被 workbench 重试；失败/超时用例的自动和手工重试都共用 `max_attempts` 预算，耗尽才冻结；
- `trace_status` 只接受终态，`pending` 留到下一轮；已有 `self_evolution_report.eval_case_run_id` 行的直接排除；
- 排序与 `LIMIT` 让每轮最多处理一个 batch，避免长 run 一次扫描全部历史。

### 2.2 trace 门禁：没有轨迹就不提前占配额

`services/self_evolution.py:446-475`。候选人拿到后还要看最终 attempt 的 `artifact_manifest_json` 里是否仍有可解析对象；这是 #272 的规则。若 badge 是旧 attempt 留下的终态而最终 attempt 没有轨迹，调用 `set_case_trace_status(..., "unlinked")` 修正，下一次不会再被同一行反复命中。

这里刻意只修正“提前入队”路径：run 终态的批量入队本次不动，避免把 #272 的完整改动混进 #288，也保证现有终态测试与生产行为不变。代价见 §6.2。

### 2.3 冻结与幂等：payload 一次定型，冲突交给唯一键

`services/self_evolution.py:476-508`。载荷仍由 `build_bad_case_payload` 生成，`badCaseId` 算法不变；插入包在 `session.begin_nested()` 内，唯一键冲突（终态批量入队或另一个 worker 抢先）只回滚这条 savepoint，不打断整轮扫描。每轮结束统一 commit，事件沿用 `eval.self_evolution.enqueued`。

### 2.4 重试一致性：新 attempt 从“未解析”开始

`services/case_attempts.py:881-887`。`build_retry_dispatch` 是自动失败重试、spot 重试和手工重试的共同入口；在这里把 `trace_status` 置为 pending，等于给每个新 attempt 重新挂上“轨迹未就绪”的状态。没有这一步，失败重试未上传新轨迹时会沿用旧 attempt 的 `ready`，被提前入队误判为可上报。

### 2.5 Worker 顺序：先看 trace，再决定发不发

`worker/main.py:225-233`。新 pass 放在 `publish_stale_cases` 之后、`capacity_once` 与 `process_pending_self_evolution_reports` 之前：trace 本轮的终态已经落库，入队后的 pending 行还能在同一轮被 POST，延迟约为一个 worker tick。

## §3 数据流走查

场景：一个 3 用例的长评测，`case-a` 先以 `succeeded + unresolved` 完成，`case-b/c` 还在跑。

1. `case-a` 完成回调写 `execution_status=succeeded`、`result_status=unresolved`，`finalize_completion` 把 `trace_status` 置为 pending 并入队 trace 解析。
2. worker 本轮 `trace_ingestion.ingest_pending` 解析成功，`publish_stale_cases` 把 case badge 发布为 ready。
3. 同一轮新 pass 查到 `case-a`：run 仍 running、非 resolved、`latest_attempt_no > 0`、trace ready、最终 attempt 有 trace 对象。
4. `build_bad_case_payload` 冻结 `BadCaseIngest`，插入 pending 行；run 级事件只记首个 count。
5. 同一轮 `process_pending_self_evolution_reports` 解密令牌并 POST，HE 返回 201，行状态置 succeeded。
6. 之后 `case-b/c` 结束，run 终态批量入队时按 `bad_case_id` 看到 `case-a` 已有行，跳过；只补 `case-b/c` 或 trace 仍 pending 的漏网用例。

## §6 讨论点

### 6.1 `eval.self_evolution.enqueued` 事件只保留首个 count

- **位置**：`services/self_evolution.py:496-503`。
- **现象**：`append_run_event` 按 `(run, event_type)` 去重，提前入队先写一条 count；run 终态兜底再入队时不会写第二条。
- **问题**：长 run 中事件里的 count 只是第一个 batch，不能代表整个 run 的总入队数。
- **预判**：issue #288 已明确接受该限制，逐用例审计留给后续 case 级事件；worker 日志的 `enqueued=N` 仍可看每轮增量。
- **结论**：按方案接受，不阻塞本 PR。

### 6.2 #272 的终态规则仍未统一

- **位置**：`services/self_evolution.py:308`（终态批量入队）。
- **现象**：提前入队跳过无轨迹用例，但 run 终态批量入队仍按 #263 规则上报无轨迹用例。
- **问题**：同一个无轨迹用例在 run 结束前后行为不一致；最终“无轨迹不上报”要等 #272 落地。
- **预判**：本 PR 只承载 #288 的提前路径；#272 是独立 issue，若在本 PR 一并收紧会改变既有终态测试与生产行为，超出本 issue 的方案边界。
- **结论**：保持现状，PR 描述已写明该限制。

## §9 文件级代码分析

### `backend/app/services/self_evolution.py`

职责：在既有“终态冻结 + worker 上报”之外，增加“结果不可变即冻结”的逐用例入口。关键依赖仍是 SQLAlchemy 的唯一约束与 savepoint，没有新增表、迁移或外部依赖。

旧路径：`enqueue_self_evolution_reports` 只在 `refresh_run_progress` 的终态事务内按 run 扫描全部 case。新路径：`enqueue_settled_case_reports` 由 worker 每轮调用，按 run + case 维度筛选，冻结逻辑复用 `build_bad_case_payload`。

实现思路：SQL 先做便宜且确定的过滤（run 状态、case 终态、trace 终态、无既有行），再在 Python 里做需要 manifest 的 trace 对象校验；插入冲突靠数据库唯一键而不是应用层“查重后插入”。这样与终态批量入队并发时，只有一条能成功。

### `backend/app/services/case_attempts.py`

职责：分片派发与重试 attempt 的唯一创建入口。变更只有一行状态重置，但覆盖自动失败、spot 中断和手工重试三条路径。

旧行为：新 attempt 的 `latest_attempt_no` 前进，`trace_status` 保留旧值；失败重试没有新轨迹时会继续显示旧 attempt 的 ready。新行为：新 attempt 一创建就 pending，等新 trace 发布后再升级。与 `workbench._create_retry_attempt` 原有的手工重试重置逻辑对齐，重复设置是幂等的。

### `backend/app/worker/main.py`

职责：单进程轮询循环。新 pass 放在 trace 发布之后、上报之前，保证“本轮解析出的终态”能在本轮变成 outbox 行并立刻 POST；异常只打印日志，不影响其他 pass。

### `tests/backend/test_self_evolution_report.py`

新增 5 例，覆盖 issue 验收中的关键分支：提前入队 + 同轮 POST、trace pending 等待、resolved/cancelled/cancelling/无轨迹过滤、失败重试耗尽前后、重复调用幂等。测试用 `_register_trace_manifest` 显式模拟 completion 上传轨迹，避免只靠 `TraceFile` 行让 `has_ingestible_trace_objects` 误判。
