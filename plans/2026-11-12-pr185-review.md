## §1 一页速览

**一句话**：把评测任务列表从“35 条平铺一页”改成“服务端每页 10 条”，总数与页码由服务端 `total` 决定，筛选后回到第 1 页，3 秒自动刷新仍停在当前页。

**比喻**：像把一张 35 米长的账单折成每页 10 行的账本；页码由柜台（服务端）的账单总数决定。换筛选条件等于换了一本账本，必须翻回第一页；但时钟每 3 秒响一次（自动刷新）时，不会替你翻页。

| 交付块 | 内容 |
|---|---|
| 分页 | `limit=10&offset=(page-1)*10`；分页器展示服务端总数，末页不足 10 条正常展示 |
| 筛选 | 搜索、状态、数据集变化后 `page=1`；总数缩小时收敛到最后一页 |
| 刷新 | 保持 3 秒 `refetchInterval`；query key 含页码，只刷新当前页 |
| 兼容 | 列、状态标签、统计卡、筛选栏、详情/取消操作不变 |
| 流程 | m8-03 issue、m8 milestone、roadmap 与预算登记 |

验证基线：`web` typecheck/build ✅；`npm test` 87/87 ✅；`lint:docs` / `verify:docs` ✅；`verify-flow` / `verify-flow --diff origin/main` ✅；本地 35 条数据集成冒烟 30/30 ✅。CI 状态见 PR 检查页。

## §2 架构导览

### 2.1 服务端列表契约

`backend/app/api/evaluations.py:417` 的 `GET /api/v1/evaluations` 接受 `limit`（1–200）与 `offset`，返回 `{status, total, items, stats}`。`backend/app/services/evaluations.py:602` 在 SQL 层做筛选、稳定排序与 `count`，`total` 是筛选后的全量条数，不是当前页条数。

统计卡不随分页窗口变化：`backend/app/services/evaluations.py:665` 的 `evaluation_list_stats` 单独按筛选条件聚合，因此翻页时“全部任务 / 运行中 / 平均解决率 / 平均耗时”仍是全量口径。这一点是本 PR 敢把列表窗口缩到 10 条的前提。

### 2.2 前端查询层

`web/src/api/evaluations.ts:732` 的 `fetchEvaluations` 默认 `limit=50`，并只在 `offset` 非 0 时写入查询串。本 PR 显式传入 `limit=10` 与 `offset=(page-1)*10`，没有改后端契约，也没有改筛选参数语义。

页面用 TanStack Query 的 `keepPreviousData`：翻页时先保留上一页数据，等新页返回再替换，避免表格瞬间塌成空态。query key 在 `web/src/pages/EvalsPage.tsx:26` 增加页码，筛选条件仍在 key 里，所以筛选或页码变化都会自然触发新请求，旧请求由 React Query 取消。

### 2.3 页面状态机

`web/src/pages/EvalsPage.tsx:104-105` 维护 `page` 与 `trimmedSearch`；`107-113` 的防抖只在“trim 后搜索词实际变化”时写入 `debouncedSearch` 并把页码重置为 1；`115-137` 发起查询；`139-144` 在总数缩小时把页码收敛到最后一页；`414-420` 把 `page`、`PAGE_SIZE`、`total` 交给 AntD Table 的分页器。

### 2.4 流程门禁

`.agents/flow/README.md` 规定 issue 的 scope 是 PR 可改文件的并集；`scripts/verify-flow.mjs` 在 diff 模式检查每个提交与 PR 标题的 `(#N)` 引用、issue 状态和文件覆盖。本 PR 的新 issue、milestone、roadmap 与预算改动都在 m8-03 的 scope 内。

## §3 数据流走查

1. 用户打开 `/evals`，`page=1`，`listQuery` 以 `q="" / status=all / datasetId=all / page=1` 为 key 发出请求。
2. 请求为 `/api/v1/evaluations?limit=10`（`offset=0` 省略），后端返回 `total=35`、`items` 10 条、`stats` 全量。
3. Table 渲染 10 行；`pagination.total=35`、`pageSize=10` 换算出 4 页，分页器显示 1–4。
4. 点击第 2 页：`setPage(2)` → 新 key → `offset=10`；`keepPreviousData` 让第 1 页行保留到响应返回，避免闪烁。
5. 点击第 4 页：`offset=30`，返回 5 条；分页器停在第 4 页，末页不足 10 条正常展示。
6. 在第 4 页停留 3 秒：`refetchInterval` 用当前 key 重新请求 `offset=30`，页码不变，统计数据同步刷新。
7. 在第 4 页输入搜索：防抖 250ms 后同时写入 `debouncedSearch` 与 `page=1`，只发一次 `q=...&limit=10` 请求，页码回到 1。
8. 切换状态或数据集：事件处理器同时 `setFilter` 与 `setPage(1)`，React 批处理成一次渲染，只发一次新筛选请求。
9. 若筛选后总数变小、当前页超界（例如从 35 条筛到 4 条时页码仍是第 4 页），`139-144` 的 effect 会收敛到 `ceil(total/10)`，避免停在空页。
10. 清除筛选：`198-204` 同时重置搜索、状态、数据集与页码，回到 35 条第 1 页。

## §6 讨论点

### D1 服务端分页 vs “只改变展示”

- **位置**：`web/src/pages/EvalsPage.tsx:130-131`。
- **现象**：列表请求从“默认一次取 50 条”变为“`limit=10` + `offset`”，即分页窗口由服务端裁剪。
- **问题**：issue 写“分页只改变展示，不改变数据来源与筛选语义”，服务端裁剪窗口是否越界？
- **预判**：没有改变数据来源（仍是同一个列表 API）与筛选语义（`q/status/dataset_id` 与统计口径不变）；只是把已有的 `limit/offset` 参数显式用起来。若纯前端分页，超过 50 条时只会看到前 50 条，`total` 与可见记录会不一致，属于隐藏缺陷。
- **结论**：建议保留服务端分页；如希望严格“前端只切页”，需要在服务端提高/取消列表上限并单独评估。

### D2 搜索词 trim 后不变时的页码重置

- **位置**：`web/src/pages/EvalsPage.tsx:105-113`。
- **现象**：旧实现对原始 `search` 做防抖，输入尾随空格等不改变筛选词的编辑也会触发 `setPage(1)`，在第 3 页输入一个空格会被弹回第 1 页。
- **问题**：这是分页体验的边界缺陷，与“搜索变化后回到第 1 页”的语义不符。
- **预判**：改为依赖 `trim` 后的 `trimmedSearch`，只在筛选词实际变化时重置；不影响正常输入。
- **结论**：已按预判修复，见 §7 与本 PR 的 `de41aed`。

### D3 总数缩小时的收敛延迟

- **位置**：`web/src/pages/EvalsPage.tsx:139-144`。
- **现象**：如果当前页因数据变化超界，会先发出一次旧页码请求，拿到新 `total` 后 effect 再收敛到最后一页。
- **问题**：是否会出现用户可感知的空页？
- **预判**：筛选变化时处理器已同步重置到第 1 页，因此该路径主要覆盖“后台删数据/自动刷新导致总数缩小”；React Query 的 `keepPreviousData` 会保留旧行，收敛请求通常在百毫秒级完成，无实害。若要彻底消除，可在同一事件里预判总数，但会增加状态耦合。
- **结论**：接受现状，保留收敛 effect 作为安全网。

### D4 前端自动化测试缺口

- **位置**：`web/` 整体。
- **现象**：仓库没有前端单测/组件测试框架；本 PR 的回归证据是 Playwright 驱动的真实页面冒烟（未提交进仓）。
- **问题**：后续重构如何防回归？
- **预判**：本 PR 不引入新框架（超出 issue 范围）；分页行为已由 30 项冒烟断言覆盖，包括边界与筛选组合。
- **结论**：记录为覆盖缺口；若前端测试框架在后续 milestone 立项，可把本 PR 的冒烟场景迁为组件测试。

### D5 ≤10 条时分页器隐藏

- **位置**：`web/src/pages/EvalsPage.tsx:419`。
- **现象**：`hideOnSinglePage: true` 使 10 条及以下不显示分页器。
- **问题**：用户是否会误以为“没有分页”？
- **预判**：验收明确要求“记录数不超过 10 条时正常展示，不出现空页”；隐藏单页分页器是 AntD 的标准行为，也与 m8-01 的 Runner 分页一致。
- **结论**：符合验收，无需调整。

## §9 文件级代码分析

### 9.1 `web/src/pages/EvalsPage.tsx`（M）

**职责**：评测任务列表页，组合统计卡、筛选栏、表格、创建与取消操作。**变更形态**：修改 `Table` 的分页配置，并增加页码状态、查询分页参数、筛选重置与超界收敛。

**关键依赖解读**：

- `@tanstack/react-query` 的 `keepPreviousData`：页面切换 query key 时保留上一份数据，属于查询缓存行为，不是网络层缓存；作用是避免翻页时表格瞬间清空。
- AntD `Table` 的 `pagination` 对象：`current` 受控、`total` 由服务端给出、`onChange` 回写页码；`hideOnSinglePage` 控制单页时是否显示分页器。没有引入新依赖。
- 服务端 `total`：`EvaluationListResponse.total` 是筛选后的全量计数，配合 `items` 当前页使用，避免用 `items.length` 计算页数。

**旧代码 vs 新代码**：

```ts
// 旧：一次取默认 50 条，全部平铺
queryKey: evaluationsQueries.list({ q: debouncedSearch, status: statusFilter, datasetId: datasetFilter }),
queryFn: ... fetchEvaluations({ q, status, datasetId }, signal),
pagination={false}
```

```ts
// 新：查询带页码，服务端窗口 10 条；筛选与页码都进入 key
const trimmedSearch = search.trim();
useEffect(() => {
  const timer = window.setTimeout(() => {
    setDebouncedSearch(trimmedSearch);
    setPage(1);
  }, 250);
  return () => window.clearTimeout(timer);
}, [trimmedSearch]);

queryKey: evaluationsQueries.list({ q: debouncedSearch, status: statusFilter, datasetId: datasetFilter }, page),
queryFn: ... fetchEvaluations({ ..., limit: PAGE_SIZE, offset: (page - 1) * PAGE_SIZE }, signal),
placeholderData: keepPreviousData,
pagination={{ current: page, pageSize: PAGE_SIZE, total: total ?? 0, showSizeChanger: false, hideOnSinglePage: true, onChange: nextPage => setPage(nextPage) }}
```

**实现思路总结**：页码是页面状态而不是组件内部状态，确保筛选、自动刷新与分页共用同一个 query key；服务端负责总数与统计，前端只负责呈现窗口。

**检视发现**：D1（服务端窗口的取舍）、D2（已修复）、D3（收敛延迟）、D5（单页隐藏）均集中在本文件；没有发现空指针、竞态或类型缺口。`listQuery.isLoading` 只在首次加载时为真，翻页依赖 `keepPreviousData` 保持稳定，没有额外的 loading 闪烁。
