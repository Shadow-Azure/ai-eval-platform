## §1 一页速览

一句话：**给平台装上"派发-回传闭环"——评测创建时把每个分片的快递单（outbox）和货物清单（manifest 原文+digest）一次事务写进数据库；worker 照单把 `repository_dispatch` 发给 GitHub；Runner 凭平台当面签发的短期通行证拉清单干活，货走平台开的预签名上传通道；每一通电话（回调）都要对上 attempt 号和通行证才能改账本，重复电话自动挂断、迟到的电话不翻旧账，三种坏消息（派发失败/Runner 失败/货丢了）都进明确的失败台账而不是永远"排队中"。**

比喻：outbox 是快递单存根（对账），manifest 端点是把清单和通行证一起递给快递员的窗口，upload-urls 是平台开的打包间（钥匙在 URL 里，10 分钟有效），回调状态机是只认工单号的台账员。

## §2 架构导览

### 2.1 一次事务写完"快递单+货物清单"（为什么对账不会撒谎）

`create_synthetic_evaluation`（services/evaluations.py:86）在**同一个事务**里写 run/case/attempt 行和每分片一条 outbox 行；`build_shard_dispatches`（:173）把契约校验过的 client_payload、**manifest 原文**和 sha256 digest 一起塞进 outbox.payload_json。manifest 原文入库是关键取舍：dispatch 契约携带 manifest_digest，Runner 拉取时按字节比对——如果 manifest 由查询时重拼，任何序列化差异都会让 digest 失配；存原文则"派发出去的清单"和"Runner 拉到的清单"必然一致（冒烟场景 04 验证 `served == stored`）。重试分片同构：`build_retry_dispatch`（case_attempts.py:375）为单个失败用例生成 `-o{ordinal}a{attempt}` 后缀分片，dispatch_key 全局唯一。

### 2.2 派发环：乐观领取是幂等底线，lease 是重启保险

`dispatch_pending_outbox`（dispatcher.py:38）先 `recover_stuck_leases`（:71）把 processing 超 lease 的行放回 pending（Worker 崩溃恢复），再逐行 `_dispatch_row`（:104）：`UPDATE … WHERE status='pending'` 抢到才算领到（多副本安全）；GitHub 204 后写 `sent + dispatched_at + github_status`（:198-204 区段）并推 attempt → queued；失败则 attempts+1 指数退避回 pending，超过 `dispatch_max_attempts` 走 `_exhaust_dispatch`（:221）：attempt dispatch_failed、case failed、run 事务内重算成 failed——**永不永久 queued**（冒烟场景 08/09）。attempt 行只在创建/重试事务里生成，恢复重派不可能复制 attempt（冒烟场景 10：pause/unpause 后 attempts=2 恰为 2 case）。

### 2.3 回调状态机：台账员的三条铁律

所有回调经 `resolve_context`（case_attempts.py:91）解析 case+run+精确 attempt，然后单事务推进：

1. **重复即挂断**：`_event_exists`（:113）按 (case_run, attempt, sequence) 唯一约束 + event_id 匹配判重，重复回调 200 deduped，计数器不二次推进（冒烟场景 07：replay 后 counters 不变）。终态 attempt 上 event_id 不同则 409 stale——同 sequence 不同事件不是重传。
2. **迟到不翻账**：终态后的 heartbeat/started/completed/failed 一律 409 stale_*，eval_event 保留审计（`case.started_late`），取消后的迟到 completed 不能把 cancelled 翻回 succeeded（测试 test_completed_after_cancel_does_not_regress）。
3. **货不对板不记账**：completed/uploads 走 `_verify_objects`（:261）HEAD 校验对象存在+大小，缺失/不符 → attempt `artifact_missing` + case failed（:266-286 区段内事务完成），验收"绝不把用例标成完整成功"。

重试语义（:464 handle_failed）：retryable 且未达 max_attempts → 恰好一个新 attempt + 一条重试 dispatch；旧 attempt 原样保留诊断。成功完成清掉 case 行残留 error 字段（冒烟抓出的 P3，commit 2e7b0c9）。

### 2.4 短期 token：平台当面签发，不进 GitHub payload

设计 06 §4 的 OIDC 建议在当前依赖集下不可行（无 RSA 验签依赖，pyproject 不在本 issue scope），MVP 取 HMAC 短期 token：`issue_short_token/verify_short_token`（short_token.py:39/:60）与 runner/lib/auth.mjs **线格式互通**（测试用 subprocess 互验对方签发/校验）。签发点在 manifest 端点（api/runners.py:395）：清单响应头 `X-Runner-Task-Token` 携带 attempt 绑定 token——密钥不出平台 env、不进 workflow env，Runner 侧只在进程内存持有。回调侧 `require_case_token`（:176）验签+过期，`_check_token_bindings`（:205）对 DB 行校验 eval_run/shard/attempt 三元组，不符 403。**冒烟抓出真实缺陷**：case 路由残留 runner 面 token 依赖导致平台 token 被 401 拦截，已移除（M2-04 遗留 b 收口：RUNNER_HEARTBEAT_TOKEN 只守卫 Runner 心跳）。`RUNNER_TASK_SECRET` 未配置时回退 `development-only-secret`（:165 effective_task_secret）——本地环路可用，生产 compose 注入真实密钥，注释明示 dev-only。

### 2.5 对象通道：平台开打包间，钥匙在 URL 里

`ObjectStore._presign`（object_store.py:75）纯 stdlib SigV4：`presign_put_url`（:115，UNSIGNED-PAYLOAD、只签 host，900s）+ 预签名 HEAD（:110）给完成校验用。**冒烟抓出真实缺陷**：X-Amz-Credential 值里的 scope 斜杠必须编码 %2F（:88-90），否则真实 MinIO/OSS 拒签——本地 stub 不验签所以只有真机才能暴露，这正是"真实链路走通一次"的价值。`object_store_from_settings` 未配置返回 None：upload-urls → 503，完成校验跳过（纯开发态）。

### 2.6 workflow 两条腿

repository_dispatch 分支：client_payload 落盘 → contracts.mjs 验 dispatch → synthetic-task（预签名上传开、token 来自 manifest 头、不进 env）。workflow_dispatch 分支 = 引导：在真实 Runner 上调平台 `POST /api/v1/evaluations` 创建评测，由平台派发环触发真实 run——**同时就是 M2-04 遗留 a 的队列拾取复验**（冒烟场景 12：bootstrap run 42516469781 success）。

## §3 数据流走查（主机端到端剧本，全部实测）

1. `POST /api/v1/evaluations`（201）→ run queued、outbox pending、eval_event `eval.created`。
2. worker 轮询（worker/main.py:35 dispatch_once）→ GitHub 204 → outbox `sent` + dispatched_at/gh_status → attempt queued → `eval.dispatched`。

## §6 讨论点（预判供拍板，结论留空）

1. **OIDC 未做，HMAC 短期 token 替代**（services/short_token.py）
   现象：设计 06 §4 首选 OIDC；当前依赖集无 RSA 验签能力且 pyproject 不在 issue scope。
   问题：HMAC token 的密钥面（平台 env ↔ 需要验证的 runner 侧）在多机扩容时如何演进？
   预判：M3 接入真实模型/资产时引入 `cryptography`+PyJWT 走 OIDC 换发；当前单固定 Runner 威胁模型下 HMAC+manifest 头下发是合理降级（代码注释与 PR 均已声明）。结论：
2. **repository_dispatch 无回执对账**（dispatcher.py）
   现象：GitHub 204 无 delivery id；对账 = outbox dispatch_key（UNIQUE）+ dispatched_at + github_status。
   问题：是否需要反向拉取 GitHub run id 回填 attempt.github_run_id？
   预判：设计 06 §5 的"未收到 started 按 1/5/15 分钟退避查询 GitHub"属调度器增强，M2 单 Runner 场景由超时失败注入兜底即可；M3 并发池化时一并做。结论：
3. **RUNNER_TASK_SECRET 的 dev 回退**（api/runners.py:165）
   现象：未配置时平台用 development-only-secret 签发（保持本地环路），生产 compose 已注入。
   问题：回退是否会掩盖"忘了配密钥"的部署事故？
   预判：deploy.sh 可加 readyz 附检（DEPLOY_ENVIRONMENT=production 且 RUNNER_TASK_SECRET 为空 → 警告），属部署侧增强，不阻塞本 PR。结论：
4. **main 旧版 workflow 的 repository_dispatch run 为红**（.github/workflows/eval-shard.yml）
   现象：合入前真实 dispatch 由 main 旧版 workflow 消费（演示 token → 401）→ Actions 出现红 run；新版已验证（workflow_dispatch @PR 分支 success）。
   问题：是否接受合并前的红 run 作为过渡态？
   预判：合并后 main 上的新版自动接管，无需回填；如介意可在 PR 描述标注（已标注）。结论：
5. **run 级 eval_event 的幂等靠 dedupe_key 而非约束**（dispatcher.py `_shard_event`）
   现象：eval_event 唯一约束只覆盖 case 级 (case_run, attempt, sequence)；run 级事件在事务内查重（payload dedupe_key）。

职责：评测生命周期唯一写入口（创建/取消/进度重算）。变更核心是 `build_shard_dispatches`——把"派发什么"（client_payload）与"Runner 拿什么"（manifest 原文）一次定版入库。实现教训已固化测试：`refresh_run_progress`（:502）必须在聚合前 `flush()`（会话 autoflush=False，否则计数读到变更前状态，冒烟前本地测试抓出）。已知弱点：创建时 case_keys 全量落单分片（默认 64/片）无容量校验，属 M3 调度器职责。

### backend/app/services/dispatcher.py（A）
职责：outbox 消费环 + 对账。亮点是失败三分层：传输失败退避重试（available_at 后移）、超限收口（attempt/case/run 三级联动 + eval.dispatch_failed）、不可派发状态（run 取消）直接落行级 failed 保留 last_error。已知弱点：单行事务内做 GitHub 网络 IO（≤15s 超时），批量大时会拉长 worker 轮询周期——M3 队列后端切换点。

### backend/app/services/case_attempts.py（A）
职责：回调状态机。亮点是"先解析后副作用"：resolve_context 在任何写之前完成 attempt/token 绑定校验，未知/旧 attempt 零副作用返回 409。`_verify_objects` 把对象缺失的处理与状态迁移放同一事务（先落 artifact_missing 再 raise），保证响应码与账本一致。已知弱点：状态迁移表未显式化（M2-04 检视 §9 同款判断）——当前 5 类回调 13 条边，抽表时机在 M3 重试策略复杂化时。

### backend/app/api/runners.py（M）
职责：协议边界扩展。manifest 端点是 token 签发与清单分发的合一天窗：一个响应同时给 Runner"干什么"（清单）与"凭证"（头），且清单字节来自 outbox 存储。检视发现已全部进 §7。

### runner/scripts/synthetic-task.mjs（M）
职责：Runner 侧参考实现。token 获取链 `--token > env > manifest 头`（空值穿透用 `||` 而非 `??`——冒烟前 node 测试抓出）；无 secret 时仍做 claims 绑定校验（token 与 dispatch 的三元组比对）；预签名上传为 opt-in（RUNNER_PRESIGN_UPLOADS=1），M2-04 本地模式保持兼容。已知弱点：upload-urls 失败时 failed 回调取 cases[0]（多 case 分片中段的失败归因可能偏差）——合成任务单 case 重试分片为主，M3 真实任务按 per-case 状态机重写。

### tests/backend/conftest.py + case_helpers.py + object_stub.py（A/M）
职责：共享测试底座。eval_env fixture（真实评测+stub 存储+runner 心跳注册）上移 conftest 的教训：跨测试模块导入 fixture 会被 ruff 当未使用符号删除——pytest 按参数名注入对静态分析不可见，共享物必须进 conftest。
