## §1 一页速览

一句话：把“Node 压缩包下载只要被网络重置一次，整个评测用例就以 permanent 失败结束”改成“只在确认是网络类 curl 错误时再下载一次，第二次仍失败才沿用原失败链”。

比喻：这像仓库门口搬一箱 Node。网络瞬断只是搬运途中被人撞了一下手，箱子掉了可以再搬一次；如果仓库明确说“没这个货”（HTTP 22）、钥匙不对（证书 60）或文件大小不符（63），再搬也解决不了，应立刻报原来的错误，而不是把所有失败都重试一遍。

| 重试条件 | 仅 6/7/28/35/52/55/56 七个网络码 | 7 个码逐一用假 curl 验证首次失败后恰好两次调用 |

## §2 架构导览

### 2.1 变更在调用链中的位置

`runner/scripts/real-task.mjs:690` 在用例容器启动后执行 `docker exec ... bash -lc runtimeAdapter.installScript()`；`runner/lib/adapters.mjs:2、5、13-17` 把 `claude-code` 适配器注册进 runtime 表。`installScript()` 返回的是一段 shell 文本，由容器内的 bash 执行，因此本次变更本质是“生成一段带受控重试的 shell 脚本”，不是 Node 进程内重试。

### 2.2 为什么用 `fetch_node` + `if fetch_node; then ... else code=$?`

Shell 里要保留首次失败的真实退出码，必须让 `fetch_node` 出现在 `if` 条件中，再在 `else` 分支第一行取 `$?`。如果写成 `if ! fetch_node; then code=$?`，条件里的 `!` 已经把状态取反，`code` 会得到 0，后续 `case` 永远匹配不到网络码。当前写法（`claude-code.mjs:19-25`）同时满足两点：`set -e` 不会因第一次下载失败而直接退出；`code` 是 curl 的真实退出码。

第二次 `fetch_node`（`:29`）不再包在条件里，因此 `set -e` 会让脚本在第二次失败时立即以第二次的退出码结束。这是“第二次失败保留第二次 stderr 与退出码”的实现基础，不需要额外 `|| exit`。

### 2.3 重试集合为什么这样选

`claude-code.mjs:12` 的集合是 6（无法解析主机）、7（无法连接）、28（超时）、35（SSL 连接错误）、52（空响应）、55（发送失败）、56（接收失败）。它们都属于连接建立或传输阶段的瞬时问题，重试一次有实际意义。22（HTTP 错误）、23（写文件失败）、60（证书）、63（大小不符）、77（CA 文件）以及 tar/权限/磁盘错误属于确定性失败，重试只会拖慢失败并掩盖真实原因，所以落到 `*)` 分支直接 `exit "$code"`。

### 2.4 失败链没有变化

重试仍失败时，`dockerRun` 的 `spawnSync` 在 `real-task.mjs:160-172` 拿到非零状态，抛出“docker 失败（code）”；`real-task.mjs:971-972` 的 catch 仍把异常折叠成 `agent.status=1`；`real-task.mjs:1010-1017` 继续调用 `classifyAgentFailure`。本次没有改这些文件，所以失败分类、`max_attempts` 与后端 `agent_crashed` 语义保持不变。

### 2.5 为什么不用 `curl --retry`

`--retry` 会按 curl 的默认策略重试，`--retry-all-errors` 更会把 HTTP/证书等确定性错误一起重试，正好违反 issue 的“必须先明确确认是网络问题，不能对任意失败盲目重试”。显式列出退出码虽然多几行，但语义边界清楚，测试也能逐个码验证。

## §3 数据流走查

以 issue 中的真实故障为例：

1. 用例容器内没有 Node，`command -v node` 失败，进入下载分支（`claude-code.mjs:17`）。
2. `fetch_node` 第一次执行 curl，TLS 读取被对端重置，curl 以 56 退出。
3. `if fetch_node` 条件为假，进入 `else`，`code=$?` 得到 56（`:22-25`）。
4. `case` 命中 `6|7|28|35|52|55|56`，向 stderr 打印 `node download network error (curl 56), retry 1/1`，再次调用 `fetch_node`（`:27-29`）。
5. 若第二次成功：继续 `mkdir -p /opt/node`、`tar -xJf ...`（`:36-37`），Node 安装完成，后续 PATH、npm、用户初始化照旧。
6. 若第二次也失败（例如 28）：`set -e` 使脚本以 28 结束；stderr 同时保留两次 curl 的错误，其中第二次的错误码和文本是最终现场；`mkdir`/`tar` 不会执行。
7. 若首次就是确定性的 22：`code=22` 进入 `*)`，直接 `exit 22`，不打印 retry 日志，也不执行第二次 curl。

## §6 讨论点

### D1 测试缺少“首次成功不重试”的正向基线

- **位置**：`tests/runner/node-download-retry.test.mjs:114-127`；对照原有失败路径 `:130-183`。
- **现象**：初版测试只验证“失败→重试”和“确定性失败→不重试”，没有验证“首次成功只调用一次”。如果未来有人把 `fetch_node` 无条件调用两次，现有测试仍会绿。
- **问题**：重试逻辑的正确性不仅在于“该重试时重试”，也在于“不该重试时不重试”。成功路径缺少断言会让回归缺少一条边。
- **预判**：补一个用例即可，成本很低；同时断言两次尝试使用同一个 Node URL，避免重试时拼错地址。
- **结论**：已在本次检视中补上 `:114-127`，并在网络码循环里补了两次 URL 一致性断言（`:139-143`）；重跑测试通过。

### D2 测试把假 curl 的落盘位置写死为 `/tmp/node.tar.xz`

- **位置**：`tests/runner/node-download-retry.test.mjs:57-60`；生产脚本的 `-o /tmp/node.tar.xz` 在 `runner/adapters/runtimes/claude-code.mjs:20`。
- **现象**：初版假 curl 解析 `-o` 后写入固定路径 `/tmp/node.tar.xz`，而不是测试自己的临时目录；也没有断言文件真的写成。
- **问题**：严格说这会污染主机 `/tmp`；如果同一台机器并发跑多个测试实例，可能互相覆盖，而且写入失败仍会 `exit 0`，成功路径的断言会失去意义。
- **预判**：不扩大生产接口，只在测试 harness 里把固定的 `/tmp/node.tar.xz` 重定向到 `$HOME/node.tar.xz`，并补文件内容断言；这样既不改变生产脚本，也消除了主机级副作用。
- **结论**：已修复：假 curl 在 `:59` 把固定路径改写到临时 `$HOME`，成功路径断言文件内容（`:121`、`:138`），失败路径断言文件不存在（`:157`、`:170`、`:181`）。

### D3 没有连接/总超时和本地缓存

- **位置**：`runner/adapters/runtimes/claude-code.mjs:20`。
- **现象**：`curl -fsSL` 没有 `--connect-timeout` / `--max-time`，也没有复用本地压缩包。
- **问题**：重试只能覆盖“第一次快速失败、第二次成功”的瞬时断流；如果网络持续故障，两次尝试都可能慢或失败，8 分钟级 stall 仍可能发生。
- **预判**：issue #397 明确把超时和缓存排除在本次范围外，理由是避免把单点重试扩大成基础设施改造；本次遵循该边界。
- **结论**：不在本 PR 修改，作为残余风险记录；如果后续再次出现长时间 stall，另开 issue 评估超时与缓存。

## §9 文件级代码分析

### 9.1 `runner/adapters/runtimes/claude-code.mjs`

职责一句话：生成安装 Claude Code 运行时的容器内 shell；本次只改其中 Node 压缩包的下载段。

变更形态：M，+25/-1。旧代码是一行裸 curl：

```sh
curl -fsSL https://registry.npmmirror.com/-/binary/node/v22.14.0/node-v22.14.0-linux-x64.tar.xz -o /tmp/node.tar.xz
```

新代码：

```sh
node_url=https://registry.npmmirror.com/-/binary/node/v22.14.0/node-v22.14.0-linux-x64.tar.xz
fetch_node() {
  curl -fsSL "$node_url" -o /tmp/node.tar.xz
}
if fetch_node; then
  :
else
  code=$?
  case "$code" in
    6|7|28|35|52|55|56)
      echo "node download network error (curl $code), retry 1/1" >&2
      fetch_node
      ;;
    *)
      exit "$code"
      ;;
  esac
fi
```

实现思路：用函数复用同一条 curl；用 `if/else` 保留首次退出码；用白名单 `case` 区分网络错误与确定性错误；第二次失败交给 `set -e` 以原码退出。

检视发现：无生产代码缺陷。需要说明的边界是：重试只覆盖下载命令本身，不覆盖 tar 解包、权限、磁盘等后续步骤；这与 issue 的“只对单点问题加重试”一致。
