## §1 一页速览

一句话：让竞争态 spot 池可以按 `min_capacity` 保留少量预热容量，不再因为一次 60 秒心跳抖动就回收实例，并把越积越多的 offline Runner 行按保留期清掉。

比喻：以前的 spot 池像“每来一位客人就临时租一间房，客人刚走 60 秒就退租”；现在可以配置“至少留一间房”，并且退租前多等几分钟确认客人真的走了，同时每天把过期的入住登记表归档删除。

| 交付块 | 内容 |
|---|---|
| warm pool | `min_capacity` 从“只影响缩容”变成容量下限；默认 0 不变 |
| lost grace | 60s → 180s；真实退出仍在几分钟内回收 |
| young runner guard | 注册不满 120s 不缩容 |
| 清理 | 7 天保留期、批大小 200、worker 每小时一次 |
| 成本 | 仍受 `max_capacity`、价格阈值、每批上限约束 |

验证基线：`pytest tests/backend` 全绿（本地 SQLite）、`npm test` 107/107、`npm run verify:docs`、`npm run verify:flow`、changed-file ruff 全绿。

## §2 架构导览

### 2.1 容量状态

`backend/app/services/capacity_control.py:334` 的 `_build_state` 现在同时计算两个缺口：

- `queue_gap = max(0, queued - idle - starting*slots)`：沿用 M4-03/M8-34 的排队缺口，仍写入 `capacity_gap`，保持控制台“当前缺口”语义。
- `warm_gap = max(0, min_capacity - live - starting*slots)`：M8-48 新增的 warm floor，按 Runner 数解释。
- `capacity_deficit = max(queue_gap, warm_gap)`：真正驱动扩容的量；`desired = min(max_capacity, current_size + ceil(deficit/slots))`。
- `_scale_up` 在 `:538` 使用 `capacity_deficit`，因此无排队时也会补 warm 容量。
- `_capacity_reason` 仍以 deficit 判断是否扩容，价格阈值与库存检查照旧，所以 warm pool 不会绕过成本上限。

### 2.2 缩容保护

`_idle_runners_for_release`（`:614`）在原有 online + 无 busy + 心跳新鲜条件上增加了：

- `Runner.status.not_in(("offline","draining"))`：显式排除历史行；
- `coalesce(registered_at, created_at) <= now - min_idle`：注册不足 120 秒的 Runner 不参与缩容。

“刚结束 Job 的 Runner”不受影响，因为保护只看注册时间，不看心跳时间。

### 2.3 lost grace 与回收

`backend/app/config.py:235` 把 `eval_spot_runner_lost_grace_seconds` 默认改为 180。`aliyun.py` 的 `sync` 仍按原有条件回收：

- Runner 行 offline：`now - last_heartbeat >= grace` 才回收；
- Runner 心跳丢失：`now - last_heartbeat > heartbeat_timeout + grace`；
- Runner 行缺失：从 `ready_at`/`created_at` 起算超过 grace。

因此 60 秒的短抖动不再触发回收；真实退出最多多等约 2 分钟。

### 2.4 Runner 清理

`backend/app/services/runners.py:226` 的 `cleanup_offline_runners`：

1. 选 `status=offline`、无 busy 绑定、`coalesce(deregistered_at, last_heartbeat_at, created_at) <= cutoff` 的行；
2. 用 `NOT EXISTS` 排除仍有活跃 attempt 或非终态实例引用的行；
3. 先把终态 attempt 与 released/interrupted 实例的 `runner_id` 置空，再批量删除 Runner 行；
4. 没有候选时直接返回，不 commit；有删除时 commit。第二次执行返回 0。

`backend/app/worker/main.py:55` 的 `runner_cleanup_once` 用进程内 monotonic 时间限频（默认 3600s），worker 每轮最多触发一次真正的清理。

## §3 数据流走查

场景：运营把池 `min_capacity` 设为 1，当前没有排队。

1. worker 调 `capacity_once` → `reconcile_pools` 扫描 active spot 池；
2. `_build_state`：`queued=0`、`idle=0`、`live=0`、`starting=0` → `queue_gap=0`、`warm_gap=1`、`deficit=1`；
3. `_capacity_reason` 返回 `capacity_scale_up`（若价格超阈值则返回 `resource_price_above_threshold`）；
4. `_scale_up` 创建 1 台实例，`desired=1`；
5. 下一 tick：`starting=1`、`warm_gap=0`、`deficit=0`，不再重复创建；
6. 实例注册 Runner 后 `live=1`，无排队时 `idle=1`、`min_capacity=1`，`_capacity_reason` 不返回 scale_down；
7. Runner 退出后：Runner 行 offline，`aliyun.sync` 在 180 秒 grace 后回收实例；不再出现“刚注册 30 秒就被回收”。

清理场景：

1. 历史上每次 ephemeral Runner 退出留下 offline 行；
2. worker 每小时一次 `cleanup_offline_runners`；
3. 超过 7 天且无活跃引用的行被删除；终态 attempt/实例先解绑外键；
4. 容量统计的 `_runner_count` 只接受 online/busy，历史行本来就不计数，清理后更不会影响查询性能。

## §6 讨论点

### D1 `capacity_gap` 的语义（已修复）

- **位置**：`backend/app/services/capacity_control.py:369`、`:399`
- **现象**：第一版让 `capacity_gap` 同时包含 warm 缺口，控制台“当前缺口”会在无排队时显示非 0。
- **问题**：`capacity_gap` 已被 UI 和测试当作“排队缺口”使用，语义重载会让既有展示与告警文案失真。
- **预判**：保留 `capacity_gap` 为 queue-only，新增 `capacity_deficit` 驱动扩容与事件去重。
- **结论**：已按预判修复（`867af70`），warm 测试同时断言 `capacity_gap=0`、`capacity_deficit=1`。

### D2 `max_capacity` 的单位（保留，记录为已知限制）

- **位置**：`backend/app/services/capacity_control.py:374`
- **现象**：`max_capacity` 在 UI 与调度器里按 Runner 数使用，但 `desired` 是实例数；`runners_per_instance=2` 时可能多出不到一个实例的 Runner。
- **问题**：严格按 Runner 数封顶需要把实例数向下取整，可能浪费一个 Runner 槽；这是 M4-03 以来的既有语义，不是本 PR 引入。
- **预判**：本 PR 不改，避免在 warm pool 修复里改变多 Runner 池的调度行为；如果需要严格成本上限，单独 issue 处理。
- **结论**：留待用户决定；当前 `max_capacity` 仍是可配置的成本上限，只是按实例粒度取整。

### D3 历史 attempt 的 `runner_id` 会被置空（接受）

- **位置**：`backend/app/services/runners.py:296`
- **现象**：删除 7 天前的 Runner 行前，终态 attempt 的 `runner_id` 被置空。
- **问题**：历史 attempt 失去直接指向 Runner 的外键；但 `eval_event`、`error_summary` 和实例 `cost_json.runner_name` 仍保留排障线索，且这是绕过 RESTRICT 外键的唯一方式。
- **预判**：保留清理，接受该取舍；若未来需要长期保留 runner 详情，应改为软删除或归档表，而不是继续积累行。
- **结论**：接受；在清理 docstring 与设计文档中写明。

### D4 控制台文案仍偏“排队”（已知小问题）

- **位置**：`web/src/pages/ResourcesPage.tsx:117`、`:148`
- **现象**：warm-only 扩容时 `capacity_gap=0`，但库存不足文案仍说“排队 Job 保持等待”。
- **问题**：这是 UI 既有文案，本 PR 不改 UI；不会误导功能，但可能让运营困惑。
- **预判**：后续单独做 UI 文案或展示 `warm_pool_gap`，避免本 PR 引入需要 before/after 截图的 UI 变更。
- **结论**：留待后续；本 PR 在描述中说明 warm pool 行为。

### D5 清理事务边界（接受）

- **位置**：`backend/app/services/runners.py:303`
- **现象**：清理函数在删除时自行 commit，而 provisioner 接口约定“调用方持有事务”。
- **问题**：与 `sweep_stale_runners` 的既有做法一致，worker 每轮独立 session，失败会被主循环捕获；批量删除需要一次性提交，避免半删。
- **预判**：保持现状，注释说明没有候选时不 commit。
- **结论**：接受。
