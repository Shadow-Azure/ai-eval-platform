## 1. 一页速览

一句话：把“cache 输入”从看不见的旁路变成总 Token 的一部分，同时把它、非缓存输入、输出三块继续分开显示，避免平台数字比远端模型账单小一个数量级。

比喻：原来的 Token 报表只记“自己带饭”的部分，cache 是“公司食堂已备好的饭”，没写进总摄入量；现在把食堂那份也算进总量，但标签上仍分别写清“自带 / 食堂 / 运动消耗”，对账时不会串。

| 交付块 | 内容 |
|---|---|
| 口径 | 总（含缓存）= 非缓存输入 + cache read + cache creation + 输出；`total_tokens` 保持 #332 非缓存语义 |
| 数据源 | LLM span 的 `attributes_json`；AGENT 汇总 span 继续排除 |
| 接口 | `/cases`、`/evaluations/{id}`、`/results`、datasets、trace 全部新增字段 |
| UI | 用例明细、结果分析、数据集详情/列表、轨迹四类页面统一 |
| 验证 | backend 全量 pytest、web build、仓库门禁、23 条全栈 UI 冒烟 |

验证基线：PR 描述记录 948 additions / 107 deletions；本地 full-stack smoke 23/23 PASS。

## 2. 架构导览

### 2.1 数据层：一条 SQL 表达式服务两种数据库

`token_usage.py:124` 用 SQLAlchemy JSON 索引访问：

```python
_CACHE_READ = TraceSpan.attributes_json["gen_ai.usage.cache_read_input_tokens"].as_integer()
```

它不是把 JSON 拉到 Python 再解析，而是让 dialect 各自编译：

- SQLite：`CAST(JSON_EXTRACT(attributes_json, '$."gen_ai.usage.cache_read_input_tokens"') AS INTEGER)`
- PostgreSQL JSONB：`CAST(attributes_json ->> 'gen_ai.usage.cache_read_input_tokens' AS INTEGER)`

好处是 `case_usage` / `dataset_token_stats` / `version_case_token_averages` 共用 `_usage_columns()`（`token_usage.py:132`），不会出现测试与生产两套口径。

### 2.2 聚合层：只改“多一列”，不新增 join

`_usage_columns()` 在原有 input/output 后追加两列 cache 求和，外层 `_dataset_case_subquery` 与 `case_usage` 的 join 完全不变。也就是说 cache 不引入新的扫描维度，查询复杂度与 #332 相同。

`TokenUsage`（`token_usage.py:52`）保留 `total_tokens` property 的非缓存语义，新增 `cache_input_tokens` / `total_tokens_with_cache` 派生属性，API 字段由 `as_metrics()` 统一输出。

### 2.3 接口层：旧字段不动，新字段旁挂

- `/cases`：`metrics` 里新增四个 cache/含缓存字段；排序新增 `total_tokens_with_cache`（`workbench.py:54`）。
- `/evaluations/{id}` 与 `/results`：`token_summary` 新增 `cache_*`、`total_tokens_with_cache`、`average_tokens_with_cache`；`/results` 另生 `total_tokens_with_cache` / `tokens_with_cache_per_case` 指标项，旧 `total_tokens` / `tokens_per_case` 仍返回（`results.py:114`）。
- datasets：`token_stats` 新增拆分与两个含缓存均值；用例预览新增 `token_avg_with_cache`（`datasets.py:104`）。
- trace：attempt `stats` 与每个 session 都新增 `cache_read/creation/input` 与 `total_tokens_with_cache`（`trace_queries.py:308`、`:461`）。

### 2.4 前端：一个展示组件，四页复用

`TokenComposition.tsx:14` 只接收已算好的四项和 meta，不重新推导总量；`EvalDetailPage.tsx:1991` 与 `DatasetDetailPage.tsx:641` 各自传入权威 summary。这样前端不会出现“合计按 A 算、拆分按 B 算”的双重口径。

## 3. 数据流走查

1. Claude Code parser 把 usage 写进 LLM span：`input_tokens`、`output_tokens` 进列，cache read/creation 进 `attributes_json`。
2. 用户打开评测详情 → `/cases` → `case_usage()` 按 case 聚合所有 attempt；`case((kind != AGENT, cache_expr), else_=0)` 把 AGENT 汇总排除。
3. 汇总条 → `/evaluations/{id}` → `summarize_case_usage()` 把 5 个有轨迹 case 的四项相加，得到 4216.2 万。
4. 结果页 → `/results` → 同一个 `run_token_summary()`，再补 synthetic metric items；前端过滤旧非缓存卡，保留含缓存卡 + 构成面板。
5. 数据集页 → `dataset_token_stats()` 跨全部版本/run 求和，`eval_count_with_tokens / eval_count` 显示覆盖率；用例预览用 `version_case_token_averages()` 的 `token_avg_with_cache`。
6. 轨迹页 → `attempt_trace()` 的 per-session stats 汇总为 attempt stats；前端概要显示含缓存总量，下方展开 read/creation/非缓存/输出。

对账脚本实测：用例行 5 条之和 = 评测汇总 = 结果 token_summary = 数据集累计；轨迹首用例 = 对应行 metrics。

## 6. 讨论点

### D1 数据集“均 / 次评测”分母只含有轨迹评测

- **位置**：`web/src/pages/DatasetsPage.tsx:579`、`backend/app/services/token_usage.py` `average_eval_tokens_with_cache`
- **现象**：2 次评测中 1 次无轨迹时，卡片写“均 4216.2 万 / 次评测”，旁边另写“覆盖 1/2 次评测”。
- **问题**：只读“均 / 次评测”容易误以为分母是 2。
- **预判**：分母本来就是“有解析轨迹的评测”，与 #332 一致；详情行已显示覆盖率，原型也采用同一写法。
- **结论**：保留，靠覆盖率行消除歧义。

### D2 PostgreSQL cast 对异常属性的鲁棒性

- **位置**：`backend/app/services/token_usage.py:124`
- **现象**：`CAST(... ->> key AS INTEGER)` 遇到非数字字符串会报错。
- **问题**：历史/第三方 parser 若把 cache 字段写成 `"n/a"` 会让整个聚合查询失败。
- **预判**：当前只有 Claude Code parser 写这两个键，且 `_int()` 保证整数；没有实际输入能产生非数字。
- **结论**：保持简单；若未来接第三方 parser，再在写入侧清洗。

### D3 `/results` 新指标未注册进 `METRIC_CONFIGS`

- **位置**：`backend/app/api/results.py:114`
- **现象**：新指标项由 `/results` 实时合成；既有数据集版本的“指标口径”表不会自动列出。
- **问题**：管理员在“指标口径”页看不到 `total_tokens_with_cache` 的定义。
- **预判**：与 #332 的既定策略一致：不冻结、不 backfill；`/results` 始终实时显示。
- **结论**：作为已知限制记录在 PR；需要时重新导入或做管理员 backfill。

### D4 `readMetricCounter` 顺带修复旧指标分子显示

- **位置**：`web/src/api/evaluations.ts:666`
- **现象**：后端指标分子是 JSON number，旧 parser 只接受 string，导致卡片 meta 显示“— / —”。
- **问题**：这是 #332 遗留的小 bug，本 PR 为让新指标项可读而一并修复。
- **预判**：属于同一展示链路的最小修复，不改变值。
- **结论**：接受，PR 已说明。

## 9. 文件级代码分析

### `backend/app/services/token_usage.py`（M）

职责：把 trace span 聚合为 case/run/dataset 三层 token/cost 数字。变更形态是“加字段、加表达式”，旧字段语义不动。

关键点：

1. `_CACHE_READ` / `_CACHE_CREATION` 是模块级 SQLAlchemy 表达式；表达式不可变，多个查询复用安全。
2. `_usage_columns()` 把 cache 求和放进同一 `SELECT`，不增加 join；AGENT 排除沿用 `_TOKEN_SPAN`。
3. `dataset_token_stats()` 的 row 索引从 8 个扩到 10 个，逐项显式解包，避免 `*row` 漂移。
4. `version_case_token_averages()` 用 `cache_total = cache_read + cache_creation` 再求和，保持“每个 case 跨 run 平均”的旧算法。

检视发现：无阻断问题；D2 记录在案。

### `backend/app/services/trace_queries.py`（M）

职责：轨迹页的 attempt/session 级统计。变更点是在原 input/output 后追加 cache 列，并把 session 的 `cache_input` / `total_with_cache` 派生好再返回。

实现思路：per-session 查询一次拿到 10 列，`_session_body()` 直接透传；attempt 汇总再对 session 值求和。这样轨迹页与 `/cases` 用同一“排除 AGENT”的规则。

检视发现：无。
