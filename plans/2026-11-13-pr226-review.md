## §1 一页速览

一句话：把“评测时注入默认分支的成品 `.claude`”改成“解析时冻结该 commit 的源码，评测时按这份源码现做 `.claude`”。

## §2 架构导览

### 2.1 解析与冻结

`resolve_assets` 在 `runtime_prerequisites_json` 非空时把源标记为 CLI 生成类，调用 `GitHubClient.archive` 取回 `resolved_commit` 的 tarball，上传到 `agent-source-archives/<tenant>/<owner>/<repo>/<commit>.tar.gz`，并把 `source_mode`、`repo_url`、`source_archive_key/digest/size` 写进快照 manifest 和评测冻结 JSON。归档按 commit 去重，不因重复解析重复上传。

`_selection_digest` 只在 `source_mode` 为真时加入该键。这样 m8-22 之前的 CLI 快照不会被同选择命中，重新“读取资产”一定会生成新快照；无命令类摘要保持原样。

### 2.2 评测

`task_asset_payload` 在派发时为 `source_archive_key` 生成 1 小时预签名 URL。Runner 的 `downloadSourceArchive` 校验 digest，`extractSourceArchive` 先列目录校验路径、再 `--strip-components=1` 解包。随后：

1. 删掉数据集仓库自带的 `.claude`；
2. 以 eval 身份在 `/asset-source` 执行 install（源码构建）；
3. 以 eval 身份在 `/testbed` 执行 init 生成新 `.claude`；
4. 从同一份源码注入仓库内选中的静态资产并校验 digest；
5. 校验所有选中资产的目标文件存在，chown 后交给 Agent。

source mode 不再下载冻结资产包；非 source mode 仍走 m8-11 的“只 install + 注入冻结快照”。

### 2.3 加载测试

加载测试也先取同一 ref 的源码树，在源码树中执行 install/init，再扫描生成的 `.claude`。私有仓库复用扫描/创建时的令牌；预览加载测试新增 `access_token` 字段。

## §3 数据流走查

1. 用户在评测页选 `main-copy-ar`，点击“读取资产” → `resolve_assets` 解析 commit，取 tarball，上传 OSS。
2. prepare 快照携带 `source_mode` + `source_archive_key`；用户确认启动。
3. 平台派发任务时预签名源码 URL；Runner 拉取、校验、解包。
4. 容器内 `/asset-source` 执行 `npm ci && npm run build && npm install -g .`；`/testbed` 执行 `codespec init ...`。
5. 静态 Skill 从 `/asset-source/skills/...` 注入 `/testbed/.claude/skills/...`；生成的 Command 由 init 写入。
6. Agent 在 `/testbed` 启动，trace 带 `asset-source.json`（repo/ref/commit、命令、日志尾、静态文件数）。

## §6 讨论点

### 讨论点 1：为什么用平台源码归档而不是 Runner 直接 `git clone`

- **位置**：`backend/app/services/git_client.py`、`runner/lib/source-archive.mjs`
- **现象**：Runner 拿到的是 commit tarball 的短期 URL，不是 Git 凭据。
- **问题**：这算不算“按 ref checkout”？
- **预判**：解包 commit tarball 与 `git clone` + `git checkout` 在“得到该版本文件树”上等价；区别是没有 `.git` 历史，依赖 `git describe` 的构建脚本可能失败。这样做符合“Runner 不存长期凭据”的架构约束，也避免评测时对 GitHub 的二次网络依赖。
- **结论**：待用户拍板；若后续出现依赖 `.git` 的 CLI，可在归档中补一个最小 git 仓库或改为短期 Git 凭据。

### 讨论点 2：旧资产源的 install 配置

- **位置**：`web/src/pages/AssetsPage.tsx`
- **现象**：只有把 install 配成源码构建（如 `npm ci && npm run build && npm install -g .`），生成的 Command 才会随 ref 变化；旧的全局安装命令仍能跑，但 CLI 版本不变。
- **问题**：现有生产源需要人工改配置。
- **预判**：这是配置项而非代码缺陷；UI 已加说明，旧源在重新配置前只会获得静态资产随 ref 变化。
- **结论**：待用户确认是否需要提供迁移脚本/编辑入口（当前资产源没有编辑 API）。

### 讨论点 3：加载测试的宿主依赖

- **位置**：`backend/app/services/agent_assets.py`
- **现象**：加载测试在 API 进程内执行 install/init，需要宿主有 node/npm。
- **问题**：这是 m8-10 既有前提；本次把 cwd 改为源码树，不新增运行时依赖，但源码构建会真正用到 node/npm。
- **预判**：部署镜像若无 node/npm，加载测试会失败；需在部署侧确认或后续把加载测试移入容器。
- **结论**：待用户确认生产 API 宿主的 node/npm 可用性。

## §9 文件级代码分析

### `backend/app/services/agent_assets.py`

变更形态 M。核心是把“加载测试使用空临时目录”改为“加载测试使用 ref 源码树”，并在解析时冻结源码归档。`extract_source_archive` 用 `tarfile` 的 `data` filter + 显式路径/条目/解压大小校验，避免归档越界。`_selection_digest` 的 `source_mode` 键解决旧快照复用问题。实现思路：把“版本”从分支名提升为 commit 归档，冻结后不可变。

### `runner/lib/source-archive.mjs`

新增 A。`downloadSourceArchive` 校验 digest；`extractSourceArchive` 先 `tar -tzf` 审核路径，再解包并统计解压大小；`injectSourceAssets` 按快照里的目标路径从源码树复制并校验 sha256；`missingSourceAssets` 检查 init 后选中项是否齐全。实现思路：静态资产从源码树取，生成资产交给 init；Runner 不接触 Git 凭据。

### `runner/scripts/real-task.mjs`

变更形态 M。新增 source mode 分支；非 source mode 代码保持原语义。source mode 的失败码分为 `asset_source_install_failed`、`asset_source_init_failed`、`asset_source_inject_failed`、`asset_source_init_incomplete`，并在 trace 写 `asset-source.json`。实现思路：把“安装 CLI”与“生成资产”拆成容器内两步，失败可定位到阶段。

### `web/src/pages/EvalWizardPage.tsx`

变更形态 M。只改文案与条件分支：CLI 生成类提示“按该版本 checkout 源码并重新构建/init”，无命令类仍提示“冻结资产”。未改 API 字段，避免前后端契约扩散。

### `prototype/app.js`、`prototype/index.html`

变更形态 M。同步默认分支、Agent 版本、将使用的 commit 与状态文案；`index.html` 由 `node prototype/build-standalone.mjs` 重新生成，保持单文件原型可直接打开。
