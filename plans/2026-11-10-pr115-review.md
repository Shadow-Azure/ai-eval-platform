## 1. 一页速览

**一句话**：把“点创建”之前的所有选择先在服务端冻成一张 15 分钟后作废的“施工单”，之后只能凭这张单开工，且同一张单重复点只产生一个工程。

**一个比喻**：以前是客户在电话里把材料、工人、预算一项项念给施工队，念到一半改了材料，施工队可能按旧清单开工；现在先出一张盖章的施工单（preparation），单上写死材料版本、工人、预算和工期，施工队只认这张单。单过期或材料变了，必须重新开单；同一张单重复递过来只算一次。

|---|---|---|
| 准备快照 | `eval_preparation` + `POST /prepare` 返回 `preparation_id / expires_at / snapshot_digest / cost_estimate` | pytest + 浏览器 |
| 幂等创建 | `POST /evaluations` 接受 `preparation_id` + `Idempotency-Key`，重放 200 同一 run | pytest + 浏览器 |

## 2. 架构导览

### 2.1 快照层：为什么新增一张表而不是塞进 eval_run

`EvalPreparation`（`backend/app/models/evaluation.py:323`）只存四件事：谁创建、什么时候过期、冻结了什么（`snapshot_json`）、这份冻结内容的身份摘要（`snapshot_digest`）。`status` 被约束为 `active / consumed / expired`（`backend/app/models/evaluation.py:355`），过期与已消费的行保留下来用于审计，不删除。

> 为什么不在创建时现算：准备快照的价值是“确认页看到的 = 最终创建的”。如果创建时重新读库，运营确认的 commit 与最终 run 之间就有窗口；把身份摘要一起存下来，创建时重算并比对，才能把“配置变了”变成一个明确的 409，而不是静默换输入。

### 2.2 服务层：prepare 冻结、consume 校验

`build_preparation`（`backend/app/services/preparations.py:467`）先跑既有 preflight，再解析用例子集，生成展示摘要、成本区间与 `identity`；`identity` 覆盖数据集状态/用例数/镜像 digest、资产 commit/tree digest、模型名/端点/凭据与撤销时间、池状态、Runtime 适配器版本、执行策略与最终镜像 digest（`_live_identity`，`:317`）。

`consume_preparation`（`:689`）按顺序：

1. 不存在 / 非本人 → 404 `preparation_not_found`；
2. 已消费：同 `Idempotency-Key` 返回原 run（200），否则 409 `preparation_consumed`；
3. 超过 `expires_at` → 标记 `expired` 并 409 `preparation_expired`；
4. 重算身份摘要，不一致 → 409 `configuration_changed` 并返回差异字段；
5. 重新解析用例子集并比对 digest，再跑一次 preflight；
6. 用冻结值创建 run，最后把 preparation 标记 `consumed` 并指向 run。

> 身份的边界很关键：它包含“会改变结果语义”的东西（commit、模型凭据、镜像、执行策略），不包含“只影响排队”的东西（在线 Runner 数、池实时容量）。容量变化走 preflight 的 blocker/warning，而不是把确认页判成“配置变了”。这是刻意的取舍，见 §6 讨论点 2。

### 2.3 API 层：错误码是产品契约

`prepare_evaluation`（`backend/app/api/evaluations.py:181`）把用例选择、执行策略与镜像覆盖归一化后交给服务层；`create_evaluation`（`:276`）优先处理 `preparation_id`，没有 `Idempotency-Key` 直接 422 `idempotency_key_required`，服务层异常经 `_preparation_http_error`（`:244`）映射为稳定错误码。`capacity_invalid` 与 `preparation_blocked` 的区分由 blocker 字段决定（并发/超时/重试/分片 → 容量类，其余 → 一致性阻塞）。

### 2.4 前端：状态机与草稿

`EvalWizardPage` 用一个 `WizardDraft` 对象承载非敏感字段（`web/src/pages/EvalWizardPage.tsx:66`），`readDraft/saveDraft`（`:124` / `:167`）读写 localStorage；任何影响冻结输入的 `update` 都会清掉 `preparation` 与 blockers（`:270`），从而保证“改了就得重新准备”。

四个步骤是纯渲染函数：`renderDatasetStep`（`:845`）、`renderAssetsStep`（`:985`）、`renderPolicyStep`（`:1193`）、`renderConfirmStep`（`:1370`）；`runPrepare`（`:667`）负责调用 prepare 并在 ready 时进入第 4 步。

## 3. 数据流走查（一条主线）

1. 用户在 `/evals/new` 选数据集版本与“按数量 5”，草稿写入 localStorage。
2. 第 2 步把已冻结的资产快照（15 个 Skill、commit `22f0b463…`）带入，`asset_snapshot_id` 是后续 prepare 的输入。
3. 第 3 步配置并发 2、超时 30 分钟、重试 1 次、预算 $10，点击“准备并检查”。
4. `POST /prepare`：preflight 计算有效并发 2、镜像 digest、容量警告；服务层解析 5 个 case_key，写 `eval_preparation`（TTL 900s，冒烟环境 60s），返回摘要与 `snapshot_digest`。
5. 确认页展示快照；点击“创建评测”发送 `{preparation_id}` + `Idempotency-Key`。
6. `consume_preparation` 重算身份摘要、重跑 preflight，`create_synthetic_evaluation` 写入 run/case/attempt/outbox，准备快照置为 consumed。
7. 详情页可读 `consistency.preparation_id`、`case_timeout_seconds=1800`、`max_attempts=3`，证明 run 与确认页一致。

## 6. 讨论点

### 6.1 “按数量”取前 N 个，而不是随机抽样

- **位置**：`backend/app/services/preparations.py:175` `resolve_case_keys`
- **现象**：`count` 模式按 `ordinal` 取前 N 个用例；原型文案写的是“随机抽取 100 个用例”。
- **问题**：前 N 个结果可复现、可预期，但可能长期只覆盖数据集开头；随机抽样覆盖更均匀，但同一配置重复准备会得到不同子集，除非把种子也冻进快照。
- **预判**：当前实现把“可复现”放在第一位，且确认页会展示实际用例数；若产品需要随机覆盖，建议新增 `mode: sample` + 可选 `seed`，而不是改 `count` 的语义。
- **结论**：（待拍板）

### 6.2 配置身份不含实时容量

- **位置**：`backend/app/services/preparations.py:317` `_live_identity`
- **现象**：在线 Runner 数、池实时容量变化不会让 preparation 失效；只有池 `status` 变化会。
- **问题**：确认页的“3 在线 / 8 上限”可能在创建时已经变化，用户看到的是旧容量。
- **预判**：容量是“排队提示”而不是“输入身份”，把它纳入摘要会让任何 Runner 心跳都使确认页失效，体验更差；容量下降由 create 时的 preflight 重新评估并给出 warning/blocker。
- **结论**：（待拍板）

### 6.3 过期行保留策略

- **位置**：`backend/migrations/versions/0017_eval_preparations.py`
- **现象**：`expired` / `consumed` 行永久保留，没有清理任务。
- **问题**：长期运行会积累快照 JSON（含资产清单与摘要），单行几 KB 到几十 KB。
- **预判**：当前量级可接受，且审计需要；后续可加“保留 N 天”的清理 worker，与 outbox 的保留策略一起设计。
- **结论**：（待拍板）

### 6.4 向导页面仍是单文件

- **位置**：`web/src/pages/EvalWizardPage.tsx`
- **现象**：约 1500 行，包含 4 个步骤、摘要与草稿逻辑。
- **问题**：可读性尚可（步骤是清晰的纯渲染函数），但后续再加“临时模型/通知”等步骤会继续膨胀。
- **预判**：与设计 §5.1 的组件边界一致，下一步可按 `LaunchStepper / DatasetStep / AgentAssetsStep / ModelResourceStep / LaunchSummary` 拆分，不影响本次契约。
- **结论**：（待拍板）

### 6.5 直接创建路径的 `case_keys` 语义变化

- **位置**：`backend/app/services/evaluations.py:221`
- **现象**：带 `dataset_version_id` 的直接创建现在会把 `case_keys` 当作子集过滤；旧实现忽略该字段。
- **问题**：若有旧客户端在数据集创建时误传 `case_keys`，行为从“忽略”变成“取子集”。
- **预判**：当前只有本仓库前端调用，且新向导走 preparation 路径；保留该行为可以让直接创建也支持子集，且非法 key 会明确 422。建议在发布说明中标注。
- **结论**：（待拍板）

## 9. 文件级代码分析

### 9.1 `backend/app/models/evaluation.py`（M）

- **职责**：评测域 ORM 模型；本次新增 `EvalPreparation`。
- **变更块**：`EvalPreparation`（`:323`）使用 `tenant_id + id` 唯一约束、`status` 检查约束、复合外键到 `eval_run`（`RESTRICT`）。快照 JSON 用项目的 `json_type()`，PostgreSQL 下是 JSONB、SQLite 下是 JSON，与既有表一致。
- **实现思路**：不把准备态放进 `eval_run`，避免一个“还没创建”的对象占用评测主表；用 `consumed_eval_run_id` 把快照与最终 run 关联，审计可回查。

### 9.2 `backend/migrations/versions/0017_eval_preparations.py`（A）

- **职责**：建表与索引，可回滚。
- **变更块**：`upgrade()` 建表 + `ix_eval_preparation_actor_status`（按人查活跃快照）+ `ix_eval_preparation_expiry`（按状态/过期扫描）；`downgrade()` 逆序删除。
- **实现思路**：沿用既有迁移风格（显式列、`sa.JSON()`、server_default），避免 `autogenerate` 在 SQLite/PG 之间的差异。

### 9.3 `backend/app/services/preparations.py`（A）

- **职责**：准备快照的冻结、身份摘要、消费与成本估算。
- **关键块**：
  - `resolve_case_keys`（`:175`）：三种模式，显式 key 必须属于该版本，按 ordinal 保持稳定顺序。
  - `estimate_cost`（`:226`）：按配置的 token/时长假设与模型 pricing 生成区间；pricing 缺失时返回 `None`，不编造数字。
  - `_live_identity`（`:317`）：从 LIVE 行重建身份；`_diff`（`:437`）产生 `asset_snapshot.resolved_commit` 这类可读差异路径。
  - `build_preparation`（`:467`）：先 preflight 再用例解析，阻塞时返回 `preparation_id: null`，仍给出 blockers 供页面展示。
  - `consume_preparation`（`:689`）：状态机、幂等重放、配置漂移、二次 preflight、创建与消费标记。
- **实现思路**：prepare 与 create 共用同一套身份摘要函数，保证“冻结”与“校验”不是两套逻辑。已知弱点：并发创建同一准备快照时依赖 `eval_run` 的幂等唯一约束，极端竞争下可能出现 IntegrityError（与既有创建路径相同），未在本 PR 扩大处理。

### 9.4 `backend/app/api/evaluations.py`（M）

- **前身**：prepare 只做一致性检查并返回 `status/ready/blockers`；create 直接吃整包配置，`idempotency_key` 在 body 里可选。
- **变更块**：
  - `CaseSelectionRequest` / `ExecutionPolicyRequest`（`:94` / `:102`）；
  - `prepare_evaluation`（`:181`）归一化 `execution` 并调用服务层；
  - `_preparation_http_error`（`:244`）：blocked 中带容量字段 → `capacity_invalid`，其余 → `preparation_blocked`，并把 fields/blockers 放进 `details`；
  - `create_evaluation`（`:276`）：`Idempotency-Key` 头优先，preparation 路径先行，保留旧直接创建路径。
- **实现思路**：错误码是前端回退逻辑的输入，因此映射集中在 API 层，服务层只抛带语义的异常。

### 9.5 `backend/app/services/preflight.py`（M）

- **职责**：一致性检查；本次新增执行策略与池上限校验。
- **变更块**：超时/重试/预算 blocker（`:145` 起）、`capacity_invalid`（请求并发 > 池 `max_capacity`）。有效并发仍用 `capacity.combine_effective_concurrency`。
- **实现思路**：策略越界是“字段错误”，容量越界是“容量错误”，但都进入 blockers，create 时由 API 层映射到不同错误码。

### 9.6 `backend/app/services/evaluations.py`（M）

- **职责**：评测创建与查询。
- **变更块**：`create_synthetic_evaluation` 新增 `selected_case_keys`、`case_timeout_seconds`、`max_attempts`；数据集分支先取全部再按 key 过滤并校验；`evaluation_summary` 暴露执行策略，`evaluation_detail` 暴露 `consistency`。
