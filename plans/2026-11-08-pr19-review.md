## §2 架构导览

### 2.1 应用装配

`backend/app/main.py:11` 的 `create_app()` 只做三件事：读配置、装 CORS、挂 health/overview 两个 router。M2-01 不引入应用服务层，是因为当前只有只读聚合接口；M2-03/M2-05 接入派发与回调时再引入 `application/`，避免现在造空壳。

### 2.2 数据模型

`backend/app/models/evaluation.py:64` 的 `EvalRun` 是评测事实的根：`idempotency_key` 由 `(tenant_id, created_by, idempotency_key)` 唯一约束（`:97`），保证同一用户重复提交不会产生第二个 run。子表 `EvalCaseRun` 与 `EvalCaseAttempt` 都用 `(tenant_id, parent_id)` 复合外键（`:104`、`:155` 附近），让“跨租户引用”在数据库层直接失败，而不是只靠查询条件。

`EvalCaseAttempt` 的 `(eval_case_run_id, attempt_no)` 唯一约束和 `(tenant_id, dispatch_key)` 唯一约束分别承担“重试不覆盖旧 attempt”和“重复派发不启动第二执行”的底线；这两个约束是 M2-03/M2-05 的契约基础，不是可选的索引优化。

### 2.3 默认作用域

`backend/app/seed.py:23` 的 `ensure_default_scope()` 先按 slug 查，再按固定 ID 创建，最后 `commit`；重复调用返回同一组 ID。迁移里也写入了同一组固定 ID（`backend/migrations/versions/1a795994c4e9_initial_schema.py` 的 upgrade 末尾），所以“空库迁移”和“应用启动 seed”两条路径不会互相打架。

### 2.4 健康与总览

`backend/app/api/health.py` 的 `/healthz` 不碰数据库，适合做 liveness；`/readyz` 执行 `SELECT 1`，配置了 `REDIS_URL` 才 ping Redis。`backend/app/api/overview.py:14` 只读默认租户下的计数，返回值刻意保持扁平（tenant/project/counts/status），让 Web 在 M2-01 不需要引入图表或指标定义。

### 2.5 Web 壳

`web/src/app/theme.ts` 把原型的 `#1677ff / #1f2937 / #f2f5fa / 10px` 映射到 AntD token；`web/src/pages/OverviewPage.tsx` 用 TanStack Query 取 `/api/v1/overview` 与 `/readyz`，API 失败时渲染带重试的 `QueryError`，刷新失败时保留旧数据并给出提示。这里没有把“失败”伪装成“空数据”，是 M2 后续排障需要的产品行为。

## §3 数据流走查

1. `docker compose up` → postgres/redis/minio 健康 → `minio-init` 创建 bucket → `api` 启动。
2. `backend/docker-entrypoint.sh` 执行 `alembic upgrade head`，再 `python -m app.seed`，最后启动 uvicorn。
3. 浏览器打开 `/overview` → Vite/Nginx 代理 `/api/v1/overview` → FastAPI 读默认 tenant/project → 返回计数 → 页面渲染状态卡与空态表。
4. Worker 启动后每 5 秒写心跳文件并打印 pending outbox 数量；Compose healthcheck 以文件 mtime 判断存活。
5. 任何一步失败：迁移失败阻断 API 启动；API `/readyz` 失败使 Worker/Web 不启动；Web 显示“控制面未连接”而不是白屏。

## §6 讨论点

### 6.1 Compose 未在本机实际启动

- **位置**：`docker-compose.yml`
- **现象**：本机没有可用的 Docker daemon；只做了 YAML 校验。
- **问题**：MinIO 健康检查依赖镜像内 `curl`，如果未来镜像变体会不会误判？
- **预判**：当前用官方镜像，Dockerfile 已确认包含 `curl`；但首次在 CI/部署机运行前不能算“已证明”。
- **结论**：保留为 M2-01 的已知限制；M2-02 接入 CI 后必须在 CI 里跑 `docker compose config` 与一次真实 up/health。

### 6.2 后端测试默认 SQLite

- **位置**：`tests/backend/conftest.py`
- **现象**：默认 SQLite 让本地无 Postgres 也能跑；Postgres 通过 `TEST_DATABASE_URL` 显式启用。
- **问题**：SQLite 的 `CHECK`/外键行为与 Postgres 不完全一致，是否会造成“假绿”？
- **预判**：约束测试在 SQLite 上启用了 `PRAGMA foreign_keys=ON`，且同一套测试在 Postgres 上已跑通；生产方言的关键差异（JSONB、时间类型）由 `alembic check` 覆盖。
- **结论**：可接受；M2-02 的 CI 固定跑 Postgres 测试作为最终裁决。

### 6.3 Web 证据的基线是原型而不是旧实现

- **位置**：`web/screenshots/`
- **现象**：本 PR 之前仓库没有可运行的 Web 应用，因此“Before”是 M1-02 原型，不是上一版生产实现。
- **问题**：这是否满足“Before/After”要求？
- **预判**：原型是既定的 UI 基线，且已在 PR 描述中明确标注；没有把原型伪装成旧生产实现。
- **结论**：保留并明确限制；如果 Reviewer 要求真实旧实现截图，需要等 Web 首次上线后才有。

### 6.4 PR 未关联 Project 导致 flow-online 失败

- **位置**：GitHub PR #19 侧栏
- **现象**：`flow-online` 报“PR 未关联 project”。
- **问题**：代码/流程门禁都通过，只有项目看板关联失败。
- **预判**：这是权限/项目配置问题，不是代码缺陷；需要人工把 PR 加入 M2 Project，或在 Project 开启 Auto-add（is:pr）。
- **结论**：等待人工处理后重跑；不放宽 CI 门禁。

## §9 文件级代码分析（分组）

### 9.1 `backend/app/models/*.py`

职责：把设计 05 的核心表落成 SQLAlchemy 2 映射。变更形态为 A。关键依赖是 SQLAlchemy 2.0 的 `Mapped`/`mapped_column`，`JSON().with_variant(JSONB, "postgresql")` 让生产用 JSONB、测试用 JSON。实现思路三行：父表保留 `UNIQUE(tenant_id, id)`；子表用复合外键引用；幂等键用唯一约束而不是应用层查重。

检视发现：初版漏了 attempt 到 runner/resource_pool、event 到 case_run、instance 到 runner 的复合外键，已在本 PR 补齐。保留的弱点：`eval_case_run.dataset_case_id` 还没有 dataset_case 表可引用（M3 数据集接入时补），当前用字符串 ID 保持 M2 可运行。

### 9.2 `backend/migrations/versions/1a795994c4e9_initial_schema.py`

职责：空库一次建全表、索引、CHECK、复合外键，并插入默认作用域。A。关键依赖 Alembic autogenerate + 手工 seed；升级/降级均可逆。实现思路：`upgrade` 建表后 `op.bulk_insert` 三条默认记录；`downgrade` 按依赖逆序 drop。

检视发现：第一版在 SQLite 上因 `now()` 失败，改成 `CURRENT_TIMESTAMP` 后两库都通过；`alembic check` 无漂移。

### 9.3 `docker-compose.yml` + `backend/Dockerfile` + `web/Dockerfile`

职责：本地一条命令拉起 6 个服务。A。关键依赖官方 postgres/redis/minio 镜像、Python 3.12、Node 22、Nginx 1.27。实现思路：健康检查决定启动顺序；MinIO 初始化用一次性 `mc` 容器；API 入口先迁移再 seed 再 uvicorn。

检视发现：`minio/minio:latest` 未固定 tag，是可复现性弱点；当前保持 latest 以跟随官方镜像，M2-02 固化版本。Compose 未本机运行，见 §6.1。

### 9.4 `web/src/pages/OverviewPage.tsx`

职责：总览页，读真实 API，展示状态卡、运行概况、系统健康与空态表。A。关键依赖 AntD Table/Button/Skeleton、TanStack Query 5、React Router 6。实现思路：查询失败分两种——无数据时整块错误 + 重试；有旧数据时保留旧数据 + 警告条。

检视发现：初版 `/readyz` 查询因 TanStack Query v5 拒绝 `undefined` 返回而报错，已改为返回 `{ok:true}`；`data.project` 可能为 null，已做 fallback。保留的弱点：最近评测表固定空数组，M2-05 接入 API 后替换。

### 9.5 `tests/backend/*`

职责：迁移、默认作用域、约束、健康/总览。A。关键依赖 pytest + FastAPI TestClient + Alembic CLI。实现思路：每个测试用独立 SQLite 文件或重建 Postgres `public` schema；通过 `TEST_DATABASE_URL` 切换方言。

检视发现：Postgres 测试曾因残留旧 revision 报 “Can't locate revision”，已改为重建 schema；`TEST_DATABASE_URL` 现在要求 URL 含 `test`，避免误删非测试库。
