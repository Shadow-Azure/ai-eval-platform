## §1 一页速览

一句话：把“每次重选四步向导”变成“一次保存、以后按 ID 启动”，同时给外部脚本三个稳定读接口。

比喻：模板像咖啡机的“常用配方”按钮——只记住豆子、水量、研磨度（选择），每次按下才真正磨豆、出水（启动），所以改了配方不会倒流影响已经做好的那杯。

| 交付块 | 结果 |
|---|---|
| 数据模型 | `eval_template` + `eval_run.template_id/version/snapshot` |
| 三个执行接口 | launch 202、status 轮询、results 终态 `is_final` |
| 管理接口 | 列表搜索/筛选/分页、CRUD、启停 |
| 前端 | 列表/详情/快速启动/向导保存/来源横幅 |
| 验证 | 后端 pytest 全绿、117 node tests、docs/flow 门禁、web build、Playwright 冒烟 |

验证基线：SQLite（本地）与 Postgres DDL 离线渲染；Postgres 实跑由 CI 覆盖。

## §2 架构导览

### 2.1 数据层

`EvalTemplate`（`backend/app/models/evaluation.py:418`）只存引用和选择：数据集版本、Runtime、资产源/Ref/路径、模型、资源池、用例范围、执行策略、提示词、轮次、超时、启用状态、版本与最近启动。引用刻意不建数据库外键：被引用对象由各自域删除，模板启动时再校验并返回显式 422，而不是把外键错误泄露成 500。

`EvalRun`（`backend/app/models/evaluation.py:154` 起）新增 `template_id`、`template_version`、`template_snapshot_json`。启动后的 run 保留来源，模板后续编辑不回溯。

迁移 `0032_eval_template` 在 Postgres 上创建 JSONB 列与索引；`template_snapshot_json` 的 `DEFAULT '{}'` 对 JSONB 合法。SQLite up/down/up 与 Postgres 离线 DDL 都实测过。

### 2.2 服务层

模板服务 `backend/app/services/eval_templates.py` 分三段：

1. 校验与规范化（`_validate_fields`，:291）：名称、数据集版本、模型、资源池、资产源/Ref、用例范围、执行策略、轮次与超时。这里的错误全部是 `TemplateInvalid`（422）并带 `details.fields`，前端可以用字段级错误。
2. 读模型（`template_view`，:578）：把 ORM 引用展开成列表/详情需要的展示字段，并按模型定价与用例数计算费用估算。列表还附带最近一次运行，供“最近启动”列使用。
3. 启动编排（`launch_template`，:783）：见 §3。

错误类自带 HTTP 语义（`TemplateNotFound` 404、`TemplateDisabled`/`TemplateConflict`/`TemplateInUse` 409、`TemplateInvalid` 422），路由层只做一次 `_http_error` 翻译。

### 2.3 API 层

`backend/app/api/eval_templates.py` 暴露 6 个管理端点与 launch。列表/详情用 `require_session` 只读；写操作与 launch 用 `require_admin`。`_update_payload` 只把 PATCH 请求实际出现的字段交给服务层，避免“未传字段被清空”。

三个执行接口中的 status/results 在 `backend/app/api/results.py`：status 是轻量轮询读模型（:244），results 复用既有指标接口并增加终态判定（:175）。

### 2.4 前端

模板列表（`EvalTemplatesPage.tsx:32`）以服务端分页为主体，`q`/`status`/`page`/`pageSize` 全部进 query key；空态保留“清除筛选”。详情页（`EvalTemplateDetailPage.tsx:49`）把固定配置、执行策略、最近运行与接口示例分成三块，右侧是启动概览与接口。启动确认（`TemplateLaunchModal.tsx:29`）只展示固定组合、费用与警告。向导第 4 步（`EvalWizardPage.tsx:2423`）新增保存开关；`?mode=template` 复用同一四步向导但只保存不启动。

## §3 数据流走查：一键启动

1. 用户在列表或快速启动点“启动” → `TemplateLaunchModal` 打开，展示 `template_view` 已算好的固定组合与费用。
2. 确认 → `launchEvalTemplate` POST `/api/v1/eval-templates/{id}/launch`，带 `Idempotency-Key`。
3. 服务端 `launch_template` 先按 `(tenant, created_by, idempotency_key)` 找已有 run：同模板直接返回原 run（202），不同模板返回 409。**这一步在 enabled 检查之前**，所以停用后的重试仍是幂等重放。
4. 模板启用 → `_resolve_template_assets` 重新解析资产 Ref（无资产源则跳过），得到新的资产快照。
5. `build_preparation` 复用既有 prepare：校验数据集/模型/资源池/容量/镜像，冻结 `EvalPreparation`。
6. `consume_preparation` 复用既有 create：生成 `eval_run`、case/attempt、分片 outbox 与 `eval.created` 事件。
7. 服务端回写 `run.template_id`、`template_version`、`template_snapshot_json`，并更新模板 `launch_count`/`last_launched_at`。
8. 返回 `run_id`、`status`、`status_url`、`result_url`；前端跳转 `/evals/{run_id}`，详情页通过 `template` 字段显示来源横幅。
9. 轮询方随后 GET status；终态后再 GET results，`is_final` 在终态为 true。

## §6 讨论点

### D1 幂等重放与“停用模板”谁优先

- 位置：`backend/app/services/eval_templates.py:806`
- 现象：初版先检查 `enabled` 再查重放；模板停用后客户端重试同一幂等键会得到 409，而不是原来的 run。
- 问题：网络重试语义被管理操作破坏；客户端可能误以为启动失败并更换新键，产生重复 run。
- 预判：重放应优先，停用只拦截“新启动”。
- 结论：已修复并加测试（2026-11-22）。

### D2 向导“启动并保存模板”的重试会重复建模板

- 位置：`web/src/pages/EvalWizardPage.tsx:695`
- 现象：初版在 create mutation 里先保存模板；若保存成功但创建 run 失败，`templateSavedRef` 在错误分支被清空，用户重试会再保存一次模板。
- 问题：重复模板污染列表，且用户无法区分。
- 预判：保存成功事实应跨重试保留；只有草稿配置变化（重新准备）才重置。
- 结论：已修复（2026-11-22）。

### D3 启动弹层的幂等键按点击生成

- 位置：`web/src/components/TemplateLaunchModal.tsx:29`
- 现象：初版每次点击都用 `crypto.randomUUID()` 生成新键；响应丢失后人工重试会创建第二个 run。
- 问题：幂等键没有覆盖“同一次启动意图”。
- 预判：同一模板弹层内的重试应复用同一个键，成功后清空。
- 结论：已修复（2026-11-22）。

### D4 列表读模型的 N+1 查询

- 位置：`backend/app/services/eval_templates.py:522`
- 现象：列表页每行 `template_view` 会再查数据集/版本/模型/资源池/资产源与最近 run；100 条上限时约数百次查询。
- 问题：模板数量进一步增长时列表延迟会放大。
- 预判：首期 10/20/50 条/页可接受；后续可在列表查询里一次 join 出展示字段，并用窗口函数批量取最近一次 run。
- 结论：暂不修改，记录为后续优化；详见 §7。

### D5 模板删除只有后端、没有前端入口

- 位置：`backend/app/api/eval_templates.py:204`
- 现象：后端提供受保护删除（有 run 时 409），前端只提供停用/启用。
- 问题：与设计文档“创建、编辑、停用和删除”的生命周期表述不完全对齐。
- 预判：停用已覆盖日常生命周期；删除是低优先级管理动作，避免误删历史来源更稳妥。
- 结论：接受当前范围，记录为后续产品决定；不是本 PR 的阻塞项。

## §9 文件级实现思路

### `backend/app/services/eval_templates.py`

职责：模板 CRUD、读模型与启动编排。启动没有另写一套创建逻辑，而是先 `build_preparation` 再 `consume_preparation`，这是本 PR 最重要的取舍：复用带来的是一致性（容量、预算、镜像、权限都走同一门禁），代价是 launch 路径较长、错误需要从准备层映射回模板层。`_preparation_error` 保留原 HTTP 状态与错误码，把 `ImageNotReady` 映射为 409、把准备阻塞映射为 422，避免把既有 409 变成 500。

### `backend/app/api/eval_templates.py`

职责：HTTP 契约与权限。列表/详情只读，写与 launch 管理员。错误统一用 `error_detail` 包络；PATCH 只提交实际出现的字段。

### `backend/migrations/versions/0032_eval_template.py`

职责：一次性加表与加列。引用不建外键是刻意的：模板保存的是“选择”，被引用对象可能被各自域删除；启动时校验比外键更可控。索引覆盖租户+启用+最近启动，对应列表默认排序。

### `web/src/pages/EvalTemplatesPage.tsx`

职责：服务端分页列表与行内动作。分页、搜索、状态都进 query key；空态保留“清除筛选”；启动按钮对停用模板与非管理员禁用。

### `web/src/pages/EvalTemplateDetailPage.tsx`

职责：固定配置与执行策略的只读展示，最近运行与接口示例。404 用 `ApiError.status` 判断，不靠错误文案匹配。

### `web/src/pages/EvalWizardPage.tsx`

职责：在不复制四步向导的前提下，增加“保存模板”分支。`buildTemplatePayload` 从同一份 draft 生成模板请求；`templateSavedRef` 保证一次启动意图只保存一次模板。

### `web/src/components/TemplateLaunchModal.tsx`

职责：只确认费用与容量，不提供字段覆盖。幂等键按模板意图缓存，成功或切换模板后重置。

### `web/src/api/evalTemplates.ts`

职责：把控制台返回的 JSON 防御式解析为前端类型；`estimated_cost` 等可选字段缺失时降级为 `null`，不让整页报错。
