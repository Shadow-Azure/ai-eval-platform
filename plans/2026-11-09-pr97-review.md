## §1 一页速览

**一句话**：把"一个 shard 一个 Job 顺序跑 64 个用例"拆成"一个 shard 先 prepare 成 64 个单用例 matrix Job"，并在平台侧加两道闸——调度器只按 `ceil(有效并发/分片大小)` 放行分片，`started` 回调再按用例数硬卡一次；超过上限的 Job 收到 429 后原地等候补位，而不是失败或重复建 attempt。

**比喻**：这是一家剧院。`requested_concurrency` 是"本场演出允许同时上台的演员数"；`effective_concurrency` 是"你想要的、剧场现有工作人员、剧场座位上限"三者取小。调度器是**团体检票口**：一次只放一个 64 人的旅行团进场（`ceil(cap/64)` 个团），团里所有人散场才放下一团；`started` 429 是**后台口数人头的场务**：团进多了，多出来的人请回候场区，不记工、不发演出记录，每 5 秒再来问一次；本地 claim 是**一次性手环**，同一个用例在同一台机器上重放会被手环挡住。

## §2 架构导览

### 2.1 有效并发：三个数字取小，缺数据时"不设限"而不是"归零"

`capacity.effective_concurrency`（`backend/app/services/capacity.py:94-118`）是纯读：`requested_concurrency`、池内"online/busy 且心跳新鲜"的 Runner 数（`:68-91`）、池上限（`:52-65`）。公式在 `combine_effective_concurrency`（`:40-49`）里被 dispatcher、preflight、started 三处共用——同一个公式三处复用，避免"预检说 8、调度说 1"的经典漂移。

两个刻意的例外：

- **没有资源池的评测不设闸**（`:109-110` 直接返回 requested）。M2 合成评测与 M3 之前的数据没有 `resource_pool_id`，若按 0 处理会把历史路径全部卡死；这类评测继续由 GitHub 队列限流，真实上限是 Runner 数。
- **池不存在/非 active 时返回 0**（`:112-113`）。语义是"平台明确知道这个池不可用"，与"没数据"区分开：前者让调度器停派，后者让 started fail-open（§2.3）。

池上限暂时读 `labels_json["max_capacity"]`（`:60-65`），因为 `ResourcePool` 模型目前确实没有 `max_capacity` 列（`backend/app/models/resources.py:18-42`），设计 05 §5 里的那一列属 M4-03。代价是：**标签写成字符串 `"8"` 会被当成"无上限"**（`isinstance(raw, int)` 不通过 → `None`），这类静默降级在语义上很危险，见 §6.6。

### 2.2 两级闸门：分片级"粗放行"，用例级"精计数"

**第一级在调度器**（`backend/app/services/dispatcher.py:40-71`、`:102-129`）。一个 shard 的 manifest 就是 `shard_size` 个用例，全放出去最多同时占 `shard_size` 个 Job，所以"允许在飞的分片数"= `ceil(cap / shard_size)`（`:68`）。已放行的分片用 attempt 状态反推：只要该分片还有 `dispatching/queued/leased/running/scoring/uploading` 的 attempt，就算在飞（`capacity.py:30-37`）。没有容量就把 outbox 行的 `available_at` 推后 10 秒、写 `queue_reason`，下一轮再看（`dispatcher.py:117-125`）；**不碰 attempts、不建新行**，所以排队不会复制 attempt（`test_capacity_scheduling.py:233-247` 钉住）。

以 500 用例、shard 64、cap 8 为例：8 个分片、`ceil(8/64)=1`，所以 shard_000 先走，等它的 64 个 attempt 全部终态，才放 shard_001。**这是本 PR 最重要的行为变化**——分片从"同时派发、GitHub 排队"变成"平台串行放行"，也是 §6.1 那个 P1 的温床。

**第二级在 `started` 回调**（`backend/app/services/case_attempts.py:196-242`）。分片级只能保证"最多一个 64 Job 的团在飞"，团里真正同时跑几个用例仍可能超过 cap（cap=8 时 64 个 Job 里只有 8 个该跑）。所以 `started` 在推进 attempt 之前数一遍"别的用例里 `execution_status == running` 的数量"（`:222-233`），`running >= cap` 就返回 429（`:234-241`），attempt 保持 queued、不写事件、不改 attempt——把"拒绝"做成**零副作用**，Runner 才能用同一个 `event_id` 安全重试。

并发下这是典型 check-then-act：两个 Runner 同时数到 `running=cap-1`，会双双放行。修复在 `:212-218`：先把 `effective_concurrency` 写入并 `flush()`，Postgres 上拿 eval_run 行锁、SQLite 上拿库写锁，把同一评测的 started 串行化。这个缺陷不是纸面推演——冒烟首轮真的采到 `running=3/4`（`reports/2026-11-09/m4-01-concurrency/report-data.json:166-180`），修复后才恒为 2（commit `cd32c7b`）。

**cap==0 的 fail-open**（`:219-221`）值得单独记住：池不可用/心跳全过期时，已经在跑的 Job 仍被放行，只把 `queue_reason` 标成 `capacity_waiting`。理由写在 docstring 里——此时拒绝可能把活着的 Job 卡死，而 Runner 表本身已经不可信；停新分片的职责交给第一级闸门。代价是"平台显示排队中，实际却在跑"，见 §6.7。

### 2.3 Runner 侧：prepare 只读，execute 单用例，claim 管本机

`plan-cases.mjs`（`runner/scripts/plan-cases.mjs`）是 prepare 入口：校验 dispatch（`:53-56`）、拉 manifest 并比对 digest（`:58-61`）、逐字段核对 manifest 与 dispatch 一致（`:72-74`），最后只把 `case_run_id` 映射成 `[{id}]` 单行 JSON（`:78`）。它**不 claim、不写平台、不落任何状态**（`:43-44` 注释，`tests/runner/plan-cases.test.mjs:44-46` 断言 stateDir 都没创建）——prepare 是纯函数，失败重跑无副作用。

`real-task.mjs` 的 `--case`（`:412`）把 claim key 从 `dispatch_key` 改成 `dispatch_key:case_run_id`，所以同一个 state dir 里 64 个用例可以并行 claim（`tests/runner/case-entry.test.mjs:113-134` 用两个进程验证）。claim 的实现仍是 `mkdir` 原子性（`runner/lib/dispatch-guard.mjs:15-29`），平台 DB 唯一约束才是跨机底线。

429 等待是 `postStartedWithCapacityWait`（`real-task.mjs:72-90`）：`retryOn429=false` 把 429 从 callback-client 的毫秒级重试里摘出来（`runner/lib/callback-client.mjs:42`），改用 5s→10s→…→60s 的退避，直到 `RUNNER_CAPACITY_WAIT_SECONDS`（默认 1800s，`:57-62`）耗尽。耗尽后 `fail(..., "callback_retryable", 1)`（`:488-496`），`fail` 在退出前释放 claim（`:43-51`），attempt 保持 queued、不误发 failed——这个取舍在 `tests/runner/case-entry.test.mjs:143-155` 有断言。

### 2.4 workflow：prepare 出 matrix，execute 一个 Job 一个用例

`.github/workflows/eval-shard.yml` 里 `prepare`（`:71-96`）只做两件事：落 dispatch、跑 `plan-cases`，把结果写进 `$GITHUB_OUTPUT`；`execute`（`:98-131`）用 `fromJson(needs.prepare.outputs.cases)` 展开 matrix，`fail-fast: false`（`:104`）保证一个用例失败不取消同片其他 Job，命令里带 `--case "${{ matrix.case.id }}"`（`:129`）。

三个边界处理：

- **空数组**：`if: ... needs.prepare.outputs.cases != '[]'`（`:100`）。prepare 被跳过（workflow_dispatch）或清单为空时，execute 整体 skip，避免 `fromJson('')` 报错。这条是结构推断，没有真实 Actions 运行证据（§5）。
- **256 Job 上限**：分片上限从 256 降到 255（`backend/app/services/evaluations.py:121-124`、`api/evaluations.py:48`），加上 prepare 正好 256。500 用例按 64 切是 8 片（`test_capacity_scheduling.py:152-167`）。
- **runner.temp 隔离**：`RUNNER_STATE_DIR` 指向 `${{ runner.temp }}/eval-state`（`:123`），execute 重新落一遍 dispatch（`:110-118`），不读 prepare 的临时文件。注意这把 claim 也一并"隔离"掉了，见 §6.4。

### 2.5 数据面：三字段 + 一处迁移

`eval_run` 新增 `queue_reason`（`backend/app/models/evaluation.py:93`），与既有的 `requested_concurrency`（`:90`）、`effective_concurrency`（`:91`）组成"我要多少 / 实际多少 / 为什么停着"。迁移 0010 只加一个 nullable 列（`backend/migrations/versions/0010_eval_run_queue_reason.py:16-19`），downgrade 删列（`:22-23`）。创建时 `effective=None, queue_reason=None`（`evaluations.py:214-216`），第一次调度才写值；详情/列表响应新增三字段（`evaluations.py:430-432`），API 测试断言了默认值与透传（`test_concurrency_api.py:20-117`）。

## §3 数据流走查：一次 500 用例评测的完整剧本

1. **创建**：`POST /api/v1/evaluations` 带 `requested_concurrency=8`（不传则取 `eval_default_requested_concurrency=8`，`api/evaluations.py:98-102`）。服务端校验 1..256、shard 1..255、用例数 ≤1000（`evaluations.py:75-77`、`:119-133`），事务内写 run + 500 个 case + 500 个 attempt + 8 条 outbox（`build_shard_dispatches`，`:274-360`）。**关键点**：8 条 outbox 的 manifest 在同一时刻生成，`deadline = now + 30min`、`expires_at = now + 60min`（`:289-290`），之后不再重算。

2. **调度第一片**：worker 每 5s 跑 `dispatch_pending_outbox`（`worker/main.py:48`）。`_capacity_decision` 读到 8 个在线 Runner、cap=8、在飞 0 → 放 shard_000（`dispatcher.py:51-71`）；其余 7 条把 `available_at` 推到 +10s（`:117-121`），run 标 `concurrency_cap` 或清空。

3. **GitHub 收单**：`repository_dispatch` 带 `manifest_url + digest`，不含用例内容。GitHub 在自托管 Runner 上拉起 workflow。

4. **prepare**：runner checkout 后跑 `plan-cases`，拿到 64 个 `case_run_id`，输出 64 项 matrix（`plan-cases.mjs:78`）。此步**不 claim**，失败重试无害；但 `plan-cases.mjs:56` 会检查 `dispatch.expires_at`，第 8 片若在 60 分钟后才被放行，prepare 直接失败。

5. **execute ×64**：每个 Job 重新落 dispatch、拉 manifest（`manifest-source.mjs:13-27`），`real-task.mjs:376` 检查 `manifest.deadline`——**这是第二个过期点**，且 8 个分片的 deadline 是同一个创建时刻 +30min。

6. **started**：每个 Job 先 claim（`real-task.mjs:412-423`），再 POST started（`:483-487`）。平台数 running：前 8 个放行（`_promote_running`，`case_attempts.py:261-263`），第 9 个起 429（`:234-241`）。Runner 等 5s/10s/… 再试，直到有槽位或 1800s 预算耗尽（`:488-496`）。

7. **完成与让位**：用例 completed → case `succeeded`、attempt 终态；dispatcher 下一轮数到 shard_000 已无在飞 attempt → 放 shard_001（`dispatcher.py:56-70`）。**但 shard_001 的 manifest 还是 t0+30min 的 deadline**，此时早已过期——见 §6.1。

8. **收尾**：全部 500 个 case 终态 → `refresh_run_progress` 把 run 推到 `completed/partial`。若中途有 Job 因过期/429 耗尽退出而没回调，case 停在 queued，run 永远 running——这本该是 M4-02（#79）的对账职责，但本 PR 把"延迟放行"做成了常态，等于把这个缺口从边角推到了主路径。

**一句话总结这条剧本的断裂点**：闸门故意让分片晚点出发，但清单上的两张"车票"（deadline 30min、expires 60min）在创建时就印死了。用例越快越看不出问题（冒烟的合成用例毫秒级），真实用例只要单片总时长超过 30 分钟就会踩中。

## §6 讨论点（预判供拍板，结论留空）

### 6.1 【P1】清单的 deadline/TTL 在创建时印死，而闸门故意让分片晚出发

- **位置**：`backend/app/services/evaluations.py:289-290`（deadline/expires_at 按创建时刻算，8 个分片共用）、`:318`/`:351`（写进 manifest 与 dispatch）；`runner/scripts/real-task.mjs:376`（`manifest 已过 deadline` → 退出）、`:328`（`dispatch 已过期`）；`runner/scripts/plan-cases.mjs:56`（prepare 也查 expires）；`backend/app/config.py:83-84`（TTL 3600s / deadline 30min）、`backend/app/models/evaluation.py:110`（用例超时 3600s）。
- **现象**：一次 500 用例、shard 64、cap 8 的评测，8 个分片的 `deadline` 都是 `t0+30min`、`expires_at` 都是 `t0+60min`。但 dispatcher 的闸门让分片串行放行：shard_000 的 64 个用例按 8 并发跑 8 波，每波若 10 分钟，单片就要 80 分钟；shard_001 在 `t0+80min` 才派发，prepare 一读 `expires_at` 就失败；即便赶上 60 分钟窗口，Job 启动时 `manifest.deadline`（30 分钟）也已过期，`real-task` 直接退出、不写任何回调，64 个 case 永远 queued。取每用例 5 分钟：shard_000 的第 7、8 波（t>30min）开始就全部过期；shard_001 起在 prepare 阶段就死。**只有单片总时长 < 30 分钟（即每用例平均 < 3.75 分钟）时整条链路才成立**，而默认单用例超时是 60 分钟。
- **问题**：闸门把"分片晚出发"从例外变成常态，但 manifest 的时效仍按"创建即出发"设计（M2-05 时一个 shard 一个 Job 立即跑完，30 分钟够用）。这不是实现 bug，而是**这次改动没有同步调整的时间契约**：要么在放行时重算 deadline/expires（manifest 原文入库、digest 字节稳定是既有约束，需要设计"放行时重渲染 + 更新 outbox"），要么把 deadline 下沉为用例级、由平台按 `case_timeout_seconds` 单独判，要么显式把 `eval_shard_deadline_minutes` 提到覆盖整个 run（会无限长）。三条路各有代价，必须先拍板。
- **预判**：这是本 PR 唯一的**验收级阻断**：issue 的"500 用例 → 8 次派发"在结构上成立、在时限上不成立。建议在合入前至少把 deadline 改成"放行时刻 + 分片预算"，或先在 M4-02 的对账里补"过期分片重派"。合成用例毫秒级完成，现有测试与冒烟都覆盖不到，必须补一个"人为把 deadline 拨到过去 + 分片延迟放行"的测试。
- **结论**：

### 6.2 【P1】lease 恢复后 `dispatching` 仍被算作"在飞"，整次评测可能永久停滞

- **位置**：`backend/app/services/capacity.py:30-37`（`RELEASED_ATTEMPT_STATUSES` 含 `dispatching`）；`backend/app/services/dispatcher.py:132-148`（`recover_stuck_leases` 只把 outbox 行放回 pending，不碰 attempts）、`:202-213`（先把 attempts 置 `dispatching` 并提交，再发 HTTP）、`:56-70`（闸门按 attempt 状态数在飞分片）。
- **现象**：`dispatching` 是在 GitHub 调用**之前**写下的（`:211-213` 的提交早于 `:216` 的 `post_repository_dispatch`）。若 worker 在"提交 processing + attempts=dispatching"之后、HTTP 返回之前崩溃（滚动发布、OOM 都会），恢复逻辑只把 outbox 行改回 pending；闸门下一轮看到这个分片仍有 64 个 `dispatching` attempt，认定"已有 1 个分片在飞"，而 `max_in_flight=ceil(8/64)=1`，于是**所有 8 条 outbox 行永远被延后**。本次检视用一个 /tmp 脚本按此顺序构造（alembic 空库 + 8 Runner + 500 用例 + 手工把 outbox 置 processing、attempt 置 dispatching），连续 4 轮 `dispatch_pending_outbox` 的结果是 `dispatched=0, queued=8, recovered=1`，`queue_reason` 停在 `capacity_waiting/concurrency_cap`——没有自愈路径。
- **问题**：模块 docstring 明确承诺"worker 重启由 lease 恢复"（`dispatcher.py:9-11`），而新闸门恰好让这个承诺失效；`dispatching` 的注释说它"证明分片已释放给 GitHub"（`capacity.py:28-29`），但代码里它只是"准备发"的标记，名实不符。修法有两种：恢复 lease 时同步把该分片的非终态 attempt 重置（`dispatching → pending`），或者把 `dispatching` 从 `RELEASED_ATTEMPT_STATUSES` 里拿掉（代价是 HTTP 在途的几秒内可能多放一片，闸门本来就是粗粒度，可接受）。
- **预判**：真实概率不高（窗口是一个提交到一次 HTTP 之间），但后果是"整次评测再也不动、且看起来只是排队"，排查成本很高；属于必须修的健壮性缺陷。建议在 `recover_stuck_leases` 里按 `payload_json.shard_id/attempt` 重置 attempt，并补一条"恢复后能继续派发"的测试（现有 `test_dispatch_loop.py` 的评测没有 pool，走不到闸门，覆盖不到）。
- **结论**：

### 6.3 【P2】429 等待预算（1800s）短于默认用例超时（3600s），耗尽后没有任何自动重派

- **位置**：`runner/scripts/real-task.mjs:57-62`（默认 1800s）、`:488-496`（耗尽后 exit 1，attempt 保持 queued）；`backend/app/models/evaluation.py:110`（用例超时 3600s）；`.github/workflows/eval-shard.yml:102`（Job 总超时 60 分钟）；`backend/app/services/dispatcher.py:90-101`（只捞 `pending` 的 outbox，`sent` 的不会重派）。
- **现象**：只要"在线 Runner 数 > 有效并发"，就会有 Job 在 429 上等。等的那段时间它占着 Runner；如果排在前面的用例正常跑满（最长 60 分钟），等待的 Job 在 30 分钟时就耗尽预算退出，exit 1、claim 释放、**case 仍 queued、outbox 仍是 sent**。平台侧没有任何东西会再把它捡起来：dispatcher 只查 pending，M4-02 的超时/对账还没做。用户看到的是"Job 红了、用例排队中、评测永远 running"。
- **问题**：预算与用例超时是两个独立配置，却共享同一段时间轴；默认值 1800 vs 3600 意味着"排队等一个满时长用例"必然失败。另外 `execute` 的 60 分钟总超时也小于"30 分钟等待 + 60 分钟执行"。把等待预算简单调大只能缓解，根因是"容量等待没有被平台记账"——理想形态是 Runner 上报 `capacity_waiting` 后主动退出，由平台把该 case 放回可派发队列（M4-02 的对账/重派），而不是让 Job 原地烧 Runner。
- **预判**：这是设计上"用 Job 等待换实现简单"的必然代价，不是笔误。短期至少把默认预算改成跟随 `case_timeout_seconds`（或 2×），并在 Job 超时上加余量；中期把 capacity_waiting 变成平台可见状态 + 自动重派，放进 M4-02。当前形态在"池子大于请求并发"时是主路径（例如 16 Runner、默认并发 8），不能当边角料。
- **结论**：

### 6.4 【P2】429 拒绝发生在 Runner 绑定之后，绑定残留会让下一个 Job 静默绕过闸门

- **位置**：`backend/app/api/runners.py:364-370`（先 `bind_case`，后调 handler）、`backend/app/services/runners.py:195-209`（bind 写 `busy_case_attempt_id` 并 commit）、`:212-219`（只有 completed/failed 才 release）；`backend/app/services/case_attempts.py:234-241`（429 在 bind 之后抛出）；`runner/lib/callback-client.mjs:41`（**所有** 409 都映射成 `stale: true`）；`runner/scripts/real-task.mjs:498-505`（`stale` 被当作可继续）。
- **现象**：Job A 的 started 被 429 → API 已经把 runner 绑到 case_A 并提交 → A 等 30 分钟耗尽退出，绑定没释放。同一个 Runner 上的下一个 Job B（case_B）来 started 时，`bind_case` 发现 `busy_case_attempt_id=case_A != case_B` → 409 `runner_busy_conflict`；`postCallback` 把所有 409 都当 stale，`real-task` 认为"stale 也能继续"，于是**B 在不发 started 的情况下直接跑 Agent**，完成后 completed 把 case 从 queued 直接推成 succeeded。后果：(a) 这个用例从未计入 `execution_status == running`，**用例级硬闸对它完全失效**；(b) 平台账本里 case_B 没有 started 事件，只有 completed，审计链断裂。绑定在 B completed 时才被 release，所以每个 429 耗尽事件会"污染"紧随其后的一个 Job。
- **问题**：`bind_case` 把"回调到达"当作"Runner 确实在跑这个用例"，但 started 可能被业务拒绝；把 429 的清理责任留给"下一个终态回调"是错的。另外 409 的语义被压平了：`stale_attempt`（可以忽略）和 `runner_busy_conflict`（绝不能继续跑）在 Runner 侧无法区分。
- **预判**：这是代码阅读得出的推断，没有实测；触发前提是 §6.3 的 429 耗尽，所以和 6.3 是同一根链条。修法很轻：429 分支在抛错前 `release_case`（或把 bind 移到容量判定之后），并让 Runner 只把 `stale_attempt` 当可继续、`runner_busy_conflict` 当致命。建议至少做前者，后者顺手。
- **结论**：

### 6.5 【P2】claim 放在 `runner.temp`，跨 Job 必然失效——"重复 Job 在启动 Agent 前退出"这个验收没有真正达成

- **位置**：`.github/workflows/eval-shard.yml:110`（注释"runner.temp is per job"）、`:123`（`RUNNER_STATE_DIR: ${{ runner.temp }}/eval-state`）；`runner/workflows/eval-shard.yml:66`、`:79`；`runner/lib/dispatch-guard.mjs:15-29`（claim 是本地目录）；`tests/runner/case-entry.test.mjs:91-111`（用跨调用持久的 `ctx.stateDir` 证明重放被挡）。
- **现象**：GitHub 在每个 Job 开始和结束时清空 `runner.temp`（外部行为，仓库内无法验证）。因此"re-run failed jobs"或重复 matrix Job 拿到的是**空 claim 目录**，`duplicate_dispatch` 分支永远不会触发。测试之所以过，是因为 `scenario-helpers.mjs` 用 `mkdtemp` 建了一个跨进程持久的 stateDir，和生产的每 Job 清空不是一回事。真正兜底的是平台：started 的 event_id 是确定性的（`real-task.mjs:475`），重复 Job 会被 dedupe 成 `ok`，然后**照样把 Agent 再跑一遍**（只保证状态不回退，不保证不重复花钱）。
- **问题**：issue 验收第 3 条写的是"同一 Job 重放不产生重复执行"，PR 描述写"重复 Job 在启动 Agent 前退出"，但本地 claim 在真实 workflow 里做不到跨 Job；能做到的只有"同一次 Job 内被调用两次"这种不存在的场景。这不是测试写错，而是**机制与主张不匹配**：跨机/跨 Job 去重必须由平台提供（例如 started 返回 `already_running` 并让 Runner 立刻退出，或一个平台侧 case claim），本地文件只能防同机同 state dir。
- **预判**：状态正确性由平台幂等保住了，所以不是数据 bug，是**成本与承诺**问题：重复 Job 会重复调用模型、重复上传。建议要么把 claim 目录挪到 Runner 宿主机的持久路径（能挡同机重放，仍挡不住跨机），要么接受"平台幂等兜底"并把 PR/issue 的措辞改成"不重复写状态、可能重复执行"，并把平台侧 claim 列入 M4-02。冒烟报告 scenario 08 目前也建立在这个失真的 state dir 上。
- **结论**：

### 6.6 【P2】分片粒度与有效并发错配：cap=8 也放出 64 个 Job，低并发评测会占满整个池并饿死其他评测

- **位置**：`backend/app/services/dispatcher.py:68`（`max_in_flight = ceil(cap/shard_size)`）；`backend/app/services/capacity.py:30-37`（在飞按分片数）；`backend/app/services/case_attempts.py:234-241`（多出来的用例 429）；`runner/scripts/real-task.mjs:72-90`（等待期间 Job 一直占着 Runner）。
- **现象**：池子 16 个 Runner、评测 A 请求并发 2，`ceil(2/64)=1` → 放一个 64 Job 的 shard。GitHub 把 16 个 Job 分给 16 个 Runner：2 个真跑，14 个在 429 上打转，**这 14 个 Runner 被占着但不产出**；此时评测 B（请求 8）的 Job 只能排队。极端情况下一个 requested_concurrency=1 的评测就能让整池利用率降到 1/16，并把其他评测挡在门外。
- **问题**：设计 06 §1 的公式假设"并行 Job 数 = 有效并发"，但实现里"放行单位"仍是分片：容量闸门只控制"几片在飞"，不控制"一片里多少 Job 会落到 Runner 上"。用例级 429 保证了不超上限，代价是把 Runner 变成等待席。这个错配是 M4-01 的核心取舍（保留"一次 workflow run 一个 shard"），但在多评测共享池时会表现为公平性/利用率问题，而不是单纯的慢。
- **预判**：单评测、池子恰好等于并发时完全没问题；一旦"池 > 请求并发"或"多评测共享池"就会暴露。缓解方向：按 `min(shard_size, cap)` 切分片（平台侧或 prepare 时按 manifest 里的 cap 截断）、或者让 429 的 Job 快速退出并交还 Runner（需要平台重派，回到 §6.3）。这属于 M4-03/M4-04 的容量治理，但本 PR 至少应在文档里承认这个行为。
- **结论**：

### 6.7 【P3】`started` 的 cap==0 fail-open 与调度器的 cap==0 硬停语义相反，UI 会显示"排队中"却在跑

- **位置**：`backend/app/services/case_attempts.py:219-221`（cap≤0：标 `capacity_waiting` 后放行）；`backend/app/services/dispatcher.py:51-54`（cap≤0：拒绝放行新分片）。
- **现象**：Runner 心跳集体过期（sidecar 挂了、网络抖动、Runner 表被 sweep）时，已经派出的分片继续跑（fail-open），而调度器停止派新分片；run 详情同时呈现 `queue_reason=capacity_waiting` 和 `running_count>0`。用户读到的信息是"在排队"，实际在烧钱跑。
- **问题**：fail-open 本身有充分理由（避免把活 Job 卡死），但"把 queue_reason 写成 waiting"是误导；应该区分 `capacity_unknown`（fail-open）与 `capacity_waiting`（真在等）。另外心跳超时 90s、sidecar 间隔 30s（`infra/runner/bootstrap.sh:60` 区段），余量只有 3 倍，抖动时容易误判。
- **预判**：不影响正确性，影响可观测性与用户信任。建议 fail-open 时用独立 reason（迁移列已就绪），或干脆不写 reason 只写 effective=0。属 P3，可随 M4-03 一起做。
- **结论**：

### 6.8 【P3】新冒烟脚本的"attempt 数"实际统计的是 case 数，证据链对不上

- **位置**：`tests/integration/m4_01_concurrency_smoke.py:247-249`（`session.query(EvalCaseRun)...count()` 赋给 `attempt_count`）；`:250-263`（打包进 evidence）；`reports/2026-11-09/m4-01-concurrency/report-data.json:4`、`:95`（"attempt 恒为 4 / attempt 数恒为 4（无重复）"）。
- **现象**：脚本从未 count `EvalCaseAttempt`，4 个用例恰好各 1 个 attempt 时数字碰巧相等，所以报告看起来对；一旦出现重复 attempt，这个字段仍然返回 4，**恰好无法证明它想证明的"不重复创建 attempt"**。同一份报告还声称"两个超额 Job 429 等待后补位"（`:107`），但脚本没有统计 429 次数、也没有记录 HTTP 日志，timeline 里 `running=2` 只出现 1 个采样点（98 个采样、50ms 间隔，`evidence.json`），属于合理推断而非直接证据。
- **问题**：验收证据的可信度问题，不是产品 bug。另外断言是 `peak <= 2`（`:271`），没有断言 `peak == 2`——如果闸门退化成"永远只跑 1 个"，测试照样绿。

### 6.9 【P3】`prepare` 的默认并发是 1、`create` 的默认是 8——同一个"没填"得到两种语义

## §9 文件级代码分析

### 9.1 `backend/app/services/capacity.py`（A，118 行）

**职责**：把"有效并发"从一个散落在 dispatcher/preflight/callback 三处的隐式概念，收敛成一个可测试的纯模块。

**关键依赖**：只依赖 SQLAlchemy 与 `Settings`，没有第三方 SDK——这让它可以被 dispatcher（后台线程）、preflight（API 请求）、started（回调事务）三处以不同 session 调用而不用担心生命周期。比喻：它是剧院门口的**座位牌**，谁来看都读同一块牌子，不自己印。

**变更代码块**（全新文件，无旧版对照，按三段看）：

1. **常量即契约**（`:24-37`）：`QUEUE_REASON_*` 是写进 DB 的字符串字面量，`RELEASED_ATTEMPT_STATUSES` 是"什么叫在飞"的定义。把定义放进 capacity 而不是 dispatcher，是为了让 started 和 preflight 也能引用同一套语义。
2. **纯公式**（`:40-49`）：`max(0, ...)` 三次夹逼，保证任何脏输入（负数、None）都退化成 0 而不是异常；`pool_max is None` 表示"没有上限"而不是"上限 0"，这个区分是全模块最容易被误读的地方。
3. **读取器**（`:52-118`）：`pool_max_capacity` 的 `isinstance(raw, bool)` 排除很讲究——Python 里 `True` 是 `int`，不排除会把 `"max_capacity": true` 读成 1；`pool_runner_capacity` 加心跳新鲜度，避免把刚被 sweep 前的一批僵尸 Runner 算进容量。

**实现思路总结**：公式纯函数化，数据读取集中在三个带 docstring 的函数里，调用方只关心 `min` 的结果。

**检视发现**：`effective_concurrency` 对"无池"返回 `requested`（`:109-110`），而 `preflight` 的 `online` 告警只按 status 统计（`preflight.py:221-258`），两者对"在线"的定义不同，预检可能出现"告警说 8 个在线、effective 却是 3"的组合；属 §6.6 之外的 P3 一致性问题。`labels_json` 的字符串值静默降级见 §6.6。

### 9.2 `backend/app/services/dispatcher.py`（M，352 行）

**职责**：outbox → GitHub 的消费环，本 PR 在"领取 → 校验 → 派发"之间插入了容量闸门。

**关键依赖**：`post_repository_dispatch`（GitHub HTTP，可注入 transport）、`capacity`（纯读）、`refresh_run_progress`（事务内聚合）。没有新增依赖。

**旧代码 vs 新代码**：

```python
# 旧（M2-05）：逐行领取后直接 _dispatch_row
for row in rows:
    _dispatch_row(session, row, ...)
```

```python
# 新：先问容量，再决定"发 / 延后"
for row in rows:
    run = session.get(EvalRun, row.aggregate_id)
    if settings.dispatch_capacity_gate and run is not None and run.resource_pool_id and run.status in ("queued", "running"):
        decision = _capacity_decision(session, run, settings=settings, now=now)
        if decision is not None:
            _cap, reason = decision
            if run.queue_reason != reason:
                run.queue_reason = reason; dirty = True
            row.available_at = now + timedelta(seconds=settings.dispatch_capacity_retry_seconds)
            dirty = True; outcome.queued += 1
            continue
        if run.queue_reason is not None:
            run.queue_reason = None; dirty = True
    _dispatch_row(session, row, ...)
if dirty:
    session.commit()
```

这段的**写法意图**很清楚：闸门只改 `available_at` 和 `queue_reason`，绝不碰 attempts——这样"排队"与"派发失败"在数据上完全分开，前者可无限重试且不产生副作用，后者才走 `_handle_dispatch_error` 的退避/收口（`:256-279`）。`dirty` 的批量提交是为了避免每行一次 commit（8 行 8 次往返），但要注意 `_dispatch_row` 内部自己会 commit（`:213`、`:252`），所以 `dirty` 的提交时机是"这一批里没有真正派发时"——不影响正确性，只是读代码时要意识到事务边界不统一。

**旧 → 新的另一个变化**是 `DispatchOutcome.queued`（`:37`）与 worker 日志（`worker/main.py:68-84`）：让"闸门在拦"这件事在运维日志里可见，否则 worker 看起来像"什么都没干"。

**实现思路总结**：闸门是"读多写少"的前置过滤，延后代替拒绝，状态与副作用分离。

**检视发现**：`_capacity_decision` 每次循环都 `run.effective_concurrency = cap`（`:52`），即使 `dispatch_capacity_gate` 后来关掉、或这一轮没有行可发，也会在后续 commit 里写一次；语义上无害，但会让"effective"在 run 还没真正调度时就被刷新。真正的问题在 §6.2：`dispatching` 被当作"已释放"。

### 9.3 `backend/app/services/case_attempts.py`（M，646 行）

**职责**：回调状态机的唯一写入口；本 PR 在 `handle_started` 的"终态检查"与"推进 running"之间插入用例级容量闸。

**关键依赖**：`capacity`（纯读）、`func.count`（SQL 聚合）、`CaseCallbackError`（API 层映射成 HTTP）。没有新依赖。

**旧代码 vs 新代码**：

```python
# 旧：started 直接推进
_promote_running(ctx, now=now, runner_id=...)
```

```python
# 新：先过闸，拒绝时零副作用
_enforce_capacity_gate(ctx, now=now)
_promote_running(ctx, now=now, runner_id=...)
```

`_enforce_capacity_gate`（`:196-242`）的四段逻辑值得逐段读：

1. **只对池化评测生效**（`:210-211`）：合成/历史评测不受影响，保证 M2 的 247 个测试与旧路径不回归。
2. **写锁**（`:212-218`）：先写 `effective_concurrency` 再 `flush()`。注释解释了为什么不用 `SELECT ... FOR UPDATE`：SQLite 会把它当普通 SELECT，测试环境挡不住竞态；`flush` 在 PG 拿行锁、在 SQLite 拿库锁，两种后端都成立。这个细节是冒烟首轮 `running=3/4` 抓出来的（`report-data.json:166-180`），属于"真实链路才暴露"的典型。
3. **cap==0 fail-open**（`:219-221`）：只标 reason、直接返回放行。取舍见 §6.7。
4. **数 running + 429**（`:222-241`）：`EvalCaseRun.id != ctx.case_run.id` 排除自己（重试 started 时自己可能已经 running）；`commit()` 在抛错前执行，把 `queue_reason` 落库——这是"拒绝也要留下可解释状态"的设计，和"零副作用"并不矛盾（拒绝不写事件、不动 attempt，但写 run 级原因）。

**实现思路总结**：把"容量拒绝"实现成一次可重试的 429，而不是状态迁移；写锁只保护计数窗口，不覆盖整个回调。

**检视发现**：`capacity.effective_concurrency(..., settings=get_settings())` 用的是全局 settings，而 `handle_started` 没有 settings 参数；测试靠 `configure_settings` 清缓存才能注入，生产无影响，但让"同一请求内 settings 不一致"成为可能（dispatcher 用传入的 settings）。属 P3。另一个已知边界：`cap<=0` 时返回前没有 `commit`，`queue_reason` 要等 `handle_started` 末尾的 commit 才落库；若后续 `_promote_running` 抛异常，reason 会丢——影响仅限可观测性。

### 9.8 `runner/scripts/real-task.mjs` / `runner/lib/callback-client.mjs`（M）

**职责**：Runner 参考实现；本 PR 加 `--case`、429 等待、退出释放 claim。

**旧 vs 新（关键三段）**：

```js
// 旧：整个 shard 一把 claim

```

```js

const claim = guard.claim(claimKey, { ...(args.caseRunId ? { case_run_id: args.caseRunId } : {}) });
```

```js

// 新：retryOn429=false + 自己的 5s→60s 循环
```

```js

function fail(message, code, exitCode = 2) {
  if (releaseClaim && exitCode !== 0 && !CLAIM_KEEPING_CODES.has(code)) releaseClaim();
  ...
}
```

**依赖解读**：`postCallback` 是自研的 at-least-once 客户端（无第三方库），用 `Idempotency-Key` 头传 event_id。`retryOn429` 这个开关加得很克制：默认行为不变（其他回调仍自动重试 429），只有 started 接管——因为 started 的 429 语义是"现在没位子"，不是"服务端忙"，重试间隔由业务决定（5s 起步），这个区分是对的。

**实现思路总结**：claim 粒度跟着执行粒度走；429 从"传输错误"升格为"业务排队"，由调用方决定节奏；退出码区分"可重跑"与"不可重跑"。

**检视发现**：claim 在真实 workflow 里跨 Job 失效（§6.5）；429 耗尽后无平台重派（§6.3）；409 一律 stale 导致绕过（§6.4）。`fail` 的 `exitCode !== 0` 条件恒真（所有调用都非 0），`CLAIM_KEEPING_CODES` 实际只排除 `callback_permanent`，逻辑正确但表达可以更直白。

### 9.9 `runner/scripts/plan-cases.mjs` / `runner/lib/manifest-source.mjs`（A）

**职责**：prepare 阶段把 shard 清单变成 matrix；manifest 拉取逻辑从 real-task 抽出来共用。

**旧 vs 新**：real-task 里原来有一段内联的 `fetchManifest`（`file://` 分支 + HTTP 头解析），本 PR 抽到 `manifest-source.mjs:13-27`，real-task 与 plan-cases 共用。抽取的收益是 **digest 计算只有一个实现**（`:28-30`），避免两个脚本对同一段字节算出不同 digest。

`plan-cases` 的核心只有一句：

只输出不透明 id，题目、资产、token 都不进 GitHub matrix——这是设计 06 §3.2"dispatch 只传引用"的延续。`--state-dir` 参数被接受但从不使用（`:43-44`），是为了让 prepare/execute 的命令行形状一致；这个"无用参数"有明确注释，不算坏味道。
