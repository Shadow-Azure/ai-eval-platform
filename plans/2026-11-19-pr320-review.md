## §1 一页速览

**一句话**：把“spot 连续回收后只能继续排队、直到 `spot_retry_exhausted`”改成“达到阈值先换到运维已有的固定/按量池，并把这次切换写进 run 快照和资源事件，让控制台能解释为什么换了池”。

**比喻**：原来的调度像一个只会回同一家店排队的顾客，店一直关门就一直重排；现在柜台记下连续失败次数，达到阈值后把顾客带到旁边已经营业的固定窗口，并在小票上写明“已换窗口”。

| 交付块 | 用户能看到什么 |
|---|---|
| 自动回退 | 连续 3 次 spot 回收（或连续 2 次库存/价格阻塞，按配置）后，新 attempt 的目标池和 `runs_on` 切到固定池 |
| 可解释 | 评测配置显示“已回退：spot-contended → fixed-eval · 连续 3 次”；源/目标池各有一条资源事件 |
| 成本护栏 | 配置成本上限后，兜底池成本未知或超上限时不回退，记录抑制原因，保留原重试 |
| 兼容 | 未配置 `fallback_pool_id` 时完全保持原 spot 重试行为；失败分类、容量核算、queue lease 不重复实现 |

验证基线：`pytest tests/backend` 全绿；`npm test` 107 通过；`npm run verify:flow`、`npm run verify:docs` 通过；`web` typecheck/build 通过；integration smoke 3 场景通过。

## §2 架构导览

### 2.1 回退状态保存在 run 快照，不新增表

`backend/app/services/spot_fallback.py:125` 的 `_write_state` 把状态深拷贝后写入 `eval_run.resource_pool_snapshot_json["spot_fallback"]`。这里有个不显眼但关键的细节：如果直接修改上次赋值的同一个 dict，SQLAlchemy 会认为 JSON 列“没变”，commit 后只剩 `resource_pool_id` 更新成功，快照回退成旧值。深拷贝同时解决“赋值后原地 update 导致历史值和新值指向同一对象”的问题。

### 2.2 两条触发路径

1. **provider 回收**：`backend/app/services/case_attempts.py:1231` 的 `handle_spot_interruption` 在标记 attempt 失败后、构建 retry 前调用 `spot_fallback.record_spot_reclaim`（`:1314`）。因此 retry 的 `build_retry_dispatch` 读取的是已经切换后的 `run.resource_pool_id`。
2. **容量供给阻塞**：`backend/app/services/capacity_control.py:851` 在 `capacity_reason` 为 `resource_inventory_insufficient` / `resource_price_above_threshold` 时，对每个仍在等待的 run 调 `record_supply_block`。连续 tick 达到阈值后走同一个 `_try_activate`。

### 2.3 切换动作

`backend/app/services/spot_fallback.py:429` 的 `_try_activate` 按顺序：

- 校验兜底池存在、同租户、active、固定模式；
- 校验成本上限（兜底池必须声明 `reference_price_cny` 或已有价格；未知/超限则 `_record_suppressed`）；
- 设 `run.resource_pool_id`、清空 effective concurrency/queue reason；
- 写 run 快照；
- `_retarget_pending_attempts` 改待派发 attempt 的池；
- `_retarget_pending_dispatches` 只改 `status=pending` 的 outbox 的 `runs_on` 和 manifest `runs_on`，并重算 digest；
- 写 run 级 `eval.spot_fallback` 与源/目标池的 `resource.spot.fallback`。

已经 `sent` 的旧 spot Job 不会迁移（强行改会破坏 GitHub 队列语义），它的后续 retry 使用新池；这由 `_queued_attempts` 继续统计 attempt 自身的池来避免把等待中的旧 Job 的 runner 缩掉（`capacity_control.py:226`）。

### 2.4 预算口径

`handle_spot_interruption` 的 `retry_allowed` 从 `spot_budget_left and attempt_budget_left` 改为 `(spot_budget_left or fallback.active) and attempt_budget_left`（`case_attempts.py:1351`）。一旦回退已激活，本次 retry 不再花 spot 预算，只受 `max_attempts` 约束；否则“阈值达到但 spot 预算也刚好耗尽”仍会直接 `spot_retry_exhausted`。

### 2.5 契约边界

runner contract 的 dispatch/manifest 都是 `additionalProperties: false`。所以 `_retarget_pending_dispatches` 只改既有 `runs_on` 字段，不把 `spot_fallback` 塞进 manifest；回退信息只保存在 outbox 的 `payload_json["fallback"]` 和 run 事件中。新增 backend 测试用真实 `validate_payload("dispatch"/"manifest")` 校验改写后的 payload。

## §3 数据流走查

场景：spot 池 `spot-contended` 配置 `fallback_pool_id=fixed-eval`、`fallback_after=3`；case 连续 3 次被 provider 停止。

1. Aliyun sync 观察到 `provider_stopped` → `_reclaim` → `case_attempts.handle_spot_interruption`。
2. 当前 attempt 标 `spot_interrupted`，释放 runner 绑定，续期兄弟 attempt 的 queue lease。
3. `record_spot_reclaim` 锁 run 行、读快照计数 +1；第 3 次进入 `_try_activate`。
4. run 池切到 `fixed-eval`，快照写 `active=true`、来源/目标、连续次数、成本快照。
5. 旧 outbox（待派发）的 `runs_on` 改成 `self-hosted,fixed-eval`；新 retry attempt 的 `resource_pool_id` 也是 fixed。
6. `build_retry_dispatch` 用 `evaluations.run_runs_on` 生成 fixed 标签的 dispatch/manifest；runner 在 fixed 池执行。
7. 控制台 `GET /config` 返回 `spot_fallback`，`ConfigPanel` 显示“已回退”；资源池详情显示配置的兜底池/阈值/上限。
8. 若成本上限拦截，第 6 步仍走 spot，快照记录 `suppressed_reason`，UI 显示“回退未启用”。

## §6 讨论点

### D1 兜底目标限定为“已有固定池”，不自动创建按量 ECS

- **位置**：`spot_fallback.py:474`、`validate_fallback_config`（`:240` 附近）
- **现象**：回退只切到同租户 active 的 fixed 池；平台不替用户创建按量实例。
- **问题**：如果 fixed 池没有在线 Runner，run 会从 spot 排队变成 fixed 排队，仍未真正执行。
- **预判**：符合 #311“优先复用现有 fixed 资源池/按量 ECS”和不新增云厂商的约束；把“需要常驻 fixed Runner”写进池表单提示和设计文档即可，不扩大到新供给器。
- **结论**：待用户拍板。

### D2 回收路径保留一次 attempt，库存/价格按 reconcile tick 计数

- **位置**：`spot_fallback.py:620`、`:669`
- **现象**：`fallback_after=3` 对回收实际取 `min(3, max_attempts-1)`，默认 `max_attempts=2` 时第一次回收就切池；对库存/价格则是 3 个 30 秒 tick（约 90 秒）。
- **问题**：回收阈值会被 run 的 attempt 预算压低，运维可能误以为配置的 N 总会生效；两种“连续失败”的时间尺度也不同。
- **预判**：保留一次 attempt 给兜底池是必要的，否则默认 `max_attempts=2` 永远无法在 fixed 上执行；UI/文档已写明“回收路径会保留最后一次 attempt”。若以后要统一成时间窗口，再单独改。
- **结论**：待用户拍板。

### D3 已发送到旧 spot 池的 queued Job 不迁移

- **位置**：`spot_fallback.py:320`、`capacity_control.py:226`
- **现象**：只改写 pending outbox 和新 retry；已 `sent` 的 Job 留在 GitHub 的 spot 队列。
- **问题**：回退瞬间可能仍有少数 Job 等旧池；平台通过继续统计 attempt 自身池保证不缩掉它们的 Runner。
- **预判**：迁移已发送 Job 需要 cancel/redispatch，语义风险大于收益；让它们自然完成或超时后 retry 到 fixed 更安全。
- **结论**：待用户拍板。

### D4 成本上限启用时要求兜底池声明参考成本

- **位置**：`spot_fallback.py:501`、`ResourcesPage.tsx:1675`
- **现象**：启用上限但兜底池没有 `reference_price_cny` 时，API 在保存池配置阶段直接 422；运行期再遇到历史脏数据则抑制回退并写事件。
- **问题**：对固定池强制声明价格会增加一次配置动作。
- **预判**：成本安全优先；未知成本时静默回退可能产生意外费用，显式失败更可控。
- **结论**：待用户拍板。

## §9 文件级代码分析

### `backend/app/services/spot_fallback.py`（A，核心）

- 职责：把“连续失败”抽象成 run 快照里的计数器与一次池切换，并负责 outbox/attempt 的池引用改写。
- 关键机制：`_state`/`_write_state` 深拷贝（JSON 变更检测）；`_try_activate` 先校验目标与成本再改 run；`_retarget_pending_dispatches` 只动 pending 行。
- 实现思路总结：不改表、不改 runner 契约；状态是 run 快照，动作是“换池 + 改写待派发”。
- 检视发现：已修两个 bug（JSON 原地更新、manifest 额外字段），并发加锁；未发现新问题。

### `backend/app/services/case_attempts.py`（M）

- 职责：在 `handle_spot_interruption` 中插入回退观察；成功完成时重置计数。
- 旧代码 vs 新代码：旧代码 `if spot_budget_left and attempt_budget_left`；新代码允许 `fallback.active` 绕过 spot 预算。
- 实现思路总结：回退必须先于 retry 构建，否则 retry 仍带 spot 标签。
- 检视发现：`fallback.failures` 在回退后继续增长（每次 provider 回收 +1），错误摘要会显示更大的次数；这是诊断信息，不影响决策，接受。

### `backend/app/services/capacity_control.py`（M）

- 职责：把库存/价格阻塞的 reconcile tick 转成 run 级连续计数；`_queued_attempts` 同时看 attempt 自身池。
- 实现思路总结：供给阻塞与回收共用 `_try_activate`，避免两套切换逻辑。
- 检视发现：`reason in (None, REASON_CAPACITY_SCALE_DOWN)` 时重置计数；若 `capacity_scale_up` 但实际未创建实例（provider 错误），不回退计数，符合“连续阻塞”语义。

### `backend/app/api/resources.py`（M）

- 职责：池创建/编辑前校验兜底配置；把 `FallbackConfigError` 转成现有 422 envelope。
- 检视发现：校验依赖 `session.get(ResourcePool)`，在 flush 前也能读到已存在池；无新增事务边界。

### `web/src/pages/EvalDetailPage.tsx` / `ResourcesPage.tsx` / `evalWorkbench.ts`（M）

- 职责：解析 `spot_fallback`、展示“已回退”、编辑兜底池/阈值/上限、识别新资源事件。
- 样式：沿用现有 `SummaryList`、`Tag color="warning"`、`resource-form-row`、`banner`，没有新增视觉语言。
- 检视发现：`FallbackSummary` 对未触发/抑制/激活三态都有文案；长池名在 `Space wrap` 内换行，未溢出。
