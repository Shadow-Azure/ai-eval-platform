## 1. 一页速览

一句话：把“Runner 启动时先去平台要脚本包”改成“spot 实例启动时已经带着脚本包”，并给网络获取一条直连私有 OSS 的短路径。

比喻：以前每个工人上班先到前台领工具箱，前台排队就开不了工；现在工具箱在入职时就放进工位，前台坏了也能直接开工，只有工位和仓库都没有时才回平台仓库借。

交付块：

| 块 | 结果 |
|---|---|
| 镜像/OSS 预置 | cloud-init 预取 + sha256 校验；镜像可烘焙 |
| 不依赖平台 scripts 端点 | dispatch payload 冻结 name/md5/sha256；镜像缓存命中即完成 |
| OSS 次选 | metadata 返回 `oss_url`（内网预签名，600s） |
| checkout 最后 | 仅镜像/OSS/代理都失败时 |
| 快速失败 | fetcher 60 秒预算；#308 的 `runner_bootstrap_failed` 已有结算步骤 |

验证基线：

- `npm test`：107 passed
- `pytest tests/backend`：全量通过
- `npm run verify:flow`、`npm run verify:docs`、`node --test tests/runner/*.test.mjs`：通过
- 本地 CLI 冒烟：端点 503 + 镜像缓存 → `source=image`；无镜像 + 直连 OSS → `source=oss`；全源不可用 → 快速非零退出

## 2. 架构导览

### 2.1 平台侧：冻结包标识

`backend/app/services/dispatcher.py:304-335` 在 M5-12 的 `scripts_bundle` pin 基础上，把同一对象写进 `client_payload`。只有 name/md5/sha256 齐全且 size>0 才发送，避免 schema 校验失败或 Runner 无法校验的“半个 pin”。`runner-contract/schemas/v1/dispatch.schema.json:67-96` 用 `additionalProperties: false` 和固定 name 正则把字段限制为内容寻址形态。

### 2.2 平台侧：直连 OSS

`backend/app/api/runners.py:788-822` 在原有代理 URL/token 之外返回 `oss_url`。它使用 `object_store_from_settings(settings, internal=True)`，与 dataset image tar 的内网预签名策略一致；bucket 仍私有，URL 只带 600 秒 SigV4 能力。

### 2.3 实例侧：启动预置

`backend/app/services/provisioning/aliyun.py:713-736` 在创建实例时生成 3600 秒预签名 GET；`spot_cloud_init.py:102-126` 在 bootstrap 中先检查 `/opt/eval/runner-scripts/<name>.tar.gz`，存在且 sha256 匹配就跳过；否则 `curl --max-time 60 --retry 2` 预取，校验后 `chmod 0644` 并 `mv` 到内容寻址路径。预取失败只写诊断，不阻塞启动。

### 2.4 workflow：获取顺序

`.github/workflows/eval-shard.yml:198-343`（prepare）与 `:415-560`（execute）内嵌同一个 fetcher：

1. `readImageCache()`：只有 dispatch pin 完整且 name 通过正则才读取；sha256/md5/size 全校。
2. 读取平台 scripts 元数据；优先 `oss_url`，再 `url` + Bearer token。
3. 都失败 → `ok=false` → 单次 `actions/checkout`（60 秒 step 超时）。
4. 整段 fetcher 由 `RUNNER_SCRIPTS_FETCH_BUDGET_MS=60000` 与 step `timeout-minutes: 2` 双重兜底；execute 的 #308 failure step 仍可回调。

### 2.5 发布

`backend/app/services/runner_scripts_cache.py:160-185` 新增 `write_runner_scripts_cache`，写 `<name>.tar.gz` 与 `manifest.json`；`scripts/cache-runner-scripts.py` 的 `--out-dir` 复用同一 builder。OSS 发布路径不变，仍由 deploy 的 `scripts/cache-runner-scripts.py` 上传。

## 3. 数据流走查

1. dispatcher 派发 shard：`_dispatch_row` 读取 settings 的 bundle pin，写入 outbox 行与 `client_payload`。
2. 平台创建 spot：capacity controller → provisioner → `render_cloud_init(scripts_bundle, scripts_bundle_url)`。
3. spot 启动：cloud-init 校验/预取 → `/opt/eval/runner-scripts/<name>.tar.gz`。
4. GitHub job：fetcher 先用 dispatch pin 找镜像缓存；命中则直接解包，不访问平台。
5. 缓存未命中：用 dispatch `manifest_url` 换 `/scripts` 元数据；直连 `oss_url`；失败再走平台代理。
6. 全部失败：`ok=false` → checkout（单次）→ 仍失败则 job failure → #308 failure step 回调 `runner_bootstrap_failed`。
7. 解包成功后 workflow 从 `EVAL_SCRIPTS_DIR` 运行 `contracts.mjs`/`plan-cases.mjs`/`real-task.mjs`。

## 6. 讨论点

### 6.1 预置使用“当前 settings”，不是 dispatch pin

- 位置：`backend/app/services/provisioning/aliyun.py:713-736`
- 现象：实例创建时用当前部署的 bundle name 预置；dispatch 冻结的是派发时的 name。
- 问题：若部署恰好在 dispatch 与实例创建之间切换 bundle，镜像缓存 name 与 pin 不一致。
- 预判：这是可接受的窄窗口；fetcher 会回退到平台元数据（仍可拿到旧对象），不会执行错版本。
- 结论：接受；无需额外同步机制。

### 6.2 prepare job 没有 `runner_bootstrap_failed` 回调

- 位置：`.github/workflows/eval-shard.yml` prepare 段
- 现象：#308 的失败回调只在 execute。
- 问题：若 prepare 连镜像/OSS/checkout 都失败，平台仍可能等 queue timeout。
- 预判：本 issue 的现场是 execute job；prepare 失败通常是平台整体不可达，回调同样不可达。该缺口属于 #308 的后续范围。
- 结论：本 PR 不扩大处理；保留为后续 issue 候选。

### 6.3 checkout 回退从两次减为一次

- 位置：`.github/workflows/eval-shard.yml` 两处 checkout
- 现象：M5-12 的第二次 checkout 重试被移除。
- 问题：checkout 首次瞬时失败时少了同 job 内的重试。
- 预判：checkout 现在只是最后回退；镜像/OSS 命中时根本不走 checkout。job 失败后平台会按重试预算生成下一次 attempt，比多等一分钟更符合 #312 的快速失败目标。
- 结论：接受；如需保留两次重试，应把它放在独立的“checkout 兜底”策略里，而不是延长启动失败路径。

## 9. 文件级代码分析

### 9.1 `runner-contract/schemas/v1/dispatch.schema.json`

职责：repository_dispatch payload 契约。变更形态 M。

新增 `scripts_bundle` 对象，`name` 用 `^eval-runner-scripts-[0-9a-f]{32}\.tar\.gz$`，digest 用十六进制模式，`size` 最小 1。`additionalProperties: false` 保持未知字段拒绝；旧 dispatch 不含该字段仍合法，因此向后兼容。

实现思路：把“包身份”从平台运行时状态前移到 dispatch 事件，workflow 不需要先访问平台即可定位内容。

检视发现：无。

### 9.2 `backend/app/services/dispatcher.py`

职责：claim → repository_dispatch。变更形态 M。

旧代码只把 pin 写到 `row.payload_json["scripts_bundle"]`；新代码在完整 pin 时同步写 `client_payload.scripts_bundle`。`bundle_size > 0` 与 md5/sha256 非空共同避免 schema 不接受的不完整对象。

检视发现：`client_payload` 在创建时已通过旧 schema 校验，dispatch 时追加字段不再走 `validate_payload`；新增 schema 属性使后续重校也成立。无实害，但若未来增加更多 dispatch 时字段，建议统一在 `_dispatch_row` 里 assemble 后校验一次。

### 9.3 `backend/app/api/runners.py`

职责：Runner 回调/元数据 API。变更形态 M。

`oss_url` 用内网 store 预签名 600 秒；代理 URL/token 保留。`presign_store or store` 保证 fake/特殊 store 场景仍能返回。

检视发现：预签名失败会抛异常并让 metadata 500；生产 ObjectStore 的 `_presign` 只做本地签算，正常配置下不会失败。若未来 endpoint 可配置为非法值，建议包一层降级到代理；当前无实害。

### 9.4 `backend/app/services/provisioning/spot_cloud_init.py`

职责：生成 spot cloud-config。变更形态 M。

bootstrap 新增 `RUNNER_SCRIPTS_*` 变量与预置块。`target` 用内容寻址名；`sha256sum -c -` 校验；失败只写 stderr。`render_cloud_init` 增加可选 `scripts_bundle`/`scripts_bundle_url`，旧调用不传仍生成旧文档。

检视发现：预置块在 `set -e` 的脚本里用 `if/elif` 包裹，失败不会中止；16KB 测试仍通过（含 URL 时约 9.7KB）。

### 9.5 `backend/app/services/provisioning/aliyun.py`

职责：阿里云竞价供给器。变更形态 M。

`_user_data` 在已有 runner tarball 分支后生成脚本包预签名 URL；只有 name+sha256 且 name 合法、对象存储已配置时才启用。使用 `internal=True` 让实例走内网 OSS。

检视发现：URL 的 access key id 会出现在 user-data 中（SigV4 公开标识），secret 不出现；user-data 由 cleanup 在启动后删除。

### 9.6 `.github/workflows/eval-shard.yml`

职责：prepare/execute workflow。变更形态 M。

两处 `Fetch the scripts bundle` 被替换为内嵌 Node fetcher；顺序为镜像缓存 → metadata → `oss_url` → 代理；失败输出 `ok=false` 并进入单次 checkout 回退。`RUNNER_SCRIPTS_FETCH_BUDGET_MS=60000` 与 `timeout-minutes: 2` 双重限制。execute 的 failure step 不变，仍能在 started 前回调。

检视发现：同一段 fetcher 在两个 job 重复，是“还没有 checkout”导致的必要重复；测试抽取两段并断言逐字相等，避免漂移。后续若引入 bootstrap 脚本发布物，可再抽公共文件。

### 9.7 `backend/app/services/runner_scripts_cache.py` 与 `scripts/cache-runner-scripts.py`

职责：确定性脚本包构建/缓存。变更形态 M。

新增 `write_runner_scripts_cache`：写内容寻址 tar 与 `manifest.json`。CLI `--out-dir` 直接返回，不要求 OSS 配置，适合镜像构建机。

检视发现：`--out-dir` 与 `--github-output` 同时使用时不会写 output；当前 deploy 不使用 `--out-dir`，镜像构建也不需要 GitHub output，行为清晰。
