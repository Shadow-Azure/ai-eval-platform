## §1 一页速览

一句话：**评测跑完后，平台把每个"没做对"的用例冻结成一份固定载荷，异步推给外部自进化平台 harness-evolution（HE），并附上一个限时会话包下载链接，让 HE 能自己来拉完整执行轨迹。**

比喻：这是给评测结果装了一个"快递柜"。评测结束（寄件人封箱，载荷冻结、重试不换内容）后，worker（快递员）按 1 分钟→5 分钟→15 分钟→1 小时的节奏反复投递；包裹上贴着一张 7 天有效的临时门禁卡（HMAC 签名 URL），收件方 HE 拿卡可以走进平台把会话轨迹（原始 NDJSON）整个搬走，卡到期就失效。

| 交付块 | 内容 |
|---|---|
| 启动配置 | `/prepare` 可选 `self_evolution` 块（base_url / workspace_id / whk_ 令牌），令牌 Fernet 密文落库、任何响应不回显 |
| 终态入队 | `refresh_run_progress` 终态事务内 `begin_nested` 冻结非 resolved 且执行过的用例为 outbox 行，`badCaseId=swe-<sha1[:20]>` 幂等 |

## §2 架构导览

### 2.1 Outbox（发件箱）：为什么先落库再发

`models/self_evolution.py:30-71` + `services/self_evolution.py:293-366`。终态回调要写 HTTP 出去吗？不——网络是会挂的，而终态事务不能等网络。所以入队（冻结载荷进 `payload_json`）发生在终态事务里，真正 POST 由 worker 独立轮询 `status='pending' AND next_attempt_at<=now`（`services/self_evolution.py:427-440`，索引 `ix_self_evolution_report_status_next`）。**冻结**是关键取舍：载荷在入队时定型，重试期间即使用例被重新归类、签名密钥轮换，也不会"偷换"已定稿的包裹内容——重试永远 POST 同样的字节。

幂等靠 `(tenant_id, bad_case_id)` 唯一约束（`models/self_evolution.py:53`），`badCaseId` 是 `swe-` + sha1(tenant:run:case_key) 前 20 位（`services/self_evolution.py:146-148`），确定性可重算；HE 侧同 id 同工作区是 200 覆盖不耗配额，跨工作区才 409（HE `ingest.py:147-153`），与本端 409 终态失败的处理对齐。

"bad case" 的判定：`result_status != 'resolved'` 且至少一次 attempt `started_at` 非空（`services/self_evolution.py:322-331`）——纯排队后被取消的用例没碰过 agent，不上报。

### 2.2 签名即授权：一张卡走遍一层楼

`services/self_evolution.py:55-117`。HMAC-SHA256 只签 `GET\n{路径前缀}\n{exp}` 三行——**不签具体 sessionId**。为什么？HE 的拉取是广度优先遍历：它拿同一张模板，把根会话和每个子会话 id 逐一替换进 `{sessionId}`（HE `client.py:108-115` 只替换这一个占位符，query 原样保留）。如果按会话逐个签名，第一跳之后就全 401 了。这是本次跨仓联调把签名从前缀化定案的原因，代价见 §6.1。

端点侧 `api/self_evolution.py:54-93` 校验：密钥未配置 → 503 fail-closed；格式错误/签名错/过期统一 401（过期单独一个 code 便于排障，但同为 401，无枚举预言机）；`hmac.compare_digest` 常量时间比较。

### 2.3 envelope 组装：严格对齐 HE 的封闭 schema

`api/self_evolution.py:166-249`。按 native_session_id 反查 trace_session（新索引 `models/trace.py:151`），运行时白名单（`claude-code`/`claude_code` 或解析器版本前缀）之外 404；一层子会话查询同 attempt 内 `parent_session_id` 匹配（`:212-221`）；轨迹从对象存储读出后按 HE 拉取侧三上限（64MiB 总量 / 1MiB 单行 / 100 万行）前置校验，超限 413 而不是截断——收件方永远不能拿到"看起来完整其实是半截"的轨迹（`api/self_evolution.py:96-163`）。

### 2.4 密钥与配置的分层

`config.py:242-258` 三个可选设置；`deploy/docker-compose.prod.yml` 注入 api + worker 双服务——api 端点要验签，worker/reconciler 也能把 run 推到终态所以要能签。`write-managed-env.sh` 把两个键加入换机迁移的托管清单，符合根 AGENTS.md 的密钥硬约束。两键留空只降级（不上报会话链接），不阻断 bad case 上报本体。

### 2.5 前端：令牌的生命周期只有一次输入

`web/src/pages/EvalWizardPage.tsx`：token 用 Password 输入 + `whk_` 前缀校验；`saveDraft` 把 token 从持久化草稿里剥掉（恢复草稿必须重新输入）；后端 `preparations.py:498-568` 服务端再验一遍（enabled 三字段必填 / disabled 三字段必须空），且只有非密字段进 `snapshot_json`（`_self_evolution_view`），密文单独列存（`models/evaluation.py:374-377`）。

14 个 scripts 的 `import.meta.url === \`file://${process.argv[1]}\`` 在 Windows（`C:\...` 路径）恒为 false，主入口永远不执行 → 门禁静默 no-op。统一改 `pathToFileURL(process.argv[1]).href`（如 `scripts/run-gates.mjs:66`）。抽查 `flow-new-issue.mjs`、`run-gates.mjs`、`verify-md-links.mjs` 三个，其余 11 个为同一模式的机械替换（diff 均为 +3/−1）。这也是 PR 描述说"npm run lint:docs / verify:flow 本地全绿"可信的前提。

## §3 数据流走查

场景：用户启用了自进化上报的一次评测，3 个用例中 2 个失败。

1. 向导 Step 3：用户打开 Switch，填 `https://he.example.com` + `ws-01` + `whk_xxx`；前端校验通过后 token 随 `POST /prepare` 提交。
2. `api/evaluations.py:116-155` 的 `SelfEvolutionConfig` 先做 Pydantic 校验；`preparations.py:506-568` 服务端复验后把 `{enabled, base_url, workspace_id}` 写进快照、令牌加密写 `eval_preparation.self_evolution_token_encrypted`。
3. 用户确认创建：`consume_preparation`（`preparations.py:925-955`）把三字段 + 密文拷到新建 `eval_run` 四列。
4. 评测执行、回调回流；最后一个用例终态时 `refresh_run_progress`（`services/evaluations.py:1308-1327`）在终态事务内 `begin_nested` 调 `enqueue_self_evolution_reports`：2 个失败用例各冻结一行 outbox，`payload_json` 里连 sessionSource 签名 URL 都已定型（用当时密钥 + 当时 exp）。入队失败只记 run 事件，绝不回滚终态。
5. worker 每轮循环跑 `self_evolution_once`（`worker/main.py:93-97, 221-233`）：解密令牌 → `POST {base}/api/workspaces/{wid}/bad-cases`。假设第一个 429 → `_mark_retry` 定时 60s；第二个 201 成功落 `succeeded`。
6. HE 收到 bad case 后 BFS 拉轨迹：先 GET 根会话 URL → 平台验签 → 返回 envelope（含一层 `childSessionIds`）→ HE 把模板代入子会话 id 继续拉，同一张卡（同 exp+sig）全部验签通过。
7. 7 天后签名过期，链接自然失效；outbox 行留在库中可审计（状态/状态码/最后错误）。

## §6 讨论点

### 6.1 签名是"全平台通行证"，不是"单次包裹的钥匙"

- **位置**：`backend/app/services/self_evolution.py:60-62, 89-93`；`backend/app/api/self_evolution.py:179-186`
- **现象**：HMAC 只覆盖 `GET\n{路径前缀}\n{exp}`。签名值仅由 exp 决定——同一秒入队的所有报告携带完全相同的 exp+sig；而端点按 `native_session_id` 全局查会话，无租户/评测范围约束。
- **问题**：任何一个 `sessionSource` URL 泄漏（它会随 bad case 载荷存在 HE 的数据库里），持卡人未来 7 天内不仅能拉本报告的会话树，还能枚举**本部署内任何 claude-code 会话**的完整轨迹（sessionId 并非机密，格式可猜）。这是签名前缀化修复带来的安全边界扩大。
- **预判**：当前部署是单租户（`DEFAULT_TENANT_ID`），HE 又是可信内部平台，实际风险有限——但这是"信任 HE = 信任 HE 库里所有 URL 的所有读者"。若要收紧，最小改法是把 scope 绑进 HMAC 消息（如 `GET\n{prefix}\n{exp}\n{run_id}`，端点从 trace_session → attempt → run 反查后验同源签名），卡片就从"全平台"缩到"单次评测"，仍兼容 BFS（同 run 的子会话同一张卡）。代价是 HE 侧无感知、本端改签名消息即可。
- **结论**：已修复 2026-11-17——签名消息改为 `GET\n{path_prefix}\n{run_id}\n{exp}`，模板与端点新增必填 `run` 参数并沿 attempt → run 链校验归属，不一致统一 401（HE 无感知，BFS 同 run 仍一张卡）。

### 6.2 PR 描述声称"清理误入库的 pyc/临时文件"，但分支里没有任何删除

- **位置**：`git diff --name-status origin/main...HEAD`（0 个 D 条目）；`git ls-files` 里 `backend/app/**/__pycache__/*.pyc` 等 50+ 个 pyc 仍在 HEAD 被跟踪
- **现象**：PR 描述"工程修复（随本 issue 顺带）"列出"清理误入库的 pyc/临时文件"，实测主提交与修复提交均无删除记录，pyc 仍在版本库中。
- **问题**：描述与实际 diff 不符——是清理被漏做、做了未提交，还是描述超前？
- **预判**：大概率是写了描述忘了提交 `git rm --cached`。无害但应纠正：要么本 PR 补一个清理提交（顺手加 `.gitignore` 规则防再犯），要么修 PR 描述。
- **结论**：已修复 2026-11-17——`git rm --cached` 移除 50 个 pyc 与 5 个 egg-info 跟踪项并删除磁盘 `__pycache__`，根 `.gitignore` 补 `__pycache__/`、`*.pyc`、`*.egg-info/` 三条，同时把 `.gitignore` 补进 issue scope（中英两侧）。

### 6.3 agentMeta 只发 `name`：修复彻底，但信息量是有意放弃的

- **位置**：`backend/app/api/self_evolution.py:223-230`；HE `session_source/claude_code.py:15-68`
- **现象**：平台侧只保留 `agent_name → name` 一个键；HE 侧 `ClaudeAgentMeta` 是 `extra="forbid"` 的封闭词表（28 个键），`name` 在表内；`agentMeta: null` 时 HE 按 `{}` 校验同样通过（`base.py:95` 以 `envelope.agent_meta or {}` 兜底）。
- **问题**：封闭词表修复是否彻底？name-only 是否丢信息？
- **预判**：**彻底**。词表内所有键 alias 与平台侧发送的 camelCase 一致，`name` 键双向同名，不会触发 422；null 兜底也安全。丢 `agentType`/`spawnDepth` 等是平台 trace 模型本身只有 `agent_name` 一个元数据列（`models/trace.py:115`）导致的上游数据不存在的"无损丢弃"——不是平台有而故意不发。将来若要传更多键，瓶颈在平台解析层存不存，不在本端点。
- **结论**：（待人类拍板）

### 6.4 子会话查询在"主会话无 attempt 归属"时的空值匹配

- **位置**：`backend/app/api/self_evolution.py:212-221`
- **现象**：`childSessionIds` 查询条件是 `parent_session_id == 本会话.id AND eval_case_attempt_id == 本会话.attempt`。若本会话 `eval_case_attempt_id` 为 NULL（存在 `unlinked` 状态的会话），SQL `== NULL` 不匹配任何行——但若两条 unlinked 会话 attempt 同为 NULL，`==` 语义在 SQLAlchemy 里是 `IS NULL`？实际生成 `attempt_id IS NULL`，会把**其他评测的其他 unlinked 子会话**也列进来。
- **问题**：unlinked 会话是否会走到这个端点？`_main_session_id`（`services/self_evolution.py:151-175`）上报主会话时显式排除 `status='unlinked'`，但端点本身不排除。
- **预判**：影响面窄（需签名泄漏 + unlinked 主会话恰好被访问 + 恰有同 NULL attempt 的子会话），当前无实害。稳妥修法是查询里对 `eval_case_attempt_id` 非空分支才做 attempt 等值过滤，或端点直接 404 掉 unlinked 会话。
- **结论**：不修复 2026-11-17——无实害；且 §6.1 的 run 作用域校验已顺带把无 attempt 归属的 unlinked 会话挡在同一 401 之外（`_verify_run_scope` 对 `eval_case_attempt_id` 为空直接 invalid）。

### 6.5 轨迹解码用 `errors="replace"`，坏字节静默变 U+FFFD

- **位置**：`backend/app/api/self_evolution.py:148`
- **现象**：非 UTF-8 字节被替换而不是报错；HE 侧 `canonicalize_ndjson` 若逐行 JSON 解析，替换后的字节大多仍能解析（U+FFFD 在字符串值内合法），因此通常不会暴露。
- **问题**：会话包对"轨迹保真"的承诺是否允许静默替换？
- **预判**：Claude Code 轨迹正常都是 UTF-8，此分支基本不触发；413 而不截断的纪律在这里出现了一个例外（内容可能被动过手脚但不告知）。可改为 `errors="strict"` 失败回 404/422。低优先。
- **结论**：不修复 2026-11-17——`replace` 语义上是容错不是截断：返回的行数与行界忠实于对象存储字节，U+FFFD 只出现在字符串值内部且对下游 JSON 解析无害，Claude Code 轨迹正常均为 UTF-8，此分支基本不触发。

## §9 文件级代码分析

### 9.1 `backend/app/services/self_evolution.py`（A，527 行）

职责：M9 的服务层中枢——载荷冻结、签名构造、worker 上报，三件事一个模块。依赖 `httpx`（运行时 HTTP，非构建期）与仓库既有 `get_secret_box`。

关键变更块：
- `session_signature` / `build_session_url_template`（`:89-117`）：三行消息 + 常量时间比较 + 模板恰好一个 `{sessionId}`。前缀化的原因写在常量注释里（`:55-62`），与 HE `client.py:108-115` 的实际替换行为逐行对上。
- `build_bad_case_payload`（`:205-285`）：sessionSource 仅在"原生主会话 id 存在且 ≤36 字符"时附带（`:164-174`，HE sessionId 上限 36 的契约）；无原生会话回退 attempt id 且**不带** sessionSource（`:217-221`），因为端点按 native id 查询，attempt id 必然 404——宁可少给链接不给死链接。
- `_mark_retry` / `_mark_terminal_failure`（`:395-413`）：429/5xx/网络错误退避，`attempts>=8` 永久放弃；401/403/409/422 直接终态，错误文本截断 1000 字符防 `last_error` 撑爆。

实现思路总结：冻结载荷换确定性，阶梯退避换最终一致，分类状态码换可诊断性。

已知弱点：签名作用域为部署级（§6.1）；`_post_bad_case` 每行新建 `httpx.Client`，批内 50 行时 TLS 握手重复（批小、频率低，无实害）。

### 9.2 `backend/app/api/self_evolution.py`（A，249 行）
