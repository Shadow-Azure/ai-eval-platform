## §1 一页速览

**一句话**：这个 PR 给平台装了一套"自动租机器"的账房——先把云账号凭据登记成"资源连接"，再给资源池配上"最少/最多几台、每台跑几个 Runner、单价超过多少就不租"，最后让 Worker 每一轮对比"排队等机器的用例数"和"手头空闲机器数"，差多少就补多少，多出来的先摘牌再退租，并把这些决定写进一本谁都能查的流水账。

**一个比喻**：容量控制器像一个**网约车调度员**。乘客（queued shard）在路边排队；调度员数一眼"已在路上的车"（starting instance，每车可能拼 2 人）和"空车"（idle runner），用 `缺口 = 乘客 − 空车 − 在途车×座位数` 算出还差几辆；雨天加价（spot price）超过公司报销上限（price threshold）时，他**不派车**，只在公告板写"价格超限，继续排队"；夜里乘客少了，他让多余的车"先打双闪靠边"（draining）→"摘掉接单资格"（offline）→"退租"（release），绝不把还在载客的车退掉。

**交付块**

| 交付块 | 载体 | 一句话 |
|---|---|---|
| 资源连接 | `connection` 表 + `/api/v1/connections` | 只存 provider/region/能力/状态，密文留在 `credential` |
| 池配置 | `resource_pool` 十列 + `/api/v1/resource-pools` | 供给模式、容量上下限、实例参数、价格阈值与容量快照 |
| 兼容性校验 | `services/resources.py` + 422 | spot 必须绑有 `ecs:spot` 的同 provider 连接；fixed 不需要 |
| 供给器缝 | `services/provisioning/` | 能力声明/询价/创建/释放/健康，四个方法一个注册表 |

## §2 架构导览

### 2.1 数据模型：连接是"插座"，凭据是"电表"，池是"用电合同"

`Connection`（`backend/app/models/resources.py:24-63`）刻意不存密钥：`credential_id` 外键指向既有的加密 `credential` 行（`kind='resource'`），表里只有 provider、region、能力清单、验证状态。用生活化的话说：**插座上只贴"这是 220V 两孔"，电表读数（密文）锁在配电间**。`UniqueConstraint(tenant_id, name)`（`:49`）保证同租户不重名；`(tenant_id, project_id)` 与 `(tenant_id, credential_id)` 两条复合外键（`:50-61`）把"跨租户借用凭据"在数据库层堵死。

`ResourcePool`（`:66-125`）新增的十列分成三组：**供给合同**（`connection_id`、`provisioning_mode`、`instance_config_json`）、**容量边界**（`min_capacity`、`max_capacity`）、**运行时快照**（`price_usd`、`capacity_reason`、`last_checked_at`、`next_check_at`）。后一组是"控制器写、API 只读"的派生状态，和配置列混在同一张表里——简单，但读写边界只能靠代码纪律（`api/resources.py:1-15` 的模块注释明确声明了这一点）。

`ResourceEvent`（`:205-242`）是"公告板"：`(tenant_id, dedupe_key)` 唯一（`:226-228`），重复 tick 想写同一条会被 `append_resource_event` 的预查询挡掉（`capacity_control.py:370-378`）。注意 `dedupe_key` 可为 NULL，而唯一约束对 NULL 不生效——设计上"需要去重的事件必须给键"，靠调用方自觉。

### 2.2 迁移：一次"加列 + 回填 + 重建表"

`0012`（`backend/migrations/versions/0012_resource_connections.py`）做两件事：建 `connection` 表（`:85-139`），给 `resource_pool` 加十列并补 FK/CHECK（`:141-179`）。因为 SQLite 不能 `ALTER` 外键和 CHECK，走了 `batch_alter_table` 重建（`:141-158`），PostgreSQL 走普通 ALTER（`:159-179`）——这是本仓库既有的双档套路。

回填靠 `server_default`：`provisioning_mode` 默认 `fixed`（`:62-67`）、`min_capacity` 默认 0（`:68`）、`max_capacity` 默认 **50**（`:69`）。SQLite 的 batch 重建与 PG 的 ADD COLUMN 都会把默认值写到既有行，所以"旧池回填 50"确实生效（§6.12 讨论为什么是 50、以及注释为何自相矛盾）。

`0013`（`:32-82`）建事件表；外键对 pool/connection 用 `ondelete=CASCADE`（`:54-65`），删池即删账本。降级按逆序 drop（`0012:182-195`），本次迁移往返测试已覆盖。

### 2.3 校验：先问"配套吗"，再问"数字合理吗"

`validate_pool_configuration`（`backend/app/services/resources.py:164-262`）是全 PR 的"合同审查员"，顺序被测试钉死（`test_resource_connections.py:318`，`test_connection_checks_win_over_capacity_checks`）：

1. 模式合法（`:186-192`）；
2. spot 必须有连接（`:194-200`）→ 连接必须声明 `ecs:spot`（`:202-209`）→ 池 `provider_key` 必须等于连接 provider（`:211-217`）；
3. 容量边界 `1 <= max`、`0 <= min <= max`（`:219-236`）；
4. 价格阈值必须是正 Decimal（`:238-254`）；
5. fixed 到此为止直接返回（`:256-257`）；spot 才继续查凭据是否 `kind=resource`、未撤销、同租户（`:259-262`）。

**顺序即语义**：一个既缺连接、容量又填错的请求，返回的是 `connection_missing` 而不是 `pool_capacity_invalid`。测试明确断言了这一点，属于有意选择——用户先解决"没插座"再谈"用电额度"。

### 2.4 供给器缝：四个动作 + 一个注册表

`backend/app/services/provisioning/__init__.py` 定义 `Provisioner` Protocol（`:106-149`）：`capabilities` / `quote` / `create` / `release` / `health`。关键契约写在 docstring 里：**create/release 只改调用方 session、绝不 commit**（`:110-112`），事务边界归控制器（`capacity_control.py:586-600`）。注册表是模块级 dict（`:152-175`），测试和 worker 启动可重置——**多进程下这是每进程一份**，不是共享状态，M4-04 接真实供给器时要记得在 worker 进程里显式注册，否则 `get_provisioner` 永远返回 None（表现是池一直 `provisioner_unavailable`）。

`FakeProvisioner`（`fake.py:44-134`）把所有故障做成构造参数：`available=False` → 库存不足、`create_error` → 创建失败、`release_error` → 释放失败（`:127-131` 状态不变）。实例号来自模块计数器（`:30,33-37`），测试可断言精确值。它 `create` 出来的行状态是 **`requested`**（`:108-115`）——这个细节是"跨 tick 不重复扩容"的关键（§6.8）。

### 2.5 容量控制器：一道算术题、两条铁律、三种出口

`capacity_control.py` 的模块 docstring（`:1-23`）已经写清设计：

```
gap     = queued - idle - starting × runners_per_instance
current = live(online+busy) + starting
desired = min(max_capacity, current + ceil(gap / runners_per_instance))
```

实现在 `_build_state`（`:264-323`）：`queued` 数"该池下仍 queued 的 attempt"（`:152-177`，经 case_run→run 两跳 join 到 `EvalRun.resource_pool_id`）；`idle` 只数 `status=online` 且心跳新鲜的 runner（`:180-198`）；`live` 数 `online+busy`；`starting` 数 `requested/creating/registering` 的实例（`:201-212`）。缺口在 `:291` 夹到非负。

两条铁律：

- **等待永不失败用例**：价格超阈值/库存不足/供给器报错，只写 `capacity_reason` 与事件（`:403-426`、`:648-655`），`_scale_up` 捕获 `ProvisionerError` 后 `break`（`:449-464`），不碰 attempt 状态；
- **先摘牌再退租**：`_scale_down` 里 runner 先 `draining` 再 `offline` 再 `release`（`:530-543`），并在 release 前 flush（`:533,536`），让顺序可被测试观测。

三种出口由 `_capacity_reason`（`:237-261`）决定：`gap>0` 时依次看价格→库存→供给器缺失→正常扩容；`gap==0 且 idle>min` 时缩容；否则无动作。

### 2.6 API 与权限：成员可读、管理员可写、容量只读

`backend/app/api/resources.py` 把路由分两半：`GET` 挂 `require_session`（`:270,351,412,497`），写操作与"测试连接/测试供给"挂 `require_admin`（`:290,323,368,436,515`）。`main.py:56` 又统一加了一层 `require_session`，属于"双保险"。

`test-provisioning`（`:511-609`）是唯一会产生真实费用的端点：先查 `confirm_cost`（`:519-525`），再查模式/供给器/连接（`:526-552`），然后 `quote` + `create`（`:554-563`），最后写资源事件 + 审计（`:569-592`）。

### 2.7 Worker 接线：每轮一次、按池限流

`worker/main.py:59-76` 的 `capacity_once` 只是薄封装：调 `reconcile_pools`，有计数才打印。主循环 `:148-156` 把它放在 reconcile 与 runner 清扫之间，异常被兜住不影响其它阶段。`reconcile_pools`（`capacity_control.py:690-751`）只扫 `status=active AND provisioning_mode=spot` 的池（`:716-725`），用 `next_check_at > 本轮时间` 跳过未到期的池（`:727-729`），**逐池 commit**（`:740`），单池异常 rollback 后继续（`:741-744`）。

## §3 数据流走查：从"配一个竞价池"到"自动退租"

**第 1 幕 · 登记插座（管理员）**
`POST /api/v1/connections`（`api/resources.py:287-317`）→ `_credential_failure`（`:147-157`）查凭据存在/同租户/`kind=resource`/未撤销 → 组装 `Connection(capabilities_json={"capabilities": [...]})` → `_commit_or_conflict`（`:255-260`）把唯一键冲突翻译成 409 → 返回 `connection_payload`（`services/resources.py:265-288`），只有 `credential_mask`，没有 `ciphertext`/`key_version`。

**第 2 幕 · 验插座**
`POST /connections/{id}/test`（`:320-341`）→ 取注册表里的 provisioner，没有就 422 `provisioner_unavailable`（这解释了 PR 边界里"M4-04 前 aliyun 连接测试返回该错误"）→ `verify_connection`（`services/resources.py:315-340`）比对"连接 provider == 供给器 provider"且"声明能力 ⊆ 支持能力"，写 `verified/failed` 与 `last_verified_at`。

**第 3 幕 · 签用电合同**
`POST /resource-pools`（`:365-406`）→ `_resolve_connection_for_write`（`:233-246`，跨租户返回 422 而非 404，隐藏存在性）→ `validate_pool_configuration`（`services/resources.py:164-262`）→ 落库，`provider_key` 对 spot 取连接 provider、对 fixed 取字符串 `"fixed"`（`:249-252`）。

**第 4 幕 · Worker 心跳里的算术**
`worker/main.py:148-156` → `reconcile_pools`：取 active spot 池 → 按 `next_check_at` 过滤 → 每个池取注册表 provisioner → `reconcile_pool`（`capacity_control.py:586-687`）：
1. 取连接（`:215-218`）、询价（`:221-234`，spot 无连接直接 None）；
2. `_build_state` 算 queued/idle/live/starting/gap/desired/reason（`:264-323`）；
3. 把 `price_usd / capacity_reason / last_checked_at / next_check_at` 写回池（`:615-619`）；
4. `reason==scale_up` → `_scale_up`：`headroom = max − current`，`needed = ceil(gap/slots)`，`batch = min(headroom, needed, settings.eval_capacity_batch_size)`（`:439-442`），逐台 `provisioner.create`，中途 `ProvisionerError` 改记 `resource_provisioning_failed` 并 `break`（`:449-464`）；
5. `reason==scale_down` → `_scale_down`：`excess = idle − min`（`:519`），挑最新的空闲 runner（`:483-507`），draining→offline→release，失败记 `resource.release_failed`（`:544-560`）；
6. 无条件写 `resource.capacity.updated`（`:658-676`），去重键 = `池:capacity:原因:缺口:价格`（`:392-395`）；
7. 返回 state + `scaled_up/scaled_down`，worker 逐池 commit。

**第 5 幕 · 控制台看账**
`GET /resource-pools/{id}`（`:409-429`）→ `pool_payload` + 实时 `capacity_state`（`pool_capacity_state`，只读不写，`:326-347`）+ 最近 20 条事件 + runner 状态汇总。`capacity_state` 里的 `price_usd/price_threshold_usd/capacity_reason/next_check_at` 就是设计 06 §6.1 要求"资源池与评测页展示"的那组字段。

## §9 文件级代码分析

### 9.1 `backend/app/models/resources.py`（M，188 → 242 行）

**职责**：资源域的五张表——连接、池、Runner、实例、事件。变更形态 M：新增 `Connection` 与 `ResourceEvent` 两张类，`ResourcePool` 加十列与两条 CHECK。

**关键依赖**：SQLAlchemy 2.0 声明式 `Mapped/mapped_column` + 仓库自定义的 `tenant_fk()`/`json_type()`/`TimestampMixin`。比喻：这是"数据库表的施工图"，`tenant_fk()` 相当于每张表都预埋的"门牌号"字段，所有业务查询都靠它做租户隔离。

**变更代码块**

```python
# 旧（M4-01 时代）：池只有配置壳
class ResourcePool(...):
    provider_key, runner_group, labels_json, status

# 新：三类列 + 两条 CHECK
connection_id / provisioning_mode / min_capacity / max_capacity
instance_config_json / price_threshold_usd / price_usd
capacity_reason / last_checked_at / next_check_at
CheckConstraint("max_capacity >= 1 AND min_capacity >= 0 AND min_capacity <= max_capacity")
```

为什么这么写：把"配置"与"运行时快照"放同表，读一次池就能渲染控制台；CHECK 把非法容量挡在数据库层，API 的 422 只是更友好的第一道门（`services/resources.py:230-236`）。代价是读写边界靠约定——`api/resources.py` 声称容量字段"控制器是唯一写者"，但数据库层没有只读视图保护。

`Connection` 的三条外键（`:50-61`）值得单独一提：`(tenant_id, project_id)` 与 `(tenant_id, credential_id)` 都是**复合外键**，因为被引用表的主键是 `(tenant_id, id)` 形式；这保证"连接必须与凭据同租户"，是比应用层校验更强的那道保险。

**检视发现**：`max_capacity` 默认 50 与 `startswith` 式回退共同造成 §6.2 的回归；`ResourceEvent` 的 `dedupe_key` 可空 + 唯一约束（`:223-228`）在 SQL 标准里对 NULL 不去重，属于"调用方必须给键"的隐含契约，建议 docstring 已写（`:211-213` 确实写了），可接受。

### 9.2 `backend/app/services/capacity_control.py`（A，751 行）

**职责**：容量控制器——读状态、算缺口、扩/缩容、写事件。

**关键依赖**：无第三方包，纯 SQLAlchemy + 标准库 `math.ceil`/`Decimal`。比喻：它就是 §1 的"网约车调度员"，`reconcile_pools` 是"巡场"，`reconcile_pool` 是"看一个站点"，`_scale_up/_scale_down` 是"派车/退车"。

**变更代码块**（新增文件，按逻辑段讲）

```python

current_size = live + starting
```

在途实例已经"预定"了未来座位，所以要从缺口里扣；否则每个 tick 都会为同一批乘客再派一次车。这是全文件最核心的一行，`test_capacity_control.py:261-300` 用 `5 − 1 − 1×2 = 2` 钉住了它。

```python

if quote is not None and threshold is not None and quote.price_usd > threshold:
    return REASON_PRICE_ABOVE_THRESHOLD
```

顺序即用户体验：贵是第一解释，其次是"没货"，最后才是"没有供给器"。`>` 而非 `>=`，与设计"高于阈值"一致（等于阈值放行）。

```python

runner.status = "draining"; session.flush()
runner.status = "offline"; runner.deregistered_at = now; session.flush()

try: provisioner.release(...)
except ProvisionerError: append_resource_event(EVENT_RELEASE_FAILED, ...)
```

`flush` 不是装饰：它让"摘牌"在 release 之前真正落库，测试才能记录到 `runner_status == "offline"`。但见 §6.3——失败后没有下一轮。

```python

f"{pool.id}:capacity:{reason}:{state['capacity_gap']}:{state['price_usd']}"
```

价格参与去重意味着"价格每变一次就多一条事件"，在竞价场景下这是**有意**的可观测性（用户要看价格波动），不是刷屏 bug。

**实现思路总结**：状态查询与决策分离（`_build_state` 纯读、`reconcile_pool` 唯一写者）；失败一律降级为"原因 + 事件"；跨 tick 幂等靠"在途实例计数 + 去重键"两道。

**检视发现**：§6.3（释放泄漏）、§6.5（无锁）、§6.6（min 语义）、§6.7（drain 瞬时）、§6.9（next_check）、§6.10（Decimal 类型）均在此文件。另：`reconcile_pools:741` 的宽 `except Exception` 会在吞掉编程错误的同时让该池整轮无事件，建议至少 `logger.exception` 或写一条 `resource.reconcile_failed` 事件，否则排障只能靠"池子不动了"。
