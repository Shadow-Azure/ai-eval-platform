## §1 一页速览

一句话：**给平台装上"Runner 值班表"——已部署的 heartbeat agent 每 30 秒来签到一次，平台记录它在不在岗、忙不忙、手上是什么活；超时没签到就翻成离线，恢复签到自动回岗，同一时刻每个 Runner 只允许领一件活。**

比喻：heartbeat agent 是跑步打卡的员工，`/runner/v1/runners/heartbeat` 是打卡机（顺带完成入职登记：第一次打卡自动建档），`runner` 表是值班表，sweep 是"超过 90 秒没打卡就画离线"的值班经理，case 回调是员工领取/完成任务的工单回执。

## §2 架构导览

### 2.1 心跳入口即注册（为什么不需要单独注册 API）

已部署 agent 的行为是"每 30 秒 POST 一次心跳"，不区分首末。平台把首跳心跳当注册：`ensure_fixed_pool`（services/runners.py:55）先保证默认租户/项目下存在固定池 `fixed-linux`（provider_key=fixed），`record_runner_heartbeat`（:110）按 `(resource_pool_id, provider_runner_id)` 唯一键 upsert——新 runner 建档（registered_at），老 runner 更新名字/标签/状态。两个并发首跳撞唯一约束时 IntegrityError 兜底重查（:87-97），保证幂等。

### 2.2 状态机与单 Job 约束

转移规则在 record_runner_heartbeat（:132-146）：

```text
busy 心跳：已有绑定且≠来者 → RunnerBusyConflict(API 层映射 409)
          否则绑定来者
online/offline 心跳：释放绑定
最后统一：status=入参，last_heartbeat_at=now
```

同一 Runner 并发一个 Job 的约束就是这个绑定冲突：agent 用环境变量 `RUNNER_CURRENT_CASE_ATTEMPT_ID` 声明在忙（heartbeat.mjs:17 buildPayload），case 契约回调 `bind_case`（:184）用同一字段做二次防线——两条路都通向同一个唯一绑定。

### 2.3 超时 → offline（两条触发路径)

- 惰性：GET /api/v1/runners(/{id}) 先跑 sweep（api/runners.py:93-107），控制台打开就看到真实状态。
- 主动：worker 每轮 sweep_once（worker/main.py:26,61），无人查询也翻转。
sweep（services/runners.py:160）只动 online/busy 且 last_heartbeat_at 早于超时线的行；**offline 保留 busy 绑定**（设计 06 §7"迟到结果按 attempt 状态处理，不覆盖取消事实"的 Runner 侧对应物），恢复心跳后回到 online。

### 2.4 契约消费：schema 文件是唯一事实源

`runner_contracts.py` 直接读 `runner-contract/schemas/v1/*.schema.json` 原文件校验（load_schema :62，schema_dir :40 按 env→repo→cwd 三级定位，Dockerfile 因此 COPY runner-contract）。validate（:108）实现 node 参考实现同款关键词子集（type/const/enum/required/additionalProperties/min-max/pattern/format），两侧语义由同一批 fixtures（tests/fixtures/runner）钉住。case 回调（api/runners.py:161）先 schema 校验（422 contract_invalid）、再校验 payload.case_run_id 与路径一致（:172-180）、最后按 x-runner-id 折入 Runner 状态——heartbeat/uploads 绑定、completed/failed 释放。

### 2.5 鉴权：一个 token，两处使用

`require_runner_token`（api/runners.py:42）读配置 `runner_heartbeat_token`（config.py:32，env 键与主机 runner.env 同名）；已配置时心跳与 case 回调都要 `Bearer <token>`，未配置（开发态）开放。主机部署 .env 已预置同名键，合并部署后自动启用。

### 2.6 bootstrap 的幂等观

bootstrap.sh 三个安装函数（install_agent :52 / merge_env_file :135 / install_unit :165）都是"内容 cmp 相同→零动作"，变化才写+重载：unit 变→daemon-reload+restart；仅 env 变→restart 使 EnvironmentFile 生效；agent 变但未 SYNC_AGENT=1→保留主机现场并提示（AGENT_DRIFTED :121）。`RUNNER_INSTALL=1`(:239) 是注册 GitHub runner 的显式门，默认运行绝不触碰已有 actions.runner 服务。**实现教训已固化在测试里**：初版把 bash 返回码语义写反（if 中 0=真=THEN，"无变化"被当"有变化"），改为全局状态变量（ENV_CHANGED/UNIT_STATE/AGENT_STATE）后由 11 项沙箱测试钉住。

## §3 数据流走查（主机端到端剧本）

1. systemd 每 30s 拉起心跳（eval-platform-heartbeat.service → heartbeat.mjs main 循环）。
2. agent 组装 `{runner_id, name, labels, status=busy?busy:online, current_case_attempt_id}` POST `/runner/v1/runners/heartbeat`，Bearer RUNNER_HEARTBEAT_TOKEN。
3. 平台 api/runners.py:59 验 token → record_runner_heartbeat 建档/更新 → 200 `{"ok":true,"status":"online",...}`。
4. GitHub workflow（eval-shard.yml）落到该 Runner：make-eval-dispatch 生成 v1 dispatch/manifest/token（file:// manifest + digest）→ synthetic-task.mjs 校验 dispatch→验签→拉 manifest→逐 case 心跳/上传/完成回调 `POST /runner/v1/case-runs/{case_run_id}/...`。
5. 平台校验契约 schema → bind/release Runner 绑定 → 控制台 GET /api/v1/runners 看到 busy→online 的完整轨迹。
6. 停心跳服务 90s+ → sweep 翻 offline（绑定保留）→ 服务恢复 → 下一跳回 online。

## §6 讨论点（预判供拍板，结论留空）

1. **case 回调鉴权口径**（api/runners.py:135-161）
   现象：契约回调复用 runner 面 Bearer token；synthetic-task 的 RUNNER_TASK_TOKEN 是另一 HMAC 体系，无法同时通过两套校验。
   问题：M2-05 引入平台签发短期 token 前后，鉴权如何统一？
   预判：M2-04 维持 runner 面共享 token（最小闭环），M2-05 签发 attempt-scoped token 后废弃共享口；已在 PR 遗留清单声明。
   结论：
2. **eval-shard.yml 的 development-only-secret**（.github/workflows/eval-shard.yml:66）
   现象：demo task token 用固定 dev secret 在 workflow 内自签自验。
   问题：是否会被误当成生产口径？
   预判：合成任务无敏感数据、token 不出 runner temp；workflow 注释已声明 M2-05 替换为 OIDC/短期 token。
   结论：
3. **bootstrap 的 RUNNER_INSTALL 分支未真机验证**（bootstrap.sh:239-268）
   现象：注册路径只被沙箱测试覆盖"默认不触发"；目标主机已有 runner，不需注册。
   问题：新固定机器到位后这条路径是否可直接用？

## §9 文件级代码分析（关键文件）

### backend/app/services/runners.py（A）
职责：Runner 状态机唯一写入点。变更块：`record_runner_heartbeat` 把"注册"折叠进心跳（upsert + 转移 + 打点一次完成）；`bind_case/release_case` 让契约回调与心跳共享同一绑定字段。已知弱点：状态转移未抽成显式转移表，规则内联在 if/else——当前仅 3 状态 4 边，抽表是过度设计；M2-05 接 attempt 状态机时可合并抽象。sqlite/PG 时区差异用 `_aware` 归一（naive 视作 UTC），CI 的 PG 与本地 sqlite 双侧验证通过。

### backend/app/api/runners.py（A）
职责：协议边界。亮点是错误信封与 M2-01 风格一致（`{"error":{code,message,request_id}}`）；409/422/404 语义在测试中逐条钉死。依赖注入 get_session/get_settings 与现有路由同构，无新框架行为引入。

### infra/runner/bootstrap.sh（A）
职责：把"一台新固定机器"和"已部署主机重入"统一成一个入口。幂等三函数 + 显式注册门 + 自检模式。关键依赖：systemd/curl/tar 属目标机 OS 件；heredoc 内嵌 agent 副本保证单文件可用（ssh 'bash -s' 场景主机无 repo）。已知弱点：env merge 的 awk 逐行重写在含反斜杠值时会转义失真——当前六键（URL/label/interval/token）均无反斜杠，无实害。

### tests/runner-heartbeat-agent.test.mjs（A）
职责：把主机已部署 agent 的行为固化为 repo 契约（sha256 pin + payload/路径/鉴权/超时断言）。这是"主机零改动接入"承诺的回归防线。
