## 2. 架构导览

### 2.1 源排序：先探测，再决定先试谁

`dataset_images.py:598` 的 `order_sources_by_health` 并行探测每个 enabled 源的 manifest（复用已有 `probe_source`）。`404`、`401/403`、`429` 分别映射为 `NOT_FOUND`、`AUTH_REQUIRED`、`RATE_LIMITED`，进入 `UNUSABLE_SOURCE_STATUSES` 后不再尝试。探测成功（200）的源按 `_source_rank` 排序：先看历史成功率，再看历史吞吐，最后看本次 TTFB；探测异常（超时/连接失败/5xx）保留为 fallback，因为探测失败不等于 pull 一定失败。

`_source_rank` 使用的历史数据在 `dataset_images.py:119` 的内存字典里，`record_source_result` 在 `dataset_image_prep.py:502` 和 `:525` 分别记录失败和成功。它是 per-process 的，重启后清空；这是有意的第一版取舍。

### 2.2 预热：把「入队」从 prepare 里拆出来

`dataset_image_artifacts.py:139` 先按版本查全部 case key，再复用 `resolve_preparation_images` 的镜像解析规则（case 级 `environment_image` → 版本级 → adapter 派生）。`warmup_version_images` 调 `readiness(recheck=True, enqueue=True)`：先 HEAD 一遍 OSS，缺失的转 `preparing`，已就绪的不重复拉。`datasets.py:618` 把它包成管理员接口；`readiness` 新增 `enqueued_count`，只统计本次真正从非 preparing 进入队列的行（`:412`）。

### 2.3 worker 并发：进程内线程池，而非多副本

`worker/image_prep.py:250` 用 `ThreadPoolExecutor` 启动 1–4 个任务，每个任务由 `_prepare_task` 开自己的 `SessionLocal`。数据库侧仍由 `claim_preparing_artifact` 的 `FOR UPDATE SKIP LOCKED` 保证不重复领取；临时 tar 路径按镜像 sha256 派生，不同镜像不会互相覆盖。sweep 只在 `pending` 为空时执行（`:292`），所以不会删除另一个任务正在写的 tar。`idle` 标志（`:254`）避免「一个长拉取 + 多个空任务」时反复查库。

### 2.4 部署与文档

`deploy/docker-compose.prod.yml:245` 给 DinD 加 `--max-concurrent-downloads=8`，`:283` 给 worker 注入并发默认 2、源探测默认开启、探测超时 4 秒。`docs/architecture.md:63` 描述现状，`:73` 补上「Squid 同机同出口且不缓存，Docker registry CONNECT 被拒绝」的结论。

## 3. 数据流走查

### 3.1 预热（新增入口）

管理员 `POST /api/v1/dataset-versions/{id}/images/warmup` → `warmup_version_images` → 查该版本全部 `DatasetCase.case_key` → 解析唯一镜像集合 → `readiness(recheck=True, enqueue=True)` 逐镜像 HEAD OSS → `missing/failed` 行改为 `preparing`、`next_attempt_at=now` → 返回 `enqueued_count` 与 artifacts readiness（含 worker 心跳、queued/processing 计数）。**没有** eval preparation 也能走通，这是 #439 里「未发起评测就不预热」缺口的直接补法。

### 3.2 单镜像准备（已有主线的变化）

worker 领取一行 → `prepare_one` 读 `effective_sources` 并 `rollback` 释放读事务 → 若开启探测，`order_sources_by_health` 并行探测 → `candidate_ref_pairs` 按排序后的源生成 ref → 逐源 `docker pull`（失败记录统计并换源）→ `docker tag` 到规范 ref → `docker image inspect` 取本地镜像字节 → `docker save | gzip -1` 写临时 tar → 内网 OSS `put_file` → HEAD 校验 → 标 ready → 清理本地镜像和 tar。pull/save/upload 三段耗时与源、tar 大小写入 `PrepareOutcome`，worker 打成一行日志；源探测结果和源统计另打 JSON 行。

### 3.3 并发与 sweep

启动时先 `sweep(startup=True)`，再开线程池。之后主循环只在 `sweep_due=False` 且 `idle=False` 时补任务；一旦到 10 分钟 sweep 点，不再提交新任务，等当前任务全部结束、`pending` 为空后执行 sweep，再继续。这样「连续有队列」时也能定期清残留，同时不碰活跃 tar。

## 6. 讨论点

### 6-1 流程优先级从 P1 改为 P2

- **位置**：`.agents/flow/issues/m8-image-pull-throughput.md:9`
- **现象**：issue 正文和调研文档把它写作 P1，但 PR 里登记为 P2。
- **问题**：m8 当前 P1 只剩 `m8-spot-oss-image-tarball` 一个未 done；新增一个 P1 会让「最高未清档剩 2 个」，按 `flow-lib.mjs` 的规则锁住已完成的 61 个 P2 issue，`verify:flow` 直接失败。
- **预判**：把本次工作登记为 P2、随当前 P2 阶段推进，比回改 61 个历史 issue 或放宽门禁更小；P1 的严重度仍记录在 GitHub issue 正文和调研文档里。
- **结论**：（留空）

### 6-2 源吞吐统计只在内存里

- **位置**：`backend/app/services/dataset_images.py:119`
- **现象**：成功率/累计字节/累计秒数在进程内字典，worker 重启即清空。
- **问题**：长时间运行的 worker 能积累足够样本；但每次部署/重启后第一批评测又回到「只看 TTFB」。
- **预判**：第一版先不引入 DB/Redis 迁移，日志已经能回放每个源的实测；若后续需要跨重启排序，再把统计落到 `service_heartbeat.detail_json` 或独立表。
- **结论**：（留空）

### 6-3 预热入口没有前端按钮

- **位置**：`backend/app/api/datasets.py:618`
- **现象**：只提供管理员 API，没有 console 按钮。
- **问题**：原型里没有「按版本预热」的交互稿，本期 scope 也不含 `web/**`；operator 目前要用 curl/API 调用。
- **预判**：先把后端入口和 readiness 打通，等 prototype 补交互后再加按钮；不建议在本 PR 里自创 UI。
- **结论**：（留空）

### 6-4 没有真实吞吐基准

- **位置**：PR 描述「限制」段
- **现象**：本机没有 Docker daemon/OSS 凭据，未跑三镜像真实拉取。
- **问题**：issue 验收要求「可量化改善」，目前只能证明代码路径和队列行为，不能证明公网源上的实际倍数。
- **预判**：合并后在部署 ECS 上按调研文档的验证计划跑 1/2 路并发与源排序对照；如果实测没有改善，再考虑 skopeo/层缓存。
- **结论**：（留空）

### 6-5 多副本 sweep 仍未隔离

- **位置**：`backend/app/worker/image_prep.py:245`、`backend/app/services/dataset_image_prep.py:606`
- **现象**：启动 sweep 会回收所有 `preparing` 行、清理工作目录下所有 tar；本次只保证单进程内 1–4 个任务安全。
- **问题**：若有人把 image-prep 扩成 2 个副本，第二个副本启动时可能重置第一个副本的活跃行。
- **预判**：部署脚本和文档仍按单副本使用；真正要多副本时，应把 sweep 改成按 `lease_owner` 前缀/按 host 工作子目录隔离，这比在线程池里继续堆逻辑更合适。
- **结论**：（留空）

### 6-6 探测跳过 401/429 的边界

- **位置**：`backend/app/services/dataset_images.py:563`
- **现象**：manifest 返回 401/403/429 时直接跳过该源。
- **问题**：个别镜像站的 manifest 需要认证，但 `docker pull` 可能用匿名 token 成功；429 也可能只是瞬时。
- **预判**：先按「探测不可用就跳过」的保守策略，日志保留 HTTP 状态；如果实测发现误杀，再把 401/429 降级为 fallback 而不是 skip。
- **结论**：（留空）

## 9. 文件级代码分析

### 9.1 `backend/app/services/dataset_images.py`

职责：从「按配置顺序盲试源」升级为「探测 + 历史吞吐 + TTFB 排序」。变更形态 M。

关键依赖：`httpx` 是运行时 HTTP 客户端；`ThreadPoolExecutor` 让 8 个 manifest 探测并行，最坏等待从 8×timeout 降到约 1×timeout。`threading.Lock` 保护进程内统计字典。

旧代码（无排序）：

```python
def candidate_ref_pairs(image, sources):
    ...
```

新代码（排序后再生成 ref）：

```python
found = sorted(
    (probe for probe in probes if probe.status == FOUND),
    key=lambda probe: _source_rank(probe, stats),
)
transient = sorted(..., key=lambda probe: _source_rank(probe, stats))
ordered = [probe.source for probe in (*found, *transient)]
```

实现思路：探测只决定顺序，不替代 `candidate_ref_pairs` 的镜像路径重写；真正 pull 的 ref 仍由已有函数生成，避免把「源排序」和「镜像名归一化」耦在一起。

检视发现：统计键用 `source.name`，依赖管理员给源起唯一名字；目前 API 只校验 registry/prefix 不重复，不校验 name。若同名，统计会合并（不影响拉取正确性，只影响排序）。可接受。

### 9.2 `backend/app/services/dataset_image_prep.py`

职责：单镜像准备主流程。变更形态 M。

旧代码：

```python
candidates = candidate_ref_pairs(image, effective_sources(session, settings))
...
for source, candidate in candidates:
    try:
        docker.pull(candidate, platform)
    except Exception as exc:
        ...
```

新代码：

```python
sources = effective_sources(session, settings)
session.rollback()
if settings.dataset_image_prep_source_probe_enabled and sources:
    ordering = order_sources_by_health(..., stats=source_stats_snapshot())
    sources = ordering.sources
candidates = candidate_ref_pairs(image, sources)
...
attempt_started = time.monotonic()
try:
    docker.pull(candidate, platform)
except Exception as exc:
    record_source_result(source.name, seconds=..., success=False)
```

实现思路：把「探测」放在 `rollback` 之后，避免多分钟的探测/拉取期间占着读事务；每个源尝试单独计时，成功源另记 `pull_attempt_seconds`。`docker image inspect` 取本地镜像字节，失败返回 `None`，不影响成功路径。

检视发现：`pull_seconds` 是「从第一个源开始到成功源结束」的总时间，包含失败源耗时；`source_stats` 用的是成功源单次耗时。两个指标口径不同，但日志字段名能区分（`pull_s` vs `source-stats`），可接受。

### 9.3 `backend/app/worker/image_prep.py`

职责：worker 生命周期与并发调度。变更形态 M。

旧代码：

```python
while not _STOP:
    with SessionLocal() as session:
        outcome = prepare_one(session, settings, docker=docker)
    ...
    time.sleep(poll_seconds)
```

新代码：

```python
with ThreadPoolExecutor(max_workers=concurrency) as pool:
    pending: set[Future] = set()
    idle = False
    while not _STOP:
        sweep_due = ...
        if not sweep_due and not idle:
            while len(pending) < concurrency:
                pending.add(pool.submit(_prepare_task, settings, docker))
        ...
        done, pending = wait(pending, timeout=poll_seconds, ...)
```

实现思路：用 `idle` 区分「队列空」与「有长任务在跑」，避免多个空任务反复查库；`sweep_due` 时停止补任务，等 `pending` 清空再 sweep。

检视发现：`idle` 是一个布尔状态机，逻辑可读但不容易单测；本期只测了 `preparation_concurrency` 的边界。若后续频繁改调度，建议抽出 `run_loop()` 注入 fake executor 做单测。

### 9.4 `backend/app/services/dataset_image_artifacts.py`

职责：预热入口的解析与入队。变更形态 M。

新代码：

```python
def resolve_version_images(session, version, settings=None):
    case_keys = list(session.scalars(select(DatasetCase.case_key).where(...)))
    return resolve_preparation_images(session, version, case_keys, settings)

def warmup_version_images(session, version, settings=None):
    refs = resolve_version_images(session, version, settings)
    return readiness(session, refs, settings, recheck=True, enqueue=True)
```

实现思路：复用已有解析规则，避免为预热再造一套镜像命名逻辑；`enqueued_count` 只统计非 preparing→preparing 的转移，重复预热不会虚报。

检视发现：`readiness` 的 `recheck=True` 会 HEAD 所有镜像；如果 OSS 慢，预热接口会慢，但它是管理员显式操作，可接受。

### 9.5 `backend/app/api/datasets.py`

职责：新增管理员预热路由。变更形态 M。

```python
@router.post("/api/v1/dataset-versions/{version_id}/images/warmup")
def warmup_dataset_version_images(...):
    version = dataset_service.get_dataset_version(session, version_id)
    result = artifact_service.warmup_version_images(session, version, settings)
    session.commit()
    return result
```

实现思路：版本不存在复用统一的 404；权限用 `require_admin`，因为一次预热可能触发大量拉取；响应直接复用 readiness，前端无需新契约。

检视发现：没有调用 `reap_stale_preparing`，与 ensure 的行为略不一致；但预热的主要路径是「missing 行入队」，陈旧 preparing 行由 ensure/worker sweep 处理，本期不改。
