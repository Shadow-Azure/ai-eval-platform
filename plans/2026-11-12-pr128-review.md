## §1 一页速览

一句话：这个 PR 把“Runner 上传了一组原生轨迹文件”变成“平台能按 attempt 判断某文件是否可信、解析过、失败在哪一行，并可安全重放”，同时不改变评分结果和执行终态。

一个比喻：它像邮局分拣中心。OSS 原件是已经盖过章的包裹，`trace_file` 是包裹登记簿，Worker 是只能领取有限数量包裹的分拣员；分拣员先核对重量（size）和指纹（sha256），再拆包，拆坏一个包裹不会让整批停摆。`trace_session/span` 是整理后的可浏览清单，旧清单只在完整新清单准备好后才整批替换。

| 交付块 | 用户/系统得到什么 | 证据 |
|---|---|---|
| 三张版本化表 | 原件、session、span 均可按 tenant+attempt 追溯 | `backend/app/models/trace.py:34` |
| 幂等入队 | 同 digest+parser_version 不重复登记 | `backend/app/services/trace_ingestion.py:131` |
| 租约与对象校验 | Worker 崩溃后能重领，旧 owner 不能误完成 | `backend/app/services/trace_ingestion.py:732` |
| 原子解析替换 | 升级失败保留旧树，成功才换新树 | `backend/app/services/trace_ingestion.py:1265` |
| 状态与事件 | failed/degraded/ready 可查询且去重通知 | `backend/app/services/trace_ingestion.py:1189` |
| 兼容与降级 | 旧单文件 manifest、坏行、未知版本都不伪装完整 | `backend/app/services/trace_parsers/generic.py:164` |

验证基线：PR 描述原记录为后端 577 collected、Runner 157 passed；当前 HEAD 在纳入 main 新增测试和本次 review 回归后，额外覆盖未知格式版本、15 条 eligible 分页恢复与 101 条跨页 backfill。远端基线 CI 7/7 通过，其中后端 CI 14m07s；冒烟修复后需重新确认最终 CI。

## §2 架构导览

### 2.1 数据边界：原件与派生树分开

`TraceFile` 保存 OSS 对象键、digest、size、Runtime/格式/parser 版本和租约；`TraceSession` 保存 native/root/parent 身份与关系证据；`TraceSpan` 保存有序事件、usage、属性与脱敏预览（`backend/app/models/trace.py:34`、`97`、`155`）。大内容字段已预留 `content_object_key`，当前只存预览，查看内容留给查询/查看器 issue（`backend/app/models/trace.py:177`）。

这张设计的重点是：派生树可以重算，原件不能丢。类似账本明细可以重新汇总，但原始票据仍要留存。

### 2.2 入队：回调只登记，不做重解析

完成回调在既有事务内调用 `enqueue_attempt`，只创建/修补 `pending` 行并设置 case 的待处理状态（`backend/app/services/case_attempts.py:672`、`718`；`trace_ingestion.py:202`）。异步解析包在 savepoint 中，失败只记录日志，不回滚评分与执行终态（`case_attempts.py:722`）。

唯一键是 `(attempt, sha256, parser_version)`（`models/trace.py:71`），所以重复回调是登记簿查重，不是再复制一份 session。

### 2.3 Parser：格式、版本和重放键分离

`ParserRegistry` 依据 Runtime、detected format 和 format version 选择 parser；`parser_version` 是重放键（`trace_parsers/__init__.py:43`）。通用 `raw-jsonl-1` parser 不猜 Runtime 专属父子关系，只建立安全的基础 session/span（`trace_parsers/generic.py:156`）。

本次 review 修复了未知版本边界：显式非 `1` 的 `format_version` 直接返回 degraded，不解析字节内容，也不生成猜测性 session（`generic.py:164`）。这对应设计 08 §9 的“格式版本未知 → failed/degraded，不启动猜测解析”。

### 2.4 Worker：领取、租约、隔离、结算

Worker 每轮按配置批次领取文件，先核对 size/sha256，再解析（`trace_ingestion.py:732`）。持久化前完成 owner 租约检查；派生树写入失败只会把当前文件标为 failed（`trace_ingestion.py:842` 附近）。Worker 主循环同时执行历史回填、待处理导入、崩溃窗口结算和原有 dataset import 清理（`backend/app/worker/main.py:167`、`180`、`195`、`222`）。

### 2.5 状态与事件：数据库是权威，事件只通知

状态按 `failed > incomplete > degraded > ready` 聚合；case 只接受最新 attempt 的条件更新。发布时先提交文件派生写入，再锁 case 行重读文件状态，inflight 时不发布终态（`trace_ingestion.py:914`、`1189`）。事件指纹包含文件状态与 parser 版本，不含原始行；并发 sequence 冲突会重新读取并重试（`trace_ingestion.py:1055`）。

这像公告板：Worker 可以同时贴通知，但公告板以数据库最终状态为准；重复通知会按指纹折叠。

## §3 数据流走查

1. Runner 完成回调提交 trace manifest。`finalize_completion` 合并对象并登记 `trace_status=pending`（`case_attempts.py:655`、`674`）。
2. 同一事务调用 `enqueue_attempt`，按 digest+parser_version 创建或复用 `TraceFile(pending)`（`trace_ingestion.py:202`）。
3. Worker 领取 pending 文件，比较对象字节长度和 sha256；任一不符只失败该文件（`trace_ingestion.py:783`、`803`）。
4. Parser 把原件整理成 `ParsedSession/ParsedSpan`；坏行记录行号但不把原文写入错误摘要（`trace_ingestion.py:812`；`generic.py:276`）。
5. 普通解析在单文件 savepoint 内替换；parser 升级先解析全部文件，再在整 attempt 事务中换树；失败调用 `_abort_upgrade` 保留旧树（`trace_ingestion.py:862`）。
6. 文件终态提交后，Worker 锁 case 行、重读 `trace_file`、聚合状态并发布去重事件（`trace_ingestion.py:1189`）。
7. 若 Worker 在文件写完与状态发布之间崩溃，`publish_stale_cases` 从 terminal file 重新结算；若旧回调早于本功能，`backfill_missing` 补建 pending 行（`trace_ingestion.py:1667`、`1760`）。
8. 前端拿到的最终依据仍是数据库查询；事件只用于通知刷新，不靠事件累加恢复。

## §6 讨论点

### 6.1 未知 `format_version` 曾会被当作 ready

**位置**：`backend/app/services/trace_parsers/generic.py:164`、`backend/app/services/trace_ingestion.py:842`。

**现象**：通用 parser 的 registry 声明接受 `*` 版本；修复前即使 manifest 写 `format_version=future-999`，仍会按 JSONL 产生 ready session。

**问题**：这违反设计 08 §9 的“未知格式版本不启动猜测解析”，可能把未来不兼容格式展示成完整轨迹。

**预判**：属于真实 Important，应保留当前 degraded 修复；不生成 session，仅保留原件和明确错误。

**结论**：

### 6.2 backfill 游标是否跨轮跳过 eligible attempt

**位置**：`backend/app/services/trace_ingestion.py:1667`、`backend/app/services/trace_ingestion.py:1760`。

**现象**：独立 task reviewer 提出两类分页怀疑：达到 `limit` 后游标是否跨调用跳过同 chunk 未处理记录；以及 `limit > 100` 时是否在首个满页后提前停止。

**问题**：跨调用跳过并不成立：15 条 eligible、`limit=10` 连续三轮返回 10/5/0，无生产代码修改即通过；游标不跨调用持久化，下一轮数据库筛选会排除已入队记录。`limit > 100` 则确有缺陷：旧代码用 `len(chunk) < target` 判耗尽，目标 101 时首个 100 条满页被误判为最后一页。

**预判**：跨轮部分为误报；`limit > 100` 部分为真实 Important，应把耗尽条件改为 `len(chunk) < chunk_size`，并补 101 条回归。

**结论**：已按 TDD 修复。101 条 eligible、`limit=101` 先只返回 100，改耗尽判定后返回 101；原 10/5/0 行为继续通过。

### 6.3 `content_object_key` 当前只有字段没有内容外置

**位置**：`backend/app/models/trace.py:177`、`backend/app/services/trace_parsers/base.py:41`。

**现象**：模型保留了大内容对象键，但本 PR 的通用 parser 只写脱敏 preview，不拆分大工具输出。

**问题**：issue #91 目标提到“大内容对象引用”；如果把它理解为本期必须端到端外置，则当前实现只完成数据位预留。

**预判**：设计 08 把按需读取与三栏查看器放在查询/查看层，PR 明确将此交给 #93/#94；本 PR 仍保留完整 OSS 原件，因此不阻塞轨迹可追溯。

**结论**：

### 6.4 结构化 JSON 的脱敏边界

**位置**：`backend/app/services/trace_ingestion.py:602`、`backend/app/services/trace_ingestion.py:664`。

**现象**：`relation_evidence_json`、`metadata_json`、`attributes_json` 由 parser 原样持久化；preview/error 已统一脱敏。

**问题**：当前通用 parser 写入的是控制字段，不泄露工具明文；未来 Runtime parser 若把完整工具参数放入属性，需要明确“parser 返回前必须脱敏”或持久化层递归清洗。

**结论**：

### 6.5 轨迹状态筛选拒绝 incomplete/degraded

**位置**：`backend/app/services/workbench.py:237`、`tests/backend/test_eval_workbench.py:202`。

**现象**：真实浏览器选择“已降级”后，前端请求 `trace_status=degraded`，后端返回 422，用例表持续显示加载骨架；`incomplete` 同样不在旧白名单。

## §9 文件级代码分析

### 9.1 `backend/app/models/trace.py`（A）

职责是把原始文件、session 和 span 分成三层，并把 tenant/attempt 归属放进复合外键。关键依赖是 SQLAlchemy 2 与 PostgreSQL JSONB；SQLite 测试用普通 JSON/Integer 变体，因此测试覆盖的是业务关系而不是 PostgreSQL 全部物理特性。

```python
# 新代码（概括）
UniqueConstraint("eval_case_attempt_id", "sha256", "parser_version")
ForeignKeyConstraint(["tenant_id", "eval_case_attempt_id"], ...)
Index("ix_trace_span_session_event", ..., unique=True)
```

“为什么这么写”：digest+parser_version 把幂等与重放绑定在一起；`native_session_key` 解决 Claude 子 Agent 复用根 sessionId；partial unique index 允许没有稳定 event id 的记录存在。

实现思路总结：原件可重放，派生行有确定唯一键，所有父子关联不跨 tenant。

检视发现：`content_object_key` 只有预留位，已登记为 #93/#94 边界。

### 9.2 `backend/app/services/trace_ingestion.py`（A）

职责覆盖整条流水线。关键依赖是对象存储抽象、SQLAlchemy savepoint/事务、Outbox 式事件模型。它相当于分拣中心调度器：先登记包裹，再领取、称重、拆包，最后统一更新公告板。

```python
# 旧代码（不存在）
completion -> score only

# 新代码
completion -> enqueue TraceFile(pending)
worker -> verify size/sha256 -> parse -> persist derived tree -> publish status/event
```

“为什么这么写”：异步与评分隔离，避免轨迹损坏阻塞已完成评测；文件级 savepoint 让单文件故障可修复；parser 升级采用 staging + 单事务替换，失败保留旧树。

实现思路总结：先验证再写入，先 stage 再替换，最后锁 case 发布状态。

检视发现：未知版本修复已落在 parser+empty-trace 边界；backfill 推测经实测驳回。

### 9.3 `backend/app/services/trace_parsers/`（A）

职责是把 Runtime 字节转换为统一值对象。`ParserRegistry` 像插件插座：Runtime/format/version 决定插哪只解析器；`raw-jsonl-1` 是不猜 Runtime 语义的安全兜底。

```python
# 旧代码（不存在）

# 新代码
parser = registry.resolve(runtime_key, detected_format, format_version)
parsed = parser.parse(bytes, ParseInput(...))
```
