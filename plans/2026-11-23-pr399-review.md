## §1 一页速览

一句话：把模板启动过的评测从「详情页内嵌最近 5 条」扩展成「列表行/详情页入口 → 浮窗 → 服务端分页 + 状态筛选 → 进入评测详情」的只读链路。

比喻：原来的模板详情像一张只贴了最近五张照片的相册封面；本 PR 在封面旁开了一扇窗，窗口里的相册按时间倒序、可以按状态筛选、可以翻页，点任意一张照片就走到那张照片的评测详情。

| 交付块 | 修改前（1500×837） | 修改后（1500×837） |
|---|---|---|
| 模板列表操作区 | 详情 / 接口 / 停用 / 启动（4 个） | 详情 / 接口 / 历史 / 停用 / 启动（5 个，单行不裁切） |
| 模板详情入口 | 只有「最近运行」5 条 | 顶部「启动历史」+ 卡头「全部历史」 |
| 启动历史 | 无 | 浮窗 1000px，默认 10 条/页、2 页、状态计数（0 保留） |
| 空态 | 无 | 「还没有启动记录」/「没有符合状态的启动记录」+ 清除筛选 |
| 详情跳转 | 无 | 行或「查看」→ `/evals/{run}?fromTemplate=...`，详情保留来源模板横幅 |
| 接口 | `GET /api/v1/evaluations` 无模板过滤 | 增加 `template_id`，404 未知模板，其余参数不变 |

验证基线：1500×837 @2x Playwright 冒烟通过；1200×800 / 1280×800 下浮窗 footer 均在视口内，正文内部滚动；列表在 1200/1280 下沿用既有横向滚动（表格 `scroll.x=1220`）。CI 以 PR 检查列表为准；本检视写作时 `docs`、`flow-offline`、`web`、`runner`、`deployment contract` 通过，`flow-online` 因 PR 未关联 Project 失败，`backend` 待跑。

## §2 架构导览

### 2.1 后端：在既有读模型上多一个条件

`backend/app/api/evaluations.py:489-560` 仍是原来的列表端点，只多了 `template_id` 参数与一次存在性校验：

- 参数校验前，先 `template_service.get_template(session, template_id)`（`:507-514`）。模板不存在时返回 404 `template_not_found`，而不是返回空页。这个选择避免前端把「模板被删除」误判成「模板没有历史」。
- `template_id` 进入 `evaluation_service.list_evaluations`（`:525-533`）和 `evaluation_list_stats`（`:553-559`），因此列表、总数和统计卡使用同一套过滤条件。
- 查询层 `_run_filter_conditions`（`backend/app/services/evaluations.py:670-695`）只追加 `EvalRun.template_id == template_id`，不引入新 join；`_needs_dataset_join` 仍由 `search` / `dataset_id` 决定，模板过滤不会额外 join 数据集表。
- 排序仍是 `EvalRun.created_at DESC, EvalRun.id DESC`（`:733-739`），这与 `recent_runs` 的排序一致；模板启动时 `created_at` 就是启动记录创建时间。

### 2.2 前端浮窗：一个受控组件、两个查询

`web/src/components/TemplateHistoryModal.tsx` 是受控展示组件：`template` 为空返回 `null`，`open`/`onClose` 由页面控制。

- 列表查询（`:167-181`）：key 由模板、状态、页码、页大小组成；`status === "all"` 时不传 status；`limit` 固定由页大小决定，`offset` 由页码推导。`keepPreviousData` 保留翻页时的上一页内容，避免闪烁。
- 计数来自同一列表响应中的 `status_counts`（`web/src/api/evaluations.ts:243-254` 解析）；后端在 `template_id` 过滤时用一次 `GROUP BY status` 计算 0 填充计数（`backend/app/services/evaluations.py:753-780`），不再为每个状态各发一个列表请求。
- 状态选项（`:202-211`）：`EVAL_STATUS_META` 的全部键都保留，计数为 0 也显示，符合验收。
- 筛选/页大小变化都 `setPage(1)`（`:291-306`）；总数缩小时 `:194-197` 把页码夹回最后一页。
- 空态（`:224-241`）区分「筛选无结果」和「没有启动记录」；前者带「清除筛选」。
- 行点击与「查看」都走 `openRun`（`:220-223`），先关浮窗再 `navigate`，URL 带 `fromTemplate`；评测详情的来源模板横幅实际来自 run 的 `template_id`（`EvalDetailPage.tsx:943-950`），`fromTemplate` 只是保留上下文。

### 2.3 入口接线

- 列表页：`EvalTemplatesPage.tsx:208-238` 在「接口」后插入「历史」，用 `historyTarget` 控制浮窗（`:379-383`）。操作列宽度从 16% 调到 22%，模板列 20%→18%，固定组合 25%→21%，其余列不动；总宽仍 100%，避免新增按钮把「停用/启动」挤出列宽。
- 详情页：`EvalTemplateDetailPage.tsx:177-199` 顶部新增「启动历史」；`:303-322` 最近运行卡头把「全部历史」和「再启动一次」并排；`:427-431` 复用同一个浮窗。最近运行的「打开」也带 `fromTemplate`（`:147-154`）。

`templates.css` 用与 PR #393 相同的 flex 封顶方案：

## §3 数据流走查

以管理员从模板列表打开「日常回归 · Verified」为例：

1. 列表页拉到模板分页数据，当前行渲染「历史」按钮（`EvalTemplatesPage.tsx:208-238`）。
2. 点击「历史」→ `setHistoryTarget(row)`；`TemplateHistoryModal` 以该 `EvalTemplate` 渲染，`open=true` 触发重置状态（`TemplateHistoryModal.tsx:160-165`）。
3. 列表查询请求 `/api/v1/evaluations?template_id=...&limit=10&offset=0`（`:167-181`）；后端校验模板存在（`evaluations.py:507-514`），查询 `EvalRun.template_id` 条件（`services/evaluations.py:670-695`），返回 `items/total`。
4. 同一响应带回 `status_counts`，前端把每个状态的计数填进下拉框；全部状态计数为求和。计数不受当前 `status` 影响，所以筛选时仍能看到全部状态。
5. 用户切换「已完成」→ `status="completed"`、`page=1`，列表查询重发，浮窗保留筛选器与清除按钮。
6. 用户点任意行或「查看」→ `openRun` 关闭浮窗并导航到 `/evals/smoke-run-01-completed?fromTemplate=...`；评测详情根据 `run.template_id` 展示「由评测模板…启动」横幅。
7. 0 次启动模板：`total=0`、计数全 0，列表查询返回空数组，Table 显示「还没有启动记录」。
8. 筛选到 0 条状态：列表查询返回空数组但筛选器保留，显示「没有符合状态的启动记录」和「清除筛选」。

## §6 讨论点

### D1 状态计数用 11 个并发列表请求，每次还跑完整 stats

- **位置**：原实现 `web/src/components/TemplateHistoryModal.tsx:26-38`、`:183-187`；后端 `backend/app/api/evaluations.py:525-578`。
- **现象**：打开浮窗时，前端对 11 个状态各发一个 `GET /api/v1/evaluations?template_id=...&status=...&limit=1`；每个请求不仅查 total，还会执行 `evaluation_list_stats` 的多组聚合查询，并构造 `items`/`stats`。理论上共 11 个 round-trip、55 个左右聚合查询，只为得到 11 个整数。
- **问题**：对当前单租户、模板历史量不大的场景，功能正确且可接受；但历史记录增长后，这个 N+1 会放大延迟和数据库压力，且每个请求都返回了不需要的 items/stats。
- **预判**：不是阻断缺陷。建议在 `template_id` 过滤时让后端返回一个轻量的 `status_counts`（group by status 一次查询），前端直接使用；这样也把「计数使用同一套过滤条件」的语义收到服务端。若不想扩展响应结构，可把计数请求改成只读 count 端点，但会引入新接口。
- **结论**：已修复（review 轮）。后端 `evaluation_status_counts` 用一次 `GROUP BY status` 返回 0 填充的 `status_counts`；前端删除 `fetchStatusCounts` 与第二个查询，直接使用同一列表响应。这样 N+1 和重复 stats 都消失，且计数与列表使用同一套 `q`/`dataset_id`/`template_id` 条件。

### D2 状态筛选用 11 个真实状态，而 issue/原型只列 5 个

- **位置**：`web/src/components/TemplateHistoryModal.tsx:17`、`:202-211`；`web/src/utils/evalStatus.ts:12-24`。
- **现象**：issue 写「全部 / 运行中 / 已完成 / 部分成功 / 失败 / 已取消」，生产下拉框实际列出 11 个 `EVAL_STATUS_META` 键（准备中、排队中、运行中、收口中、已完成、部分成功、失败、预算暂停中、预算已暂停、取消中、已取消）。
- **问题**：这是否违背「按原型」？原型 mock 只有 5 个状态，生产枚举更细；把准备中/排队中/收口中等并成「运行中」需要改后端 status 语义（目前 status 是精确枚举），不属于本 issue 的「复用现有 status 参数」。
- **预判**：保留 11 个真实状态是正确取舍：计数 0 也保留，用户能看到所有可能状态；issue 的 5 个是原型 mock 的状态子集。PR 描述已说明差异。
- **结论**：不修复；如产品坚持 5 组，需要单独定义状态分组契约并改后端。

### D3 API 默认 limit 仍是 50，issue 写默认 10

- **位置**：`backend/app/api/evaluations.py:491`；前端 `TemplateHistoryModal.tsx:174` 显式传 `pageSize`。
- **现象**：浮窗默认 10 条，但直接请求 `GET /api/v1/evaluations?template_id=...` 不带 limit 时，后端默认 50；issue 的接口段写「limit 默认 10」。
- **问题**：UI 行为与验收一致，但 API 契约和 issue 文字有差异；如果未来有客户端依赖「模板历史默认 10」，会拿到 50。
- **预判**：浮窗始终显式传 limit，当前无实害；建议在模板过滤存在且调用方未传 limit 时默认 10，同时保留通用列表默认 50，并在响应回显 `limit`/`offset`。
- **结论**：已修复（review 轮）。`template_id` 存在且调用方未传 `limit` 时默认 10，通用列表仍默认 50；响应回显实际生效的 `limit`/`offset`，后端测试覆盖默认值与显式值。

### D4 行点击没有键盘等价操作

- **位置**：`TemplateHistoryModal.tsx:145-148`。
- **现象**：`onRow` 只绑定 `onClick`，行本身没有 `tabIndex`/`onKeyDown`；键盘用户只能通过「查看」按钮进入。
- **问题**：鼠标行点击是原型行为；「查看」按钮已提供键盘可达路径，不算阻断。
- **预判**：可给行加 `tabIndex=0` 和 Enter/Space 处理，约 6 行；但会让整行进入 Tab 顺序，和「查看」按钮重复。当前保留按钮路径。
- **结论**：不修复。

### D5 `fromTemplate` 只是 URL 上下文，真正横幅靠 run.template_id

- **位置**：`TemplateHistoryModal.tsx:220-223`；`EvalDetailPage.tsx:943-950`。
- **现象**：历史行导航带 `?fromTemplate=...`，但评测详情不读这个参数，而是从列表接口的 `template` 字段渲染横幅。
- **问题**：参数与横幅来源不一致，未来若有人只复制 URL 到没有模板的 run，横幅不会出现；但这是正确行为（run 本身没有来源模板）。
- **预判**：保留参数作为上下文/埋点，不把它当权限或数据来源；与原型 URL 形式一致。
- **结论**：不修复。

### D6 1200/1280 下列表仍有横向滚动

- **位置**：`EvalTemplatesPage.tsx:315` `scroll={{ x: 1220 }}`。
- **现象**：1500×837 下表格不滚动；1200/1280 下 `scrollWidth=1220`、`clientWidth` 约 914/978，出现横向滚动。这是既有列表设计（固定列宽总和 1220），不是本 PR 新增。
- **问题**：新增「历史」后操作列宽度从 16% 调到 22%，但总宽仍 100%，1500 下已不裁切；1200 下需要横向滚动才能看到最右操作。
- **预判**：原型验收视口是 1500×837；1200 下的横向滚动是既有行为，不在本 issue 范围。若后续要做窄屏优化，可把「费用估算/更新」列折叠或改成卡片。
- **结论**：不修复。

## §9 文件级代码分析

### 9.1 `backend/app/api/evaluations.py`（M）

职责：控制面评测读接口。变更形态：在既有 `GET /api/v1/evaluations` 上增加 `template_id`、模板历史默认 limit 10、响应回显 `limit`/`offset` 与 `status_counts`。

旧代码（base）只接受 `limit/offset/q/status/dataset_id`，直接调用 `list_evaluations`。新代码先校验模板存在，再把 `template_id` 传给列表和统计：

```python
if template_id is not None:
    try:
        template_service.get_template(session, template_id)
    except template_service.TemplateNotFound as exc:
        raise HTTPException(status_code=404, detail=error_detail("template_not_found", ...)) from exc
```

实现思路：把「模板可见性」放在 API 层，把「按模板过滤」放在 service 层；404 与模板详情接口保持同一错误码，避免调用方分别处理两套错误。实现思路补充：`effective_limit` 在模板过滤存在时缺省 10，通用列表保持 50；`status_counts` 只在模板过滤时计算，避免给普通列表增加额外查询。

### 9.2 `backend/app/services/evaluations.py`（M）

职责：评测列表/统计查询。变更形态：三个函数多一个可选 `template_id` 形参；条件构造器多一个 `EvalRun.template_id == template_id`。

关键依赖：SQLAlchemy 2.x 的 `select`/`func.count`；`_run_select` 负责可选的数据集 join。实现思路：模板过滤不依赖数据集 join，因此 `_needs_dataset_join` 不变；`list_evaluations` 的 `joins = True` 仍只用于页面要展示的 dataset name/version。`evaluation_status_counts`（`:753-780`）复用同一套 conditions，但显式不传 `status`，因此筛选时计数不会被选中的状态收敛；一次 `GROUP BY status` 返回全部计数。

### 9.3 `web/src/components/TemplateHistoryModal.tsx`（A）

职责：启动历史浮窗。关键依赖：`@tanstack/react-query` 的 `useQuery`/`keepPreviousData`、antd 的 `Modal`/`Table`/`Select`/`Pagination`。

实现思路：查询 key 与筛选状态绑定；计数用独立 key，不随 status 变化；`HistoryTable` 保持纯展示，`openRun` 负责关闭与导航。计数随列表响应返回，不再有独立计数请求；D4 的键盘路径只靠按钮。

### 9.4 `web/src/pages/EvalTemplatesPage.tsx` / `EvalTemplateDetailPage.tsx`（M）

职责：入口与浮窗状态。列表页新增 `historyTarget`，详情页新增 `historyOpen`；两页复用同一个 `TemplateHistoryModal`。详情页的最近运行「打开」补 `fromTemplate`。实现思路：入口只负责选中模板/开关，数据请求全部留在浮窗组件内。

### 9.5 `web/src/styles/templates.css`（M）

职责：浮窗视觉。实现思路：flex 封顶 + body 内部滚动；表格行压缩到 3px padding；摘要/筛选/分页/API 行与原型同构。已知弱点：1200 以下 body 会内部滚动（正常），列表横向滚动是既有行为。

### 9.6 `tests/backend/test_eval_templates.py`（M）

职责：模板历史过滤回归。新增测试用两个模板各启动若干次，断言 `total`、跨模板隔离、状态过滤、分页和 404；不依赖前端。测试同时覆盖模板历史默认 `limit=10`、显式 `limit/offset` 回显、`status_counts` 的 0 填充与「计数不受 status 过滤影响」。
