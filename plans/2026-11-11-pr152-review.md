## §1 一页速览

**一句话**：把“粘贴 JSON 文本”的导入页换成“上传文件 → 隔离进程体检 → 确认后落成不可变版本”的三步向导，导入失败不再留下半成品。

**一个比喻**：像机场行李托运。值机柜台只收下箱子并贴条（上传 + 暂存），安检在独立房间完成并给出一张检查单（隔离子进程 + 校验报告），旅客确认后才打印登机牌并把行李装舱（单事务生成不可变版本）；检查不通过、旅客取消或安检机断电，箱子都不会被装错航班。

| 交付块 | 内容 |
|---|---|
| 上传 API | `POST /api/v1/dataset-imports/uploads`（multipart，≤1 GB，JSON/JSONL/NDJSON） |
| 状态机 | `queued → validating → validated → committing → succeeded`，失败/取消/重复为终态 |
| 校验报告 | 总数、有效/无效、逐字段完整率、错误分类与逐项定位、重复 case_key、致命错误 |
| 隔离执行 | 独立 Python 子进程；wall-clock 超时、RLIMIT_AS/CPU；父进程按退出码兜底 |
| 版本生成 | 复用 `materialize_dataset_version`，单事务写 dataset/version/cases；提交前校验文件 digest |
| 前端 | 左侧步骤条、拖放上传、上传百分比、校验中、通过/失败、生成中、成功、取消入口 |
| 运维 | Worker 回收心跳过期的导入；部署新增 `DATASET_IMPORT_*` 变量 |

**验证基线**：后端 608 passed / 1 skipped（本地 SQLite；CI PostgreSQL 另跑迁移 dry-run）；前端 typecheck + build 通过；文档 8 项门禁全绿；冒烟 10 场景通过。PR 描述内含 Before/After 与原型对照截图。

## §2 架构导览

### 2.1 API 层：三个动作，一条状态机

`backend/app/api/datasets.py:250` 的上传路由先校验适配器与扩展名（`AdapterNotFound` 只捕获预期异常），再把 multipart 分块写入 `DATASET_IMPORT_DIR`，边写边算 sha256，超过上限立即删除并返回 413。写库失败也会删除暂存文件（`:365`）。随后通过 `BackgroundTasks` 启动子进程任务。

`commit`（`:386`）只做一次原子状态迁移：`begin_commit`（`services/dataset_imports.py:709`）用 `UPDATE ... WHERE status='validated'` 抢占，`rowcount != 1` 返回 409，避免双击生成两个版本。`cancel`（`:414`）只允许 `queued` / `validated`，避免和正在运行的 worker 互相覆盖。

**关键机制：`version` 与 `version_detail` 分离**。`GET /dataset-imports/:id` 的 `version` 保持导入标签字符串，完整版本摘要放在 `version_detail`（`api/datasets.py:212`）。这是冒烟发现的缺陷修复：早期实现用版本对象覆盖了字符串，前端成功页因此丢失版本号。

### 2.2 服务层：报告是持久事实，版本是单事务结果

`services/dataset_imports.py` 是本次新增的核心。

- `validate_source_file`（`:118`）流式消费 `iter_source_records`，按适配器 `required_fields` 累计完整率；错误按 code/field 聚合，明细最多保留 200 条（`errors_truncated` 记录剩余数）。重复 `case_key` 在内存集合中判定；用户可控的 key 截断到 200 字符后进入报告。
- `begin_validation`（`:311`）用条件 UPDATE 从 `queued` 抢占到 `validating`；若用户已取消则返回 False，worker 直接退出，不会把 `cancelled` 复活成 `validated`。这是自检阶段补上的竞态修复。
- `materialize_uploaded_import`（`:474`）先校验文件 digest 未变，再把流交给 `materialize_dataset_version`。**生成过程不再分段 commit**：早期版本每 1000 条提交一次，后续解析错误会留下半成品版本；现在进度只在内存里累计，最后随状态一次性提交。
- `run_import_job`（`:640`）启动子进程：最小环境变量白名单（只保留 PATH/HOME/PYTHONPATH/DATABASE_URL/DATASET_IMPORT_*/PG* 等），不透传 Runner、模型与 S3 凭据；父进程 `communicate(timeout=...)`，超时后按进程组 SIGKILL 并把 `worker_timeout` 写到导入行。
- `reap_stale_imports`（`:545`）由 Worker 每轮调用，把心跳超过窗口的 `queued/validating/committing` 标为 `worker_interrupted`，把长期无人提交的 `validated` 标为 `import_expired`，两者都会删除暂存文件，避免向导无限转圈或磁盘被遗弃导入占满。

### 2.3 共享版本写入：旧 JSON 接口不回归

`services/datasets.py:208` 新增 `materialize_dataset_version`，负责“重复/冲突判定 → dataset/指标/version/用例 → 导入记录”的完整事务。旧的 `POST /dataset-imports` 仍走 `import_dataset_version`（`:442`）：先内存校验，再调用同一 materialize，所以旧测试的幂等、冲突、失败分类行为不变。新流程用 `import_record` 参数把已存在的上传导入行终结为 succeeded/duplicate/failed，而不是新建第二条记录。

### 2.4 流式解析：数组与 JSONL 两条路径

`backend/app/datasets/source.py:63` 按首字节选择：

- JSON 数组（`:114`）：`json.JSONDecoder.raw_decode` 增量解码，缓冲区随消费压缩；未闭合的数组/尾部垃圾抛 `SourceFormatError`，已解析记录仍计入报告。
- JSONL（`:96`）：逐行 `json.loads`，空行跳过；坏行变成带行号的 `invalid_json`，不中断整个文件。
- 单条记录上限 64 MB（`:29`），防止一个损坏的数组把读缓冲无限撑大。

### 2.5 前端：状态只从后端来

`web/src/pages/DatasetImportPage.tsx:55` 重写为三步。轮询 effect（`:83`）只在 active 状态存在时调度下一次请求；网络抖动会 `setPollTick` 重新计时，而不是把向导停在旧状态。上传通过 XHR 报告进度（`web/src/api/datasets.ts` 的 `uploadDatasetImport`），提交/取消复用统一 `request` 封装。步骤条、拖放区、安全提示与统计卡使用 `web/src/styles/datasets.css` 对齐 prototype；成功后只渲染后端 `status`/`version_detail`，不在前端编造版本。

## §3 数据流走查（一条真实主线）

1. 管理员在 `/datasets/import` 选择 SWE-bench 适配器，拖入 `verified-slice.jsonl`，填写 `v2026.11-smoke-c` 与 commit `3f2c9a1`（`DatasetImportPage.tsx:263`）。
2. 点击“校验数据” → XHR `POST /uploads`（multipart）。API 校验扩展名/适配器，分块写 `/tmp/eval-dataset-imports/<uuid>.jsonl` 并计算 sha256，创建 `dataset_import(status=queued)`。
3. 响应返回后，后台任务启动 `python -m app.worker.dataset_import <id> validate`；子进程把状态抢占为 `validating`，流式解析 6 条记录，计算 5 个必填字段完整率，写入 `validation_report_json`，状态变为 `validated`。
4. 前端每 0.9 s 轮询 `GET /dataset-imports/<id>`。收到 `validated` 后展示三张统计卡、通过横幅、完整率与来源文件指纹；`status !== validated` 时“生成版本”禁用。
5. 点击“生成版本” → `POST /commit` 原子迁移到 `committing` → 子进程先比对文件 digest，再在单事务中写 dataset / 4 个指标定义 / version / 6 条 case / 导入记录 `succeeded`，最后删除暂存文件。
6. 前端轮询到 `succeeded`，展示不可变版本；`查看数据集` 跳转详情。失败、取消、重复、超时都有独立终态与证据。

## §6 讨论点

### 6.1 OSS 五文件任务是本次的边界还是缺口？

- **位置**：`services/datasets.py:208`、`DatasetImportPage.tsx:537`（成功页文案）。
- **现象**：design 07 §2 规划 `task.toml` / `instruction.md` / Dockerfile / test.sh / solve.sh 五文件任务包与 OSS manifest；本 PR 生成的是 DB 内的不可变用例任务视图，成功页写“平台任务视图”。
- **问题**：issue #143 的目标写了“版本三元组 + 任务包”。当前实现是否满足？还是应把五文件任务包作为独立 issue？
- **预判**：M3-01 基线就未实现 `build_task`，本次只补上传闭环；强行塞入 OSS 五文件会同时改动 runner 读取契约与存储布局，超出“导入上传”范围。建议单独立项。
- **结论**：（留空）

### 6.2 隔离 worker 挂在 API 进程的线程池里，规模上限在哪？

- **位置**：`api/datasets.py:365`、`services/dataset_imports.py:640`。
- **现象**：每次上传由 API 的 `BackgroundTasks` 在线程池中同步等待子进程，单任务最长 30 分钟，默认线程池 40。
- **问题**：大量并发上传会占满线程池，影响普通 API 请求。是否需要独立 worker 队列 + 共享暂存盘/OSS？
- **预判**：单管理员、低频导入的当前产品阶段可接受；若导入成为批量入口，应把任务投递到 `backend/app/worker` 轮询队列，并用共享卷或 OSS 传递源文件。
- **结论**：（留空）

### 6.3 1 GB 文件的临时磁盘放大

- **位置**：`api/datasets.py:318`、`deploy/docker-compose.prod.yml:91`。
- **现象**：Starlette multipart 会先把上传落到 SpooledTemporaryFile（>1 MB 即落盘），API 再复制一份到 `DATASET_IMPORT_DIR`；最坏约 2 倍文件大小的临时占用。
- **问题**：部署盘容量是否需要单独水位或流式直传 OSS？
- **预判**：当前 1 GB 上限下 2 GB 临时空间可接受；如放宽上限，应改为对象存储直传 + worker 下载。
- **结论**：（留空）

### 6.4 参考补丁为空：错误还是警告？

- **位置**：`datasets/swebench.py:120`、`DatasetImportPage.tsx:440`。
- **现象**：prototype Step 2 把空参考补丁显示为非阻塞警告；现有适配器把 `patch` 列为必填，按错误处理。
- **问题**：是否要按 design 07 “参考补丁仅用于自检”改成 warning，并允许无 patch 用例入库？
- **预判**：改语义会影响评分自检与既有导入测试，不应在 UI 修复 ticket 内顺手改；若产品确认可导入无 patch 用例，再单独调整适配器契约。
- **结论**：（留空）

## §9 文件级代码分析

### 9.1 `backend/app/api/datasets.py`（M）

职责：导入 API 入口。变更形态：在旧 JSON 导入旁新增上传/提交/取消，详情响应扩展。

旧：`POST /dataset-imports` 一次请求校验并写版本；详情只返回摘要。
新：上传先落文件与 `queued` 记录，异步校验；`commit` 原子迁移；`version` 与 `version_detail` 分离。

实现思路：HTTP 层只做参数/文件/状态守卫，解析与持久化交给服务；错误统一走 `error_detail` 封套。

检视发现：`get_adapter` 原来捕获所有异常，已收窄为 `AdapterNotFound`；写库失败会清理暂存文件。

### 9.2 `backend/app/services/dataset_imports.py`（A）

职责：上传导入的完整生命周期。新增文件。

关键机制：校验报告、隔离子进程、最小环境、超时兜底、心跳回收、原子提交。比喻：安检房间与登机牌打印机分离，安检失败不能打印登机牌。

检视发现：见 §7 的 partial commit、取消竞态、环境透传三项，均已修复。

### 9.3 `backend/app/services/datasets.py`（M）

职责：版本写入共用实现。变更形态：从旧 `import_dataset_version` 中抽出 `materialize_dataset_version`。

旧：校验 → 直接在该函数内写 dataset/version/cases。
新：校验留在旧入口；写入接受任意可迭代记录与 `total_count`，可选收尾既有导入记录。

实现思路：把“已校验数据”的写入与“如何得到数据”解耦，旧 JSON 与上传流共用一套幂等/冲突/事务语义。

检视发现：写入条数与 `total_count` 不一致时抛 `DatasetSourceChanged`，避免静默生成部分版本。

### 9.4 `backend/app/datasets/source.py`（A）

职责：流式 JSON/JSONL 读取。新增文件。
