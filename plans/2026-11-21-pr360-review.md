## §1 一页速览

一句话：把“模型 token 属于哪个分片”改成“模型 token 属于哪个用例的哪次 attempt”，让网关只在调用方自己的 attempt 结束时吊销它。

一个比喻：原来的 token 像一张“整个宿舍楼通用”的门禁卡，宿管却按“楼里第一个人退宿”就注销了整张卡；现在每个学生拿自己的房卡，只有自己退宿才失效，楼里其他人不受影响。退楼（run 取消）和欠费（预算暂停）仍然整栋楼一起停。

## §2 架构导览

1. **签发层**：`shard_manifest` 新增可选 `case_run_id`（`backend/app/api/runners.py:701`）。`_load_case_attempt_for_token`（`:643`）先确认 case 属于本 run，再确认 attempt 属于本 shard/attempt，终态 attempt 直接 409，避免发一个注定被网关拒绝的 token。
2. **凭证层**：`GatewayClaims` 增加 `case_run_id` / `case_attempt_id`（`backend/app/model_gateway/tokens.py:53-54`），签发与校验都写入/读取（`:79-82`、`:118-119`、`:138-140`）。
3. **撤销层**：`validate_claims_binding`（`backend/app/model_gateway/service.py:106`）分成两条路径：
   - 有 case 维度：按 `EvalCaseAttempt.id` 唯一查询，只检查这一行（`:129-160`）。
   - 无 case 维度：旧 token 兼容路径，查询该 shard/attempt 的全部 attempt，只有全部终态才 409（`:163-184`）；超过截止时间直接 409 `legacy_token_retired`。
   - run 级取消/预算暂停在两条路径之前统一由 `_check_run_state`（`:77`）拒绝，保持全局语义。
4. **Runner 层**：`fetchManifest` 支持 `caseRunId`（`runner/lib/manifest-source.mjs:23`），在图片拉取完成后、Agent 启动前重新拉 manifest（`runner/scripts/real-task.mjs:560-590`）。拿不到 `modelToken` 时用 `model_token_unavailable` 结束该 case，不再使用启动早期的 shard token。
5. **归因层**：`record_usage` 写入 `case_run_id`（`backend/app/model_gateway/service.py:271`），模型费用可按用例归因，run 汇总口径不变。

## §3 数据流走查

1. 平台派发 shard，GitHub job 启动 `real-task.mjs`，先拉一次 manifest 取得任务 payload 与任务 token（此时不拿模型 token）。
2. 跑到某个 case，准备启动 Agent 前调用 `fetchManifest(dispatch.manifest_url, {caseRunId: item.case_run_id})`，URL 变成 `.../manifest?...&case_run_id=ecr_...`。
3. 后端 `_load_shard_dispatch` 验证 dispatch 三元组；`_load_case_attempt_for_token` 验证 case 与 attempt 归属；`GatewayClaims` 带上 case 两维；响应头返回 case token。
4. Agent 用该 token 调 `/model-gateway/...`。网关查 `EvalCaseAttempt.id` 这一行：若该 attempt 还在跑，放行；若该 attempt 已终态，409 `stale_attempt`；若 run 取消/预算暂停，409 全局错误。
5. 同 shard 的另一个 case 即使已经结束，也不会进入第 4 步的查询结果，因此不会被误杀。
6. 老 runner 不带 `case_run_id`：后端在兼容期内发旧 shard token；网关走“全部 attempt 终态才拒绝”的兼容分支。截止时间后不再发/不再收旧 token，老 runner 在 Agent 启动前 fail closed。

## §6 讨论点

### 6.1 兼容期默认不设截止时间

- **位置**：`backend/app/config.py:317`、`deploy/docker-compose.prod.yml:101`
- **现象**：`GATEWAY_LEGACY_TOKEN_DEADLINE` 默认空，旧 shard token 兼容分支会一直开放。
- **问题**：如果不主动设置，就退化成长期双模式，和 issue 的“不长期双模式”有张力。
- **预判**：默认空是部署安全的折中：立即设置过去时间会让还在跑的旧 job 直接失败。建议合并后在实例替换完成、旧 run 清空时立即设置截止时间。
- **结论（2026-11-21）**：保留可配置、默认空；在 PR 的“兼容与部署”里写明操作时机。是否改成固定默认日期需要运维排期，不在本 PR 拍板。

### 6.2 端点对未知 case 返回 404

- **位置**：`backend/app/api/runners.py:661-666`
- **现象**：`case_run_id` 不存在或不属于本 run 时返回 404 `case_run_not_found`。
- **问题**：这会让持有合法 dispatch key 的 runner 区分“case 不存在”和“case 存在但不在本分片”。
- **预判**：调用方本来就持有该分片的 dispatch key 和任务 token，信息增量有限；404 比 403 更利于 runner 诊断。
- **结论（2026-11-21）**：保留 404；错误码稳定，便于 runner 日志定位。

### 6.3 Runner 在图片拉取后才换 token

- **位置**：`runner/scripts/real-task.mjs:560-590`
- **现象**：case token 在镜像准备完成、Agent 启动前才获取。
- **问题**：如果平台在拉图期间不可达，case 会以 `model_token_unavailable` 失败，而不是继续用早期 shard token。
- **预判**：这正是 #358 要求的 fail closed；代价是平台短暂不可用时 case 失败更早、更明确。图片拉取不会再消耗 token TTL，符合 M8-41 的设计。
- **结论（2026-11-21）**：保留。

### 6.4 Usage 只补了 case_run_id，没有加 case_attempt_id 列

- **位置**：`backend/app/model_gateway/service.py:271`
- **现象**：`ModelUsage` 已有 `case_run_id` 但没有 attempt id 列，本次只写 case_run_id 和原有 attempt 序号。
- **问题**：同一 case 的两次 attempt 在用量表里只能靠 `attempt` 序号区分。
- **预判**：issue 把 case 归因列为“可选”；现有列已能按 case/attempt 聚合，新增迁移会扩大本 PR 面。
- **结论（2026-11-21）**：本次不新增列，保留后续按需迁移。

## §9 文件级代码分析

### `backend/app/model_gateway/tokens.py`

职责：签发/校验 M3-02 短期模型 token。变更形态 M。旧 token 只有 run/shard/attempt；新 token 增加 `case_run_id` 与 `case_attempt_id`，校验时按类型读取，缺失不报错（交给网关区分旧 token 与不完整 token）。实现思路：保持 wire format 不变，只增加可选 claim，旧签名/验签逻辑无需迁移。

### `backend/app/model_gateway/service.py`

职责：模型网关的撤销、预算与用量。变更形态 M。旧逻辑用 `(run, shard, attempt_no)` 查 attempt 后 `.first()`；新逻辑把“有 case 维度”和“无 case 维度”分开：前者按主键精确查一行，后者用 `.all()` 看到整个 shard 的 attempt 集合。run 状态检查抽成 `_check_run_state`，保证两种 token 都受取消/预算暂停约束。兼容截止用可注入的 `deadline`/`now`，便于单测冻结时间。

### `backend/app/api/runners.py`

职责：Runner 面 API。变更形态 M。`_load_case_attempt_for_token` 复用现有 `_load_shard_dispatch` 的 dispatch 校验，再叠加 case/attempt 归属与状态校验；manifest 端点仅在 `model_config_id` 存在时签发 token，兼容截止后返回无 token 的 manifest 而不是 409，保证新 runner 仍能先读 manifest 再按 case 换 token。

### `runner/lib/manifest-source.mjs` / `runner/scripts/real-task.mjs`

职责：Runner 侧 manifest 与真实 case 执行。变更形态 M。`fetchManifest` 只增加 query 参数，不改 digest 校验；`realCase` 删除 shard token 入参，在启动 Agent 前按 case 重新拉 manifest，缺少 case token 时直接 `failCase`。这消除了“旧 shard token 兜底”的静默路径。

### `runner/lib/mock-platform.mjs`

职责：Runner 契约测试桩。变更形态 M。manifest 路由从精确匹配 `/manifest` 改为按 pathname 匹配，允许 `case_run_id` query；`behavior.modelToken` 回调收到请求 URL，测试可以只对 per-case 请求返回 token。

### 测试

新增后端用例覆盖：多 case 同 shard 的终态隔离、重试新旧 attempt、部分/缺失 case 维度、旧 token 全终态、兼容截止、manifest case 绑定和 cutoff 后不下发旧 token、取消对 case token 的全局生效。Runner 用例覆盖 per-case 刷新与缺失 case token 的 fail closed。
