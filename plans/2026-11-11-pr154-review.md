## §2 架构导览

### 2.1 入口层：从抽屉回到路由

`EvalsPage` 不再持有 `detailId`、`detailQuery`、`eventsQuery`，也不再声明 Drawer 专属的 `caseColumns` / `shardColumns` / `eventLabel` / `eventDescription`。两处入口统一走 `navigate`：

- 创建成功：`EvalsPage.tsx:75`
- 列表“详情”：`EvalsPage.tsx:132`

**为什么**：Drawer 与独立页同时存在会造成两份详情实现、两套查询与两套状态语义；issue 允许二选一，这里选择独立页作为唯一入口，删除抽屉以消除死代码。

### 2.2 服务层：progress 是唯一事实

`evaluation_detail` 在原有 `case_counts` / `trace_counts` 之上计算：

- `finished = total - queued - running`
- `percent`：未全部结束前最多 99，避免 999/1000 四舍五入成 100%
- `resolve_rate = resolved / (resolved + unresolved + failed)`
- ETA：仅 `status == "running"` 且 `0 < finished < total` 时，用“已耗时 / 已完成数 × 未完成数”线性外推

锚点：`evaluations.py:597`、`:668`、`:705`。

**为什么**：原先 ETA 用 `Date.now()` 在组件里计算，不同标签页、不同刷新时刻会得到不同结果；`paused_budget` 时还会显示一个永远不会推进的倒计时。现在响应里带 `estimated_remaining_seconds` 与 `estimated_finish_at`，前端只格式化。

### 2.3 客户端：契约解析 + 轮询

`EvaluationProgress` 是必填字段，`readProgress` 在响应缺字段时抛 `invalid_response`。详情 query 在非终态每 3 秒刷新（`EvalDetailPage.tsx:525`），因此 SSE 事件流之外还有一条低频快照对账，保证 ETA 与分片状态不会在页面打开后定格。

### 2.4 事件页：保留线上增量

`EventsPanel` 接收 `shards`，在事件表之上增加两张卡：

- **分片派发对账**：shard / attempt / outbox 状态 / GitHub HTTP / 派发时间 / 最近错误
- **Attempt 心跳时间线**：最近 8 条 `case.heartbeat`，展示用例、attempt、序号、进度

锚点：`EvalDetailPage.tsx:2344`、`:2490`、`:2517`。心跳与分片数据都来自服务端，不在前端造数。

## §3 数据流走查

1. 用户点击列表“详情” → `navigate('/evals/<id>')` → `AppRoutes` 命中 `/evals/:runId` → `EvalDetailPage`。
2. `detail` query 调 `GET /api/v1/evaluations/{id}`；服务端把 run + cases + shards + `progress` 一次返回。
3. 页面用 `progress.finished / percent / resolve_rate / estimated_*` 渲染统计卡、堆叠进度和上下文；浏览器不再做 `Date.now()` 推算。
4. 非终态下 3 秒后 query 重新取数；SSE 继续推送事件，`useEvalEvents` 只更新事件流状态。
5. 事件页用 `detail.shards` 渲染分片对账，用事件窗口过滤 `case.heartbeat` 渲染心跳时间线。
6. 用例行 → `?tab=cases&case=...` → `CaseDrawer`；失败用例的重试仍走既有 API 与预算/容量守卫。

## §6 讨论点

### 6.1 轨迹入口缺失

- **位置**：`web/src/pages/EvalDetailPage.tsx` CaseDrawer “轨迹与对象”
- **现象**：issue #145 验收要求“从失败用例可进入会话轨迹页”，但主分支没有 `TracePage`，也没有 m6-04 轨迹查询 API；`#94`（m6-05）仍 OPEN。
- **问题**：若在 M5-17 里硬加一个 `/trace` 链接，只能指向 404 或伪造页面。
- **预判**：这是 issue 写作时误以为 m6-05 已合入造成的跨 milestone 依赖，不是 M5-17 代码缺陷。
- **结论（2026-11-11）**：保持现状并在 PR 中声明；PR 使用 `Refs #145` 不自动关 issue；待 #94 合入后补真实链接再闭环该条验收。

### 6.2 ETA 线性外推过于朴素

- **位置**：`backend/app/services/evaluations.py:681`
- **现象**：用历史平均完成速度外推剩余时间，假设每个用例耗时相同。
- **问题**：SWE-bench 用例耗时长尾明显，早期 ETA 会偏乐观/偏悲观；不是新引入的复杂模型，但会波动。
- **预判**：MVP 可接受；真正的预测需要按难度/仓库分层或滑动窗口，属于后续优化。
- **结论（2026-11-11）**：接受。已限制只在 `running` 时给出，暂停/取消/终态返回 null，避免误导。

### 6.3 百分比四舍五入

- **位置**：`backend/app/services/evaluations.py:668`
- **现象**：`round(999/1000*100)` 会得到 100，但仍有 1 个用例未结束。
- **问题**：页面会出现“100% + 排队 1”的自相矛盾。
- **预判**：真实大评测容易触发。
- **结论（2026-11-11）**：已修复：未全部结束时 percent 上限 99。

### 6.4 3 秒轮询与 SSE 并存

- **位置**：`web/src/pages/EvalDetailPage.tsx:525`
- **现象**：SSE 推事件，detail query 每 3 秒拉聚合。
- **问题**：两条链路语义重叠，增加一点请求量。
- **预判**：聚合无法只靠 SSE 增量事件可靠重建（事件窗口/重连会丢），低频快照是对账成本最低的方案；终态即停。
- **结论（2026-11-11）**：接受。列表页本来也是 3 秒刷新，量级一致。

### 6.5 `progress` 必填的契约风险

- **位置**：`web/src/api/evaluations.ts:647`
- **现象**：旧后端响应没有 `progress` 时，前端抛 `invalid_response`。
- **问题**：滚动发布期间新前端配旧后端会整页报错。
- **预判**：本仓 web 与 api 同镜像发布，且无外部消费者；严格解析能尽早暴露契约漂移。
- **结论（2026-11-11）**：接受。若未来前后端独立发布，再改为可选并回退。

### 6.6 与原型事件页的字段差异

- **位置**：`EvalDetailPage.tsx:2490` 一带
- **现象**：原型事件表有“耗时”和“导出日志”，本实现没有。
- **问题**：后端事件契约没有耗时字段，导出也没有端点。
- **预判**：补字段属于后端契约扩展，不是 M5-17 范围；伪造前端耗时会误导排障。
- **结论（2026-11-11）**：保持差异，PR 描述已说明。

## §9 文件级代码分析

### 9.1 `backend/app/services/evaluations.py`

- **职责**：评测创建/查询/生命周期服务；本次只改 `evaluation_detail`。
- **变更形态**：M。旧函数直接返回 counts/cases/shards；新函数在末尾增加 `progress`。
- **关键逻辑**：
  - `total` 取 `run.total_cases`，`finished` 由排队/运行数反推，避免依赖可能滞后的 run 计数器。
  - `percent` 未完成时封顶 99。
  - ETA 只在 `running` 且已有完成样本时计算，时间戳统一按 UTC 处理（SQLite 的 naive datetime 先补 tzinfo）。
- **实现思路**：把所有“需要口径一致”的派生数字放到服务端一次算完；客户端只做展示。
- **检视发现**：无新增缺陷；ETA 精度问题见 §6.2。

### 9.2 `tests/backend/test_eval_workbench.py`

- **职责**：M5-05 工作台读路径与重试守卫测试；新增 1 个测试。
- **变更形态**：M。
- **关键逻辑**：固定 `now`，构造 4 个用例（2 resolved / 1 failed / 1 running），断言 percent=75、resolve_rate=66.7、ETA=200s；再切换 `paused_budget` 断言 ETA 为 null；最后终态断言 100% 且无 ETA。
- **实现思路**：用注入的 `now` 消除时间抖动，让 ETA 可精确断言。
