## §2 架构导览

### 2.1 数据层：一镜像一行，`next_attempt_at` 一列三用

`dataset_image_artifact` 以 `(tenant_id, image_ref)` 唯一，`object_key` 由镜像引用 sha256 派生（`backend/migrations/versions/0029_dataset_image_artifacts.py:29-81`、`backend/app/models/dataset.py:304-347`）。`status ∈ missing/preparing/ready/failed`，`local_cleanup ∈ pending/done/failed`；`next_attempt_at` 同时承载“入队时间 / 领取租约 / 失败退避”（`backend/app/services/dataset_image_artifacts.py:192-220`、`:446-480`）。

### 2.2 判定层：readiness 是唯一事实来源

`resolve_preparation_images` 按“case 镜像 → 版本镜像 → adapter 派生”去重（`dataset_image_artifacts.py:84-128`），与 `dataset_images.image_for_case` 同源；`readiness` 以 8 线程 HEAD、最多 200 条输出，把结果写回台账（`:223-337`）。边界：只有 `ObjectMissing` 才降级 `missing`，其他 store 错误只记 `error`，不把 `ready` 打回 `missing`（`:270-282`）；`enqueue` 不越过租约/退避（`:284-289`）。

### 2.3 执行层：worker 只认台账，不认 HTTP

`prepare_one` 先 `requeue_due_failed_artifacts` 再 claim，claim 后立刻 commit 释放事务，再做多分钟 Docker 工作（`backend/app/services/dataset_image_prep.py:297-326`）。上传成功后**先提交 ready、再清理**（`:424-428`、`:433-459`）；清理失败不影响 ready，只写 `local_cleanup=failed`，由 10 分钟周期扫描兜底（`:469-556`、`backend/app/worker/image_prep.py:31`、`:142-144`）。启动扫描额外回收所有 `preparing` 行与全部临时 tar（`:483-488`、`:542-543`）。

### 2.4 接口层与门禁

`GET artifacts?preparation_id=` 返回当前快照；`ensure` 可带 `recheck` 先 HEAD 再入队；`retry` 重置 attempts 并立即入队（`backend/app/api/dataset_image_artifacts.py:89-127`）。create 在真正建 run 前再 `ensure_preparation_images`，不就绪则先 commit 入队再抛 409（`backend/app/services/preparations.py:972-987`）。

### 2.5 前端与部署

Step 4 渲染进度、计数、逐镜像 chip、失败横幅与详情抽屉（`web/src/components/RuntimeImagePrepCard.tsx:130-425`）；启动按钮由 `imageReadinessBlocked` 禁用（`web/src/pages/EvalWizardPage.tsx:2502`）。`image-prep-dind` 是 privileged DinD，只加入 `image_prep_internal`；`image-prep` 同时加入默认网络，靠 `DOCKER_HOST=tcp://image-prep-dind:2375` 连接，两服务由 `image-prep` profile 门控（`deploy/docker-compose.prod.yml:223-296`、`:350-358`）。

### 2.6 支撑件

`put_file` 用文件句柄 + `Content-Length` 流式 PUT，避免 4GB tar 进内存（`backend/app/services/object_store.py:196-238`）；`candidate_ref_pairs` 把镜像映射为“源 + pull 引用”，Hub 保持规范形、镜像站加 registry/prefix、digest 保留（`backend/app/services/dataset_images.py:351-392`）；`DockerCliImagePreparer` 用参数列表而非 shell，`docker save` 边读边 gzip 并带看门狗（`backend/app/services/dataset_image_prep.py:79-199`）。

## §3 数据流走查

1. 管理员导入 SWE-bench 数据集，每个 case 已写入派生的 `environment_image`（`backend/app/services/datasets.py:439`）；runner 只消费该字段与 OSS tar。
2. 用户选 6 个 case 触发 `POST /evaluations/prepare`。
3. `build_preparation` 解析去重镜像（`preparations.py:746-748`），`readiness(recheck=True, enqueue=True)` 逐个 HEAD 并把缺失项置 `preparing`（`:749-751`），把 `image_refs` 写进快照（`:791`）、返回 `image_readiness`（`:882`），最后 commit（`:858`）。
4. Step 4 首次进入自动 `ensure`，之后每 3 秒 `GET artifacts`（`EvalWizardPage.tsx:840-894`）；未就绪时创建按钮禁用（`:2502`）。
5. worker 每 5 秒一轮：退避到期的 failed → preparing（`dataset_image_prep.py:317`）→ claim 并写 900 秒租约（`:319`、`dataset_image_artifacts.py:478`）→ HEAD 命中直接 ready（`:345-361`）→ 否则按源 pull（`:382-392`）、必要时 tag（`:398-400`）、`docker save|gzip`（`:401`）、PUT（`:404`）、HEAD 校验大小（`:410-420`）→ 提交 ready（`:428`）→ 删临时 tar 与全部候选镜像（`:433-459`）。
6. 用户点创建：`consume_preparation` 校验快照/用例摘要/preflight，再 `ensure_preparation_images` HEAD 一遍；仍有非 ready 时先 commit 入队再 409（`preparations.py:979-987`），前端显示 `image_not_ready` 并刷新卡片（`EvalWizardPage.tsx:684-704`）。
7. 全部 ready 后建 run；runner 仍用 `task_json.environment_image` + `task_image_tarball`（`backend/app/api/runners.py:996-1007`），原 tar 优先/公开源回退路径未改。

## §6 讨论点

### 6.1 准备快照 15 分钟 TTL 与“串行准备 3–6 个 4.16GB 镜像”的现实时长不匹配

- **位置**：`backend/app/config.py:239`（TTL 900s）；`backend/app/services/dataset_image_prep.py:42-46`（pull 1800s、save 1800s、upload 3600s）；`web/src/pages/EvalWizardPage.tsx:808`、`:2502`。
- **现象**：快照 15 分钟过期；worker 串行，单镜像允许跑 30/30/60 分钟。“3 个已有 + 3 个缺失”若每个数分钟就很容易越线，首次 6 个更明显；过期后创建按钮禁用，create 返回 `preparation_expired`。
- **问题**：镜像准备是本 PR 新引入的、耗时不可控的 out-of-band 工作，但 TTL 没随之调整；Step 4 没有“续期/重新准备”入口，用户只能退回上一步重走，而后台 worker 仍在继续准备。这不是数据错误，却是验收场景几乎必然出现的体验断点。
- **预判**：`image_readiness` 仍有 pending 时延长 TTL（或 prepare 返回建议 TTL），Step 4 提供“重新准备并保留选择”；并把 TTL 从 compose 透出（当前 `deploy/docker-compose.prod.yml` 未传 `EVAL_PREPARATION_TTL_SECONDS`）。
- **结论**：（待用户拍板）

### 6.2 前端在“全失败”时停止轮询，但 worker 还会自动重试

- **位置**：`web/src/pages/EvalWizardPage.tsx:817-823`、`:871-874`；`backend/app/services/dataset_image_artifacts.py:206-220`、`:408-443`；`backend/app/services/dataset_image_prep.py:317`。
- **现象**：卡片注释把 failed 当终态，只有 `preparing_count>0 || missing_count>0` 才轮询；但 worker 每轮 `requeue_due_failed_artifacts` 会把 `attempts < max` 且退避到期的 failed 自动改回 preparing（60/120 秒）。
- **问题**：镜像第一次失败时前端立刻停轮询；后台 60 秒后自动重试并可能 ready，页面却一直停在“失败”，直到用户手动点按钮或重进 Step 4。用户会误以为必须重试，实际后台正在恢复，失败原因与进度都不再更新。
- **预判**：failed 且 attempts < max 不是终态。后端返回 `next_attempt_at`（或 `retry_scheduled`）让前端在退避窗口继续轮询，或至少 failed 也保持低频轮询；纯前端修即可，可把条件抽成纯函数单测。
- **结论**：（待用户拍板）

### 6.3 `retry` 是 admin-only，但仍要求“当前用户是创建者”，viewer 的卡片却显示重试按钮

- **位置**：`backend/app/api/dataset_image_artifacts.py:49-72`、`:115-125`；`web/src/components/RuntimeImagePrepCard.tsx:338-348`；`tests/backend/test_dataset_image_artifacts.py:743-761`。
- **现象**：`retry` 用 `require_admin`，但 `_load_preparation` 仍校验 `created_by == 当前用户`。viewer 自己 prepare 的卡片也显示“重试失败镜像”：viewer 点 → 403；admin 代点 → 404（不是 owner）。测试只分别覆盖 viewer 403 与 admin 访问他人 404，组合起来正好是死路。
- **问题**：显式 retry 是唯一重置 attempts 的路径（见 6.5），但 viewer 创建的准备没有角色能走通；viewer 只能用“重新检查→继续准备”绕过，且会清掉 error、不重置 attempts。按钮对 viewer 是误导。
- **预判**：二选一——retry 改 `require_session` + owner（按钮给创建者），或保留 admin 但去掉 retry 的 owner 限制（租户内代重试）。当前“admin-only + owner-only”是矛盾组合。
- **结论**：（待用户拍板）

### 6.4 profile 未启动时“准备中”永久悬挂；`PREP_ENABLED=false` 还会让容器重启循环

- **位置**：`deploy/docker-compose.prod.yml:212-217`；`backend/app/worker/image_prep.py:108-110`；`web/src/pages/EvalWizardPage.tsx:820-823`。
- **现象**：prepare 已把缺失行置 preparing，但 image-prep 服务不随普通部署启动。没有 worker 时行永远停在 preparing（无人 claim、无超时转移），前端每 3 秒轮询、一直“准备中”；`DATASET_IMAGE_PREP_ENABLED=false` 时 `main()` 在写心跳前退出，`restart: unless-stopped` 会反复重启，healthcheck 永远不绿。
- **问题**：运维忘启 profile、数据盘未就绪、worker 崩溃时，用户看到永久“准备中”，没有“worker 未运行”的信号，同一行也不会自动 failed。与 PR known limitation（须显式启动）叠加，合并后到运维启动前，所有带镜像的数据集都无法开评。
- **预判**：给 preparing 加“多久没被 claim 就转 failed 并提示准备服务未运行”的兜底，或把 worker 心跳/最后 claim 时间暴露到 operations 页；停用用 `stop` 而不是 env=false；Step 4 对空转 preparing 给更明确的提示。
- **结论**：（待用户拍板）

### 6.5 attempts 上限会被 create 的 recheck 绕过，且会清掉上次错误

- **位置**：`backend/app/services/dataset_image_artifacts.py:206-220`、`:270-282`、`:284-289`；`backend/app/services/preparations.py:979-987`；设计承诺在 `plans/m1-02-fullstack-design/05-data-model.md:61`。
- **现象**：`failed`（attempts=3、next_attempt_at=NULL）在 create/prepare 的 `recheck=True` 下 HEAD 404 → 状态改 `missing`、`error` 清空（attempts 仍 3），随后 `_needs_enqueue(missing)` 恒真 → 再入队。我用内存 SQLite 复现：`failed/3 → preparing/3，error=None`。
- **问题**：设计文档说“达到 max_attempts 后保持 failed，只有显式 retry 才重置 attempts 并立即入队”；实际每次点创建都会再触发一次完整 4GB pull，旧错误被清空，attempts 无上限增长——上限只对 worker 自动重试路径生效。
- **预判**：要么 recheck 不把 failed 降级（保持终态，只由显式 retry 解锁），要么把 create 的重新入队定义为“新一次尝试”并显式重置 attempts + UI 提示。两种语义都合理，但不能只对 worker 生效；补一条 `failed at cap + recheck` 测试。
- **结论**：（待用户拍板）

### 6.6 900 秒租约短于 pull 的 1800 秒，启动扫描又是无条件回收；只在单 worker 时安全

- **位置**：`backend/app/config.py:123`；`backend/app/services/dataset_image_prep.py:42`、`:446-480`、`:542-543`、`:551-553`；`backend/app/worker/image_prep.py:123`。
- **现象**：claim 写 900 秒租约后不续；pull 允许 1800 秒。startup sweep 无条件把所有 preparing 行重置到 now 并删本地镜像/全部临时 tar。当前单副本、主循环单线程，sweep 不会与 prepare 并发，无实害。
- **问题**：一旦 `--scale image-prep=2`、旧容器因 orphan 未清理而重叠，第二个 worker 会在 900 秒后抢到同一行；重启 worker 的 startup sweep 还会删掉另一个进程在途的镜像/临时 tar，造成重复 pull、上传覆盖或导出失败。“并发不会重复”只成立于单副本。
- **预判**：pull/save 期间续租（长任务心跳），或 lease 大于所有阶段超时之和；startup sweep 只回收“自己上次进程”的租约（台账加 worker_id）或至少要求 lease 已过期。单副本可先接受，扩缩容前必须修。
- **结论**：（待用户拍板）

## §9 文件级代码分析

### 9.1 `backend/migrations/versions/0029_dataset_image_artifacts.py`（A）

职责：建镜像 tar 台账，含唯一键、状态/清理 check、`(status,next_attempt_at)` 与 tenant 索引；downgrade 反向删除。纯新增、无 backfill（首次 prepare 的 HEAD 自然建行）。思路：把“是否需要准备”做成一行状态机，`next_attempt_at` 兼作租约/退避，省掉独立队列表。检视发现：check/索引名与模型命名约定一致；但模型 FK 名与迁移显式名不一致（见 §7），迁移往返测试没查约束名，属弱校验。

### 9.2 `backend/app/models/dataset.py` + `models/__init__.py`（M）

新增 `DatasetImageArtifact` 与状态常量（`dataset.py:52`、`:304-347`）；`tenant_fk()` 自带索引，`TimestampMixin` 的 `onupdate` 对 Core 批量 update 也生效。检视发现：模型用约定生成 `fk_dataset_image_artifact_tenant_id_tenant`，迁移叫 `fk_dataset_image_artifact_tenant`；Alembic 不按名字比对，故不影响运行，但单独 `DROP CONSTRAINT` 时要小心。

### 9.3 `backend/app/services/dataset_image_artifacts.py`（A）

职责：预检/入队/租约/重试的全部纯服务逻辑。`resolve_preparation_images`（`:84-128`）、`readiness`（`:223-337`）、`ensure/retry`（`:349-405`）、`requeue/claim`（`:408-480`）分层清晰；HEAD 并发、状态机单点写、租约用 SQL 条件更新避免 Python 时区比较。检视发现：`get_or_create` 用 savepoint + 唯一键兜底并发（`:140-176`）思路正确；`readiness` 无行时 `checked_at` 回退 now 属可接受空态；6.5 的 failed→missing 降级是最需拍板的语义。

### 9.4 `backend/app/services/dataset_image_prep.py`（A）

职责：单镜像 `pull→tag→save|gzip→PUT→HEAD→cleanup` 与 startup/periodic sweep。Docker 操作收在 `ImagePreparer` Protocol 后（`:67-76`），测试注入 `FakeDocker`。关键顺序是“先提交 ready 再清理”（`:424-428`），清理覆盖 canonical + 所有候选引用（`:434`）。检视发现：pull 允许 1800 秒但不续租（6.6）；`_retry_at` 达上限返回 None，与 6.5 叠加后上限形同虚设。

### 9.5 `backend/app/worker/image_prep.py`、`docker-entrypoint.sh`、`Dockerfile`（A/M）

职责：worker 主循环（5 秒 claim）、10 秒心跳、600 秒 sweep；entrypoint 新增 `image-prep` 模式；Dockerfile 从 `docker:27-cli` 阶段拷静态 CLI。思路：心跳独立线程，避免长 pull 被 healthcheck 判死；异常按轮捕获。检视发现：`PREP_ENABLED=false` 直接 return 0 会被 restart 策略反复拉起（6.4）；心跳只证明进程活着，不证明队列有进展。

### 9.6 `backend/app/api/dataset_image_artifacts.py` + `main.py`（A/M）

职责：三端点全部要求登录；GET/ensure 由 owner 使用，retry 要求 admin（`:120`）；`_load_preparation` 统一做 404/409（`:49-72`）。响应保持 JSON-safe，不返回 OSS 凭据或签名 URL。检视发现：retry 的 admin+owner 组合是 6.3；ensure 允许 owner 用 `recheck=true` 反复 HEAD，量级受 preparation 镜像数限制，可接受。

### 9.7 `backend/app/services/preparations.py`（M）

职责：prepare 冻结 `image_refs`，create 做最后门禁。旧 prepare 只冻结数据集/模型/资产等；新代码在 `:746-751` 解析并 HEAD、`:791` 写快照、`:829`/`:882` 返回 readiness，create 在 `:979-987` 先 commit 入队再 409。思路：把“缺失不阻塞快照、但阻塞建 run”拆成两个检查点。检视发现：`ImageNotReady` 的 counts/truncated 很完整（`:120-152`），但 TTL 未随 pending 调整（6.1）。

### 9.8 `backend/app/services/dataset_images.py`（M）

职责：新增 `_format_image_ref` 与 `candidate_ref_pairs`，按源排序生成 pull 引用；Hub 保持规范形式，镜像站加 registry/prefix，digest 保留。思路：剥离原始 registry，统一用配置源重写，避免 shadow 源把 pull 引到非预期 registry。检视发现：digest + mirror 的 tag 目标未覆盖（见 §7）；排序/去重/禁用源/空源回退测试齐全。

### 9.9 `backend/app/services/object_store.py`（M）

职责：新增 `put_file`，用 `getsize` + 文件句柄 + `Content-Length` 流式 PUT，返回大小供 HEAD 比对。旧代码只有内存版 `put_bytes`。思路：多 GB tar 不读内存。检视发现：presign 在 `with handle` 之前，抛错时句柄泄漏（§7）；S3 stub 测试覆盖 body 与 Content-Length。

### 9.10 `backend/app/config.py`（M）

职责：新增 9 个 prep 参数（租约、启用开关、工作目录、docker bin、platform、8GiB 门槛、轮询、心跳、最大尝试）。思路：全部给默认值，compose 只透出需要的项。检视发现：`eval_preparation_ttl_seconds` 没有在 compose 透出（6.1）；`dataset_image_arch` 与 `dataset_image_prep_platform` 是两个独立配置，若前者改 arm64 而后者仍 amd64，派生镜像与 pull 平台可能不一致（小概率漂移）。

### 9.11 `deploy/docker-compose.prod.yml`、`deploy.sh`、`rollback.sh`（M×3）

职责：新增 privileged DinD + worker 的 `image-prep` profile、专用网络、心跳 healthcheck、数据盘 bind mount；普通 up/rollback 去掉 `--remove-orphans`。思路：DinD 只进专用网络，worker 同时进默认网络，靠 `DOCKER_HOST` 连接；profile 保证普通部署不拉起。检视发现：取舍见 §7；DinD 2375 未加 TLS 但未发布端口且只连专用网络，当前可接受；`docker:27-dind` 与仓库 `postgres:16-alpine` 一样是浮动 minor 标签，非本 PR 新模式。

### 9.12 `web/src/api/evaluations.ts`（M）

职责：新增 `ImageReadiness` 类型、容错解析与三个调用；`parseImageReadiness` 把未知 status 归 missing、未知 cleanup 归 null（`:1102-1128`）；legacy 响应缺失 `image_readiness` 时返回 null，保持旧行为（`:1154`）。思路：解析层容错，避免后端新增字段导致前端崩。检视发现：`retryImageReadiness` 不带角色信息，按钮显隐只能靠页面/权限上下文（6.3）。

### 9.13 `web/src/components/RuntimeImagePrepCard.tsx`（A）

职责：Step 4 卡片 + 详情抽屉 + 清理标签。思路：计数/进度/逐镜像 chip/失败横幅/操作按钮；`imageShortLabel` 取镜像名末尾 case 后缀，chip 按 ready→preparing→failed 排序，抽屉展示 object key、大小、来源、cleanup/error；`cleanupSummary` 用一句“后台本地 0 镜像/0 tar”强化清理承诺（`:105-119`）。检视发现：ready 但个别行 `local_cleanup=pending` 时仍说已清理（§7）；重试按钮未按角色隐藏（6.3）。

### 9.14 `web/src/pages/EvalWizardPage.tsx`（M）

职责：Step 4 readiness 状态机：prepare 响应初始化、首次自动 ensure、3 秒轮询、三动作、动作 token 防旧响应覆盖、离开 Step 4 清理、按钮禁用与 409 刷新。思路：`activePreparationRef` + `imageActionTokenRef` 处理并发/旧响应，`imageEnsureStartedRef` 防 StrictMode 双发。检视发现：轮询把 failed 当终态（6.2）；轮询没有 AbortController/请求序号，慢响应可能覆盖新状态（概率低）。整体生命周期处理比多数 PR 细致。

### 9.15 测试（A×3 + M×5）

`test_dataset_image_artifacts.py`（838 行）覆盖解析/去重、HEAD 排序、错误容忍、租约/退避/上限、200 条截断、prepare 冻结、create 409、三端点权限与过期；`test_dataset_image_prep.py`（698 行）覆盖成功/镜像源回退/对象已存在/失败清理/磁盘门槛/无 OSS/清理失败/上传大小不符/租约/退避上限/sweep/心跳。缺口：无真实 Docker/OSS E2E（PR 自述）、无 digest+mirror 的 tag 测试、无“failed 达上限 + create recheck”测试（6.5）、无前端轮询纯函数测试、无 viewer 自己 / admin 他人两条权限组合的端到端断言。测试密度高于本仓库平均，属加分项。
