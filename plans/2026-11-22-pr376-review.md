## 1. 一页速览

一句话：把“失败原因”做成端到端结构化字段，让控制台和 bad case 上报看到供应商 429 的原文，而不是一个 `agent_failed`。

比喻：Runner 是唯一的快递分拣员。以前的包裹只贴“异常”标签；现在它同时贴“限流/配额/鉴权/超时/崩溃/资产安装”分拣码、供应商原始面单和运单号（request_id），平台只负责存档和展示。

交付块：

| 块 | 结果 |
|---|---|
| Runner 分类 | 429/配额/401/超时/崩溃/资产安装；request_id 与上游原文 |
| 契约与兼容 | 完成/失败回调可选 `failure`；旧评分报告仍可解析 |
| 后端持久化 | case/attempt `failure_detail_json`，新迁移 0031 |
| 重试 | 429 进入既有 attempt 预算；配额/鉴权/崩溃永久 |
| UI | 类别 + 上游原文 + request_id + 轨迹入口；失败分布 |
| 上报 | bad case `reason` 使用同一结构化原因 |

验证基线：`npm test` 117、`pytest tests/backend` 全量、`node --test tests/runner/*.test.mjs` 189、docs/flow gates、web build、Playwright 本地全栈冒烟 8/8。

## 2. 架构导览

### 2.1 Runner 是唯一分类点

`runner/lib/failure-classify.mjs` 读取 Claude Code `claude-stream.jsonl` 的最后一个 `system/api_error`（或 `result` error），并从 stderr 兜底：429 → 配额/限流，401/403 → 鉴权，5xx → 供应商不可用，超时 → `agent_timeout`，其余 → `agent_crashed`。`real-task.mjs` 把结果同时写进评分报告（`entry.failure`）与完成回调（`failure`），`failCase` 也补上 `failure`。范围：`runner/scripts/real-task.mjs:1000`、`:1690`。

### 2.2 网关保留上游原文

`api/model_gateway.py` 在读取上游错误 body 后追加 `upstream_message`、`upstream_status` 与 `request_id`，并返回 `x-request-id`；`service.upstream_error_message` 负责 JSON/纯文本提取、redact 与截断。Claude Code 的 `api_error` 因此能看到「Token Plan 用量上限 (2056)」。范围：`backend/app/api/model_gateway.py:210`、`backend/app/model_gateway/service.py:360`。

### 2.3 解析与持久化

`swebench.parse_report` 新增 `ParsedFailure`；旧报告只有 `error`/`message` 时也生成结构化类别，`message` 不再被丢弃。`scoring.service.ingest_score_report` 把 detail 写到 case 与 attempt，并更新 `error_summary`。`finalize_completion` 合并回调 `failure`，在进度刷新前排队可重试 attempt（避免单用例 run 先被标终态），随后 ingest 再把重试用例恢复为 `not_scored`。范围：`backend/app/scoring/swebench.py:33`、`backend/app/scoring/service.py:95`、`backend/app/services/case_attempts.py:780-900`。

### 2.4 UI 与上报共用一份数据

API 在 case row、attempt row、评测详情与 `failure_counts` 中返回 `failure`；`web/src/utils/failure.ts` 统一中文类别与展示模型；用例单元格内联类别/上游/request_id，抽屉展示完整原因与轨迹入口，概览新增失败分布。`self_evolution._failure_text` 复用同一 code/message/request_id 组合。范围：`web/src/utils/failure.ts:1`、`web/src/pages/EvalDetailPage.tsx:1388`、`backend/app/services/self_evolution.py:305`。

## 3. 数据流走查

1. 网关收到上游 429，`upstream_error_message` 提取「已达到 Token Plan 用量上限 (2056)」，响应带 `request_id` 与 `x-request-id`。
2. Claude Code 重试 10 次后退出 1；runner 读取 trace 的最后一个 `api_error`，分类为 `model_quota_exhausted`、`retryable=false`，生成中文 message、HTTP 429、request_id。
3. runner 上传评分报告（entry 含 `failure`）并发送完成回调（顶层 `failure`）。
4. 后端 `finalize_completion` 写入 attempt/case `failure_detail_json`；`ingest_score_report` 再次以报告为准补齐；配额永久失败不排队重试；`refresh_run_progress` 收口 run。
5. 控制台详情读取 case/attempt `failure`，列表显示「配额耗尽 + 上游摘要 + request_id」，抽屉显示 HTTP 429/永久失败/完整原文/轨迹入口，概览按 code 聚合失败分布。
6. bad case 上报在 `_build_reason` 中输出「模型配额耗尽：…（request_id: …）」。

## 6. 讨论点

### 6.1 Runner 只取“最后一个”终态错误

- 位置：`runner/lib/failure-classify.mjs:70`
- 现象：初版把所有 `api_error` 拼接分类，早期已重试成功的 429 会盖住后续鉴权/崩溃。
- 问题：误分类会把永久失败当成可重试限流，消耗 attempt 预算。
- 预判：改为只取最后一个终态事件；仅当最后事件没有错误信号时用 stderr 兜底。
- 结论：已修复，新增“早期 429 + 后续 401”回归测试。

### 6.2 失败原因独立列压缩用例表

- 位置：`web/src/pages/EvalDetailPage.tsx:1388`
- 现象：初版新增 240px 独立列后，1440 宽度下用例名按字符换行，右侧列进入横向滚动。
- 问题：与 prototype 的单行表格结构不一致，影响可读性。
- 预判：失败信息内联到用例单元格，保持既有列结构。
- 结论：已修复；Playwright 重测通过，截图见 PR 描述。

### 6.3 完成回调重试依赖顶层 `failure`

- 位置：`backend/app/services/case_attempts.py:865`
- 现象：可重试完成失败由顶层 `failure` 驱动；旧 runner 不发送该字段时不自动重试。
- 问题：滚动升级期间旧 runner 的 429 仍需人工重试。
- 预判：可接受。旧 runner 本身不分类，无法可靠判断 429 与配额；平台保留人工重试入口，升级后自动生效。
- 结论：接受，不做额外推断。

### 6.4 网关错误体可能暴露供应商内部文本

- 位置：`backend/app/model_gateway/service.py:360`
- 现象：`upstream_message` 回显上游 error body。
- 问题：需要确保不含凭据，且长度受控。
- 预判：复用 `trace_redaction.redact_text` 屏蔽 bearer/sk/私钥等模式并截断 500 字符；错误体通常不含 Key。
- 结论：接受；单测覆盖 upstream 原文与 request_id。
