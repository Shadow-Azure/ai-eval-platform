## §1 一页速览

一句话：让镜像准备队列“看得见有没有人在消费”，并让自动上传走内网 OSS。

比喻：原来的准备 Worker 像没有叫号屏的理发店——顾客只看到“等待中”，不知道店里有没有理发师、自己是不是已进店；本 PR 装了叫号屏（heartbeat + queued/processing），把排队和正在理发分开（claimed_at），并把理发师默认排班（deploy 启动）。

| 块 | 结果 |
|---|---|
| 上传链路 | 默认内网 OSS；内网不可达回退公网；pull 前 HEAD 探测 |
| 消费监控 | `service_heartbeat['image-prep']` + readiness `worker` + queue head wait |
| 排队语义 | `claimed_at` / `lease_owner`；GET 只读；offline-only reaping；reaped 行 terminal |
| 启动门禁 | worker 离线 503 `image_prep_unavailable`；在线仍 409 `image_not_ready` |
| 部署 | 数据盘满足门槛时启动/更新；有已领取任务时跳过 |

验证基线：`pytest` 全量 1126 collected 全绿（1 skipped）；`npm test` 127；deploy contract 50；docs/flow 门禁全绿；CI 见 PR checks。

## §2 架构导览

### 2.1 Worker：内网 endpoint 选择

`prepare_one` 仍在 `backend/app/services/dataset_image_prep.py:297` 起走“领取 → 拉取 → 导出 → 上传 → HEAD → 清理”。新增 `_select_store`（`:240` 附近）：先构造 internal store，再构造 public store；对目标 key 做一次 HEAD；internal 可达且对象不存在 → 用 internal；internal 连不上 → 试 public；两个都失败才报错。这把 endpoint 选择从“配置一次”变成“探测一次”，且探测发生在多 GB pull 之前。

### 2.2 队列：`preparing` 拆成 queued / processing

`DatasetImageArtifact` 新增 `claimed_at` / `lease_owner`（`backend/app/models/dataset.py:330` 附近）。`claim_preparing_artifact` 领取时写 host:pid（`dataset_image_artifacts.py:589` 附近）；`_needs_enqueue` / `_recheck_blocked` 拒绝动已领取行（`:222` / `:201`）。状态值保持 `preparing`，readiness 同时返回旧 `preparing_count` 与新的 `queued_count` / `processing_count`（`:377` 附近），避免破坏前端轮询。

### 2.3 监控：心跳在 DB

API 与 Worker 不同容器，无法读 `/tmp/image-prep-heartbeat`。`image_prep_health.py` 复用 `service_heartbeat` 表：Worker 的 DB 心跳线程每 30 秒 upsert 一行并写队列深度（`backend/app/worker/image_prep.py:82` 附近）；`image_prep_health` 读这行并实时统计 queued/processing/failed 与队头等待（`image_prep_health.py:96` 附近）。

### 2.4 启动门禁：409 与 503

`consume_preparation` 在图片未就绪时看 `image_readiness['worker']['online']`（`preparations.py:1109` 附近）：在线 → 原 409 `image_not_ready`；离线 → 503 `image_prep_unavailable`，消息直接说“镜像准备服务未运行/心跳过期”，并带同一份 readiness。

### 2.5 部署：默认排班，不打断正在理发

`deploy.sh` 新增 `image_prep_residency` 阶段（`:117` 附近）：检查数据盘父目录与可用空间 → 检查 image-prep 是否运行 → 查 DB 是否有 `claimed_at IS NOT NULL AND next_attempt_at > now()` 的活跃领取 → 无活跃任务才 `up -d`，有则跳过。失败只记 stage failed，不触发回滚。

## §3 数据流走查

1. 模板 launch → `build_preparation` 冻结镜像并 `readiness(..., enqueue=True)`，缺失行置 `preparing`、`claimed_at=NULL`。
2. `consume_preparation` 再 `ensure_preparation_images`；`readiness` 读 heartbeat：无心跳 → 503；有心跳但未 ready → 409。
3. 调用方 GET `readiness`（控制台）→ 只读，返回 `worker`、`queued_count`、`processing_count`、每行 `phase`。
4. Worker 心跳线程先写 `service_heartbeat`；`prepare_one` 领取一行（写 claimed_at/lease_owner/attempts+1/lease 7200s），选择 internal store，HEAD 目标 key；缺失则 pull → save/gzip → PUT → HEAD 校验 → ready → 清理。
5. 若 worker 一直不在：GET 只显示 `worker.online=false`，不写库；ensure 超过 stale 窗口后把从未领取的排队行标 failed，且该行不再被 ensure 自动复活，直到显式 retry。
6. 进程重启：startup sweep 把 preparing 行重置为可领取并清 claimed_at；临时 tar 仍按原策略清理。

## §6 讨论点

### 6.1 部署“活跃领取检查”与 `up -d` 的竞态

- **位置**：`deploy/deploy.sh` `image_prep_residency`。
- **现象**：先查活跃领取，再 `up -d`；两次命令之间 worker 可能刚领取新镜像。
- **问题**：极小窗口内仍可能打断一次新领取。
- **预判**：可接受——窗口秒级；严格方案需要 worker 优雅停机/lease 暂停，属于后续。
- **结论**：保留“空闲时更新”，不扩大为分布式锁。

### 6.2 控制台仍未展示 `worker.online`

- **位置**：`web/src/components/RuntimeImagePrepCard.tsx`（本 PR 未改）。
- **现象**：readiness 带 `worker`，卡片不渲染；操作员在 step 4 仍可能只看到“准备中”，直到点启动收到 503。
- **问题**：issue 要求“查询明确返回”，API 已满足；控制台提示是 UI 增强。
- **预判**：后续可加 banner，但需要原型/前后截图与人工验收。
- **结论**：本 PR 保持后端 P0，不改 UI。

### 6.3 `readiness` 的 HEAD 仍走公网 endpoint

- **位置**：`dataset_image_artifacts.py` `readiness`。
- **现象**：Worker 上传/校验走内网；API readiness HEAD 仍默认公网。
- **问题**：HEAD 很小，公网可达时无实害；公网被限制时会看到 HEAD 失败。
- **预判**：可后续把 HEAD 也切 internal + 回退；本 PR 按 P0 只改 `prepare_one`。
- **结论**：保留，作为后续优化。

### 6.4 本地流程优先级 P2

- **位置**：`.agents/flow/issues/m8-image-prep-internal-oss.md`。
- **现象**：issue 严重度是 P0，但本地流程 priority 设为 P2。
- **问题**：m8 的 P1 档还有 #273 未 done；把 #436 设为 P1 会让“P1 剩 2 个”锁死已完成的 P2 issue；设 P0/P1 都会破坏现有 flow-online 门禁。
- **预判**：P2 仅用于串行排队，不改变实际严重度；issue 内已写明。
- **结论**：保留，待 #273 关闭后可随流程整理。

## §9 文件级代码分析

### 9.1 `dataset_image_prep.py`

职责：单镜像准备流水线与残留清理。变更 M。旧：`store = object_store_from_settings(settings)` 直接默认公网。新：`store, existing_size = _select_store(settings, object_key)`，internal 优先、public 回退；`outcome.endpoint` 供 Worker 日志诊断。实现思路：把 endpoint 选择从静态配置变成“带一次 HEAD 探测的选择”，避免拉完几 GB 才发现内网不通。检视发现：无；`_select_store` 的 HEAD 失败会带 endpoint 与错误返回，便于定位。

### 9.2 `dataset_image_artifacts.py`

职责：ledger、readiness、enqueue/claim/reap。变更 M。旧：reaper 只看 `next_attempt_at`，GET 也写库。新：heartbeat 在线即 no-op；只回收 `claimed_at IS NULL`；GET 只读；reaped 行 `next_attempt_at=None` 后 terminal。实现思路：把“有没有消费”从时间推断改成显式心跳；把“排队”从 `preparing` 里拆出来但不改状态值。检视发现：`_needs_enqueue` 对 failed + `next_attempt_at=None` 改为 terminal，防止 reaper 刚标 failed 又被 ensure 复活；测试覆盖。

### 9.3 `image_prep_health.py`

职责：心跳 upsert 与队列健康快照。变更 A。实现思路：Worker 写、API 读；计数实时查 ledger，心跳只证明进程活着。检视发现：每次 readiness 多 3 个 count 查询；表小且有 status 索引，可接受。

### 9.4 `preparations.py`

职责：prepare/consume 门禁。变更 M。新：图片未就绪且 worker 离线 → `ImagePrepUnavailable` 503；否则原 409。409 的 message/counts 保持兼容。检视发现：503 是新码，机器调用方需能处理 5xx；PR 描述已说明。

### 9.5 `worker/image_prep.py`

职责：Worker 循环与心跳。变更 M。新：文件心跳继续给容器 healthcheck；DB 心跳线程给 API；启动时先写一次，长 pull 期间仍刷新。检视发现：DB 心跳失败只打印，不退出；符合“队列可恢复”的设计。

### 9.6 `api/dataset_image_artifacts.py`

职责：API 只读语义。变更 M。新：GET 不再 `reap_stale_preparing`，ensure 保留回收。检视发现：无；GET 的 `get_or_create` 仍可能为未知 image 建行，这是原有行为，不属于本 PR。

### 9.7 `deploy/deploy.sh`

职责：部署阶段。变更 M。新：数据盘/空间 → 运行状态 → 活跃领取查询 → 空闲才 `up -d`；失败不触发回滚。检视发现：竞态见 §6.1；`df --output` 依赖 GNU coreutils，生产 Linux 满足。
