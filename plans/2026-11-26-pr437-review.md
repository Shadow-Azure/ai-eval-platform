## §1 一页速览

一句话：把“镜像准备”从“一个看不见的黑盒串行队列”改成“有心跳、有排队/领取区分、可等待、可恢复”的后台任务。

比喻：原来的准备 Worker 像一个没有叫号屏的理发店——顾客只能看到“等待中”，不知道店里有没有理发师、前面还有几个人、自己是不是已经被叫进去；本 PR 装了叫号屏（heartbeat + queued/processing）、把排队和正在理发分开（claimed_at），并把理发师默认排班（deploy 启动），同时把“推子”从慢速公网换成内网。

交付块：

| 块 | 结果 |
|---|---|
| 上传链路 | 默认内网 OSS；内网不可达回退公网；pull 前 HEAD 探测 |
| 消费监控 | `service_heartbeat['image-prep']` + readiness `worker` + queue head wait |
| 排队语义 | `claimed_at` / `lease_owner`；GET 只读；offline-only reaping；reaped 行 terminal |
| TTL | `max(基础窗口, 600s × 镜像数)`，上限 24h；ensure/retry 续期 |
| 机器调用 | 服务令牌 `eval:read` 读、`eval:launch` 推进；409/503 返回 `readiness_url` |
| 重启安全 | `.complete` tar 保留 24h；上传失败/重启直接重传 |
| 部署 | 数据盘满足门槛时启动/更新；有已领取任务时跳过 |

验证基线：本地全量 `pytest` 1126 collected / 全绿（1 skipped）；`npm test` 127；deploy contract 50；docs/flow 门禁全绿。CI 结果见 PR checks。

## §2 架构导览

### 2.1 Worker 侧：从“拉取-导出-上传”到“可恢复的三段流水线”

`dataset_image_prep.py` 的 `prepare_one` 仍是“领取一行 → 拉取 → 导出 → 上传 → HEAD → 清理”的主线（`backend/app/services/dataset_image_prep.py:401` 起）。新增两件事：

1. **endpoint 选择**：`_select_store`（`:280` 附近）先构造 internal store，再构造 public store；对目标 key 做一次 HEAD。internal 可达且对象不存在时直接返回 internal；internal 连不上时尝试 public。这样跨 region 或非阿里云部署不会因为 internal host 不可解析而直接失败，且探测发生在多 GB pull 之前。
2. **导出完成标记**：`complete_tarball_size` / `_mark_tarball_complete`（`:250` 附近）用 `<tar>.complete` sidecar 记录导出大小。上传失败时 `keep_tar=True`（`:541`），下一次 `prepare_one` 读到完整 tar 就跳过 pull/export，直接重传（`:461`）。这直接对应 #436 的“重启—重拉—再卡”循环。

### 2.2 队列侧：`preparing` 不再是一个含义

`DatasetImageArtifact` 新增 `claimed_at` / `lease_owner`（`backend/app/models/dataset.py:330` 附近）。`claim_preparing_artifact` 领取时写入 host:pid（`dataset_image_artifacts.py:589` 附近）；`_needs_enqueue` 与 `_recheck_blocked` 都拒绝动已领取行（`:222` / `:201`）。因此：

- `status=preparing, claimed_at=NULL` = 排队；
- `status=preparing, claimed_at!=NULL` = 处理中；
- readiness 同时返回旧的 `preparing_count`（兼容前端轮询）与新的 `queued_count` / `processing_count`（`:377`）。

### 2.3 监控侧：心跳在 DB，不在容器文件

API 与 Worker 不在同一容器，无法读 `/tmp/image-prep-heartbeat`。`image_prep_health.py` 复用 `service_heartbeat` 表，Worker 的 DB 心跳线程每 30 秒 upsert 一行并写入队列深度（`backend/app/worker/image_prep.py:82` 附近）。`image_prep_health` 再读这行并实时统计 queued/processing/failed 与队头等待（`image_prep_health.py:96` 附近）。

### 2.4 启动门禁：409 与 503 的分工

`consume_preparation` 在图片未就绪时先看 `image_readiness['worker']['online']`（`preparations.py:1109` 附近）：

- 在线 → 原有 `409 image_not_ready`，body 增加 `readiness_url` / `retry_after_seconds`；
- 离线 → 新 `503 image_prep_unavailable`，消息直接说“镜像准备服务未运行/心跳过期”，并带同一份 readiness。

### 2.5 部署：默认排班，但不打断正在理发的顾客

`deploy.sh` 新增 `image_prep_residency` 阶段（`:117` 附近）。它先查 `image-prep` 是否在运行，再查 DB 是否有 `claimed_at IS NOT NULL AND next_attempt_at > now()` 的活跃领取；无活跃任务才 `up -d`（会按新镜像重建），有则跳过并在部署记录里写明。数据盘父目录不存在或空间不足则跳过，不失败整个部署。

## §3 数据流走查

一条端到端主线（机器接口 launch）：

1. `POST /api/v1/eval-templates/{id}/launch` → `build_preparation` 冻结镜像并 `readiness(..., enqueue=True)`，缺失行置 `preparing`、`claimed_at=NULL`，TTL 按镜像数延长。
2. `consume_preparation` 再 `ensure_preparation_images`；`readiness` 读 heartbeat：
   - 无心跳 → `ImagePrepUnavailable` 503，body 含 `readiness_url`、`worker.age_seconds=null`、`counts`。
   - 有心跳但未 ready → 409，body 含同一 readiness 和重试建议。
3. 调用方按 `readiness_url` GET（`eval:read` 或控制台会话）→ 只读，返回 `worker`、`queued_count`、`processing_count`、每行 `phase`。
4. Worker 心跳线程先写一行 `service_heartbeat`；主循环 `prepare_one` 领取一行（写 `claimed_at`、`lease_owner`、`attempts+1`、lease 7200s），选择 internal store，HEAD 目标 key；缺失则 pull → save/gzip → `.complete` → PUT → HEAD 校验 → ready → 清理。
5. 若上传失败：行 failed，保留完整 tar，`local_cleanup=pending`；重试后 `prepare_one` 复用 tar 上传，不重新 pull。
6. 若进程被重启：startup sweep 把 `preparing` 行重置为可领取，但保留 `.complete` tar；新进程复用。只有未完成 tar 被删。
7. 若 worker 一直不在：GET 只显示 `worker.online=false`，不写库；ensure 在超过 stale 窗口后把从未领取的排队行标 failed，且该行不再被 ensure 自动复活，直到显式 retry。

## §6 讨论点

### 6.1 `local_cleanup` 与“保留 tar”语义

- **位置**：`backend/app/services/dataset_image_prep.py` sweep 行循环。
- **现象**：上传失败保留完整 tar 时，`prepare_one` 先把 `local_cleanup` 设为 pending；10 分钟 sweep 清理本地镜像后若直接写 done，字段会声称“本地已清理”，但 `/work` 仍有 1GB+ tar。
- **问题**：控制台 cleanup 摘要会误报“0 个临时 tar”。
- **预判**：sweep 检测到该行是 failed、attempts 未到上限且完整 tar 仍存在时，应保持 pending；ready 行的残留 tar 则直接删。
- **结论**：已在 `8eed7d8` 修复并补测试 `test_sweep_keeps_a_complete_retry_tarball_pending_but_drops_a_ready_one`。

### 6.2 部署“活跃领取检查”与启动更新之间的竞态

- **位置**：`deploy/deploy.sh` `image_prep_residency` 阶段。
- **现象**：先查活跃领取，再执行 `up -d`；两次命令之间 worker 可能刚领取一个新镜像。
- **问题**：极小窗口内仍可能打断一次新领取。
- **预判**：可接受——窗口是秒级，且 `.complete` tar 复用已把重启损失降到“最多重新 pull 当前镜像”；若要严格，可在 worker 侧增加优雅停机/lease 暂停。
- **结论**：留作后续；当前 PR 以“空闲时更新”为目标，不扩大为分布式锁。

### 6.3 控制台仍未展示 `worker.online`

- **位置**：`web/src/components/RuntimeImagePrepCard.tsx`（本 PR 未改）。
- **现象**：readiness 已带 `worker`，但卡片不渲染；操作员在 step 4 仍可能只看到“准备中”，直到点启动收到 503。
- **问题**：issue 要求“查询明确返回”，API 已满足；控制台提示属于 UI 增强。
- **预判**：若要补，应在卡片 banner 显示“镜像准备服务未运行，最近心跳…”，但这会改变 UI，需要原型/前后截图与人工验收。
- **结论**：本 PR 保持后端范围，不擅自改 UI；作为后续可选增强。

### 6.4 `readiness` 的 HEAD 仍走公网 endpoint

- **位置**：`backend/app/services/dataset_image_artifacts.py` `readiness`。
- **现象**：Worker 上传/校验已走内网，但 API 的 readiness HEAD 仍用 `object_store_from_settings(settings)`（默认公网）。
- **问题**：HEAD 很小，公网可达时无实害；若公网 OSS 被限制，控制台会看到 HEAD 失败。
- **预判**：可后续把 HEAD 也切 internal + 回退；本 PR 按 issue 明确要求只改 `prepare_one`，避免一次改两条 OSS 路径。
- **结论**：保留，作为后续运维优化。

### 6.5 服务令牌 allowlist 的路径判断

- **位置**：`backend/app/api/dependencies.py:122` 附近。
- **现象**：模板 allowlist 只约束 `template_id` 路径；artifacts 路由无 template_id，按 `request.url.path.startswith('/api/v1/dataset-images/artifacts')` 放行，再由 preparation owner 约束。
- **问题**：字符串前缀匹配依赖路由路径稳定；新增非模板 `eval:launch` 路由时容易忘记扩这里。
- **预判**：可接受；当前只有 artifacts ensure/retry 两个非模板 `eval:launch` 路由，测试已覆盖 allowlist token 的 allow 与 template 路径的 deny。
- **结论**：保留；后续新增路由时复用同一模式。

## §9 文件级代码分析

### 9.1 `backend/app/services/dataset_image_prep.py`

职责：单镜像准备流水线与残留清理。变更形态 M。

关键依赖：无新增第三方包；`urllib`/SigV4 来自现有 `object_store`。比喻：`.complete` sidecar 像快递面单——没有面单的箱子可能是半成品，有面单的箱子可以直接重新投递。

旧代码 vs 新代码：

```python
# 旧：默认公网 store，失败 finally 永远删 tar
store = object_store_from_settings(settings)
...
finally:
    cleanup_status, cleanup_error = _cleanup(docker, tar_path, refs)
```

```python
# 新：internal 优先 + 公网回退；完整 tar 保留
store, existing_size = _select_store(settings, object_key)
...

    tar_complete = True
...

    docker, tar_path, refs, remove_tar=not keep_tar

```

实现思路：把“导出完成”从进程内存状态提升为磁盘标记；把 endpoint 选择从一次构造变成一次带探测的选择。两者都让“重启/跨网络”从致命变成可恢复。
