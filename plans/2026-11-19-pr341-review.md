## §1 一页速览

一句话：**会话包不再按“同名最新一行”认亲，而是主入口找回真正的根，子入口用平台会话 id 找每个 Agent。**

比喻：Claude Code 的一家人（主 Agent 和所有子 Agent）户口本上都写着同一个名字。旧端点只认名字，谁最后登记就选谁，于是经常把“孩子”当成“家长”；现在主入口按“家长”身份（没有父级、非 unlinked、ordinal 最小）挑人，子入口则给每个成员发了唯一的门牌号（`TraceSession.id`），HE 拿着门牌号逐层敲门即可。

| 交付块 | 内容 |
|---|---|
| 根解析 | 签名 run 内 `parent_session_id IS NULL`、`status != 'unlinked'`、ordinal 最小的行；没有则 404 |
| 子解析 | 按全局唯一 `TraceSession.id`；`unlinked` 行返回 404 |
| 返回身份 | `childSessionIds` 与更深层 `parentSessionId` 用 `TraceSession.id`；直接子级的父 id 仍是 native 根 id |
| 作用域 | 选择查询先 join `trace_session → eval_case_attempt → eval_case_run`，把选择收敛到签名 run |
| 展示 | `agentId` 仍只进 `agentMeta`，不参与寻址 |

## §2 架构导览

### 2.1 根入口：native id + 根行选择

`backend/app/api/self_evolution.py:159-170`。根请求的 `sessionId` 是 bad case 载荷里冻结的 native 根 id，不能变；但同一 native id 下还有全部子 Agent 行。新查询先按 `native_session_id` 命中，再要求 `parent_session_id IS NULL` 且 `status != 'unlinked'`，最后按 `ordinal, id` 取第一行。旧查询的 `ORDER BY created_at DESC`（`:216-221`，已删除）正是“子 Agent 通常后入库”时选错人的根因。

### 2.2 子入口：平台会话 id

`backend/app/api/self_evolution.py:172-178`。HE 把根 envelope 的 `childSessionIds` 逐一代入模板；新值改为 `TraceSession.id`（`:316-324`），与前端 session picker、URL `?session=`、spans API 使用的是同一身份。更深层 `parentSessionId` 取父行 id（`:305-315`），直接挂在根下的子节点仍回报 native 根 id，保证与遍历父 envelope 的 `sessionId` 一致。

### 2.3 作用域与错误

`backend/app/api/self_evolution.py:132-146` 的 join 把候选行限制在签名 run；`_verify_run_scope`（`:103-129`、`:282-284`）作为第二道校验保留。run 内存在但不可用的 id（如 unlinked）返回 404；只在别的 run 存在的 id 返回与坏签名相同的 401，避免模板泄漏后探测他人 run。

## §3 数据流走查

以测试 fixture 为例：根 R（native `S`，parent 空，ordinal 0）、子 C1/C2（native 都是 `S`，parent=R，ordinal 1/2）、孙 G（parent=C1，ordinal 3）、unlinked U（native `S`，parent 空，ordinal 4，最后入库）。

1. HE GET `/sessions/S`：根查询排除 U（unlinked）与 C1/C2（有父），返回 R；`agentKind=main`，`parentSessionId=null`，`childSessionIds=[C1.id, C2.id]`。
2. HE GET `/sessions/C1.id`：根查询不命中（id 不是 native id），按平台 id 命中 C1；`parentSessionId=S`，`childSessionIds=[G.id]`。
3. HE GET `/sessions/G.id`：`parentSessionId=C1.id`，不再错误地回报 native 根 id。
4. 若有人 GET `/sessions/U.id`：404；GET `/sessions/S` 在另一个 run 上也存在时，签名 run 内的 R 胜出，不会 401。

## §6 讨论点

### 6.1 同一 run 内跨 attempt 的同名根行

- **位置**：`backend/app/api/self_evolution.py:166`
- **现象**：签名 URL 只有 run 作用域，没有 attempt；同一 native id 若在同一 run 的两个 attempt 各有根行，`ordinal` 是 attempt 内序号，可能相同，最终由 `id` 字典序决定。
- **问题**：理论上可能选中旧 attempt 的根行。
- **预判**：生产上 native id 每次执行唯一，重放通常落到另一个 run（#338 场景 D），本 PR 已用 run 作用域覆盖；要彻底按 attempt 选，需要改签名/载荷契约，超出本 issue。
- **结论**：留空。

### 6.2 unlinked 的错误码

- **位置**：`backend/app/api/self_evolution.py:176-177`
- **现象**：按平台 id 命中 unlinked 行时返回 404 `self_evolution_session_not_found`。
- **问题**：issue 允许 404 或 409；404 与“不存在”同码，排障时略难区分。
- **预判**：404 不新增契约码、不泄露行状态，符合端点“存在性校验在签名之后”的既有风格；409 会暗示“这行存在但不可用”。
- **结论**：留空。

### 6.3 `_verify_run_scope` 的双重校验

- **位置**：`backend/app/api/self_evolution.py:282-284`
- **现象**：选择查询已经带 run 作用域，之后仍调用一次 `_verify_run_scope`。
- **问题**：多一次两表查询，看似冗余。
- **预判**：开销可忽略，保留它可在未来有人改坏 `_run_scoped_sessions` 时兜底为 401，而不是把别的 run 的会话包发出去。
- **结论**：留空。

### 6.4 前端会话选择器副标题

- **位置**：`web/src/features/traces/traceModel.ts`（本 PR 未改）
- **现象**：issue 提到 picker 副标题对每个会话都显示相同的 `native_session_id`。
- **问题**：不是寻址正确性问题，只是可读性。
- **预判**：属于前端体验优化，需单独 UI 变更与 Before/After 截图，不在本后端缺陷 PR 内顺手改。
- **结论**：留空。

## §9 文件级代码分析

### 9.1 `backend/app/api/self_evolution.py`

职责：签名会话包端点。变更形态 M。

旧代码（`git show origin/main:backend/app/api/self_evolution.py`）：

```python
trace_session = session.scalar(
    select(TraceSession)
    .where(TraceSession.native_session_id == session_id)
    .order_by(TraceSession.created_at.desc(), TraceSession.id)
    .limit(1)
)
```

新代码：

```python
root = session.scalar(
    _run_scoped_sessions(run_id)
    .where(
        TraceSession.native_session_id == session_id,
        TraceSession.parent_session_id.is_(None),
        TraceSession.status != "unlinked",
    )
    .order_by(TraceSession.ordinal, TraceSession.id)
    .limit(1)
)
```

思路总结：把“按名字找最新行”拆成“主入口按根身份找根行 + 子入口按唯一 id 找节点”，两段都先收敛到签名 run；身份字段与前端 session picker 对齐。

### 9.2 `tests/backend/test_self_evolution_sessions.py`

职责：端点回归。变更形态 M。

旧 fixture 给子会话造了不同的 `native_session_id`，BFS 第二跳“碰巧”通过。新 fixture 让根、子、孙、unlinked 共用 `MAIN_SESSION`，并按入库顺序把 unlinked 放在最后，直接复现“最新行是子 Agent”的旧缺陷；新增 BFS 用例让每个 `childSessionIds` 都真正回请求一次，等于在测试里跑了一遍 HE 的拉取循环。
