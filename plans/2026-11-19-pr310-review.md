## §1 一页速览

一句话：把“分片一派人就开始按 3600 秒墙钟杀排队 attempt”改成“分片里只要有人开始跑或跑完，排队的兄弟就续租；整片真的没进度才按 `case_timeout + 600s` 判死，最多续到 23 小时”。

比喻：以前像电影院检票——整场观众同一时刻进场，1 小时后没进场的票全部作废；现在每有一位观众进场或离场，检票员就把还在队伍里的人的入场截止时间往后推，只有整条队伍连续一小时没人动才清场，但清场最晚不超过 23 小时。

## §2 架构导览

### 2.1 数据层：两列租约，NULL 即旧行

`eval_case_attempt` 新增 `queue_started_at` / `queue_deadline`（`backend/app/models/evaluation.py:277-283`），迁移 0030 只做两个 nullable `ADD COLUMN`（`backend/migrations/versions/0030_queue_progress_lease.py:30-40`）。选择 nullable 而不是带默认值回填，是为了让升级前已完成/已超时的历史行保持原样，并让 reaper 通过 `queue_deadline IS NULL` 精确识别旧行。

### 2.2 计算层：预算与续期只在一个模块

`queue_lease.queue_budget_seconds` 负责 `min(case_timeout + grace, max)`（`backend/app/services/queue_lease.py:50-56`）；`stamp_dispatch_lease` 在派发时写 `queue_started_at=now` 与 `queue_deadline=now+budget`（`:59-66`）；`renew_shard_leases` 只改“同 run、同 shard_id、同 attempt_no、仍在等待”的兄弟行，并用一条 `UPDATE ... WHERE id IN (...)` 完成（`:90-130`）。绝对上限取片内最早 `queue_started_at/phase_changed_at/created_at` 加 `eval_queue_timeout_max_seconds`（`:112-125`）。

### 2.3 触发层：只认“跑过”的进度

- started：`_promote_running` 在 `mark_status("running")` 后调用续期（`backend/app/services/case_attempts.py:245-265`）。
- 成功完成：`finalize_completion` 在标记终态后调用，条件是 `started_at is not None`（`:662-676`）。
- 失败/超时：`settle_attempt_failure` 在终态与释放 runner 后调用，同样要求“跑过”（`backend/app/services/lifecycle.py:286-303`）。
- spot 中断：`handle_spot_interruption` 直接标记 failed，不经过 settle，因此单独补了一次续期（`case_attempts.py:1041-1053`）。
- 队列超时/取消/派发失败不续期：`started_at is None` 或根本不走这些路径，避免“死分片自我续命”。

### 2.4 判定层：reaper 只读 deadline，旧行回退

`reaper.py:131-190` 的排队循环先读 `queue_deadline`；为空时按 `phase_changed_at + eval_queue_timeout_seconds` 判旧逻辑。超时时计算 `queue_wait_seconds`、`last_progress_at`、`shard_queue_started_at`，把 `queue_deadline`、`lease_budget_seconds`、`shard_size`、`concurrency` 一起写进 `case.timeout` 事件；摘要写成“等待 X 秒未启动，最近 Y 秒无进度（租约 Z 秒）”。执行/评分/上传/心跳四条规则未改。

### 2.5 支撑件

`_shard_attempts` 通过 join `eval_case_run` 限定同一 run，避免不同 run 复用 shard_id 时串片（`queue_lease.py:68-86`）；`_aware` 统一 SQLite naive UTC 与 Postgres aware datetime（`:36-42`）；`shard_progress` 取片内 `started_at/ended_at` 最大值作为最近进度（`:133-158`）。

## §3 数据流走查

1. 创建评测：全部 attempt 先为 `pending`，不写租约。
2. dispatcher 成功 POST repository_dispatch 后，对每个 attempt `mark_status("queued")` 并写 `queue_started_at=now`、`queue_deadline=now+4200s`（默认 60min case + 600s grace）。
3. 第一波 Runner 启动：`handle_started` → `_promote_running` 把该 attempt 置 `running`，并把同片仍在 `queued` 的兄弟 deadline 推到 `now+4200s`，但不超过片内最早入队时间 + 82800s。
4. 第一波完成：`handle_completed` → `finalize_completion` 标记成功并再次续期；即使完成回调晚到，`started_at` 仍非空，续期成立。
5. 第一波失败/超时：`handle_failed` 或 reaper → `settle_attempt_failure` 标记终态并续期；若是心跳丢失且可重试，还会创建新 attempt。
6. 持续多波：每一波开始/结束都会把等待者的 deadline 推后，直到最后一批 attempt 开始或整片连续 `4200s` 没有 started。
7. 整片卡死：deadline 到点，reaper 判 `queue_timeout`，事件记录等待时长与最近进度；若已到 23h 上限，续期被压到上限后立即到期。
8. 升级中的旧分片：`queue_deadline` 为 NULL，reaper 走 `phase_changed_at + 3600s`，不会因新列缺失报错或集体误杀。

## §6 讨论点

### 6.1 取消/预算暂停是否也应续期

- **位置**：`backend/app/services/lifecycle.py:293-303`、`backend/app/services/reaper.py:131-190`。
- **现象**：只有 `started`、成功完成、失败/超时结算和 spot 中断会续期；run 取消、预算暂停时对已运行 attempt 的取消不续期。
- **问题**：issue 原文写“任意 attempt 进入终态（succeeded/failed/timeout/cancelled）”，字面上包含取消；当前实现没有在取消路径续期。
- **预判**：取消/暂停后不应再让排队 attempt 等待，续期没有意义，反而会延长收口；但需要确认这是否符合“终态即续期”的验收口径。
- **结论**：

### 6.2 旧行的绝对上限起点可能早于实际派发

- **位置**：`backend/app/services/queue_lease.py:105-118`。
- **现象**：`shard_started_at` 取 `queue_started_at → phase_changed_at → created_at` 的最早值；缺少前两者的极旧行会从 `created_at` 起算 23h。
- **问题**：若一个旧分片在容量门禁里等了很久才派发，`created_at` 会提前消耗 23h 上限；不过旧行本就走 3600s 回退，且 M4-02 之后 `phase_changed_at` 在派发时写入。
- **预判**：影响面仅限缺少 `phase_changed_at` 的极旧行，且不会造成误杀（只会更早到上限）；可以接受。
- **结论**：

### 6.3 详情页只靠摘要展示排队时长，没有结构化字段

- **位置**：`backend/app/services/reaper.py:147-190`、`web/src/pages/EvalDetailPage.tsx` 现有 `error_code/error_summary` 渲染。
- **现象**：事件 payload 有 `queue_wait_seconds` 等结构化字段，但前端事件列表只渲染 `error_summary`；这次没有改前端。
- **问题**：验收要求“详情页/事件能区分并显示排队等待时长”，摘要文本满足；但若后续要做筛选/排序/图表，需要 API 或前端消费结构化字段。
- **预判**：本次不改 UI 是合理的（避免为一个后端超时修复引入视觉回归）；结构化字段已落库，后续可单独做展示。
- **结论**：

### 6.4 续期使用一条批量 UPDATE，但未加索引

- **位置**：`backend/app/services/queue_lease.py:120-129`。
- **现象**：续期按 `id IN (...)` 更新，S ≤ 255；reaper 仍按 `status IN ('dispatching','queued')` 取批。
- **问题**：没有为 `queue_deadline` 建索引；若未来 attempt 表很大且大量排队行，reaper 仍会扫描 status 索引命中的行，而不是按 deadline 排序。
- **预判**：当前 `eval_lifecycle_batch_size=100` 且有 `status` 相关索引，量级可控；加 deadline 索引属于后续优化，不应阻塞本 issue。
- **结论**：

## §9 文件级代码分析

### 9.1 `backend/app/services/queue_lease.py`（A）

职责：把“分片进度租约”的预算、派发盖章、批量续期、进度快照收在一个模块，避免 dispatcher/callback/reaper 各算一套。

关键依赖：标准库 `datetime` + SQLAlchemy `select/update`；不依赖任何网络或 GitHub 客户端，因此可以被 dispatcher、回调、reaper 和测试共同复用。

变更代码块分析：

1. `WAITING_ATTEMPT_STATUSES` 包含 `pending/dispatching/queued/leased`（`:33`）。为什么：续期应覆盖所有“还没开始”的状态；`leased` 是 M2 旧状态机的遗留值，保留以兼容历史行。
2. `queue_budget_seconds` 先取 `run.case_timeout_seconds`，再取配置 fallback，最后 `min(..., max)`（`:50-56`）。为什么：预算必须跟随每个 run 的用例预算，而不是全局固定值；上限避免 60min 用例在 24 小时排队上限前仍无限续。
3. `renew_shard_leases` 先筛兄弟，再取片内最早时间，最后一条 UPDATE（`:90-130`）。为什么：S ≤ 255，批量更新足够；只改“仍在等待”的行，不去碰已 running/terminal 的 attempt，避免覆盖状态机。
4. `shard_progress` 返回最近 `started_at/ended_at` 和最早入队时间（`:133-158`）。为什么：超时事件需要向运维解释“最后一次进度是什么时候”，而不是只给一个布尔值。

实现思路总结：租约是一个纯函数 + 一次批量写，调用方只决定“何时算进度”。

### 9.2 `backend/app/services/reaper.py`（M）

职责：五类超时的唯一扫描器；本次只改第一类（平台排队）。

变更代码块分析：

1. 旧的 `_expired(_phase_marker(attempt), eval_queue_timeout_seconds)` 被替换为“有 deadline 读 deadline，否则回退旧墙钟”（`:131-145`）。为什么：新行按进度续租，旧行必须保持升级前行为。
2. `expire` 增加 `extra_payload` 参数（`:98-124`）。为什么：queue_timeout 需要额外字段，但其他四类超时的 payload 不应被污染。
3. 超时摘要与 payload 直接复用 `shard_progress`（`:147-190`）。为什么：把“等了多少秒 / 最近一次进度”放在事件里，详情页无需新增 API 就能显示。

### 9.3 `backend/app/services/case_attempts.py`（M）

职责：Runner 回调状态机；本次在 started、完成、spot 中断三个真实进度点续期。

变更代码块分析：

1. `_promote_running` 末尾续期（`:245-265`）。为什么：这是“第一次 started”的唯一入口；heartbeat/upload 复用该函数时若已 running 会提前返回，不会重复续期。
2. `finalize_completion` 在 `started_at` 非空时续期（`:662-676`）。为什么：成功完成是明确进度；`artifact_missing` 等终态也走这里，条件仍成立。
3. `handle_spot_interruption` 单独续期（`:1041-1053`）。为什么：spot 路径直接写 failed，不经过 `settle_attempt_failure`，不补就会漏掉“运行中被云侧回收”的进度。

### 9.4 `backend/app/services/lifecycle.py`（M）

职责：失败/超时结算的唯一事务路径；本次在 `settle_attempt_failure` 中续期。

变更代码块分析：在 `mark_status`、`ended_at`、`error_*`、`release_runner_binding` 之后调用续期（`:286-303`）。为什么放在这里：所有失败/超时（回调、reaper、重试）都汇聚到此；条件是 `started_at is not None`，保证队列超时/取消/派发失败不会给同片续命。

### 9.5 `backend/app/services/dispatcher.py`（M）

职责：outbox → repository_dispatch；本次在成功派发后盖章。

变更代码块分析：`mark_status("queued")` 之后立即 `stamp_dispatch_lease`（`:365-375`）。为什么在成功 POST 之后：容量门禁可能把分片压住数小时，租约必须从真正到达 GitHub 时起算，而不是创建时间。

### 9.6 `backend/app/config.py`、`models/evaluation.py`、`0030` 迁移（M/A）

职责：配置与持久化。
