## §1 一页速览

**一句话**：把「实时事件」从直接打印 payload 的调试列表，改成先经过一层可读投影、再按关键事件挑选的原型时间线。

**一个比喻**：原来的卡片像把货运单上的二维码原样贴到墙上；现在多了一个「翻译员」`eventTimeline.ts`，先把二维码读成「3 个文件 ready」，再让「排班员」`recentTimeline()` 决定墙上只挂最近 6 张关键单据，完整档案仍留在「查看全部」。

**交付块**

| 块 | 内容 |

| 摘要映射 | `trace.ingestion.updated` 显示文件计数，未知类型只读标量 |
| 概览时间线 | 主体 + 动作 + 上下文 + `HH:MM`，圆点与连线 |
| 概览挑选 | 关键事件白名单、按 attempt 折叠入库快照、心跳不占位 |
| 完整日志 | 复用摘要；类型列中文标签不再竖排 |

## §2 架构导览

### 2.1 纯函数投影层

`web/src/features/evaluations/eventTimeline.ts:182` 的 `describeEvent()` 是唯一入口：输入一条 `EvaluationEvent` 和 case key 映射，输出 `{subject, action, context, tone}`。它不依赖 React，因此能被 Node 测试直接导入（`tests/eval-event-timeline.test.mjs:1`）。

关键约束在 `eventTimeline.ts:140` 的 `ingestionCopy()`：只从 `counts` / `file_counts` 读数字，payload 里的 `files`、`errors` 数组从不进入文案。默认分支（`eventTimeline.ts:388`）也只扫描 `reason`、`error`、`status` 等白名单标量，这是「不再出现 `files=`」的结构性保证，而不是靠截断字符串。

### 2.2 概览挑选层

`eventTimeline.ts:57` 定义概览白名单：评测生命周期、关键用例事件、`trace.ingestion.updated`；心跳、`started_late`、下载类事件只留完整日志。

`eventTimeline.ts:441` 的 `recentTimeline()` 从新到旧遍历：入库快照按 `(case_run_id, attempt_no)` 去重；有关键事件时最多保留 `INGESTION_OVERVIEW_SLOTS = 2` 条入库，没有关键事件时用入库填满 6 条。最后按 id 倒序输出，保证时间列和数据库顺序一致。

### 2.3 展示层

`EvalDetailPage.tsx:1595` 用 `useMemo` 把事件数组投影成 6 条 `EventTimelineItem`；`EvalDetailPage.tsx:1867` 的 DOM 是 `圆点 / 文案 / time` 三列网格。CSS 在 `eval-detail.css:539` 用 `grid-template-columns: 16px minmax(0, 1fr) auto` 复刻原型 `timeline-item`，`:not(:last-child)::before` 画连线。

事件日志（`EvalDetailPage.tsx:2908`）复用 `eventSummary()`，并把类型列改成「英文类型 tag + 中文标签」两行，解决长 tag 把中文标签挤成每行一个字的问题。

## §3 数据流走查

1. `useEvalEvents()`（`web/src/api/useEvalEvents.ts:64`）拉最近 100 条快照并按 id 合并，终态 run 不再连 SSE。
2. `OverviewPanel` 收到 `events` 和 `caseKeyById`，`recentTimeline()` 过滤、去重、截取 6 条。
3. 每条事件经 `describeEvent()`：case key 来自 payload 或映射；入库事件读计数；失败事件带错误码和摘要；完成事件按 `result_status` 给动作和色调。
4. 渲染成时间线；点击「查看全部」切到事件日志 tab。
5. 事件日志对同一批事件逐行调用 `eventSummary()`，展开行仍可看原始 payload 供排查。

## §6 讨论点

### 6.1 概览只取最新 100 条窗口

**位置**：`web/src/api/useEvalEvents.ts:73`（快照 `limit: 100`）、`eventTimeline.ts:441`。

**现象**：概览只在这 100 条里挑关键事件。若最新 100 条恰好全是被折叠的入库快照 / 心跳，概览会只剩 2 条入库，看不到更早的完成 / 失败。

**问题**：阈值是否足够覆盖真实长评测？单 case 每次入库可能写多条快照，6 个 case 就可能超过 100 条。

**预判**：当前修复已满足 issue 的「最近事件不被打满」；如生产再出现关键事件被挤出，可把快照上限提高到 200（API 上限）或给概览单独请求 `case.completed/failed`。不建议在本 PR 扩大接口面。

**结论**：

### 6.2 长 case key 的自然换行

**位置**：`EvalDetailPage.tsx:1867`、`eval-detail.css:539`。

**现象**：`scikit-learn__scikit-learn-10297` 等长 key 在 310–320px 卡片内会占两行，动作文字可能从第二行开始。

**问题**：原型使用较短的 `django__django-11019`，长 key 下是否应该把 subject 强制独占一行？

**预判**：保持原型的内联「主体 + 动作」；换行不产生横向滚动，也不影响时间列。强制堆叠会偏离原型，收益有限。

**结论**：

### 6.3 冒烟数据的真实性

**位置**：PR 描述「限制」。

**现象**：After 截图来自本地 SQLite + 直接写入的同形状 50 条事件，不是真实 Runner 轨迹入库链路。

**问题**：fixture 可能漏掉真实数据中的字段差异（例如 `counts` 缺失、`files` 超大）。

**预判**：摘要逻辑只依赖计数和标量，且用真实生产 payload 结构构造 fixture；合并部署后补一次真实评测截图即可闭环。

**结论**：

## §9 文件级代码分析

### 9.1 `web/src/features/evaluations/eventTimeline.ts`（A）

**职责一句话**：把任意事件投影成人类可读副本，并挑选概览时间线；纯函数、无 React 依赖。

**关键依赖解读**：只依赖 `EvaluationEvent` 类型。仓库的 Node 测试直接用原生 type stripping 导入 `.ts`（`tests/trace-viewer-model.test.mjs` 同法），所以纯函数层可以被低成本覆盖。

**变更代码块分析**

新增的入库投影：

```ts
const counts = asRecord(payload.counts) ?? asRecord(payload.file_counts);
const ready = asCount(counts?.ready) ?? 0;
...
const action = parts.length
  ? `轨迹入库：${parts.join(" · ")}`
  : `轨迹入库：${expected !== null ? `${expected} 个文件待处理` : "暂无文件状态"}`;
```

这在做什么：把生产 payload 的两套计数字段统一成一行；为什么这么写：`counts` 与 `file_counts` 在 `trace_ingestion.py:1124` 是同一份字典，但历史事件可能只有一套，取到就够。

新增的概览挑选：

```ts
const ingestionSlots = ingestion.length
  ? Math.min(limit, lifecycle.length ? INGESTION_OVERVIEW_SLOTS : limit)
  : 0;
const selected = [
  ...lifecycle.slice(0, limit - ingestionSlots),
  ...ingestion.slice(0, ingestionSlots),
];
```

这在做什么：先给关键事件留位，再给入库快照固定 2 个名额；为什么这么写：直接 `slice(-6)` 会让入库快照和心跳挤掉完成 / 失败，而完全丢掉入库又看不到轨迹状态。

**实现思路总结**：投影层只信标量白名单；挑选层先保关键、再限快照；排序按 id 保证稳定。

**检视发现**：无正确性问题。`expected` 与各状态之和不等时额外显示「预期 N 个文件」，对 `MAX_EVENT_FILES` 只保留部分文件的 payload 有解释价值。

### 9.2 `web/src/pages/EvalDetailPage.tsx`（M）

**职责一句话**：评测详情页；本次只改事件摘要来源、概览渲染和日志类型列。

**关键依赖解读**：Ant Design 提供 Card/Tag/Space/Table；时间线不再用 antd `Timeline`，因为原型需要「右侧时间列 + 连线」的自定义网格。

**变更代码块分析**

旧（删）：

```tsx
const recentEvents = events.slice(-6).reverse();
...
```

新：

这在做什么：把「一条事件的大段文本」拆成结构化的主体 / 动作 / 上下文 / 时间四槽；为什么这么写：原型和 issue 都要求时间始终可见，且事件类型不再挤占第二行。

**检视发现**：`payloadValue()` 仍用于心跳时间线，未受影响；完整日志的展开行仍展示原始 JSON，但只在用户主动展开时出现，符合「查看全部排查」的定位。
