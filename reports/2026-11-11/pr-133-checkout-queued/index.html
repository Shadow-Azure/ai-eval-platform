Executive summary

先给结论

结论

checkout 失败并没有把 runner 卡住；它让平台失去了“用例已开始”的唯一信号。

runner 侧的 job 已经失败并结束，平台侧的 attempt 仍停在 queued，直到 3600s 队列超时把它判成 timeout。PR #133 用 3 次 checkout 尝试降低“一次抖动就失败”的概率，属于有效的止血；但平台感知不到 job 失败这个根因没有变。

止血有效 根因未修 PR 描述需改

它想修什么

阿里云 spot Runner 是全新实例，每次 execute 都要从 github.com 冷克隆。一次 TLS 断连就让 job 在第一步失败，用例永远等不到 started。3 次尝试把“一次就失败”改成“连续三次才失败”。

为什么是 queued

queued 的语义是“dispatch 已成功，等 started 回调”，不是“GitHub 还在排队”。checkout 排在 started 之前，失败时没有任何回调能推进 attempt。

还差什么

平台不监听 workflow run 的失败；3600s 后是 timeout 终结，不是自动重排；若 run 已终结，连手动重试都会被拒绝。真正的修复在平台侧，不在 workflow。

阅读路径

下文按“事实 → 链路 → 场景 → 放大 → 修复 → 建议 → 检视”展开。先看 01 的事故时间线，再看 03 的四层原因；如果你只关心“什么场景会卡”，直接跳到 04 和 05。

01

What changed

PR #133 改了什么

改动只有一个文件：.github/workflows/eval-shard.yml。prepare 与 execute 的 checkout 各从 1 次变成 3 次；后两次重试都靠上一步的 outcome == 'failure' 触发。

改动结构

# 改动前（prepare / execute 各一处）
- uses: actions/checkout@v4

# 改动后
- name: Checkout
  id: checkout
  uses: actions/checkout@v4
  continue-on-error: true
- name: Checkout (retry 1)
  id: checkout_retry_1
  if: steps.checkout.outcome == 'failure'
  uses: actions/checkout@v4
  continue-on-error: true
- name: Checkout (retry 2)
  if: steps.checkout.outcome == 'failure' && steps.checkout_retry_1.outcome == 'failure'
  uses: actions/checkout@v4
位置：prepare :123-134，execute :181-192。

设计意图

  • 第一次失败不终止 job：continue-on-error: true 让 outcome 记为 failure，但 job 继续。
  • retry 1 只在第一次失败时跑；同样 continue-on-error，给最后一次机会。
  • retry 2 要求前两次都失败；没有再兜底，失败即 job 失败。
  • prepare 与 execute 各一套：prepare 失败会让整个 matrix 不生成，影响更大。

影响面

execute：失败只影响当前 matrix 分支（fail-fast: false），同 shard 的其他用例继续跑。

prepare：失败后 cases 输出为空，execute 整个 matrix 不创建；一个 shard 的所有用例一起卡。

共同点：两种情况都不会发出 started，平台都只能等 3600s。

execute 失败 = 1 个 case；prepare 失败 = 整个 shard。

queued 的准确含义

queued 不是“GitHub 队列里还在排队”。它是平台在 post_repository_dispatch 成功后写入的状态（dispatcher.py:317），语义是 “已交给 GitHub，等待 runner 脚本的 started 回调”。因此 GitHub 上的 job 失败、被取消、甚至 runner 消失，平台都不会自动改写这个状态。

平台 attempt 状态机

只在回调点推进；没有 job 级事件。

pending→ dispatching→ queued→ running→ scoring / uploading→ succeeded
失败分支： failed timeout cancelled artifact_missing

GitHub run / job 状态机

平台并不读取它的 conclusion。

queued→ in_progress→ completed (success / failure / cancelled)

checkout 失败时，这套状态机已经走到 failure；平台那套还停在 queued。两套机器之间没有因果同步。

03

Root cause

四层原因：为什么 checkout 失败 = queued 不结束

把因果链拆成四层：谁在报活、失败点在哪、平台缺哪条通道、最后谁来兜底。四层叠在一起，才是“卡一小时”。

01

started 是平台唯一的“开工信号”

在 handle_started 之前，attempt 没有 started_at、没有 heartbeat_at、没有 runner_id，也没有任何 case 事件。平台无法区分“job 还在排队”“runner 正在克隆”“job 已经失败”——三者看起来完全一样。

handle_started 一次写入 running、started_at、heartbeat_at、runner 绑定和 sequence 0（case_attempts.py:378-430）。在此之前，attempt 对平台来说只是一个已派发的壳。

02

checkout 排在 started 之前

workflow 的步骤顺序是固定的：

Checkout
Materialize and validate the dispatch payload
Execute exactly one case   # 这里才运行 real-task.mjs，started 在里面

checkout 失败，后两步直接 skipped；real-task.mjs 不会启动，started 不会发出。prepare 更严重：checkout 失败 → plan 不执行 → cases 输出为空 → execute 整个 matrix 不会创建。

execute 失败 = 1 个 case；prepare 失败 = 整个 shard。
03

平台没有 job 失败的通道

平台与 GitHub 是“回调驱动”，不是“状态同步”。eval-shard.yml 里没有 if: failure() 的兜底回调；worker 也不轮询 workflow run 的 conclusion。find_workflow_run 只在取消流程里用（reconciler.py:126-168），不用于失败检测。

所以 GitHub 上 job 已经红了，平台侧的 attempt 仍然是 queued——不是平台“选择等待”，而是它根本没有收到任何能改变状态的事件。

04

唯一兜底：3600s 队列超时

for attempt, case, run in rows("dispatching", "queued"):
    if _expired(_phase_marker(attempt), settings.eval_queue_timeout_seconds, now):
        expire(
            ...,
            error_code=lifecycle.QUEUE_TIMEOUT,
            retryable=False,   # 不创建新 attempt
        )

retryable=False 意味着结算时不会创建新 attempt。attempt 和 case 直接进入 timeout（lifecycle.py:223-330）。

纠正 PR 描述

PR 描述写的是“平台只在 3600s 队列超时后才重排”。按当前分支代码，这句话只对了一半：

对的一半是，3600s 内平台确实不会做任何事，因为 queued 只由 started 推进。
不对的一半是，3600s 后不是“重排”，而是 queue_timeout 终结。reaper.py:122-133 把 retryable=False 传给 settle_attempt_failure，attempt 和 case 直接进入 timeout，不会生成新的 attempt。

因此真实影响是：先白等约 48 分钟，再把用例判为 timeout；如果这是最后一个未完成用例，run 还会终结为 partial/failed，连手动重试都会被 run_not_running 拒绝。生产中若确实看到“重排”，需要确认是否走了人工重试、外部脚本或旧版本路径。

Scenarios

什么场景下 checkout 会让用例一直 queued

不是只有“checkout 红”这一种。所有发生在 started 之前的失败，都会长成同一个样子；反过来，不是所有 queued 都是故障。

术语先对齐

如果 UI 显示的是“GitHub job 还在排队”，checkout 不是原因——checkout 只有在 job 被 Runner 领取之后才会执行。这里说的“卡在 queued”是平台 attempt 的状态：job 已经领取、甚至已经失败，平台仍显示 queued。

三看：现场怎么区分“死 queued”和“正常排队”

一看 GitHub run

conclusion 是 failure，且失败步骤是 actions/checkout → 基本可判定为 S1 / S2。

二看 attempt

started_at、heartbeat_at、runner_id 都为空 → 用例从未开始，不是执行慢。

三看队列原因

capacity_waiting / 429 → 合法等待；concurrency_cap → 被 shard 闸门挡住；两者都不是 checkout 故障。

合法的 queued 长什么样

started 返回 429 capacity_waiting 时，real-task.mjs 会保持 attempt 为 queued，并按 5s → 10s → … → 60s 退避重试同一个 event_id，默认最多 1800 秒（real-task.mjs:70, 81-99）。这时 runner 还活着、脚本正在重试；和 checkout 失败的“死 queued”不是一回事。

05

Blast radius

为什么影响不止“晚一小时”

一个 queued 的 attempt 不只是占着一条状态记录。它会占住 shard 闸门、拖住 run 的收敛、影响 spot 容量决策，最后还会把“可重试的启动故障”变成“终态的 timeout”。

5.1 容量闸门按 shard 计数，不按 case 计数

_capacity_decision 用“已经释放过的 shard 数”做闸门，而不是“正在跑的 case 数”。只要 shard 里还有一个 queued，它就一直占着名额。

released_shards = count(distinct shard_id)
    where attempt.status in ("dispatching","queued","leased","running","scoring","uploading")

max_in_flight = max(1, ceil(cap / shard_size))

if released_shards >= max_in_flight:
    return cap, QUEUE_REASON_CONCURRENCY_CAP   # 后续 shard 全部等待

按 ceil(cap / shard_size) 估算；cap 是 effective_concurrency。默认值来自 config.py:101-102；本次生产按每个 run 只有 1 个 execute job 推断为 1 case/shard。

5.2 run 无法收敛，UI 一直显示“排队中”

refresh_run_progress 只有在 queued_count == 0 && running_count == 0 时才结算 run（evaluations.py:930-960）。一个 queued 就足以让 run 停在 running；页面会显示“4/5 完成、1 排队”，而“重试失败用例”按钮不会出现，因为 run 还没结束。

5.3 spot 容量控制器会为“幽灵需求”保留或补机器

_queued_attempts 把 pending / dispatching / queued 都算作需求；gap = queued - idle - starting * slots（capacity_control.py:296-315）。runner 空闲时，缩容的 excess = idle - queued - keep_for_min 会把它留下；runner 已随 job 失败被回收时，控制器还可能补一台 spot 来满足这个“幽灵需求”。两种情况都是空转成本。

5.4 超时之后：不是重排，而是终结

队列超时后 case 变 timeout；如果这是最后一个未完成用例，run 立刻变 partial/failed。retry_case 要求 run.status == "running"（workbench.py:354-370），此时会以 run_not_running 拒绝。若还有其他 shard 在跑，run 仍是 running，才允许人工重试。

最坏的结局

“卡一小时”不是最坏的。最坏的是：一小时后用例被判 timeout、run 终结、不能原地重试，只能新建评测或走内部修复。对 5 用例的复测来说，这等于这次复测白跑。

5.5 与 job timeout 的 3600s 竞态

平台队列时钟从 dispatch 开始，job 时钟从 runner 领取开始，二者都是 3600 秒。pickup 花了约 5 分钟的那次 run，如果 checkout 一直挂到 job 的 60 分钟上限，平台会先超时约 5 分钟；之后即使 job 成功，started 也会因 attempt 已 terminal 被判 stale。这是次要但真实的竞态。

06

Fix assessment

这次修复能解决什么、不能解决什么

这是一次合理的工程止血：不改状态机、风险低、直接覆盖最常见的瞬态故障。但它不是根因修复，不能把 MTTR 从 1 小时降下来。

有效

  • 3 次独立克隆，覆盖 TLS 断连、443 连接超时这类瞬态故障。
  • actions/checkout 自身在单次里还会重试 fetch（本次日志里两次），所以最坏情况下有 3×3 次 fetch 机会。
  • prepare 与 execute 都覆盖；prepare 的保护价值更高（影响整个 shard）。
  • 不改平台状态机，风险低，可先合并止血。

边界

  • 同一网络路径的故障是相关的，3 次不一定独立；持续 10 分钟以上的断网仍会全部失败。
  • 每次 checkout 失败可能耗时 5-7 分钟；3 次会吃掉 job 60 分钟预算的很大一块。
  • 只覆盖 checkout；checkout 之后的 Node / manifest / token 失败，仍然是同样的“无 started → queued”。
  • 平台侧 MTTR 没变：真失败时仍要等 3600 秒。
场景修复前修复后残余风险
单次 TLS 抖动job 失败大概率重试成功连续三次失败仍卡
持续断网 10+ 分钟job 失败仍失败无平台感知，等 3600s
prepare 失败整 shard 卡降低概率其他 prepare 步骤失败仍卡
超时语义timeout未改不是自动重排
可观测性无无仍要等 3600s 才知道
不要把 3 次当成 99.9%

三次尝试走同一条出口链路、同一个 GitHub 端点，故障高度相关；这次日志里 actions/checkout 内部已经重试两次仍失败，就是相关性的一次现场演示。3 次的价值在于覆盖“短时抖动”，不是覆盖“网络不可用”。

07

Recommendations

如果要补根因，按这个顺序做

目标不是“让 checkout 更稳”，而是“job 失败后，平台在分钟级知道并做出正确决策”。前者是概率，后者是 MTTR。

P0

让平台在分钟级感知“job 已失败”

推荐做法：reconciler 对 queued 超过 5-10 分钟的 attempt，先用 find_workflow_run 定位 run，再调用 GitHub GET /actions/runs/{id} 读取 status/conclusion；若 conclusion=failure 且该 attempt 没有 case.started 事件，就用新的 start_failed（可重试）结算，立即重排。

备选：workflow 增加 if: failure() 的失败回调。它最直接，但需要凭据；当前 workflow 测试明确禁止 secrets.，要引入 OIDC 或平台签发的一次性 token，改动更大。

落点：reconciler.py、github_dispatch.py、lifecycle.py。收益：MTTR 从 60 分钟降到 5-10 分钟。

P1

区分“从未开始”和“启动失败”

queue_timeout 目前一刀切 retryable=False；容量等待和基础设施故障被混在一起。建议新增 start_failed 或 checkout_failed 分类，归入 RETRYABLE_FAILURE_CODES；queue_timeout 只保留给“确实一直没轮到”的场景。

落点：lifecycle.py 的失败分类、reaper.py 的结算参数。收益：同类故障可以自动重试，而不是人工介入。

P2

降低对 github.com 冷克隆的依赖

execute 只需要 runner/ 脚本；可以把它们打进 runner 镜像，或像 runner 包一样从平台下载。这样 execute 不再需要 checkout，直接消除这一类失败。prepare 仍可保留 checkout + 重试。

落点：spot cloud-init / runner 包发布链路、workflow 的 execute 步骤。收益：从“重试提高成功率”变成“没有这个失败模式”。

P3

可观测性与容量口径

指标：queued_age_seconds、checkout_failure_total、no_started_total；告警：queued > 10 分钟且无 started。容量控制器应把“超过 N 分钟没有 started 的 queued”视为可疑需求，避免为幽灵 attempt 补机器。UI 增加 “stuck queued” 标记，直接链到 GitHub run。

落点：worker 指标、capacity_control、评测详情页。收益：下次同类故障能在 dashboard 上直接看到。

P4

仓库卫生

删除 76 个 .pyc；补根 .gitignore（__pycache__/、*.pyc）；在 CI 加 git diff --check 或 pre-commit 防回归。

收益：review 噪音从 77 个文件回到 1 个文件。

Review notes

如果我是 reviewer，会提这些

先看改动是否安全，再看它是否解决了描述里的问题，最后看有没有把噪声带进来。这个 PR 在“安全”上没问题，在“描述”和“噪声”上需要返工。

P1

76 个 .pyc 混入 PR

git diff --stat fe21944..HEAD 显示 77 个文件变更、+30/−2；其中 76 个是 __pycache__/*.pyc，真正的代码改动只有 workflow 一个文件。仓库没有根 .gitignore（只有 web/.gitignore），git check-ignore 对 pyc 返回 1。

请求：从 PR 移除这些文件，补 __pycache__/、*.pyc 规则。

P1

“3600s 后重排”与代码不符

PR 描述和 workflow 注释都写着平台会在 3600s 队列超时后 re-queue。按 reaper.py:122-133，实际是 retryable=False 的 timeout 终结，不会创建新 attempt。

请求：改描述与注释，或把“自动重排”真正实现出来；两者不能只做一半。

P2

只覆盖 checkout，不覆盖同类前置失败

Node 缺失、manifest/token 拉取失败、回调网络不可达，都会在 started 之前失败，症状完全相同。这个 PR 只把 checkout 的窗口收窄了。

请求：另开 issue 补“job 失败感知”，不要让它停留在 workflow 重试。

P2

三次重试的时间预算

单次 checkout 失败可能耗时约 7 分钟；3 次约 21 分钟，占 job 60 分钟预算的三分之一。极端情况下会挤压真正的执行时间。

请求：评估是否需要给 checkout step 加 timeout-minutes，或在第 3 次失败时提前给出更明确的诊断。

P3

测试没有钉住重试结构

tests/eval-shard-workflow.test.mjs 断言了 prepare/execute 的结构，但没有断言“恰好 3 个 checkout step”和两个重试条件。未来有人把重试删掉，测试不会红。

请求：加 3 条结构断言（step 数、outcome 条件、retry 2 无 continue-on-error）。

P3

失败后的工作目录清理

第一次 checkout 失败会留下半初始化的 .git；actions/checkout 默认 clean: true 会清理，但建议显式写出，或在注释里说明依赖这个默认值，避免未来改成 clean: false 时踩坑。

请求：显式 clean: true，或补一行说明。

结论

方向正确，建议作为止血合并；合并前先删 pyc、修正“重排”表述，并把平台侧感知作为 follow-up。

否则同类故障只是从“经常发生”变成“偶尔发生”，MTTR 仍是 1 小时。
