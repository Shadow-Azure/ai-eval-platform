# ADR 0002 · 交付流水线的健康信息边界

[English](adr-0002-deployment-health-boundary.en.md) | 中文

- 状态：已接受
- 日期：2026-11-11
- 关联 issue：#146（M5-18 交付流水线页面与受控回滚）
- 决策者：本 issue 实现者；依据 `plans/m1-02-fullstack-design/02-prototype-and-interactions.md`、`09-frontend-implementation.md` 与 `10-deployment-testing-and-review.md`

## 背景

M5-18 把原型的「交付流水线」页面落到 `/deployments`，其中包含环境组件健康摘要。平台已经有一个管理员专用的 `/operations`「运营状态」页，展示数据库容量、表行数、Redis 内存、对象存储桶、Runner 与模型网关等诊断信息。如果两页都完整展示健康信息，会出现两种问题：普通成员能看到的页面被迫提升为管理员页面，或者同一份诊断数据被复制两份、口径逐渐漂移。

## 决策

- `/deployments` 面向所有已登录成员，只展示**部署所需的组件健康摘要**：控制面 API、PostgreSQL、Redis、对象存储与调度 Worker 的状态和一句话摘要；不返回延迟、容量、存储桶名、表行数或任何凭据材料。
- `/operations` 保持平台管理员专用，作为**详细诊断面**：数据库大小/连接数/表清单、Redis 内存与客户端、对象存储桶探活、Runner 与模型网关明细、各服务延迟；它不提供部署回滚入口。
- 部署记录、当前/上一版本、Alembic 版本对照、五阶段时间线与受控回滚只属于 `/deployments`；`/operations` 不重复部署历史。
- 两页都可以展示数据库是否健康，但粒度不同：部署页只回答“这次部署依赖的组件是否正常”，运营页回答“容量、资源和诊断细节是否正常”。
- 回滚只在 `/deployments` 提供，且必须同时满足：平台管理员、显式二次确认、目标为上一成功版本、当前部署与目标的迁移版本都与当前数据库一致；API 写入审计记录后通过 `repository_dispatch` 交给部署工作流执行，API 本身不直接操作主机，也不执行数据库 downgrade。

## 影响

- `backend/app/api/deployments.py` 与会话级依赖提供紧凑健康摘要；`backend/app/api/operations.py` 保持管理员依赖和详细负载不变。
- `web/src/pages/DeploymentsPage.tsx` 展示环境摘要与回滚；`OperationsPage` 继续承载容量与诊断。
- 新增的部署读取接口对普通成员开放，但不扩大任何写权限；回滚写接口仍由 `require_admin` 保护。
- 健康探针失败只让对应组件显示异常，不阻断部署历史与迁移版本读取。

## 未采纳的方案

- **直接复用 `/operations` 响应**：该接口要求管理员，且返回容量、表清单和基础设施细节；给普通成员开放会扩大权限面，裁剪响应又会把两页耦合在同一份 DTO 上。
- **健康信息只留在 `/operations`**：与 M5-18 的验收和原型不一致，普通成员无法判断一次部署依赖的组件是否正常。
- **两页都展示完整健康信息**：重复探针与重复展示会让口径分叉，也增加误把诊断信息暴露给普通成员的风险。
- **API 直接 SSH 到 ECS 执行回滚**：控制面不应持有主机操作通道；沿用部署工作流的 SSH 与状态记录路径，审计和主机操作职责更清晰。
