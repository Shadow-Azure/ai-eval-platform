# 四层叙事写作规范

## feature：这个 PR 实现了什么

**回答三个问题**，顺序固定：

1. 现在用户能做什么（一句话能力描述，动词开头）
2. 之前缺什么 / 为什么值得做（动机，从 issue 与 note 提炼，不抄原文）
3. 影响面（谁会感知到：哪些操作、哪些场景、哪些边界变化）

**通俗性标准**：假设读者不知道任何内部模块名。第一次提到模块/服务/协议时，用括号一句话解释它在本 PR 里的角色。**禁止**出现未解释的缩写。

**禁止**：实现细节（属方案设计与代码地图）、变更过程叙述（"本次重构了…"→ 改成现状式"现在 X 由 Y 负责"）。

## userFlow：用户怎么操作

每一步一行，格式：`在 <入口> <动作> → <系统做什么> → <用户看到什么>`。

- 3-6 步为宜；超过 6 步说明功能该拆页或用子流程图
- 必须包含：主路径、至少一条边界/错误路径（如超限、无权限、能力不足时用户看到什么）
- 步骤之间可插入图（见 diagram-guide）
- 纯开发流程 PR（无用户面变化）写单行：`无用户面变化（<一句原因>）`

**自检**：拿这组步骤给没见过该功能的人，他能照着走一遍。走不通就是写失败了。

## architectural：架构变化

**先分两类，再写**：

- **结构变化**：新增/移动/删除了模块、接口、数据通路、所有权。每条写：变更点 → 现在归谁负责 → 为什么挪（链 Agent Note，不抄全文）。
- **语义变化**：既有结构不动，但行为/边界/时序变了（如缓存策略、错误分类、守卫条件）。每条写：旧语义 → 新语义 → 触发条件。

没有变化就写：`无结构变化；<一句说明为什么这个 PR 不需要动架构>`。**不许空着，不许写"无"就完事**。

**分层建议**：从外到内（用户面边界 → 模块间契约 → 模块内关键机制），每层 1-3 条。跨模块关系变化必须配图。

**图文结合**：`architectural` 正文要与 `architecturalFlowchart` 同构——先沿图讲一条主链路（起点 → 关键分支 → 终点，正文中引用图题），再补图装不下的要点。正文的模块/动作名与图中节点 label 一字不差；图里带标签的分支边必须在正文讲清每个走向的后果。

`architecturalFlowchart.explanation` 是图下的读图入口：先给机制结论，再解释为什么用这条主链、分叉或回边表达它；正文不重复说明，而是继续讲结构变化和取舍。

## design：方案设计说明（可选但强烈建议）

模板（四段，段落标题用 markdown 三级标题）：

### 问题与约束
- 要解决的核心矛盾是什么；硬约束（离线、安全边界、平台、既有契约）列清

### 候选方案
- 2-3 个真实考虑过的方案（从 Agent Note 的被否方案提炼；没有就诚实写"直接方案，未考虑替代"并说明为什么不需要）
- 每个候选一段：怎么做 → 优点 → 代价

### 选型与理由
- 选了哪个、为什么、放弃了什么（这是本节的核心价值）

### 关键权衡与边界
- 明确说清：牺牲了什么换来了什么；已知不处理的情况；后续演进方向（如有）

**写作标准**：让读者读完后能回答"如果我来做，我会做同样的选择吗"。这是检视者判断设计合理性的主要依据。

**图文结合**：每个功能点的叙事先沿该点的 `designFlowcharts` 流程图讲实现链路（引用图题，如"沿图「门禁事实源与自测试」：……"），再展开权衡与边界；术语与图中节点 label 保持一致。

每个 `designFlowcharts[].explanation` 要说明该功能点图的机制结论与画图理由，并和本功能点的实现思路互相呼应；读者应能从图和说明先建立方案骨架，再进入文件映射。

## 通用禁令（四层共用）

- 不写"本次""新增了""原来""之前"——渲染产物是长期页面，不是 PR 描述（diff 语义已在代码地图）
- 不用感叹号、不用营销词（"强大""优雅""完美"）
- 数字带单位；行数引用写"约"，除非来自门禁精确计数
- 中英混排：中文句子内的英文术语两侧加空格

## 落地映射：方案设计 → 变更文件树

方案设计写完后，**必须补一节"落地映射"**（放在 design 字段末尾，标题 `### 落地映射：功能点 → 变更文件`）——它回答检视者接下来的自然问题："这套设计落到了哪些文件上"。

**按功能点逐个小节展开**，每节结构固定：

1. 一段 2-3 句的实现思路，开头引用该功能点的流程图图题：沿图讲这个功能点如何从设计推导出这样的文件划分（让读者看到"图 → 设计 → 代码"的推导链，而不是拿到一堆文件名）
2. 文件树形式的清单（缩进树或列表，按职责聚类、不按字母序；测试文件与实现文件同组出现；纯流程件归并一组放最后）
3. 每个文件跟一句职责：**它在该功能点里承担什么**（入口/状态机/纯函数/渲染/测试），禁止复述文件名本身

```text
<功能点 A：实现思路一段>

src/<模块>/
  ├─ core.ts     状态机与决策逻辑：所有分支判断收敛在这里
  ├─ render.ts   展示层：只消费 core 的结果，不含业务判断
  └─ core.spec.ts 上述分支的逐条验证（与实现同组便于对照）
```

**功能点多时按重要性排序**；检视指引（reviewGuide.order）应与这里的分组顺序呼应——读者先读设计映射，再按 order 下钻，两条线必须对得上。

每个功能点小节在 yaml 里都要配一条对应的 `designFlowcharts` 流程图（feature 名与小节名逐字一致），见 `flowchart-guide.md`。
